## 重要な用語

| 用語 | 意味 |
|:---|:---|
| Active Directory (AD) | Windowsネットワークのユーザー、コンピューター、ルールを保存するMicrosoftのディレクトリサービス |
| ドメイン | ADの管理単位。例: `corp.local`。メンバー全員が一つのアカウントデータベースを共有する |
| ドメインコントローラー (DC) | ADのデータベースを持ち、ログインを確認するサーバー |
| フォレスト | スキーマを共有し、互いに信頼する一つ以上のドメインの集まり |
| OU | 組織単位 (Organizational Unit)。オブジェクトをまとめ、ポリシーを適用するためのフォルダ |
| GPO | グループポリシーオブジェクト。ユーザーやコンピューターに自動で適用される設定の集まり |
| LDAP | ディレクトリの内容を読み書きするためのプロトコル |
| Kerberos | ADの主要なログインプロトコル |
| SID | セキュリティ識別子。アカウントやグループごとの一意のID |
| NTDS.dit | 各ドメインコントローラーにあるADのデータベースファイル |

## 1. Active Directoryが重要な理由

Windowsを使う中規模以上の企業のほとんどは、社員のアカウントをActive Directoryで管理している。一つのADアカウントで、ノートPC、メール、ファイル共有、VPN、多くの社内アプリにログインする。

そのため、ADは攻撃者の主な標的にもなる。攻撃者がDomain Adminのアカウントを手に入れれば、実質的にネットワーク全体を支配できる。大規模なランサムウェア事件の報告書には、ほぼ必ず「攻撃者はDomain Admin権限を取得し、グループポリシー経由でランサムウェアを配布した」という一文がある。

| 職種 | ADを理解すべき理由 |
|:---|:---|
| SOCアナリスト | Windowsのログインや権限に関するアラートの多くはドメインコントローラーから来る |
| ペンテスター | 社内ネットワークのテストはほぼ必ずADにたどり着く |
| インシデント対応者 | ランサムウェアのタイムラインは、たいてい1台のノートPCからドメインコントローラーへ進む |
| システム管理者 | ADの小さな設定ミスがDomain Adminへの道を開くことがある |

## 2. ドメイン、ツリー、フォレスト

```
  Forest: corp.local
  ┌────────────────────────────────────┐
  │             corp.local             │  ← ルートドメイン
  │            /          \            │
  │   jkt.corp.local   osk.corp.local  │  ← 子ドメイン (一つのツリー)
  └────────────────────────────────────┘
                    │ 信頼関係
  ┌────────────────────────────────────┐
  │        Forest: partner.local       │  ← 別のフォレスト
  └────────────────────────────────────┘
```

| 構造 | 説明 |
|:---|:---|
| ドメイン | 一つのアカウントデータベースと一つのDNS名前空間。例: `corp.local` |
| ツリー | 名前が連続する親ドメインと子ドメイン。例: `corp.local`の下の`jkt.corp.local` |
| フォレスト | 一つ以上のツリー。本当のセキュリティ境界はフォレスト |

セキュリティ上の要点: **ドメインはセキュリティ境界ではなく、フォレストが境界である。** 子ドメインの管理者は、フォレスト全体の管理者になれてしまう。二つの事業部門を本当に分離する必要があるなら、別々のフォレストが必要になる。

## 3. ドメインコントローラーと保存しているもの

ドメインコントローラーは、AD DS (Active Directory Domain Services) の役割を持つWindowsサーバーだ。1台が止まってもログインできるよう、通常は2台以上ある。1台での変更はほかのDCに複製される。

DCが持つ主なもの:

| 構成要素 | 場所 | 内容 |
|:---|:---|:---|
| `NTDS.dit` | `C:\Windows\NTDS\` | 全オブジェクトのデータベース。各ユーザーのパスワードハッシュを含む |
| SYSVOL | `C:\Windows\SYSVOL\` | ログオンスクリプトとグループポリシーのファイル。ドメインの全ユーザーが読める |
| DNS | DC上のDNSサービス | コンピューターがDCを見つけるためのレコード |
| KDC | Kerberosサービス | ログイン用のチケットを発行する |

DCから`NTDS.dit`をコピーできる人は、ドメイン内の全ユーザーのパスワードハッシュを手に入れる。だからDCへのログオンとそのバックアップへのアクセスは、厳しく制限しなければならない。

ドメイン参加済みのコンピューターからDCを確認する:

```powershell
nltest /dclist:corp.local         # ドメインコントローラーの一覧
echo %LOGONSERVER%                # 自分のログインを処理したDC (cmdで)
Get-ADDomainController -Filter *  # RSATのActiveDirectoryモジュールが必要
```

## 4. オブジェクト: ユーザー、グループ、コンピューター、OU

ADの中身はすべて、**属性**を持つ**オブジェクト**として保存される。

| オブジェクト | 属性の例 | セキュリティ上の注意 |
|:---|:---|:---|
| ユーザー | `sAMAccountName`, `memberOf`, `pwdLastSet`, `servicePrincipalName` | SPNを持つアカウントは特に注意が必要 |
| グループ | `member`, `groupType` | グループはほかのグループを含められるので、所属が入れ子になる |
| コンピューター | `dNSHostName`, `operatingSystem` | ドメイン参加済みのコンピューターも、それぞれ自分のアカウントとパスワードを持つ |
| OU | `gPLink` | GPOをリンクする場所 |
| GPO | `gPCFileSysPath` | 中身はSYSVOLにある |

オブジェクトの完全な名前は**識別名 (DN)** で書く:

```text
CN=Rina Putri,OU=Finance,OU=Jakarta,DC=corp,DC=local
```

右から読む。ドメイン`corp.local`、OU Jakarta、OU Finance、そしてユーザーRina Putri。

PowerShellでオブジェクトを見る (RSATのActiveDirectoryモジュール):

```powershell
Get-ADUser rina -Properties memberOf, pwdLastSet, lastLogonDate
Get-ADGroupMember "Domain Admins" -Recursive    # 入れ子のグループのメンバーも含む
Get-ADComputer -Filter * -Properties operatingSystem | Select Name, operatingSystem
```

ドメインのユーザーなら誰でも、LDAPでADの大部分を読める。これは設計どおりだが、普通のアカウントを一つ盗んだだけの攻撃者でも、ドメイン全体の地図を作れるということでもある。

## 5. 知っておくべきグループ

| グループ | 権限 | 悪用されると危険な理由 |
|:---|:---|:---|
| Domain Admins | ドメインの完全な管理者 | 攻撃者の主な標的 |
| Enterprise Admins | フォレスト全体の管理者 | ルートドメインにのみ存在する |
| Administrators (組み込み) | ドメインコントローラーの管理者 | Domain Adminと同等 |
| Account Operators | ほとんどのアカウントを作成・変更できる | 忘れられがちで、Domain Adminへの道として知られている |
| Backup Operators | `NTDS.dit`を含むDC上のファイルをバックアップできる | バックアップは全ハッシュのコピーそのもの |
| Server Operators | DCにログオンし、サービスを変更できる | DCのサービスを変えることは、SYSTEMとしてコードを実行することに等しい |
| DnsAdmins | DC上のDNSを管理する | DNSサービスにDLLを読み込ませる悪用例があった |
| Group Policy Creator Owners | 新しいGPOを作成できる | GPOは多くのコンピューターでスクリプトを実行できる |
| Protected Users | 管理者グループではなく、保護用のグループ | メンバーはNTLMやRC4を使えなくなる |

目安: 上のグループのメンバーは最小限にし、定期的に見直すこと。

```powershell
"Domain Admins","Enterprise Admins","Administrators","Account Operators","Backup Operators","Server Operators" |
  ForEach-Object { "== $_"; Get-ADGroupMember $_ -Recursive | Select -Expand SamAccountName }
```

## 6. グループポリシー

グループポリシーは、多くのコンピューターに設定を一度に適用する。パスワードポリシー、ファイアウォール、ログオンスクリプト、ソフトウェアの配布などだ。

```
GPO "ノートPCポリシー"  ──リンク──►  OU=Laptops  ──含む──►  50台のコンピューター
```

適用の順序 (最後に適用されたものが勝つ): **ローカル → サイト → ドメイン → 親OU → 子OU**。略してLSDOU。

| コマンド | 目的 |
|:---|:---|
| `gpupdate /force` | コンピューターに最新のポリシーを取得させる |
| `gpresult /r` | このユーザーとコンピューターに適用されているGPOを表示する |
| `gpresult /h report.html` | HTML形式の詳細レポート |

セキュリティの観点で覚えておくべき2点:

1. **多くのコンピューターにリンクされたGPOを編集できる人は、そのすべてでコードを実行できる。** GPOの編集権限は、それらのコンピューターの管理者権限と同等だ。
2. **SYSVOLはドメインの全ユーザーが読める。** かつてのグループポリシー基本設定 (Group Policy Preferences) という機能は、パスワードをXMLファイル (`cpassword`) としてSYSVOLに保存しており、その鍵はMicrosoft自身が公開していた。この機能はパッチMS14-025で塞がれたが、古いファイルが残っていることがある。SYSVOLで`cpassword`を探すのは、監査で最初に行う確認の一つだ。

```powershell
# 監査の確認: cpasswordを含む古いファイルが残っていないか
findstr /S /I cpassword \\corp.local\SYSVOL\corp.local\Policies\*.xml
```

## 7. ADが使うプロトコル

| プロトコル | ポート | 用途 |
|:---|:---|:---|
| DNS | 53 | コンピューターは`_ldap._tcp.dc._msdcs.corp.local`のようなSRVレコードでDCを見つける |
| Kerberos | 88 | ログインとアクセス用チケット |
| LDAP / LDAPS | 389 / 636 | ディレクトリの読み書き |
| グローバルカタログ | 3268 / 3269 | フォレスト全体のオブジェクト検索 |
| SMB | 445 | SYSVOLへのアクセス、ファイル共有、リモート管理 |
| RPC | 135 + 動的ポート | 複製と多くの管理機能 |
| NTLM | (SMBやHTTPなどの内部) | 古いログインプロトコル。今も予備として有効になっている |

DNSが重要な理由: DNSが間違っていると、コンピューターはDCを見つけられず、ログインに失敗する。DNSとADの関係は[LC-041](../../networking/ja/DNS%20%26%20Domain%20Name%20System%20Security.md)で先に扱っている。

```powershell
nslookup -type=SRV _ldap._tcp.dc._msdcs.corp.local
```

## 8. ドメイン間の信頼関係

信頼関係 (トラスト) があると、あるドメインのユーザーが別のドメインのリソースにアクセスできる。

| トラストの種類 | 方向 | 例 |
|:---|:---|:---|
| 親子 | 双方向、推移的、自動 | `jkt.corp.local` ↔ `corp.local` |
| フォレストトラスト | 一方向または双方向 | 買収後の`corp.local` ↔ `partner.local` |
| 外部トラスト | 一方向または双方向、非推移的 | 別フォレストの古いドメインへ |

トラストの方向は混乱しやすい。ドメインAがドメインBを**信頼する**なら、**Bのユーザーが**Aのリソースにアクセスできる。アクセスはトラストの向きと逆に流れる。

何年も前に、すでに終わったプロジェクトのために作られたトラストは忘れられがちで、侵入口になる。トラストの棚卸しはAD監査の一部だ。

```powershell
Get-ADTrust -Filter * | Select Name, Direction, TrustType, ForestTransitive
nltest /domain_trusts
```

## 9. 演習

### Task 1: 概念

1. ADの本当のセキュリティ境界はドメインとフォレストのどちらか。
2. ドメインコントローラー上で全ユーザーのパスワードハッシュを持っているファイルは何か。
3. グループポリシーが適用される順序を、最初から最後まで答えよ。
4. ドメインAがドメインBを信頼している。どのドメインのユーザーが、どのドメインのリソースにアクセスできるか。

<details><summary>解答</summary>

1. フォレスト。子ドメインの管理者がフォレスト全体の管理者になれてしまう。
2. `C:\Windows\NTDS\`の`NTDS.dit`。
3. ローカル、サイト、ドメイン、親OU、子OU (LSDOU)。設定が衝突した場合は最後のものが勝つ。
4. ドメインBのユーザーが、ドメインAのリソースにアクセスできる。

</details>

### Task 2: 識別名を読む

```text
CN=svc_backup,OU=Service Accounts,OU=IT,DC=jkt,DC=corp,DC=local
```

1. このオブジェクトはどのドメインにあるか。
2. どのOUにあるか。
3. 名前から判断して、このアカウントを詳しく確認すべき理由は何か。

<details><summary>解答</summary>

1. `jkt.corp.local`。`corp.local`の子ドメイン。
2. `IT` OUの中の`Service Accounts` OU。
3. バックアップ用のサービスアカウントだから。この種のアカウントは、古いパスワードが変更されないまま使われていることが多く、SPNを持つことも多い。さらにBackup Operatorsに所属していれば`NTDS.dit`をバックアップできる。

</details>

### Task 3: ラボでの小さな監査

自分が所有するADラボで次を実行し、結果を記録する:

1. Domain Adminsのメンバーは誰か。入れ子のグループのメンバーも含めること。
2. `pwdLastSet`が365日以上前のユーザーアカウントはいくつあるか。
3. SYSVOLに`cpassword`を含む`.xml`ファイルはあるか。

<details><summary>コマンドの例</summary>

```powershell
Get-ADGroupMember "Domain Admins" -Recursive | Select SamAccountName
Get-ADUser -Filter * -Properties pwdLastSet |
  Where-Object { [datetime]::FromFileTime($_.pwdLastSet) -lt (Get-Date).AddDays(-365) } |
  Select SamAccountName
findstr /S /I cpassword \\corp.local\SYSVOL\corp.local\Policies\*.xml
```

</details>
