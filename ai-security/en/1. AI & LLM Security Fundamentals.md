## Key terms

| Term | Meaning |
|:---|:---|
| LLM | Large Language Model: a model that generates text from input text |
| Prompt | The input text to the model. The system prompt holds the developer's instructions; the user prompt comes from the user |
| Prompt injection | Text that makes the model follow instructions that did not come from the application's developer |
| RAG | Retrieval-Augmented Generation: the application fetches relevant documents and includes them in the prompt |
| Embedding / vector database | A numeric representation of text, used to find similar documents |
| Agent | An LLM application that can call tools, such as sending email or running queries |
| Tool / function calling | The way a model asks the application to run a specific function with specific arguments |
| Guardrail | A check around the model, such as input and output filters |
| AI red teaming | Structured testing of an AI application to find unsafe behavior |
| Model card | A document describing a model's origin, intended use, and limitations |

## 1. Why AI applications need special attention

Ordinary applications draw a firm line between **code** (instructions) and **data**. SQL injection ([LC-047](../../web/Vulnerabilities/en/1.%20SQL%20Injection%20%28SQLi%29.md)) happens precisely when that line leaks, and the fix is clear: parameterized queries.

In an LLM application, instructions and data are both natural-language text, and everything goes into one prompt. The model has no reliable way to tell "this is an instruction from the developer" from "this is the content of an email that happens to contain a command". There is still no equivalent of parameterized queries for LLMs.

So the right approach is to **limit the impact**: assume the model can be steered, then design the application so that being steered is not dangerous.

| LLM property | Security consequence |
|:---|:---|
| Instructions and data are mixed | Prompt injection cannot be fully prevented |
| Results vary between runs | Hard to test in the usual way; needs repeated evaluation |
| Can sound confident while wrong | Output must not be trusted blindly for important decisions |
| Often connected to data and tools | A model's mistake can become a real action |

## 2. Anatomy of an LLM application

```
 User ──► Application ──────────────► LLM (API or local model)
             │  ▲                       │
             │  └── answer ─────────────┘
             │
             ├──► Vector DB / documents (RAG)
             └──► Tools: email, database, calendar, shell, internal APIs
```

Every arrow is a trust boundary. For each arrow, ask:

1. What data crosses here, and who may see it?
2. Who can influence its content?
3. If the content is malicious, what is the worst outcome?

Threat modeling with STRIDE from [LC-078](../../devsecops/en/1.%20DevSecOps%20Fundamentals.md) still applies here.

## 3. The OWASP Top 10 for LLM applications

OWASP publishes a list of risks specific to LLM applications. The 2025 version:

| ID | Risk | The core problem |
|:---|:---|:---|
| LLM01 | Prompt Injection | Text from users or documents steers the model's behavior |
| LLM02 | Sensitive Information Disclosure | The model leaks personal data, secrets, or other users' data |
| LLM03 | Supply Chain | Untrusted third-party models, datasets, or libraries |
| LLM04 | Data and Model Poisoning | Training or fine-tuning data is deliberately corrupted |
| LLM05 | Improper Output Handling | Model output is used directly in HTML, SQL, or a shell |
| LLM06 | Excessive Agency | An agent has too many permissions or too much freedom to act |
| LLM07 | System Prompt Leakage | The system prompt contains secrets that can be read |
| LLM08 | Vector and Embedding Weaknesses | Leaks or manipulation in a RAG system |
| LLM09 | Misinformation | Wrong but convincing answers are used to make decisions |
| LLM10 | Unbounded Consumption | Unlimited use that burns through budget or capacity |

The following sections cover the ones that come up most in practice.

## 4. Prompt injection

| Type | Source of the malicious text | Example situation |
|:---|:---|:---|
| Direct | The user types it into the chatbot | A user tries to make a customer-service chatbot ignore its rules |
| Indirect | Content the model reads: email, web pages, PDFs, search results | An email assistant summarizes an incoming email that quietly contains commands aimed at the model |

Indirect prompt injection is the more dangerous kind. A legitimate user can become the victim without noticing, because the commands were planted by a third party whose text the model reads.

Since it cannot be fully prevented, the defense is layered and focused on impact:

| Control | Explanation |
|:---|:---|
| No secrets in the system prompt | Assume the system prompt can be read (LLM07). API keys and access rules do not belong there |
| Authorization in the application, not the prompt | "Do not show other users' data" must be enforced by code and the database, not by a sentence in the prompt |
| Separate untrusted content | Clearly mark which parts are instructions and which are external content, for example with special delimiters. This reduces the risk but does not remove it |
| Limit capabilities while handling external content | When summarizing outside email, do not give the model a tool that sends email |
| Human approval for important actions | Sending money, deleting data, or sending email outside the company needs user confirmation |
| Input and output filters | Classifiers that detect injection patterns help but can be bypassed. Never rely on them alone |
| Logging and monitoring | Keep prompts and tool calls so odd events can be investigated |

## 5. Model output is untrusted input

LLM output should be treated like input from an anonymous user. If it goes straight into HTML, a query, or a shell command, old vulnerabilities come back.

| Output used in | Vulnerability | Control |
|:---|:---|:---|
| A web page | XSS ([LC-048](../../web/Vulnerabilities/en/2.%20Cross-Site%20Scripting%20%28XSS%29.md)) | HTML escaping, Markdown sanitization, Content Security Policy |
| A database query | SQL injection | Parameterized queries, a read-only database account |
| A shell command | Command injection ([LC-051](../../web/Vulnerabilities/en/5.%20Command%20Injection%20%26%20File%20Inclusion%20%28LFI%20%26%20RFI%29.md)) | Do not run shell commands from model output. If you must, use an allowlist and a sandbox |
| A URL the server fetches | SSRF ([LC-050](../../web/Vulnerabilities/en/4.%20Server-Side%20Request%20Forgery%20%28SSRF%29.md)) | Domain allowlist, block internal addresses |
| Image links in Markdown | Data leaking through image URLs | Restrict which domains images may load from |

Rendering a model's answer safely in a Python application:

```python
import bleach, markdown

def render_answer(model_text: str) -> str:
    html = markdown.markdown(model_text)
    return bleach.clean(
        html,
        tags={"p", "ul", "ol", "li", "code", "pre", "strong", "em", "a"},
        attributes={"a": ["href"]},
        protocols={"https"},
    )
```

## 6. Agents and excessive permissions

An agent that can call tools turns a text mistake into a real action. OWASP names three sources of the problem: too much **functionality**, too many **permissions**, and too much **autonomy without approval**.

| Source | Bad example | Safer |
|:---|:---|:---|
| Excessive functionality | A calendar-reading agent is given a `run_shell` tool | Only the tools it needs: `read_calendar` |
| Excessive permissions | The database tool uses an admin account | A read-only account that can see specific tables only |
| Excessive autonomy | The agent can email anyone without confirmation | The agent writes a draft; it is sent after the user presses "Send" |

The basic pattern in code:

```python
ALLOWED_TOOLS = {"search_documents", "read_calendar", "draft_email"}
NEEDS_CONFIRMATION = {"draft_email"}

def run_tool(name, args, user):
    if name not in ALLOWED_TOOLS:
        raise PermissionError(f"tool {name} is not allowed")
    if name in NEEDS_CONFIRMATION and not ask_confirmation(user, name, args):
        return "cancelled by the user"
    # the tool runs with this user's rights, not an admin service account
    return TOOLS[name](args, credentials=user.scoped_token)
```

The principle is the same as least privilege in cloud IAM ([LC-077](../../cloud-security/en/1.%20Cloud%20Security%20Fundamentals.md)): if the agent is steered, the damage is limited to what that user was allowed to do anyway.

## 7. Data: leakage, RAG, and access rights

### Data sent to the model provider

When you use a third-party model API, prompts and documents are sent to their servers.

| Question | Why it matters |
|:---|:---|
| Is the data used to train models? | Many providers offer business plans that do not train on customer data. Check the contract |
| How long is the data kept? | Ties into data protection obligations ([LC-079](../../grc/en/1.%20GRC%20Fundamentals.md)) |
| In which country is it processed? | Cross-border data transfer rules may apply |
| Are employees pasting confidential data into public chatbots? | You need a clear AI use policy and a safe, approved alternative |

### RAG and access rights

A common mistake: every company document goes into one vector database, and the chatbot answers anyone using any document. The result is that an intern can ask about the directors' salaries.

```
Wrong:  question ──► search ALL documents ──► LLM ──► answer
Right:  question ──► search ONLY documents this user may read ──► LLM ──► answer
```

Access rights must be checked **before** documents are retrieved, by storing permission information (such as which groups may read it) with every document chunk in the vector database, then filtering by the user's identity.

Documents added to RAG can also carry indirect prompt injection. Limit who may add documents to the knowledge base.

## 8. The model supply chain

| Risk | Example | Control |
|:---|:---|:---|
| Model files that run code | PyTorch's pickle format (`.pt`, `.bin`) can execute Python code when loaded | Use the `safetensors` format, load with `torch.load(..., weights_only=True)` |
| Models from unclear sources | A model on a public hub imitating a popular model's name | Download from the official organization, read the model card, pin a specific version or commit |
| Poisoned datasets | Fine-tuning data with harmful examples slipped in | Clear data provenance, review samples, evaluate before and after fine-tuning |
| Libraries and plugins | Vulnerable dependencies in AI frameworks | SCA scanning as in LC-078 |

```python
from safetensors.torch import load_file
weights = load_file("model.safetensors")     # tensor data only, no code is executed
```

## 9. Cost and availability

Every call to a large model costs money. Without limits, one user or one script can burn a month's budget overnight (LLM10).

| Control | Example |
|:---|:---|
| Per-user rate limits | At most 30 requests per minute |
| Input and output length limits | `max_tokens` on every call, truncate overly long documents |
| Agent step limits | The agent stops after 10 tool calls in one task |
| Cost alerts | A notification when daily usage passes a threshold |
| Authentication | AI endpoints are not open to the public without login |

## 10. AI governance

The GRC frameworks from LC-079 apply to AI too, along with a few AI-specific ones:

| Framework | Contents |
|:---|:---|
| NIST AI RMF 1.0 | Four functions: Govern, Map, Measure, Manage. Free |
| ISO/IEC 42001:2023 | An AI management system standard, certifiable like ISO 27001 |
| EU AI Act | A risk-based EU regulation. Some uses are banned; high-risk uses carry strict obligations |
| MITRE ATLAS | A catalog of attack tactics and techniques against AI systems, similar to ATT&CK ([LC-074](../../blue-team/en/3.%20Threat%20Hunting%20%26%20Detection%20Engineering%20%28Sigma%2C%20YARA%2C%20ATT%26CK%29.md)) |

Practical steps for an organization:

1. **Inventory**: which AI applications and services are in use, including ones employees use without official approval.
2. **An AI use policy**: what data may and may not be put into AI tools.
3. **Risk assessment** for each AI application, like any other system.
4. **Humans stay accountable** for important decisions made with AI assistance.

## 11. Testing your own AI applications

Testing an AI application differs from an ordinary pentest because model results vary. One failed attempt does not prove the application is safe.

| Approach | Explanation |
|:---|:---|
| Automated evaluation | A set of test cases run repeatedly whenever the prompt or model changes |
| Structured red teaming | A team tries to provoke unsafe behavior according to the risk list, with permission and a clear scope |
| Architecture review | Check what does not depend on the model: RAG access rights, tool permissions, output escaping, rate limits |

Open-source tools for testing applications you own:

| Tool | Purpose |
|:---|:---|
| promptfoo | Runs test suites and security checks against LLM applications; fits into CI |
| garak (NVIDIA) | A scanner that runs a range of probes against a model |
| PyRIT (Microsoft) | A framework for automating AI red teaming |

The architecture review usually gives the most value for the least effort. If RAG access rights are right and tools are restricted, even a prompt injection that gets through has little impact.

## 12. Practice

### Task 1: concepts

1. Why can't prompt injection be solved the way SQL injection is?
2. What is the difference between direct and indirect prompt injection?
3. Why must API keys not be placed in the system prompt?
4. Which model file format is safer than pickle?

<details><summary>Answer key</summary>

1. In an LLM, instructions and data are both text in a single prompt, and there is no mechanism like parameterized queries to separate them reliably.
2. Direct: the user types the malicious text themselves. Indirect: the malicious text sits in content the model reads, such as email, web pages, or documents.
3. The system prompt must be assumed to be readable by users (LLM07).
4. `safetensors`.

</details>

### Task 2: map the risks

A company builds an internal email assistant:

- It reads every employee's incoming email and writes a daily summary.
- It can send email on an employee's behalf without confirmation.
- Summaries are displayed as HTML on an internal dashboard.
- It uses one service account that can read every employee's inbox.
- There is no limit on the number of requests.

Map each point to the most fitting OWASP LLM risk and name one control for each.

<details><summary>Example answer</summary>

| Point | Risk | Control |
|:---|:---|:---|
| Reads email from outside | LLM01 indirect prompt injection | Disable the send-email tool while summarizing external email |
| Sends email without confirmation | LLM06 excessive agency | The agent only drafts; the user presses send |
| Summary rendered as HTML | LLM05 improper output handling | Sanitize Markdown/HTML, CSP |
| One service account for every inbox | LLM06 and LLM02 | Per-user tokens that can only read that user's own inbox |
| No request limit | LLM10 unbounded consumption | Rate limits and cost alerts |

</details>

### Task 3: review a RAG chatbot design

The HR team wants a chatbot that answers employee questions from HR documents: leave policy, the employee handbook, and per-employee salary data. Write at least five security controls that must be in place before it launches.

<details><summary>Example answer</summary>

1. Salary data does not go into the general RAG index. If needed, fetch it through an API that returns only the logged-in employee's own data.
2. Every document chunk in the vector database carries a permission label, and searches are filtered by the user's identity.
3. Only the HR team may add or change source documents.
4. Answers are rendered with HTML sanitization.
5. Login is required, there are per-user rate limits, and questions are logged for audit with a retention period that matches the data policy.
6. Answers cite their source documents so they can be checked, with a note that official decisions still come from HR.
7. The contract with the model provider ensures data is not used for training.

</details>
