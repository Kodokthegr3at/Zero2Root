## Istilah penting

| Istilah | Artinya |
|:---|:---|
| LLM | Large Language Model: model yang menghasilkan teks berdasarkan teks masukan |
| Prompt | Teks masukan ke model. System prompt berisi instruksi dari pembuat aplikasi, user prompt dari pengguna |
| Prompt injection | Teks yang membuat model mengikuti instruksi yang bukan dari pembuat aplikasi |
| RAG | Retrieval-Augmented Generation: aplikasi mengambil dokumen yang relevan lalu menyertakannya ke prompt |
| Embedding / vector database | Representasi angka dari teks, dipakai untuk mencari dokumen yang mirip |
| Agent | Aplikasi LLM yang bisa memanggil tool, misalnya mengirim email atau menjalankan query |
| Tool / function calling | Cara model meminta aplikasi menjalankan fungsi tertentu dengan argumen tertentu |
| Guardrail | Pemeriksaan di sekitar model, misalnya filter input dan output |
| Red teaming AI | Menguji aplikasi AI secara terstruktur untuk mencari perilaku yang tidak aman |
| Model card | Dokumen yang menjelaskan asal, kegunaan, dan keterbatasan sebuah model |

## 1. Kenapa aplikasi AI butuh perhatian khusus

Aplikasi biasa memisahkan dengan tegas antara **kode** (instruksi) dan **data**. SQL injection ([LC-047](../../web/Vulnerabilities/id/1.%20SQL%20Injection%20%28SQLi%29.md)) terjadi justru ketika batas itu bocor, dan solusinya jelas: parameterized query.

Di aplikasi LLM, instruksi dan data sama-sama berupa teks bahasa manusia, dan semuanya masuk ke satu prompt. Model tidak punya cara yang andal untuk membedakan "ini instruksi dari developer" dan "ini isi email yang kebetulan berisi kalimat perintah". Sampai sekarang belum ada padanan parameterized query untuk LLM.

Akibatnya, pendekatan yang benar adalah **membatasi dampak**: anggap model bisa saja dibelokkan, lalu rancang aplikasi supaya hal itu tidak berbahaya.

| Sifat LLM | Akibat untuk keamanan |
|:---|:---|
| Instruksi dan data bercampur | Prompt injection tidak bisa dicegah sepenuhnya |
| Hasilnya tidak selalu sama | Sulit diuji dengan cara biasa, perlu evaluasi berulang |
| Bisa terdengar yakin walau salah | Keluaran tidak boleh langsung dipercaya untuk keputusan penting |
| Sering terhubung ke data dan tool | Kesalahan model bisa berubah menjadi aksi nyata |

## 2. Anatomi aplikasi LLM

```
 Pengguna ──► Aplikasi ──────────────► LLM (API atau model lokal)
                │  ▲                     │
                │  └── jawaban ──────────┘
                │
                ├──► Vector DB / dokumen (RAG)
                └──► Tool: email, database, kalender, shell, API internal
```

Setiap panah adalah batas kepercayaan. Pertanyaan yang perlu dijawab untuk setiap panah:

1. Data apa yang lewat di sini, dan siapa yang boleh melihatnya?
2. Siapa yang bisa memengaruhi isinya?
3. Kalau isinya berbahaya, apa akibat terburuknya?

Threat modeling dengan STRIDE dari [LC-078](../../devsecops/id/1.%20DevSecOps%20Fundamentals.md) tetap berlaku di sini.

## 3. OWASP Top 10 untuk aplikasi LLM

OWASP menerbitkan daftar risiko khusus aplikasi LLM. Versi 2025:

| ID | Risiko | Inti masalah |
|:---|:---|:---|
| LLM01 | Prompt Injection | Teks dari pengguna atau dokumen membelokkan perilaku model |
| LLM02 | Sensitive Information Disclosure | Model membocorkan data pribadi, rahasia, atau data pengguna lain |
| LLM03 | Supply Chain | Model, dataset, atau library dari pihak ketiga yang tidak tepercaya |
| LLM04 | Data and Model Poisoning | Data latih atau data fine-tuning sengaja dirusak |
| LLM05 | Improper Output Handling | Keluaran model langsung dipakai di HTML, SQL, atau shell |
| LLM06 | Excessive Agency | Agent punya izin atau kebebasan bertindak terlalu luas |
| LLM07 | System Prompt Leakage | System prompt berisi rahasia yang bisa terbaca |
| LLM08 | Vector and Embedding Weaknesses | Kebocoran atau manipulasi di sistem RAG |
| LLM09 | Misinformation | Jawaban yang salah tapi meyakinkan dipakai untuk keputusan |
| LLM10 | Unbounded Consumption | Pemakaian tanpa batas yang menghabiskan biaya atau kapasitas |

Bagian-bagian berikut membahas yang paling sering muncul dalam praktik.

## 4. Prompt injection

| Jenis | Sumber teks berbahaya | Contoh situasi |
|:---|:---|:---|
| Langsung (direct) | Pengguna mengetik sendiri ke chatbot | Pengguna mencoba membuat chatbot layanan pelanggan mengabaikan aturannya |
| Tidak langsung (indirect) | Konten yang dibaca model: email, halaman web, PDF, hasil pencarian | Asisten email merangkum email masuk yang diam-diam berisi kalimat perintah untuk model |

Prompt injection tidak langsung lebih berbahaya. Pengguna yang sah bisa menjadi korban tanpa menyadarinya, karena yang menyisipkan perintah adalah pihak ketiga yang tulisannya dibaca oleh model.

Karena tidak bisa dicegah sepenuhnya, pertahanannya berlapis dan berfokus pada dampak:

| Kontrol | Penjelasan |
|:---|:---|
| Jangan taruh rahasia di system prompt | Anggap system prompt bisa terbaca (LLM07). API key dan aturan akses tidak boleh ada di sana |
| Otorisasi di aplikasi, bukan di prompt | "Jangan tampilkan data user lain" harus ditegakkan oleh kode dan database, bukan oleh kalimat di prompt |
| Pisahkan konten tidak tepercaya | Tandai jelas mana instruksi dan mana konten eksternal, misalnya dengan pembatas khusus. Ini mengurangi, tapi tidak menghilangkan, risiko |
| Batasi kemampuan saat memproses konten eksternal | Saat merangkum email dari luar, jangan berikan tool untuk mengirim email |
| Persetujuan manusia untuk aksi penting | Mengirim uang, menghapus data, atau mengirim email keluar butuh konfirmasi pengguna |
| Filter input dan output | Classifier untuk mendeteksi pola injection membantu, tapi bisa dilewati. Jangan jadikan satu-satunya pertahanan |
| Log dan monitoring | Simpan prompt dan pemanggilan tool supaya kejadian aneh bisa diselidiki |

## 5. Output model adalah input yang tidak tepercaya

Keluaran LLM harus diperlakukan sama seperti input dari pengguna anonim. Kalau langsung dimasukkan ke HTML, query, atau perintah shell, celah lama muncul kembali.

| Keluaran dipakai di | Celah | Kontrol |
|:---|:---|:---|
| Halaman web | XSS ([LC-048](../../web/Vulnerabilities/id/2.%20Cross-Site%20Scripting%20%28XSS%29.md)) | Escape HTML, sanitasi Markdown, Content Security Policy |
| Query database | SQL injection | Parameterized query, akun database read-only |
| Perintah shell | Command injection ([LC-051](../../web/Vulnerabilities/id/5.%20Command%20Injection%20%26%20File%20Inclusion%20%28LFI%20%26%20RFI%29.md)) | Jangan jalankan shell dari keluaran model. Kalau terpaksa, pakai allowlist dan sandbox |
| URL yang diambil server | SSRF ([LC-050](../../web/Vulnerabilities/id/4.%20Server-Side%20Request%20Forgery%20%28SSRF%29.md)) | Allowlist domain, blokir alamat internal |
| Link gambar di Markdown | Kebocoran data lewat URL gambar | Batasi domain gambar yang boleh dimuat |

Contoh menampilkan jawaban model dengan aman di aplikasi Python:

```python
import bleach, markdown

def render_jawaban(teks_model: str) -> str:
    html = markdown.markdown(teks_model)
    return bleach.clean(
        html,
        tags={"p", "ul", "ol", "li", "code", "pre", "strong", "em", "a"},
        attributes={"a": ["href"]},
        protocols={"https"},
    )
```

## 6. Agent dan izin yang berlebihan

Agent yang bisa memanggil tool mengubah kesalahan teks menjadi aksi nyata. OWASP menyebut tiga sumber masalah: terlalu banyak **fungsi**, terlalu banyak **izin**, dan terlalu banyak **kebebasan bertindak tanpa persetujuan**.

| Sumber masalah | Contoh buruk | Lebih aman |
|:---|:---|:---|
| Fungsi berlebihan | Agent pembaca kalender diberi tool `run_shell` | Hanya tool yang dibutuhkan: `read_calendar` |
| Izin berlebihan | Tool database memakai akun admin | Akun read-only yang hanya bisa melihat tabel tertentu |
| Otonomi berlebihan | Agent bisa mengirim email ke siapa saja tanpa konfirmasi | Draf dibuat agent, dikirim setelah pengguna menekan "Kirim" |

Pola dasar di kode:

```python
TOOLS_DIIZINKAN = {"cari_dokumen", "baca_kalender", "buat_draf_email"}
BUTUH_KONFIRMASI = {"buat_draf_email"}

def jalankan_tool(nama, argumen, user):
    if nama not in TOOLS_DIIZINKAN:
        raise PermissionError(f"tool {nama} tidak diizinkan")
    if nama in BUTUH_KONFIRMASI and not minta_konfirmasi(user, nama, argumen):
        return "dibatalkan oleh pengguna"
    # tool berjalan dengan hak akses milik user ini, bukan akun layanan admin
    return TOOLS[nama](argumen, credentials=user.token_terbatas)
```

Prinsipnya sama dengan least privilege di IAM cloud ([LC-077](../../cloud-security/id/1.%20Cloud%20Security%20Fundamentals.md)): kalau agent dibelokkan, kerusakannya terbatas pada apa yang memang boleh dilakukan pengguna itu.

## 7. Data: kebocoran, RAG, dan hak akses

### Data yang dikirim ke penyedia model

Saat memakai API model dari pihak ketiga, prompt dan dokumen dikirim ke server mereka.

| Pertanyaan | Kenapa penting |
|:---|:---|
| Apakah data dipakai untuk melatih model? | Banyak penyedia punya opsi bisnis yang tidak memakai data pelanggan untuk pelatihan. Periksa kontraknya |
| Berapa lama data disimpan? | Berkaitan dengan kewajiban hukum perlindungan data ([LC-079](../../grc/id/1.%20GRC%20Fundamentals.md)) |
| Di negara mana data diproses? | Bisa terkena aturan transfer data lintas negara |
| Apakah karyawan menempelkan data rahasia ke chatbot publik? | Perlu kebijakan penggunaan AI yang jelas dan alternatif resmi yang aman |

### RAG dan hak akses

Kesalahan yang sering terjadi: semua dokumen perusahaan dimasukkan ke satu vector database, lalu chatbot menjawab siapa saja dengan dokumen apa saja. Akibatnya staf magang bisa bertanya tentang gaji direksi.

```
Salah:  pertanyaan ──► cari di SEMUA dokumen ──► LLM ──► jawaban
Benar:  pertanyaan ──► cari HANYA di dokumen yang boleh dibaca user ini ──► LLM ──► jawaban
```

Hak akses harus diperiksa **sebelum** dokumen diambil, dengan menyimpan informasi izin (misalnya grup yang boleh membaca) bersama setiap potongan dokumen di vector database, lalu memfilter berdasarkan identitas pengguna.

Dokumen yang dimasukkan ke RAG juga bisa menjadi jalan prompt injection tidak langsung. Batasi siapa yang boleh menambahkan dokumen ke sumber pengetahuan.

## 8. Supply chain model

| Risiko | Contoh | Kontrol |
|:---|:---|:---|
| File model yang menjalankan kode | Format pickle di PyTorch (`.pt`, `.bin`) bisa menjalankan kode Python saat dimuat | Pakai format `safetensors`, muat dengan `torch.load(..., weights_only=True)` |
| Model dari sumber tidak jelas | Model yang meniru nama model populer di hub publik | Ambil dari organisasi resmi, periksa model card, kunci ke versi atau commit tertentu |
| Dataset yang diracuni | Data fine-tuning yang disisipi contoh berbahaya | Asal-usul data jelas, tinjau sampel, evaluasi sebelum dan sesudah fine-tuning |
| Library dan plugin | Dependency rentan di framework AI | Pemindaian SCA seperti di LC-078 |

```python
from safetensors.torch import load_file
bobot = load_file("model.safetensors")      # hanya data tensor, tidak ada kode yang dijalankan
```

## 9. Biaya dan ketersediaan

Setiap panggilan ke model besar memakan biaya. Tanpa batas, satu pengguna atau satu skrip bisa menghabiskan anggaran bulanan dalam semalam (LLM10).

| Kontrol | Contoh |
|:---|:---|
| Rate limit per pengguna | Maksimal 30 permintaan per menit |
| Batas panjang input dan output | `max_tokens` pada setiap panggilan, potong dokumen yang terlalu panjang |
| Batas langkah agent | Agent berhenti setelah 10 pemanggilan tool dalam satu tugas |
| Alert biaya | Notifikasi kalau pemakaian harian melewati ambang |
| Autentikasi | Endpoint AI tidak terbuka untuk publik tanpa login |

## 10. Tata kelola AI

Kerangka GRC dari LC-079 juga berlaku untuk AI, dengan beberapa kerangka khusus:

| Kerangka | Isi |
|:---|:---|
| NIST AI RMF 1.0 | Empat fungsi: Govern, Map, Measure, Manage. Gratis |
| ISO/IEC 42001:2023 | Standar sistem manajemen AI, bisa disertifikasi seperti ISO 27001 |
| EU AI Act | Regulasi Uni Eropa berbasis tingkat risiko. Beberapa penggunaan dilarang, penggunaan berisiko tinggi punya kewajiban ketat |
| MITRE ATLAS | Katalog taktik dan teknik serangan terhadap sistem AI, mirip ATT&CK ([LC-074](../../blue-team/id/3.%20Threat%20Hunting%20%26%20Detection%20Engineering%20%28Sigma%2C%20YARA%2C%20ATT%26CK%29.md)) |

Langkah praktis untuk organisasi:

1. **Inventaris**: aplikasi dan layanan AI apa saja yang dipakai, termasuk yang dipakai karyawan tanpa izin resmi.
2. **Kebijakan penggunaan AI**: data apa yang boleh dan tidak boleh dimasukkan ke tool AI.
3. **Penilaian risiko** untuk setiap aplikasi AI, sama seperti sistem lain.
4. **Manusia tetap bertanggung jawab** atas keputusan penting yang dibantu AI.

## 11. Menguji aplikasi AI milik sendiri

Pengujian aplikasi AI berbeda dari pentest biasa karena hasil model tidak selalu sama. Satu percobaan yang gagal tidak membuktikan aplikasinya aman.

| Pendekatan | Penjelasan |
|:---|:---|
| Evaluasi otomatis | Kumpulan kasus uji yang dijalankan berulang setiap kali prompt atau model berubah |
| Red teaming terstruktur | Tim mencoba memancing perilaku yang tidak aman sesuai daftar risiko, dengan izin dan ruang lingkup yang jelas |
| Uji arsitektur | Periksa hal yang tidak bergantung pada model: hak akses RAG, izin tool, escape output, rate limit |

Tool open source yang bisa dipakai untuk menguji aplikasi milik sendiri:

| Tool | Fungsi |
|:---|:---|
| promptfoo | Menjalankan kumpulan kasus uji dan pemeriksaan keamanan terhadap aplikasi LLM, cocok dimasukkan ke CI |
| garak (NVIDIA) | Pemindai yang menjalankan berbagai probe terhadap model |
| PyRIT (Microsoft) | Kerangka untuk mengotomatiskan red teaming AI |

Uji arsitektur biasanya memberi hasil paling besar dengan usaha paling kecil. Kalau hak akses RAG benar dan tool dibatasi, prompt injection yang lolos pun dampaknya kecil.

## 12. Latihan

### Task 1: konsep

1. Kenapa prompt injection tidak bisa diselesaikan seperti SQL injection?
2. Apa beda prompt injection langsung dan tidak langsung?
3. Kenapa API key tidak boleh ditaruh di system prompt?
4. Format file model apa yang lebih aman daripada pickle?

<details><summary>Kunci jawaban</summary>

1. Di LLM, instruksi dan data sama-sama berupa teks dalam satu prompt, dan belum ada mekanisme seperti parameterized query yang memisahkannya secara andal.
2. Langsung: pengguna sendiri yang mengetik teks berbahaya. Tidak langsung: teks berbahaya ada di konten yang dibaca model, seperti email, web, atau dokumen.
3. System prompt harus dianggap bisa terbaca oleh pengguna (LLM07).
4. `safetensors`.

</details>

### Task 2: petakan risikonya

Sebuah perusahaan membuat asisten email internal:

- Asisten membaca semua email masuk karyawan dan membuat ringkasan harian.
- Asisten bisa mengirim email atas nama karyawan tanpa konfirmasi.
- Ringkasan ditampilkan sebagai HTML di dashboard internal.
- Asisten memakai satu akun layanan yang bisa membaca kotak masuk semua karyawan.
- Tidak ada batas jumlah permintaan.

Petakan setiap poin ke risiko OWASP LLM yang paling sesuai, lalu sebutkan satu kontrol untuk masing-masing.

<details><summary>Contoh jawaban</summary>

| Poin | Risiko | Kontrol |
|:---|:---|:---|
| Membaca email dari luar | LLM01 prompt injection tidak langsung | Saat merangkum email eksternal, matikan tool pengiriman email |
| Mengirim email tanpa konfirmasi | LLM06 excessive agency | Agent hanya membuat draf, pengguna yang menekan kirim |
| Ringkasan sebagai HTML | LLM05 improper output handling | Sanitasi Markdown/HTML, CSP |
| Satu akun layanan untuk semua kotak masuk | LLM06 dan LLM02 | Token per pengguna yang hanya bisa membaca kotak masuk miliknya |
| Tanpa batas permintaan | LLM10 unbounded consumption | Rate limit dan alert biaya |

</details>

### Task 3: tinjau desain chatbot RAG

Tim HR ingin chatbot yang menjawab pertanyaan karyawan dari dokumen HR: kebijakan cuti, panduan karyawan, dan data gaji per karyawan. Tulis minimal lima kontrol keamanan sebelum chatbot ini boleh diluncurkan.

<details><summary>Contoh jawaban</summary>

1. Data gaji tidak dimasukkan ke RAG umum. Kalau memang dibutuhkan, ambil lewat API yang hanya mengembalikan data milik karyawan yang login.
2. Setiap potongan dokumen di vector database diberi label izin, dan pencarian difilter sesuai identitas pengguna.
3. Hanya tim HR yang boleh menambahkan atau mengubah dokumen sumber.
4. Jawaban dirender dengan sanitasi HTML.
5. Login wajib, rate limit per pengguna, dan log pertanyaan untuk audit dengan masa simpan yang sesuai kebijakan data.
6. Jawaban menyertakan sumber dokumen supaya bisa dicek, dan ada catatan bahwa keputusan resmi tetap dari HR.
7. Kontrak dengan penyedia model memastikan data tidak dipakai untuk pelatihan.

</details>
