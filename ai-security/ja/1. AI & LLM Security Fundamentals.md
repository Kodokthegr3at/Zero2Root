## 重要な用語

| 用語 | 意味 |
|:---|:---|
| LLM | 大規模言語モデル。入力されたテキストから文章を生成するモデル |
| プロンプト | モデルへの入力テキスト。システムプロンプトは開発者の指示、ユーザープロンプトは利用者の入力 |
| プロンプトインジェクション | アプリケーションの開発者からではない指示にモデルを従わせるテキスト |
| RAG | 検索拡張生成。アプリケーションが関連文書を取得し、プロンプトに含める |
| 埋め込み / ベクトルデータベース | テキストを数値で表したもの。似た文書を探すのに使う |
| エージェント | メール送信やクエリ実行などのツールを呼び出せるLLMアプリケーション |
| ツール / 関数呼び出し | モデルが、特定の関数を特定の引数で実行するようアプリケーションに頼むしくみ |
| ガードレール | 入力や出力のフィルターなど、モデルの周りに置くチェック |
| AIレッドチーミング | 安全でない振る舞いを見つけるための、AIアプリケーションの体系的な検査 |
| モデルカード | モデルの出所、想定用途、限界を説明する文書 |

## 1. AIアプリケーションに特別な注意が必要な理由

普通のアプリケーションは、**コード** (命令) と**データ**をはっきり分けている。SQLインジェクション ([LC-047](../../web/Vulnerabilities/ja/1.%20SQL%20Injection%20%28SQLi%29.md)) は、まさにその境界が破れたときに起き、対策もはっきりしている。パラメータ化クエリだ。

LLMアプリケーションでは、命令もデータもどちらも自然言語のテキストで、すべてが一つのプロンプトに入る。モデルには「これは開発者からの指示」と「これはたまたま命令文を含んでいるメールの本文」を確実に区別する方法がない。LLMには、パラメータ化クエリに相当するものがまだない。

そのため正しい考え方は、**影響を限定する**ことだ。モデルは誘導されうると考え、誘導されても危険にならないようにアプリケーションを設計する。

| LLMの性質 | セキュリティ上の影響 |
|:---|:---|
| 命令とデータが混ざる | プロンプトインジェクションを完全には防げない |
| 実行ごとに結果が変わる | 通常の方法では検査しにくく、繰り返しの評価が必要 |
| 間違っていても自信ありげに答える | 重要な判断に出力をそのまま信用してはならない |
| データやツールにつながっていることが多い | モデルの誤りが実際の操作になりうる |

## 2. LLMアプリケーションの構造

| 経路 | 流れるもの |
|:---|:---|
| 利用者 → アプリケーション | 質問や指示 |
| アプリケーション → LLM (APIまたはローカルモデル) | システムプロンプト、利用者の入力、取得した文書 |
| LLM → アプリケーション | 回答やツール呼び出しの要求 |
| アプリケーション → ベクトルDB / 文書 (RAG) | 検索の問い合わせと、取得された文書 |
| アプリケーション → ツール | メール、データベース、カレンダー、シェル、社内APIの操作 |

それぞれの経路が信頼境界だ。経路ごとに次を考える:

1. ここを通るデータは何で、誰が見てよいのか。
2. その内容に影響を与えられるのは誰か。
3. 内容が悪意のあるものだった場合、最悪どうなるか。

[LC-078](../../devsecops/ja/1.%20DevSecOps%20Fundamentals.md)のSTRIDEによる脅威モデリングは、ここでもそのまま使える。

## 3. LLMアプリケーションのOWASP Top 10

OWASPはLLMアプリケーションに特有のリスクの一覧を公開している。2025年版:

| ID | リスク | 問題の核心 |
|:---|:---|:---|
| LLM01 | Prompt Injection | 利用者や文書のテキストがモデルの振る舞いを誘導する |
| LLM02 | Sensitive Information Disclosure | モデルが個人情報、秘密、ほかの利用者のデータを漏らす |
| LLM03 | Supply Chain | 信頼できない第三者のモデル、データセット、ライブラリ |
| LLM04 | Data and Model Poisoning | 学習データやファインチューニング用データが意図的に汚染される |
| LLM05 | Improper Output Handling | モデルの出力がそのままHTML、SQL、シェルで使われる |
| LLM06 | Excessive Agency | エージェントの権限や行動の自由が広すぎる |
| LLM07 | System Prompt Leakage | システムプロンプトに読み取られうる秘密が含まれている |
| LLM08 | Vector and Embedding Weaknesses | RAGのしくみでの漏えいや改ざん |
| LLM09 | Misinformation | 間違っているがもっともらしい回答が判断に使われる |
| LLM10 | Unbounded Consumption | 制限のない利用で予算やキャパシティを使い果たす |

以下の節では、実務でよく問題になるものを扱う。

## 4. プロンプトインジェクション

| 種類 | 悪意のあるテキストの出どころ | 状況の例 |
|:---|:---|:---|
| 直接 | 利用者がチャットボットに自分で入力する | 利用者が顧客対応のチャットボットにルールを無視させようとする |
| 間接 | モデルが読むコンテンツ: メール、Webページ、PDF、検索結果 | メールアシスタントが要約した受信メールに、モデル向けの命令文がひそかに含まれている |

危険なのは間接的なプロンプトインジェクションのほうだ。命令文を仕込んだのはモデルが読む文章を書いた第三者なので、正当な利用者が気付かないまま被害者になりうる。

完全には防げないので、防御は多層にし、影響に焦点を当てる:

| 対策 | 説明 |
|:---|:---|
| システムプロンプトに秘密を置かない | システムプロンプトは読まれうると考える (LLM07)。APIキーやアクセスのルールを置く場所ではない |
| 認可はプロンプトではなくアプリケーションで | 「ほかの利用者のデータを表示しない」は、プロンプトの一文ではなく、コードとデータベースで強制する |
| 信頼できないコンテンツを分ける | 専用の区切りなどで、どこが命令でどこが外部コンテンツかを明示する。リスクは下がるが、なくなりはしない |
| 外部コンテンツを扱う間は機能を絞る | 外部のメールを要約するときは、メール送信のツールを渡さない |
| 重要な操作には人の承認を | 送金、データの削除、社外へのメール送信には利用者の確認を必須にする |
| 入力と出力のフィルター | インジェクションのパターンを検知する分類器は役に立つが、すり抜けられる。これだけに頼らない |
| ログと監視 | プロンプトとツール呼び出しを記録し、不審な事象を調査できるようにする |

## 5. モデルの出力は信頼できない入力

LLMの出力は、匿名の利用者からの入力と同じように扱う。そのままHTML、クエリ、シェルコマンドに入れれば、古い脆弱性がよみがえる。

| 出力の使い道 | 脆弱性 | 対策 |
|:---|:---|:---|
| Webページ | XSS ([LC-048](../../web/Vulnerabilities/ja/2.%20Cross-Site%20Scripting%20%28XSS%29.md)) | HTMLのエスケープ、Markdownのサニタイズ、Content Security Policy |
| データベースのクエリ | SQLインジェクション | パラメータ化クエリ、読み取り専用のデータベースアカウント |
| シェルコマンド | コマンドインジェクション ([LC-051](../../web/Vulnerabilities/ja/5.%20Command%20Injection%20%26%20File%20Inclusion%20%28LFI%20%26%20RFI%29.md)) | モデルの出力からシェルを実行しない。どうしても必要なら許可リストとサンドボックス |
| サーバーが取得するURL | SSRF ([LC-050](../../web/Vulnerabilities/ja/4.%20Server-Side%20Request%20Forgery%20%28SSRF%29.md)) | ドメインの許可リスト、内部アドレスのブロック |
| Markdownの画像リンク | 画像URL経由のデータ漏えい | 画像を読み込めるドメインを制限する |

Pythonアプリケーションでモデルの回答を安全に表示する:

```python
import bleach, markdown

def render_answer(model_text: str) -> str:
    html = markdown.markdown(model_text)
    return bleach.clean(
        html,
        tags={"p", "ul", "ol", "li", "code", "pre", "strong", "em", "a"},
        attributes={"a": ["href"]},
        protocols={"https"},
    )
```

## 6. エージェントと過剰な権限

ツールを呼べるエージェントは、テキストの誤りを実際の操作に変えてしまう。OWASPは問題の原因として、**機能**が多すぎること、**権限**が多すぎること、**承認なしの自律性**が大きすぎることの三つを挙げている。

| 原因 | 悪い例 | より安全な例 |
|:---|:---|:---|
| 過剰な機能 | カレンダーを読むエージェントに`run_shell`ツールを渡す | 必要なツールだけ: `read_calendar` |
| 過剰な権限 | データベースのツールが管理者アカウントを使う | 特定のテーブルだけを読める読み取り専用アカウント |
| 過剰な自律性 | エージェントが確認なしに誰にでもメールを送れる | エージェントは下書きを作り、利用者が「送信」を押してから送る |

コードでの基本的な形:

```python
ALLOWED_TOOLS = {"search_documents", "read_calendar", "draft_email"}
NEEDS_CONFIRMATION = {"draft_email"}

def run_tool(name, args, user):
    if name not in ALLOWED_TOOLS:
        raise PermissionError(f"tool {name} is not allowed")
    if name in NEEDS_CONFIRMATION and not ask_confirmation(user, name, args):
        return "cancelled by the user"
    # ツールは管理者のサービスアカウントではなく、この利用者の権限で動く
    return TOOLS[name](args, credentials=user.scoped_token)
```

考え方はクラウドIAMの最小権限 ([LC-077](../../cloud-security/ja/1.%20Cloud%20Security%20Fundamentals.md)) と同じだ。エージェントが誘導されても、被害はその利用者にもともと許されていた範囲にとどまる。

## 7. データ: 漏えい、RAG、アクセス権

### モデル事業者に送られるデータ

第三者のモデルAPIを使うと、プロンプトと文書は事業者のサーバーに送られる。

| 確認すること | 重要な理由 |
|:---|:---|
| データはモデルの学習に使われるか | 多くの事業者には、顧客のデータで学習しない法人向けプランがある。契約を確認する |
| データはどれくらいの期間保存されるか | 個人情報保護の義務 ([LC-079](../../grc/ja/1.%20GRC%20Fundamentals.md)) に関わる |
| どの国で処理されるか | 越境移転の規則が適用されうる |
| 社員が公開チャットボットに機密データを貼り付けていないか | 明確なAI利用ポリシーと、安全で公認の代替手段が必要 |

### RAGとアクセス権

よくある失敗: 社内の文書をすべて一つのベクトルデータベースに入れ、チャットボットが誰にでもどの文書でも使って答えてしまう。その結果、インターンが役員の給与について質問できてしまう。

| | 流れ |
|:---|:---|
| 誤り | 質問 → **すべての**文書を検索 → LLM → 回答 |
| 正しい | 質問 → **この利用者が読んでよい文書だけ**を検索 → LLM → 回答 |

アクセス権は文書を取得する**前に**確認する。ベクトルデータベースの各チャンクに権限の情報 (読めるグループなど) を一緒に保存し、利用者のIDで絞り込む。

RAGに追加された文書も、間接的なプロンプトインジェクションの経路になりうる。ナレッジベースに文書を追加できる人を限定すること。

## 8. モデルのサプライチェーン

| リスク | 例 | 対策 |
|:---|:---|:---|
| コードを実行するモデルファイル | PyTorchのpickle形式 (`.pt`、`.bin`) は読み込み時にPythonコードを実行できる | `safetensors`形式を使い、`torch.load(..., weights_only=True)`で読み込む |
| 出所の不明なモデル | 公開ハブ上で人気モデルの名前をまねたモデル | 公式の組織から取得し、モデルカードを読み、特定のバージョンかコミットに固定する |
| 汚染されたデータセット | 有害な例を紛れ込ませたファインチューニング用データ | データの出所を明確にし、サンプルを確認し、ファインチューニングの前後で評価する |
| ライブラリとプラグイン | AIフレームワークの脆弱な依存関係 | LC-078と同様のSCAスキャン |

```python
from safetensors.torch import load_file
weights = load_file("model.safetensors")     # テンソルのデータだけで、コードは実行されない
```

## 9. コストと可用性

大きなモデルの呼び出しには、毎回お金がかかる。制限がなければ、一人の利用者や一つのスクリプトが一晩で1か月分の予算を使い果たしかねない (LLM10)。

| 対策 | 例 |
|:---|:---|
| 利用者ごとのレート制限 | 1分あたり最大30リクエスト |
| 入力と出力の長さの制限 | すべての呼び出しに`max_tokens`、長すぎる文書は切り詰める |
| エージェントのステップ数の制限 | 1つのタスクでツール呼び出しが10回に達したら止まる |
| コストのアラート | 1日の利用量がしきい値を超えたら通知 |
| 認証 | AIのエンドポイントをログインなしで公開しない |

## 10. AIガバナンス

LC-079のGRCのフレームワークはAIにも当てはまる。それに加えて、AI専用のものがいくつかある:

| フレームワーク | 内容 |
|:---|:---|
| NIST AI RMF 1.0 | Govern、Map、Measure、Manageの四つの機能。無料 |
| ISO/IEC 42001:2023 | AIマネジメントシステムの標準。ISO 27001と同様に認証を取得できる |
| EU AI法 (EU AI Act) | リスクに基づくEUの規則。禁止される用途があり、高リスクの用途には厳しい義務がある |
| MITRE ATLAS | AIシステムに対する攻撃の戦術と技術のカタログ。ATT&CK ([LC-074](../../blue-team/ja/3.%20Threat%20Hunting%20%26%20Detection%20Engineering%20%28Sigma%2C%20YARA%2C%20ATT%26CK%29.md)) に似ている |

組織での実践的な手順:

1. **棚卸し**: 使われているAIアプリケーションとサービスを把握する。社員が正式な承認なしに使っているものも含める。
2. **AI利用ポリシー**: AIツールに入れてよいデータと、入れてはいけないデータを決める。
3. ほかのシステムと同じように、AIアプリケーションごとに**リスク評価**を行う。
4. AIの支援を受けた重要な判断でも、**責任は人が持つ**。

## 11. 自分のAIアプリケーションを検査する

モデルの結果は毎回変わるので、AIアプリケーションの検査は通常のペネトレーションテストとは異なる。一度の試行が失敗しても、アプリケーションが安全だとは言えない。

| 手法 | 説明 |
|:---|:---|
| 自動評価 | プロンプトやモデルを変えるたびに繰り返し実行するテストケースの集まり |
| 体系的なレッドチーミング | 許可と明確な範囲のもとで、リスクの一覧に沿って安全でない振る舞いを引き出そうとする |
| アーキテクチャのレビュー | RAGのアクセス権、ツールの権限、出力のエスケープ、レート制限など、モデルに依存しない部分を確認する |

自分のアプリケーションを検査するためのオープンソースのツール:

| ツール | 目的 |
|:---|:---|
| promptfoo | LLMアプリケーションに対してテストとセキュリティチェックを実行する。CIに組み込みやすい |
| garak (NVIDIA) | さまざまなプローブをモデルに対して実行するスキャナー |
| PyRIT (Microsoft) | AIレッドチーミングを自動化するフレームワーク |

最小の労力で最大の効果が出やすいのは、アーキテクチャのレビューだ。RAGのアクセス権が正しく、ツールが制限されていれば、すり抜けたプロンプトインジェクションでも影響は小さい。

## 12. 演習

### Task 1: 概念

1. プロンプトインジェクションをSQLインジェクションと同じ方法で解決できないのはなぜか。
2. 直接と間接のプロンプトインジェクションの違いは何か。
3. APIキーをシステムプロンプトに置いてはいけないのはなぜか。
4. pickleより安全なモデルファイルの形式は何か。

<details><summary>解答</summary>

1. LLMでは命令とデータがどちらも一つのプロンプト内のテキストであり、パラメータ化クエリのように両者を確実に分けるしくみがないから。
2. 直接: 利用者自身が悪意のあるテキストを入力する。間接: メール、Web、文書など、モデルが読むコンテンツに悪意のあるテキストが含まれている。
3. システムプロンプトは利用者に読まれうると考えるべきだから (LLM07)。
4. `safetensors`。

</details>

### Task 2: リスクを対応付ける

ある会社が社内向けのメールアシスタントを作った:

- 全社員の受信メールを読み、毎日の要約を作る。
- 確認なしに社員の名前でメールを送れる。
- 要約は社内ダッシュボードにHTMLとして表示される。
- 全社員の受信箱を読める一つのサービスアカウントを使っている。
- リクエスト数に制限がない。

各項目を最も当てはまるOWASP LLMのリスクに対応付け、それぞれ対策を一つ挙げよ。

<details><summary>解答例</summary>

| 項目 | リスク | 対策 |
|:---|:---|:---|
| 社外からのメールを読む | LLM01 間接的なプロンプトインジェクション | 外部のメールを要約する間はメール送信ツールを無効にする |
| 確認なしにメールを送る | LLM06 過剰なエージェンシー | エージェントは下書きだけを作り、利用者が送信を押す |
| 要約をHTMLで表示 | LLM05 不適切な出力処理 | Markdown/HTMLのサニタイズ、CSP |
| 全受信箱を読める一つのサービスアカウント | LLM06とLLM02 | 本人の受信箱だけを読める利用者ごとのトークン |
| リクエスト数の制限がない | LLM10 無制限の消費 | レート制限とコストのアラート |

</details>

### Task 3: RAGチャットボットの設計レビュー

人事チームが、人事の文書 (休暇の規程、社員ハンドブック、社員ごとの給与データ) をもとに社員の質問に答えるチャットボットを作りたいと考えている。公開前に必要なセキュリティ対策を少なくとも五つ書け。

<details><summary>解答例</summary>

1. 給与データは共通のRAGに入れない。必要なら、ログインしている社員本人のデータだけを返すAPIで取得する。
2. ベクトルデータベースの各チャンクに権限のラベルを付け、利用者のIDで検索を絞り込む。
3. 元の文書を追加・変更できるのは人事チームだけにする。

5. ログインを必須にし、利用者ごとのレート制限を設け、データのポリシーに合った保存期間で質問を監査用に記録する。
6. 回答に出典の文書を示して確認できるようにし、正式な判断は人事が行うと明記する。
7. モデル事業者との契約で、データが学習に使われないことを確認する。
