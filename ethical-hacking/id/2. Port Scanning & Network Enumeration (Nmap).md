## 1. Scanning sebagai Inventaris (Jaringan Berizin Saja)

Port scanning dalam konteks profesional adalah pengukuran permukaan jaringan: host yang hidup, port yang listening, dan layanan yang diiklankan. Kegiatan ini hanya dilakukan pada:

- Infrastruktur milik sendiri
- Lab CTF / VM yang Anda kontrol
- Engagement dengan RoE tertulis

Inventaris berguna kalau berhasil menemukan port yang benar-benar terbuka, dengan sedikit false positive dan sedikit layanan yang terlewat.

Catatan ini menjelaskan mekanika protokol dan artefak yang terlihat oleh defender. Ini bukan buku resep evasion untuk jaringan pihak ketiga.

## 2. TCP Three-Way Handshake (Mekanika)

```
Client                                Server
  │  SYN (seq=x)                        │
  │────────────────────────────────────>│
  │  SYN-ACK (seq=y, ack=x+1)           │
  │<────────────────────────────────────│
  │  ACK (ack=y+1)                      │
  │────────────────────────────────────>│
  │         ESTABLISHED                 │
```

Transisi state (disederhanakan):

```text
server:  LISTEN  --SYN-->  SYN-RCVD  --ACK-->  ESTABLISHED
```

```text
client:  CLOSED  --SYN-->  SYN-SENT  --SYN-ACK-->  ESTABLISHED
```

### Intuisi respons port

| Yang terlihat oleh pengamat | Makna umum |
|:---|:---|
| SYN-ACK | Sesuatu menerima SYN (kandidat open) |
| RST | Ditolak secara aktif / closed |
| Diam / drop | Filtered, packet loss, atau stealth ACL |

Firewall yang drop dan yang reject menghasilkan jejak berbeda, baik di sisi klien maupun di log keamanan. Perbedaan ini penting bagi blue team.

## 3. SYN Scan vs Connect Scan (Pengetahuan Protokol)

### Connect scan (konsep `-sT`)
Stack OS menyelesaikan handshake penuh lalu menutup koneksi. Terlihat seperti koneksi aplikasi yang singkat.

Karena handshake-nya diselesaikan penuh, connect scan lebih mahal dan tercatat sebagai koneksi sungguhan di target.

### SYN scan (konsep `-sS`)
Pengirim mengamati SYN-ACK lalu biasanya mengirim RST, tanpa menyelesaikan sesi aplikasi. Ini tetap merupakan paket kontrol TCP yang sangat terlihat oleh NIDS modern.

```
SYN scan sketch (conceptual):
  Scanner --SYN--> Target
  Scanner <--SYN-ACK-- Target   ⇒ infer "open"
  Scanner --RST--> Target       ⇒ tear down early
```

Secara historis SYN scan disebut "half-open". Itu tidak berarti tidak terlihat. IDS modern mengorelasikan SYN flood, fan-out scan, dan handshake yang tidak lengkap.

SYN scan disebut "setengah terbuka" walau tetap bukan berarti tidak terdeteksi. Handshake yang tidak lengkap menjadi bahan deteksi.

| Properti | Connect | SYN (konsep) |
|:---|:---|:---|
| Menyelesaikan handshake | Ya | Sering tidak |
| Butuh raw socket / privilege | Biasanya tidak | Sering ya |
| Log lapisan aplikasi | Lebih mungkin | Lebih ke network IDS |
| Stealth vs NIDS modern | Rendah | Tetap rendah jika berisik |

## 4. UDP, ICMP & Ambiguitas

UDP tidak memiliki handshake. Inferensi "open" bersifat statistik:

```text
ada balasan datagram    → kemungkinan terbuka
ICMP port unreachable   → kemungkinan tertutup
tidak ada jawaban       → open|filtered (tidak bisa dipastikan)
```

Rate-limiting ICMP di router meningkatkan ambiguitas. Defender sebaiknya mendokumentasikan kebijakan ICMP yang diharapkan agar SOC tidak salah membaca hasil scan.

## 5. Flag Nmap Umum untuk Inventaris Jaringan Sendiri

Gunakan hanya pada scope yang berizin. Contoh di bawah adalah inventaris operasional, bukan playbook serangan.

| Flag / opsi | Peran dalam inventaris |
|:---|:---|
| `-sn` | Host discovery tanpa port scan |
| `-sV` | Probe versi/layanan (lebih berisik) |
| `-O` | Heuristik OS fingerprint (tidak andal sendirian) |
| `-p` / `-p-` | Kontrol set port |
| `-T3` / `-T2` | Timing template (lebih rendah = lebih lembut) |
| `-oA basename` | Simpan format normal + XML + grepable |
| `--reason` | Alasan Nmap mengklasifikasikan suatu state |

```bash
# ── Authorized lab / own subnet inventory examples ───────────
# Replace CIDR with YOUR documented scope only.

nmap -sn 192.0.2.0/24 -oA lab_hosts
nmap -sV -p 22,80,443,3389 192.0.2.10 -oA lab_svc --reason
nmap -sU --top-ports 20 192.0.2.10 -oA lab_udp   # slow; expect ambiguity
```

`-A` (agresif) menggabungkan banyak probe sekaligus. Berguna di lab, tapi berisiko di produksi tanpa jendela pemeliharaan.

Utamakan daftar port yang ditargetkan berdasarkan CMDB dibandingkan scan full-range yang membabi buta pada segmen OT/ICS yang rapuh.

## 6. Bagaimana Defender Mendeteksi Scan

### Sumber telemetri
- Counter accept/deny di firewall
- Signature Zeek/Suricata untuk sweep horizontal/vertikal
- NetFlow / IPFIX: fan-out dari satu sumber ke banyak port/host
- Host agent: lonjakan koneksi TCP yang tidak lengkap

### Fitur deteksi sederhana

Scan mudah dikenali kalau satu sumber menyentuh banyak port atau banyak host dalam waktu singkat, atau meninggalkan banyak handshake TCP yang tidak selesai. Aturan deteksi biasanya menimbang ketiga sinyal ini bersama-sama.

Ambang batas bersifat spesifik per lingkungan. Sesuaikan terhadap scanner admin yang dikenal (jendela Nessus, dan sejenisnya) untuk mengurangi false positive.

```
         many ports
Single IP ──────────────► many hosts   = classic sweep pattern
              │
              ▼
     SOC alert / rate-limit / tarpit policy
```

Membagikan kalender jendela vulnerability scan yang sah ke tim terkait dapat mengurangi noise alert.

## 7. Hardening Jaringan Terhadap Scanning yang Tidak Diinginkan

| Kontrol | Efek |
|:---|:---|
| Default-deny inbound | Perkecil eksposur listening |
| Segregasi / mikrosegmentasi | Batasi nilai fan-out lateral |
| SYN cookies / tuning backlog | Ketahanan terhadap SYN flood |
| Allowlist geo / ASN (bila relevan) | Kurangi noise internet |
| Minimisasi banner | Kurangi intel gratis dari `-sV` |
| Canary port / honeyport | Alert dengan keyakinan tinggi |
| Kontrol egress | Host yang sudah dikompromikan bisa scan lebih sedikit |

### Perspektif Stallings
Kerahasiaan dan integritas layanan dimulai dari mengurangi listener yang tidak perlu. Scanning adalah cara attacker (dan auditor) menemukan listener tersebut, sehingga menutupnya adalah pertahanan utama.

### Trade-off filter vs reject

| Kebijakan | Sudut pandang attacker | Operasional defender |
|:---|:---|:---|
| REJECT (RST/ICMP) | Pemetaan lebih cepat | Log lebih jelas |
| DROP | Lebih lambat / ambigu | Troubleshooting lebih sulit |

Pilih kebijakan ini secara sadar per zona (DMZ vs internal).

## 8. Checklist Defensif & Lab

```text
[ ] Written authorization / own lab confirmed
[ ] Change window notified for production inventory
[ ] Output saved (-oA) with date in filename
[ ] Timing tempered on sensitive segments
[ ] Results diffed against last CMDB export
[ ] Unexpected listeners ticketed for closure
[ ] SOC allowlisted or informed for scheduled scans
[ ] No scan of third-party SaaS without their consent
```

### Menginterpretasikan hasil untuk hardening

| Temuan | Tindakan |
|:---|:---|
| RDP/SSH tak terduga di internet | Pindahkan ke belakang VPN / bastion |
| Dev tools di VLAN produksi | Relokasi jalur jaringan |
| Banyak port obscure yang filtered | Verifikasi maksud ACL |
| String versi yang usang | Jalur patch |

## Catatan Keamanan

| Risiko | Penyebab | Mitigasi |
|:---|:---|:---|
| DoS tidak sengaja | Timing agresif / rentang besar | `-T2`, `-p` yang sempit, rate limit |
| Risiko hukum | Scanning tanpa otorisasi | RoE / bukti kepemilikan |
| Blind spot | Hanya DROP tanpa sensor internal | Telemetri jaringan internal |
| Alert fatigue | Vulnerability scanner tanpa pemberitahuan | Kalender scan bersama |
| Terlalu percaya OS detect | Noise pada fingerprint | Korelasikan dengan agent CMDB |
