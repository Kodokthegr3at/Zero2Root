## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| ペネトレーションテスト | 本物の攻撃者より先に弱点を見つける、認可された模擬攻撃 |
| スコープ | テストを許された、正確なシステムと行為 |
| Rules of Engagement(RoE) | スコープ、時期、制限を定めた署名済みの合意 |
| 偵察(reconnaissance) | 標的についての情報収集 |

| OSINT | 公開情報源からのインテリジェンス |
| 方法論 | 繰り返せて文書化された、作業の進め方 |
| 修正(remediation) | レポートが勧める修正 — 本当の目的 |

## 1. 方法論が必要な理由

枠組みのないペネトレーションテストは、簡単に場当たり的なハッキングに変わってしまう。スコープが曖昧になり、運用上のリスクが高まり、行動につながらない報告書しか残らない。PTES、OSSTMM、NIST SP 800-115といった方法論は、次の4点を要求する。

- あらゆる活動の前に書面による認可を得ること
- 技術的な境界を明確にすること（IP、ドメイン、実施時間帯、禁止技術）
- 監査可能な文書化を行うこと
- 「シェルを取ること」自体ではなく、修復を最終目標とすること

ペネトレーションテストに価値があるのは、スコープが明確で、証拠がしっかりしていて、顧客がレポートを使って実際に修正できるときだ。

認可されたテストは、制御されたリスク活動である。方法論は依頼者・テスター・第三者のすべてを守る。The Hacker Playbook 3もWeidmanの著作も、事前準備（pre-engagement）と報告を後付けの作業ではなく、第一級のフェーズとして扱っている。ペネトレーションテストの価値は、どれだけ深く侵入できたかではなく、スコープの明確さと報告書の質によって決まる。

## 2. PTESの7フェーズ

```
┌──────────────────────────────────────────────────────────────────┐
│                    PTES EXECUTION PIPELINE                       │
├────┬─────────────────────────────────────────────────────────────┤
│ 1  │ Pre-engagement Interactions  → RoE, NDA, scope, contacts    │
│ 2  │ Intelligence Gathering       → OSINT & authorized discovery │
│ 3  │ Threat Modeling              → assets, actors, paths        │
│ 4  │ Vulnerability Analysis       → inventory flaws (lab/scope)  │
│ 5  │ Exploitation                 → prove impact under RoE       │
│ 6  │ Post-Exploitation            → data exposure / lateral risk │
│ 7  │ Reporting                    → executive + technical fix    │
└────┴─────────────────────────────────────────────────────────────┘
```

### 各フェーズの意図（防御側から見た読み方）

| フェーズ | テスターの目標 | 防御側が学ぶべきこと |
|:---|:---|:---|
| Pre-engagement | 法的保護と停止条件の確立 | 「認可されている」の定義を決める |
| Intel gathering | 攻撃対象領域の地図化 | 公開されている情報を減らす |
| Threat modeling | 攻撃経路の優先順位付け | SOCを重要資産に合わせる |
| Vuln analysis | 発見事項のランク付け | パッチと設定の対応リスト化 |
| Exploitation | 影響の実証 | 検知とインシデント対応の検証 |
| Post-exploit | 被害範囲の提示 | セグメンテーションと最小権限 |
| Reporting | 修復の後押し | クローズまでのSLA追跡 |

フェーズ5と6は、RoEが許可し、かつ環境がそれを支える場合（ラボ、ステージング、あるいはメンテナンス時間帯を設けた本番環境）にのみ実施される。多くのエンゲージメントはフェーズ4で終わり、ペイロードを実行することなく、設定不備や脆弱性の証拠だけを残す。

プロのエンゲージメントにおける「Exploitation」とは、影響を制御された形で実証することであり、無差別にマルウェアを展開することではない。Gray Hat Hackingは、これを契約によって適用される責任ある開示文化として位置づけている。

## 3. OSSTMM、NISTと他の標準

### OSSTMM（Open Source Security Testing Methodology Manual）
運用上のセキュリティ指標に焦点を当てる。人的、物理的、無線、データネットワークなどのチャネル、トラスト分析、ポートホール/ベクターのカバレッジなどである。クライアントが「あるチャネルがどれだけ開いているか」を定量的なスコアで求める場合に有用となる。

### NIST SP 800-115
セキュリティテストのための技術ガイドで、planning、discovery、attack（認可範囲内）、reportingという構成をとる。政府機関やコンプライアンス要件が重い環境に適している。

### 簡易対応表

| 観点 | PTES | OSSTMM | NIST 800-115 |
|:---|:---|:---|:---|
| 契約と倫理 | Pre-engagement | Rules of engagement | Planning |
| 偵察 | Intel gathering | Visibility / exposure | Discovery |
| 影響の実証 | Exploitation | Controlled verification | Attack (authorized) |
| 出力 | Reporting | Metrics + report | Reporting |

カバレッジとは、スコープ内の攻撃対象のうち実際にテストできた割合のこと。例: スコープ内のWebアプリ50個のうち40個をテストすれば80%になる。

理論上の100%ではなく、時間と予算に見合った現実的なカバレッジを目標にする。

## 4. Rules of Engagement（RoE）

### 書面で必ず定めるべき項目

1. テスターとクライアント側の法的主体の身元
2. スコープ内の資産（CIDR、FQDN、アプリケーション、クラウドアカウント）
3. スコープ外の対象（サードパーティSaaS、個人所有デバイス、本番DBへの書き込み、DoS）
4. 許可された技術（例: クレデンシャルスタッフィングはラボ環境のみ）
5. 実施時間帯と緊急連絡先
6. データの取り扱い（PIIの最小化、証拠の保管時暗号化）
7. 停止条件（可用性への影響、ランサムウェアの兆候、リーガルホールド）

```
┌──────────────┐     written RoE      ┌─────────────────┐
│  Client CISO │◄────────────────────►│  Lead tester    │
└──────┬───────┘                      └────────┬────────┘
       │ emergency phone / chat                │
       └──────────── kill-switch ──────────────┘
```

RoEがなければ、「ペンテストに似た」活動がコンピュータ不正アクセス関連の法律に抵触しうる。認可はチャットでの非公式な誘いとは異なる。

公開情報のみを使うパッシブOSINTであっても、利用規約、プライバシー法、クライアントの評判リスクによる制約を受ける。CTログ、DNS、公開されたWHOISなど、クライアント自身が公開情報として想定している出典を優先する。

チャットでの口頭許可はRoEの代わりにはならない。書面によるスコープと停止条件は必須である。

## 5. スキャン前の脅威モデリング

### 資産クラス
- クラウンジュエル: 認証IdP、決済、ソースコード、顧客PII
- Ingress: VPN、メールゲートウェイ、公開Web、APIゲートウェイ
- トラストブリッジ: CI/CD、ジャンプホスト、共有されたADトラスト

### 単純な優先順位付け

各ターゲットに、ビジネスへの影響、露出度、悪用のしやすさをそれぞれ1〜5で点数を付け、3つを掛け合わせる。合計が高いものから先にテストする。

CVSSだけに頼るのではなく、クライアントと合意した序数尺度（1〜5）を使う。

脅威モデリングは、IdPがMFAレビューされないまま放置される一方で、影響の小さいサブドメインに時間を浪費するといった事態を防ぐ。

## 6. 合法かつ倫理的なパッシブOSINT

### 「パッシブ」の意味
すでに公開されている範囲を超えて対象インフラへプローブを送ることなく、公開情報源から情報を集めることを指す。たとえば公開DNSへの問い合わせに応答を得ること、通常の訪問者と同じように公開サイトを閲覧することなどが該当する。

| 情報源の種類 | 利用例（認可済み） | 防御側の視点 |
|:---|:---|:---|
| Certificate Transparency | 発行済みホスト名のインベントリ | 不要なSANを最小化 |
| 公開DNS / WHOIS | 所有者とメールホストの把握 | レコード内の情報漏えいを減らす |
| 求人情報 / GitHub組織 | 技術スタックの手がかり | シークレットスキャンの徹底 |
| 侵害通知フィード | クレデンシャル露出リスク | ローテーションとMFAの強制 |

この資料が扱わないもの: 利用規約を回避する技術、法律に反する強引なスクレイピング、契約のない第三者への「偵察」。焦点は、公開されている攻撃対象領域を理解し、それを縮小できるようにすることにある。

The Hacker Playbook 3は、OSINTをスコープの精緻化のための入力として扱う。すなわち、クライアントが公開情報だと思っているものと、実際に公開されているものを突き合わせる作業である。Weidmanは、最終報告書のために情報源を記録しておくことの重要性を強調している。

OSINTは攻撃手順のレシピではない。公開面を縮小するためのインベントリである。

```
Public CT logs ──► hostname set H
Public DNS   ──► address set A
Job/tech docs──► stack hypotheses S
                 │
                 ▼
        Attack-surface inventory (for hardening)
```

## 7. 文書化と証拠管理の規律

### 証拠の原則
- すべての観測にタイムスタンプ（UTC）を付ける
- 再現性: スクリーンショットだけでなく、コマンドと文脈を残す
- 報告書の付録に含める機微情報を最小化する
- ラボのストレージにコピーしたクライアントデータのチェーンオブカストディを維持する

### プロフェッショナルな報告書の構成

| セクション | 対象読者 | 内容 |
|:---|:---|:---|
| エグゼクティブサマリー | 経営層 | リスクの物語と事業への影響 |
| 方法論 | 監査担当 | 使用した標準、スコープ、限界 |
| 発見事項 | セキュリティエンジニア | 深刻度、証拠、修復方法 |
| 付録 | 技術担当 | ツールのバージョン、生のインベントリ |

```text
何が起きたか  |  どこで  |  影響  |  修正方法  |  修正の確認方法
```

良い報告書は、ブルーチームがエンゲージメント全体をやり直さなくても修正を検証できるようにする。

## 8. 発見事項を防御コントロールへ対応付ける

| よくある偵察の発見 | コントロールの分類 | ハードニングの例 |
|:---|:---|:---|
| 過剰な公開ホスト名 | 攻撃対象領域管理 | 廃止 / スプリットDNS |
| 技術スタックの露出 | セキュアなデフォルト設定 | サーバーバナーを慎重に削除しパッチを当てる |
| 露出した管理パネル | ネットワークとアプリの制御 | VPN / SSO / IP許可リスト |
| 古いDNS / シャドーIT | CMDBの整備 | 継続的なディスカバリーと責任の明確化 |

Gray Hat Hackingが繰り返し強調するテーマ: 修復の担当者が決まっていない攻撃側の発見事項は、セキュリティ向上に何ももたらさない。

## 9. プロセスチェックリスト（認可されたエンゲージメント向け）

```text
[ ] Signed RoE / NDA / scope list
[ ] Emergency contacts & kill-switch tested
[ ] Inventory of in-scope environments (prod/stage/lab)
[ ] Passive public inventory only as permitted
[ ] Threat model ranked with client
[ ] Vuln analysis tools limited to scope
[ ] Exploitation only if explicitly allowed
[ ] Evidence stored encrypted; PII minimized
[ ] Draft findings reviewed for false positives
[ ] Remediation owners + retest window agreed
```

### ラボと本番環境の違い

| モード | 一般的な深さ | 備考 |
|:---|:---|:---|
| 隔離されたラボ | 方法論を完全に実践できる | 学習には最も適している |
| ステージング | 本番に近い設定 | 本番環境を慎重に再現する |
| 本番環境 | 範囲を絞り、時間を区切る | 最も厳格な変更管理が必要 |

## セキュリティに関する注意

| プロセス上のリスク | 原因 | 緩和策 |
|:---|:---|:---|
| 不正アクセスの主張 | 書面のRoEがない | プローブの前に契約を交わす |
| テストによる障害 | 制限のないアクティブテスト | レート制限、メンテナンス時間帯 |
| 報告書からのPII漏えい | 生データのコピー&ペースト | 匿名化と必要最小限の付録 |
| スコープクリープ | 「あと1台だけ」 | 変更依頼のプロセスを設ける |
| 検証できない発見事項 | 検証手順が存在しない | リテストの基準を含める |
