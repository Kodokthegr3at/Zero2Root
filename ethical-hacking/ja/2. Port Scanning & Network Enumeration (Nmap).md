## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| ポートスキャン | ホストのどのポートが開いているかを調べること |
| 列挙(enumeration) | 見つけたサービスの詳細を集めること |
| Nmap | ポートスキャンと列挙の標準ツール |
| open / closed / filtered | サービスが応答 / 何もない / ファイアウォールで遮断 |
| SYNスキャン | 接続を完全には完了させない高速なスキャン |
| サービス / バージョン検出 | ポートで動くソフトとバージョンを特定すること |
| ホスト発見 | 範囲内でどのホストが生きているかを見つけること |

## 1. インベントリとしてのスキャン（認可済みネットワーク限定）

プロフェッショナルな文脈でのポートスキャンは、ネットワーク表面の測定である。生存しているホスト、listening状態のポート、公開されているサービスを把握する作業であり、次の対象に対してのみ行う。

- 自分が所有するインフラ
- 自分で管理するCTFラボ / VM
- 書面のRoEがあるエンゲージメント

インベントリが役に立つのは、本当に開いているポートを見つけ、誤検知も見落としも少ないときだ。

この資料が扱うのはプロトコルの仕組みと、防御側から見える痕跡である。第三者ネットワーク向けの回避手順集ではない。

## 2. TCPスリーウェイハンドシェイクの仕組み

```
Client                                Server
  │  SYN (seq=x)                        │
  │────────────────────────────────────>│
  │  SYN-ACK (seq=y, ack=x+1)           │
  │<────────────────────────────────────│
  │  ACK (ack=y+1)                      │
  │────────────────────────────────────>│
  │         ESTABLISHED                 │
```

状態遷移（簡略化）:

```text
server:  LISTEN  --SYN-->  SYN-RCVD  --ACK-->  ESTABLISHED
```

```text
client:  CLOSED  --SYN-->  SYN-SENT  --SYN-ACK-->  ESTABLISHED
```

### ポート応答から読み取れること

| 観測者から見える挙動 | 一般的な意味 |
|:---|:---|
| SYN-ACK | 何かがSYNを受け入れた（open候補） |
| RST | 積極的に拒否 / closed |
| 無応答 / drop | filtered、パケットロス、またはステルスACL |

ファイアウォールがdropするかrejectするかによって、クライアント側と防御側のログに残る痕跡が変わる。この違いはブルーチームにとって重要である。

## 3. SYNスキャンとConnectスキャン（プロトコルの知識）

### Connectスキャン（`-sT`の概念）
OSのスタックがハンドシェイクを完全に完了させてから接続を閉じる。短いアプリケーション接続のように見える。

ハンドシェイクを最後まで完了させるので、コネクトスキャンはコストが高く、ターゲット側には本物の接続として記録される。

### SYNスキャン（`-sS`の概念）
送信側はSYN-ACKを観測した後、通常はRSTを送ってアプリケーションセッションを完了させない。それでも現代のNIDSからは非常によく見えるTCP制御パケットであることに変わりはない。

```
SYN scan sketch (conceptual):
  Scanner --SYN--> Target
  Scanner <--SYN-ACK-- Target   ⇒ infer "open"
  Scanner --RST--> Target       ⇒ tear down early
```

歴史的にSYNスキャンは「ハーフオープン」と呼ばれてきたが、それは不可視であることを意味しない。現代のIDSはSYNフラッド、スキャンのファンアウト、不完全なハンドシェイクを相関させて検知する。

| 性質 | Connect | SYN（概念） |
|:---|:---|:---|
| ハンドシェイクを完了させるか | する | しないことが多い |
| raw socket / 権限が必要か | 通常不要 | 必要なことが多い |
| アプリ層のログ | 残りやすい | ネットワークIDS側に残りやすい |
| 現代のNIDSに対するステルス性 | 低い | ノイズが多ければ同様に低い |

## 4. UDP、ICMPとその曖昧さ

UDPにはハンドシェイクが存在しない。「open」の推測は統計的にならざるを得ない。

```text
応答データグラムあり     → おそらく開いている
ICMP port unreachable    → おそらく閉じている
応答なし(タイムアウト)  → open|filtered(区別できない)
```

ルーターでのICMPレート制限は曖昧さを増す。防御側は、SOCがスキャン結果を誤読しないよう、想定されるICMPポリシーを文書化しておくべきである。

## 5. 自ネットワーク向けインベントリのための主要Nmapフラグ

認可されたスコープに対してのみ使用する。以下の例はあくまで運用上のインベントリであり、攻撃の手順書ではない。

| フラグ / オプション | インベントリでの役割 |
|:---|:---|
| `-sn` | ポートスキャンなしのホスト検出 |
| `-sV` | サービス/バージョンのプローブ（ノイズが多い） |
| `-O` | OSフィンガープリントのヒューリスティック（単独では不確実） |
| `-p` / `-p-` | ポート範囲の指定 |
| `-T3` / `-T2` | タイミングテンプレート（数値が小さいほど穏やか） |
| `-oA basename` | normal + XML + grepable形式で保存 |
| `--reason` | Nmapがその状態と判断した理由 |

```bash
# ── Authorized lab / own subnet inventory examples ───────────
# Replace CIDR with YOUR documented scope only.

nmap -sn 192.0.2.0/24 -oA lab_hosts
nmap -sV -p 22,80,443,3389 192.0.2.10 -oA lab_svc --reason
nmap -sU --top-ports 20 192.0.2.10 -oA lab_udp   # slow; expect ambiguity
```

`-A`（aggressive）は多数のプローブを一度にまとめて実行する。ラボでは有用だが、メンテナンス時間帯のない本番環境ではリスクが大きい。

壊れやすいOT/ICSセグメントに対しては、無差別なフルレンジスキャンよりも、CMDBから導いたターゲットを絞ったポートリストを優先する。

## 6. 防御側はどうスキャンを検知するか

### テレメトリの情報源
- ファイアウォールのaccept/denyカウンター
- 水平/垂直スイープに対するZeek/Suricataのシグネチャ
- NetFlow / IPFIX: 単一の送信元から多数のポート/ホストへのファンアウト
- ホストエージェント: 不完全なTCP接続のバースト

### 単純な検知指標

1つの送信元が短時間に多くのポートや多くのホストに触れたり、未完了のTCPハンドシェイクを大量に残したりすると、スキャンは目立つ。検知ルールは通常この3つのシグナルを組み合わせて評価する。

閾値は環境ごとに異なる。既知の管理用スキャナー（Nessusの実行時間帯など）に合わせて調整し、誤検知を減らす。

```
         many ports
Single IP ──────────────► many hosts   = classic sweep pattern
              │
              ▼
     SOC alert / rate-limit / tarpit policy
```

正規の脆弱性スキャンの実施予定をカレンダーで共有しておくと、アラートのノイズを減らせる。

## 7. 望まれないスキャンに対するネットワーク硬化

| コントロール | 効果 |
|:---|:---|
| インバウンドのデフォルト拒否 | listeningの露出を縮小 |
| セグリゲーション / マイクロセグメンテーション | 横方向のファンアウトの価値を制限 |
| SYN cookie / backlogのチューニング | SYNフラッドへの耐性 |
| 地域 / ASN単位の許可リスト（適用可能な場合） | インターネットからのノイズを削減 |
| バナー情報の最小化 | `-sV`から得られる無料の情報を減らす |
| カナリアポート / ハニーポート | 高確度のアラート |
| Egress制御 | 侵害されたホストがスキャンに使いにくくなる |

### Stallingsの視点
サービスの機密性と完全性は、不要なlistenerを減らすことから始まる。スキャンとは、攻撃者（そして監査担当者）がそうしたlistenerを発見する手段であり、だからこそそれを閉じることが第一の防御になる。

### FilterとRejectのトレードオフ

| ポリシー | 攻撃者から見た場合 | 防御側の運用 |
|:---|:---|:---|
| REJECT（RST/ICMP） | マッピングが速い | ログが明確 |
| DROP | 遅い / 曖昧 | トラブルシューティングが難しい |

このポリシーは、DMZか内部かといったゾーンごとに意図的に選ぶべきである。

## 8. 防御・ラボ用チェックリスト

```text
[ ] Written authorization / own lab confirmed
[ ] Change window notified for production inventory
[ ] Output saved (-oA) with date in filename
[ ] Timing tempered on sensitive segments
[ ] Results diffed against last CMDB export
[ ] Unexpected listeners ticketed for closure
[ ] SOC allowlisted or informed for scheduled scans
[ ] No scan of third-party SaaS without their consent
```

### ハードニングのための結果の読み方

| 発見事項 | 対応 |
|:---|:---|
| インターネット上に想定外のRDP/SSH | VPN / 踏み台の背後へ移動 |
| 本番VLAN上の開発ツール | ネットワーク経路を再配置 |
| filteredな不明ポートが多数 | ACLの意図を検証 |
| バージョン文字列が古い | パッチ適用のパイプラインへ |

## セキュリティに関する注意

| リスク | 原因 | 緩和策 |
|:---|:---|:---|
| 意図しないDoS | 攻撃的なタイミング / 広すぎる範囲 | `-T2`、`-p`を絞る、レート制限 |
| 法的リスク | 認可のないスキャン | RoE / 所有権の証明 |
| 盲点 | DROPのみで内部センサーがない | 内部ネットワークのテレメトリ |
| アラート疲れ | 事前告知のない脆弱性スキャナー | 共有スキャンカレンダー |
| OS検出への過信 | フィンガープリントのノイズ | CMDBエージェントとの突き合わせ |
