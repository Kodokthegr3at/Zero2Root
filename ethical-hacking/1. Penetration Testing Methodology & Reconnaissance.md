## 1. 🧭 Why Formal Methodology Matters

### 🇮🇩 Bahasa Indonesia
Penetration testing tanpa kerangka kerja mudah berubah menjadi **ad-hoc hacking**: scope kabur, risiko operasional tinggi, dan laporan yang tidak bisa ditindaklanjuti. Metodologi (PTES, OSSTMM, NIST SP 800-115) memaksa:

- **Otorisasi tertulis** sebelum aktivitas apa pun
- **Batasan teknis** (IP, domain, jam, teknik terlarang)
- **Dokumentasi** yang bisa diaudit
- **Remediasi** sebagai tujuan akhir — bukan “koleksi shell”

$$
\text{Value}_{\text{pentest}} \approx f(\text{Scope clarity},\ \text{Evidence quality},\ \text{Remediation usability})
$$

### 🇬🇧 English
Authorized testing is a **controlled risk activity**. The methodology protects the client, the tester, and third parties. Hacker Playbook 3 and Weidman both emphasize pre-engagement and reporting as first-class phases—not afterthoughts.

### 🇯🇵 日本語
認可されたテストは**制御されたリスク活動**です。方法論は依頼者・テスター・第三者を守ります。偵察や侵入そのものより、スコープと報告の質が価値を決めます。

## 2. 🔄 PTES — Seven Phases

```
┌──────────────────────────────────────────────────────────────────┐
│                    PTES EXECUTION PIPELINE                       │
├────┬─────────────────────────────────────────────────────────────┤
│ 1  │ Pre-engagement Interactions  → RoE, NDA, scope, contacts    │
│ 2  │ Intelligence Gathering       → OSINT & authorized discovery │
│ 3  │ Threat Modeling              → assets, actors, paths        │
│ 4  │ Vulnerability Analysis       → inventory flaws (lab/scope)  │
│ 5  │ Exploitation                 → prove impact under RoE       │
│ 6  │ Post-Exploitation            → data exposure / lateral risk │
│ 7  │ Reporting                    → executive + technical fix    │
└────┴─────────────────────────────────────────────────────────────┘
```

### Phase intents (defense-oriented reading)

| Phase | Tester goal | Defender takeaway |
|:---|:---|:---|
| Pre-engagement | Legal cover & stop conditions | Define what “authorized” means |
| Intel gathering | Attack surface map | Shrink public footprint |
| Threat modeling | Prioritize paths | Align SOC with crown jewels |
| Vuln analysis | Rank findings | Patch & config backlog |
| Exploitation | Demonstrate impact | Validate detection & IR |
| Post-exploit | Show blast radius | Segment & least privilege |
| Reporting | Drive remediations | Track closure SLAs |

### 🇮🇩 Bahasa Indonesia
Fase 5–6 **hanya** dijalankan jika RoE mengizinkan dan lingkungan mendukung (lab, staging, atau produksi dengan jendela pemeliharaan). Banyak engagement berhenti di fase 4 dengan bukti konfigurasi/kerentanan tanpa eksekusi payload.

### 🇬🇧 English
“Exploitation” in a professional engagement means **controlled validation** of impact—not indiscriminate malware deployment. Gray Hat frames this as responsible disclosure culture applied contractually.

### 🇯🇵 日本語
プロの「Exploitation」は影響の**制御された実証**であり、無差別なマルウェア展開ではありません。

## 3. 📐 OSSTMM, NIST & Companion Models

### OSSTMM (Open Source Security Testing Methodology Manual)
Fokus pada **operational security metrics**: channels (human, physical, wireless, data networks, etc.), trust analysis, and porthole/vector coverage. Berguna ketika klien meminta skor kuantitatif “seberapa terbuka saluran X”.

### NIST SP 800-115
Technical guide untuk security testing: planning, discovery, attack (within authorization), dan reporting. Cocok untuk lingkungan pemerintah / compliance-heavy.

### Mapping ringkas

| Concern | PTES | OSSTMM | NIST 800-115 |
|:---|:---|:---|:---|
| Contract & ethics | Pre-engagement | Rules of engagement | Planning |
| Recon | Intel gathering | Visibility / exposure | Discovery |
| Prove impact | Exploitation | Controlled verification | Attack (authorized) |
| Output | Reporting | Metrics + report | Reporting |

$$
\text{Coverage} = \frac{\text{Authorized vectors tested}}{\text{In-scope attack surface}} \quad (0 \le \text{Coverage} \le 1)
$$

Targetkan coverage yang realistis terhadap waktu & budget—bukan 100% teoritis.

## 4. 📜 Rules of Engagement (RoE)

### Wajib ada tertulis

1. **Identity of tester & client legal entity**
2. **In-scope assets** (CIDR, FQDN, apps, cloud accounts)
3. **Out-of-scope** (third-party SaaS, personal devices, production DB writes, DoS)
4. **Allowed techniques** (e.g. credential stuffing against lab only)
5. **Time windows** & emergency contacts
6. **Data handling** (PII minimization, encryption at rest for evidence)
7. **Stop conditions** (availability impact, ransomware indicators, legal hold)

```
┌──────────────┐     written RoE      ┌─────────────────┐
│  Client CISO │◄────────────────────►│  Lead tester    │
└──────┬───────┘                      └────────┬────────┘
       │ emergency phone / chat                │
       └──────────── kill-switch ──────────────┘
```

### 🇮🇩 Bahasa Indonesia
Tanpa RoE, aktivitas “mirip pentest” bisa melanggar hukum akses komputer. **Otorisasi ≠ undangan informal di chat.**

### 🇬🇧 English
Passive OSINT using *public* sources is still constrained by ToS, privacy law, and client reputation risk. Prefer sources the client already expects to be public (CT logs, DNS, published WHOIS).

### 🇯🇵 日本語
チャットでの口頭許可はRoEの代わりになりません。書面の範囲と停止条件が必須です。

## 5. 🗺️ Threat Modeling Before Scanning

### Asset classes
- **Crown jewels**: auth IdP, payment, source code, customer PII
- **Ingress**: VPN, email gateway, public web, API gateways
- **Trust bridges**: CI/CD, jump hosts, shared AD trusts

### Simple prioritization

$$
\text{Priority} = \text{BusinessImpact} \times \text{Exposure} \times \text{EaseOfAbuse}_{\text{est}}
$$

Gunakan skala ordinal (1–5) yang disepakati klien—bukan “CVSS saja”.

### 🇮🇩 Bahasa Indonesia
Threat modeling mencegah pemborosan waktu di subdomain rendah dampak sementara IdP dibiarkan tanpa MFA review.

## 6. 🕵️ Passive OSINT Concepts (Legal & Ethical)

### Apa yang “pasif” berarti
Mengumpulkan informasi dari **sumber publik** tanpa mengirim probe ke infrastruktur milik target di luar yang sudah dipublikasikan (mis. merespons DNS publik, membuka situs publik seperti browser biasa).

| Source type | Example use (authorized) | Defense note |
|:---|:---|:---|
| Certificate Transparency | Inventory of issued hostnames | Minimize unnecessary SANs |
| Public DNS / WHOIS | Ownership & mail hosts | Reduce data leakage in records |
| Job posts / GitHub org | Tech stack hints | Secret scanning hygiene |
| Breach notification feeds | Credential exposure risk | Force rotation & MFA |

### 🇮🇩 Bahasa Indonesia
**Tidak termasuk** dalam catatan ini: teknik bypass ToS, scraping agresif yang melanggar hukum, atau “hacking recon” terhadap pihak ketiga tanpa kontrak. Fokus: **memahami permukaan serangan publik agar bisa diperkecil**.

### 🇬🇧 English
Hacker Playbook 3 treats OSINT as *input to scoping refinement*—confirm what the client thinks is public vs what actually is. Weidman stresses documenting sources for the final report.

### 🇯🇵 日本語
OSINTは攻撃手順のレシピではなく、**公開面を縮小するためのインベントリ**です。

```
Public CT logs ──► hostname set H
Public DNS   ──► address set A
Job/tech docs──► stack hypotheses S
                 │
                 ▼
        Attack-surface inventory (for hardening)
```

## 7. 📝 Documentation & Evidence Discipline

### Evidence principles
- **Timestamp** every observation (UTC)
- **Reproducibility**: command/context, not only screenshot
- **Minimize sensitive data** in report appendices
- **Chain of custody** for any client data copied to lab storage

### Report structure (professional)

| Section | Audience | Content |
|:---|:---|:---|
| Executive summary | Leadership | Risk narrative + business impact |
| Methodology | Audit | Standards used, scope, limitations |
| Findings | Security eng | Severity, evidence, remediations |
| Appendix | Technical | Tool versions, raw inventories |

$$
\text{Finding}_{\text{good}} = \{\text{What},\ \text{Where},\ \text{Impact},\ \text{Fix},\ \text{Verify}\}
$$

### 🇮🇩 Bahasa Indonesia
Laporan yang bagus membuat tim blue-team bisa **memverifikasi perbaikan** tanpa mengulang seluruh engagement.

## 8. 🛡️ Mapping Findings to Defensive Controls

| Typical recon insight | Control family | Example hardening |
|:---|:---|:---|
| Excess public hostnames | Attack surface mgmt | Decommission / split DNS |
| Tech stack disclosure | Secure defaults | Remove server banners carefully + patch |
| Exposed admin panels | Network & app control | VPN / SSO / IP allowlists |
| Stale DNS / shadow IT | CMDB hygiene | Continuous discovery + ownership |

Gray Hat’s recurring theme: **offensive findings without remediation owners produce no security gain**.

## 9. ✅ Process Cheatsheet (Authorized Engagements)

```text
[ ] Signed RoE / NDA / scope list
[ ] Emergency contacts & kill-switch tested
[ ] Inventory of in-scope environments (prod/stage/lab)
[ ] Passive public inventory only as permitted
[ ] Threat model ranked with client
[ ] Vuln analysis tools limited to scope
[ ] Exploitation only if explicitly allowed
[ ] Evidence stored encrypted; PII minimized
[ ] Draft findings reviewed for false positives
[ ] Remediation owners + retest window agreed
```

### Lab vs production

| Mode | Typical depth | Notes |
|:---|:---|:---|
| Isolated lab | Full methodology practice | Preferred for learning |
| Staging | Near-prod configs | Mirror prod carefully |
| Production | Narrow, time-boxed | Highest change-control |

## 🔐 Security Notes

| Risiko proses | Penyebab | Mitigasi |
|:---|:---|:---|
| Illegal access claims | No written RoE | Contract before any probe |
| Outage from testing | Unbounded active tests | Rate limits, maintenance windows |
| PII leakage in reports | Copy-paste dumps | Redact + need-to-know appendices |
| Scope creep | “Just one more host” | Change-order process |
| Unfixable findings | No verify steps | Include retest criteria |
