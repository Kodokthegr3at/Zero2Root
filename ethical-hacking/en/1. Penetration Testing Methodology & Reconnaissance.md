## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| Penetration test | An authorized, simulated attack to find weaknesses before real attackers do |
| Scope | The exact systems and actions you're allowed to test |
| Rules of Engagement (RoE) | The signed agreement defining scope, timing, and limits |
| Reconnaissance | Gathering information about a target |
| Passive vs active recon | Learning without touching the target vs probing it directly |
| OSINT | Intelligence from public sources |
| Methodology | A repeatable, documented process for the engagement |
| Remediation | The fixes the report recommends — the real goal |

## 1. Why Formal Methodology Matters

Penetration testing without a framework easily turns into ad-hoc hacking: unclear scope, high operational risk, and reports nobody can act on. Methodologies such as PTES, OSSTMM, and NIST SP 800-115 require four things:

- Written authorization before any activity starts
- Clear technical boundaries (IP ranges, domains, hours, prohibited techniques)
- Documentation that can be audited
- Remediation as the actual goal, not a shell collection

A pentest is valuable when the scope is clear, the evidence is solid, and the client can actually use the report to fix things.

Authorized testing is a controlled risk activity. The methodology protects the client, the tester, and third parties. Hacker Playbook 3 and Weidman both treat pre-engagement and reporting as first-class phases, not afterthoughts. The value of an engagement comes from scope clarity and report quality, not from how deep the tester managed to get.

## 2. PTES: Seven Phases

```
┌──────────────────────────────────────────────────────────────────┐
│                    PTES EXECUTION PIPELINE                       │
├────┬─────────────────────────────────────────────────────────────┤
│ 1  │ Pre-engagement Interactions  → RoE, NDA, scope, contacts    │
│ 2  │ Intelligence Gathering       → OSINT & authorized discovery │
│ 3  │ Threat Modeling              → assets, actors, paths        │
│ 4  │ Vulnerability Analysis       → inventory flaws (lab/scope)  │
│ 5  │ Exploitation                 → prove impact under RoE       │
│ 6  │ Post-Exploitation            → data exposure / lateral risk │
│ 7  │ Reporting                    → executive + technical fix    │
└────┴─────────────────────────────────────────────────────────────┘
```

### Phase intents (defense-oriented reading)

| Phase | Tester goal | Defender takeaway |
|:---|:---|:---|
| Pre-engagement | Legal cover & stop conditions | Define what "authorized" means |
| Intel gathering | Attack surface map | Shrink public footprint |
| Threat modeling | Prioritize paths | Align SOC with crown jewels |
| Vuln analysis | Rank findings | Patch & config backlog |
| Exploitation | Demonstrate impact | Validate detection & IR |
| Post-exploit | Show blast radius | Segment & least privilege |
| Reporting | Drive remediations | Track closure SLAs |

Phases 5 and 6 only run when the RoE allows it and the environment supports it, whether that's a lab, staging, or production with a maintenance window. Many engagements stop at phase 4 with configuration and vulnerability evidence alone, without running a payload.

"Exploitation" in a professional engagement means controlled validation of impact, not indiscriminate malware deployment. Gray Hat frames this as responsible disclosure culture applied contractually.

## 3. OSSTMM, NIST & Companion Models

### OSSTMM (Open Source Security Testing Methodology Manual)
Focuses on operational security metrics: channels (human, physical, wireless, data networks, and others), trust analysis, and porthole/vector coverage. Useful when a client wants a quantitative score for how exposed a given channel is.

### NIST SP 800-115
A technical guide for security testing: planning, discovery, attack (within authorization), and reporting. Fits government and compliance-heavy environments well.

### Quick mapping

| Concern | PTES | OSSTMM | NIST 800-115 |
|:---|:---|:---|:---|
| Contract & ethics | Pre-engagement | Rules of engagement | Planning |
| Recon | Intel gathering | Visibility / exposure | Discovery |
| Prove impact | Exploitation | Controlled verification | Attack (authorized) |
| Output | Reporting | Metrics + report | Reporting |

Coverage is the share of the in-scope attack surface you actually tested. Example: testing 40 of 50 in-scope web apps gives 80% coverage.

Aim for coverage that's realistic given time and budget, not a theoretical 100%.

## 4. Rules of Engagement (RoE)

### Must exist in writing

1. Identity of tester and client legal entity
2. In-scope assets (CIDR, FQDN, apps, cloud accounts)
3. Out-of-scope items (third-party SaaS, personal devices, production DB writes, DoS)
4. Allowed techniques (for example credential stuffing against lab only)
5. Time windows and emergency contacts
6. Data handling (PII minimization, encryption at rest for evidence)
7. Stop conditions (availability impact, ransomware indicators, legal hold)

```
┌──────────────┐     written RoE      ┌─────────────────┐
│  Client CISO │◄────────────────────►│  Lead tester    │
└──────┬───────┘                      └────────┬────────┘
       │ emergency phone / chat                │
       └──────────── kill-switch ──────────────┘
```

Without a RoE, activity that "looks like" a pentest can violate computer access laws. Authorization is not an informal invitation in chat.

Passive OSINT using public sources is still constrained by ToS, privacy law, and client reputation risk. Prefer sources the client already expects to be public, such as CT logs, DNS, and published WHOIS.

Verbal permission in chat cannot substitute for a RoE. Written scope and stop conditions are mandatory.

## 5. Threat Modeling Before Scanning

### Asset classes
- Crown jewels: auth IdP, payment, source code, customer PII
- Ingress: VPN, email gateway, public web, API gateways
- Trust bridges: CI/CD, jump hosts, shared AD trusts

### Simple prioritization

Give each target a 1-5 score for business impact, exposure, and how easy it looks to abuse, then multiply the three. The highest totals get tested first.

Use an ordinal scale (1-5) agreed with the client, rather than relying on CVSS alone.

Threat modeling stops time being wasted on low-impact subdomains while the IdP goes without an MFA review.

## 6. Passive OSINT (Legal and Ethical)

### What "passive" means
Collecting information from public sources without sending probes to target infrastructure beyond what is already published, such as querying public DNS or browsing a public site the way an ordinary visitor would.

| Source type | Example use (authorized) | Defense note |
|:---|:---|:---|
| Certificate Transparency | Inventory of issued hostnames | Minimize unnecessary SANs |
| Public DNS / WHOIS | Ownership & mail hosts | Reduce data leakage in records |
| Job posts / GitHub org | Tech stack hints | Secret scanning hygiene |
| Breach notification feeds | Credential exposure risk | Force rotation & MFA |

Not covered in this note: ToS bypass techniques, aggressive scraping that breaks the law, or "hacking recon" against a third party without a contract. The focus is understanding the public attack surface well enough to shrink it.

Hacker Playbook 3 treats OSINT as input to scoping refinement: confirming what the client thinks is public versus what actually is. Weidman stresses documenting sources for the final report.

OSINT is not a recipe for an attack sequence. It is an inventory for shrinking the public surface.

```
Public CT logs ──► hostname set H
Public DNS   ──► address set A
Job/tech docs──► stack hypotheses S
                 │
                 ▼
        Attack-surface inventory (for hardening)
```

## 7. Documentation & Evidence Discipline

### Evidence principles
- Timestamp every observation (UTC)
- Reproducibility: keep the command/context, not just a screenshot
- Minimize sensitive data in report appendices
- Chain of custody for any client data copied to lab storage

### Report structure (professional)

| Section | Audience | Content |
|:---|:---|:---|
| Executive summary | Leadership | Risk narrative + business impact |
| Methodology | Audit | Standards used, scope, limitations |
| Findings | Security eng | Severity, evidence, remediations |
| Appendix | Technical | Tool versions, raw inventories |

```text
what happened  |  where  |  impact  |  how to fix  |  how to verify the fix
```

A good report lets the blue team verify a fix without repeating the whole engagement.

## 8. Mapping Findings to Defensive Controls

| Typical recon insight | Control family | Example hardening |
|:---|:---|:---|
| Excess public hostnames | Attack surface mgmt | Decommission / split DNS |
| Tech stack disclosure | Secure defaults | Remove server banners carefully + patch |
| Exposed admin panels | Network & app control | VPN / SSO / IP allowlists |
| Stale DNS / shadow IT | CMDB hygiene | Continuous discovery + ownership |

Gray Hat's recurring theme: offensive findings without remediation owners produce no security gain.

## 9. Process Cheatsheet (Authorized Engagements)

```text
[ ] Signed RoE / NDA / scope list
[ ] Emergency contacts & kill-switch tested
[ ] Inventory of in-scope environments (prod/stage/lab)
[ ] Passive public inventory only as permitted
[ ] Threat model ranked with client
[ ] Vuln analysis tools limited to scope
[ ] Exploitation only if explicitly allowed
[ ] Evidence stored encrypted; PII minimized
[ ] Draft findings reviewed for false positives
[ ] Remediation owners + retest window agreed
```

### Lab vs production

| Mode | Typical depth | Notes |
|:---|:---|:---|
| Isolated lab | Full methodology practice | Preferred for learning |
| Staging | Near-prod configs | Mirror prod carefully |
| Production | Narrow, time-boxed | Highest change-control |

## Security Notes

| Process risk | Cause | Mitigation |
|:---|:---|:---|
| Illegal access claims | No written RoE | Contract before any probe |
| Outage from testing | Unbounded active tests | Rate limits, maintenance windows |
| PII leakage in reports | Copy-paste dumps | Redact + need-to-know appendices |
| Scope creep | "Just one more host" | Change-order process |
| Unfixable findings | No verify steps | Include retest criteria |
