## 1. Linux ディストリビューションとは何か

ディストリビューション（ディストロ）とは、Linux カーネルに一貫性のあるユーザーランド、パッケージマネージャ、init システム、既定の設定を組み合わせたパッケージのことである。

$$
\text{Distro} = \underbrace{\text{Linux Kernel}}_{\text{カーネル}} + \underbrace{\text{Userland}}_{\text{GNU, libs, tools}} + \underbrace{\text{Packaging}}_{\text{apt/dnf/pacman}} + \underbrace{\text{Policy}}_{\text{defaults, init, branding}}
$$

カーネル単体では、すぐに使えるデスクトップ用や サーバー用の OS にはならない。ディストロは GNU ツールチェーン、systemd（またはその代替）、パッケージリポジトリ、既定のセキュリティポリシーを追加する。各ディストロは、同じカーネル ABI の思想を共有しつつ、リリース頻度、パッケージのバージョン、セキュリティの既定値が異なる互換性のあるバリエーションだと考えるとよい。

| 層 | 例 | 役割 |
|:---|:---|:---|
| カーネル | `linux`、モジュール、ファームウェア | ハードウェアアクセスとプロセスの隔離 |
| Cライブラリ | glibc、musl | システムコールのラッパー |
| Init | systemd、OpenRC | 起動とサービスの監督 |
| パッケージ | deb、rpm、pkg | インストール、アップグレード、削除 |
| ポリシー | SELinux/AppArmor の既定値 | 閉じ込め（confinement）のベースライン |

## 2. ディストロのスタックモデル

```
┌─────────────────────────────────────────────┐
│  Applications / Desktop / Server Roles      │
├─────────────────────────────────────────────┤
│  Package Manager (apt / dnf / pacman)       │
├─────────────────────────────────────────────┤
│  Userland (GNU coreutils, shells, libs)     │
├─────────────────────────────────────────────┤
│  Init & Logging (systemd, journald, rsyslog)│
├─────────────────────────────────────────────┤
│  Linux Kernel + modules + firmware          │
├─────────────────────────────────────────────┤
│  Hardware (CPU, disk, NIC, TPM, …)          │
└─────────────────────────────────────────────┘
```

### パッケージ管理の形式的な関係

パッケージ集合 $P$ と依存グラフ $G=(P,E)$ が与えられているとき、

$$
\text{install}(p) \text{ succeeds} \iff \forall\, q \in \mathrm{Deps}(p):\ q \in P_{\text{installed}} \cup \{\text{to-install}\}
$$

依存関係の破損や署名のないパッケージは、サプライチェーンの整合性を壊す（9章のセキュリティノートを参照）。

## 3. リリースモデル: Stable、Rolling、LTS

| モデル | 更新頻度 | パッチの方式 | 向いている用途 | リスク |
|:---|:---|:---|:---|:---|
| Stable | 約1〜2年 | セキュリティ修正をバックポート | サーバー、コンプライアンス | 機能が古くなる |
| LTS | 2〜5年以上のサポート | セキュリティと一部の修正のみ | エンタープライズ、本番 | 機能の遅れ |
| Rolling | 継続的更新 | 最新の upstream を反映 | デスクトップ、実験用 | 破損や変更の多さ |
| Point / スナップショット | 固定されたツリー | 定期的に再構築 | 再現性のあるビルド | 手動アップグレード |

本番サーバーでは stable または LTS 系統が好まれる。パッケージ全体を大きく変えずに CVE をバックポートできるためである。Rolling リリースは最新性を最大化する代わりに、リグレッション（既存機能の破損）のリスクを負う。本番環境では Debian Stable、Ubuntu LTS、RHEL、AlmaLinux、Rocky Linux が向いている。Arch や Kali Rolling のような rolling 系ディストロはラボには適するが、厳格な hardening プロセスなしでは本番のベースラインにはできない。

## 4. 主要なディストロファミリー

```
                    ┌──────────┐
                    │  Debian  │
                    └────┬─────┘
         ┌───────────────┼───────────────┐
         │               │               │
      Ubuntu           Kali          Raspberry Pi OS
         │            Parrot
    Mint / Pop!_OS

                    ┌──────────┐
                    │   RHEL   │
                    └────┬─────┘
         ┌───────────────┼───────────────┐
      Fedora          AlmaLinux       Rocky Linux
                         CentOS Stream (upstream-ish)

                    ┌──────────┐
                    │   Arch   │
                    └────┬─────┘
                      Manjaro / EndeavourOS
                      BlackArch (security tools repo)
```

### 一般的な用途の比較

| ディストロ | 向いている用途 | パッケージマネージャ | Init | 既定の MAC |
|:---|:---|:---|:---|:---|
| Ubuntu | デスクトップ、クラウドイメージ | `apt` | systemd | AppArmor |
| Debian | サーバー、アプライアンス | `apt` | systemd | AppArmor（任意） |
| Fedora | 最新技術のデスクトップ/開発 | `dnf` | systemd | SELinux |
| RHEL / Alma / Rocky | エンタープライズサーバー | `dnf` | systemd | SELinux |
| Arch | DIY、学習用 | `pacman` | systemd | （手動） |
| openSUSE | エンタープライズ + YaST | `zypper` | systemd | AppArmor |

補足: 従来型の CentOS Linux（リビルド版）はすでに EOL（サポート終了）である。代わりに AlmaLinux、Rocky Linux、CentOS Stream のいずれかを意図的に選ぶこと。

## 5. セキュリティ志向のディストロ

「セキュリティ」ディストロという言葉は、たいてい2つの意味のどちらかを指す。1つはラボや監査作業向けにツール一式があらかじめ入っているもの、もう1つはプライバシーや hardening を中心に設計されたものである。これらは隔離された VM やラボで動かすべきで、明確なパッチ方針と最小権限の運用なしに本番の常用環境にしてはならない。

| ディストロ | ベース | 焦点（防御・教育用途） | 備考 |
|:---|:---|:---|:---|
| Kali Linux | Debian | セキュリティツール群 | Rolling; 本番サーバー用 OS ではない |
| Parrot OS | Debian | セキュリティと軽量デスクトップ | 研修ラボでよく使われる |
| BlackArch | Arch | 大量のセキュリティパッケージ | 追加リポジトリが利用可能 |
| Qubes OS | Xen + Fedora テンプレート | 強力な隔離 UX | 異なる脅威モデル |
| Tails | Debian | 記憶を残さない、プライバシー重視のライブ環境 | USB からのライブセッション |

```
Why Linux dominates security workstations (defense view)
───────────────────────────────────────────────────────
Open source  → audit patches, reproduce builds
Control      → minimal services, clear attack surface
Tooling      → native packet capture, scripting, containers
Packaging    → signed updates via distro security teams
```

## 6. ディストロの選び方: 判断マトリクス

| 要件 | 推奨 | 主力にすべきでないもの |
|:---|:---|:---|
| 24時間稼働の本番サーバー | Debian Stable、Ubuntu LTS、RHEL系 | 検証されていない rolling リリース |
| コンプライアンス、長期サポート | RHEL、Ubuntu LTS、Debian LTS | 短命なスピン |
| デスクトップ初心者 | Ubuntu、Fedora Workstation、Mint | 準備ができるまでは最小構成の Arch |
| 組み込み / SBC | Raspberry Pi OS、Debian | 重量級のデスクトップスピン |
| 許可されたセキュリティラボ | VM 上の Kali/Parrot | 本番ゲートウェイと同一イメージ |
| 再現可能なビルド | Debian、NixOS*、Guix* | 場当たり的なバイナリ配布 |

\*NixOS と Guix は特殊な宣言的モデルを採用している。再現性には優れるが学習コストは高い。

### 「サポート期間」の形式的な考え方

年間の CVE 発見率を $\lambda$、LTS のもとでの平均パッチ適用時間を $T$ とすると、パッチ適用が遅れた場合の残存リスクはおおよそ $\lambda \cdot T$ に比例して増える。セキュリティのバックポートが速い系統を選ぶべきである。

## 7. Debian 詳細

Debian は厳格なフリーズプロセス、Debian Security チームによるセキュリティ管理、`apt`/`dpkg` エコシステムで知られている。Ubuntu、Kali、Parrot などの多くのディストロは Debian のパッケージングポリシーの多くを受け継いでおり、Ubuntu はそこにさらに速いデスクトップ/クラウドのリリース頻度と Launchpad/Snap のレイヤーを追加している。

**スイート（チャンネル）:**
- `stable`: 本番用
- `testing`: 次の stable の候補
- `unstable`（`sid`）: 開発用、サーバーには使わない

```
Debian suites (simplified)
──────────────────────────
unstable ──► testing ──► stable ──► oldstable
   (sid)      (freeze)     (prod)     (LTS/ELTS may apply)
```

### APT クイックリファレンス（Debian系）

```bash
# Refresh indices & apply security updates
sudo apt update
sudo apt upgrade                 # or: sudo apt full-upgrade when needed

sudo apt install <pkg>
sudo apt remove <pkg>
sudo apt purge <pkg>             # remove config too
apt search <keyword>
apt show <pkg>
apt list --installed
dpkg -l | less
```

### セキュリティチャンネル

- Debian/Ubuntu のサーバーには `unattended-upgrades` を入れて、セキュリティパッチを自動適用する。
- 公式ミラーを HTTPS 経由で優先し、インストール時にリリースキーを検証する。

## 8. 稼働中ホストでのディストロ識別

```bash
cat /etc/os-release          # ID, VERSION_ID, VARIANT
lsb_release -a               # if package installed
hostnamectl                  # pretty OS + kernel
uname -r                     # kernel release
cat /etc/debian_version      # Debian-derived
cat /etc/redhat-release      # RHEL-family
```

| フィールド（`os-release`） | 意味 |
|:---|:---|
| `ID` | ディストロID（`debian`、`ubuntu`、`fedora`） |
| `ID_LIKE` | ファミリーのヒント（`debian`、`rhel`） |
| `VERSION_CODENAME` | スイート名（`bookworm`、`noble`） |
| `SUPPORT_END` | サポート終了日（提供されている場合） |

## 9. セキュリティノート: 防御と Hardening

| 脅威・欠陥 | 重要な理由 | 対策 |
|:---|:---|:---|
| サポート切れ / EOL のディストロ | セキュリティのバックポートがない | サポート対象の LTS にアップグレード。`os-release` で棚卸しする |
| 無秩序な PPA やサードパーティ RPM の混在 | サプライチェーンと信頼性のリスク | 公式リポジトリを優先し、キーを pin して確認する |
| Kali/Parrot を本番ゲートウェイに使う | 攻撃対象領域の増加 | ラボの VM 専用にとどめ、本番は最小構成の stable にする |
| パッチ未適用のパッケージ | 既知の CVE が残ったままになる | `unattended-upgrades` / `dnf-automatic` を使い、DSA/USN を監視する |
| 更新のないフラットなコンテナホスト | カーネル共有のリスク | ホストカーネルをパッチし、namespace と MAC で隔離する |
| 「セキュリティ」ブランドを鵜呑みにする | ツールがあることと hardening された既定値は別物である | 下記の hardening ベースラインを適用する |

### ファミリーごとの hardening ベースライン

1. サポート対象のリリースにとどまり、セキュリティのメーリングリストや RSS を購読する。
2. ポリシーが許す範囲で、セキュリティのみの自動更新を有効にする。
3. AppArmor（Debian/Ubuntu）や SELinux（RHEL/Fedora）を permissive ではなく enforcing に保つ。
4. インストールするパッケージを最小限にする。攻撃対象領域はおおよそ $|P_{\text{installed}}|$ に比例する。
5. ラボ用イメージと本番用イメージを分けておく。

```bash
# Quick posture checks (admin / auditor)
grep -E '^(NAME|VERSION|SUPPORT)' /etc/os-release
systemctl is-enabled unattended-upgrades 2>/dev/null || true
aa-status 2>/dev/null | head          # AppArmor hosts
getenforce 2>/dev/null                # SELinux hosts
```

## 10. クイックリファレンス・チートシート

```bash
# Identity
cat /etc/os-release && uname -a

# Debian/Ubuntu updates
sudo apt update && sudo apt upgrade
apt-cache policy <pkg>

# Fedora / RHEL family
sudo dnf check-update
sudo dnf upgrade

# Arch
sudo pacman -Syu

# Package counts (rough surface)
dpkg -l | wc -l
rpm -qa | wc -l
```

| 特徴 | Ubuntu LTS | Debian Stable | Fedora | RHEL/Alma/Rocky | Arch | Kali（ラボ） |
|:---|:---|:---|:---|:---|:---|:---|
| 更新頻度 | 2年 LTS | 約2年 | 約6ヶ月 | 長期サポート | Rolling | Rolling |
| 既定の MAC | AppArmor | AppArmor* | SELinux | SELinux | 手動 | AppArmor |
| 本番サーバー | 可 | 可 | 一部可 | 可 | 一部可 | 不可 |
| 学習用デスクトップ | 可 | 可 | 可 | 一部可 | 可 | ラボ VM |

\*パッケージ構成によっては有効化が必要な場合がある。
