## 1. コンテナと仮想マシン

コンテナはホストカーネルを共有します。隔離はハイパーバイザー上のフルなゲストカーネルではなく、namespacesとcgroupsによって実現されます。

$$
\text{VM} = \text{Guest OS} + \text{App},\quad
\text{Container} = \text{App + libs} \text{ on shared kernel}
$$

コンテナは起動が速く密度も高くできますが、VMではありません。カーネル脱出や過剰な `--privileged` コンテナはホストを危険にさらします。非root、capabilityの削減、読み取り専用rootfsといった多層防御で運用します。

```
┌─────────────────────────────────────────────┐
│ Host Linux Kernel                           │
│  ┌─────────────┐  ┌─────────────┐           │
│  │ Container A │  │ Container B │           │
│  │ PID/NET/MNT │  │ PID/NET/MNT │  (namespaces)
│  │ cgroups     │  │ cgroups     │           │
│  └─────────────┘  └─────────────┘           │
│         dockerd / containerd / podman       │
└─────────────────────────────────────────────┘

vs VM: each guest has its own kernel under a hypervisor
```

| 観点 | VM | コンテナ |
|:---|:---|:---|
| 隔離 | ハードウェア/仮想HW | カーネルのnamespaces |
| 起動時間 | 分単位 | 秒単位 |
| 密度 | 低い | 高い |
| カーネル | ゲストごとに個別 | 共有 |
| 代表的なツール | KVM、VMware | Docker、Podman |

## 2. Linuxのプリミティブ — NamespacesとCgroups

カーネルは2つの隔離要素を提供します。namespacesはプロセスから見える範囲(PID、net、mountなど)を分離し、cgroupsはリソース使用量を制限します。

| Namespace | 隔離対象 |
|:---|:---|
| `pid` | プロセスID |
| `net` | インターフェース、ルート、ポート |
| `mnt` | マウントツリー |
| `uts` | ホスト名 |
| `ipc` | IPCオブジェクト |
| `user` | UID/GIDマッピング(rootless) |

cgroupsはCPU、メモリ、I/O、PID数を制限します。

Capabilityはrootの権限を分割したものです(`CAP_NET_BIND_SERVICE` など)。Dockerはデフォルトで多くのcapabilityを落としますが、`--cap-add` は攻撃対象領域を広げます。

```bash
# Peek at container namespaces (host admin, container ID from docker ps)
pid=$(docker inspect -f '{{.State.Pid}}' mycontainer)
sudo ls -l /proc/$pid/ns/
sudo cat /proc/$pid/cgroup
```

## 3. Dockerの基本ワークフロー

`docker.io`(Debian)または `docker-ce` をインストールします。`dockerd` デーモンがイメージとコンテナを管理します。

イメージは階層化された読み取り専用ファイルシステムとメタデータです。コンテナはその上に乗る書き込み可能なレイヤーです。デフォルトのレジストリはDocker Hubで、本番環境ではダイジェストを固定します。

```bash
# Install (Debian/Ubuntu lab)
sudo apt update && sudo apt install docker.io -y
sudo systemctl enable --now docker
sudo usermod -aG docker $USER   # re-login for group

# Pull & run
docker pull nginx:1.25-alpine
docker run -d --name web -p 8080:80 nginx:1.25-alpine
docker ps
docker logs web
docker stop web && docker rm web

# Inspect
docker inspect web
docker image ls
docker system df
```

| コマンド | 動作 |
|:---|:---|
| `docker pull` | イメージをダウンロード |
| `docker run` | コンテナを作成して起動 |
| `docker ps -a` | コンテナ一覧表示 |
| `docker exec -it` | 実行中コンテナ内でシェル起動 |
| `docker rm` / `docker rmi` | コンテナ/イメージを削除 |

## 4. Dockerfile と Docker Compose

Dockerfileはイメージビルドを定義し、Composeはラボや開発環境で複数コンテナをオーケストレーションします。

マルチステージビルドで最終イメージを小さくできます。秘密情報をレイヤーに埋め込まず、ビルドシークレットかvaultからのランタイム環境変数を使います。

**最小限のDockerfile:**

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER 1000:1000
EXPOSE 8000
CMD ["python", "-m", "http.server", "8000", "--bind", "0.0.0.0"]
```

```bash
docker build -t myapp:lab .
docker run -d -p 8000:8000 --read-only --tmpfs /tmp myapp:lab
```

**docker-compose.ymlのスケッチ:**

```yaml
services:
  web:
    image: nginx:alpine
    ports:
      - "127.0.0.1:8080:80"
    read_only: true
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: changeme
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

```bash
docker compose up -d
docker compose ps
docker compose logs -f web
docker compose down
```

## 5. Podman — rootless優先の代替手段

Podmanはデーモンレス(fork-execモデル)で、`docker` グループなしのrootlessコンテナに向いています。

CLIはDockerとほぼ互換です(`podman run`、`podman build`)。systemdとの統合は `podman generate systemd` で行います。

```bash
sudo apt install podman -y
podman run -d --name web -p 8080:80 docker.io/library/nginx:alpine
podman ps
podman exec -it web sh

# Rootless (unprivileged user)
podman run --rm -it alpine id
```

| Docker | Podmanでの相当コマンド |
|:---|:---|
| `docker` | `podman` |
| `docker compose` | `podman compose` |
| デーモンソケット | 中央デーモンなし |

## 6. 日常運用(Day-2 Operations)

コンテナが稼働し始めた後は、リソース監視、再起動ポリシー、ボリュームのバックアップ、ログローテーションが日常業務になります。

ホストの `/` やDockerソケットをコンテナへbind-mountすると、ホストレベルの権限をコンテナに与えてしまいます。これは本番環境のパターンでは禁止です。

```bash
# Resource stats
docker stats --no-stream

# Restart policies
docker run -d --restart unless-stopped nginx:alpine

# Volumes
docker volume create appdata
docker run -v appdata:/data alpine sh -c 'echo test > /data/file'

# Interactive debug (authorized)
docker exec -it mycontainer sh
docker cp mycontainer:/etc/nginx/nginx.conf ./nginx.conf.bak
```

## 7. セキュリティノート — 防御とブレイクアウトへの意識

安全な態勢とは、非root、`--privileged` を使わない、Dockerソケットをマウントしない、イメージを固定する、信頼できるレジストリでスキャンする、ということです。

コンテナエスケープの研究は許可されたラボ環境でのみ行います。防御側はcapabilityの削減、seccomp/AppArmorプロファイル、カーネルパッチ適用に注力します。

| 誤設定 | 影響 | 対策 |
|:---|:---|:---|
| `--privileged` | ホスト上でほぼroot相当の権限 | 避ける; capabilityを最小限に |
| `/var/run/docker.sock` のマウント | すべてのコンテナを制御できてしまう | 信頼できないワークロードでは絶対に行わない |
| コンテナ内でrootとして実行 | エスケープの連鎖が容易になる | Dockerfileで `USER` を非rootに |
| 本番での `:latest` 使用 | サプライチェーンのドリフト | ダイジェスト/バージョンを固定 |
| 公開レジストリのイメージ | マルウェア/バックドア | スキャン(Trivy/Grypeなど); 信頼できるレジストリ |
| env/ビルド引数内の秘密情報 | `docker inspect`/履歴からの漏洩 | シークレットマネージャー、ランタイムでの注入 |
| ホストネットワークモード `--network host` | ホストのネットワークスタックを共有 | 必要な場合を除きデフォルトのbridgeを使う |

```bash
# Defensive posture checks (authorized)
docker info 2>/dev/null | grep -i root
docker ps --quiet | xargs -r docker inspect -f '{{.Name}} privileged={{.HostConfig.Privileged}} caps={{.HostConfig.CapAdd}}'
# podman
podman ps --format '{{.Names}} {{.Privileged}}'
```

## 8. クイックリファレンスチートシート

```bash
# Docker
docker pull IMAGE
docker run -d --name N -p HOST:CONT PORT IMAGE
docker ps -a
docker logs -f N
docker exec -it N sh
docker stop N && docker rm N

# Build & Compose
docker build -t app:tag .
docker compose up -d
docker compose down

# Podman
podman run -d --name N -p 8080:80 nginx:alpine
podman ps

# Cleanup
docker system prune -f
```
