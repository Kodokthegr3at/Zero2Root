## 1. 階層的トラブルシューティングの手法

**ボトムアップ** あるいは **トップダウン** のアプローチを使い、各層での仮説と証拠を記録していきます。

```text
App → DNS → TCP/UDP → Routing → Interface → Physical
```

Linux サーバーでの典型的な流れは、**リンクが up か**、**IP アドレスは正しいか**、**デフォルトルートは存在するか**、**DNS は解決できるか**、**リモートポートに到達できるか**(`nc`/`curl`)の順に確認し、それでも原因が分からない場合に初めて **キャプチャ** に進むというものです。ICMP だけに頼って判断しないことが重要です。

```
Symptom: "curl https://app.internal fails"
  │
  ├─ ip link / ip addr        → interface up? correct IP?
  ├─ ip route                 → default gw present?
  ├─ ping gw                  → L2/L3 local OK?
  ├─ dig app.internal         → DNS resolves?
  ├─ curl -v / nc -vz         → TCP 443 reachable?
  └─ tcpdump on interface     → where packets die?
```

| 層 | 確認すること | ツール |
|:---|:---|:---|
| L1/L2 | ケーブル、VLAN、ブリッジは正常か | `ip link`, `ethtool` |
| L3 | IP とルートは正しいか | `ip addr`, `ip route`, `ping` |
| L4 | ポートは開いているか、フィルタされているか | `ss`, `nc`(許可された範囲で) |
| L7 | アプリ、TLS、HTTP は正常か | `curl -v`, `openssl s_client` |

## 2. 到達性 — `ping`, `traceroute`, `mtr`

**ICMP echo**(`ping`)は往復時間を測定し、**traceroute**、`tracepath`、**mtr** はホップごとの遅延とロスを示します。ファイアウォールが ICMP をブロックしていることは珍しくないため、ping が通らないからといって TCP も失敗しているとは限りません。TCP ベースのプローブと組み合わせて判断してください。

```bash
ping -c 4 10.10.14.1
ping -6 -c 4 2001:db8::1

traceroute 8.8.8.8
tracepath example.com
mtr -rwzc 50 example.com    # report mode, 50 cycles

# TCP-based traceroute alternative when ICMP blocked
sudo traceroute -T -p 443 example.com
```

| ツール | 表示内容 |
|:---|:---|
| `ping` | 単一ホストへの RTT とロス |
| `traceroute` | ホップごとのルーター(ICMP/UDP/TCP の各バリアント) |
| `mtr` | ping と traceroute を組み合わせた統計 |

## 3. ソケットと接続 — `ss` と `netstat`

**`ss`** は **`netstat`** の後継です。listen 中のポート、確立済みの接続、キューのバックログを確認できます。自分が管理するホストでのインシデント対応中は、`-p` オプションで不審な発信接続をプロセスに紐づけます。

```bash
ss -tulnp                    # listening TCP/UDP + process
ss -tan state established    # active TCP
ss -o state established '( dport = :443 )'

# Legacy
netstat -tulnp 2>/dev/null

# Bandwidth per socket (if installed)
sudo ss -ti
```

| ステート | 意味 |
|:---|:---|
| `LISTEN` | 着信接続を待機中 |
| `ESTAB` | アクティブなセッション |
| `TIME-WAIT` | クローズ側が 2MSL を待機中 |
| `SYN-RECV` | SYN フラッドまたはハーフオープン接続の可能性 |

## 4. パケットキャプチャ — `tcpdump`

**`tcpdump`** はインタフェース上を流れるフレーム/パケットをそのままキャプチャします。**`CAP_NET_RAW`** 権限か root が必要です。キャプチャは監視することを **許可されている** ネットワークやシステムに限定してください。pcap ファイルには平文 HTTP の場合に資格情報が含まれ得るため、暗号化して保管します。

```bash
# List interfaces
tcpdump -D

# Basic capture (lab)
sudo tcpdump -i eth0 -nn -c 20
sudo tcpdump -i eth0 -nn host 10.10.14.5 and port 443

# Write pcap for Wireshark
sudo tcpdump -i eth0 -w /tmp/capture.pcap -c 500
tcpdump -r /tmp/capture.pcap -nn | head

# Common filters
# tcp port 80
# icmp
# net 10.10.14.0/24
# not port 22
```

| フィルタ式 | マッチ条件 |
|:---|:---|
| `host X` | 送信元または宛先が X |
| `port 53` | TCP または UDP の 53番ポート |
| `tcp[tcpflags] & tcp-syn != 0` | SYN パケット |
| `vlan 100` | VLAN タグ(存在する場合) |

**Berkeley Packet Filter(BPF)** はユーザー空間へコピーされる前にカーネル内で処理されるため効率的です。

## 5. ARP と近隣探索 — `ip neigh`, `arp`

IPv4 の **ARP** は、ローカルセグメント内で IP アドレスを MAC アドレスに対応付けます。近隣テーブルは **`ip neigh`** で確認します。古くなった、あるいは汚染された ARP エントリは、通信障害の原因になったり、信頼できない LAN 上での MITM につながったりします。可能であればスイッチ側で DAI や 802.1X を使ってください。

```bash
ip neigh show
arp -n

# Clear single stale entry (careful on production)
sudo ip neigh del 10.10.14.1 dev eth0
sudo ip neigh flush dev eth0

# Link diagnostics
ethtool eth0
ethtool -S eth0 | head
```

## 6. アプリケーション層のプローブ — DNS と HTTP

L3/L4 に問題がないと分かったら、`dig`、`curl`、`openssl` で **DNS** と **HTTP/TLS** を確認します。`curl -v` はリダイレクト、証明書エラー、SNI の挙動を表示してくれるので、vHost や TLS のデバッグに非常に有効です。

```bash
dig +trace example.com A
dig @10.10.14.1 internal.lab A

curl -v http://127.0.0.1:8080/
curl -vk https://app.lab/health
curl -o /dev/null -w '%{http_code} time=%{time_total}\n' -s https://example.com/

# TLS handshake inspect
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -subject -dates

# TCP port probe
nc -vz 10.10.14.10 22
nc -vz -w 3 example.com 443
```

## 7. セキュリティ上の注意点 — 倫理と防御

キャプチャと ARP の調査は、管理する権限を **本当に持っている** システムやネットワークに限定してください。pcap は機微なデータです。プロミスキャスモードやパケットダンプはプライバシーへの影響が大きい操作です。自分が管理するホストでのインシデント対応中は、listener の情報を認証ログ(ノート28)と突き合わせます。

| 行為 | 許可される文脈 | 悪用リスク |
|:---|:---|:---|
| LAN 上での `tcpdump` | ポリシーのある SOC/NOC | 資格情報の窃取、プライバシー侵害 |
| ARP の調査 | 自分のサブネットのトラブルシューティング | 転送と組み合わせると MITM になり得る |
| `ss` によるプロセスの紐付け | 自分が管理するホストでの IR | 侵害済みの共有ホストでの偵察 |
| プロミスキャスモード | IDS センサー | 悪用されるとカバートチャネルになり得る |

**防御的なモニタリング:**

```bash
# Unexpected promiscuous interface?
ip link | grep PROMISC

# New listeners after change window
ss -tulnp | grep LISTEN

# Auth + network correlation (see note 28)
journalctl -u ssh --since "1 hour ago" | tail
```

関連: インタフェース設定はノート24、ファイアウォールのドロップはノート27、より詳しい IP の計算は `networking/IP Addressing & Subnetting.md` を参照してください。

## 8. クイックリファレンス チートシート

```bash
# Reachability
ping -c 4 GATEWAY
traceroute HOST
mtr -rw HOST

# Sockets
ss -tulnp
ss -tan state established

# Capture
sudo tcpdump -i eth0 -nn -c 50
sudo tcpdump -i eth0 -w out.pcap host X and port Y

# L2/L3
ip neigh show
ip route get 8.8.8.8

# App layer
dig A HOST +short
curl -v URL
nc -vz HOST PORT
```
