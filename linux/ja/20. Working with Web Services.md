## 1. Linux上のHTTPサービス — Webスタックの役割

LinuxにおけるWebサービスは通常、次のような流れをたどります。

$$
\text{Client} \xrightarrow{\text{HTTP/HTTPS}} \text{Listener (80/443)} \rightarrow \text{Daemon} \rightarrow \text{DocRoot} + \text{App}
$$

よく使われるデーモンはApache(`httpd`/`apache2`)、Nginx、時にCaddyです。その背後にはPHP-FPM、uWSGI、あるいはコンテナ化されたアプリへのリバースプロキシが存在することがあります。管理者はドキュメントルート、リスナーソケット、ログ、TLS証明書を理解しておく必要があります。

```
Internet / LAN
      │
      ▼
 ┌────────────┐     ┌──────────────┐
 │ Firewall   │────►│ nginx/apache │
 │ (ufw/nft)  │     │ :80 / :443   │
 └────────────┘     └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
           DocRoot      PHP-FPM      Upstream app
         /var/www/…                 127.0.0.1:8000
```

| ポート | プロトコル | 典型的な用途 |
|:---:|:---|:---|
| 80 | HTTP | HTTPSへのリダイレクト、またはACME |
| 443 | HTTPS | 本番トラフィック |
| 8080/8000 | HTTP | ローカル/開発用バインド(ループバック推奨) |

## 2. Apache HTTP Server

Debian/Ubuntuでは、`apache2` パッケージは次のようなレイアウトを使います。

| パス | 役割 |
|:---|:---|
| `/var/www/html/` | デフォルトのドキュメントルート |
| `/etc/apache2/apache2.conf` | メイン設定 |
| `/etc/apache2/ports.conf` | Listenディレクティブ |
| `/etc/apache2/sites-available/` | サイト定義 |
| `/etc/apache2/sites-enabled/` | 有効化されたシンボリックリンク |
| `/etc/apache2/mods-enabled/` | 有効なモジュール |
| `/var/log/apache2/` | `access.log`, `error.log` |

サイトは `a2ensite`、モジュールは `a2enmod` で有効化し、再読込の前に `apache2ctl configtest` を実行します。

```bash
sudo apt install apache2 -y
sudo systemctl enable --now apache2
sudo apache2ctl configtest
sudo a2enmod headers ssl rewrite
sudo a2ensite 000-default.conf
sudo systemctl reload apache2
systemctl status apache2 --no-pager
```

**最小限のハードニング案(Apache):**
- 使っていないモジュールを無効化する(`a2dismod`)。
- 必要な場合を除きIndexesを無効にするなど、`Directory` の設定を制限的にする。
- 専用のサービスユーザーを使い、docrootに `chmod -R 777` を絶対に行わない。

## 3. Nginx — イベント駆動サーバーとリバースプロキシ

Nginxはリバースプロキシと静的ファイルサーバーとして優れています。設定は以下の通りです。

| パス | 役割 |
|:---|:---|
| `/etc/nginx/nginx.conf` | グローバル設定 |
| `/etc/nginx/sites-available/` | server block |
| `/etc/nginx/sites-enabled/` | 有効化されたリンク |
| `/var/log/nginx/access.log` | アクセステレメトリ |
| `/var/log/nginx/error.log` | エラー |

`reload` の前には必ず `nginx -t` を実行します。アップストリームアプリは可能な限りlocalhostで待ち受けさせ、プロキシだけを外部に公開します。

```bash
sudo apt install nginx -y
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx
```

リバースプロキシの設定例(管理者教育用):

```nginx
server {
    listen 443 ssl http2;
    server_name app.example.com;
    # ssl_certificate     /etc/ssl/...;
    # ssl_certificate_key /etc/ssl/...;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## 4. TLS終端 — 管理者が押さえるべきこと

TLSはHTTPのレコード層に機密性と完全性を提供します。

$$
\text{HTTPS} = \mathsf{TLS}(\text{HTTP bytes}),\quad
\text{verify cert chain to trust anchor}
$$

| プラクティス | 理由 |
|:---|:---|
| TLS 1.2以降(理想的には1.3)を使う | 古いプロトコルを排除する |
| HTTPSが安定してからHSTSを導入する | SSLストリップのリスクを減らす |
| 秘密鍵のパーミッションを `600` rootに分離する | 鍵漏洩への耐性を高める |
| 更新を自動化する(例: ACME) | 証明書の失効を防ぐ |
| 80から443へリダイレクトする | 一貫したセキュリティUX |

```bash
# Inspect remote cert (ops / monitoring)
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
```

## 5. 軽量HTTPサーバー — ローカルラボ専用

ワンライナーのHTTPサーバーはローカルの試作(ドキュメントやループバック上の静的ファイル)に便利です。認証やTLSなしに信頼できないネットワークへ公開してはいけません。組み込みサーバーは許可されたローカル開発向けであり、デフォルトでは `127.0.0.1` にバインドします。`0.0.0.0` へのバインドは意図的な公開とみなし、ファイアウォールルールを必須とします。

```bash
# Prefer loopback for labs
python3 -m http.server 8000 --bind 127.0.0.1
php -S 127.0.0.1:8080
```

| ツール | 向いている用途 | 注意点 |
|:---|:---|:---|
| `python3 -m http.server` | 静的ファイル | 認証なし; ディレクトリ一覧表示 |
| `php -S` | PHPの簡易動作確認 | 本番非対応 |
| `npx http-server` | 静的SPAのプレビュー | ネットワークバインドを確認 |

## 6. 端末クライアント — `curl` と `wget`

`curl` はヘッダー確認、HTTPメソッドの検証、API のデバッグに向いています。`wget` はファイルのダウンロードや制御されたミラーリングに向いています。

これらのクライアントは自分が管理するサービスの検証、すなわちステータスコード、リダイレクト、TLS、レスポンスヘッダーの確認に使います。本番ホストではリモートのコンテンツを直接シェルへパイプしないでください。

```bash
curl -I https://localhost/                 # headers only
curl -v https://app.example.com/health     # verbose trace
curl -o /tmp/file.tgz https://example.com/file.tgz

wget -c https://example.com/large.iso      # resume
wget --spider https://example.com/         # reachability check
```

**安全な運用パターン:** ダウンロード、チェックサム確認、内容確認、そしてインストールの順に行います。

$$
\mathsf{Verify}(file) = \big(\mathrm{SHA256}(file) = \mathrm{SHA256}_{\text{published}}\big)
$$

## 7. バーチャルホスト(名前ベースのホスティング)

一つのIPで複数のドメイン名を提供できます。サーバーはHTTPの `Host:` ヘッダー(またはTLSのSNI)に基づいてvHostを選択します。

名前ベースのバーチャルホスティングは一つのリスナーに複数サイトを多重化します。誤設定されたデフォルトvHostはステージングサイトを漏らしがちです。`404`/`444` を返す明示的なデフォルトを設定してください。

```
Client request: GET / HTTP/1.1
Host: admin.example.com
        │
        ▼
   Match server_name / ServerName
        │
        ▼
   DocRoot or proxy for that site
```

```bash
# Test Host routing against your lab IP (authorized hosts only)
curl -H "Host: app.lab.local" http://127.0.0.1/

# Local name resolution for lab VMs you control
# (edit /etc/hosts only on machines you administer)
```

Apacheでは `sites-available/` 以下にファイルを分けます。Nginxでは `server { server_name … }` ブロックを分けます。

## 8. セキュリティノート — 防御とハードニング

| 誤設定 | 影響 | 対策 |
|:---|:---|:---|
| ディレクトリインデックス有効 | バックアップ、`.env`、ダンプの漏洩 | `Options -Indexes` / `autoindex off` |
| docrootが誰でも書き込み可(`777`) | 不正なコンテンツ改変 | ディレクトリ `755`、ファイル `644`; CI用ユーザーでデプロイ |
| デフォルトの `phpinfo` / `server-status` が公開状態 | 情報漏洩 | 削除するかIP+認証で制限 |
| ファイアウォールなしでアプリが `0.0.0.0` で待受 | リモート攻撃対象領域 | localhostにバインド; プロキシ; UFW/nftの許可リスト |
| HTTPのみの管理パネル | 認証情報の盗聴 | HTTPS強制、HSTS、強固な認証 |
| リモートスクリプトを直接シェルへパイプ | サプライチェーンリスク | チェックサムを検証; パッケージマネージャーを使う |
| 本番での詳細なエラーページ | パス/スタックの漏洩 | 汎用エラー; 詳細ログはサーバー側のみ保持 |

### ハードニングチェックリスト
1. ラボ以外のトラフィックにはすべてTLSを適用し、モダンな暗号方式を使う。
2. `www-data`/`nginx` ユーザーは最小権限にし、シェルログインを許可しない。
3. 書き込み可能なアップロードディレクトリと実行可能なスクリプトディレクトリを分ける。
4. アクセス/エラーログを中央のストアへ送り、4xx/5xxの急増を監視する。
5. パッケージを常に最新に保ち(`apt`/`dnf`)、使わないモジュールを削除する。
6. インターネットに面する場合はエッジにWAF/レート制限を置く。

```bash
# Posture snippets (admin)
namei -l /var/www/html | head
sudo apache2ctl -M 2>/dev/null | head
sudo nginx -T 2>/dev/null | grep -E 'listen|server_name|root' | head
ss -tulnp | grep -E ':80|:443'
```

## 9. クイックリファレンスチートシート

```bash
# Apache
sudo systemctl reload apache2
sudo apache2ctl configtest
sudo a2enmod ssl headers
sudo tail -f /var/log/apache2/error.log

# Nginx
sudo nginx -t && sudo systemctl reload nginx
sudo tail -f /var/log/nginx/access.log

# Clients
curl -I https://example.com
curl -o out.bin https://example.com/file
wget -c https://example.com/file

# Local static (loopback)
python3 -m http.server 8000 --bind 127.0.0.1
```
