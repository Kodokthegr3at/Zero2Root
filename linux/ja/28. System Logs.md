## 1. Linuxのロギングアーキテクチャ

現代のLinuxは通常、2つのテレメトリ経路を並行して運用します。

1. `systemd-journald`、構造化されたバイナリログで `journalctl` から問い合わせます。
2. `rsyslog` / `syslog-ng`、`/var/log/` 以下の従来型テキストファイルです。

これらは合わせて認証、カーネルイベント、サービスのstdout/stderr、アプリケーションのメッセージを記録します。防御側はログを証拠として扱います。整合性と保持期間は内容と同じくらい重要です。

```
 Kernel / services / apps
            │
            ▼
     ┌──────────────┐
     │ journald     │────► journalctl queries
     └──────┬───────┘
            │ (forward)
            ▼
     ┌──────────────┐
     │ rsyslog      │────► /var/log/*.log
     └──────┬───────┘
            │
            ▼
     SIEM / remote syslog (optional)
```

## 2. Syslogのファシリティと重要度(形式)

従来のsyslogは各メッセージにファシリティ $f$ と重要度 $p$ のラベルを付けます。

$$
\text{priority} = 8f + p
$$

| 重要度 $p$ | 名前 | 意味 |
|:---:|:---|:---|
| 0 | emerg | システム使用不能 |
| 1 | alert | 即座の対応が必要 |
| 2 | crit | 危機的な状態 |
| 3 | err | エラー |
| 4 | warning | 警告 |
| 5 | notice | 通常だが注意すべき事象 |
| 6 | info | 情報 |
| 7 | debug | デバッグ |

主なファシリティ: `auth`/`authpriv`、`kern`、`daemon`、`cron`、`local0〜7`。

```bash
# Emit a test message (lab)
logger -p auth.notice "lab test auth notice from $(whoami)"
```

## 3. `/var/log` 内の主要ファイル

| ファイル | ディストロ系統 | 内容 |
|:---|:---|:---|
| `auth.log` | Debian/Ubuntu | SSH、sudo、PAM、ユーザー認証 |
| `secure` | RHEL系 | `auth.log` と同じ役割 |
| `syslog` / `messages` | Debian / RHEL | 一般的なシステムイベント |
| `kern.log` | Debian | カーネルメッセージ(テキスト) |
| `wtmp` / `btmp` | 全般 | ログイン成功/失敗(バイナリ) |
| `lastlog` | 全般 | ユーザーごとの最終ログイン |
| `apache2/` / `nginx/` | Webスタック | アクセス + エラー |
| `audit/` | auditdホスト | SELinux/監査の記録 |

```bash
ls -lah /var/log
sudo tail -n 50 /var/log/auth.log     # Debian family
sudo tail -n 50 /var/log/secure       # RHEL family
```

| ツール | 読み取り対象 | 用途 |
|:---|:---|:---|
| `last` | `wtmp` | ログイン成功記録 |
| `lastb` | `btmp` | ログイン失敗記録(root) |
| `who` / `w` | `utmp` | 現在のセッション |
| `zgrep` | `*.gz` | ローテート済みログの検索 |

## 4. `journalctl` — ジャーナルへの問い合わせ

`journalctl` はユニット、時間、優先度、起動セッションでフィルタします。

インシデント対応中は時間範囲を絞ったクエリを優先し、ノイズに埋もれないようにします。

```bash
journalctl -f                              # follow
journalctl -b                              # current boot
journalctl -u ssh.service                  # one unit
journalctl -u nginx --since "1 hour ago"
journalctl --since "2026-08-01" --until "2026-08-16"
journalctl -p err..emerg                   # severities
journalctl -k                              # kernel via journal
journalctl --disk-usage
journalctl --no-pager -o short-iso
```

永続ジャーナル: `/var/log/journal/` 以下にストレージを有効化し、`/etc/systemd/journald.conf` で保持設定(`SystemMaxUse=`、`MaxRetentionSec=`)を行います。

## 5. `dmesg` — カーネルのリングバッファ

`dmesg` はカーネルの循環バッファを読み取ります。ハードウェアの検出、OOMイベント、ドライバーエラー、segfaultの通知などです。

リングバッファは有限で揮発性です。重要なカーネルイベントは、より長い保持のためにジャーナルやsyslogにも記録されるべきです。

```bash
sudo dmesg -T
sudo dmesg -l err,crit
sudo dmesg -T | grep -iE 'error|fail|oom|segfault'
```

## 6. `logrotate` — ディスクを埋めない保持管理

ローテーションがないと、ログがディスクを埋め尽くし可用性のDoSを引き起こします。`logrotate` は古い世代をアーカイブ、圧縮、破棄します。

フォレンジックの必要性(長い保持期間)とディスクコストのバランスを取ります。積極的な削除の前にホスト外へコピーを送ります。

| ディレクティブ | 意味 |
|:---|:---|
| `daily` / `weekly` | 頻度 |
| `rotate N` | N世代保持 |
| `compress` | 古いログをgzip圧縮 |
| `delaycompress` | 次のサイクルから圧縮開始 |
| `missingok` | ファイルがなければスキップ |
| `notifempty` | 空のファイルはスキップ |

パス: `/etc/logrotate.conf`、`/etc/logrotate.d/*`。

```bash
sudo logrotate -d /etc/logrotate.conf     # debug / dry
sudo logrotate -f /etc/logrotate.conf     # force (careful)
zgrep "Failed password" /var/log/auth.log.*.gz
```

## 7. 防御的なハンティング — 認証と権限のテレメトリ

以下は検知の例であり、反フォレンジックの手法ではありません。SSHのブルートフォース、sudoの悪用、勤務時間外のログインなどです。

これらのワンライナーは、自分が所有するシステムにおいて管理者やblue teamの助けになります。ファイアウォール/Fail2Banのデータやチケットのタイムラインと突き合わせます。

```bash
# Top sources of failed SSH passwords (Debian auth.log)
sudo grep "Failed password" /var/log/auth.log \
  | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr | head

# Successful sudo commands (audit trail)
sudo grep "COMMAND=" /var/log/auth.log | tail -n 30

# Session history
last -n 20
sudo lastb -n 20

# Journal view of ssh
journalctl -u ssh --since "24 hours ago" | grep -i fail
```

Web側の防御担当者は、アクセスログでの `404`/`401`/`500` の急増もスキャンやアプリの不具合の兆候として監視しますが、ログをエクスプロイトの経路として扱うことはありません。

## 8. セキュリティノート — 防御とハードニング

| リスク | 影響 | 対策 |
|:---|:---|:---|
| ログがホストにしかない | rootを奪った攻撃者がローカルファイルを改ざんできる | リモートsyslog/SIEM; 可能ならappend-only/WORM |
| 誰でも読める認証ログ | 資格情報に近い情報の漏洩 | `/var/log` のパーミッションを制限; `authpriv` を分離 |
| 時刻同期がない | タイムラインが壊れる | NTP/chrony; UTCで保存 |
| 保持期間が短すぎる | 調査が行えなくなる | ポリシーに合わせる; オフサイトのコピーを保持 |
| 信頼できないアプリがユーザー制御の文字列をログに書き込む | ログの扱いを誤ると混乱や二次的なバグが起きる | ログファイルをアプリコードに `include` しない; 表示をサニタイズ; ログはコードではなくデータとして扱う |
| 詳細デバッグによるディスクフル | 可用性の停止 | `logrotate`、ジャーナルサイズの上限、レート制限 |
| `btmp`/`lastb` の無視 | ブルートフォースの見逃し | 閾値によるアラート; Fail2Ban |

### 整合性のプラクティス
1. `auth` と重要なユニットをTLS経由でコレクターへ転送する。
2. 非rootで `journalctl` を実行できる人を制限する(systemdのACL/グループを慎重に設定)。
3. 突然のジャーナルの欠落(時刻の飛び、消去された範囲)をインシデントの兆候として監視し、「消去の練習」ではなくバックアップ/SIEM経由で調査する。
4. 高保証ホストでは `auditd` のルールを保護する。
5. エクスポートした証拠ファイル(ハッシュ)のチェーン・オブ・カストディを文書化する。

```bash
# Health / posture
journalctl --disk-usage
timedatectl status
sudo ss -tulnp | grep -E 'syslog|514'
```

## 9. クイックリファレンスチートシート

```bash
# Live tails
sudo tail -f /var/log/auth.log
sudo tail -f /var/log/syslog
journalctl -f

# Journal filters
journalctl -u ssh.service -p err..warning
journalctl -b -p err

# Kernel
sudo dmesg -T | tail

# Sessions
who; w; last -n 10

# Compressed search
zgrep -H "error" /var/log/syslog.*.gz
```
