この教材でよく出てくる言葉である。

| 用語 | 意味 |

| 攻撃対象領域 | 攻撃者が狙えるすべて: 開いたポート、ユーザー、ソフトウェア |

| パッチ適用 | 既知の脆弱性を直す更新を導入すること |

## 1. Linux セキュリティの目標 — 攻撃対象領域を縮小する

ハードニングとは、業務機能を壊さずに露出を減らすことです。

リスクは、資産の価値、脅威の多さ、システムの弱点の多さ、そして露出の大きさに比例して大きくなります。

私たちが減らすのは **露出(Exposure)**(ポート、パッケージ、ユーザー、権限)と **脆弱性(Vulnerabilities)**(パッチ適用、安全な設定)です。ハードニング済みのホストは、リスナーの数が少なく、インストール済みパッケージが少なく、最小権限が徹底されており、MAC が実際に強制モードで動作し、管理チャネルが暗号化され、認証ログが監視されています。

```
          Before                         After (sketch)
   ┌─────────────────┐              ┌─────────────────┐
   │ Many packages   │              │ Minimal packages│
   │ Open ports **** │     ───►     │ Only 22/443     │
   │ Password SSH    │              │ Keys only SSH   │
   │ MAC complain    │              │ MAC enforcing   │
   └─────────────────┘              └─────────────────┘
```

| 柱 | 具体的な統制例 |
|:---|:---|
| アイデンティティ | 強力な認証、root SSH の共有をしない |
| ネットワーク | デフォルト拒否のファイアウォール |
| ソフトウェア | 署名済みアップデート、最小構成 |
| 権限 | sudo の範囲を限定、NOPASSWD:ALL は使わない |
| 検知 | journal/auth をアラートへ転送 |
| 復旧 | テスト済みのバックアップ(ノート21) |

## 2. アクセス制御 — DAC, MAC, RBAC

| モデル | 誰が決定するか | Linux での仕組み |
|:---|:---|:---|
| **DAC** | リソースの所有者 | `chmod`/`chown` のモードビット |
| **MAC** | システムポリシー | SELinux, AppArmor |
| **RBAC** | ロールの割り当て | グループ + `sudo` + ポリシー |

Unix のモードビットのおさらいです。

```text
  s       rwx     rwx     rwx
special   user    group   other

chmod 750 file   →   rwx r-x ---
```

DAC の設定が正しくても、**MAC** がプロセスを閉じ込めていない限り、乗っ取られた `root` によって迂回されてしまいます。

## 3. 多層防御(Defense-in-Depth) — 独立した統制の積み重ね

効果的な Linux セキュリティは、互いに独立した統制を積み重ねる構造を持ちます。どれか一つの層が破られても、ホストが即座に丸ごと開放されることはありません。

| 層 | Linux での例 | 詳細ノート |
|:---|:---|:---|
| ネットワークの境界 | ルーター ACL, VPN | `networking/` モジュール |
| **ホストファイアウォール** | iptables, UFW, firewalld | **ノート27** |
| トランスポート/管理 | SSH 鍵, TLS | このノートの §4 |
| OS のアイデンティティ | PAM, sudo, shadow | **ノート15** |
| オブジェクトの権限 | chmod, SUID 監査 | **ノート14** |
| MAC | SELinux, AppArmor | 下記 §7 |
| モニタリング | 認証ログ, journal | **ノート28** |

ネットワーク、ホストファイアウォール、認証、MAC、ログという順で層を設計します。

```
Internet
   │
   ▼
Edge firewall / WAF
   │
   ▼
Host firewall (note 27) ── default deny inbound
   │
   ▼
SSH/TLS hardened admin path (§4)
   │
   ▼
DAC + sudo RBAC + MAC (§2, §7)
   │
   ▼
Logging & alerting (note 28)
```

**原則:** ネットワーク境界ではデフォルト拒否、あらゆる場所で最小権限、そして侵害は起きるものと想定して被害範囲を限定します。

## 4. OpenSSH のハードニング — `/etc/ssh/sshd_config`

### 基本ディレクティブ

| ディレクティブ | ハードニング後の値 | 目的 |
|:---|:---|:---|
| `PermitRootLogin` | `no` | root への直接ログインを禁止 |
| `PasswordAuthentication` | `no` | 鍵認証のみ |
| `PubkeyAuthentication` | `yes` | 鍵認証を有効化 |
| `KbdInteractiveAuthentication` | `no` | 認証面を減らす |
| `MaxAuthTries` | `3` | 総当たりを遅くする |
| `AllowUsers` / `AllowGroups` | 明示指定 | アカウントの許可リスト |
| `X11Forwarding` | `no`(未使用の場合) | 攻撃対象領域を減らす |
| `ClientAliveInterval` | 例: `300` | 放置されたセッションを切断 |

```bash
# Audit effective non-comment config
sudo sshd -T | egrep 'permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries'

# Validate before restart
sudo sshd -t && sudo systemctl reload ssh
```

**展開時のコツ:** 設定変更のテスト中は別セッションを開いたままにしておき、リモートならコンソールやクラウドのシリアルアクセスを用意しておきます。

管理用の鍵を生成します(管理者のワークステーション上で実行)。

```bash
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_admin
# install public key to ~/.ssh/authorized_keys on server (mode 600)
```

## 5. Fail2Ban — 自動対応

Fail2Ban はログを監視し、一定の時間窓の中で N 回失敗すると、その IP をファイアウォールで T 秒間 ban します。

Fail2Ban は鍵認証のみの SSH やファイアウォールの許可リストを補完するものであり、それらの代わりにはなりません。

```bash
sudo apt install fail2ban -y
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
sudo fail2ban-client set sshd unbanip 203.0.113.50
```

jail.local の `findtime`、`maxretry`、`bantime` を調整し、管理用の NAT はホワイトリストに慎重に登録してください。

## 6. `sysctl` によるカーネルハードニング

役立つ防御的パラメータです(自分のワークロードに対して検証してから適用してください)。

| パラメータ | 値 | 意図 |
|:---|:---:|:---|
| `net.ipv4.tcp_syncookies` | `1` | SYN フラッドへの耐性 |
| `net.ipv4.conf.all.accept_redirects` | `0` | 悪意ある ICMP リダイレクトへの耐性 |
| `net.ipv4.conf.all.accept_source_route` | `0` | ソースルーティングされたパケットを破棄 |
| `net.ipv4.conf.all.log_martians` | `1` | あり得ないアドレスをログに記録 |
| `net.ipv4.icmp_echo_ignore_broadcasts` | `1` | smurf 攻撃的なノイズの抑制 |
| `kernel.randomize_va_space` | `2` | 完全な ASLR |
| `fs.protected_hardlinks` | `1` | ハードリンクの安全性 |
| `fs.protected_symlinks` | `1` | シンボリックリンクの安全性 |
| `kernel.yama.ptrace_scope` | `1` または `2` | プロセストレースの制限 |

```bash
sudo tee /etc/sysctl.d/99-hardening.conf << 'EOF'
net.ipv4.tcp_syncookies = 1
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.icmp_echo_ignore_broadcasts = 1
kernel.randomize_va_space = 2
fs.protected_hardlinks = 1
fs.protected_symlinks = 1
EOF
sudo sysctl --system
cat /proc/sys/kernel/randomize_va_space   # expect 2
```

ASLR の直感的な理解は、ベースアドレスをランダム化することで、固定オフセットを前提にした素朴なメモリ破壊攻撃を当てにならなくする、というものです。

`randomize_va_space=2` の設定では、正しいアドレスを推測できる確率はごくわずかです。

## 7. 強制アクセス制御 — AppArmor と SELinux

| フレームワーク | 対象ディストリビューション | モデル |
|:---|:---|:---|
| **AppArmor** | Ubuntu/Debian | パスベースのプロファイル |
| **SELinux** | Fedora/RHEL/Alma/Rocky | ラベル/タイプによる強制 |

```bash
# AppArmor
sudo aa-status
sudo aa-enforce /etc/apparmor.d/usr.sbin.nginx   # example

# SELinux
getenforce
sudo setenforce 1                                # enforcing until reboot policy
# persistent: SELINUX=enforcing in /etc/selinux/config
```

**方針:** 本番環境では **enforcing** モードを優先し、complain/permissive はプロファイルを開発している間だけ使い、その後は締め直します。

## 8. 素早くパッチを当て、インストールは最小限に

インストールされたパッケージや待ち受けポートが1つ増えるたびに、攻撃対象領域は広がります。

```bash
# Debian/Ubuntu
sudo apt update && sudo apt upgrade
sudo apt install unattended-upgrades
sudo dpkg-query -f '${binary:Package}\n' -W | wc -l

# RHEL family
sudo dnf upgrade
sudo dnf install dnf-automatic

# Listeners audit
ss -tulnp
systemctl list-units --type=service --state=running
```

使っていないサービスは無効化します(`systemctl disable --now …`)。ポリシーが許すなら、本番のエッジホストからコンパイラや余分なインタプリタを削除します。

## 9. セキュリティ上の注意点 — 防御チェックリスト

| 統制領域 | 確認内容 | 是正方法 |
|:---|:---|:---|
| アップデート | サポート対象のリリースか、直近のセキュリティ更新が適用されているか | 自動セキュリティ更新を有効化 |
| SSH | `sshd -T` でパスワード/root ログインが無効か | 鍵 + AllowUsers + ファイアウォール |
| ファイアウォール | デフォルト拒否、許可は最小限か | UFW/nft のルールをレビュー |
| MAC | プロファイル/ラベルが enforcing か | denial は正しく修正し、MAC 自体を無効化しない |
| Sudo | 広範な `NOPASSWD: ALL` がないか | コマンド単位で制限、グループを活用 |
| SUID/SGID の棚卸し | 特殊ビットを定期的にレビュー | 不要な setuid を削除 |
| world-writable なディレクトリ | 特に cron/backup のパス | 所有者とモードを修正 |
| ログ | auth と journal が保持/転送されているか | ノート28の実践 |
| バックアップ | 暗号化され、復元テスト済みか | ノート21の実践 |
| ファイアウォール | デフォルト拒否、許可がドキュメント化されているか | ノート27のルール |
| 機密情報 | web root や誰でも読める home に鍵がないか | 鍵は `600`、vault/HSM を使う |

```bash
# Defensive audit snippets (authorized admin)
sshd -T | egrep 'permitrootlogin|passwordauthentication'
sudo ufw status verbose
getenforce 2>/dev/null; sudo aa-status 2>/dev/null | head
find /usr -perm -4000 -type f 2>/dev/null | head   # inventory only
sudo grep -R "NOPASSWD" /etc/sudoers /etc/sudoers.d 2>/dev/null
```

この SUID バイナリの棚卸しは、自分が管理するシステムでの **削減とモニタリング** のためのものであり、悪用のためのレシピ集ではありません。

### 多層防御のスタック
```
Users/Apps
   │  DAC (chmod) + sudo RBAC
   ▼
MAC (AppArmor/SELinux)
   │
   ▼
Kernel hardening (ASLR, sysctl)
   │
   ▼
Host firewall (note 27) + Fail2Ban
   │
   ▼
Network edge / WAF / VPN
```
