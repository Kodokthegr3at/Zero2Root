## 1. HTTP Services on Linux — Role of the Web Stack

A web service on Linux typically follows this flow:

```text
Client --HTTP/HTTPS--> Listener (80/443) → Daemon → DocRoot + App
```

Common daemons include Apache (`httpd`/`apache2`), Nginx, and sometimes Caddy. Behind them there may be PHP-FPM, uWSGI, or a reverse proxy to a containerized app. Administrators need to understand document roots, listener sockets, logs, and TLS certificates.

```
Internet / LAN
      │
      ▼
 ┌────────────┐     ┌──────────────┐
 │ Firewall   │────►│ nginx/apache │
 │ (ufw/nft)  │     │ :80 / :443   │
 └────────────┘     └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
           DocRoot      PHP-FPM      Upstream app
         /var/www/…                 127.0.0.1:8000
```

| Port | Protocol | Typical use |
|:---:|:---|:---|
| 80 | HTTP | Redirect to HTTPS or ACME |
| 443 | HTTPS | Production traffic |
| 8080/8000 | HTTP | Local/dev bind (prefer loopback) |

## 2. Apache HTTP Server

On Debian/Ubuntu, the `apache2` package uses this layout:

| Path | Role |
|:---|:---|
| `/var/www/html/` | Default document root |
| `/etc/apache2/apache2.conf` | Main config |
| `/etc/apache2/ports.conf` | Listen directives |
| `/etc/apache2/sites-available/` | Site definitions |
| `/etc/apache2/sites-enabled/` | Enabled symlinks |
| `/etc/apache2/mods-enabled/` | Active modules |
| `/var/log/apache2/` | `access.log`, `error.log` |

Enable sites with `a2ensite`, modules with `a2enmod`, then run `apache2ctl configtest` before reloading.

```bash
sudo apt install apache2 -y
sudo systemctl enable --now apache2
sudo apache2ctl configtest
sudo a2enmod headers ssl rewrite
sudo a2ensite 000-default.conf
sudo systemctl reload apache2
systemctl status apache2 --no-pager
```

**Minimal hardening ideas (Apache):**
- Disable unused modules (`a2dismod`).
- Set restrictive `Directory` options (no Indexes unless required).
- Prefer a dedicated service user; never `chmod -R 777` on the docroot.

## 3. Nginx — Event-Driven Server & Reverse Proxy

Nginx excels as a reverse proxy and static file server. Its configuration:

| Path | Role |
|:---|:---|
| `/etc/nginx/nginx.conf` | Global settings |
| `/etc/nginx/sites-available/` | Server blocks |
| `/etc/nginx/sites-enabled/` | Enabled links |
| `/var/log/nginx/access.log` | Access telemetry |
| `/var/log/nginx/error.log` | Errors |

Always run `nginx -t` before `reload`. Upstream apps should listen on localhost when possible; expose only the proxy.

```bash
sudo apt install nginx -y
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx
```

Example reverse proxy sketch (admin education):

```nginx
server {
    listen 443 ssl http2;
    server_name app.example.com;
    # ssl_certificate     /etc/ssl/...;
    # ssl_certificate_key /etc/ssl/...;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## 4. TLS Termination — Admin Essentials

TLS provides confidentiality and integrity for the HTTP record layer:

HTTPS is simply HTTP sent inside a TLS connection, and the client checks the server's certificate chain up to a trusted root.

| Practice | Why |
|:---|:---|
| Prefer TLS 1.2+ (ideally 1.3) | Drop obsolete protocols |
| HSTS after HTTPS is proven | Reduce SSL-strip risk |
| Separate privkey permissions `600` root | Resist key leakage |
| Automate renewal (e.g. ACME) | Avoid expired certs |
| Redirect 80→443 | Consistent security UX |

```bash
# Inspect remote cert (ops / monitoring)
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
```

## 5. Lightweight HTTP Servers — Local Lab Only

One-liner HTTP servers are useful for local prototyping, such as documentation or static files on loopback. Do not expose them to an untrusted network without authentication or TLS. Built-in servers are meant for authorized local development; they bind to `127.0.0.1` by default, and anything bound to `0.0.0.0` should be treated as an intentional exposure requiring firewall rules.

```bash
# Prefer loopback for labs
python3 -m http.server 8000 --bind 127.0.0.1
php -S 127.0.0.1:8080
```

| Tool | Good for | Caution |
|:---|:---|:---|
| `python3 -m http.server` | Static files | No auth; directory listing |
| `php -S` | Quick PHP smoke tests | Not production |
| `npx http-server` | Static SPA previews | Review network bind |

## 6. Terminal Clients — `curl` & `wget`

`curl` is useful for header inspection, HTTP methods, and API debugging. `wget` is useful for file downloads and controlled mirroring.

Use these clients to verify your own services: status codes, redirects, TLS, and response headers. Avoid piping remote content directly into a shell on production hosts.

```bash
curl -I https://localhost/                 # headers only
curl -v https://app.example.com/health     # verbose trace
curl -o /tmp/file.tgz https://example.com/file.tgz

wget -c https://example.com/large.iso      # resume
wget --spider https://example.com/         # reachability check
```

**Safe ops pattern:** download, checksum, inspect, then install.

```text
sha256sum file    →  must match the hash published by the vendor
```

## 7. Virtual Hosts (Name-Based Hosting)

A single IP can serve many domain names. The server picks a vHost based on the HTTP `Host:` header (or SNI over TLS).

Name-based virtual hosting multiplexes sites on one listener. A misconfigured default vHost often leaks staging sites; set an explicit default that returns `404`/`444`.

```
Client request: GET / HTTP/1.1
Host: admin.example.com
        │
        ▼
   Match server_name / ServerName
        │
        ▼
   DocRoot or proxy for that site
```

```bash
# Test Host routing against your lab IP (authorized hosts only)
curl -H "Host: app.lab.local" http://127.0.0.1/

# Local name resolution for lab VMs you control
# (edit /etc/hosts only on machines you administer)
```

Apache separates files under `sites-available/`. Nginx separates `server { server_name … }` blocks.

## 8. Security Notes — Defense / Hardening

| Misconfiguration | Impact | Defense |
|:---|:---|:---|
| Directory indexing enabled | Leaks backups, `.env`, dumps | `Options -Indexes` / `autoindex off` |
| Docroot world-writable (`777`) | Unauthorized content change | `755` dirs, `644` files; deploy via a CI user |
| Default `phpinfo` / `server-status` public | Information disclosure | Remove or restrict by IP + auth |
| App listens on `0.0.0.0` without a firewall | Remote attack surface | Bind localhost; proxy; UFW/nft allowlist |
| HTTP-only admin panels | Credential sniffing | Force HTTPS, HSTS, strong auth |
| Piping remote scripts to a shell | Supply-chain risk | Verify checksums; use package managers |
| Verbose error pages in production | Path/stack leaks | Generic errors; detailed logs kept server-side |

### Hardening checklist
1. TLS everywhere for non-lab traffic, with modern ciphers.
2. Least privilege for `www-data`/`nginx` users, no shell login.
3. Separate writable upload directories from executable script directories.
4. Ship access/error logs to a central store; monitor 4xx/5xx spikes.
5. Keep packages updated (`apt`/`dnf`); remove unused modules.
6. Add a WAF/rate-limit at the edge when facing the internet.

```bash
# Posture snippets (admin)
namei -l /var/www/html | head
sudo apache2ctl -M 2>/dev/null | head
sudo nginx -T 2>/dev/null | grep -E 'listen|server_name|root' | head
ss -tulnp | grep -E ':80|:443'
```
