## 1. Network Services on Linux — The Daemon Layer

A network service is a daemon that listens on a socket (TCP/UDP) and serves a network protocol: DNS, DHCP, NFS, SMB, SSH, HTTP, and similar. A Linux administrator needs to know who is listening, on which port, and where the configuration lives.

$$
\text{Client request} \xrightarrow{\text{L3/L4}} \text{Listener (port)} \rightarrow \text{Daemon} \rightarrow \text{Config + data}
$$

Linux hosts often run both client and server network roles. Client config lives in `/etc/resolv.conf`, NetworkManager, or systemd-networkd; server roles use dedicated packages (`bind9`, `isc-dhcp-server`, `nfs-kernel-server`, `samba`).

```
Application                Kernel network stack
     │                              │
     │                              │
  dig/curl/mount.nfs  ←→  socket bind :53/:445/:2049
                                    │
                                    ▼
                            named / smbd / nfsd
```

| Service | Default port(s) | Package (Debian) | Config hub |
|:---|:---:|:---|:---|
| DNS resolver (client) | none | `systemd-resolved` | `/etc/resolv.conf`, `/etc/systemd/resolved.conf` |
| DNS server | 53/tcp,udp | `bind9` | `/etc/bind/` |
| DHCP server | 67/udp | `isc-dhcp-server` | `/etc/dhcp/dhcpd.conf` |
| NFS | 2049/tcp | `nfs-kernel-server` | `/etc/exports` |
| Samba (SMB) | 445/tcp | `samba` | `/etc/samba/smb.conf` |
| SSH | 22/tcp | `openssh-server` | `/etc/ssh/sshd_config` |

## 2. Name Resolution — DNS & `/etc/hosts`

Before querying external DNS, Linux checks `/etc/hosts` (static) first, then falls back to the resolver, usually `systemd-resolved` or `/etc/resolv.conf`.

Resolution order is governed by NSS (`/etc/nsswitch.conf`):

$$
\text{gethostbyname} \rightarrow \texttt{files} \rightarrow \texttt{dns} \rightarrow \texttt{\ldots}
$$

Use `dig`, `host`, or `resolvectl` to debug resolution. Misconfigured DNS leaks queries or enables spoofing on untrusted networks; prefer trusted resolvers and DNSSEC where policy requires it.

```bash
# Static local names (lab VMs you administer)
cat /etc/hosts
# 127.0.0.1   localhost
# 10.10.14.5  target.lab

# Resolver state
resolvectl status
cat /etc/resolv.conf

# Query DNS (authorized targets)
dig A example.com +short
dig MX example.com +short
host -t TXT example.com
nslookup example.com
```

| File / tool | Role |
|:---|:---|
| `/etc/hosts` | Static hostname to IP mapping |
| `/etc/resolv.conf` | Nameserver list (often symlinked to systemd-resolved) |
| `/etc/systemd/resolved.conf` | Stub listener `127.0.0.53`, DNS over TLS options |
| `dig` / `host` | Diagnostic queries |
| `systemd-resolved` | Caching stub resolver on modern distros |

**Minimal BIND server sketch (lab only):**

```bash
sudo apt install bind9 -y
# /etc/bind/named.conf.local — zone definition for lab.internal
sudo named-checkconf
sudo systemctl reload bind9
dig @127.0.0.1 lab.internal SOA
```

## 3. DHCP — Dynamic Host Configuration

DHCP assigns an IP, gateway, DNS, and other options to clients. On Linux desktops and servers, the client is usually NetworkManager or `dhclient`; running a DHCP server at the edge is rare outside of lab environments.

The client lease lifecycle follows DISCOVER → OFFER → REQUEST → ACK. Renewals happen at $T/2$. Monitor leases on the server side to catch a rogue DHCP server, an attacker on the LAN offering a bad gateway or DNS.

```bash
# Client: view lease (NetworkManager)
nmcli dev show eth0 | grep -E 'IP4.ADDRESS|IP4.GATEWAY|IP4.DNS'

# Client: release / renew (legacy)
sudo dhclient -r eth0
sudo dhclient eth0

# Server config snippet (/etc/dhcp/dhcpd.conf) — lab
# subnet 10.10.14.0 netmask 255.255.255.0 {
#   range 10.10.14.100 10.10.14.200;
#   option routers 10.10.14.1;
#   option domain-name-servers 10.10.14.1;
# }
sudo systemctl enable --now isc-dhcp-server
```

| DHCP risk | Mitigation |
|:---|:---|
| Rogue DHCP on LAN | DHCP snooping on switches; 802.1X |
| Stale leases | Short lease times in dynamic pools |
| No logging | Log assignments on the authoritative server |

## 4. NFS — Network File System

NFS mounts a remote directory through the kernel client. The server defines an export in `/etc/exports`; the client uses `mount -t nfs`.

NFSv4 simplifies ports (2049/tcp) compared with legacy NFSv3 (rpcbind plus several ports). Never export a world-writable path without strong authentication; prefer Kerberos (`sec=krb5p`) in production.

```bash
# Server
sudo apt install nfs-kernel-server -y
echo '/srv/nfs/share 10.10.14.0/24(rw,sync,no_subtree_check)' | sudo tee -a /etc/exports
sudo exportfs -ra
sudo systemctl enable --now nfs-server
showmount -e localhost

# Client (authorized lab network)
sudo mkdir -p /mnt/nfs_share
sudo mount -t nfs 10.10.14.10:/srv/nfs/share /mnt/nfs_share
df -hT /mnt/nfs_share
# Persistent: add to /etc/fstab
# 10.10.14.10:/srv/nfs/share  /mnt/nfs_share  nfs  defaults  0  0
```

| Export option | Meaning |
|:---|:---|
| `rw` / `ro` | Read-write vs read-only |
| `sync` | Safer; `async` is faster but riskier on a crash |
| `no_root_squash` | Dangerous, remote root maps to local root |
| `root_squash` | Default, safer mapping |

## 5. Samba — SMB/CIFS File Sharing

Samba (`smbd`/`nmbd`) serves the Windows SMB protocol so Linux can share folders to Windows/macOS or mount a Windows share.

Shares are configured in `/etc/samba/smb.conf`. Use `smbpasswd` for Samba users (separate from the Unix password unless integrated). Test with `testparm` before every reload.

```bash
sudo apt install samba -y
sudo testparm -s

# Minimal share block in smb.conf:
# [shared]
#   path = /srv/samba/shared
#   browseable = yes
#   read only = no
#   valid users = alice

sudo smbpasswd -a alice
sudo systemctl enable --now smbd nmbd

# Client mount (authorized)
sudo mount -t cifs //10.10.14.10/shared /mnt/smb -o username=alice,uid=1000
smbclient -L //10.10.14.10 -U alice
```

| Check | Command |
|:---|:---|
| Config syntax | `testparm` |
| Active shares | `smbstatus` |
| Listening | `ss -tlnp \| grep smbd` |

## 6. Auditing Listening Network Services

Run a routine inventory: open ports, owning processes, and related systemd units. Every listener should have a clear business reason. Map every listener to an operational need, and treat an unexpected `0.0.0.0` bind as a high-priority finding.

```bash
# Modern socket audit
ss -tulnp
ss -tulnp | grep LISTEN

# Legacy (may be absent on minimal images)
netstat -tulnp 2>/dev/null

# Map to systemd units
systemctl list-units --type=service --state=running | grep -E 'ssh|nfs|samba|bind|apache|nginx'

# What owns port 445?
sudo lsof -i :445
sudo fuser -v 445/tcp
```

$$
\text{Exposure score} \uparrow \text{ with listeners on } 0.0.0.0 \text{ and weak auth services}
$$

## 7. Security Notes — Defense / Hardening

Network services widen the attack surface. Default posture: do not expose services to the internet unless required, narrow exports and shares, and audit listeners regularly. Treat every extra daemon as extra exposure. Open recursive DNS, guest shares, and `no_root_squash` are classic high-impact misconfigurations.

| Misconfiguration | Impact | Defense |
|:---|:---|:---|
| NFS `no_root_squash` + wide subnet | Remote root file write | `root_squash`; narrow exports; Kerberos |
| Samba guest write | Anonymous malware drop | Disable guest; require auth |
| Open DNS recursion to internet | Amplification abuse | Recursion allowlist only |
| Rogue DHCP | MITM gateway/DNS | DHCP snooping; static config on servers |
| Stale `/etc/hosts` overrides | Wrong routing to internal apps | Configuration management |
| Unencrypted NFSv3 on untrusted LAN | Data sniffing | NFSv4 + Kerberos or VPN |

```bash
# Defensive audit (authorized admin)
grep -v '^#' /etc/exports 2>/dev/null
testparm -s 2>/dev/null | head -30
ss -tulnp | awk 'NR==1 || /0.0.0.0|:::/'
resolvectl dns
```
