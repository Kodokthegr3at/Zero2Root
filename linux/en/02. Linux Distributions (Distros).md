## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| Distribution (distro) | A ready-to-use OS built from the Linux kernel plus tools |
| Package manager | The tool that installs/updates software (`apt`, `dnf`, `pacman`) |
| Repository | The online store of packages a distro installs from |
| Base distro | The distro others are built on (Debian → Ubuntu → Mint) |
| Rolling vs fixed release | Always-latest updates vs. periodic numbered versions |
| LTS | Long-Term Support: a release patched for years |
| Desktop environment | The graphical interface (GNOME, KDE) |
| Init system | What starts and supervises services at boot (usually systemd) |

## 1. What is a Linux Distribution?

A distribution (distro) packages the Linux kernel with a coherent userland, package manager, init system, and configuration defaults:

```text
Distro = Linux kernel        (the core)
       + userland            (GNU tools, libraries)
       + package manager     (apt / dnf / pacman)
       + policy              (defaults, init system, branding)
```

The kernel by itself is not a ready-to-use desktop or server OS. A distro adds the GNU toolchain, systemd (or an alternative), package repositories, and default security policies. Think of distros as compatible variants that share the same kernel ABI philosophy but differ in release cadence, package versions, and security defaults.

| Layer | Examples | Role |
|:---|:---|:---|
| Kernel | `linux`, modules, firmware | Hardware access and process isolation |
| C library | glibc, musl | Syscall wrappers |
| Init | systemd, OpenRC | Boot and service supervision |
| Packages | deb, rpm, pkg | Install, upgrade, remove |
| Policy | SELinux/AppArmor defaults | Confinement baseline |

## 3. Release Models: Stable, Rolling, LTS

| Model | Cadence | Patch style | Best for | Risk |
|:---|:---|:---|:---|:---|
| Stable | ~1-2 years | Backports security fixes | Servers, compliance | Older feature set |
| LTS | 2-5+ years support | Security plus selected fixes | Enterprise, prod | Feature lag |
| Rolling | Continuous | Latest upstream | Desktops, labs | Breakage, churn |
| Point / snapshot | Frozen tree | Rebuild periodically | Reproducible builds | Manual upgrades |

Production servers favor stable or LTS channels so CVEs can be backported without wholesale package churn. Rolling releases maximize freshness at the cost of regression risk. For production, prefer Debian Stable, Ubuntu LTS, RHEL, AlmaLinux, or Rocky Linux. Rolling distros such as Arch or Kali Rolling are fine for a lab, but they are not a baseline for production without a strict hardening process.

### General-purpose comparison

| Distro | Best for | Package manager | Init | Default MAC |
|:---|:---|:---|:---|:---|
| Ubuntu | Desktop, cloud images | `apt` | systemd | AppArmor |
| Debian | Servers, appliances | `apt` | systemd | AppArmor (optional) |
| Fedora | Cutting-edge desktop/dev | `dnf` | systemd | SELinux |
| RHEL / Alma / Rocky | Enterprise servers | `dnf` | systemd | SELinux |
| Arch | DIY, learning | `pacman` | systemd | (manual) |
| openSUSE | Enterprise + YaST | `zypper` | systemd | AppArmor |

Note: classic CentOS Linux (the rebuild distro) is end of life. Use AlmaLinux, Rocky Linux, or CentOS Stream deliberately instead.

## 5. Security-Oriented Distributions

A "security" distro usually means one of two things: a toolset preinstalled for lab and audit work, or a design built around privacy and hardening. Run these in an isolated VM or lab. Do not make one a production daily driver without a real patch policy and least-privilege setup.

| Distro | Base | Focus (defense education) | Notes |
|:---|:---|:---|:---|
| Kali Linux | Debian | Security tool ecosystem | Rolling; not a production server OS |
| Parrot OS | Debian | Security plus a lighter desktop | Common in training labs |
| BlackArch | Arch | Large security package set | Add-on repos available |
| Qubes OS | Xen + Fedora templates | Strong isolation UX | Different threat model |
| Tails | Debian | Amnesic, privacy-focused live system | USB live sessions |

```
Why Linux dominates security workstations (defense view)
───────────────────────────────────────────────────────
Open source  → audit patches, reproduce builds
Control      → minimal services, clear attack surface
Tooling      → native packet capture, scripting, containers
Packaging    → signed updates via distro security teams
```

## 6. Choosing a Distro: Decision Matrix

| Requirement | Prefer | Avoid as primary |
|:---|:---|:---|
| 24/7 production server | Debian Stable, Ubuntu LTS, RHEL family | Untested rolling releases |
| Compliance, long support | RHEL, Ubuntu LTS, Debian LTS | Short-lived spins |
| Desktop beginners | Ubuntu, Fedora Workstation, Mint | Minimal Arch (until ready) |
| Embedded / SBC | Raspberry Pi OS, Debian | Heavy desktop spins |
| Authorized security lab | Kali/Parrot in a VM | Same image as a production gateway |
| Reproducible builds | Debian, NixOS*, Guix* | Ad-hoc binary drops |

\*NixOS and Guix use a special declarative model: excellent for reproducibility, with a steeper learning curve.

### A formal view of the "support window"

If the CVE discovery rate is λ per year and the mean time to patch under LTS is T, residual exposure roughly scales with λ·T when patching is delayed. Prefer channels with fast security backports.

## 7. Debian: Deep Dive

Debian is known for its strict freeze process, security handled through the Debian Security team, and the `apt`/`dpkg` ecosystem. Many distros (Ubuntu, Kali, Parrot) inherit much of Debian's packaging policy, with Ubuntu adding a faster desktop/cloud cadence and Launchpad/Snap layers on top.

**Suites (channels):**
- `stable`, used for production
- `testing`, the candidate for the next stable release
- `unstable` (`sid`), for development, not for servers

```
Debian suites (simplified)
──────────────────────────
unstable ──► testing ──► stable ──► oldstable
   (sid)      (freeze)     (prod)     (LTS/ELTS may apply)
```

### APT quick reference (Debian family)

```bash
# Refresh indices & apply security updates
sudo apt update
sudo apt upgrade                 # or: sudo apt full-upgrade when needed

sudo apt install <pkg>
sudo apt remove <pkg>
sudo apt purge <pkg>             # remove config too
apt search <keyword>
apt show <pkg>
apt list --installed
dpkg -l | less
```

### Security channels

- Install `unattended-upgrades` on Debian/Ubuntu servers for automatic security patches.
- Prefer official mirrors over HTTPS, and verify release keys during install.

## 8. Distro Identity on a Live Host

```bash
cat /etc/os-release          # ID, VERSION_ID, VARIANT
lsb_release -a               # if package installed
hostnamectl                  # pretty OS + kernel
uname -r                     # kernel release
cat /etc/debian_version      # Debian-derived
cat /etc/redhat-release      # RHEL-family
```

| Field (`os-release`) | Meaning |
|:---|:---|
| `ID` | Distro id (`debian`, `ubuntu`, `fedora`) |
| `ID_LIKE` | Family hints (`debian`, `rhel`) |
| `VERSION_CODENAME` | Suite name (`bookworm`, `noble`) |
| `SUPPORT_END` | End of support (when provided) |

## 9. Security Notes: Defense and Hardening

| Threat / gap | Why it matters | Defense |
|:---|:---|:---|
| Unsupported / EOL distro | No security backports | Upgrade to a supported LTS; inventory with `os-release` |
| Mixing random PPAs / third-party RPMs | Supply-chain and trust risk | Prefer official repos; pin and review keys |
| Using Kali/Parrot as a production gateway | Extra attack surface | Lab VMs only; production stays minimal and stable |
| Unpatched packages | Known CVEs remain open | `unattended-upgrades` / `dnf-automatic`; monitor DSA/USN |
| Flat container host without updates | Shared kernel risk | Patch the host kernel; isolate with namespaces and MAC |
| Blind trust in "security" branding | Tools don't equal hardened defaults | Apply the hardening baseline below |

### Hardening baseline per family

1. Stay on a supported release, and subscribe to security mailing lists or RSS feeds.
2. Enable automatic security-only updates where policy allows.
3. Keep AppArmor (Debian/Ubuntu) or SELinux (RHEL/Fedora) enforcing, not permissive.
4. Minimize installed packages: attack surface scales roughly with |P_installed|.
5. Keep lab images separate from production images.

```bash
# Quick posture checks (admin / auditor)
grep -E '^(NAME|VERSION|SUPPORT)' /etc/os-release
systemctl is-enabled unattended-upgrades 2>/dev/null || true
aa-status 2>/dev/null | head          # AppArmor hosts
getenforce 2>/dev/null                # SELinux hosts
```

## 10. Quick Reference Cheatsheet

```bash
# Identity
cat /etc/os-release && uname -a

# Debian/Ubuntu updates
sudo apt update && sudo apt upgrade
apt-cache policy <pkg>

# Fedora / RHEL family
sudo dnf check-update
sudo dnf upgrade

# Arch
sudo pacman -Syu

# Package counts (rough surface)
dpkg -l | wc -l
rpm -qa | wc -l
```

| Feature | Ubuntu LTS | Debian Stable | Fedora | RHEL/Alma/Rocky | Arch | Kali (lab) |
|:---|:---|:---|:---|:---|:---|:---|
| Cadence | 2y LTS | ~2y | ~6mo | Long support | Rolling | Rolling |
| Default MAC | AppArmor | AppArmor* | SELinux | SELinux | Manual | AppArmor |
| Production server | Yes | Yes | Partial | Yes | Partial | No |
| Learning desktop | Yes | Yes | Yes | Partial | Yes | Lab VM |

\*May need enabling depending on the package set.
