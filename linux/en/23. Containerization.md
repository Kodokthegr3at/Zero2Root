## 1. Containers vs Virtual Machines

A container shares the host kernel; isolation comes from namespaces and cgroups rather than a hypervisor running a full guest kernel.

```text
VM        = full guest OS + app
container = app + libraries, sharing the host kernel
```

Containers start fast and pack densely, but they are not VMs. A kernel escape or an excessive `--privileged` container can compromise the host. Run them with defense-in-depth: non-root, dropped capabilities, read-only rootfs.

```
┌─────────────────────────────────────────────┐
│ Host Linux Kernel                           │
│  ┌─────────────┐  ┌─────────────┐           │
│  │ Container A │  │ Container B │           │
│  │ PID/NET/MNT │  │ PID/NET/MNT │  (namespaces)
│  │ cgroups     │  │ cgroups     │           │
│  └─────────────┘  └─────────────┘           │
│         dockerd / containerd / podman       │
└─────────────────────────────────────────────┘

vs VM: each guest has its own kernel under a hypervisor
```

| Aspect | VM | Container |
|:---|:---|:---|
| Isolation | Hardware/virtual HW | Kernel namespaces |
| Boot time | Minutes | Seconds |
| Density | Lower | Higher |
| Kernel | Per guest | Shared |
| Typical tool | KVM, VMware | Docker, Podman |

## 2. Linux Primitives — Namespaces & cgroups

The kernel provides two isolation building blocks: namespaces separate what a process can see (PID, net, mount, and so on), and cgroups limit resource usage.

| Namespace | Isolates |
|:---|:---|
| `pid` | Process IDs |
| `net` | Interfaces, routes, ports |
| `mnt` | Mount tree |
| `uts` | Hostname |
| `ipc` | IPC objects |
| `user` | UID/GID mapping (rootless) |

cgroups limit CPU, memory, I/O, and PID counts.

Capabilities split root's power (`CAP_NET_BIND_SERVICE` and others). Docker drops many capabilities by default; `--cap-add` widens the attack surface.

```bash
# Peek at container namespaces (host admin, container ID from docker ps)
pid=$(docker inspect -f '{{.State.Pid}}' mycontainer)
sudo ls -l /proc/$pid/ns/
sudo cat /proc/$pid/cgroup
```

## 3. Docker Core Workflow

Install `docker.io` (Debian) or `docker-ce`. The `dockerd` daemon manages images and containers.

An image is a layered read-only filesystem plus metadata; a container is a writable layer on top. The default registry is Docker Hub; pin digests in production.

```bash
# Install (Debian/Ubuntu lab)
sudo apt update && sudo apt install docker.io -y
sudo systemctl enable --now docker
sudo usermod -aG docker $USER   # re-login for group

# Pull & run
docker pull nginx:1.25-alpine
docker run -d --name web -p 8080:80 nginx:1.25-alpine
docker ps
docker logs web
docker stop web && docker rm web

# Inspect
docker inspect web
docker image ls
docker system df
```

| Command | Action |
|:---|:---|
| `docker pull` | Download an image |
| `docker run` | Create and start a container |
| `docker ps -a` | List containers |
| `docker exec -it` | Shell inside a running container |
| `docker rm` / `docker rmi` | Remove a container / image |

## 4. Dockerfile & Docker Compose

A Dockerfile defines the image build; Compose orchestrates multiple containers in a lab or dev setting.

Multi-stage builds shrink the final image. Never embed secrets in a layer; use build secrets or a runtime env from a vault.

**Minimal Dockerfile:**

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER 1000:1000
EXPOSE 8000
CMD ["python", "-m", "http.server", "8000", "--bind", "0.0.0.0"]
```

```bash
docker build -t myapp:lab .
docker run -d -p 8000:8000 --read-only --tmpfs /tmp myapp:lab
```

**docker-compose.yml sketch:**

```yaml
services:
  web:
    image: nginx:alpine
    ports:
      - "127.0.0.1:8080:80"
    read_only: true
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: changeme
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

```bash
docker compose up -d
docker compose ps
docker compose logs -f web
docker compose down
```

## 5. Podman — Rootless-First Alternative

Podman is daemonless (a fork-exec model), which suits rootless containers without a `docker` group.

Its CLI is largely Docker-compatible: `podman run`, `podman build`. systemd integration comes through `podman generate systemd`.

```bash
sudo apt install podman -y
podman run -d --name web -p 8080:80 docker.io/library/nginx:alpine
podman ps
podman exec -it web sh

# Rootless (unprivileged user)
podman run --rm -it alpine id
```

| Docker | Podman equivalent |
|:---|:---|
| `docker` | `podman` |
| `docker compose` | `podman compose` |
| daemon socket | no central daemon |

## 6. Day-2 Operations

Monitoring resources, restart policies, volume backups, and log rotation are the routine work once a container is running.

Bind-mounting the host's `/` or the Docker socket into a container grants host-level power; this is forbidden in production patterns.

```bash
# Resource stats
docker stats --no-stream

# Restart policies
docker run -d --restart unless-stopped nginx:alpine

# Volumes
docker volume create appdata
docker run -v appdata:/data alpine sh -c 'echo test > /data/file'

# Interactive debug (authorized)
docker exec -it mycontainer sh
docker cp mycontainer:/etc/nginx/nginx.conf ./nginx.conf.bak
```

## 7. Security Notes — Defense / Breakout Awareness

A safe posture: non-root, no `--privileged`, no mounted Docker socket, pinned images, scanning against trusted registries.

Container escape research belongs only in authorized lab environments. Defenders focus on capability reduction, seccomp/AppArmor profiles, and kernel patching.

| Misconfiguration | Impact | Defense |
|:---|:---|:---|
| `--privileged` | Near-root on the host | Avoid; keep capabilities minimal |
| Mounting `/var/run/docker.sock` | Control over all containers | Never in untrusted workloads |
| Running as root in a container | Easier escape chains | `USER` non-root in the Dockerfile |
| `:latest` in production | Supply-chain drift | Pin digest/version |
| Public registry images | Malware/backdoors | Scan (Trivy/Grype); trusted registries |
| Secrets in env/build args | Leak via `docker inspect`/history | Secrets manager, runtime inject |
| Host network mode `--network host` | Shares the host stack | Default bridge unless required |

```bash
# Defensive posture checks (authorized)
docker info 2>/dev/null | grep -i root
docker ps --quiet | xargs -r docker inspect -f '{{.Name}} privileged={{.HostConfig.Privileged}} caps={{.HostConfig.CapAdd}}'
# podman
podman ps --format '{{.Names}} {{.Privileged}}'
```
