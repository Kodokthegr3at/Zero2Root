## 1. Metodologi Troubleshooting Berlapis

Gunakan pendekatan **bottom-up** atau **top-down**; catat hipotesis dan bukti di setiap layer.

```text
App → DNS → TCP/UDP → Routing → Interface → Physical
```

Di server Linux, alur umum: pastikan **link up**, **IP** benar, **default route** ada, **DNS** resolve, **port remote** bisa dijangkau (`nc`/`curl`), baru lakukan **capture** kalau masih gagal.

```
Symptom: "curl https://app.internal fails"
  │
  ├─ ip link / ip addr        → interface up? correct IP?
  ├─ ip route                 → default gw present?
  ├─ ping gw                  → L2/L3 local OK?
  ├─ dig app.internal         → DNS resolves?
  ├─ curl -v / nc -vz         → TCP 443 reachable?
  └─ tcpdump on interface     → where packets die?
```

| Layer | Pertanyaan | Tools |
|:---|:---|:---|
| L1/L2 | Kabel/VLAN/bridge? | `ip link`, `ethtool` |
| L3 | IP & rute benar? | `ip addr`, `ip route`, `ping` |
| L4 | Port terbuka/terfilter? | `ss`, `nc` (berizin) |
| L7 | App/TLS/HTTP OK? | `curl -v`, `openssl s_client` |

## 2. Reachability — `ping`, `traceroute`, `mtr`

**ICMP echo** (`ping`) menguji round-trip; **traceroute**, `tracepath`, dan `mtr` menunjukkan delay dan loss per hop. Firewall sering memblokir ICMP, jadi ping yang gagal tidak membuktikan TCP juga gagal. Kombinasikan dengan probe TCP.

```bash
ping -c 4 10.10.14.1
ping -6 -c 4 2001:db8::1

traceroute 8.8.8.8
tracepath example.com
mtr -rwzc 50 example.com    # report mode, 50 cycles

# TCP-based traceroute alternative when ICMP blocked
sudo traceroute -T -p 443 example.com
```

| Tool | Menampilkan |
|:---|:---|
| `ping` | RTT, loss ke satu host |
| `traceroute` | Router per hop (varian ICMP/UDP/TCP) |
| `mtr` | Statistik gabungan ping + traceroute |

## 3. Socket & Koneksi — `ss` & `netstat`

**`ss`** menggantikan **`netstat`**. Lihat listening port, koneksi established, dan backlog antrian dengannya. Saat incident response di host milik sendiri, petakan koneksi outbound yang mencurigakan ke proses dengan `-p`.

```bash
ss -tulnp                    # listening TCP/UDP + process
ss -tan state established    # active TCP
ss -o state established '( dport = :443 )'

# Legacy
netstat -tulnp 2>/dev/null

# Bandwidth per socket (if installed)
sudo ss -ti
```

| State | Arti |
|:---|:---|
| `LISTEN` | Menunggu koneksi masuk |
| `ESTAB` | Sesi aktif |
| `TIME-WAIT` | Sisi yang menutup, menunggu 2MSL |
| `SYN-RECV` | Kemungkinan SYN flood atau half-open |

## 4. Packet Capture — `tcpdump`

**`tcpdump`** menangkap frame/paket langsung dari interface. Butuh **`CAP_NET_RAW`** atau root. Capture hanya pada jaringan/sistem yang benar-benar **berizin** untuk dimonitor. Simpan file pcap terenkripsi karena bisa berisi kredensial kalau trafiknya HTTP polos.

```bash
# List interfaces
tcpdump -D

# Basic capture (lab)
sudo tcpdump -i eth0 -nn -c 20
sudo tcpdump -i eth0 -nn host 10.10.14.5 and port 443

# Write pcap for Wireshark
sudo tcpdump -i eth0 -w /tmp/capture.pcap -c 500
tcpdump -r /tmp/capture.pcap -nn | head

# Common filters
# tcp port 80
# icmp
# net 10.10.14.0/24
# not port 22
```

| Ekspresi filter | Mencocokkan |
|:---|:---|
| `host X` | Src atau dst X |
| `port 53` | TCP atau UDP 53 |
| `tcp[tcpflags] & tcp-syn != 0` | Paket SYN |
| `vlan 100` | Tag VLAN (jika ada) |

**Berkeley Packet Filter (BPF)** berjalan di dalam kernel supaya efisien sebelum data disalin ke userspace.

## 5. ARP & Neighbor Discovery — `ip neigh`, `arp`

**ARP** IPv4 memetakan IP ke MAC di segmen lokal. Tabel neighbor dilihat lewat **`ip neigh`**. Entri ARP yang basi atau diracuni menyebabkan gangguan koneksi yang halus atau MITM di LAN yang tidak dipercaya. Pakai DAI/802.1X di switch bila memungkinkan.

```bash
ip neigh show
arp -n

# Clear single stale entry (careful on production)
sudo ip neigh del 10.10.14.1 dev eth0
sudo ip neigh flush dev eth0

# Link diagnostics
ethtool eth0
ethtool -S eth0 | head
```

## 6. Probe Layer Aplikasi — DNS & HTTP

Setelah L3/L4 dipastikan OK, verifikasi **DNS** dan **HTTP/TLS** dengan `dig`, `curl`, `openssl`. `curl -v` menampilkan redirect, error sertifikat, dan perilaku SNI, sangat membantu untuk debugging vHost dan TLS.

```bash
dig +trace example.com A
dig @10.10.14.1 internal.lab A

curl -v http://127.0.0.1:8080/
curl -vk https://app.lab/health
curl -o /dev/null -w '%{http_code} time=%{time_total}\n' -s https://example.com/

# TLS handshake inspect
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -subject -dates

# TCP port probe
nc -vz 10.10.14.10 22
nc -vz -w 3 example.com 443
```

## 7. Catatan Keamanan — Etika & Pertahanan

Capture dan inspeksi ARP hanya pada sistem/jaringan yang **Anda punya izin** untuk mengelolanya. pcap adalah data sensitif. Mode promiscuous dan dump paket termasuk operasi yang berdampak besar ke privasi. Korelasikan listener dengan log auth (catatan 28) saat incident response di host milik sendiri.

| Aktivitas | Konteks berizin | Risiko penyalahgunaan |
|:---|:---|:---|
| `tcpdump` di LAN | SOC/NOC dengan kebijakan | Pencurian kredensial, pelanggaran privasi |
| Inspeksi ARP | Troubleshooting subnet sendiri | MITM jika dikombinasikan dengan forwarding |
| Pemetaan proses via `ss` | IR di host milik sendiri | Recon di host bersama yang sudah diretas |
| Mode promiscuous | Sensor IDS | Covert channel jika disalahgunakan |

**Monitoring defensif:**

```bash
# Unexpected promiscuous interface?
ip link | grep PROMISC

# New listeners after change window
ss -tulnp | grep LISTEN

# Auth + network correlation (see note 28)
journalctl -u ssh --since "1 hour ago" | tail
```

```bash
# Reachability
ping -c 4 GATEWAY
traceroute HOST

# Sockets
ss -tulnp
ss -tan state established

# Capture
sudo tcpdump -i eth0 -nn -c 50
sudo tcpdump -i eth0 -w out.pcap host X and port Y

# L2/L3
ip neigh show
ip route get 8.8.8.8

# App layer
dig A HOST +short
curl -v URL
nc -vz HOST PORT
```
