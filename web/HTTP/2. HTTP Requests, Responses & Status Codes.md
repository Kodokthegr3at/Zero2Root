## 1. 📦 HTTP Message Model

### 🇮🇩 Bahasa Indonesia
Pesan HTTP/1.1 (RFC 9112) secara kasar:

$$
\mathsf{Message} = \mathsf{Start\text{-}Line} \;\|\; (\mathsf{Header}\,\texttt{CRLF})^* \;\|\; \texttt{CRLF} \;\|\; [\mathsf{Body}]
$$

Header berakhir dengan baris kosong. Body boleh kosong. Framing body ditentukan `Content-Length`, `Transfer-Encoding: chunked`, atau aturan khusus metode/status.

### 🇬🇧 English
Security relevance: **everything after the blank line is data** that application frameworks parse into params, JSON, multipart parts — primary injection surfaces (see SQLi/XSS series). Proxies may parse framing differently → desync class (concept in §7).

### 日本語
空行の後がボディです。アプリがボディをどう解釈するかが注入面になります。

```http
POST /api/v1/items HTTP/1.1
Host: app.lab.local
Content-Type: application/json
Content-Length: 27
Authorization: Bearer <token>

{"name":"notebook","qty":1}
```

```
┌──────────────────────────────┐
│ Start-line                   │
├──────────────────────────────┤
│ Header fields                │
├──────────────────────────────┤
│ empty CRLF                   │
├──────────────────────────────┤
│ Optional body                │
└──────────────────────────────┘
```

## 3. ⚡ Method Semantics — Safe & Idempotent

RFC 9110 defines **safe** and **idempotent** properties:

| Method | Safe | Idempotent | Typical use | Security note |
|:---|:---:|:---:|:---|:---|
| `GET` | ✅ | ✅ | Read | Must not mutate (CSRF/cache) |
| `HEAD` | ✅ | ✅ | Metadata | Same as GET w/o body |
| `OPTIONS` | ✅ | ✅ | Probe | CORS preflight |
| `TRACE` | ✅ | ✅ | Echo | **Disable** on servers (XST legacy) |
| `POST` | ❌ | ❌ | Create/action | CSRF tokens if cookie auth |
| `PUT` | ❌ | ✅ | Replace | AuthZ on full replace |
| `DELETE` | ❌ | ✅ | Remove | AuthZ + confirm |
| `PATCH` | ❌ | ❌* | Partial update | Schema validate (*often non-idempotent) |

### Formal intuition

- **Safe:** no intended state change on server resources.  
- **Idempotent:** $N$ identical requests ⇒ same state effect as 1 (aside from logs).

$$
\mathsf{Idempotent}(m)
\;\Rightarrow\;
\mathsf{State}(m^n) = \mathsf{State}(m^1)
$$

### 🇬🇧 English
WAHH: many “CSRF-friendly” bugs are simply **unsafe GET**. Framework route tables should enforce method; do not accept `GET` for logout/password change “for convenience.”

### 日本語
状態変更に`GET`を使わないでください。CSRFとキャッシュ事故の原因になります。

```bash
# OWN LAB — observe method enforcement on your API
curl -sS -o /dev/null -w "%{http_code}\n" -X DELETE https://localhost:8443/api/item/1 \
  -H "Authorization: Bearer $TOKEN"
```

## 4. 📥 Response Structure

Then headers + optional body. Clients primarily branch on **status-code** (three digits), not the reason phrase (human text; may be ignored).

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/items/42
Cache-Control: no-store
Content-Length: 15

{"id":42,"ok":1}
```

| Field | Defensive practice |
|:---|:---|
| `Server` / stack traces | Minimize version leakage |
| `Location` | Open-redirect allowlist |
| Body on 4xx/5xx | Generic messages to clients; detail in logs |
| Cache headers | `no-store` for authenticated responses |

## 5. 📊 Status Code Classes

| Class | Range | Meaning | API guidance |
|:---|:---|:---|:---|
| 1xx | 100–199 | Informational | Rare in app code |
| 2xx | 200–299 | Success | `200`/`201`/`204` correctly |
| 3xx | 300–399 | Redirection | Validate `Location` targets |
| 4xx | 400–499 | Client error | Distinguish 401 vs 403 carefully |
| 5xx | 500–599 | Server error | Don’t dump exceptions |

### Selected codes (security-relevant)

| Code | Name | Notes |
|:---:|:---|:---|
| 200 | OK | With body |
| 201 | Created | + `Location` |
| 204 | No Content | Empty body |
| 301/302/307/308 | Redirects | 307/308 preserve method more strictly |
| 400 | Bad Request | Validation failure |
| 401 | Unauthorized | Missing/invalid auth — send `WWW-Authenticate` if applicable |
| 403 | Forbidden | Authenticated but not allowed |
| 404 | Not Found | Also used to hide existence (trade-off vs UX) |
| 405 | Method Not Allowed | + `Allow` header |
| 409 | Conflict | Concurrent update |
| 415 | Unsupported Media Type | Unexpected `Content-Type` |
| 429 | Too Many Requests | Rate limiting |
| 500 | Internal Error | Log server-side |
| 502/503/504 | Gateway / Unavailable / Timeout | Edge/proxy |

### 🇮🇩 Bahasa Indonesia
Jangan andalkan “security through obscure status” saja. Authorization checks harus eksplisit di server. Hindari perbedaan status yang memungkinkan **user enumeration** tanpa rate limit (mis. login `403` vs `401` vs pesan terlalu detail).

### 🇬🇧 English
Consistent error shapes + rate limits beat clever status tricks. For auth endpoints, prefer uniform responses where enumeration matters.

### 日本語
認証エンドポイントではユーザー列挙を抑えるため、応答を均一化しレート制限します。

## 6. 🧾 Request Body Encodings

| `Content-Type` | Shape | Pitfalls |
|:---|:---|:---|
| `application/x-www-form-urlencoded` | `a=1&b=2` | CSRF classic surface; charset |
| `multipart/form-data` | Boundaries + parts | Upload vulns; huge parts |
| `application/json` | JSON text | Prototype pollution in some parsers; depth limits |
| `application/xml` | XML | XXE if parser unsafe |
| `text/plain` | Raw | Still validate |

```bash
# Lab: multipart to your uploader (authorized)
curl -sS -F "file=@./sample.png;type=image/png" \
  https://localhost:8443/upload -H "Cookie: session=$SID"
```

**Content-Length** must match body (proxies sensitive). Prefer framework parsers over manual string splits.

## 7. 🧩 Request Smuggling / Desync — Concept Only

Ketika front proxy dan backend memparse batas body berbeda (`Content-Length` vs `chunked`), request dapat “menyatu” secara berbahaya di antrian koneksi HTTP/1.1 keep-alive.

$$
\mathsf{Parse}_{\mathsf{front}}(B) \;\neq\; \mathsf{Parse}_{\mathsf{back}}(B)
$$

**Defense (ops):** HTTP/2 end-to-end where possible; normalize at edge; reject ambiguous framing; keep proxy/app patched; disable backend reuse across trust zones carelessly. This note does **not** provide smuggling payloads.

## 8. 🛡️ Secure API Design Rules

1. Enforce methods explicitly; reject unexpected verbs with `405`.  
2. Mutating methods require authN + authZ + CSRF strategy if cookies.  
3. Validate `Content-Type` before parsing.  
4. Bound body size (`client_max_body_size`, framework limits).  
5. Use precise status codes; hide internals.  
6. Cache authenticated content carefully (`Cache-Control: private, no-store`).  
7. Idempotency keys for payments/`POST` where retries happen.  
8. Uniform auth error policy + rate limits.  
9. Disable `TRACE`; restrict `OPTIONS` to needed CORS.  
10. Log method, path template, status — not secrets.

# Request
METHOD /path?query HTTP/1.1
Host: example
Header: value

body...

# Response
HTTP/1.1 200 OK
Header: value

| Need | Code |
|:---|:---|
| Read OK | 200 |
| Created | 201 |
| Bad input | 400 |
| Auth missing | 401 |
| AuthZ fail | 403 |
| Rate limit | 429 |
| Bug | 500 (generic client msg) |

```bash
curl -sS -X OPTIONS https://localhost:8443/api -D - -o /dev/null
curl -sS -X TRACE https://localhost:8443/ -D - -o /dev/null   # expect deny
```

## 🔐 Security Notes — Threats & Defenses

| Threat | Mechanism | Defense |
|:---|:---|:---|
| CSRF via GET mutate | Safe method violated | Read-only GET |
| Verb tampering | Alternate method bypasses check | Central method+authZ |
| Info leak via errors | Stack in body | Generic 5xx |
| Open redirect | Unchecked `Location` | Allowlist |
| Desync | Parser mismatch | Normalize; HTTP/2; patches |
| Oversized body | DoS | Limits |
