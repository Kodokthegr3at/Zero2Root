## 1. 📨 HTTP Request Structure — Anatomy of an HTTP Request

### 🇮🇩 Bahasa Indonesia
Setiap komunikasi dari klien (browser, cURL, scanner) ke web server dikirim sebagai **HTTP Request**. Sebuah pesan HTTP request terdiri dari tiga komponen utama:
1. **Request Line (Baris Permintaan)**: Berisi metode HTTP (misal `GET`, `POST`), URI path yang diminta (`/index.html`), dan versi protokol (`HTTP/1.1`).
2. **HTTP Headers (Header Permintaan)**: Pasangan *key-value* yang memberikan metadata tentang klien, format yang didukung, kredensial autentikasi, dan cookie sesi.
3. **Message Body (Badan Pesan / Payload)**: Opsional, berisi data aktual yang dikirim ke server (misal parameter form saat login atau payload JSON pada REST API). Dipisahkan dari header dengan satu baris kosong (*CRLF / `\r\n\r\n`*).

### 🇬🇧 English
Every communication initiated from a client (browser, cURL, proxy scanner) to a web server is transmitted as an **HTTP Request**. A standardized HTTP request message comprises three primary components:
1. **Request Line**: Specifies the HTTP verb/method (`GET`, `POST`), the targeted resource URI path (`/index.html`), and the protocol version (`HTTP/1.1`).
2. **HTTP Headers**: Colon-separated key-value pairs providing client metadata, supported encodings, authentication tokens, and session cookies.
3. **Message Body (Payload)**: Optional content carrying raw data to the server (e.g., form input during authentication or JSON payloads for REST APIs). Delimited from headers by an empty line (*CRLF / `\r\n\r\n`*).

### 🇯🇵 日本語
クライアント（ブラウザ、cURL、スキャナー等）からWebサーバーへのすべての通信は **HTTPリクエスト** として送信されます。標準的なHTTPリクエストは主に3つの要素で構成されます：
1. **リクエスト行（Request Line）**: HTTPメソッド（`GET`、`POST`等）、対象リソースのURIパス（`/index.html`）、プロトコルバージョン（`HTTP/1.1`）を指定します。
2. **HTTPヘッダー（HTTP Headers）**: クライアントの情報、サポートするデータ形式、認証トークン、セッションCookieなどのメタデータを提供するキー・バリュー形式のペア。
3. **メッセージ本文（Message Body / Payload）**: サーバーへ送信する実データ（ログインフォームの入力値やREST APIのJSON等）。ヘッダー部とは空行（*CRLF / `\r\n\r\n`*）で区切られます。

```http
POST /api/v1/auth/login HTTP/1.1
Host: target.htb
User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:109.0) Gecko/20100101 Firefox/115.0
Accept: application/json, text/plain, */*
Content-Type: application/json
Content-Length: 47
Connection: close

{"username":"admin","password":"SuperSecretPassword123!"}
```

```
┌─────────────────────────────────────────────────────────────┐
│ Request Line : POST /api/v1/auth/login HTTP/1.1             │
├─────────────────────────────────────────────────────────────┤
│ Headers      : Host: target.htb                             │
│                User-Agent: Mozilla/5.0...                   │

├─────────────────────────────────────────────────────────────┤
│ Body/Payload : {"username":"admin","password":"..."}        │
└─────────────────────────────────────────────────────────────┘
```

## 2. ⚡ HTTP Methods (Verbs) — Actions on Resources

### 🇮🇩 Bahasa Indonesia
HTTP mendefinisikan sekumpulan metode (*verbs*) untuk menunjukkan aksi yang diinginkan terhadap resource yang dituju:
- **Safe Methods (Metode Aman)**: Metode yang tidak mengubah state atau data di server (seperti `GET`, `HEAD`, `OPTIONS`).
- **Idempotent Methods**: Metode yang jika dijalankan berkali-kali dengan parameter sama akan menghasilkan efek sistem yang persis sama (seperti `GET`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`). `POST` **bukan** idempotent karena pemanggilan berulang dapat membuat entitas baru berulang kali.

### 🇬🇧 English
HTTP defines a standard set of request methods (verbs) to specify the desired action performed on a resource:
- **Safe Methods**: Operations that do not alter the state of the server or modify backend records (`GET`, `HEAD`, `OPTIONS`).
- **Idempotent Methods**: Methods where multiple identical requests produce the identical server outcome and state as a single request (`GET`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`). `POST` is **non-idempotent** because repeating a request may create duplicate records.

### 🇯🇵 日本語
HTTPはリソースに対する操作を指定するための標準メソッド（HTTP動詞）を定義しています：
- **安全なメソッド（Safe Methods）**: サーバーの状態やデータを変更しない読み取り専用メソッド（`GET`、`HEAD`、`OPTIONS`）。
- **冪等なメソッド（Idempotent Methods）**: 同じリクエストを何度実行してもサーバーの状態が一度の実行と同じになるメソッド（`GET`、`PUT`、`DELETE`、`HEAD`、`OPTIONS`）。`POST` は重複データが作成される可能性があるため**非冪等**です。

| Method | 🇮🇩 Fungsi | 🇬🇧 Function | 🇯🇵 機能 | Safe? | Idempotent? |
|--------|-----------|-------------|---------|-------|-------------|
| **GET** | Ambil representasi resource | Retrieve resource representation | リソースの取得 | ✅ Yes | ✅ Yes |
| **POST** | Kirim data untuk diproses / buat baru | Submit data / create new entity | データの送信・新規作成 | ❌ No | ❌ No |
| **PUT** | Ganti / timpa resource secara penuh | Replace / overwrite resource | リソースの完全置換 | ❌ No | ✅ Yes |
| **PATCH** | Modifikasi sebagian dari resource | Apply partial modifications | リソースの一部更新 | ❌ No | ❌ No |
| **DELETE** | Hapus resource target | Remove target resource | リソースの削除 | ❌ No | ✅ Yes |
| **HEAD** | Sama seperti GET tapi tanpa body response | Same as GET, returns headers only | ヘッダーのみ取得 | ✅ Yes | ✅ Yes |
| **OPTIONS** | Cek metode yang didukung server | Query permitted communication options | 許可メソッドの確認 | ✅ Yes | ✅ Yes |
| **TRACE** | Echo request kembali untuk diagnostik | Loop-back diagnostics of request | リクエストのループバック | ✅ Yes | ✅ Yes |

## 3. 📥 HTTP Response Structure — Server Return Message

### 🇮🇩 Bahasa Indonesia
Setelah memproses request, server mengembalikan **HTTP Response** yang terdiri dari:
1. **Status Line (Baris Status)**: Berisi versi protokol (`HTTP/1.1`), kode status numerik (`200`), dan frasa penjelas (`OK`).
2. **Response Headers**: Metadata dari server, seperti tipe MIME dokumen (`Content-Type: text/html`), ukuran data (`Content-Length`), set cookie (`Set-Cookie`), dan security headers (`Content-Security-Policy`).
3. **Response Body**: Konten aktual yang dikembalikan (kode HTML halaman web, gambar biner, file PDF, atau data JSON).

### 🇬🇧 English
Upon processing a client request, the web server yields an **HTTP Response** structured as follows:
1. **Status Line**: Contains the protocol version (`HTTP/1.1`), a three-digit numeric status code (`200`), and a human-readable reason phrase (`OK`).
2. **Response Headers**: Server-side metadata specifying MIME types (`Content-Type: text/html; charset=UTF-8`), response length (`Content-Length`), session state directives (`Set-Cookie`), and security posture headers (`X-Frame-Options`).
3. **Response Body**: The actual transmitted payload (rendered HTML document, binary image stream, or API JSON response).

### 🇯🇵 日本語
クライアントからのリクエストを処理した後、Webサーバーは以下の構造を持つ **HTTPレスポンス** を返します：
1. **ステータス行（Status Line）**: プロトコルバージョン（`HTTP/1.1`）、3桁のステータスコード（`200`）、およびステータステキスト（`OK`）を含みます。
2. **レスポンスヘッダー（Response Headers）**: サーバーのメタデータ。MIMEタイプ（`Content-Type`）、コンテンツ長（`Content-Length`）、Cookie発行（`Set-Cookie`）、セキュリティポリシー（`Strict-Transport-Security`）等。
3. **レスポンス本文（Response Body）**: 実際に返されるデータ本体（HTMLドキュメント、バイナリ画像、JSONデータ等）。

```http
HTTP/1.1 200 OK
Date: Mon, 16 Aug 2026 00:00:00 GMT
Server: Apache/2.4.52 (Ubuntu)
Set-Cookie: sessionid=abc123xyz789; Path=/; HttpOnly; Secure; SameSite=Strict
Content-Type: text/html; charset=UTF-8
Content-Length: 128
Connection: close

<!DOCTYPE html>
<html>
<head><title>Dashboard</title></head>
<body><h1>Welcome, Administrator!</h1></body>
</html>
```

## 4. 🔢 HTTP Status Codes — Response Status Classification

### 🇮🇩 Bahasa Indonesia
Kode status HTTP adalah angka 3-digit yang distandarisasi oleh IETF (RFC 9110) untuk mengindikasikan status eksekusi request:
- **1xx (Informational)**: Request diterima dan proses sedang berlanjut.
- **2xx (Success)**: Request berhasil diterima, dipahami, dan diproses.
- **3xx (Redirection)**: Tindakan lanjutan diperlukan untuk menyelesaikan request (pengalihan URL).
- **4xx (Client Error)**: Kesalahan dari sisi klien (sintaks salah, autentikasi gagal, atau resource tidak ditemukan).
- **5xx (Server Error)**: Server gagal memenuhi request yang sah akibat kesalahan internal.

### 🇬🇧 English
HTTP Status Codes are standardized 3-digit integers specified by IETF (RFC 9110) describing the operational outcome of a request:
- **1xx (Informational)**: Request received, process continuing.
- **2xx (Success)**: Action was successfully received, understood, and accepted.
- **3xx (Redirection)**: Further action must be taken by the client to complete the request.
- **4xx (Client Error)**: Client-side issue encountered (invalid syntax, unauthorized access, non-existent resource).
- **5xx (Server Error)**: Server-side failure while attempting to fulfill an otherwise valid request.

### 🇯🇵 日本語
HTTPステータスコードは、IETF（RFC 9110）で標準化された3桁の数値で、リクエストの処理結果を示します：
- **1xx（情報）**: リクエストを受領し、処理を継続中。
- **2xx（成功）**: リクエストが正常に受理、理解、処理された。
- **3xx（リダイレクト）**: リクエスト完了のためにクライアント側で追加の処理（URL転送等）が必要。
- **4xx（クライアントエラー）**: クライアント側の問題（構文誤り、認証失敗、リソース未存在）。
- **5xx（サーバーエラー）**: サーバー側の内部処理エラーによるリクエスト処理失敗。

| Status Code | Reason Phrase | 🇮🇩 Deskripsi | 🇬🇧 Description | 🇯🇵 説明 | Pentest Relevance |
|-------------|---------------|--------------|----------------|---------|-------------------|
| **200** | OK | Request sukses normal | Standard successful response | 正常成功 | 🟢 Baseline |
| **201** | Created | Resource baru berhasil dibuat | New resource created | リソース新規作成 | 🟢 Success |
| **204** | No Content | Sukses, tidak ada body balasan | Success with empty body | 本文なし成功 | 🟢 API behavior |
| **301** | Moved Permanently | Resource dipindah permanen | Permanent redirection (cached) | 恒久的リダイレクト | 🟡 Check Location header |
| **302** | Found | Resource dialihkan sementara | Temporary redirection | 一時的リダイレクト | 🟠 Auth redirect testing |
| **304** | Not Modified | Cache klien masih valid | Client cache is fresh | キャッシュ有効 | 🟢 Cache probing |
| **400** | Bad Request | Sintaks request salah / rusak | Malformed request syntax | 不正リクエスト | 🟡 Fuzzing indicator |
| **401** | Unauthorized | Memerlukan autentikasi | Authentication credentials required | 認証が必要 | 🔴 Auth testing / brute force |
| **403** | Forbidden | Ditolak oleh server (izin kurang) | Forbidden / Access denied | アクセス禁止 | 🔴 Bypasses via headers |
| **404** | Not Found | Resource tidak ditemukan | Resource does not exist | リソース未存在 | 🟠 Dirbuster / Fuzzing |
| **405** | Method Not Allowed | Metode HTTP tidak diizinkan | HTTP verb not allowed on endpoint | メソッド不許可 | 🔴 Verb tampering |
| **413** | Payload Too Large | Ukuran request melebihi batas | Body exceeds server limits | ペイロード過大 | 🟡 DoS / Buffer testing |
| **429** | Too Many Requests | Rate limit terlampaui | Rate limiting / throttling active | レート制限超過 | 🟠 Rate limit bypass |
| **500** | Internal Server Error | Server crash / error logika backend | Generic backend exception / crash | 内部サーバーエラー | 🔴 SQLi / Code Injection leak |
| **502** | Bad Gateway | Reverse proxy menerima respons invalid | Invalid upstream response | 不正ゲートウェイ | 🟡 Reverse proxy analysis |
| **503** | Service Unavailable | Server overload atau maintenance | Server overloaded or down | サービス利用不可 | 🟡 DoS indicator |

## 5. 📦 Request Body Formats — Content Types

### 🇮🇩 Bahasa Indonesia
Parameter dan payload dikirimkan dengan header `Content-Type` yang mendefinisikan format serialisasi data:
1. `application/x-www-form-urlencoded`: Format form HTML default (`user=admin&pass=123`).
2. `multipart/form-data`: Digunakan saat upload file (`type="file"`) dengan batas pemisah (*boundary*).
3. `application/json`: Format standar REST API modern (`{"user":"admin"}`).
4. `application/xml` / `text/xml`: Format data berbasis XML (target serangan XXE - *XML External Entity*).

### 🇬🇧 English
Payloads and parameters are transmitted with an explicit `Content-Type` header governing parser deserialization:
1. `application/x-www-form-urlencoded`: Standard HTML form encoding (`key1=val1&key2=val2`).
2. `multipart/form-data`: Required for binary file uploads, utilizing arbitrary delimiter boundaries.
3. `application/json`: Predominant standard for modern RESTful APIs and SPAs (`{"key":"value"}`).
4. `application/xml` / `text/xml`: Structured XML representation (critical surface for XXE attacks).

### 🇯🇵 日本語
リクエスト本文のデータは、パース方法を指定する `Content-Type` ヘッダーとともに送信されます：
1. `application/x-www-form-urlencoded`: 標準的なHTMLフォーム形式（`key1=val1&key2=val2`）。
2. `multipart/form-data`: ファイルアップロード用の境界（boundary）区切り形式。
3. `application/json`: モダンWeb API / REST API の標準JSON形式。
4. `application/xml` / `text/xml`: XMLデータ形式（XXE脆弱性の主要ターゲット）。

## 6. 🔐 Security Note — HTTP Verb Tampering, Info Leakage & Status Exploitation

### 🇮🇩 Bahasa Indonesia
Dalam *The Web Application Hacker's Handbook* dan *The Tangled Web*, analisis request/response mengungkap celah fundamental:
1. **HTTP Verb Tampering**: Banyak backend web filter atau file `.htaccess` hanya memblokir `POST` atau `GET` untuk endpoint tertentu (misal `<Limit GET POST>`). Mengganti metode ke `PUT`, `HEAD`, `TRACE`, `PATCH`, atau bahkan custom method seperti `JEFF` dapat membypass pemeriksaan otorisasi (*Authentication & Access Control Bypass*).
2. **Information Disclosure via 500 & 4xx Errors**: Respons `500 Internal Server Error` yang memuntahkan stack trace, framework internals, query SQL, atau database versioning membantu penyerang memetakan backend dan merancang exploit injection spesifik.
3. **HTTP Response Splitting / Header Injection**: Jika input pengguna yang tidak disanitasi dimasukkan ke header response (misal `Set-Cookie` atau `Location`), penyerang dapat menyisipkan karakter `\r\n` (CRLF) untuk memalsukan status code, menginjeksi header berbahaya, atau menulis ulang seluruh body response (XSS / Cache Poisoning).
4. **Fuzzing & Directory Discovery**: Perbedaan status code (misal `403 Forbidden` vs `404 Not Found` vs `302 Found`) digunakan oleh scanner seperti `ffuf` dan `gobuster` untuk mengidentifikasi file tersembunyi dan endpoint administrasi.

### 🇬🇧 English
As documented in *The Web Application Hacker's Handbook* and *The Tangled Web*, HTTP message mechanics present significant offensive vectors:
1. **HTTP Verb Tampering**: Flawed access control configurations (e.g., `<Limit GET>` in Java EE `web.xml` or Apache configs) only validate standard methods. Switching methods to `HEAD`, `OPTIONS`, `PUT`, `PATCH`, or arbitrary custom verbs bypasses security constraints while still executing underlying handlers.
2. **Verbose Error Information Leakage**: Unhandled exceptions triggering `500 Internal Server Error` frequently leak database connection strings, absolute server paths, framework versions (e.g., Laravel, Django, Spring), and raw SQL snippets.
3. **HTTP Response Splitting / CRLF Injection**: Injecting newline sequences (`%0d%0a` / `\r\n`) into response headers allows attackers to split the response into two separate messages, facilitating cache poisoning and persistent Cross-Site Scripting (XSS).
4. **Differential Status Analysis**: Status code variances (`200 OK` vs `403 Forbidden` vs `404 Not Found`) form the logic behind directory enumeration tools (`ffuf`, `dirsearch`) to map protected attack surfaces.

### 🇯🇵 日本語
『The Web Application Hacker's Handbook』および『The Tangled Web』に詳述されている通り、HTTPメッセージの挙動には重要な攻撃手法が存在します：
1. **HTTPメソッド改ざん（Verb Tampering）**: 認可制御が `GET` や `POST` のみに適用されている場合（Javaの `web.xml` 設定不備など）、`HEAD`、`PUT`、`PATCH` や任意のメソッドに変更することでアクセス制限をバイパスできる場合があります。
2. **エラー画面からの情報漏洩**: `500 Internal Server Error` 時に出力されるスタックトレース、SQLクエリ、フレームワーク内部パスは、攻撃者にとって格好の偵察情報となります。
3. **CRLFインジェクション（HTTPレスポンス分割）**: レスポンスヘッダーに改行コード（`\r\n` / `%0d%0a`）を注入し、偽のヘッダーや任意のHTML本文を混入させてXSSやキャッシュ汚染を引き起こす攻撃。
4. **ステータスコードの差異分析**: `403 Forbidden`、`404 Not Found`、`302 Found` などの応答の違いを利用して、`ffuf` や `gobuster` による隠しディレクトリの洗い出しを行います。

```bash
# ── HTTP VERB TAMPERING TESTING WITH CURL ────────────────────

# 1. Test standard GET vs HEAD vs OPTIONS
$ curl -i -X GET http://target.htb/admin
$ curl -i -X HEAD http://target.htb/admin
$ curl -i -X OPTIONS http://target.htb/admin

# 2. Bypass GET-only filter using POST or custom verb
$ curl -i -X POST http://target.htb/admin
$ curl -i -X PUT http://target.htb/admin
$ curl -i -X TEST http://target.htb/admin

# ── CRLF INJECTION TESTING ───────────────────────────────────
$ curl -i "http://target.htb/redirect.php?url=%0d%0aSet-Cookie:%20admin=true"
```

## 7. 🧠 Quick Reference Cheatsheet

```bash
# ── TEST HTTP METHODS WITH CURL ──────────────────────────────
curl -X GET http://target.com/
curl -X POST -H "Content-Type: application/json" -d '{"id":1}' http://target.com/api
curl -X PUT -d "data=updated" http://target.com/resource/1
curl -X DELETE http://target.com/resource/1
curl -X OPTIONS -i http://target.com/              # check allowed methods
curl -I http://target.com/                         # HEAD request only

# ── INSPECT HEADERS & STATUS CODES ───────────────────────────
curl -s -o /dev/null -w "%{http_code}\n" http://target.com/  # print status only
curl -v http://target.com/api/test                           # full req/res flow
```
