## 1. ネットワークスタックにおけるHTTPの位置づけ

HTTP（Hypertext Transfer Protocol）は、URIで識別されるリソースを操作するためのアプリケーション層プロトコルである。中心となる意味論、すなわちメソッド、ステータスコード、ヘッダーはRFC 9110で定義され、それを古典的なTCPコネクションへどう写像するかはRFC 9112（HTTP/1.1）で定義されている。

```text
Client --request--> Server --response--> Client
```

HTTP自体は機密性も完全性も提供しない。その役割を担うのがTLS（HTTPS）である。慣習的なポート番号は、平文が80番、TLSが443番である。

WAHHは、HTTPを読み解く力をほぼすべてのWeb脆弱性クラスを理解するための土台として扱っている。インジェクションのシンクはパラメータ、ヘッダー、ボディに現れ、信頼に関する判断はCookieとoriginに現れる（『The Tangled Web』を参照）。

| レイヤー | 例 | セキュリティ上の注意 |
|:---|:---|:---|
| アプリケーション層 | HTTPメソッド、ヘッダー | 認可、入力の信頼性 |
| プレゼンテーション相当 | TLSレコード | 機密性、完全性 |
| トランスポート層 | TCP / QUIC | 信頼性、多重化 |
| ネットワーク層 | IP | ルーティング、ファイアウォール |

## 2. URL、authority、origin

### 2.1 URLの構造（概念）

<img width="1940" height="480" alt="image" src="https://github.com/user-attachments/assets/eeb6bbf0-c21f-4911-b6f7-7d7a62b2f58b" />

```
https://user:pass@app.example:443/path/res?x=1&y=2#frag
└─┬─┘  └────┬────┘ └────┬────┘ └┬┘ └──┬──┘ └─┬─┘ └─┬─┘
scheme   userinfo      host    port  path  query fragment
```

| 要素 | サーバーへ送信されるか | 注意点 |
|:---|:---|:---|
| scheme | 間接的（TLSか否か） | 機密性の高いアプリでは`https`必須 |
| userinfo | ほとんど使われず非推奨 | 歴史的にログやRefererへ漏れやすい |
| host + port | `Host` / `:authority` | バーチャルホスティング |
| path + query | request-target | 主要なインジェクション面 |
| fragment | 送信されない（ブラウザ内のみ） | DOM XSSのソースになり得る |

### 2.2 originタプル（『The Tangled Web』）

```text
Origin = (scheme, host, port)

https://example.com:443  と  https://example.com:8443   → 別のorigin(ポートが違う)
```

同一オリジンポリシー（SOP）はこのoriginを比較する。CORS、Cookie、CSRFの各ノートに進む前に、このタプルの理解が前提となる。

機密情報をクエリ文字列に入れてはならない。アクセスログ、ブラウザ履歴、`Referer`ヘッダーに残ってしまう。認証情報はボディとTLSで扱う。

セキュリティ境界でのURL正規化は慎重に行う必要がある。パーサーの実装差は、オープンリダイレクト、SSRF、キャッシュキーの混同といったバイパスの原因になってきた歴史がある。

## 3. プロトコルバージョン（セキュリティ上の差異）

| バージョン | 多重化 | ヘッドオブラインブロッキング | 典型的なトランスポート |
|:---|:---|:---|:---|
| HTTP/1.0 | なし | コネクション単位で発生 | TCP |
| HTTP/1.1 | パイプライニング（ほぼ未使用） | あり（TCP由来） | TCP、`Host`必須 |
| HTTP/2 | ストリーム | アプリ層で緩和 | 通常TCP + TLS |
| HTTP/3 | ストリーム | QUICによりさらに改善 | QUIC/UDP |

セキュリティ上の注意:

- HTTP/2のHPACKとHTTP/3はパーサーの複雑さを増す。実装は常にパッチ済みに保つこと。リクエストスマグリング研究は、歴史的にフロントエンドとバックエンドのパーサー間の解釈のずれ（desync）を狙ってきた。
- TLS 1.2以上、できれば1.3を優先し、可能なら平文通信は無効化する。
- `Connection: keep-alive`は通常の挙動である。この上に独自のフレーミングを作ってはならない。

## 4. TLSの信頼境界

```text
HTTPS = HTTP + TLS protection
```

```bash
# 自分のラボ - 自分が管理するホストまたは公開テストホストの証明書チェーンを確認する
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates
```

| コントロール | 目的 |
|:---|:---|
| 有効な証明書 + ホスト名一致 | サーバーの認証 |
| HSTS | ブラウザにHTTPSを強制する |
| TLS 1.3 | 最新の暗号スイート、デフォルトでの前方秘匿性 |
| 証明書ピンニング（モバイル、追加対策） | 運用コストと引き換えの追加的な信頼固定 |

curlはデフォルトで証明書を検証する。本番環境で`-k`を常用する癖をつけてはならない。

|:---|:---|:---|

## 6. 防御的・許可されたラボのためのcurl

curlはブラウザのレンダリングエンジンなしにHTTP(S)を話せるため、自分が所有するシステムのステータス行、ヘッダー、ボディを生の形で確認するのに適している。

### 6.1 安全な基本操作

```bash
# レスポンスヘッダー + ボディを表示、TLSエラー時は失敗させる（良い習慣）
curl -sS -D - -o body.bin https://localhost:8443/health

# タイミングとステータスのみ
curl -sS -o /dev/null -w "code=%{http_code} time=%{time_total}\n" https://localhost:8443/

# 明示的なメソッド + JSONを自分のAPIへ
curl -sS -X POST https://localhost:8443/api/echo \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  --data '{"ping":true}'
```

### 6.2 便利なフラグ（ラボ用）

| フラグ | 用途 |
|:---|:---|
| `-v` / `--trace-ascii` | 通信内容のデバッグ（注意: 機密情報が表示されることがある） |
| `-D -` | レスポンスヘッダーをダンプする |
| `-H` | ヘッダーを追加する |
| `-A` | User-Agentを設定する |
| `-L` | リダイレクトを追跡する（自作のSSRFツールではこの挙動を必ず再検証すること） |
| `--http1.1` / `--http2` | プロトコルバージョンを固定する |
| `--cacert` / `--cert` | カスタムの信頼ストアやmTLSラボ |
| `-x http://127.0.0.1:8080` | ローカルの許可されたプロキシ経由で送信する |

### 6.3 アンチパターン

| 習慣 | リスク |
|:---|:---|
| 常に`-k`を使う | 中間者攻撃や誤ったデプロイを見逃す |
| パスワードをシェル履歴に残す | 秘密情報の漏洩 |
| CIで`-v`の全出力をログに残す | トークン漏洩 |
| ユーザー由来のURLに`-L`を無条件で使う | SSRFクラスの問題 |

## 7. 許可されたプロキシ経由の検証（Burp、ZAP、mitmproxy）

許可されたラボでは、クライアントをローカルプロキシへ向ける。

```bash
export HTTPS_PROXY=http://127.0.0.1:8080
export HTTP_PROXY=http://127.0.0.1:8080
curl -sS https://app.lab.local/login --proxy http://127.0.0.1:8080
```

ラボ用CAを信頼ストアに追加するのは、練習用VMに限定する。見知らぬCAを日常使いのブラウザに追加してはならない。

WAHH流のワークフローは、傍受してパラメータを理解し、コードや設定を修正するというものである。許可のないターゲットに対して公開エクスプロイトを実行することではない。

## 8. 早見表

```bash
# ヘッダーのみ
curl -sSI https://localhost:8443/

# POSTフォーム
curl -sS -X POST https://localhost:8443/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data "user=alice&pass=$PASS"

# ボディを保存
curl -sS -o out.json https://localhost:8443/api/me -H "Authorization: Bearer $TOKEN"

# mTLSラボ
curl -sS https://localhost:8443/secure \
  --cacert lab-ca.pem --cert client.pem --key client.key
```

| 概念 | 要点 |
|:---|:---|
| origin | scheme + host + port |
| HTTPS | HTTP + TLS |
| curlのデフォルト | TLSを検証する |
| fragment | サーバーへ送信されない |
| ラボのルール | スコープ内のシステムのみ |

## 9. セキュリティノート: 脅威と対策

| 課題 | 対策 |
|:---|:---|
| 平文HTTP | HTTPSへのリダイレクト + HSTS。可能なら80番ポートを無効化する |
| URL内の機密情報 | ボディやヘッダーを使う。ログから取り除く |
| 本番スクリプトの`-k` | 削除し、CAをピン留めする |
| 日常ブラウザへのプロキシCA導入 | ラボ用プロファイルを分離する |
| リダイレクトチェーン | ホップ数を制限し、遷移先を検証する |
