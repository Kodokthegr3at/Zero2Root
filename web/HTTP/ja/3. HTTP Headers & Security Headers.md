## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| ヘッダー | リクエストやレスポンス内の名前/値のメタデータ行 |
| セキュリティヘッダー | ブラウザに保護を強制させるレスポンスヘッダー |
| CSP | Content-Security-Policy。ページが読み込めるスクリプト/リソースを制限する |
| HSTS | サイトに対してブラウザにHTTPSの使用を強制する |
| クッキー | セッション追跡のためにサーバーがブラウザに保存する小さな値 |
| SameSite | クロスサイトでの送信を制限するクッキー設定(CSRF対策) |
| CORS | あるサイトが別サイトのリソースを呼べる条件の規則 |

## 1. ヘッダーフィールドモデル

ヘッダーはメッセージのスタートラインにある名前と値のペアである(RFC 9110)。名前は大文字小文字を区別しない。値は危険な制御文字を含んではならない。多くのWebセキュリティ機能は`CSP`、`Set-Cookie`、`HSTS`のようにレスポンスヘッダーだけで表現される。

```text
Name: value

Content-Type: text/html; charset=utf-8
```

『The Tangled Web』は重要な指摘をしている。ブラウザは複雑な信頼エンジンであり、ヘッダーは理解せずにどこかからコピーして貼り付けるものではなく、意図をもって設定すべきポリシーのレバーである。

認可の根拠としてリクエストヘッダーだけを信用してはならない。`X-Forwarded-For`、`X-Original-URL`、そして誤設定されたプロキシの背後では偽装され得る`Host`がその例である。信頼できるエッジがこれらを正規化するまでは、単なる手がかりとして扱う。

## 2. 主要なリクエストヘッダー

<img width="626" height="401" alt="image" src="https://github.com/user-attachments/assets/923366e1-b7c0-4c29-be66-052cfc1d22bf" />

| ヘッダー | 役割 | セキュリティ上の注意 |
|:---|:---|:---|
| `Host` | 仮想ホスト | 不正な値は拒否する。SSRF判断の根拠として生の値を信用しない |
| `User-Agent` | クライアントの製品トークン | UAで認証しない。ログ出力は慎重に行う |
| `Authorization` | 認証情報 | Bearer、JWT、Basicのいずれか。TLS必須、ログに出さない |
| `Cookie` | 保存された状態 | CSRFおよびXSSと関わる |
| `Origin` | fetchの発生元オリジン | CORSの判断材料 |
| `Referer` | ナビゲーション元 | プライバシー上の懸念。URLに埋め込まれたトークンを漏らす可能性がある |
| `Accept` | 希望するメディアタイプ | コンテンツネゴシエーション |
| `Content-Type` | ボディの種類 | 状態を変更するエンドポイントでは検証を強制する |
| `If-None-Match` / `If-Modified-Since` | 条件付きリクエスト | キャッシュの正確性 |
| `Sec-Fetch-*` | fetchメタデータ | CSRF分離ポリシー |
| `X-Forwarded-For` | プロキシ経由のクライアントIP | 信頼できるホップが強制しない限り偽装可能 |

```http
GET /api/profile HTTP/1.1
Host: app.lab.local
Authorization: Bearer <access_token>
Cookie: session=<sid>
Origin: https://app.lab.local
Sec-Fetch-Site: same-origin
Sec-Fetch-Mode: cors
Accept: application/json
```

## 4. セキュリティレスポンスヘッダー、ベースライン

### 4.1 表: 現代的なベースライン

<img width="748" height="472" alt="image" src="https://github.com/user-attachments/assets/b7b95d03-366c-45c2-99e1-97a1e965782a" />

| ヘッダー | 設定例 | 軽減する脅威 |
|:---|:---|:---|
| `Content-Security-Policy` | `default-src 'self'; script-src 'nonce-...'` | XSSの影響を縮小する |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | ダウングレード攻撃、cookie-stripping系の問題 |
| `X-Content-Type-Options` | `nosniff` | MIMEスニッフィングによるXSS |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Referer経由のトークン漏洩 |
| `Permissions-Policy` | 使わない強力なAPIを無効化する | 機能の悪用 |
| `Cross-Origin-Opener-Policy` | `same-origin` | クロスオリジンのウィンドウ攻撃 |
| `Cross-Origin-Resource-Policy` | `same-origin` / `same-site` | Spectre系のリソース読み取り攻撃 |
| `Cross-Origin-Embedder-Policy` | `require-corp`(必要な場合) | 分離、COOPと組み合わせる |
| `X-Frame-Options` | `DENY` / `SAMEORIGIN` | クリックジャッキング(レガシー。CSPの`frame-ancestors`推奨) |

### 4.2 CSPの構成

しっかりしたCSPでは、少なくとも `default-src`、`script-src`、`object-src`、`base-uri`、`frame-ancestors` を設定する。

`'unsafe-inline'`よりnonceやhashを優先する。CSPは多層防御の一つであり、出力エンコーディングを省略してよい理由にはならない。詳細はXSSのノートを参照。

### 4.3 HSTS

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

含めるすべてのサブドメインでHTTPSが正しく展開された後にのみ有効化する。

WAHH流のラボハードニングでは、ログインのレスポンス、JSON API、ファイルダウンロードのヘッダーを監査する。ルートごとにポリシーが一貫していないことが多い。

既存の本番アプリではまずreport-onlyのCSP(`Content-Security-Policy-Report-Only`)から始め、その後enforceに移行する。

## 5. Cookie属性(RFC 6265)

```text
Set-Cookie: session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/
```

| 属性 | 目的 |
|:---|:---|
| `Secure` | HTTPSのみで送信 |
| `HttpOnly` | `document.cookie`から隠す |
| `SameSite=Strict\|Lax\|None` | クロスサイト送信ポリシー(`None`は`Secure`が必須) |
| `Max-Age` / `Expires` | 有効期限 |
| `Path` / `Domain` | 適用範囲。狭く保つ |
| `__Host-` / `__Secure-` | より強固なCookieのためのプレフィックス規則 |

多くのアプリでのセッションCookieのベースライン。

```http
Set-Cookie: __Host-session=...; Path=/; Secure; HttpOnly; SameSite=Lax
```

## 6. 同一オリジンポリシーとCORS

### 6.1 SOP(ブラウザ)

オリジンAのスクリプトは、デフォルトではオリジンBのレスポンスを読み取れない。一方でフォーム送信のようなクロスオリジンの書き込みは依然として発生し、これがCSRFというクラスの根本原因になる。

### 6.2 CORS

サーバーは次のヘッダーを通じて制御された読み取りを許可する。

| ヘッダー | 意味 |
|:---|:---|
| `Access-Control-Allow-Origin` | 厳密なオリジン、または(認証情報を伴わない場合の)`*` |
| `Access-Control-Allow-Credentials` | Cookieを許可する。`*`オリジンとの併用は禁止 |
| `Access-Control-Allow-Methods` | プリフライトで許可するメソッド |
| `Access-Control-Allow-Headers` | 許可するリクエストヘッダー |
| `Access-Control-Max-Age` | プリフライトのキャッシュ時間 |

安全なパターンは、許可リストにあるオリジンだけを反映することである。

```text
Originが許可リストにある   → Access-Control-Allow-Origin: <そのorigin>
それ以外                   → ヘッダーを付けない
```

認証情報を伴う任意のオリジンに対して`ACAO = request.Origin`を設定してはならない。

## 7. ヘッダーインジェクションと信頼の失敗

| クラス | 概要 | 対策 |
|:---|:---|:---|
| CRLFインジェクション | 攻撃者がヘッダー値に`\r\n`を挿入し、response splittingやcookieインジェクションを可能にする | CR/LFを除去する。フレームワークのcookie APIを使う |
| Hostヘッダー攻撃 | 絶対URL生成やキャッシュキーを汚染する | 信頼できる`Host` / `X-Forwarded-Host`のポリシーを強制する |
| キャッシュポイズニング | キャッシュキーに含まれないヘッダーがキャッシュされるボディに影響する | Varyを正しく設定する。信頼できない入力をキャッシュキーから除外する |
| `XFF`経由のIP偽装 | ヘッダーから取得したクライアントIPに基づく認可判断 | 自分自身のプロキシからの最終ホップのみを信頼する |
| 冗長な`Server` / `X-Powered-By` | 偵察の手助けになる | 削除するか汎用的な値にする |

```python
# UNSAFE sketch
location = "https://app/" + user_next  # open redirect, and header issues if mis-sent

# SAFE - allowlist the path
ALLOWED = {"/home", "/settings"}
if user_next not in ALLOWED:
    user_next = "/home"
# use the framework's redirect helper (encodes safely)
```

## 8. curlによる許可済みヘッダー監査

```bash
# OWN LAB - dump security-relevant response headers
curl -sSI https://localhost:8443/login | egrep -i \
  'HTTP/|content-security-policy|strict-transport|x-content-type|referrer-policy|permissions-policy|set-cookie|access-control|x-frame|cross-origin'

# Check the redirect target
curl -sSI https://localhost:8443/old | egrep -i 'HTTP/|location'

# Observe a CORS preflight against YOUR API
curl -sSI -X OPTIONS https://localhost:8443/api/data \
  -H "Origin: https://app.lab.local" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: authorization,content-type"
```

結果をベースラインの表と照らし合わせ、サーバー設定やアプリケーションのミドルウェアを修正する。ここでの目的は制御を回避することではない。

## 9. ベースラインチェックリスト

| 項目 | 目標 |
|:---|:---|
| HTTPS + HSTS | 本番ホストで有効 |
| `nosniff` | すべてのレスポンス |
| CSP | nonceまたはhashベース。不要な`unsafe-inline`を使わない |
| `frame-ancestors` / XFO | クリックジャッキング対策 |
| Referrer-Policy | 漏洩の少ないデフォルト |
| Cookie | `Secure; HttpOnly; SameSite` |
| CORS | 明示的な許可リスト。認証情報と`*`の併用禁止 |
| キャッシュ | 認証済みJSON/HTMLには`no-store` |
| 除去 | `X-Powered-By` / 詳細な`Server`値 |
| プロキシ | `Host`と転送ヘッダーを正規化する |

```
 ブラウザ側の信頼レバー              サーバーが意図的に設定するもの
 -------------------               -----------------------------
 CSP / COOP / CORP        <------  security middleware
 Cookie flags             <------  session layer
 CORS ACAO                <------  API gateway / app
 HSTS                     <------  TLS-enabled edge
```

## セキュリティノート: 脅威と対策

| 脅威 | ヘッダーの観点 | 対策 |
|:---|:---|:---|
| XSS | CSP、nosniff、エンコーディング | 多層防御 |
| CSRF | SameSite、トークン、Sec-Fetch | CSRFのノートを参照 |
| クリックジャッキング | `frame-ancestors` | デフォルトで拒否 |
| MITMダウングレード | HSTS | まず正しいHTTPS展開が前提 |
| Referer中のトークン | Referrer-Policy | URLにシークレットを含めない |
| CORS誤設定 | ACAOの反映 | 許可リスト |
| Response splitting | ヘッダー値中のCR/LF | 拒否する。フレームワークのAPIを使う |
