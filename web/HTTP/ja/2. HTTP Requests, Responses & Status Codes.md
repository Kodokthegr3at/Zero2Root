## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| リクエストライン | リクエストの1行目: メソッド + パス + バージョン |
| メソッド | GET(取得)、POST(データ送信)、PUT、DELETE など |
| ステータスコード | 2xx 成功、3xx リダイレクト、4xx クライアントエラー、5xx サーバーエラー |
| ヘッダー | ボディの前にあるメタデータの行 |
| ボディ | 実際の中身(フォームデータ、JSON、ファイル) |
| MIMEタイプ | ボディの種類(`text/html`、`application/json`) |
| 冪等(idempotent) | 1回送っても何回送っても効果が同じリクエスト |

## 1. HTTPメッセージモデル

HTTP/1.1のメッセージ（RFC 9112）は、おおまかに次のように表せる。

```text
開始行             GET /index.html HTTP/1.1
ヘッダー           Host: example.com
                   Accept: text/html
(空行)
ボディ(省略可)
```

ヘッダー部分は空行で終わる。ボディは空でもよい。ボディの区切り方は、`Content-Length`、`Transfer-Encoding: chunked`、またはメソッドやステータスに固有のルールによって決まる。

セキュリティ上の意味: 空行より後ろはすべて、アプリケーションフレームワークがパラメータ、JSON、マルチパートの各部分として解釈するデータである。ここが主要なインジェクション面になる（SQLiとXSSの各ノートを参照）。プロキシがこの区切りを別の方法で解釈すると、7節で扱うdesyncクラスの根本原因になる。

```http
POST /api/v1/items HTTP/1.1
Host: app.lab.local
Content-Type: application/json
Content-Length: 27
Authorization: Bearer <token>

{"name":"notebook","qty":1}
```

```
+--------------------------------+
| Start-line                     |
+--------------------------------+
| Header fields                  |
+--------------------------------+
| 空行（CRLF）                    |
+--------------------------------+
| オプションのボディ               |
+--------------------------------+
```

## 2. リクエスト行とリクエストターゲット

### HTTP/1.1の形式

<img width="1981" height="961" alt="image" src="https://github.com/user-attachments/assets/9ab34ec0-11b8-44d3-b8e9-425bc8f551c9" />

| ターゲット形式 | 例 | 用途 |
|:---|:---|:---|
| origin-form | `/path?query` | 絶対パス。`Host`と組み合わせて使うのが一般的 |
| absolute-form | `https://h/path` | プロキシ |
| authority-form | `host:443` | `CONNECT` |
| asterisk-form | `*` | `OPTIONS *` |

`Host`はHTTP/1.1で必須である。バーチャルホストはこれに依存しており、Hostヘッダーの異常値はキャッシュやルーティングを狂わせる典型的な落とし穴になる。値は正規化し、不審なものは拒否する。

パスとクエリは、検証されるまでは信頼できない文字列である。監査ログやSQL/HTMLのシンクへそのまま転記してはならない。

## 3. メソッドの意味論: safeとidempotent

RFC 9110は**safe**と**idempotent**という二つの性質を定義している。

| メソッド | Safe | Idempotent | 典型的な用途 | セキュリティ上の注意 |
|:---|:---:|:---:|:---|:---|
| `GET` | はい | はい | 読み取り | 状態を変更してはならない（変更するとCSRFやキャッシュ事故の原因になる） |
| `HEAD` | はい | はい | メタデータ | ボディがないGETと同じ |
| `OPTIONS` | はい | はい | プローブ | CORSプリフライト |
| `TRACE` | はい | はい | エコー | サーバー側で無効化する（レガシーなXSTリスク） |
| `POST` | いいえ | いいえ | 作成 / アクション | Cookie認証下ではCSRFトークンが必要 |
| `PUT` | いいえ | はい | 置換 | 全置換に対する認可が必要 |
| `DELETE` | いいえ | はい | 削除 | 認可と確認が必要 |
| `PATCH` | いいえ | 多くの場合いいえ | 部分更新 | スキーマ検証が必要。実務上は冪等でないことが多い |

**Safe（安全）:** サーバーのリソースに意図した状態変更が起きないこと。
**Idempotent（冪等）:** N回の同一リクエストが、ログを除けば1回のリクエストと同じ状態変化しか生まないこと。

つまり、同じ冪等なリクエストを1回送っても10回送っても、サーバーの状態は同じになる。

WAHHの指摘は今も有効である。「CSRFに弱い」バグの多くは、単に安全でないGETを使っているだけである。ルーティングテーブルはメソッド制限を明示的に強制すべきであり、ログアウトやパスワード変更を「利便性のため」にGETで受け付けてはならない。

```bash
# 自分のラボ - 自分のAPIでメソッド制限が機能しているか確認する
curl -sS -o /dev/null -w "%{http_code}\n" -X DELETE https://localhost:8443/api/item/1 \
  -H "Authorization: Bearer $TOKEN"
```

## 4. レスポンスの構造

<img width="2020" height="1127" alt="image" src="https://github.com/user-attachments/assets/25e45825-6138-49d4-aaf0-f62b16f52d5c" />

ステータス行の後にヘッダー、続いてオプションのボディが続く。クライアントは主に3桁のステータスコードで分岐処理を行い、人間向けテキストであり無視されることもあるreason phraseには依存しない。

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/items/42
Cache-Control: no-store
Content-Length: 15

{"id":42,"ok":1}
```

| フィールド | 防御的な運用 |
|:---|:---|
| `Server` / スタックトレース | バージョン情報の漏洩を最小化する |
| `Location` | オープンリダイレクト防止のためallowlist化する |
| 4xx/5xxのボディ | クライアントには汎用メッセージ、詳細はログに残す |
| キャッシュヘッダー | 認証済みレスポンスには`no-store` |

## 5. ステータスコードのクラス

| クラス | 範囲 | 意味 | APIでの指針 |
|:---|:---|:---|:---|
| 1xx | 100-199 | 情報 | アプリケーションコードではほぼ使わない |
| 2xx | 200-299 | 成功 | `200`、`201`、`204`を正しく使い分ける |
| 3xx | 300-399 | リダイレクト | `Location`の遷移先を検証する |
| 4xx | 400-499 | クライアントエラー | 401と403を丁寧に区別する |
| 5xx | 500-599 | サーバーエラー | 例外をクライアントにダンプしない |

### セキュリティ上重要な代表的コード

| コード | 名前 | 備考 |
|:---:|:---|:---|
| 200 | OK | ボディあり |
| 201 | Created | `Location`を付与 |
| 204 | No Content | ボディなし |
| 301/302/307/308 | リダイレクト | 307と308はメソッドをより厳密に保持する |
| 400 | Bad Request | バリデーション失敗 |
| 401 | Unauthorized | 認証情報の欠落または不正。該当する場合は`WWW-Authenticate`を送る |
| 403 | Forbidden | 認証済みだが許可されていない |
| 404 | Not Found | 存在の秘匿にも使われる。UXとのトレードオフがある |
| 405 | Method Not Allowed | `Allow`ヘッダーを付与 |
| 409 | Conflict | 同時更新の競合 |
| 415 | Unsupported Media Type | 想定外の`Content-Type` |
| 429 | Too Many Requests | レート制限 |
| 500 | Internal Error | サーバー側でログに記録する |
| 502/503/504 | Gateway / Unavailable / Timeout | エッジやプロキシ層の問題 |

「あいまいなステータスコードによるセキュリティ」だけに頼ってはならない。認可のチェックはサーバー側で明示的に行う必要がある。レート制限のないユーザー列挙を許すようなステータスの違い、例えばアカウントの存在有無によって403と401、あるいは詳細すぎるメッセージを返し分けるようなログインエンドポイントは避ける。

一貫したエラー形式とレート制限の組み合わせは、凝ったステータスコードの小細工よりも効果的である。認証系エンドポイントでは、列挙が問題になる箇所すべてで均一なレスポンスを優先する。

## 6. リクエストボディのエンコーディング

| `Content-Type` | 形式 | 落とし穴 |
|:---|:---|:---|
| `application/x-www-form-urlencoded` | `a=1&b=2` | 古典的なCSRF面。文字コードの問題もある |
| `multipart/form-data` | 境界（boundary）と各パート | アップロード脆弱性。巨大なパート |
| `application/json` | JSONテキスト | 一部パーサーでのプロトタイプ汚染。深さ制限が必要 |
| `application/xml` | XML | パーサーが安全でない場合のXXE |
| `text/plain` | 生テキスト | それでも検証は必要 |

```bash
# ラボ: 自分のアップローダーへのマルチパート送信（許可された場合）
curl -sS -F "file=@./sample.png;type=image/png" \
  https://localhost:8443/upload -H "Cookie: session=$SID"
```

`Content-Length`はボディと一致していなければならない。プロキシはこの不一致に敏感である。手作業での文字列分割より、フレームワークのパーサーを優先する。

## 7. リクエストスマグリング / desync（概念のみ）

フロントのプロキシとバックエンドがボディの境界、つまり`Content-Length`と`chunked`を異なる方法で解釈すると、HTTP/1.1のkeep-alive接続のキュー内でリクエストが危険な形で融合してしまうことがある。

問題は、フロントのプロキシとバックエンドが同じバイト列を読みながら、1つのリクエストがどこで終わり次がどこから始まるかについて食い違うときに起きる。

運用面の対策: 可能な限りエンドツーエンドでHTTP/2を使う、エッジでフレーミングを正規化する、あいまいなフレーミングを拒否する、プロキシとアプリケーションを常にパッチ済みに保つ、信頼レベルの異なるゾーン間でバックエンド接続を不用意に再利用しないといった対応が中心になる。本ノートはスマグリング用のペイロードを提供しない。

## 8. 安全なAPI設計のルール

1. メソッドを明示的に強制し、想定外の動詞は`405`で拒否する。
2. 状態を変更するメソッドには認証、認可、そしてCookieを使う場合はCSRF対策が必要である。
3. パースする前に`Content-Type`を検証する。
4. ボディサイズを制限する（`client_max_body_size`、フレームワーク側の上限）。
5. 正確なステータスコードを使い、内部情報を隠す。
6. 認証済みコンテンツのキャッシュは慎重に扱う（`Cache-Control: private, no-store`）。
7. リトライが発生し得る決済や`POST`操作には冪等性キーを使う。
8. 認証エラーのポリシーを統一し、レート制限を併用する。
9. `TRACE`を無効化し、`OPTIONS`はCORSに本当に必要な範囲に絞る。
10. ログにはメソッド、パスのテンプレート、ステータスを記録し、機密情報は記録しない。

## 9. 早見表

```http
# リクエスト
METHOD /path?query HTTP/1.1
Host: example
Header: value

body...

# レスポンス
HTTP/1.1 200 OK
Header: value

body...
```

| 用途 | コード |
|:---|:---|
| 読み取り成功 | 200 |
| 作成成功 | 201 |
| 不正な入力 | 400 |
| 認証情報なし | 401 |
| 認可失敗 | 403 |
| レート制限 | 429 |
| バグ | 500（クライアントには汎用メッセージ） |

```bash
curl -sS -X OPTIONS https://localhost:8443/api -D - -o /dev/null
curl -sS -X TRACE https://localhost:8443/ -D - -o /dev/null   # 拒否されることを期待する
```

## セキュリティノート: 脅威と対策

| 脅威 | メカニズム | 対策 |
|:---|:---|:---|
| GETによる状態変更を悪用したCSRF | safeメソッドの原則違反 | GETを読み取り専用に保つ |
| Verb tampering | 別のメソッドでチェックを回避される | メソッドと認可の判定を一箇所に集約する |
| エラー経由の情報漏洩 | ボディ内のスタックトレース | 汎用的な5xxレスポンス |
| オープンリダイレクト | `Location`の未検証 | allowlist |
| Desync | プロキシとバックエンドのパーサー不一致 | 正規化、HTTP/2、パッチ適用の徹底 |
| 過大なボディ | サービス拒否 | サイズ制限 |
