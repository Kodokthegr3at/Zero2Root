## Istilah penting

Istilah-istilah ini akan sering muncul di materi.

| Istilah | Artinya |
|:---|:---|
| Request line | Baris pertama sebuah request: method + path + versi |
| Method | GET (ambil), POST (kirim data), PUT, DELETE, dan lainnya |
| Status code | 2xx sukses, 3xx redirect, 4xx error klien, 5xx error server |
| Header | Baris metadata sebelum body |
| Body | Muatan sebenarnya (data form, JSON, sebuah file) |
| MIME type | Jenis konten body-nya (`text/html`, `application/json`) |
| Idempotent | Request yang efeknya sama dikirim sekali atau berkali-kali |

## 1. Model pesan HTTP

Pesan HTTP/1.1 (RFC 9112) secara kasar berbentuk:

```text
start line         GET /index.html HTTP/1.1
header             Host: example.com
                   Accept: text/html
(baris kosong)
body (opsional)
```

Bagian header diakhiri dengan baris kosong. Body boleh kosong. Framing body ditentukan oleh `Content-Length`, `Transfer-Encoding: chunked`, atau aturan khusus untuk metode/status tertentu.

Relevansi keamanan: semua yang ada setelah baris kosong adalah data yang diparsing oleh framework aplikasi menjadi parameter, JSON, atau bagian multipart. Itulah permukaan injeksi utama (lihat catatan SQLi dan XSS). Proxy bisa memparsing framing secara berbeda, dan itulah akar dari kelas desync yang dibahas di bagian 7.

```http
POST /api/v1/items HTTP/1.1
Host: app.lab.local
Content-Type: application/json
Content-Length: 27
Authorization: Bearer <token>

{"name":"notebook","qty":1}
```

```
+--------------------------------+
| Start-line                     |
+--------------------------------+
| Header fields                  |
+--------------------------------+
| baris kosong (CRLF)            |
+--------------------------------+
| Body opsional                  |
+--------------------------------+
```

## 2. Request-line dan request target

### Bentuk di HTTP/1.1

<img width="1981" height="961" alt="image" src="https://github.com/user-attachments/assets/9ab34ec0-11b8-44d3-b8e9-425bc8f551c9" />

| Bentuk target | Contoh | Kegunaan |
|:---|:---|:---|
| Origin-form | `/path?query` | Path absolut, umum bersama `Host` |
| Absolute-form | `https://h/path` | Proxy |
| Authority-form | `host:443` | `CONNECT` |
| Asterisk-form | `*` | `OPTIONS *` |

`Host` wajib di HTTP/1.1. Virtual host bergantung padanya; anomali host header adalah jebakan klasik untuk cache dan routing, jadi normalisasi nilainya dan tolak apa pun yang terlihat aneh.

Path dan query adalah string tidak dipercaya sampai divalidasi. Jangan mirror mentah-mentah ke log rahasia atau ke sink SQL/HTML.

## 3. Semantik metode: safe dan idempotent

RFC 9110 mendefinisikan properti **safe** dan **idempotent**:

| Metode | Safe | Idempotent | Kegunaan umum | Catatan keamanan |
|:---|:---:|:---:|:---|:---|
| `GET` | Ya | Ya | Baca | Tidak boleh mengubah state (jika mengubah: risiko CSRF dan cache) |
| `HEAD` | Ya | Ya | Metadata | Sama seperti GET tanpa body |
| `OPTIONS` | Ya | Ya | Probe | CORS preflight |
| `TRACE` | Ya | Ya | Echo | Nonaktifkan di server (risiko XST warisan) |
| `POST` | Tidak | Tidak | Create / aksi | Butuh token CSRF jika autentikasi lewat cookie |
| `PUT` | Tidak | Ya | Replace | AuthZ untuk penggantian penuh |
| `DELETE` | Tidak | Ya | Hapus | AuthZ ditambah konfirmasi |
| `PATCH` | Tidak | Sering tidak | Update parsial | Validasi skema; dalam praktik sering tidak idempotent |

**Safe:** tidak ada perubahan state yang disengaja pada resource server.
**Idempotent:** N request identik menghasilkan efek state yang sama seperti satu request, terlepas dari log.

Dengan kata lain, mengirim request idempotent yang sama sekali atau sepuluh kali akan menghasilkan state server yang sama.

Pengamatan WAHH masih berlaku: sebagian besar bug "CSRF-friendly" sebenarnya hanyalah GET yang tidak aman. Route table harus menegakkan pembatasan metode, dan logout atau ganti password tidak boleh menerima GET "demi kenyamanan."

```bash
# LAB SENDIRI - amati penegakan metode di API Anda
curl -sS -o /dev/null -w "%{http_code}\n" -X DELETE https://localhost:8443/api/item/1 \
  -H "Authorization: Bearer $TOKEN"
```

## 4. Struktur respons

<img width="2020" height="1127" alt="image" src="https://github.com/user-attachments/assets/25e45825-6138-49d4-aaf0-f62b16f52d5c" />

Setelah status line diikuti header, lalu body opsional. Klien bercabang terutama berdasarkan kode status tiga digit, bukan reason phrase yang merupakan teks untuk manusia dan boleh diabaikan klien.

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/items/42
Cache-Control: no-store
Content-Length: 15

{"id":42,"ok":1}
```

| Field | Praktik defensif |
|:---|:---|
| `Server` / stack trace | Minimalkan kebocoran versi |
| `Location` | Allowlist untuk mencegah open redirect |
| Body pada 4xx/5xx | Pesan generik ke klien; detail tetap di log |
| Header cache | `no-store` untuk respons yang terautentikasi |

## 5. Kelas kode status

| Kelas | Rentang | Arti | Panduan API |
|:---|:---|:---|:---|
| 1xx | 100-199 | Informational | Jarang dipakai di kode aplikasi |
| 2xx | 200-299 | Sukses | Gunakan `200`, `201`, `204` dengan tepat |
| 3xx | 300-399 | Redirection | Validasi target `Location` |
| 4xx | 400-499 | Client error | Bedakan 401 dan 403 dengan cermat |
| 5xx | 500-599 | Server error | Jangan pernah membuang exception ke klien |

### Kode terpilih (relevan untuk keamanan)

| Kode | Nama | Catatan |
|:---:|:---|:---|
| 200 | OK | Dengan body |
| 201 | Created | Ditambah `Location` |
| 204 | No Content | Body kosong |
| 301/302/307/308 | Redirect | 307 dan 308 mempertahankan metode lebih ketat |
| 400 | Bad Request | Validasi gagal |
| 401 | Unauthorized | Auth hilang/tidak valid; kirim `WWW-Authenticate` bila relevan |
| 403 | Forbidden | Terautentikasi tapi tidak diizinkan |
| 404 | Not Found | Juga dipakai untuk menyembunyikan eksistensi, trade-off dengan UX |
| 405 | Method Not Allowed | Ditambah header `Allow` |
| 409 | Conflict | Update konkuren |
| 415 | Unsupported Media Type | `Content-Type` tak terduga |
| 429 | Too Many Requests | Rate limiting |
| 500 | Internal Error | Log di sisi server |
| 502/503/504 | Gateway / Unavailable / Timeout | Lapisan edge atau proxy |

Jangan mengandalkan "security through obscure status" saja. Pemeriksaan otorisasi harus eksplisit di server. Hindari perbedaan status yang memungkinkan user enumeration tanpa rate limit, misalnya endpoint login yang mengembalikan 403 vs 401 vs pesan terlalu detail tergantung apakah akun tersebut ada.

Bentuk error yang konsisten plus rate limit lebih efektif daripada trik status yang rumit. Untuk endpoint autentikasi, utamakan respons yang seragam di mana pun enumeration menjadi risiko.

## 6. Encoding body request

| `Content-Type` | Bentuk | Jebakan |
|:---|:---|:---|
| `application/x-www-form-urlencoded` | `a=1&b=2` | Permukaan CSRF klasik; masalah charset |
| `multipart/form-data` | Boundary plus bagian | Kerentanan upload; bagian berukuran besar |
| `application/json` | Teks JSON | Prototype pollution di beberapa parser; perlu batas kedalaman |
| `application/xml` | XML | XXE jika parser tidak aman |
| `text/plain` | Mentah | Tetap perlu divalidasi |

```bash
# Lab: multipart ke uploader Anda (berizin)
curl -sS -F "file=@./sample.png;type=image/png" \
  https://localhost:8443/upload -H "Cookie: session=$SID"
```

`Content-Length` harus cocok dengan body karena proxy sensitif terhadap ketidakcocokan. Utamakan parser framework dibanding pemotongan string manual.

## 7. Request smuggling / desync, konsep saja

Ketika front proxy dan backend memparsing batas body secara berbeda, yaitu `Content-Length` versus `chunked`, request dapat "menyatu" secara berbahaya di antrean koneksi HTTP/1.1 keep-alive.

Masalahnya muncul ketika front proxy dan backend membaca byte yang sama tetapi tidak sepakat di mana satu request berakhir dan request berikutnya dimulai.

Pertahanan operasional: gunakan HTTP/2 end-to-end bila memungkinkan, normalisasi framing di edge, tolak framing ambigu, jaga proxy dan aplikasi tetap ter-patch, dan hindari penggunaan ulang koneksi backend secara ceroboh lintas zona trust. Catatan ini tidak menyediakan payload smuggling.

## 8. Aturan desain API aman

1. Tegakkan metode secara eksplisit; tolak verb tak terduga dengan `405`.
2. Metode yang mengubah state butuh autentikasi, otorisasi, dan strategi CSRF jika memakai cookie.
3. Validasi `Content-Type` sebelum parsing.
4. Batasi ukuran body (`client_max_body_size`, batas framework).
5. Gunakan kode status yang presisi dan sembunyikan detail internal.
6. Cache konten terautentikasi dengan hati-hati (`Cache-Control: private, no-store`).
7. Gunakan idempotency key untuk pembayaran dan operasi `POST` lain yang rawan retry.
8. Terapkan kebijakan error autentikasi yang seragam plus rate limit.
9. Nonaktifkan `TRACE`; batasi `OPTIONS` sesuai kebutuhan CORS saja.
10. Log metode, template path, dan status, jangan pernah rahasia.

## 9. Referensi cepat

```http
# Request
METHOD /path?query HTTP/1.1
Host: example
Header: value

body...

# Response
HTTP/1.1 200 OK
Header: value

body...
```

| Kebutuhan | Kode |
|:---|:---|
| Baca sukses | 200 |
| Berhasil dibuat | 201 |
| Input salah | 400 |
| Auth hilang | 401 |
| AuthZ gagal | 403 |
| Rate limit | 429 |
| Bug | 500 (pesan generik ke klien) |

```bash
curl -sS -X OPTIONS https://localhost:8443/api -D - -o /dev/null
curl -sS -X TRACE https://localhost:8443/ -D - -o /dev/null   # harus ditolak
```

## Catatan keamanan: ancaman dan pertahanan

| Ancaman | Mekanisme | Pertahanan |
|:---|:---|:---|
| CSRF via GET yang mengubah state | Properti safe method dilanggar | Jaga GET tetap read-only |
| Verb tampering | Metode alternatif melewati pemeriksaan | Sentralisasi penegakan metode dan authZ |
| Kebocoran info via error | Stack trace di body | Respons 5xx generik |
| Open redirect | `Location` tidak diperiksa | Allowlist |
| Desync | Ketidakcocokan parser proxy dan backend | Normalisasi; HTTP/2; jaga sistem ter-patch |
| Body berukuran besar | Denial of service | Batas ukuran |
