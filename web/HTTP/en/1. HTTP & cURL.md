## 1. HTTP in the network stack

HTTP (Hypertext Transfer Protocol) is an application-layer protocol for manipulating resources identified by a URI. The core semantics, meaning methods, status codes, and headers, are defined in RFC 9110. The mapping onto a classic TCP connection is defined in RFC 9112 (HTTP/1.1).

```text
Client --request--> Server --response--> Client
```

HTTP on its own provides no confidentiality or integrity. That job belongs to TLS (HTTPS). The de facto ports are 80 for cleartext and 443 for TLS.

WAHH treats HTTP fluency as the foundation for understanding almost every web vulnerability class: injection sinks appear in parameters, headers, and bodies, and trust decisions appear in cookies and origins (see *The Tangled Web*).

| Layer | Example | Security note |
|:---|:---|:---|
| Application | HTTP methods, headers | AuthZ, input trust |
| Presentation-ish | TLS record | Confidentiality, integrity |
| Transport | TCP / QUIC | Reliability, multiplexing |
| Network | IP | Routing, firewall |

## 2. URL, authority, and origin

### 2.1 URL anatomy (conceptual)

<img width="1940" height="480" alt="image" src="https://github.com/user-attachments/assets/eeb6bbf0-c21f-4911-b6f7-7d7a62b2f58b" />

```
https://user:pass@app.example:443/path/res?x=1&y=2#frag
└─┬─┘  └────┬────┘ └────┬────┘ └┬┘ └──┬──┘ └─┬─┘ └─┬─┘
scheme   userinfo      host    port  path  query fragment
```

| Part | Sent to server? | Notes |
|:---|:---|:---|
| Scheme | Indirect (TLS vs not) | `https` required for sensitive apps |
| Userinfo | Rarely used, discouraged | Historically leaks in logs and Referer |
| Host + port | `Host` / `:authority` | Virtual hosting |
| Path + query | Request-target | Primary injection surface |
| Fragment | No (browser-only) | Can feed DOM XSS sources |

### 2.2 Origin tuple (*The Tangled Web*)

```text
Origin = (scheme, host, port)

https://example.com:443  vs  https://example.com:8443   → different origins (the port differs)
```

The Same-Origin Policy compares origins. Understanding this tuple is mandatory before working through the CORS, cookie, and CSRF notes.

Do not put secrets in the query string: they end up in access logs, browser history, and the `Referer` header. Prefer the body plus TLS for credentials.

Normalize URLs carefully at security boundaries. Parser differentials have historically caused bypasses, including open redirects, SSRF, and cache-key confusion.

## 3. Protocol versions (security-relevant differences)

| Version | Multiplexing | Head-of-line blocking | Typical transport |
|:---|:---|:---|:---|
| HTTP/1.0 | No | Per connection | TCP |
| HTTP/1.1 | Pipelining (rarely used) | Yes (TCP) | TCP, `Host` required |
| HTTP/2 | Streams | Mitigated at app layer | TCP + TLS usually |
| HTTP/3 | Streams | Better, via QUIC | QUIC/UDP |

Security notes:

- HTTP/2 HPACK and HTTP/3 add parsing complexity. Keep implementations patched; request-smuggling research has historically targeted desync between front-end and back-end parsers (see section 2 for the desync concept elsewhere in this series).
- Prefer TLS 1.2 or newer, ideally 1.3; disable cleartext where possible.
- `Connection: keep-alive` is normal behavior. Do not invent custom framing on top of it.

## 4. TLS boundary and trust

```text
HTTPS = HTTP + TLS protection
```

```bash
# OWN LAB - inspect the certificate chain of a host you control or a public test host
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates
```

| Control | Purpose |
|:---|:---|
| Valid cert + hostname | Authenticate the server |
| HSTS | Force HTTPS in browsers |
| TLS 1.3 | Modern ciphers, forward secrecy by default |
| Certificate pinning (mobile, extra) | Extra trust lock, at an operational cost |

curl verifies certificates by default. Do not get into the habit of using `-k` in production.

## 6. curl for defensive and authorized labs

curl speaks HTTP(S) without a browser renderer, which makes it ideal for inspecting raw status lines, headers, and bodies on systems you own.

### 6.1 Safe baseline habits

```bash
# Show response headers + body; fail on TLS errors (good)
curl -sS -D - -o body.bin https://localhost:8443/health

# Timing / status only
curl -sS -o /dev/null -w "code=%{http_code} time=%{time_total}\n" https://localhost:8443/

# Explicit method + JSON to YOUR API
curl -sS -X POST https://localhost:8443/api/echo \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  --data '{"ping":true}'
```

### 6.2 Useful flags (lab)

| Flag | Use |
|:---|:---|
| `-v` / `--trace-ascii` | Debug the wire format (careful: this can expose secrets) |
| `-D -` | Dump response headers |
| `-H` | Add a header |
| `-A` | Set the User-Agent |
| `-L` | Follow redirects (re-validate this behavior in any SSRF tooling you write) |
| `--http1.1` / `--http2` | Force a protocol version |
| `--cacert` / `--cert` | Custom trust store or mTLS lab |
| `-x http://127.0.0.1:8080` | Send through a local authorized proxy |

### 6.3 Anti-patterns

| Habit | Risk |
|:---|:---|
| Always using `-k` | Hides MITM issues and bad deployments |
| Putting passwords in shell history | Secret leak |
| Logging full `-v` output in CI | Token leakage |
| Blindly using `-L` on user-supplied URLs | SSRF class |

## 7. Authorized proxying (Burp, ZAP, mitmproxy)

For an authorized lab, point the client at a local proxy:

```bash
export HTTPS_PROXY=http://127.0.0.1:8080
export HTTP_PROXY=http://127.0.0.1:8080
curl -sS https://app.lab.local/login --proxy http://127.0.0.1:8080
```

Install the lab CA in the trust store only on the practice VM. Never install an unknown CA in your daily browser.

The WAHH workflow is: intercept, understand the parameters, then fix the code or configuration. It is not about running public exploits against a target without authorization.

## 8. Cheatsheet

```bash
# Headers only
curl -sSI https://localhost:8443/

# POST form
curl -sS -X POST https://localhost:8443/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data "user=alice&pass=$PASS"

# Save body
curl -sS -o out.json https://localhost:8443/api/me -H "Authorization: Bearer $TOKEN"

# mTLS lab
curl -sS https://localhost:8443/secure \
  --cacert lab-ca.pem --cert client.pem --key client.key
```

| Concept | One-liner |
|:---|:---|
| Origin | scheme + host + port |
| HTTPS | HTTP + TLS |
| curl default | verifies TLS |
| Fragment | not sent to the server |
| Lab rule | only systems in scope |

## 9. Security notes: threats and defenses

| Issue | Defense |
|:---|:---|
| Cleartext HTTP | Redirect to HTTPS + HSTS; disable port 80 where possible |
| Secret in URL | Use the body or headers instead; strip logs |
| `-k` in production scripts | Remove it; pin the CA |
| Proxy CA on a daily browser | Isolate lab profiles |
| Redirect chains | Bound the number of hops; validate destinations |
