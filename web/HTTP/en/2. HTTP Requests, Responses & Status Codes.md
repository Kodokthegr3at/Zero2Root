## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| Request line | The first line of a request: method + path + version |
| Method | GET (fetch), POST (send data), PUT, DELETE, and others |
| Status code | 2xx success, 3xx redirect, 4xx client error, 5xx server error |
| Header | Metadata lines before the body |
| Body | The actual payload (form data, JSON, a file) |
| MIME type | What kind of content the body is (`text/html`, `application/json`) |
| Idempotent | A request that has the same effect whether sent once or many times |

## 1. HTTP message model

An HTTP/1.1 message (RFC 9112) is, roughly:

```text
start line         GET /index.html HTTP/1.1
headers            Host: example.com
                   Accept: text/html
(empty line)
body (optional)
```

The header section ends with a blank line. The body can be empty. Body framing is determined by `Content-Length`, `Transfer-Encoding: chunked`, or rules specific to the method or status.

Security relevance: everything after the blank line is data that application frameworks parse into parameters, JSON, or multipart parts. That is the primary injection surface (see the SQLi and XSS notes). Proxies may parse framing differently, which is the root of the desync class discussed in section 7.

```http
POST /api/v1/items HTTP/1.1
Host: app.lab.local
Content-Type: application/json
Content-Length: 27
Authorization: Bearer <token>

{"name":"notebook","qty":1}
```

```
+--------------------------------+
| Start-line                     |
+--------------------------------+
| Header fields                  |
+--------------------------------+
| empty CRLF                     |
+--------------------------------+
| Optional body                  |
+--------------------------------+
```

## 2. Request-line and request target

### HTTP/1.1 form

<img width="1981" height="961" alt="image" src="https://github.com/user-attachments/assets/9ab34ec0-11b8-44d3-b8e9-425bc8f551c9" />

| Target form | Example | Use |
|:---|:---|:---|
| Origin-form | `/path?query` | Absolute path, common alongside `Host` |
| Absolute-form | `https://h/path` | Proxies |
| Authority-form | `host:443` | `CONNECT` |
| Asterisk-form | `*` | `OPTIONS *` |

`Host` is required in HTTP/1.1. Virtual hosts depend on it; host-header anomalies are a classic cache and routing footgun, so normalize the value and reject anything that looks wrong.

The path and query are untrusted strings until validated. Do not mirror them raw into secure logs or into SQL/HTML sinks.

## 3. Method semantics: safe and idempotent

RFC 9110 defines the **safe** and **idempotent** properties:

| Method | Safe | Idempotent | Typical use | Security note |
|:---|:---:|:---:|:---|:---|
| `GET` | Yes | Yes | Read | Must not mutate state (CSRF and cache risk otherwise) |
| `HEAD` | Yes | Yes | Metadata | Same as GET without a body |
| `OPTIONS` | Yes | Yes | Probe | CORS preflight |
| `TRACE` | Yes | Yes | Echo | Disable on servers (legacy XST risk) |
| `POST` | No | No | Create / action | Needs CSRF tokens under cookie auth |
| `PUT` | No | Yes | Replace | AuthZ on full replace |
| `DELETE` | No | Yes | Remove | AuthZ plus confirmation |
| `PATCH` | No | Often not | Partial update | Schema validation; frequently non-idempotent in practice |

**Safe:** no intended state change on server resources.
**Idempotent:** N identical requests produce the same state effect as one request, aside from logs.

In other words, sending the same idempotent request once or ten times leaves the server in the same state.

WAHH's observation still holds: a large share of "CSRF-friendly" bugs are simply unsafe GET requests. Route tables should enforce method restrictions, and logout or password change should never accept GET "for convenience."

```bash
# OWN LAB - observe method enforcement on your API
curl -sS -o /dev/null -w "%{http_code}\n" -X DELETE https://localhost:8443/api/item/1 \
  -H "Authorization: Bearer $TOKEN"
```

## 4. Response structure

<img width="2020" height="1127" alt="image" src="https://github.com/user-attachments/assets/25e45825-6138-49d4-aaf0-f62b16f52d5c" />

After the status line comes headers, then an optional body. Clients branch primarily on the three-digit status code, not on the reason phrase, which is human-readable text that clients may ignore.

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/items/42
Cache-Control: no-store
Content-Length: 15

{"id":42,"ok":1}
```

| Field | Defensive practice |
|:---|:---|
| `Server` / stack traces | Minimize version leakage |
| `Location` | Allowlist for open-redirect prevention |
| Body on 4xx/5xx | Generic messages to clients; detail stays in logs |
| Cache headers | `no-store` for authenticated responses |

## 5. Status code classes

| Class | Range | Meaning | API guidance |
|:---|:---|:---|:---|
| 1xx | 100-199 | Informational | Rare in application code |
| 2xx | 200-299 | Success | Use `200`, `201`, `204` correctly |
| 3xx | 300-399 | Redirection | Validate `Location` targets |
| 4xx | 400-499 | Client error | Distinguish 401 from 403 carefully |
| 5xx | 500-599 | Server error | Never dump exceptions to the client |

### Selected codes (security-relevant)

| Code | Name | Notes |
|:---:|:---|:---|
| 200 | OK | With body |
| 201 | Created | Plus `Location` |
| 204 | No Content | Empty body |
| 301/302/307/308 | Redirects | 307 and 308 preserve the method more strictly |
| 400 | Bad Request | Validation failure |
| 401 | Unauthorized | Missing or invalid auth; send `WWW-Authenticate` where applicable |
| 403 | Forbidden | Authenticated but not allowed |
| 404 | Not Found | Also used to hide existence, a trade-off against UX |
| 405 | Method Not Allowed | Plus `Allow` header |
| 409 | Conflict | Concurrent update |
| 415 | Unsupported Media Type | Unexpected `Content-Type` |
| 429 | Too Many Requests | Rate limiting |
| 500 | Internal Error | Log server-side |
| 502/503/504 | Gateway / Unavailable / Timeout | Edge or proxy layer |

Do not rely on "security through obscure status codes" alone. Authorization checks must be explicit on the server. Avoid status differences that enable user enumeration without rate limiting, for example a login endpoint that returns 403 vs 401 vs an overly detailed message depending on whether the account exists.

Consistent error shapes plus rate limits beat clever status tricks. For authentication endpoints, prefer uniform responses wherever enumeration matters.

## 6. Request body encodings

| `Content-Type` | Shape | Pitfalls |
|:---|:---|:---|
| `application/x-www-form-urlencoded` | `a=1&b=2` | Classic CSRF surface; charset issues |
| `multipart/form-data` | Boundaries plus parts | Upload vulnerabilities; oversized parts |
| `application/json` | JSON text | Prototype pollution in some parsers; depth limits needed |
| `application/xml` | XML | XXE if the parser is unsafe |
| `text/plain` | Raw | Still needs validation |

```bash
# Lab: multipart to your uploader (authorized)
curl -sS -F "file=@./sample.png;type=image/png" \
  https://localhost:8443/upload -H "Cookie: session=$SID"
```

`Content-Length` must match the body, since proxies are sensitive to mismatches. Prefer framework parsers over manual string splitting.

## 7. Request smuggling / desync, concept only

When a front proxy and a backend parse the body boundary differently, meaning `Content-Length` versus `chunked`, requests can merge dangerously in an HTTP/1.1 keep-alive connection queue.

The trouble starts when the front proxy and the backend read the same bytes and disagree about where one request ends and the next begins.

Operational defense: use HTTP/2 end-to-end where possible, normalize framing at the edge, reject ambiguous framing, keep proxies and applications patched, and avoid reusing backend connections carelessly across trust zones. This note does not provide smuggling payloads.

## 8. Secure API design rules

1. Enforce methods explicitly; reject unexpected verbs with `405`.
2. Mutating methods require authentication, authorization, and a CSRF strategy if using cookies.
3. Validate `Content-Type` before parsing.
4. Bound body size (`client_max_body_size`, framework limits).
5. Use precise status codes and hide internals.
6. Cache authenticated content carefully (`Cache-Control: private, no-store`).
7. Use idempotency keys for payments and other `POST` operations subject to retries.
8. Apply a uniform authentication error policy plus rate limits.
9. Disable `TRACE`; restrict `OPTIONS` to what CORS actually needs.
10. Log method, path template, and status, never secrets.

## 9. Cheatsheet

```http
# Request
METHOD /path?query HTTP/1.1
Host: example
Header: value

body...

# Response
HTTP/1.1 200 OK
Header: value

body...
```

| Need | Code |
|:---|:---|
| Read OK | 200 |
| Created | 201 |
| Bad input | 400 |
| Auth missing | 401 |
| AuthZ fail | 403 |
| Rate limit | 429 |
| Bug | 500 (generic client message) |

```bash
curl -sS -X OPTIONS https://localhost:8443/api -D - -o /dev/null
curl -sS -X TRACE https://localhost:8443/ -D - -o /dev/null   # expect deny
```

## Security notes: threats and defenses

| Threat | Mechanism | Defense |
|:---|:---|:---|
| CSRF via GET mutate | Safe method violated | Keep GET read-only |
| Verb tampering | Alternate method bypasses a check | Centralize method and authZ enforcement |
| Info leak via errors | Stack trace in the body | Generic 5xx responses |
| Open redirect | Unchecked `Location` | Allowlist |
| Desync | Parser mismatch between proxy and backend | Normalize; HTTP/2; keep systems patched |
| Oversized body | Denial of service | Size limits |
