## 1. Definisi

SSRF terjadi ketika aplikasi sisi server mengambil resource berdasarkan referensi yang bisa dipengaruhi penyerang (URL, host, atau path), sehingga server menjadi confused deputy yang mencapai target yang sebenarnya tidak dimaksudkan untuk publik: layanan internal, localhost, alamat link-local, atau metadata cloud.

$$
\mathsf{Fetch}(\mathsf{url}_{\mathsf{user}})
\;\Rightarrow\;
\text{request originates from trusted server IP / VPC}
$$

Berbeda dari CSRF, di mana browser korban yang mengirim request, pada SSRF justru server aplikasi itu sendiri yang mengirim request.

SSRF berbahaya karena firewall dan layanan "internal-only" sering secara default mempercayai subnet aplikasi itu sendiri. Kelas bug yang mendasarinya adalah pembatasan yang tidak memadai pada request keluar dari sisi server.

---

## 2. Kelas dampak (konseptual)

| Kelas | Deskripsi | Penekanan pertahanan |
|:---|:---|:---|
| Internal recon | Menyentuh port atau layanan di dalam VPC | Allowlist egress; network policy |
| Local service abuse | Mengenai port admin `localhost` atau agent lokal | Blokir loopback; jangan ekspos unix socket lewat URL HTTP |
| Cloud credential exposure | Mencapai endpoint instance metadata | IMDSv2 / hop limit; firewall endpoint metadata |
| File/handler scheme | Scheme URL berbahaya kalau library mengizinkannya | Allowlist scheme, hanya `https` |
| Response misuse | Aplikasi meneruskan body response internal balik ke penyerang | Jangan pernah merefleksikan body fetch mentah; terapkan batas ukuran |
| Blind SSRF | Hanya side effect yang teramati (DNS, timing, webhook) | Kontrol URL yang sama; monitor egress |

Beberapa library secara historis mendukung scheme non-HTTP. Catatan ini tidak membahas rantai eksploit untuk scheme tersebut; poin yang perlu dipahami adalah membatasi scheme dan parser sekaligus.

---

## 3. Akar masalah

Fitur produk yang umum memicu SSRF:

- URL preview, unfurl link, atau thumbnail generator
- Webhook tester, atau fitur "fetch callback ini"
- Import dari URL, PDF generator, atau document converter
- SSO atau metadata discovery dengan URL yang dikendalikan pengguna
- Image proxy atau CDN yang menarik dari origin sembarang

Akar masalahnya adalah memperlakukan string URL sebagai aman hanya karena "HTTP client library cuma mengunduh." Keamanan bergantung pada kebijakan destinasi, bukan pada "kami pakai HTTPS."

## 4. Jebakan validasi URL

Validasi naif sering gagal karena lapisan yang berbeda menafsirkan URL secara berbeda.

### 4.1 Allowlist hostname vs allowlist IP

Memblokir string `127.0.0.1` saja tidak cukup kalau:

- DNS bisa mengembalikan IP internal setelah pemeriksaan lolos, yang disebut DNS rebinding, sebuah TOCTOU resolve-check-resolve.
- Bentuk desimal, hex, atau IPv6-mapped bisa mengkodekan alamat loopback.
- Alias hostname internal bisa menunjuk ke target yang diblokir dengan nama yang berbeda.

Pola yang aman: resolve DNS, verifikasi bahwa alamat IP hasilnya ada di allowlist kebijakan, lalu connect hanya ke IP yang sudah diverifikasi (pin) itu, dengan TTL pendek dan memvalidasi ulang di setiap redirect, bukan mempercayai lagi hostname aslinya.

### 4.2 Redirect

`http://allowed.example` bisa mengembalikan 302 ke `http://169.254.169.254/`. Kalau client mengikuti redirect tanpa validasi ulang, kontrolnya terlewati.

### 4.3 Ketidakcocokan parser

Library URL di bahasa A tidak selalu sepakat dengan parser di bahasa B; *The Tangled Web* justru menekankan inkonsistensi parser seperti ini. Satu sisi sistem melihat host yang "aman" sementara sisi lain connect ke host yang berbeda.

### 4.4 Sketsa kebijakan formal

$$
\begin{aligned}
&\mathsf{scheme}(u) \in \{\mathsf{https}\} \\
&\mathsf{ip}(\mathsf{resolve}(u)) \in \mathcal{A}_{\mathsf{public\_allow}} \\
&\mathsf{ip}(\cdot) \notin \mathcal{B}_{\mathsf{blocked}} \\
&\quad \mathcal{B} \supseteq \{\mathsf{loopback},\,\mathsf{link\text{-}local},\,\mathsf{RFC1918},\,\mathsf{CGNAT},\,\mathsf{metadata}\}
\end{aligned}
$$

Utamakan allowlist positif untuk destinasi (host partner yang dikenal) dibanding hanya mengandalkan blocklist raksasa.

## 5. Pola berbahaya vs aman

### 5.1 Berbahaya

```python
# UNSAFE — attacker controls URL; server fetches anything reachable
import requests
url = request.args["url"]
resp = requests.get(url, timeout=3)
return resp.text  # may leak internal responses
```

### 5.2 Sketsa yang lebih aman: allowlist scheme, blokir IP privat, tanpa redirect, batas ukuran

```python
# HARDENED SKETCH — still review for DNS rebinding in production
from urllib.parse import urlparse
import ipaddress, socket, requests

ALLOWED_PORTS = {443}
BLOCK_NETS = [
    ipaddress.ip_network("0.0.0.0/8"),
    ipaddress.ip_network("10.0.0.0/8"),
    ipaddress.ip_network("127.0.0.0/8"),
    ipaddress.ip_network("169.254.0.0/16"),
    ipaddress.ip_network("172.16.0.0/12"),
    ipaddress.ip_network("192.168.0.0/16"),
    ipaddress.ip_network("::1/128"),
    ipaddress.ip_network("fc00::/7"),
    ipaddress.ip_network("fe80::/10"),
]

def ip_blocked(ip: str) -> bool:
    addr = ipaddress.ip_address(ip)
    return any(addr in net for net in BLOCK_NETS)

def safe_fetch(user_url: str) -> bytes:
    u = urlparse(user_url)
    if u.scheme != "https" or not u.hostname:
        raise ValueError("scheme")
    port = u.port or 443
    if port not in ALLOWED_PORTS:
        raise ValueError("port")
    infos = socket.getaddrinfo(u.hostname, port, type=socket.SOCK_STREAM)
    ips = {info[4][0] for info in infos}
    if not ips or any(ip_blocked(ip) for ip in ips):
        raise ValueError("ip")
    # Production: connect via pinned IP + SNI/Host carefully; re-check redirects
    r = requests.get(user_url, timeout=3, allow_redirects=False, stream=True)
    return r.content[: 200_000]
```

Untuk banyak produk, jalan yang lebih aman adalah tidak menerima URL mentah sama sekali; terima `resource_id` internal yang dipetakan server ke URL tetap.

## 6. Hardening metadata cloud (konsep)

Instance metadata service (IMDS) membagikan kredensial sementara ke workload cloud. SSRF yang mencapai IMDS adalah salah satu pola berdampak paling tinggi dalam respons insiden cloud modern.

| Kontrol | Tujuan |
|:---|:---|
| IMDSv2 (berbasis session) | Mewajibkan hop method/header yang tidak bisa direproduksi dengan mudah oleh SSRF GET dasar |
| Hop limit / firewall | Mencegah container mencapai metadata secara tidak terduga |
| Role least-privilege | Membatasi blast radius kredensial yang dicuri |
| Tanpa proxy metadata mentah | Aplikasi tidak pernah fetch URL metadata yang bersumber dari input pengguna |

Catatan ini tidak menyediakan resep eksploit metadata, hanya sisi hardening-nya.

## 7. Tumpukan pertahanan berlapis

1. Utamakan indirection: kirim ID, bukan URL bebas.
2. Allowlist scheme, biasanya hanya `https`.
3. Allowlist destinasi untuk partner yang dikenal.
4. Blokir rentang privat, link-local, dan metadata setelah resolusi DNS; pin IP-nya.
5. Nonaktifkan redirect, atau validasi ulang di setiap hop.
6. Network egress policy: subnet aplikasi tidak boleh mencapai segmen sensitif.
7. Proxy outbound khusus dengan DLP atau penegakan allowlist.
8. Jangan pernah mengembalikan body response internal mentah ke klien.
9. Timeout, batas ukuran, dan allowlist content-type.
10. Otorisasi pada fitur itu sendiri, mengontrol siapa yang boleh memicu fetch.

WAHH menekankan pemetaan permukaan "dari mana aplikasi ini membuat koneksi keluar." Inventarisasi setiap HTTP client di seluruh codebase, termasuk PDF generator, wrapper ffmpeg, dan pengirim webhook, bukan cuma yang jelas terlihat.

Perbaikan SSRF yang hanya menyaring kecocokan string pada hostname, tanpa menangani redirect dan jendela TOCTOU DNS, tetap rapuh. Pencocokan string hostname saja tidak cukup; kontrol resolusi ulang DNS, redirect, dan scheme secara bersamaan.

## 8. Sinyal deteksi berizin

- Pencarian kode untuk pola seperti `requests.get(user`, `HttpClient`, `curl_exec`, `file_get_contents("http`.
- Monitoring egress: awasi pod aplikasi yang connect ke `169.254.169.254` atau rentang RFC1918 secara tidak terduga.
- Unit test yang menolak alamat loopback, menolak redirect ke IP privat, dan menolak scheme non-HTTPS.

```bash
# Lab only: verify YOUR egress firewall denies metadata IP from app netns
# (ops check — not an exploit)
curl -sS -o /dev/null -w "%{http_code}\n" --connect-timeout 2 https://example.com/
```

## 9. Checklist developer

| Cek | Lulus |
|:---|:---|
| URL dari pengguna benar-benar dibutuhkan? | Utamakan ID |
| Scheme | Hanya `https` |
| Redirect | Nonaktif, atau divalidasi ulang |
| Kebijakan IP | Memblokir rentang privat, link-local, dan metadata |
| DNS | TOCTOU dipertimbangkan; IP dipin |
| Response | Tidak direfleksikan mentah; dibatasi |
| Egress | Network policy deny-by-default |
| Cloud | IMDSv2 plus role minimal |

```
 Client URL ─► Policy gate ─► Egress proxy ─► Allowlisted targets only
                 │ reject
                 └── private / metadata / bad scheme
```

## Catatan keamanan: ancaman dan pertahanan

| Pola ancaman | Mekanisme | Pertahanan |
|:---|:---|:---|
| Menyentuh port internal | Server mencapai layanan VPC | Allowlist egress |
| Akses metadata | IMDS link-local terjangkau | IMDSv2; blokir; jangan pernah pakai URL dari pengguna |
| Bypass lewat redirect | 302 mengarah ke internal | `allow_redirects=False` plus validasi ulang |
| DNS rebinding | IP berubah setelah pemeriksaan | Pin IP; TTL pendek; validasi ulang |
| Scheme smuggling | Handler non-HTTP diterima | Allowlist scheme |
