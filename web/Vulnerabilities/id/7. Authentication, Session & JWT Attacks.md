## Istilah penting

Istilah-istilah ini akan sering muncul di materi.

| Istilah | Artinya |
|:---|:---|
| Autentikasi | Membuktikan siapa kamu (login) |
| Session | Ingatan server bahwa kamu sudah login, terikat ke sebuah session ID |
| Cookie | Tempat session ID atau token biasanya disimpan di browser |
| Token | Kredensial mandiri yang dikirim di tiap request |
| JWT | Token bertanda tangan yang membawa klaim (siapa kamu, kapan kedaluwarsa) |
| MFA | Autentikasi multi-faktor: bukti kedua selain password |

| Brute force | Menebak password dengan mencoba banyak; dilawan rate limit + lockout |

## 1. Tujuan autentikasi

Autentikasi menetapkan identitas subjek. Session management mempertahankan ikatan itu lintas request. Otorisasi memutuskan apa yang boleh mereka lakukan. WAHH memisahkan ketiganya karena alasan yang jelas: bug "login lemah" dan bug "session mudah difiksasi atau dibajak" adalah kelas kegagalan yang berbeda.

Properti keamanan klasik:

| Properti | Makna |
|:---|:---|
| Authenticity | Hanya pemilik kredensial yang bisa membuka session |
| Integrity | Token atau session tidak bisa diubah tanpa terdeteksi |
| Confidentiality | Secret tidak bocor lewat XSS, log, atau Referer |
| Binding | Session terikat ke konteksnya (pengguna, kebijakan device) |
| Revocation | Server bisa memutus akses sebelum expiry |

Password, WebAuthn, OIDC, dan API key adalah kelas kredensial. Session dan JWT adalah artifact yang membuktikan bahwa autentikasi sebelumnya terjadi; pilihan kriptografi dan penyimpanan keduanya jauh lebih mendominasi mode kegagalan modern dibanding form login itu sendiri.

## 2. Model session sisi server

```text
1. login OK     → server membuat sid acak (minimal 128 bit)
2. server simpan → sid: {user id, metadata, waktu kedaluwarsa}
3. tiap request → browser mengirim cookie sid, server mencarinya
```

Keunggulan model ini: revocation mudah (hapus entry `sid`), dan payload yang disimpan di klien minimal.

Kelas risiko di sini, secara konseptual bukan sebagai exploit kit: nilai `sid` yang bisa ditebak karena entropy rendah, fixation (penyerang menetapkan `sid` sebelum login), pencurian lewat XSS atau penangkapan jaringan, dan tidak adanya regenerasi saat privilege berubah.

Mitigasi inti: regenerate session ID saat login, gunakan entropy tinggi, simpan store di sisi server, terapkan timeout idle maupun absolut, dan wajibkan re-autentikasi sebelum langkah kritis.

## 3. Hardening cookie (*The Tangled Web* / RFC 6265)

| Atribut | Peran |
|:---|:---|
| `Secure` | HTTPS saja |
| `HttpOnly` | Tidak bisa dibaca dari JS |
| `SameSite` | Mengurangi CSRF |
| `Path` / `Domain` | Jaga cakupan tetap sempit |
| Prefix `__Host-` | Batasan tambahan pada host cookie |

Hindari menaruh session di `localStorage` kalau bisa dihindari; XSS langsung mencurinya. Kalau SPA menyimpan Bearer token di memori sebagai gantinya, pahami trade-off CSRF-vs-XSS yang tersirat dari pilihan itu.

## 4. Struktur JWT: matematika compact serialization JWS

Format JWT yang paling umum dipakai adalah JWS (RFC 7515) dalam bentuk compact:

```text
JWT = base64url(H) . base64url(P) . base64url(S)

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMifQ.<signature>
```

di mana:

- H adalah header JSON (algoritma, tipe, kadang `kid`)
- P adalah payload/claims JSON
- S adalah signature atau MAC tag atas signing input

Signing input:

```text
SI = base64url(H) . base64url(P)      (the signing input)
```

### 4.1 HMAC (alg `HS256`, dst.)

```text
S = HMAC-SHA256(k, SI)
```

dengan kunci bersama k. Verifikasi menghitung ulang S' dan membandingkannya dengan S secara constant-time.

### 4.2 Asimetrik (alg `RS256` / `ES256`, dst.)

```text
Verify(SI, S, pk) → true / false
```

Signature dibuat dengan private key dan diverifikasi dengan public key, yang berguna untuk microservice yang tidak berbagi secret HMAC.

### 4.3 Claims (payload)

Claims terdaftar dari RFC 7519 mencakup `iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`. Aplikasi menambahkan claims privat di atasnya. Jangan pernah menaruh secret sensitif di JWT yang bisa dibaca klien, karena header dan payload hanya di-encode, bukan dienkripsi. Untuk kerahasiaan claims, gunakan JWE, atau simpan datanya di sisi server saja.

Base64url bukan kerahasiaan:

```text
base64url_decode("eyJzdWIiOiIxMjMifQ")  →  {"sub":"123"}
```

Siapa pun bisa melakukan decoding ini. Tidak perlu kunci apa pun.

## 5. Checklist verifikasi yang benar

Implementasi yang aman harus:

1. Parse ketiga bagian; tolak format yang tidak sesuai.
2. Pilih kunci dari trust store berdasarkan `kid` yang diizinkan; jangan pernah mengambil JWKS dari URL yang diberikan pengguna.
3. Terapkan allowlist algoritma di sisi server, misalnya hanya `ES256` atau hanya `RS256`.
4. Verifikasi signature dengan API kripto yang teruji; tolak jika gagal.
5. Validasi claims: `exp`/`nbf` dengan clock skew kecil δ; kecocokan persis pada `iss` dan `aud`; `sub` dipetakan ke otorisasi.
6. Tolak token yang bagian signature-nya hilang atau kosong.
7. Gunakan perbandingan constant-time untuk HMAC.
8. Log kegagalan tanpa mencetak token secara penuh.

```python
# SAFE sketch — algorithm allowlist + verify + claims
# (library APIs differ; never roll your own crypto)
import jwt  # PyJWT-style illustration

PUBLIC_KEY = open("jwks_rsa_pub.pem").read()
ALLOWED = ["RS256"]

def accept_bearer(token: str) -> dict:
    return jwt.decode(
        token,
        PUBLIC_KEY,
        algorithms=ALLOWED,          # critical
        audience="api.myapp.example",
        issuer="https://idp.myapp.example/",
        options={"require": ["exp", "iat", "sub"]},
    )
```

## 6. Algorithm confusion (konsep saja)

Algorithm confusion, yang secara historis terkait dengan penanganan `alg=none` dan verifikasi HMAC-vs-RSA yang tertukar, terjadi ketika penerima mempercayai field `alg` dari token itu sendiri, lalu memilih jalur verifikasi yang salah berdasarkan itu.

Contoh konseptual:

- Token menyatakan `alg=HS256`, tapi verifier memakai public key RSA sebagai secret HMAC. Kalau library mengizinkannya, penyerang yang tahu public key bisa memalsukan MAC yang valid.
- Token menyatakan `alg=none` dengan signature kosong. Verifier lama yang "menerima none" akan menerima payload apa saja.

Server yang menetapkan algoritma mana yang diterima. Header hanya metadata yang harus cocok dengan kebijakan itu, bukan pihak yang menentukan kebijakannya.

Catatan ini sengaja tidak membahas konstruksi eksploit atau tooling cracking. Kalau Anda memelihara sebuah verifier, tambahkan regression test di mana nilai `alg` yang dipalsukan harus gagal secara tertutup.

## 7. Kegagalan desain umum (kelas)

| Kelas kegagalan | Deskripsi | Mitigasi |
|:---|:---|:---|
| Session ID lemah atau bisa ditebak | Entropy rendah | CSPRNG, minimal 128 bit |
| Session fixation | SID pra-login tetap dipakai setelah login | Rotasi saat login |
| JWT berumur panjang tanpa revoke | Token yang dicuri tetap berfungsi sampai `exp` | `exp` pendek plus rotasi refresh; deny-list `jti` bila perlu |
| Data sensitif di dalam JWT | Claims bisa dibaca siapa pun yang punya tokennya | Claims minimal; simpan data di server |
| Injeksi `kid` / injeksi header | Penyerang mengarahkan verifier ke kunci yang tidak tepercaya | Pin JWKS yang ketat; allowlist nilai `kid` |
| Cek `aud`/`iss` yang hilang | Token diterima lintas layanan yang tidak seharusnya | Pengecekan audience yang eksplisit |
| "Verifikasi" yang cuma decode | Decode Base64 tanpa pengecekan kripto | Selalu verifikasi signature |
| Penyalahgunaan refresh token | Pencurian berujung akses jangka panjang | Rotasi; binding; deteksi reuse |
| Penyimpanan password | Fungsi hash yang cepat | Argon2id, bcrypt, atau scrypt plus pepper |

Untuk login password: rate limiting, lockout atau backoff, MFA untuk akun berhak istimewa, dan perbandingan constant-time untuk hash password lewat API KDF yang teruji.

## 8. Pola berbahaya vs aman

```python
# UNSAFE — trusts alg from token; or decode without verify
jwt.decode(token, key, options={"verify_signature": False})  # never in prod
jwt.decode(token, key, algorithms=["HS256", "RS256", "none"])  # too broad
```

```python
# SAFE — narrow algorithms; verify aud/iss/exp
jwt.decode(token, key, algorithms=["ES256"], audience=AUD, issuer=ISS)
```

```python
# SAFE session sketch
sid = secrets.token_urlsafe(32)
redis.setex(f"sess:{sid}", TTL, user_id)
# On login success: destroy old sid, issue new
```

## 9. Tumpukan pertahanan berlapis

1. MFA yang tahan phishing untuk akun bernilai tinggi (WebAuthn).
2. HTTPS di mana-mana, dengan HSTS.
3. Cookie session: `Secure; HttpOnly; SameSite`.
4. JWT: access token berumur pendek, refresh token yang dirotasi, algoritma yang di-allowlist.
5. Revocation sisi server untuk respons pelanggaran (`jti` atau session store).
6. Step-up authentication untuk ganti password, payout, dan pembuatan API key.
7. Token CSRF kalau session berbasis cookie (lihat catatan CSRF).
8. Pertahanan XSS, karena pencurian session adalah akibat dari itu.
9. Auth terpusat (OIDC) yang dibangun di atas library teruji; jangan menciptakan protokol kripto sendiri.
10. Audit log untuk kegagalan autentikasi dan reuse refresh token.

### Opaque session vs JWT

| | Server session ID | JWT access token |
|:---|:---|:---|
| Revoke | Mudah | Butuh infrastruktur |
| Ukuran | Cookie kecil | Lebih besar |
| Kripto saat verifikasi | Lookup | Verifikasi signature |
| Use case | Aplikasi web klasik | API / pembaca terdistribusi |

Hybrid yang umum: session opaque untuk browser, JWT berumur pendek untuk panggilan service-to-service dengan mTLS.

## 10. Checklist developer

| Cek | Lulus |
|:---|:---|
| Entropy session ID | CSPRNG, minimal 128 bit |
| Rotasi SID saat login | Ya |
| Flag cookie | `Secure`, `HttpOnly`, `SameSite` semuanya disetel |
| Verifikasi JWT | Signature plus `iss`/`aud`/`exp` |
| Kebijakan algoritma | Allowlist server; tanpa `none` |
| Key | Private key di KMS atau HSM; dirotasi |
| Refresh | Rotasi plus deteksi reuse |
| Password | KDF modern; tidak pernah di-log plaintext |
| Test | Kasus algorithm-confusion gagal secara tertutup |

```
 AuthN success
     │
     ├─► create server session (opaque sid) ─► Set-Cookie hardened
     │
     └─► issue JWS access token
              SI = b64(H).b64(P)
              S  = Sign_k(SI) or MAC_k(SI)
              verify with allowlisted alg + claims
```

## Catatan keamanan: ancaman dan pertahanan

| Kelas ancaman | Mengapa | Pertahanan |
|:---|:---|:---|
| Cookie session yang dicuri | XSS atau malware | `HttpOnly`; CSP; TTL pendek |
| JWT yang dipalsukan | Verifikasi yang rusak, atau algorithm confusion | Allowlist plus verifikasi yang benar |
| Kebocoran bearer token berumur panjang | Log, Referer, XSS | `exp` pendek; hindari token di URL |
| Fixation | SID disetel sebelum autentikasi | Regenerate saat login |
| Credential stuffing | Password yang dipakai ulang | MFA; rate limiting; pengecekan breach |
