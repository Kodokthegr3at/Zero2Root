## 1. Definisi

CSRF (Cross-Site Request Forgery) adalah kelas serangan di mana browser korban yang sudah terautentikasi dikelabui untuk mengirim request yang mengubah state ke origin target, dan aplikasi menerima request itu sebagai niat korban karena kredensial ambient, biasanya cookie, ikut terkirim otomatis.

Berbeda dari XSS, CSRF umumnya tidak membutuhkan injeksi skrip ke origin target. Yang disalahgunakan adalah perilaku browser sendiri: mengirim cookie ke origin mana pun yang cocok dengan tujuan request.

CSRF memanfaatkan fakta bahwa browser menyertakan cookie, dan kadang kredensial ambient lain, ke request berdasarkan URL tujuan, bukan berdasarkan apakah request itu dipicu oleh gestur UI first-party yang bisa dipercaya server.

---

## 2. Prasyarat (konseptual)

Secara konseptual, CSRF berhasil kalau semua hal berikut benar.

1. Aksi yang relevan bisa dipicu oleh request HTTP yang dipalsukan (misalnya `POST /transfer`).
2. Session atau kredensial auth terkirim otomatis (cookie session, atau kadang HTTP Basic warisan lama).
3. Tidak ada secret khusus request yang harus dibaca dari halaman origin itu sendiri (token anti-CSRF, header custom yang sulit dipalsukan lintas situs, dan semacamnya).
4. Korban berada dalam konteks di mana browser akan menyertakan kredensial itu, artinya mereka sedang login.

Server mengautentikasi request hanya dari cookie yang dilampirkan browser, tanpa bukti bahwa user memang sengaja mengirimnya dari situs yang sama.

Method yang "aman" (`GET`) yang mengubah state melanggar spesifikasi HTTP dan memperbesar permukaan CSRF, karena sebuah link, tag `img`, atau prefetch bisa memicunya. Poin WAHH tegas: jangan pernah pakai GET untuk aksi berakibat. Method yang idempotent-safe seharusnya tidak mengubah apa pun. Kalau `GET` mengubah state, permukaan CSRF meluas ke setiap tempat di mana URL bisa diminta lintas situs.

## 3. Akar masalah: ambient authority

Server melihat sesuatu seperti ini.

```http
POST /api/password HTTP/1.1
Host: bank.example
Cookie: session=...
```

Server membuktikan siapa yang mengirim request (lewat session), tetapi tidak membuktikan apakah UI same-origin yang sah benar-benar memicu aksi itu. CSRF hidup di celah ini: autentikasi bukan hal yang sama dengan otorisasi niat.

*The Tangled Web* membahas bagaimana fitur browser (form lintas situs, redirect, plugin warisan) secara historis mengaburkan batas ini. Mitigasi modernnya adalah cookie SameSite, token CSRF, dan Fetch Metadata.

Perbaiki CSRF dengan mewajibkan bukti yang tidak bisa dipalsukan dan terikat ke session, yang membuktikan request datang dari halaman atau alur aplikasi sendiri, atau dengan memastikan cookie tidak terkirim pada request lintas situs untuk aksi sensitif.

## 4. Model token anti-CSRF

### 4.1 Synchronizer token (model klasik yang diutamakan)

1. Server menghasilkan token acak t ← {0,1}ⁿ (minimal 128 bit entropy disarankan).
2. Simpan t di session sisi server, atau di artifact sisi server yang diberi MAC.
3. Sematkan t di form, atau ekspos ke JS same-origin lewat response.
4. Pada request yang mengubah state, verifikasi t_req = t_session memakai perbandingan constant-time.

```text
terima hanya jika:   token di request == token di session   dan   session masih valid
```

### 4.2 Double-submit cookie (varian stateless)

Token ada di cookie dan di parameter/header; server memeriksa kecocokan keduanya. Ini harus dipasangkan dengan pemahaman yang jelas soal risiko subdomain dan cookie injection. Utamakan pola synchronizer atau proteksi CSRF bawaan framework bila memungkinkan.

### 4.3 Yang bukan fungsi token

- Bukan pengganti otorisasi; pengecekan IDOR tetap harus dilakukan.
- Bukan perlindungan terhadap XSS di origin yang sama, karena skrip yang berjalan di sana bisa langsung membaca token itu.
- Token harus unik per session, atau per form dengan rotasi yang benar.

## 5. Cookie SameSite (praktik RFC 6265bis)

| Nilai | Perilaku lintas situs (disederhanakan) | Catatan |
|:---|:---|:---|
| `Strict` | Cookie tidak dikirim pada request lintas situs | Kuat; bisa memengaruhi navigasi kembali |
| `Lax` | Dikirim pada navigasi GET top-level; ditahan pada kebanyakan POST lintas situs | Baseline default yang umum |
| `None` | Dikirim lintas situs; mewajibkan `Secure` | Dibutuhkan untuk beberapa embed; perlakukan dengan perhatian paling besar untuk CSRF |

`SameSite` mengurangi CSRF berbasis cookie, tapi bukan satu-satunya kontrol yang penting: browser lama, deployment `SameSite=None`, dan beberapa alur lintas situs tetap membutuhkan token atau desain lain.

Pertahanan berlapis berarti `SameSite=Lax` atau `Strict` ditambah token anti-CSRF pada endpoint yang mengubah state, terutama kalau mendukung klien lama atau deployment lintas situs.

## 6. Pola aplikasi berbahaya vs aman

### 6.1 Berbahaya: session cookie tanpa secret request

```http
POST /settings/email HTTP/1.1
Host: app.example
Cookie: session=abc
Content-Type: application/x-www-form-urlencoded

email=attacker@evil.example
```

Tanpa token yang memadai atau setelan SameSite, form lintas situs bisa memicu aksi yang sama.

### 6.2 Aman: synchronizer token di form

```html
<form method="POST" action="/settings/email">
  <input type="hidden" name="csrf" value="{{ csrf_token }}">
  <input type="email" name="email">
  <button type="submit">Update</button>
</form>
```

```python
# SAFE sketch — framework comparison
if not hmac.compare_digest(session["csrf"], request.form["csrf"]):
    abort(403)
# then perform state change + authZ checks
```

### 6.3 Aman: header custom untuk XHR/fetch same-origin

SPA sering mengirim header seperti `X-CSRF-Token`, atau mengandalkan salah satu pola berikut.

- Cookie session `HttpOnly` plus header token yang diambil dari meta tag, atau
- Nilai `Authorization: Bearer` yang disimpan di `localStorage` atau memori, bukan cookie. CSRF klasik jadi lemah di bawah model ini, tapi XSS menjadi jauh lebih kritis, jadi pilih model ancaman ini dengan sadar.

## 7. API JSON, CORS, dan Fetch Metadata

Request `Content-Type: application/json` dari form HTML lintas situs biasa tidak semudah `application/x-www-form-urlencoded`, karena form HTML polos tidak mudah mengirim JSON mentah. Tapi jangan jadikan "ini JSON, jadi aman" sebagai aturan.

- Plugin warisan dan bug browser di masa lalu pernah mengubah asumsi ini.
- Endpoint yang juga menerima input form-urlencoded tetap rentan, apa pun jalur JSON-nya.
- CORS yang salah konfigurasi, misalnya `Access-Control-Allow-Origin: *` dikombinasikan dengan `Allow-Credentials: true` (kombinasi yang tidak valid dan berbahaya kalau benar-benar dibiarkan terjadi), bisa memperburuk masalah cross-origin yang melibatkan kredensial.

Header Fetch Metadata (`Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest`) memungkinkan server menolak request lintas situs untuk resource sensitif, pola yang sering disebut Resource Isolation Policy.

Sikap API yang disarankan:

1. Method yang mengubah state mewajibkan token CSRF atau bukti auth non-cookie.
2. Tolak nilai `Sec-Fetch-Site` yang tidak diharapkan untuk mutasi yang terautentikasi via cookie, selama kompatibilitas mengizinkan.
3. CORS sebaiknya memakai allowlist origin yang eksplisit, dan jangan pernah merefleksikan header `Origin` sembarang bersamaan dengan kredensial.

## 8. Tumpukan pertahanan berlapis

| Lapisan | Kontrol |
|:---|:---|
| 1 | Tidak ada perubahan state lewat `GET` |
| 2 | Token anti-CSRF pada mutasi |
| 3 | `SameSite=Lax` atau `Strict` pada cookie session |
| 4 | Flag cookie `Secure` + `HttpOnly` |
| 5 | Re-autentikasi atau step-up untuk aksi berisiko tinggi (ganti password, payout) |
| 6 | Isolasi Fetch Metadata |
| 7 | Cek origin untuk workflow custom |
| 8 | Notifikasi pengguna atau konfirmasi transaksi |

Login CSRF dan logout CSRF juga muncul di literatur WAHH. Pertimbangkan token pada POST login itu sendiri kalau session fixation atau login confusion relevan dengan model ancaman Anda.

## 9. Checklist developer

| Cek | Kriteria lulus |
|:---|:---|
| Mutasi | Hanya POST/PUT/PATCH/DELETE |
| Token | Diverifikasi di server untuk mutasi cookie-auth |
| Cookie | `Secure; HttpOnly; SameSite` disetel dengan sengaja |
| CORS | Allowlist origin eksplisit; penggunaan kredensial adalah keputusan sadar |
| XSS | Diperlakukan sebagai risiko bypass CSRF, karena token jadi bisa dibaca |
| Test | Test otomatis memastikan token yang hilang atau tidak valid mengembalikan 403 |
| Aksi admin | Wajib step-up authentication |

```
                    block)           └─────────────────────┘
```

## Catatan keamanan: ancaman dan pertahanan

| Pola ancaman | Mengapa | Pertahanan |
|:---|:---|:---|
| CSRF form klasik | Cookie terkirim otomatis | Token + SameSite |
| Mutasi lewat GET | Mudah dipicu lintas situs | Jadikan GET read-only |
| Mitos "hanya JSON itu aman" | Content type lain, atau bug browser di masa lalu | Desain CSRF eksplisit |
| XSS di origin | Pencurian token, atau pemanggilan API langsung | Perbaiki XSS-nya; HttpOnly tetap melindungi cookie itu sendiri |
| CORS salah konfigurasi | Pembacaan atau pemanggilan cross-origin yang membawa kredensial | Allowlist ACAO yang ketat |
