## Istilah penting

Istilah-istilah ini akan sering muncul di materi.

| Istilah | Artinya |
|:---|:---|
| SQL | Bahasa yang dipakai aplikasi untuk mengakses database |
| SQL injection | Menipu aplikasi agar menjalankan SQL yang dikendalikan penyerang |
| Query | Perintah yang dikirim ke database |
| Prepared statement | Query yang datanya dikirim terpisah dari kode — perbaikan utama |
| Parameter binding | Mengisi placeholder dengan nilai yang diperlakukan DB sebagai data, bukan kode |
| Blind SQLi | Injeksi yang hasilnya disimpulkan dari perilaku, bukan output langsung |
| WAF | Web Application Firewall: filter di depan aplikasi (defense in depth) |

## 1. Model ancaman, mengapa SQLi penting

SQL injection terjadi ketika data yang tidak dipercaya memengaruhi struktur pernyataan SQL, bukan hanya nilai literal di dalamnya. WAHH (Ch.9) memperlakukan database sebagai sumber kebenaran aplikasi: kredensial, PII, status otorisasi, audit trail. Ketika penyerang mengendalikan sintaks SQL, dampak yang tipikal terlihat seperti ini.

| Kelas dampak | Contoh konsekuensi |
|:---|:---|
| Confidentiality | Pembacaan baris atau tabel di luar otorisasi |
| Integrity | UPDATE/DELETE di luar intent bisnis |
| Availability | Query mahal, lock, atau truncate (DoS di level logika) |
| Privilege | Penyalahgunaan fungsi DB berbahaya jika akun DB punya hak berlebih |
| Lateral movement | Pivot ke OS hanya jika fitur DB dan konfigurasi mengizinkan, bukan default yang aman |

SQLi adalah CWE-89, OWASP A03:2021 *Injection*.

Perlakukan setiap boundary yang mencapai mesin SQL (parameter HTTP, header, cookie, field JSON, nama file, payload message-queue) sebagai tidak tepercaya. Kerentanannya bukan soal "punya database"; ini soal mencampur kode dan data dalam satu string.

## 2. Akar masalah: konstruksi query

Misalkan query dibangun lewat konkatenasi:

```text
Q = T₀ + u₁ + T₁ + u₂ + ... + Tₙ

Contoh:
  "SELECT * FROM users WHERE name = '" + input + "'"
  input = ' OR '1'='1
  hasil: SELECT * FROM users WHERE name = '' OR '1'='1'      (sekarang cocok dengan semua baris)
```

di mana Tᵢ adalah fragmen SQL tetap (kode) dan uⱼ adalah input pengguna (data). Keamanan membutuhkan:

```text
parse(Q)  harus sama dengan  parse(T₀ + lit(u₁) + T₁ + ...)
```

dengan lit(·) yang tidak pernah mengubah AST hasil parsing. Konkatenasi mentah gagal memenuhi ini: karakter kutip, urutan komentar, atau operator bisa menutup literal dan membuka klausa baru.

Prepared statement dan parameter binding memisahkan proses jadi dua fase.

1. Prepare: parser menerima template dengan placeholder (`?`, `$1`, named parameter).
2. Execute: driver mengirim nilai terikat di luar teks SQL, lewat protokol biner dengan typed parameter.

Secara abstrak:

```text
stmt = Prepare(T)       T = "SELECT * FROM users WHERE name = ?"
Execute(stmt, v)        v = [input]
```

v tidak pernah digabung ke T sebagai teks yang di-parse ulang sebagai SQL.

Escaping bisa bekerja kalau sempurna untuk dialek dan charset yang tepat, tetapi dari pengalaman, ia sering gagal karena trik encoding, escaping yang tidak lengkap, atau API yang salah. Utamakan parameter dibanding escaping kutip buatan sendiri.

## 3. Klasifikasi injeksi, taksonomi konseptual (WAHH)

Kelas di bawah menjelaskan bagaimana efeknya diamati, bukan resep serangan.

| Kelas | Observability | Intuisi | Catatan pertahanan |
|:---|:---|:---|:---|
| In-band | Hasil atau error muncul di response HTTP yang sama | Input mengubah output yang terlihat | Parameter plus least privilege; sembunyikan error DB |
| Inferential (blind) | Hanya perbedaan perilaku (true/false, latensi) | Aplikasi "menjawab" lewat side channel | Perbaikan akar sama; normalkan juga perilaku error dan timing |
| Out-of-band | Side channel (DNS/HTTP dari host DB) jika fitur DB dan network egress mengizinkan | Jarang; butuh kemampuan DB spesifik dan egress | Blokir egress dari tier DB; nonaktifkan fitur DB berbahaya |
| Second-order | Payload disimpan dulu, lalu dieksekusi di query lain | Validasi setiap sink SQL secara independen | Parameterize semua sink, termasuk job admin dan reporting |

Poin WAHH: blind dan out-of-band bukan jenis SQL yang berbeda, melainkan strategi observasi yang dipakai ketika aplikasi tidak menampilkan data query secara langsung. Mitigasi utama tetap sama: jangan biarkan input menjadi sintaks. Jangan mengejar katalog payload per kelas; perbaiki model konstruksi query di setiap tempat query dibangun, termasuk batch job, export, search, dan jalur ORM yang jatuh kembali ke raw SQL.

## 4. Injeksi orde kedua dan realita multi-sink

Pola berbahaya klasik:

1. Input disimpan dengan aman ke kolom (INSERT berparameter).
2. Nanti, proses lain membaca nilai itu dan menggabungkannya ke SQL dinamis, misalnya laporan, cron job, atau fitur "advanced search".

"Input sudah di-sanitize saat insert" tidak cukup. Setiap sink SQL harus aman secara independen.

Threat-model setiap jalur kode yang memanggil `query()`, `execute()`, atau membangun SQL dari string template, termasuk tools admin yang jarang dipakai. Aman saat insert tapi berbahaya di laporan setelahnya tetap disebut second-order SQL injection. Pertahankan setiap sink SQL, bukan hanya sink pertama yang dilewati input.

## 5. Pola kode berbahaya vs aman

### 5.1 Anti-pattern: konkatenasi string (ilustratif)

```php
// UNSAFE — user data becomes SQL syntax
$sql = "SELECT id, role FROM users WHERE email = '" . $_GET['email'] . "'";
$rows = $db->query($sql);
```

```python
# UNSAFE
sql = f"SELECT * FROM products WHERE category = '{category}' AND q = '{q}'"
cursor.execute(sql)
```

### 5.2 Aman: parameter terikat

```php
// SAFE — structure fixed; values bound
$stmt = $pdo->prepare('SELECT id, role FROM users WHERE email = ?');
$stmt->execute([$email]);
```

```python
# SAFE (DB-API style)
cursor.execute(
    "SELECT * FROM products WHERE category = %s AND q = %s",
    (category, q),
)
```

```java
// SAFE
PreparedStatement ps = conn.prepareStatement(
    "SELECT id, role FROM users WHERE email = ?");
ps.setString(1, email);
```

### 5.3 Identifier dinamis (tabel, kolom, ORDER BY)

Parameter binding tidak mengikat nama identifier. Untuk `ORDER BY` atau nama kolom:

- Gunakan allowlist ketat, misalnya `{"name","price","created_at"}`, yang dipetakan ke literal SQL tetap.
- Tolak input di luar himpunan itu.

```text
if col not in {"name", "price", "created_at"}: reject
```

Jangan pernah membangun `"ORDER BY " + userInput`.

### 5.4 LIKE dan wildcard

Binding mencegah injeksi sintaks, tetapi `%` dan `_` tetap wildcard di dalam nilai `LIKE`. Escape karakter wildcard di lapisan aplikasi kalau pencarian literal dibutuhkan.

## 6. ORM, stored procedure, dan NoSQL

| Teknologi | Rasa aman yang keliru | Kebutuhan sebenarnya |
|:---|:---|:---|
| ORM | "Kita tidak menulis SQL" | Hindari pemanggilan raw atau string interpolation; tinjau `whereRaw`, `order`, dan API kriteria serupa |
| Stored procedure | "Logika ada di DB" | Procedure yang mengonkatenasi SQL secara internal tetap bisa diinjeksi |
| Query builder | Fluent API | Pastikan SQL final memakai placeholder, bukan string yang direkatkan |
| NoSQL (misalnya query object Mongo) | "Bukan SQL" | Injeksi operator (`$gt`, `$where`) ketika JSON menggabungkan objek tidak tepercaya ke filter |

Untuk NoSQL, jangan `JSON.parse` body request lalu langsung digabung ke filter query. Parse hanya field yang diizinkan, dan bangun objek filter di server.

Cara berpikir bab injeksi WAHH berlaku di luar SQL juga. Interpreter apa pun (LDAP, shell OS, XPath, template engine) gagal dengan cara yang sama ketika kode dan data tercampur dalam satu string.

## 7. Tumpukan pertahanan berlapis

### 7.1 Kontrol utama (wajib)

- Parameterized query, atau stored procedure tanpa konkatenasi SQL dinamis.
- Allowlist untuk identifier dan filter bertipe enum.

### 7.2 Kontrol sekunder

| Kontrol | Tujuan |
|:---|:---|
| Akun DB least-privilege | Role aplikasi punya DML terbatas; tanpa hak FILE, SUPER, atau gaya `xp_cmdshell` |
| Kredensial terpisah | Kredensial replica read-only untuk reporting bila memungkinkan |
| Segmentasi jaringan | Trafik app-ke-DB tetap privat; DB tanpa akses internet umum |
| Penanganan error | Error generik ke klien; error SQL detail hanya di log yang aman |
| Validasi input | Cek panjang, tipe, dan charset sebagai pertahanan berlapis, bukan pengganti parameter |
| WAF / RASP | Sinyal sementara dan virtual patch, bukan perbaikan akar |
| Secrets | Tanpa kredensial DB di kode frontend; rotasi berkala; simpan di vault atau KMS |

### 7.3 Output encoding bukan perbaikan SQLi

HTML encoding (pertahanan XSS) tidak memperbaiki SQLi. Kontrol harus sesuai dengan bahasa sink-nya.

Urutan prioritas: parameterize semua sink lebih dulu, lalu terapkan least privilege, lalu validasi dan allowlisting, lalu monitoring. Jangan bergantung pada blacklist kata kunci yang menyaring `OR` atau `UNION`; mudah dilewati dan merusak input sah. Utamakan keamanan struktural (bind parameter) dibanding filter leksikal.

## 8. Deteksi dan verifikasi berizin

Untuk lab sendiri atau pentest berizin, fokus pada indikator level kelas, bukan katalog payload.

- Bandingkan perilaku aplikasi saat input memutus literal (5xx generik versus 200), lalu perbaiki akar masalahnya, jangan sekadar menyembunyikan error.
- Code review: cari string SQL yang dibangun berdampingan dengan variabel; tambahkan rule SAST untuk konkatenasi.
- Unit dan integration test: pastikan driver memakai parameter terikat; pasang rule CI seperti Semgrep atau CodeQL `sql-injection`.
- Logging: rekam template query dan metadata parameter, jangan pernah field password.

```bash
# Lab only: inspect that YOUR app uses TLS to DB and least-priv account
# (example connectivity check — not an attack tool)
psql "host=127.0.0.1 dbname=app user=app_rw sslmode=verify-full" -c 'SELECT current_user;'
```

## 9. Checklist mitigasi developer

| Cek | Kriteria lulus |
|:---|:---|
| Semua sink SQL | Prepared atau bound parameter |
| ORDER BY / kolom | Hanya lewat allowlist map |
| Filter multi-tenant | `tenant_id` server-side dari session, tidak pernah dari klien saja |
| Error | Tidak ada stack trace atau teks SQL yang dikirim ke klien |
| Role DB | Grant minimal; tanpa fitur integrasi OS |
| Migrasi / skrip admin | Standar sama dengan jalur request produksi |
| Jalur second-order | Report, queue, dan search indexer juga diparameterisasi |
| Test | Minimal satu regression test per bug konkatenasi historis |

```
 Trust boundary          Safe interior
 ┌─────────────┐         ┌──────────────────────────┐
 │ HTTP / MQ   │  values │  Prepare(T) + Bind(v)    │──► SQL engine
 │ untrusted   │────────►│  Allowlist(identifiers)  │
 └─────────────┘         └──────────────────────────┘
        ✗ never:  sql = "SELECT ... " + user
```

## Catatan keamanan: ancaman dan pertahanan

| Pola ancaman | Mengapa berhasil | Pertahanan |
|:---|:---|:---|
| Bypass auth lewat WHERE yang diubah | Data menjadi logika boolean | Bind parameter; tegakkan otorisasi di server lewat session |
| Pembentukan hasil gaya UNION | Penyerang menyelaraskan kolom saat output direfleksikan | Parameter; minimalkan error dan data SQL yang direfleksikan |
| Inferensi blind | Aplikasi membocorkan side channel boolean atau timing | Parameter; halaman error yang nyaris constant-time; rate limit |
| Fitur DB yang berhak istimewa | Akun DB yang terlalu berkuasa | Cabut privilege berbahaya; kontrol egress |
| Raw SQL di ORM | Jalan pintas yang mengonkatenasi string | Larang atau tinjau API raw; jalankan SAST |
