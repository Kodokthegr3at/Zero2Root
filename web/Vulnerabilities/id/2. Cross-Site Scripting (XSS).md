## Istilah penting

Istilah-istilah ini akan sering muncul di materi.

| Istilah | Artinya |
|:---|:---|
| XSS | Membuat browser korban menjalankan JavaScript dari penyerang |
| Stored XSS | Payload disimpan di server dan disajikan ke banyak korban |
| Reflected XSS | Payload memantul balik dari satu request yang dirancang |
| DOM XSS | Payload dipicu sepenuhnya oleh JavaScript sisi klien |
| Output encoding | Menampilkan teks user sebagai teks, bukan kode — perbaikan utama |
| Same-origin policy | Aturan yang mengisolasi script satu situs dari situs lain |
| CSP | Header yang membatasi script mana yang boleh jalan (defense in depth) |

## 1. Model kepercayaan browser

Browser menjalankan JavaScript dengan hak akses origin dokumen (Same-Origin Policy). Kalau penyerang menyuntikkan skrip ke origin aplikasi sendiri, skrip itu berjalan sebagai bagian dari aplikasi: bisa memanggil API same-origin, membaca DOM, dan pada kebanyakan kasus bertindak atas nama sesi pengguna yang sedang login. Ini disebut session riding lewat skrip, berbeda dari CSRF klasik.

XSS adalah kegagalan menjaga batas itu: data yang tidak dipercaya diperlakukan sebagai kode aktif.

*The Tangled Web* karya Zalewski membingkai XSS sebagai masalah confused deputy di dalam browser: browser korban "dideputasi" untuk menjalankan skrip milik penyerang dengan hak akses situs itu sendiri. Memperbaiki XSS soal menyusun string tidak tepercaya secara aman ke dalam dokumen dan skrip, bukan soal memfilter kata-kata jahat.

## 2. Klasifikasi XSS, konseptual

| Kelas | Di mana skrip disisipkan | Persistensi | Sink tipikal |
|:---|:---|:---|:---|
| Reflected | Request ke response langsung | Tidak | Echo pencarian, pesan error |
| Stored | Disimpan lalu disajikan ke korban | Ya | Komentar, profil, tiket |
| DOM-based | JS di sisi klien menulis data tidak tepercaya ke sink berbahaya | Bervariasi | `innerHTML`, `document.write`, URL ke HTML |

WAHH memisahkan reflected dari stored berdasarkan apakah aplikasi menyimpan data berbahaya itu secara persisten. DOM XSS tetap terjadi meski sisi server benar, kalau JavaScript di sisi klien menggabungkan `location`, `postMessage`, atau fragment URL ke sink berbahaya.

Ketiganya berbagi satu akar: sink injeksi JavaScript atau HTML mengonsumsi data yang dipengaruhi penyerang tanpa encoding yang sesuai konteks atau API yang aman.

## 3. Konteks output, encoding bergantung konteks

Misalkan string tidak tepercaya u disisipkan ke dokumen. Encoding yang benar bergantung pada konteks gramatikalnya.

| Konteks | Berbahaya kalau mentah | Pendekatan aman (prinsip) |
|:---|:---|:---|
| Teks body HTML | Markup atau tag diinterpretasi | HTML entity encode |
| Atribut HTML (dikutip) | Keluar dari tanda kutip | Attribute encode, dan selalu beri kutip pada atribut |
| Literal string JavaScript | Keluar dari string JS | JS string encode, atau hindari inline script |
| Query/path URL | `javascript:` atau scheme jahat lainnya | URL encode plus allowlist scheme |
| CSS | Expression atau escape gaya lama | Hindari CSS tidak tepercaya; allowlist ketat |
| JSON di dalam `<script>` | Breakout `</script>` | Pola serialisasi JSON yang aman |

Secara formal, encoding E_c untuk konteks c harus menjamin:

```text
template:   <p>Hello, {{name}}</p>
name    =   <script>alert(1)</script>
encoded →   &lt;script&gt;alert(1)&lt;/script&gt;     (tampil sebagai teks, tidak dijalankan)
```

artinya u tetap data, tidak pernah menjadi non-terminal baru dalam grammar c.

Satu fungsi "escape HTML" saja tidak cukup untuk semua konteks. Menyisipkan ke event handler (`onclick=...`) atau ke URL adalah konteks yang berbeda, masing-masing punya aturan encoding sendiri.

Pilihan paling aman adalah tidak menaruh data tidak tepercaya di konteks script atau style sama sekali. Sampaikan data lewat atribut `data-*` yang dibaca sebagai `textContent`, atau `JSON.parse` sebuah blob JSON yang di-escape dengan benar dan dirancang untuk keperluan itu.

## 4. Pola akar masalah

1. Konkatenasi HTML di sisi server dari field request atau database ke template tanpa auto-escaping.
2. Escaping dinonaktifkan di template engine (`| safe`, `raw`, `{{{ }}}`).
3. Sink DOM yang mem-parsing HTML: `innerHTML`, `outerHTML`, `insertAdjacentHTML`.
4. API bergaya jQuery yang menginterpretasi string sebagai HTML, misalnya `$(userString)`.
5. Data `postMessage` yang salah ditangani, atau `outerHTML` dari widget rich content.
6. Kebingungan Content-Type, di mana konten pengguna disajikan sebagai `text/html` alih-alih attachment atau tipe yang aman.

## 5. Pola berbahaya vs aman

### 5.1 Body HTML

```html
<!-- UNSAFE (template sketch) -->
<p>Hello {{ user.name }}</p>
<!-- dangerous if engine does not auto-escape, or name contains markup -->
```

```javascript
// UNSAFE
el.innerHTML = "Hello " + userName;

// SAFE — text node, not HTML parser
el.textContent = "Hello " + userName;
```

### 5.2 Atribut

```html
<!-- UNSAFE -->
<img src="{{ url }}">
<!-- prefer scheme allowlist https: only; never untrusted javascript: -->

<!-- SAFER pattern: fixed attribute structure + encoded value + validation -->
<a href="https://example.com/u?id={{ id | urlencode }}">profile</a>
```

### 5.3 Hindari konkatenasi inline script

```html
<!-- UNSAFE pattern -->
<script>var u = "{{ user_input }}";</script>
```

```html
<!-- SAFER: data island consumed as text, then JSON.parse -->
<div id="cfg" data-user=""></div>
<script>
  const raw = document.getElementById('cfg').dataset.user;
  // populate dataset from server with HTML-attribute encoding;
  // or serve application/json on a separate endpoint
</script>
```

### 5.4 Default framework

Framework modern (text children `{}` di React, escaping default Angular, interpolasi teks Vue) memangkas sebagian besar risiko XSS secara otomatis, selama developer menghindari `dangerouslySetInnerHTML`, `[innerHTML]`, atau `v-html` tanpa sanitizer.

## 6. CSP, flag cookie, dan Trusted Types

### 6.1 Content-Security-Policy (pertahanan berlapis)

CSP membatasi origin skrip mana yang boleh berjalan. Kebijakan yang ketat terlihat seperti ini.

- `default-src 'self'`
- `script-src` dengan nonce atau hash (hindari `'unsafe-inline'` dan `'unsafe-eval'` bila memungkinkan)
- `object-src 'none'`; `base-uri 'none'`; `frame-ancestors` disetel sesuai kebutuhan aplikasi

CSP bukan pengganti encoding. Ia adalah jaring pengaman untuk saat encoding mengalami regresi.

### 6.2 Hardening cookie (mengurangi dampak sesi)

| Atribut | Efek |
|:---|:---|
| `HttpOnly` | Memblokir akses `document.cookie` ke cookie itu |
| `Secure` | Hanya dikirim lewat TLS |
| `SameSite=Lax/Strict` | Mengurangi pengiriman cookie lintas situs (terkait CSRF) |
| Prefix `__Host-` | Menegakkan batasan path/domain pada cookie |

`HttpOnly` mengurangi pencurian cookie lewat XSS, tetapi payload XSS tetap bisa memanggil API aplikasi atas nama korban.

### 6.3 Trusted Types (bila didukung)

Trusted Types adalah kebijakan browser yang memblokir assignment berbahaya (`innerHTML` dan sejenisnya) kecuali nilainya adalah objek tepercaya yang dibuat oleh policy factory, sehingga memaksa developer meninjau setiap sink.

*The Tangled Web* menekankan betapa rumitnya parser HTML dan JS sebenarnya. Semakin sedikit tempat string mentah mengalir ke HTML, semakin kecil permukaan serangan XSS.

Sanitasi HTML hanya kalau rich text memang kebutuhan produk, dan gunakan sanitizer yang terawat baik dengan allowlist tag dan atribut. Jangan pernah mengandalkan regex yang mencoba membuang tag `<script>`.

## 7. DOM XSS: source dan sink (peta defensif)

| Source tidak tepercaya (contoh) | Sink berbahaya (contoh) |
|:---|:---|
| `location`, `location.hash`, `location.search` | `innerHTML`, `outerHTML`, `document.write` |
| `document.referrer` | `eval`, `new Function`, `setTimeout(string)` |
| `data` event `postMessage` | `element.src` / `href` dengan URL tidak divalidasi |
| Nilai web storage yang disalin ke HTML | API interpretasi HTML gaya jQuery |

Perlakukan semua source di atas sebagai tidak tepercaya. Gunakan sink yang aman (`textContent`, `setAttribute` dengan nilai tervalidasi), dan validasi baik `origin` maupun skema dari setiap `postMessage`.

## 8. Tumpukan pertahanan berlapis

1. Output encoding yang sadar konteks, dengan auto-escape framework aktif secara default.
2. Hindari sink berbahaya; larang `v-html` atau `dangerouslySetInnerHTML` tanpa review.
3. Allowlist sanitizer HTML, dipakai hanya untuk rich content.
4. Nonce atau hash CSP; hilangkan `unsafe-inline` secara bertahap.
5. Flag cookie, masa sesi yang pendek, dan re-autentikasi untuk aksi sensitif.
6. Header keamanan, dibahas di seri HTTP (`X-Content-Type-Options` dan header terkait).
7. Code review dan rule SAST untuk sink HTML mentah.
8. Pelaporan penyalahgunaan, atau `report-to` CSP di produksi, ditangani hati-hati terkait PII.

## 9. Checklist developer

| Item | Lulus? |
|:---|:---|
| Template auto-escape secara default | ☐ |
| Tidak ada data tidak tepercaya di JS/CSS inline | ☐ |
| Kode DOM memakai `textContent` / pembangun URL aman | ☐ |
| Rich HTML hanya lewat allowlist sanitizer | ☐ |
| CSP tanpa `unsafe-inline` yang tidak perlu | ☐ |
| Cookie session memakai `HttpOnly; Secure; SameSite` | ☐ |
| Unduhan file memakai `Content-Type` + `Content-Disposition` yang aman | ☐ |
| Origin dan skema `postMessage` divalidasi | ☐ |

```
        ▼
  Choose context c ──► apply E_c(u) ──► insert into template

```

## Catatan keamanan: ancaman dan pertahanan

| Pola ancaman | Mekanisme | Pertahanan |
|:---|:---|:---|
| Reflected XSS | Request digemakan ke HTML | Encode; CSP; jangan pernah merefleksikan input mentah |
| Stored XSS | Konten persisten disajikan ke pengguna lain | Encode saat output; sanitasi rich text |
| DOM XSS | Sink di sisi klien mem-parsing data penyerang | API DOM yang aman; CSP |
| Mutation / mXSS | Ketidakcocokan antara sanitizer dan parser browser | Sanitizer yang teruji; sederhanakan HTML |
| JS lawas di PDF/Flash | Permukaan plugin | Nonaktifkan plugin; pakai browser modern |
