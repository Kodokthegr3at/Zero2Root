## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| XSS | Getting a victim's browser to run attacker-supplied JavaScript |
| Stored XSS | The payload is saved on the server and served to many victims |
| Reflected XSS | The payload bounces back from a single crafted request |
| DOM XSS | The payload is triggered entirely by client-side JavaScript |
| Output encoding | Rendering user text as text, not code — the main fix |
| Same-origin policy | The rule isolating one site's scripts from another's |
| CSP | A header that limits which scripts may run (defense in depth) |

## 1. Browser trust model

A browser runs JavaScript with the privileges of the document's origin (the Same-Origin Policy). When an attacker injects a script into the application's own origin, that script runs as part of the application: it can call same-origin APIs, read the DOM, and in most cases act on behalf of the logged-in user's session. This is session riding through script, distinct from classical CSRF.

XSS is a failure to hold that boundary: untrusted data gets treated as active code.

Zalewski's *The Tangled Web* frames XSS as a confused deputy problem inside the browser: the victim's browser is deputized to run attacker-controlled script with the site's own privileges. Fixing XSS is about safe composition of untrusted strings into documents and scripts, not about filtering bad words.

## 2. XSS classes, conceptual

| Class | Where script is introduced | Persistence | Typical sink |
|:---|:---|:---|:---|
| Reflected | Request to immediate response | No | Search echo, error messages |
| Stored | Saved then served to victims | Yes | Comments, profiles, tickets |
| DOM-based | Client-side JS writes untrusted data into a dangerous sink | Varies | `innerHTML`, `document.write`, URL to HTML |

WAHH separates reflected from stored based on whether the application persists the dangerous data. DOM XSS happens even when the server side is correct, if client-side JavaScript merges `location`, `postMessage`, or a URL fragment into a dangerous sink.

All three share one root: a JavaScript or HTML injection sink consumes attacker-influenced data without context-appropriate encoding or a safe API.

## 3. Output contexts, encoding is context-dependent

Suppose an untrusted string u is inserted into a document. Correct encoding depends on the grammatical context.

| Context | Dangerous if raw | Safe approach (principle) |
|:---|:---|:---|
| HTML body text | Markup or tags get interpreted | HTML entity encode |
| HTML attribute (quoted) | Breaks out of the quotes | Attribute encode, and always quote attributes |
| JavaScript string literal | Breaks out of the JS string | JS string encode, or avoid inline scripts |
| URL query / path | `javascript:` or another rogue scheme | URL encode plus a scheme allowlist |
| CSS | Expressions or legacy escapes | Avoid untrusted CSS; strict allowlist |
| JSON inside `<script>` | `</script>` breakout | Safe JSON serialization patterns |

Formally, the encoding E_c for context c has to guarantee:

```text
template:   <p>Hello, {{name}}</p>
name    =   <script>alert(1)</script>
encoded →   &lt;script&gt;alert(1)&lt;/script&gt;     (shown as text, not run)
```

meaning u stays data, never a new non-terminal in grammar c.

A single "escape HTML" function is not enough for every context. Inserting into an event handler (`onclick=...`) or into a URL is a different context, each with its own encoding rules.

The safest option is not putting untrusted data in script or style contexts at all. Pass data through `data-*` attributes read as `textContent`, or `JSON.parse` a correctly escaped JSON blob designed for that purpose.

## 4. Root cause patterns

1. Server-side HTML concatenation of request or database fields into templates without auto-escaping.
2. Escaping disabled in a template engine (`| safe`, `raw`, `{{{ }}}`).
3. DOM sinks that parse HTML: `innerHTML`, `outerHTML`, `insertAdjacentHTML`.
4. jQuery-like APIs that interpret a string as HTML, such as `$(userString)`.
5. Mishandled `postMessage` data, or `outerHTML` of a rich widget.
6. Content-Type confusion, where user content is served as `text/html` instead of an attachment or a safe type.

## 5. Unsafe vs safe patterns

### 5.1 HTML body

```html
<!-- UNSAFE (template sketch) -->
<p>Hello {{ user.name }}</p>
<!-- dangerous if engine does not auto-escape, or name contains markup -->
```

```javascript
// UNSAFE
el.innerHTML = "Hello " + userName;

// SAFE — text node, not HTML parser
el.textContent = "Hello " + userName;
```

### 5.2 Attributes

```html
<!-- UNSAFE -->
<img src="{{ url }}">
<!-- prefer scheme allowlist https: only; never untrusted javascript: -->

<!-- SAFER pattern: fixed attribute structure + encoded value + validation -->
<a href="https://example.com/u?id={{ id | urlencode }}">profile</a>
```

### 5.3 Avoid inline script concatenation

```html
<!-- UNSAFE pattern -->
<script>var u = "{{ user_input }}";</script>
```

```html
<!-- SAFER: data island consumed as text, then JSON.parse -->
<div id="cfg" data-user=""></div>
<script>
  const raw = document.getElementById('cfg').dataset.user;
  // populate dataset from server with HTML-attribute encoding;
  // or serve application/json on a separate endpoint
</script>
```

### 5.4 Framework defaults

Modern frameworks (React's `{}` text children, Angular's default escaping, Vue's text interpolation) cut most XSS risk automatically, as long as developers avoid `dangerouslySetInnerHTML`, `[innerHTML]`, or `v-html` without a sanitizer.

## 6. CSP, cookie flags and Trusted Types

### 6.1 Content-Security-Policy (defense in depth)

CSP restricts which script origins are allowed to run. A strict policy looks like this.

- `default-src 'self'`
- `script-src` with a nonce or a hash (avoid `'unsafe-inline'` and `'unsafe-eval'` where possible)
- `object-src 'none'`; `base-uri 'none'`; `frame-ancestors` set to what the app actually needs

CSP is not a substitute for encoding. It is a safety net for when encoding regresses.

### 6.2 Cookie hardening (reduces session impact)

| Attribute | Effect |
|:---|:---|
| `HttpOnly` | Blocks `document.cookie` access to that cookie |
| `Secure` | Sent only over TLS |
| `SameSite=Lax/Strict` | Reduces cross-site cookie sends (CSRF-related) |
| `__Host-` prefix | Enforces path/domain constraints on the cookie |

`HttpOnly` reduces cookie theft through XSS, but an XSS payload can still call the application's APIs as the victim.

### 6.3 Trusted Types (where supported)

Trusted Types is a browser policy that blocks dangerous assignments (`innerHTML` and similar) unless the value is a trusted object minted by a policy factory, which forces developers to review every sink.

*The Tangled Web* stresses how complex HTML and JS parsers really are. The fewer places a raw string flows into HTML, the smaller the XSS surface.

Sanitize HTML only when rich text is an actual product requirement, and use a well-maintained sanitizer configured with an allowlist of tags and attributes. Never rely on a regex that tries to strip `<script>` tags.

## 7. DOM XSS: sources and sinks (defensive map)

| Untrusted sources (examples) | Dangerous sinks (examples) |
|:---|:---|
| `location`, `location.hash`, `location.search` | `innerHTML`, `outerHTML`, `document.write` |
| `document.referrer` | `eval`, `new Function`, `setTimeout(string)` |
| `postMessage` event `data` | `element.src` / `href` with an unvalidated URL |
| Web storage values copied into HTML | jQuery HTML-interpreting APIs |

Treat every source above as untrusted. Use safe sinks (`textContent`, `setAttribute` with validated values), and validate both the `origin` and the schema of every `postMessage`.

---

## 8. Defense-in-depth stack

1. Context-aware output encoding, with framework auto-escape on by default.
2. Avoid dangerous sinks; ban `v-html` or `dangerouslySetInnerHTML` without review.
3. An HTML sanitizer allowlist, used only for rich content.
4. CSP nonces or hashes; strip `unsafe-inline` over time.
5. Cookie flags, a short session lifetime, and re-authentication for sensitive actions.
6. Security headers, covered in the HTTP series (`X-Content-Type-Options` and related headers).
7. Code review and SAST rules for raw HTML sinks.
8. Abuse reporting, or CSP `report-to` in production, handled carefully around PII.

## 9. Developer checklist

| Item | Pass? |
|:---|:---|
| Templates auto-escape by default | ☐ |
| No untrusted data in inline JS/CSS | ☐ |
| DOM code uses `textContent` / safe URL builders | ☐ |
| Rich HTML goes through a sanitizer allowlist only | ☐ |
| CSP without unnecessary `unsafe-inline` | ☐ |
| Session cookies use `HttpOnly; Secure; SameSite` | ☐ |
| File downloads use a safe `Content-Type` + `Content-Disposition` | ☐ |
| `postMessage` origin and schema are validated | ☐ |

```
 Untrusted string u
        │
        ▼
  Choose context c ──► apply E_c(u) ──► insert into template
        │
        └── if need HTML subset ──► Sanitizer_allowlist(u) only
```

## Security notes: threats and defenses

| Threat pattern | Mechanism | Defense |
|:---|:---|:---|
| Reflected XSS | Request echoed into HTML | Encode; CSP; never reflect raw input |
| Stored XSS | Persisted content served to other users | Encode on output; sanitize rich text |
| DOM XSS | A client-side sink parses attacker data | Safe DOM APIs; CSP |
| Mutation / mXSS | Mismatch between a sanitizer and the browser's parser | A battle-tested sanitizer; simplify the HTML |
| Legacy JS in PDF/Flash | Plugin surfaces | Disable plugins; use modern browsers |
