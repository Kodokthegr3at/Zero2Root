## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| SQL | The language apps use to query a database |
| SQL injection | Tricking an app into running attacker-controlled SQL |
| Query | A command sent to the database |
| Prepared statement | A query where data is sent separately from code — the main fix |
| Parameter binding | Filling placeholders with values the DB treats as data, never code |
| Blind SQLi | Injection where you infer results from behavior, not direct output |
| WAF | Web Application Firewall: a filter in front of the app (defense in depth) |

## 1. Threat model, why SQLi matters

SQL injection happens when untrusted data affects the structure of a SQL statement, not just a literal value inside it. WAHH (Ch.9) treats the database as the application's source of truth: credentials, PII, authorization state, audit trails. When an attacker controls SQL syntax, the typical impact looks like this.

| Impact class | Example consequence |
|:---|:---|
| Confidentiality | Reading rows or tables outside authorization |
| Integrity | UPDATE/DELETE outside business intent |
| Availability | Expensive queries, locks, or truncation (logic-level DoS) |
| Privilege | Abuse of dangerous DB functions if the DB account has excess rights |
| Lateral movement | Pivoting to the OS only when DB features and configuration allow it, never the safe default |

SQLi is CWE-89, OWASP A03:2021 *Injection*.

Treat every boundary that reaches a SQL engine (HTTP parameters, headers, cookies, JSON fields, file names, message-queue payloads) as untrusted. The vulnerability is not having a database; it is mixing code and data in one string.

## 2. Root cause: query construction

Consider a query built by concatenation:

```text
Q = T₀ + u₁ + T₁ + u₂ + ... + Tₙ

Example:
  "SELECT * FROM users WHERE name = '" + input + "'"
  input = ' OR '1'='1
  result: SELECT * FROM users WHERE name = '' OR '1'='1'     (now matches every row)
```

where Tᵢ is a fixed SQL fragment (code) and uⱼ is user input (data). Security requires:

```text
parse(Q)  must equal  parse(T₀ + lit(u₁) + T₁ + ...)
```

with lit(·) that never changes the resulting AST. Raw concatenation fails this: quote characters, comment sequences, or operators can close a literal and open a new clause.

Prepared statements and parameter binding split the process into two phases.

1. Prepare: the parser receives a template with placeholders (`?`, `$1`, named parameters).
2. Execute: the driver sends bound values outside the SQL text, over a binary protocol with typed parameters.

Abstractly:

```text
stmt = Prepare(T)       T = "SELECT * FROM users WHERE name = ?"
Execute(stmt, v)        v = [input]
```

v is never merged into T as text that gets re-parsed as SQL.

Escaping can work when it is perfect for the exact dialect and character set, but history shows it fails under encoding tricks, partial escaping, or the wrong API. Prefer parameters over hand-rolled quote escaping.

## 3. Injection classes, conceptual taxonomy (WAHH)

The classes below describe how the effect is observed, not attack recipes.

| Class | Observability | Intuition | Defense note |
|:---|:---|:---|:---|
| In-band | Results or errors appear in the same HTTP response | Input changes visible output | Parameters plus least privilege; hide DB errors |
| Inferential (blind) | Only a behavioral difference (true/false, latency) | The application answers through a side channel | Same root fix; also normalize error and timing behavior |
| Out-of-band | A side channel (DNS/HTTP from the DB host) when DB features and network egress allow it | Rare; requires specific DB capability and egress | Block egress from the DB tier; disable dangerous DB features |
| Second-order | Payload is stored first, then executed in a different query | Validate every SQL sink independently | Parameterize all sinks, including admin and reporting jobs |

WAHH's point is that blind and out-of-band are not different kinds of SQL, they are observation strategies used when the application does not display query data directly. The primary mitigation stays the same: never let input become syntax. Do not chase class-specific payload catalogs; fix the construction model everywhere a query is built, including batch jobs, exports, search, and ORM code paths that fall back to raw SQL.

## 4. Second-order and multi-sink reality

The classic dangerous pattern:

1. Input is stored safely in a column (a parameterized INSERT).
2. Later, a different process reads that value and concatenates it into dynamic SQL, for example a report, a cron job, or an "advanced search" feature.

"The input was sanitized at insert time" is not sufficient. Every SQL sink has to be safe independently.

Threat-model every code path that calls `query()`, `execute()`, or builds SQL from string templates, including low-frequency admin tools. Being safe at insert time and dangerous in a later report is still a second-order SQL injection. Defend every SQL sink, not only the first one an input passes through.

## 5. Unsafe vs safe code patterns

### 5.1 Anti-pattern: string concatenation (illustrative)

```php
// UNSAFE — user data becomes SQL syntax
$sql = "SELECT id, role FROM users WHERE email = '" . $_GET['email'] . "'";
$rows = $db->query($sql);
```

```python
# UNSAFE
sql = f"SELECT * FROM products WHERE category = '{category}' AND q = '{q}'"
cursor.execute(sql)
```

### 5.2 Safe: bound parameters

```php
// SAFE — structure fixed; values bound
$stmt = $pdo->prepare('SELECT id, role FROM users WHERE email = ?');
$stmt->execute([$email]);
```

```python
# SAFE (DB-API style)
cursor.execute(
    "SELECT * FROM products WHERE category = %s AND q = %s",
    (category, q),
)
```

```java
// SAFE
PreparedStatement ps = conn.prepareStatement(
    "SELECT id, role FROM users WHERE email = ?");
ps.setString(1, email);
```

### 5.3 Dynamic identifiers (table, column, ORDER BY)

Parameter binding does not bind identifier names. For `ORDER BY` or column names:

- Use a strict allowlist, for example `{"name","price","created_at"}`, mapped to a fixed SQL literal.
- Reject any input outside that set.

```text
if col not in {"name", "price", "created_at"}: reject
```

Never build `"ORDER BY " + userInput`.

### 5.4 LIKE and wildcards

Binding prevents syntax injection, but `%` and `_` remain wildcards inside a `LIKE` value. Escape the wildcard characters at the application layer when a literal match is required.

## 6. ORM, stored procedures and NoSQL

| Technology | False sense of safety | Real requirement |
|:---|:---|:---|
| ORM | "We don't write SQL" | Avoid raw or string-interpolated calls; review `whereRaw`, `order`, and similar criteria APIs |
| Stored procedures | "Logic lives in the DB" | A procedure that concatenates SQL internally is still injectable |
| Query builders | Fluent API | Confirm the final SQL uses placeholders, not glued strings |
| NoSQL (for example Mongo query objects) | "Not SQL" | Operator injection (`$gt`, `$where`) when JSON merges untrusted objects into the filter |

For NoSQL, do not `JSON.parse` a request body and merge it straight into a filter query. Parse only the fields you allow, and build the filter object on the server.

WAHH's injection-chapter mindset applies beyond SQL. Any interpreter (LDAP, an OS shell, XPath, template engines) fails the same way when code and data mix in one string.

## 7. Defense-in-depth stack

### 7.1 Primary control (mandatory)

- Parameterized queries, or stored procedures without dynamic SQL concatenation.
- Allowlists for identifiers and enum-like filters.

### 7.2 Secondary controls

| Control | Purpose |
|:---|:---|
| Least-privilege DB account | App role has limited DML; no FILE, SUPER, or `xp_cmdshell`-style rights |
| Separate credentials | Read-only replica credentials for reporting where possible |
| Network segmentation | App-to-DB traffic stays private; the DB has no general internet egress |
| Error handling | Generic client-facing errors; detailed SQL errors only in secure logs |
| Input validation | Length, type, and character-set checks as defense in depth, not a substitute for parameters |
| WAF / RASP | A temporary signal and virtual patch, not the root fix |
| Secrets | No DB credentials in frontend code; rotate them; store them in a vault or KMS |

### 7.3 Output encoding is not an SQLi fix

HTML encoding (an XSS defense) does not fix SQLi. Controls have to match the sink language.

Priority order: parameterize every sink first, then apply least privilege, then validation and allowlisting, then monitoring. Do not rely on a keyword blacklist that filters `OR` or `UNION`; it is easy to bypass and it breaks legitimate input. Prefer structural safety (bind parameters) over lexical filters.

## 8. Authorized detection and verification signals

For your own lab or an authorized pentest, focus on class-level indicators, not a payload catalog.

- Diff application behavior when input breaks out of a literal (a generic 5xx versus a 200), then fix the root cause instead of just hiding the error.
- Code review: search for SQL strings built next to variables; add SAST rules for concatenation.
- Unit and integration tests: confirm the driver uses bound parameters; wire CI rules such as Semgrep or CodeQL `sql-injection` checks.
- Logging: capture query templates and parameter metadata, never password fields.

```bash
# Lab only: inspect that YOUR app uses TLS to DB and least-priv account
# (example connectivity check — not an attack tool)
psql "host=127.0.0.1 dbname=app user=app_rw sslmode=verify-full" -c 'SELECT current_user;'
```

## 9. Developer mitigation checklist

| Check | Pass criteria |
|:---|:---|
| All SQL sinks | Prepared or bound parameters |
| ORDER BY / columns | Allowlist map only |
| Multi-tenant filters | Server-side `tenant_id` from session, never from the client alone |
| Errors | No stack trace or SQL text sent to clients |
| DB role | Minimal grants; no OS-integration features |
| Migrations / admin scripts | Same standards as the production request path |
| Second-order paths | Reports, queues, and search indexers are parameterized too |
| Tests | At least one regression test per historical concatenation bug |

```
 Trust boundary          Safe interior
 ┌─────────────┐         ┌──────────────────────────┐
 │ HTTP / MQ   │  values │  Prepare(T) + Bind(v)    │──► SQL engine
 │ untrusted   │────────►│  Allowlist(identifiers)  │
 └─────────────┘         └──────────────────────────┘
        ✗ never:  sql = "SELECT ... " + user
```

## Security notes: threats and defenses

| Threat pattern | Why it works | Defense |
|:---|:---|:---|
| Auth bypass via altered WHERE | Data becomes boolean logic | Bind parameters; enforce authorization server-side via the session |
| UNION-style result shaping | Attacker aligns columns when output is reflected | Parameters; minimize reflective SQL errors and data |
| Blind inference | The app leaks boolean or timing side channels | Parameters; constant-time-ish error pages; rate limits |
| Privileged DB features | An over-powered DB account | Drop dangerous privileges; control egress |
| ORM raw SQL | An escape hatch that concatenates strings | Ban or review raw APIs; run SAST |
