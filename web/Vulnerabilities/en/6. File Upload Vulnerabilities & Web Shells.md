## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| File upload | A feature that lets users send files to the server |
| Web shell | A malicious uploaded file that lets an attacker run commands |
| Content-Type | The declared type of an upload (easily faked, so don't trust it alone) |
| Magic bytes | The real file-type signature at the start of a file |
| Extension allowlist | Accepting only known-safe file extensions |
| Execution | The real danger: the server running an uploaded file as code |
| Re-encoding | Rebuilding an image to strip hidden payloads |

## 1. Threat model

A file upload feature turns the client into a writer on the server's filesystem or object store. WAHH stresses the chained impact: if an uploaded file can be executed by the web runtime, or processed by a vulnerable parser, the result can be RCE, stored XSS (through SVG or HTML), SSRF through a parser that follows URLs, or denial of service (zip bombs, decompression abuse).

A web shell, as a concept, is a script that gets uploaded and then invoked over HTTP, so the server executes the attacker's commands. This note explains how to prevent that class of bug, not how to write or upload one.

CWE-434 covers *Unrestricted Upload of File with Dangerous Type*. Dangerous does not mean only "`.php`"; it includes anything the environment will interpret: templates, server-side includes, certain "document" formats inside office converters, or HTML served with the wrong MIME type.

A dangerous upload, put simply, is any file type the server or browser will interpret or execute that got placed there without adequate control.

## 2. Root causes

| Failure | What goes wrong |
|:---|:---|
| Trusting the client's `Content-Type` or filename | Both are attacker-controlled metadata |
| Storing under a web-executable root | The URL maps directly to a code runtime |
| Keeping the user's extension | `.php`, `.aspx`, `.jsp`, double extensions, trailing dots |
| No random object key | Overwrites, predictable paths, cache poisoning |
| Serving with the wrong `Content-Type` | The browser executes it as HTML/JS (XSS) |
| Processing with unsafe parsers | ImageTragick-class bugs, XXE in an XML-based "preview" |
| A symlink or path embedded in the filename | Traversal into other directories |

## 3. Content validation, principles

### 3.1 Layered checks (none sufficient alone)

1. Extension allowlist, for example `{png,jpg,webp,pdf}`, mapped server-side.
2. Magic-byte / `file(1)`-style sniffing, checked against the declared type.
3. Re-encode or transcode: for images, decode then write a new file with a trusted library, which destroys most polyglot tricks.
4. Size limits, both per file and per user quota.
5. Filename discard: never reuse the raw user filename as the storage key.

```text
accept the file only if:
  the extension is on the allowlist
  and the magic bytes match that extension
  and the size ≤ the limit
```

### 3.2 Polyglots (concept)

A single file can be valid as more than one format, for example an image plus embedded script content, depending on which parser reads it. Re-encoding, plus a strict `Content-Type` at serving time, reduces this risk.

### 3.3 SVG / HTML

An SVG can contain script if it is served inline as `image/svg+xml` in certain contexts. Safer options: rasterize the SVG to PNG server-side, or serve it with `Content-Disposition: attachment` plus a strict CSP.

## 4. Safe storage design

```
 ┌──────── viewer / CDN ────────┐
 │  signed URL, short TTL       │
 └─────────────▲────────────────┘
               │
 ┌─────────────┴────────────────┐
 │ Object store bucket          │
 │  - random keys               │
 │  - no public execute         │
 │  - antivirus/async scan opt. │
 └─────────────▲────────────────┘
               │
         app writes only
```

Principles:

- Store files outside the document root, or in a bucket with no script execution at all.
- Object key: a UUID plus a fixed extension drawn from the allowlist.
- The database maps `user_id → object_key → declared_type`.
- Access only through an authorized download handler or a signed URL.
- On Apache/Nginx, the upload directory's `location` block explicitly disables script engines, which is defense in depth even if some other layer is misconfigured.

---

## 5. Execution barrier

The goal: requesting an uploaded file over HTTP must never run code on the server.

Controls:

- Never map an upload path to a PHP, ASP, or JSP interpreter.
- Download headers: the correct `Content-Type`, plus `X-Content-Type-Options: nosniff`.
- `Content-Disposition: attachment` for risky types.
- Disable handlers in the upload folder at the ops/config layer (adapt to your own stack).

Even with perfect extension checks, a later bug elsewhere (an LFI of the upload path, or a template include) can revive the risk. Keep uploads non-executable and non-includable as code, independent of how well the upload check itself works.

## 6. Unsafe vs safe patterns

### 6.1 Unsafe

```python
# UNSAFE — trusts filename & stores in web root
f = request.files["file"]
f.save("/var/www/html/uploads/" + f.filename)
# later: https://app/uploads/evil.php may execute if PHP enabled there
```

### 6.2 A safer sketch

```python
import uuid
from pathlib import Path

ALLOWED = {
    "image/png": ".png",
    "image/jpeg": ".jpg",
}
STORE = Path("/var/app/upload_data")  # not served as scripts

def save_upload(file_storage, sniffed_mime: str) -> str:
    if sniffed_mime not in ALLOWED:
        raise ValueError("type")
    if file_storage.content_length and file_storage.content_length > 5_000_000:
        raise ValueError("size")
    key = f"{uuid.uuid4().hex}{ALLOWED[sniffed_mime]}"
    dest = STORE / key
    # Prefer: decode/re-encode image here instead of raw save when applicable
    file_storage.save(dest)
    return key
```

```nginx
# Defense-in-depth example: deny script execution in a mistaken alias
location ^~ /media/ {
    internal;  # or alias to read-only files with types {}
    add_header X-Content-Type-Options nosniff always;
    default_type application/octet-stream;
}
```

## 7. Media and document processors

Uploads often get processed further: a thumbnail, a virus scan, or an office-to-PDF conversion.

| Risk class | Mitigation |
|:---|:---|
| Command injection in a converter CLI | Argv arrays; allowlist; sandbox |
| Parser vulnerabilities (images, XML, fonts) | Updated libraries; isolate workers; resource limits |
| XXE in XML-based formats | Disable external entities; use safe parsers |
| Zip bombs / compression ratios | Limit uncompressed size and entry count |
| SSRF through remotely linked resources | Disable network access inside the worker |

Run the processing worker in isolation: a non-root container, no egress, seccomp applied.

---

## 8. Defense-in-depth stack

1. AuthN/AuthZ on the upload API, controlling who can upload what.
2. Allowlist MIME type, magic bytes, and size.
3. Random keys; discard user filenames.
4. Re-encode images when possible.
5. Non-executable storage, in a separate bucket or account.
6. Safe serving headers, or signed URLs.
7. Async malware scanning where it makes sense.
8. Rate limits and quotas.
9. Monitoring for a spike in upload errors or unexpected new object types.
10. No include or LFI paths that can point back at the upload directory.

## 9. Developer checklist

| Check | Pass criteria |
|:---|:---|
| Storage location | Outside script roots |
| Type policy | Allowlist plus magic-byte check |
| Filename | Server-generated |
| Serving | `nosniff` plus the correct MIME type |
| SVG/HTML | Rasterized, or forced to download as an attachment |
| Workers | Sandboxed converters |
| Path | No user-controlled destination directories |
| Tests | Disallowed types are rejected; non-exec config is verified |

```
 Client file
    │
    ▼
 Validate type/size ──► Re-encode? ──► Store random key
    │                                   │
    └ reject                            ▼
                              Serve via authz + safe headers
```

## Security notes: threats and defenses

| Threat pattern | Class | Defense |
|:---|:---|:---|
| Executable upload | RCE through the web runtime | Non-exec storage plus a type allowlist |
| Stored XSS via HTML/SVG | Browser script execution | MIME control, CSP, sanitize or rasterize |
| Overwriting critical files | Integrity | Random keys; no user-supplied paths |
| Malicious archives | DoS, or path write | Limits; safe extraction |
| Converter abuse | RCE/SSRF | Sandbox; argv arrays; no egress |
