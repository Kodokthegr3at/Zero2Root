## 1. Definition

CSRF (Cross-Site Request Forgery) is an attack class where an already-authenticated victim's browser is tricked into sending a state-changing request to a target origin, and the application accepts that request as the victim's intent because ambient credentials, usually cookies, ride along automatically.

Unlike XSS, CSRF generally does not require injecting a script into the target origin. What gets abused is the browser's own behavior of sending cookies to whichever origin matches the request destination.

CSRF exploits the fact that browsers attach cookies, and sometimes other ambient credentials, to requests based on the destination URL, not on whether the request was triggered by a first-party UI gesture the server can trust.

---

## 2. Preconditions (conceptual)

CSRF conceptually succeeds when all of the following hold.

1. A relevant action can be triggered by a forged HTTP request (for example `POST /transfer`).
2. The session or auth credential is sent automatically (a session cookie, or occasionally legacy HTTP Basic).
3. No request-specific secret has to be read from the origin's own page (an anti-CSRF token, a custom header that is hard to forge cross-site, and so on).
4. The victim is in a context where the browser will include those credentials, meaning they are logged in.

The server authenticates the request only by the cookies the browser attached, with no proof that the user really meant to send it from the same site.

A "safe" method (`GET`) that mutates state violates the HTTP spec and expands the CSRF surface, since a link, an `img` tag, or a prefetch can all trigger it. WAHH's point is direct: never use GET for an action with consequences. Idempotent-safe methods should not mutate anything. If `GET` mutates state, the CSRF surface expands to every place a URL can be requested cross-site.

## 3. Root cause: ambient authority

The server sees something like this.

```http
POST /api/password HTTP/1.1
Host: bank.example
Cookie: session=...
```

The server proves who is making the request (the session), but it does not prove whether a legitimate same-origin UI actually triggered the action. CSRF lives in that gap: authentication is not the same thing as authorization of intent.

*The Tangled Web* discusses how browser features (cross-site forms, redirects, legacy plugins) have historically muddied this boundary. Modern mitigations are SameSite cookies, CSRF tokens, and Fetch Metadata.

Fix CSRF by requiring an unforgeable, session-bound proof that the request came from your own application's pages or flows, or by ensuring cookies are not sent on cross-site requests for sensitive actions.

## 4. Anti-CSRF token models

### 4.1 Synchronizer token (the classic preferred model)

1. The server generates a random token t ← {0,1}ⁿ (at least 128 bits of entropy is recommended).
2. Store t in the server-side session, or in a MAC'd server-side artifact.
3. Embed t in the form, or expose it to same-origin JS through the response.
4. On a state-changing request, verify t_req = t_session using a constant-time comparison.

```text
accept only if:   token in request == token in session   and   the session is valid
```

### 4.2 Double-submit cookie (a stateless variant)

The token lives in a cookie and in a parameter or header; the server checks that they match. This needs to be paired with a clear understanding of subdomain and cookie-injection risk. Prefer the synchronizer pattern or a framework's built-in CSRF protection when you can.

### 4.3 What tokens are not

- Not a substitute for authorization; IDOR checks still have to happen.
- Not a protection against XSS on the same origin, since a script running there can just read the token.
- The token has to be unique per session, or per form with correct rotation.

## 5. SameSite cookies (RFC 6265bis practice)

| Value | Cross-site behavior (simplified) | Notes |
|:---|:---|:---|
| `Strict` | Cookie is not sent on cross-site requests | Strong; can affect return navigations |
| `Lax` | Sent on top-level GET navigations; withheld on most cross-site POST | The common default baseline |
| `None` | Sent cross-site; requires `Secure` | Needed for some embeds; treat with the most care for CSRF |

`SameSite` reduces cookie-based CSRF, but it is not the only control that matters: older browsers, `SameSite=None` deployments, and some cross-site flows still need a token or another design.

Defense in depth means `SameSite=Lax` or `Strict` plus anti-CSRF tokens on state-changing endpoints, especially if you support older clients or cross-site deployments.

## 6. Unsafe vs safe application patterns

### 6.1 Unsafe: cookie session with no request secret

```http
POST /settings/email HTTP/1.1
Host: app.example
Cookie: session=abc
Content-Type: application/x-www-form-urlencoded

email=attacker@evil.example
```

Without an adequate token or SameSite setting, a cross-site form can trigger the same action.

### 6.2 Safe: synchronizer token in the form

```html
<form method="POST" action="/settings/email">
  <input type="hidden" name="csrf" value="{{ csrf_token }}">
  <input type="email" name="email">
  <button type="submit">Update</button>
</form>
```

```python
# SAFE sketch — framework comparison
if not hmac.compare_digest(session["csrf"], request.form["csrf"]):
    abort(403)
# then perform state change + authZ checks
```

### 6.3 Safe: custom header for same-origin XHR/fetch

SPAs often send a header such as `X-CSRF-Token`, or rely on one of these patterns.

- An `HttpOnly` session cookie plus a token header sourced from a meta tag, or
- An `Authorization: Bearer` value held in `localStorage` or memory instead of a cookie. Classic CSRF weakens under this model, but XSS becomes far more critical, so choose this threat model deliberately.

## 7. JSON APIs, CORS and Fetch Metadata

A `Content-Type: application/json` request from a plain cross-site HTML form is not trivially achievable the same way `application/x-www-form-urlencoded` is, since a bare HTML form cannot easily send raw JSON. Do not treat "it's JSON, so it's safe" as a rule though.

- Legacy plugins and past browser bugs have changed these assumptions before.
- An endpoint that also accepts form-urlencoded input stays vulnerable regardless of the JSON path.
- Misconfigured CORS, such as `Access-Control-Allow-Origin: *` combined with `Allow-Credentials: true` (an invalid and dangerous combination if it is actually allowed to happen), can make credentialed cross-origin problems worse.

Fetch Metadata headers (`Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest`) let a server reject cross-site requests for sensitive resources, a pattern often called a Resource Isolation Policy.

Recommended API posture:

1. State-changing methods require a CSRF token or a non-cookie auth proof.
2. Reject unexpected `Sec-Fetch-Site` values for cookie-authenticated mutations, where compatibility allows it.
3. CORS should allowlist exact origins, and never reflect an arbitrary `Origin` header alongside credentials.

## 8. Defense-in-depth stack

| Layer | Control |
|:---|:---|
| 1 | No state change through `GET` |
| 2 | Anti-CSRF tokens on mutations |
| 3 | `SameSite=Lax` or `Strict` on session cookies |
| 4 | `Secure` + `HttpOnly` cookie flags |
| 5 | Re-authentication or step-up for high-risk actions (password change, payout) |
| 6 | Fetch Metadata isolation |
| 7 | Origin checks for custom workflows |
| 8 | User notifications or transaction confirmations |

Login CSRF and logout CSRF also appear in the WAHH literature. Consider a token on the login POST itself if session fixation or login confusion is relevant to your threat model.

## 9. Developer checklist

| Check | Pass criteria |
|:---|:---|
| Mutations | POST/PUT/PATCH/DELETE only |
| Token | Verified server-side for cookie-auth mutations |
| Cookie | `Secure; HttpOnly; SameSite` set intentionally |
| CORS | Explicit origin allowlist; credential use is a deliberate decision |
| XSS | Treated as a CSRF-bypass risk, since tokens become readable |
| Tests | An automated test confirms a missing or invalid token returns 403 |
| Admin actions | Step-up authentication required |

## Security notes: threats and defenses

| Threat pattern | Why | Defense |
|:---|:---|:---|
| Classic form CSRF | Cookies are auto-sent | Token + SameSite |
| GET mutation | Trivial to trigger cross-site | Make GET read-only |
| The "JSON-only is safe" myth | Other content types, or past browser bugs | Explicit CSRF design |
| XSS on the origin | Token theft, or direct API calls | Fix the XSS; HttpOnly still protects the cookie itself |
| Misconfigured CORS | Credentialed cross-origin reads or calls | A strict ACAO allowlist |
