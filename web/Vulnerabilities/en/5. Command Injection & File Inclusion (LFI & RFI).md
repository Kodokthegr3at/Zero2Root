## 1. Shared root cause: mixing code and data

Command injection and file inclusion are siblings of SQL injection; WAHH calls this whole family "injecting into interpreted languages." An attacker-influenced string gets merged into something that will be interpreted: a shell, a PHP `include`, a template engine, and so on.

$$
\mathsf{Interpreter}(T_0 \,\|\, u \,\|\, T_1)
\;\neq\;
\mathsf{Interpreter}(T_0 \,\|\, \mathsf{lit}(u) \,\|\, T_1)
$$

When $u$ can change how the interpreter parses the input, data turns into code, or into a path outside the intended contract.

The primary fix is always structural: do not start a shell, do not include an arbitrary path, and use APIs that take argument vectors or fixed, allowlisted resources instead of building a string and handing it to an interpreter.

## 2. OS command injection (CWE-78)

### 2.1 When it appears

It shows up in any feature that calls an external tool: ImageMagick, `ping`, converters, git wrappers, backup scripts, or an admin "diagnose hostname" utility.

### 2.2 The dangerous pattern

Shell metacharacters, conceptually: command separators, substitution, pipes, turn one intended command into several. This note does not list a payload catalog; the point is to understand the risk class.

### 2.3 Safe approach: an argv array, no shell

```python
# UNSAFE — shell=True + user input
os.system("ping -c 1 " + host)
subprocess.call("convert " + user_path + " out.png", shell=True)

# SAFE — no shell; fixed executable; validate host/path first
subprocess.run(
    ["/usr/bin/ping", "-c", "1", "--", host],
    check=False,
    capture_output=True,
    timeout=3,
)
# host must still match allowlist regex (e.g. DNS label rules)
```

```php
// UNSAFE
shell_exec("dig " . $_GET["d"]);

// SAFER — avoid shell; use library or escapeshellarg *only* if shell unavoidable
// Best: do not expose dig; use PHP DNS APIs / internal service
```

If a shell is genuinely unavoidable, use `escapeshellarg` or the equivalent for your platform, but understand it stays inferior to an argv array.

### 2.4 Defense extras

- Allowlist arguments as an enum of known jobs, not free-form strings.
- Drop privileges; apply seccomp or AppArmor; keep containers free of unnecessary binaries.
- Remove debugging utilities from production images.

## 3. Local File Inclusion (LFI)

### 3.1 Definition

The application picks a local file to `include`, `require`, or read based on input, so it ends up reading, or in some languages executing as code, a file outside the one intended.

A conceptual anti-pattern:

```php
// UNSAFE sketch — user controls path segment
include($_GET["page"] . ".php");
```

### 3.2 Why it hurts

| Outcome | Mechanism (class) |
|:---|:---|
| Information disclosure | Reading configs, keys, logs |
| Code execution | Including an uploaded file or a log that turns into executable PHP when misconfigured |
| Auth bypass | Including an unexpected "page" |

The "log poisoning into include" chain is an advanced version of the same class; the mitigation stays the same, do not include a user-supplied path, and do not store user content as a file that later gets executed.

### 3.3 Safe pattern: an allowlist map

```php
// SAFE — explicit map, no filesystem path from user
$pages = [
  "home" => __DIR__ . "/pages/home.php",
  "about" => __DIR__ . "/pages/about.php",
];
$key = $_GET["page"] ?? "home";
if (!isset($pages[$key])) {
  http_response_code(404);
  exit;
}
include $pages[$key];
```

## 4. Remote File Inclusion (RFI)

RFI is inclusion or execution of a remote resource (a URL) when the language or configuration allows it, historically `allow_url_include` in PHP. It combines URL trust problems with code execution.

Modern default configurations often disable remote include, but verify it rather than assuming so. Prefer never using a URL-capable include at all. If you need remote content, fetch it as data with SSRF controls applied, never `include` it as code.

| Control | RFI relevance |
|:---|:---|
| Disable URL includes in the language runtime | Critical |
| No user-controlled include targets | Critical |
| Network egress deny | Defense in depth |

## 5. Path traversal relation (CWE-22)

Path traversal, the `../`-style class of tricks, often accompanies LFI and file download features.

$$
\mathsf{canon}(\mathsf{base} \,\|\, u) \;\overset{?}{\in}\; \mathsf{Tree}(\mathsf{base})
$$

Safe file read pattern:

```python
from pathlib import Path

BASE = Path("/var/app/static").resolve()

def read_user_file(name: str) -> bytes:
    # name: allowlist characters only, e.g. [A-Za-z0-9._-]+
    candidate = (BASE / name).resolve()
    if not candidate.is_relative_to(BASE):  # py3.9+: use try relative_to
        raise PermissionError("escape")
    return candidate.read_bytes()
```

Do not rely on filtering the literal string `../` alone; encoding tricks, nested sequences, and absolute paths all bypass a naive filter.

## 6. Side-by-side summary

| Pattern | Unsafe idea | Safe idea |
|:---|:---|:---|
| Commands | `shell=True` plus string concatenation | An `argv` list plus an allowlist |
| Includes | `include($user)` | A map from a key to a fixed path |
| Downloads | `open("/data/"+user)` | `resolve()` plus `is_relative_to` |
| Templates | The user picks a template path | Allowlist template names |
| RFI | Including a URL | Disabled; never include remote code |

## 7. Defense-in-depth stack

### Command injection

1. Prefer a native library over shelling out to an OS tool.
2. Use `subprocess` or `execve` argv arrays; never `/bin/sh -c` with user data.
3. Validate with allowlists (character set plus length).
4. Least privilege plus a sandbox.
5. Structured logging of exit codes, not attacker-controlled command strings.

### File inclusion and traversal

1. Allowlist resource IDs.
2. Canonicalize the path and enforce a base-directory jail.
3. Keep data storage and executable code in separate root directories.
4. Store uploads outside the web root; serve them through a controlled handler.
5. Disable remote-include language features; harden `open_basedir` or chroot where applicable.
6. In PHP, never `include` an uploaded file; use `readfile` for serving data if needed.

*The Tangled Web* is relevant here because path and URL parsing so often disagrees between layers (a proxy, the app, the filesystem). Always normalize at one single server-side point of trust.

WAHH treats these as injection into the OS and into the language runtime; review every `exec`, `system`, `popen`, `include`, `require`, and `file_get_contents` call that takes a variable path.

## 8. Developer checklist

| Area | Check |
|:---|:---|
| Shell | No `shell=True` / `system` with request data |
| Binaries | Full path to the binary; fixed flags |
| Includes | Map or allowlist only |
| Files | `resolve()` plus base containment |
| Uploads | Stored in non-executable locations |
| Config | Remote include disabled |
| Tests | Attempted escape paths are rejected in unit tests |
| SAST | Rules cover command exec and dynamic include |

```
 User input          Safe control plane
 ──────────          ──────────────────
  host/name    ──►   allowlist / map
  path piece   ──►   jail under BASE
  "command"    ──►   fixed argv, no shell
  remote URL   ──►   never include-as-code
```

## Security notes: threats and defenses

| Threat class | Root | Defense |
|:---|:---|:---|
| Command injection | Shell grammar | Argv plus allowlist |
| LFI | Dynamic include or read | ID map plus jail |
| RFI | Remote content treated as code | Disable it; never include URLs |
| Traversal | Relative-path escape | Canonical containment |
| Upload+include chain | An executable upload directory | Decouple storage from execution |
