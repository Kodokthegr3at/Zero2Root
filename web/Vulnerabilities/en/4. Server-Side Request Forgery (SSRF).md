## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| SSRF | Making the server itself send requests to a target the attacker chooses |
| Confused deputy | A trusted component tricked into acting for an attacker |
| Internal service | A system only reachable from inside the network |
| Cloud metadata endpoint | A special internal address holding cloud credentials (a prime SSRF target) |
| Allowlist | A list of permitted destinations — the main defense |
| Blind SSRF | SSRF where the response isn't shown back to the attacker |

---

## 1. Definition

SSRF happens when a server-side application fetches a resource based on a reference an attacker can influence (a URL, host, or path), turning the server into a confused deputy that reaches targets never meant to be public: internal services, localhost, link-local addresses, or cloud metadata.

The request then comes from the server's own trusted IP inside the network, not from the attacker.

Unlike CSRF, where the victim's browser sends the request, in SSRF it is the application's own server that sends it.

SSRF is dangerous because firewalls and "internal-only" services often trust the application's own subnet by default. The underlying bug class is insufficient restriction on server-side outbound requests.

---

## 2. Impact classes (conceptual)

| Class | Description | Defense emphasis |
|:---|:---|:---|
| Internal recon | Touching ports or services inside the VPC | Egress allowlist; network policy |
| Local service abuse | Hitting `localhost` admin ports or local agents | Block loopback; do not expose unix sockets through an HTTP URL |
| Cloud credential exposure | Reaching instance metadata endpoints | IMDSv2 / hop limits; firewall the metadata endpoint |
| File/handler schemes | Dangerous URL schemes when the library allows them | Scheme allowlist, `https` only |
| Response misuse | The app relays an internal response body back to the attacker | Never reflect raw fetch bodies; enforce size limits |
| Blind SSRF | Only side effects are observable (DNS, timing, webhooks) | The same URL controls; monitor egress |

Some libraries have historically supported non-HTTP schemes. This note does not cover exploit chains for those schemes; the point to understand is to restrict both the scheme and the parser.

## 3. Root cause

Product features that commonly trigger SSRF:

- URL preview, link unfurling, or thumbnail generators
- Webhook testers, or a "fetch this callback" feature
- Import-from-URL, PDF generators, or document converters
- SSO or metadata discovery with a user-controlled URL
- Image proxies or a CDN that pulls from an arbitrary origin

The root cause is treating a URL string as safe just because "the HTTP client library only downloads." Security depends on a destination policy, not on "we use HTTPS."

## 4. URL validation pitfalls

Naive validation often fails because different layers interpret the URL differently.

### 4.1 Hostname allowlist vs IP allowlist

Blocking the string `127.0.0.1` is not enough when:

- DNS can return an internal IP after the check passes, which is DNS rebinding, a resolve-check-resolve TOCTOU.
- Decimal, hex, or IPv6-mapped forms can encode loopback addresses.
- An internal hostname alias can point at a blocked target under a different name.

The safe pattern: resolve DNS, verify the resulting IP address is in the policy's allowlist, then connect only to that verified (pinned) IP, using a short TTL and re-checking on every redirect instead of trusting the original hostname again.

### 4.2 Redirects

`http://allowed.example` can 302 to `http://169.254.169.254/`. If the client follows the redirect without re-validating, the control is bypassed.

### 4.3 Parser discrepancies

A URL library in language A does not always agree with a parser in language B; *The Tangled Web* stresses exactly this kind of parser inconsistency. One side of a system sees a "safe" host while the other side connects to a different one.

### 4.4 Formal policy sketch

```text
1. the scheme must be https
2. the resolved IP must be on the public allowlist
3. the resolved IP must NOT be loopback, link-local, RFC1918 private,
   CGNAT, or a cloud metadata address
```

Prefer a positive allowlist of destinations (known partner hosts) over relying on a giant blocklist alone.

## 5. Unsafe vs safe patterns

### 5.1 Unsafe

```python
# UNSAFE — attacker controls URL; server fetches anything reachable
import requests
url = request.args["url"]
resp = requests.get(url, timeout=3)
return resp.text  # may leak internal responses
```

### 5.2 A safer sketch: scheme allowlist, block private IPs, no redirects, size cap

```python
# HARDENED SKETCH — still review for DNS rebinding in production
from urllib.parse import urlparse
import ipaddress, socket, requests

ALLOWED_PORTS = {443}
BLOCK_NETS = [
    ipaddress.ip_network("0.0.0.0/8"),
    ipaddress.ip_network("10.0.0.0/8"),
    ipaddress.ip_network("127.0.0.0/8"),
    ipaddress.ip_network("169.254.0.0/16"),
    ipaddress.ip_network("172.16.0.0/12"),
    ipaddress.ip_network("192.168.0.0/16"),
    ipaddress.ip_network("::1/128"),
    ipaddress.ip_network("fc00::/7"),
    ipaddress.ip_network("fe80::/10"),
]

def ip_blocked(ip: str) -> bool:
    addr = ipaddress.ip_address(ip)
    return any(addr in net for net in BLOCK_NETS)

def safe_fetch(user_url: str) -> bytes:
    u = urlparse(user_url)
    if u.scheme != "https" or not u.hostname:
        raise ValueError("scheme")
    port = u.port or 443
    if port not in ALLOWED_PORTS:
        raise ValueError("port")
    infos = socket.getaddrinfo(u.hostname, port, type=socket.SOCK_STREAM)
    ips = {info[4][0] for info in infos}
    if not ips or any(ip_blocked(ip) for ip in ips):
        raise ValueError("ip")
    # Production: connect via pinned IP + SNI/Host carefully; re-check redirects
    r = requests.get(user_url, timeout=3, allow_redirects=False, stream=True)
    return r.content[: 200_000]
```

For many products, the safer route is not accepting a raw URL at all; accept an internal `resource_id` that the server maps to a fixed URL.

## 6. Cloud metadata hardening (concept)

Instance metadata services (IMDS) hand out temporary credentials to cloud workloads. SSRF reaching IMDS is one of the highest-impact patterns in modern cloud incident response.

| Control | Intent |
|:---|:---|
| IMDSv2 (session-oriented) | Requires a method/header hop that a basic SSRF GET cannot trivially reproduce |
| Hop limit / firewall | Prevents containers from reaching metadata unexpectedly |
| Least-privilege roles | Limits the blast radius of stolen credentials |
| No raw metadata proxying | The app never fetches a metadata URL sourced from user input |

This note does not provide a metadata exploit recipe, only the hardening side.

## 7. Defense-in-depth stack

1. Prefer indirection: pass IDs, not free-form URLs.
2. Scheme allowlist, typically `https` only.
3. Destination allowlist for known partners.
4. Block private, link-local, and metadata ranges after DNS resolution; pin the IP.
5. Disable redirects, or re-validate on every hop.
6. Network egress policy: the app subnet cannot reach sensitive segments.
7. A dedicated outbound proxy with DLP or allowlist enforcement.
8. Never return raw internal response bodies to clients.
9. Timeouts, size limits, and content-type allowlists.
10. Authorization on the feature itself, controlling who can trigger a fetch at all.

WAHH stresses mapping the surface of "where does this application make outbound connections from." Inventory every HTTP client across the codebase, including PDF generators, ffmpeg wrappers, and webhook deliverers, not just the obvious ones.

An SSRF fix that only filters string equality on hostnames, without addressing redirects and the DNS TOCTOU window, stays fragile. Hostname string matching alone is not enough; control DNS re-resolution, redirects, and scheme together.

## 8. Authorized detection signals

- Code search for patterns like `requests.get(user`, `HttpClient`, `curl_exec`, `file_get_contents("http`.
- Egress monitoring: watch for app pods connecting to `169.254.169.254` or an RFC1918 range unexpectedly.
- Unit tests that reject loopback addresses, reject redirects to a private IP, and reject non-HTTPS schemes.

```bash
# Lab only: verify YOUR egress firewall denies metadata IP from app netns
# (ops check — not an exploit)
curl -sS -o /dev/null -w "%{http_code}\n" --connect-timeout 2 https://example.com/
```

## 9. Developer checklist

| Check | Pass |
|:---|:---|
| User-supplied URL needed at all? | Prefer IDs |
| Scheme | `https` only |
| Redirects | Off, or re-validated |
| IP policy | Blocks private, link-local, and metadata ranges |
| DNS | TOCTOU considered; IP pinned |
| Response | Not reflected raw; capped |
| Egress | Network policy is deny-by-default |
| Cloud | IMDSv2 plus minimal roles |

```
 Client URL ─► Policy gate ─► Egress proxy ─► Allowlisted targets only
                 │ reject
                 └── private / metadata / bad scheme
```

## Security notes: threats and defenses

| Threat pattern | Mechanism | Defense |
|:---|:---|:---|
| Internal port touch | Server reaches VPC services | Egress allowlist |
| Metadata access | Link-local IMDS reachable | IMDSv2; block it; never a user-supplied URL |
| Redirect bypass | A 302 pointing internal | `allow_redirects=False` plus re-checking |
| DNS rebinding | The IP changes after the check | Pin the IP; short TTL; re-validate |
| Scheme smuggling | Non-HTTP handlers accepted | Scheme allowlist |
