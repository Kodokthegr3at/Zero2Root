## 1. Authentication goals

Authentication establishes the identity of a subject. Session management maintains that binding across requests. Authorization decides what they are permitted to do. WAHH keeps these separate for a reason: a "weak login" bug and an "easily fixated or hijacked session" bug are different failure classes.

The classic security properties:

| Property | Meaning |
|:---|:---|
| Authenticity | Only the credential owner can open a session |
| Integrity | The token or session cannot be modified undetected |
| Confidentiality | Secrets do not leak through XSS, logs, or Referer |
| Binding | The session is tied to its context (user, device policy) |
| Revocation | The server can cut access before expiry |

Passwords, WebAuthn, OIDC, and API keys are credential classes. Sessions and JWTs are artifacts that prove a prior authentication happened; their cryptography and storage choices dominate modern failure modes far more than the login form itself.

## 2. Server-side session model

```text
1. login OK     → server creates a random sid (at least 128 bits)
2. server saves → sid: {user id, metadata, expiry}
3. each request → browser sends the sid cookie, server looks it up
```

The advantage of this model: revocation is easy (delete the `sid` entry), and the payload kept on the client is minimal.

Risk classes here, conceptually rather than as an exploit kit: predictable `sid` values from low entropy, fixation (an attacker pre-sets a `sid` before login), theft through XSS or network capture, and missing regeneration when privilege changes.

Core mitigation: regenerate the session ID on login, use high entropy, keep the store server-side, apply both idle and absolute timeouts, and require re-authentication before critical steps.

## 3. Cookie hardening (*The Tangled Web* / RFC 6265)

| Attribute | Role |
|:---|:---|
| `Secure` | HTTPS only |
| `HttpOnly` | Not readable from JS |
| `SameSite` | Reduces CSRF |
| `Path` / `Domain` | Keep the scope narrow |
| `__Host-` prefix | Extra constraints on host cookies |

Avoid putting a session in `localStorage` when you can avoid it; XSS steals it directly. If an SPA keeps a Bearer token in memory instead, understand the CSRF-vs-XSS trade-off that choice implies.

## 4. JWT structure: the mathematics of JWS compact serialization

The JWT format most commonly used is JWS (RFC 7515) in its compact form:

```text
JWT = base64url(H) . base64url(P) . base64url(S)

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMifQ.<signature>
```

where:

- H is the header JSON (algorithm, type, sometimes `kid`)
- P is the payload/claims JSON
- S is the signature or MAC tag over the signing input

Signing input:

```text
SI = base64url(H) . base64url(P)      (the signing input)
```

### 4.1 HMAC (alg `HS256`, etc.)

```text
S = HMAC-SHA256(k, SI)
```

with a shared key k. Verification recomputes S' and compares it to S in constant time.

### 4.2 Asymmetric (alg `RS256` / `ES256`, etc.)

```text
Verify(SI, S, pk) → true / false
```

The signature is created with a private key and verified with the public key, which is useful for microservices that do not share an HMAC secret.

### 4.3 Claims (payload)

Registered claims from RFC 7519 include `iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`. Applications add private claims on top. Never put a sensitive secret in a JWT that the client can read, since the header and payload are only encoded, not encrypted. For claim confidentiality, use JWE, or keep the data server-side instead.

Base64url is not confidentiality:

```text
base64url_decode("eyJzdWIiOiIxMjMifQ")  →  {"sub":"123"}
```

Anyone can do this decoding. No key is needed.

## 5. Correct verification checklist

A safe implementation has to:

1. Parse all three parts; reject any malformed format.
2. Select the key from a trust store based on an allowed `kid`; never fetch a JWKS from a user-supplied URL.
3. Enforce an algorithm allowlist server-side, for example only `ES256` or only `RS256`.
4. Verify the signature with a vetted crypto API; reject on any failure.
5. Validate the claims: `exp`/`nbf` with a small clock skew δ; exact match on `iss` and `aud`; `sub` mapped to authorization.
6. Reject a token with a missing or empty signature section.
7. Use a constant-time comparison for HMAC.
8. Log failures without printing the full token.

```python
# SAFE sketch — algorithm allowlist + verify + claims
# (library APIs differ; never roll your own crypto)
import jwt  # PyJWT-style illustration

PUBLIC_KEY = open("jwks_rsa_pub.pem").read()
ALLOWED = ["RS256"]

def accept_bearer(token: str) -> dict:
    return jwt.decode(
        token,
        PUBLIC_KEY,
        algorithms=ALLOWED,          # critical
        audience="api.myapp.example",
        issuer="https://idp.myapp.example/",
        options={"require": ["exp", "iat", "sub"]},
    )
```

## 6. Algorithm confusion (concept only)

Algorithm confusion, historically tied to `alg=none` handling and mixed-up HMAC-vs-RSA verification, happens when the receiver trusts the `alg` field from the token itself and picks the wrong verification path based on it.

Conceptual examples:

- The token claims `alg=HS256`, but the verifier uses a public RSA key as the HMAC secret. If the library allows it, an attacker who knows the public key can forge a valid MAC.
- The token claims `alg=none` with an empty signature. An old verifier that "accepts none" will accept any payload at all.

The server sets which algorithms it accepts. The header is only metadata that has to match that policy, never the authority deciding it.

This note intentionally omits exploit construction and cracking tooling. If you maintain a verifier, add regression tests where forged `alg` values must fail closed.

## 7. Common design flaws (classes)

| Flaw class | Description | Mitigation |
|:---|:---|:---|
| Weak or guessable session IDs | Low entropy | CSPRNG, at least 128 bits |
| Session fixation | A pre-login SID is kept after login | Rotate on login |
| Long-lived JWT with no revoke | A stolen token works until `exp` | Short `exp` plus refresh rotation; deny-list `jti` if needed |
| Sensitive data inside the JWT | Claims are readable by anyone with the token | Minimal claims; keep data server-side |
| `kid` injection / header injection | An attacker points the verifier at an untrusted key | Strict JWKS pinning; allowlist `kid` values |
| Missing `aud`/`iss` checks | Cross-service token acceptance | Explicit audience checking |
| "Verify" that only decodes | Base64 decoding without a crypto check | Always verify the signature |
| Refresh token abuse | Theft leads to long-lived access | Rotate; bind; detect reuse |
| Password storage | Fast hash functions | Argon2id, bcrypt, or scrypt plus a pepper |

For password login: rate limiting, lockout or backoff, MFA for privileged accounts, and constant-time comparison of password hashes through vetted KDF APIs.

## 8. Unsafe vs safe patterns

```python
# UNSAFE — trusts alg from token; or decode without verify
jwt.decode(token, key, options={"verify_signature": False})  # never in prod
jwt.decode(token, key, algorithms=["HS256", "RS256", "none"])  # too broad
```

```python
# SAFE — narrow algorithms; verify aud/iss/exp
jwt.decode(token, key, algorithms=["ES256"], audience=AUD, issuer=ISS)
```

```python
# SAFE session sketch
sid = secrets.token_urlsafe(32)
redis.setex(f"sess:{sid}", TTL, user_id)
# On login success: destroy old sid, issue new
```

## 9. Defense-in-depth stack

1. Phishing-resistant MFA for high-value accounts (WebAuthn).
2. HTTPS everywhere, with HSTS.
3. Session cookies: `Secure; HttpOnly; SameSite`.
4. JWT: short-lived access tokens, rotating refresh tokens, allowlisted algorithms.
5. Server-side revocation for breach response (`jti` or a session store).
6. Step-up authentication for password changes, payouts, and API key minting.
7. CSRF tokens if the session is cookie-based (see the CSRF note).
8. XSS defense, since session theft is downstream of it.
9. Central auth (OIDC) built on vetted libraries; do not invent your own crypto protocol.
10. Audit logs for authentication failures and refresh-token reuse.

### Opaque session vs JWT

| | Server session ID | JWT access token |
|:---|:---|:---|
| Revoke | Easy | Needs infrastructure |
| Size | A tiny cookie | Larger |
| Crypto on verify | A lookup | A signature verification |
| Use case | Classic web apps | APIs / distributed readers |

A common hybrid: an opaque session for the browser, and a short-lived JWT for service-to-service calls with mTLS.

## 10. Developer checklist

| Check | Pass |
|:---|:---|
| Session ID entropy | CSPRNG, at least 128 bits |
| Rotate SID on login | Yes |
| Cookie flags | `Secure`, `HttpOnly`, `SameSite` all set |
| JWT verify | Signature plus `iss`/`aud`/`exp` |
| Algorithm policy | Server allowlist; no `none` |
| Keys | Private keys in a KMS or HSM; rotated |
| Refresh | Rotation plus reuse detection |
| Passwords | A modern KDF; never logged in plaintext |
| Tests | Algorithm-confusion cases fail closed |

```
 AuthN success
     │
     ├─► create server session (opaque sid) ─► Set-Cookie hardened
     │
     └─► issue JWS access token
              SI = b64(H).b64(P)
              S  = Sign_k(SI) or MAC_k(SI)
              verify with allowlisted alg + claims
```

## Security notes: threats and defenses

| Threat class | Why | Defense |
|:---|:---|:---|
| Stolen session cookie | XSS or malware | `HttpOnly`; CSP; short TTL |
| Forged JWT | Broken verification, or algorithm confusion | Allowlist plus proper verification |
| Long-lived bearer token leakage | Logs, Referer, XSS | Short `exp`; avoid tokens in URLs |
| Fixation | SID set before authentication | Regenerate on login |
| Credential stuffing | Reused passwords | MFA; rate limiting; breach checks |
