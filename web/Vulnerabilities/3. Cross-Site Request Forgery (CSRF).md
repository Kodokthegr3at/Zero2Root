## 1. 🎯 Definition

### 🇮🇩 Bahasa Indonesia
**CSRF** (Cross-Site Request Forgery) adalah kelas serangan di mana browser korban yang sudah terautentikasi dikelabui untuk mengirim **request state-changing** ke origin target, sementara aplikasi menerima request itu sebagai niat korban karena **kredensial ambient** (biasanya cookies) ikut terkirim otomatis.

Berbeda dengan XSS: CSRF umumnya **tidak** membutuhkan injeksi skrip ke origin target; yang disalahgunakan adalah perilaku browser mengirim cookie ke origin yang cocok.

### 🇬🇧 English
CSRF exploits the fact that browsers attach cookies (and sometimes other ambient credentials) to requests based on **destination URL**, not on whether the request was initiated by a first-party UI gesture the server can trust.

### 日本語
CSRFは、ブラウザが宛先オリジンへCookie等を自動添付する性質を悪用し、被害者の意図しない**状態変更リクエスト**を正当なセッションとして処理させる攻撃クラスです。

## 2. 📋 Preconditions (Conceptual)

CSRF “berhasil” secara konseptual jika semua ini benar:

1. **Relevant action** dapat dipicu oleh request HTTP yang dipalsukan (mis. `POST /transfer`).
2. **Session / auth** dikirim otomatis (cookie session, kadang HTTP Basic di warisan lama).
3. **Tidak ada rahasia request-specific** yang harus dibaca dari halaman origin (anti-CSRF token, custom header yang sulit dipalsu cross-site, dll.).
4. Korban berada di konteks di mana browser akan menyertakan kredensial (sedang login).

$$
\mathsf{Auth}(req) = \mathsf{CookieJar}(origin)
\quad\text{tanpa}\quad
\mathsf{Proof}(\text{user intent from same site})
$$

### 🇮🇩 Bahasa Indonesia
Method “aman” (`GET`) yang mengubah state melanggar spesifikasi HTTP dan memperbesar CSRF (link, `img`, prefetch). WAHH menekankan: **jangan gunakan GET untuk aksi berakibat**.

### 🇬🇧 English
Idempotent-safe methods should not mutate. If `GET` mutates, CSRF surface expands to every place a URL can be requested cross-site.

### 日本語
状態変更に`GET`を使うと、CSRFの攻撃面が大きく広がります。

## 3. 🧬 Root Cause — Ambient Authority

### 🇮🇩 Bahasa Indonesia
Server melihat:

```http
POST /api/password HTTP/1.1
Host: bank.example
Cookie: session=...
```

Server membuktikan *siapa* (session), tetapi tidak membuktikan *apakah UI sah origin yang sama yang memicu aksi*. CSRF mengisi celah **autentikasi ≠ otorisasi niat**.

*The Tangled Web* membahas bagaimana fitur browser (form lintas situs, redirects, plugin warisan) historis memperumit batas ini — modern mitigations: **SameSite cookies**, **CSRF tokens**, **Fetch metadata**.

### 🇬🇧 English
Fix CSRF by requiring a **unforgeable, session-bound proof** that the request came from your application’s own pages/flows — or by ensuring cookies are not sent on cross-site requests for sensitive actions.

## 4. 🔐 Anti-CSRF Token Models

### 4.1 Synchronizer token (preferred classic)

1. Server menghasilkan token acak $t \leftarrow \{0,1\}^{n}$ ($n \ge 128$ bit entropy recommended).  
2. Simpan $t$ di server-side session (atau mac’d server artifact).  
3. Sematkan $t$ di form / response untuk same-origin JS.  
4. Pada request state-changing, verifikasi $t_{\mathsf{req}} = t_{\mathsf{session}}$ dengan **compare konstan-waktu**.

$$
\mathsf{Verify}:\;
t_{\mathsf{req}} \stackrel{?}{=} t_{\mathsf{sess}}
\;\wedge\;
\mathsf{SessionValid}
$$

### 4.2 Double-submit cookie (stateless variant)

Token di cookie **dan** di parameter/header; server cek kesetaraan. Harus dipasangkan dengan pemahaman risiko subdomain / cookie injection. Prefer synchronizer atau framework built-ins when possible.

### 4.3 What tokens are *not*
- Bukan pengganti **authorization** (IDOR tetap harus dicek).  
- Bukan perlindungan jika ada **XSS** di origin yang sama (skrip dapat membaca token).  
- Harus unik per session (atau per form dengan rotasi yang benar).

## 5. 🍪 SameSite Cookies (RFC 6265bis practice)

| Value | Cross-site behavior (simplified) | Notes |
|:---|:---|:---|
| `Strict` | Cookie not sent on cross-site requests | Strong; can affect return navigations |
| `Lax` | Sent on top-level GET navigations; withheld on most cross-site POST | Common default baseline |
| `None` | Sent cross-site; **requires** `Secure` | Needed for some embeds; highest CSRF care |

### 🇮🇩 Bahasa Indonesia
`SameSite` mengurangi CSRF berbasis cookie tetapi **bukan** satu-satunya kontrol: browser lama, pola `SameSite=None`, dan beberapa alur lintas situs tetap membutuhkan token / design lain.

### 🇬🇧 English
Defense in depth: `SameSite=Lax/Strict` **plus** anti-CSRF tokens for state-changing endpoints, especially if you support older clients or cross-site deployments.

### 日本語
`SameSite`は有効ですが、状態変更APIにはCSRFトークン等の追加防御を推奨します。

## 6. ⚖️ Unsafe vs Safe Application Patterns

### 6.1 Unsafe — cookie session + no request secret

```http
POST /settings/email HTTP/1.1
Host: app.example
Cookie: session=abc
Content-Type: application/x-www-form-urlencoded

email=attacker@evil.example
```

Jika tidak ada token/SameSite memadai, form silang-situs dapat memicu aksi yang sama.

### 6.2 Safe — synchronizer token in form

```html
<form method="POST" action="/settings/email">
  <input type="hidden" name="csrf" value="{{ csrf_token }}">
  <input type="email" name="email">
  <button type="submit">Update</button>
</form>
```

```python
# SAFE sketch — framework comparison
if not hmac.compare_digest(session["csrf"], request.form["csrf"]):
    abort(403)
# then perform state change + authZ checks
```

### 6.3 Safe — custom header for same-origin XHR/fetch

SPA sering kirim header seperti `X-CSRF-Token` atau mengandalkan:

- Cookie `HttpOnly` session **plus** header token dari meta tag, atau  
- **Authorization: Bearer** di `localStorage`/`memory` (bukan cookie) — CSRF klasik lemah, tetapi XSS menjadi lebih kritis; pilih model ancaman dengan sadar.

## 7. 🛰️ JSON APIs, CORS & Fetch Metadata

### 🇮🇩 Bahasa Indonesia
Request `Content-Type: application/json` dari browser silang-situs sederhana lewat HTML form **tidak** trivially sama dengan form `application/x-www-form-urlencoded` (form tidak mudah mengirim JSON mentah). Namun jangan mengandalkan “JSON saja aman”:

- Flash/plugin warisan (historis) dan bug browser pernah mengubah asumsi.  
- Endpoint yang juga menerima form-urlencoded tetap rentan.  
- CORS yang salah (`Access-Control-Allow-Origin: *` + `Allow-Credentials: true` — kombinasi tidak valid/ berbahaya jika disalah-konfigurasi) dapat memperburuk masalah terkait credentialed cross-origin.

**Fetch Metadata** (`Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest`) memungkinkan server menolak request cross-site untuk sumber daya sensitif (Resource Isolation Policy).

### 🇬🇧 English
Recommended API posture:

1. State-changing methods require CSRF token **or** non-cookie auth proof.  
2. Reject unexpected `Sec-Fetch-Site` values for cookie-authenticated mutations where compatibility allows.  
3. CORS allowlist exact origins; never reflect arbitrary `Origin` with credentials.

### 日本語
Cookieセッションの変更系APIにはCSRF対策を明示し、CORSはオリジン許可リストで厳密に設定します。

## 8. 🛡️ Defense-in-Depth Stack

| Layer | Control |
|:---|:---|
| 1 | No state change via `GET` |
| 2 | Anti-CSRF tokens on mutations |
| 3 | `SameSite=Lax` or `Strict` on session cookies |
| 4 | `Secure` + `HttpOnly` cookie flags |
| 5 | Re-auth / step-up for high-risk actions (password, payout) |
| 6 | Fetch Metadata isolation |
| 7 | Origin checks for custom workflows |
| 8 | User notifications / transaction confirmations |

Login CSRF dan “logout CSRF” juga ada di literatur WAHH — pertimbangkan token pada POST login jika session fixation / login confusion relevan untuk ancaman Anda.

## 9. ✅ Developer Checklist

| Check | Pass criteria |
|:---|:---|
| Mutations | POST/PUT/PATCH/DELETE only |
| Token | Verified on server for cookie-auth mutations |
| Cookie | `Secure; HttpOnly; SameSite` set intentionally |
| CORS | Explicit origin allowlist; credentials reasoned |
| XSS | Treated as CSRF-bypass risk (tokens readable) |
| Tests | Automated test: missing/invalid token → 403 |
| Admin actions | Step-up authentication |

## 🔐 Security Notes — Threats & Defenses

| Threat pattern | Why | Defense |
|:---|:---|:---|
| Classic form CSRF | Cookies auto-sent | Token + SameSite |
| GET mutation | Easy cross-site fetch | Make GET read-only |
| JSON-only myth | Other content-types / past browser bugs | Explicit CSRF design |
| XSS on origin | Token theft / direct API calls | Fix XSS; HttpOnly still helps cookies |
| Mis-set CORS | Credentialed cross-origin reads/calls | Strict ACAO allowlist |
