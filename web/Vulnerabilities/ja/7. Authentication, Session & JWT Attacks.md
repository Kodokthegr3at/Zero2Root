## 1. 認証の目標

認証は主体の身元を確立する。セッション管理は、その紐付けをリクエストをまたいで維持する。認可は、その主体に何が許されるかを決める。WAHHがこれらを分けているのには理由がある。「弱いログイン」のバグと、「セッションが固定攻撃やハイジャックを受けやすい」バグは異なる失敗のクラスだからである。

古典的なセキュリティ特性は次の通りである。

| 特性 | 意味 |
|:---|:---|
| Authenticity | 資格情報の所有者だけがセッションを開ける |
| Integrity | トークンやセッションが検出されずに改変されることがない |
| Confidentiality | シークレットがXSS、ログ、Refererを通じて漏れない |
| Binding | セッションがそのコンテキスト(ユーザー、デバイスポリシー)に結び付いている |
| Revocation | 有効期限前にサーバーがアクセスを断てる |

パスワード、WebAuthn、OIDC、APIキーは資格情報のクラスである。セッションとJWTは、以前に認証が行われたことを証明するアーティファクトであり、そのクラフトグラフィーと保存方法の選択こそが、ログインフォーム自体よりもはるかに現代の失敗モードを支配している。

## 2. サーバー側セッションモデル

$$
\begin{aligned}
&\mathsf{Login}(\mathsf{creds}) \Rightarrow \mathsf{sid} \leftarrow \{0,1\}^{n},\quad n\ge 128 \\
&\mathsf{Store}[\mathsf{sid}] = \{\mathsf{uid},\, \mathsf{meta},\, \mathsf{exp}\} \\
&\mathsf{Request}:\ \mathsf{Cookie}(\mathsf{sid}) \Rightarrow \mathsf{lookup}(\mathsf{sid})
\end{aligned}
$$

このモデルの利点は、無効化が容易であること(`sid`のエントリを削除するだけでよい)と、クライアント側に保持されるペイロードが最小限であることである。

ここでのリスクのクラスは、攻撃キットとしてではなく概念として述べると、低エントロピーによる予測可能な`sid`、固定攻撃(攻撃者がログイン前に`sid`を設定する)、XSSやネットワークキャプチャによる窃取、権限変更時に再生成が行われないことなどである。

中核となる対策は、ログイン時にセッションIDを再生成すること、高いエントロピーを使うこと、ストアをサーバー側に保つこと、アイドルタイムアウトと絶対タイムアウトの両方を適用すること、そして重要な操作の前に再認証を要求することである。

## 3. Cookieのハードニング(『The Tangled Web』/ RFC 6265)

| 属性 | 役割 |
|:---|:---|
| `Secure` | HTTPSのみ |
| `HttpOnly` | JSから読み取れない |
| `SameSite` | CSRFを軽減する |
| `Path` / `Domain` | 範囲を狭く保つ |
| `__Host-`プレフィックス | ホストCookieへの追加制約 |

可能であればセッションを`localStorage`に置くのは避ける。XSSに直接盗まれてしまう。SPAが代わりにBearerトークンをメモリに保持する場合は、その選択が意味するCSRFとXSSのトレードオフを理解しておく。

## 4. JWTの構造: JWS compact serializationの数学

最も一般的に使われるJWT形式は、compact形式のJWS(RFC 7515)である。

$$
\texttt{JWT} \;=\; \mathsf{b64url}(H) \;\|\; \texttt{.} \;\|\; \mathsf{b64url}(P) \;\|\; \texttt{.} \;\|\; \mathsf{b64url}(S)
$$

ここで、

- $H$はヘッダーのJSON(アルゴリズム、タイプ、場合によっては`kid`)
- $P$はペイロード/claimsのJSON
- $S$はsigning inputに対する署名またはMACタグ

である。Signing inputは次の通り。

$$
\mathsf{SI} = \mathsf{b64url}(H) \,\|\, \texttt{.} \,\|\, \mathsf{b64url}(P)
$$

### 4.1 HMAC(alg `HS256`など)

$$
S = \mathsf{HMAC}\text{-}\mathsf{SHA256}_{k}(\mathsf{SI})
$$

共有鍵$k$を使う。検証では$S'$を再計算し、定数時間で$S$と比較する。

### 4.2 非対称(alg `RS256` / `ES256`など)

$$
\mathsf{Verify}(\mathsf{SI},\, S,\, pk) = \mathsf{true/false}
$$

署名は秘密鍵で作成され、公開鍵で検証される。これはHMACシークレットを共有しないマイクロサービス間で有用である。

### 4.3 Claims(ペイロード)

RFC 7519に登録されているclaimsには`iss`、`sub`、`aud`、`exp`、`nbf`、`iat`、`jti`がある。アプリケーションはその上にプライベートなclaimsを追加する。ヘッダーとペイロードはエンコードされているだけで暗号化されていないため、クライアントが読めるJWTに機微なシークレットを決して入れてはならない。claimsの機密性が必要な場合はJWEを使うか、データをサーバー側に保持する。

Base64urlは機密性を提供しない。

$$
\mathsf{b64url}^{-1}(P) = P_{\mathsf{json}}\quad\text{(誰でも読める)}
$$

## 5. 正しい検証のチェックリスト

安全な実装は次を満たす必要がある。

1. 3つの部分をすべてパースする。不正な形式は拒否する。
2. 許可された`kid`に基づいてトラストストアから鍵を選択する。ユーザーが指定したURLからJWKSを取得しない。
3. サーバー側でアルゴリズムの許可リストを強制する。例えば`ES256`のみ、または`RS256`のみ。
4. 検証済みの暗号APIで署名を検証する。失敗したら拒否する。
5. claimsを検証する。`exp`/`nbf`は小さなクロックスキュー$\delta$を許容する。`iss`と`aud`は完全一致させる。`sub`は認可にマッピングする。
6. 署名部分が欠落または空のトークンは拒否する。
7. HMACには定数時間比較を使う。
8. 完全なトークンを出力せずに失敗をログに記録する。

```python
# SAFE sketch — algorithm allowlist + verify + claims
# (library APIs differ; never roll your own crypto)
import jwt  # PyJWT-style illustration

PUBLIC_KEY = open("jwks_rsa_pub.pem").read()
ALLOWED = ["RS256"]

def accept_bearer(token: str) -> dict:
    return jwt.decode(
        token,
        PUBLIC_KEY,
        algorithms=ALLOWED,          # critical
        audience="api.myapp.example",
        issuer="https://idp.myapp.example/",
        options={"require": ["exp", "iat", "sub"]},
    )
```

## 6. アルゴリズム混同(概念のみ)

アルゴリズム混同は、歴史的には`alg=none`の扱いやHMACとRSAの検証の取り違えに関連しており、受信側がトークン自身の`alg`フィールドを信頼し、それに基づいて誤った検証経路を選んでしまうときに発生する。

概念的な例は次の通りである。

- トークンが`alg=HS256`を名乗っているが、検証側は公開鍵RSAをHMACのシークレットとして使ってしまう。ライブラリがそれを許してしまえば、公開鍵を知る攻撃者は有効なMACを偽造できる。
- トークンが空の署名で`alg=none`を名乗っている。「noneを受け入れる」古い検証実装は、どんなペイロードでも受け入れてしまう。

$$
\text{Safe rule:}\quad
\mathsf{alg} \in \mathcal{A}_{\mathsf{server}}
\;\ll\;
\mathsf{alg}\text{ from untrusted header alone}
$$

どのアルゴリズムを受け入れるかはサーバーが定める。ヘッダーはそのポリシーに一致しなければならないメタデータに過ぎず、ポリシーを決める権威ではない。

この文書は意図的に、攻撃の構築方法やクラッキングツールについては扱わない。検証実装を保守する場合は、偽造された`alg`の値が必ずfail closedになることを確認する回帰テストを追加する。

## 7. よくある設計上の欠陥(クラス)

| 欠陥のクラス | 説明 | 対策 |
|:---|:---|:---|
| 弱い、または推測可能なセッションID | 低エントロピー | CSPRNG、少なくとも128ビット |
| セッション固定攻撃 | ログイン前のSIDがログイン後もそのまま使われる | ログイン時にローテーションする |
| 無効化されない長寿命のJWT | 盗まれたトークンが`exp`まで有効なまま使える | 短い`exp`とリフレッシュのローテーション。必要なら`jti`の拒否リスト |
| JWT内の機微なデータ | トークンを持つ誰もがclaimsを読める | claimsを最小限にする。データはサーバー側に保持する |
| `kid`インジェクション/ヘッダーインジェクション | 攻撃者が信頼できない鍵を検証側に指定させる | 厳格なJWKSのpin。`kid`の値を許可リスト化する |
| `aud`/`iss`チェックの欠落 | サービスをまたいでトークンが受け入れられてしまう | 明示的なaudienceのチェック |
| decodeするだけの「検証」 | 暗号チェックなしのBase64デコード | 常に署名を検証する |
| リフレッシュトークンの悪用 | 窃取が長期のアクセスにつながる | ローテーション、バインド、再利用の検知 |
| パスワードの保存 | 高速なハッシュ関数 | Argon2id、bcrypt、またはscryptにpepperを加える |

パスワードログインについては、レート制限、ロックアウトやバックオフ、権限のあるアカウントに対するMFA、検証済みのKDF APIによるパスワードハッシュの定数時間比較を行う。

## 8. 危険なパターンと安全なパターン

```python
# UNSAFE — trusts alg from token; or decode without verify
jwt.decode(token, key, options={"verify_signature": False})  # never in prod
jwt.decode(token, key, algorithms=["HS256", "RS256", "none"])  # too broad
```

```python
# SAFE — narrow algorithms; verify aud/iss/exp
jwt.decode(token, key, algorithms=["ES256"], audience=AUD, issuer=ISS)
```

```python
# SAFE session sketch
sid = secrets.token_urlsafe(32)
redis.setex(f"sess:{sid}", TTL, user_id)
# On login success: destroy old sid, issue new
```

## 9. 多層防御スタック

1. 価値の高いアカウントにはフィッシング耐性のあるMFA(WebAuthn)。
2. どこでもHTTPSを使い、HSTSを設定する。
3. セッションCookie: `Secure; HttpOnly; SameSite`。
4. JWT: 短寿命のアクセストークン、ローテーションするリフレッシュトークン、許可リスト化されたアルゴリズム。
5. 侵害対応のためのサーバー側の無効化(`jti`またはセッションストア)。
6. パスワード変更、出金、APIキー発行に対するステップアップ認証。
7. セッションがCookieベースの場合はCSRFトークン(CSRFのノートを参照)。
8. XSS対策。セッション窃取はその延長線上にある。
9. 検証済みライブラリの上に構築された中央集権的な認証(OIDC)。自前の暗号プロトコルを発明しない。
10. 認証失敗やリフレッシュトークンの再利用に対する監査ログ。

### Opaqueセッション対JWT

| | サーバーのセッションID | JWTアクセストークン |
|:---|:---|:---|
| 無効化 | 容易 | インフラが必要 |
| サイズ | 小さなCookie | より大きい |
| 検証時の暗号処理 | ルックアップ | 署名検証 |
| ユースケース | 古典的なWebアプリ | API / 分散した読み手 |

よくあるハイブリッド構成は、ブラウザにはopaqueなセッション、mTLSを使うサービス間呼び出しには短寿命のJWTを使うものである。

## 10. 開発者向けチェックリスト

| チェック項目 | 合格 |
|:---|:---|
| セッションIDのエントロピー | CSPRNG、少なくとも128ビット |
| ログイン時のSIDローテーション | あり |
| Cookieフラグ | `Secure`、`HttpOnly`、`SameSite`がすべて設定されている |
| JWTの検証 | 署名と`iss`/`aud`/`exp` |
| アルゴリズムポリシー | サーバー側の許可リスト。`none`なし |
| 鍵 | 秘密鍵はKMSまたはHSMに。ローテーション済み |
| リフレッシュ | ローテーションと再利用検知 |
| パスワード | 現代的なKDF。平文でログに残さない |
| テスト | アルゴリズム混同のケースがfail closedになる |

```
 AuthN success
     │
     ├─► create server session (opaque sid) ─► Set-Cookie hardened
     │
     └─► issue JWS access token
              SI = b64(H).b64(P)
              S  = Sign_k(SI) or MAC_k(SI)
              verify with allowlisted alg + claims
```

## セキュリティノート: 脅威と対策

| 脅威クラス | 理由 | 対策 |
|:---|:---|:---|
| 盗まれたセッションCookie | XSSまたはマルウェア | `HttpOnly`。CSP。短いTTL |
| 偽造されたJWT | 壊れた検証、またはアルゴリズム混同 | 許可リストと正しい検証 |
| 長寿命のBearerトークンの漏洩 | ログ、Referer、XSS | 短い`exp`。URLへのトークン埋め込みを避ける |
| 固定攻撃 | 認証前にSIDが設定される | ログイン時に再生成する |
| クレデンシャルスタッフィング | 使い回されたパスワード | MFA。レート制限。漏洩チェック |
