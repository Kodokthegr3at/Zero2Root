## 1. 定義

SSRFは、サーバー側のアプリケーションが攻撃者の影響を受けるリファレンス(URL、ホスト、パス)に基づいてリソースを取得するときに発生する。これによりサーバーは、本来公開されるべきでない対象、つまり内部サービス、localhost、リンクローカルアドレス、クラウドメタデータなどに到達してしまうconfused deputyになる。

するとリクエストは攻撃者からではなく、ネットワーク内で信頼されているサーバー自身のIPから送られることになる。

被害者のブラウザがリクエストを送るCSRFとは異なり、SSRFではアプリケーション自身のサーバーがリクエストを送る。

SSRFが危険なのは、ファイアウォールや「内部専用」のサービスがアプリケーション自身のサブネットをデフォルトで信頼していることが多いためである。根底にあるバグのクラスは、サーバー側のアウトバウンドリクエストに対する制限が不十分であることである。

## 2. 影響のクラス(概念)

| クラス | 説明 | 対策の重点 |
|:---|:---|:---|
| 内部偵察 | VPC内のポートやサービスに触れる | egress許可リスト。ネットワークポリシー |
| ローカルサービスの悪用 | `localhost`の管理ポートやローカルエージェントを叩く | ループバックをブロックする。unixソケットをHTTP URL経由で公開しない |
| クラウド認証情報の漏洩 | インスタンスメタデータのエンドポイントに到達する | IMDSv2 / hop limit。メタデータエンドポイントをファイアウォールで保護する |
| ファイル/ハンドラスキーム | ライブラリが許容する場合の危険なURLスキーム | スキームの許可リスト、`https`のみ |
| レスポンスの悪用 | アプリが内部のレスポンスボディを攻撃者へ中継してしまう | 生のフェッチ結果を反映しない。サイズ制限を強制する |
| Blind SSRF | 観測できるのは副作用のみ(DNS、タイミング、webhook) | 同じURL制御。egressを監視する |

一部のライブラリは歴史的に非HTTPスキームをサポートしてきた。この文書ではそうしたスキームの攻撃チェーンは扱わない。理解すべき要点は、スキームとパーサーの両方を制限することである。

## 3. 根本原因

SSRFを引き起こしやすい製品機能は次の通りである。

- URLプレビュー、リンク展開、サムネイル生成
- Webhookテスター、あるいは「このコールバックをfetchする」機能
- URLからのインポート、PDF生成、ドキュメント変換
- ユーザー制御のURLを使うSSOやメタデータディスカバリ
- 任意のオリジンから取得する画像プロキシやCDN

根本原因は、「HTTPクライアントライブラリはダウンロードするだけだから」という理由でURL文字列を安全だと見なしてしまうことにある。安全性は宛先ポリシーに依存するのであって、「HTTPSを使っている」ことには依存しない。

## 4. URL検証の落とし穴

素朴な検証は、異なるレイヤーがURLを別様に解釈することでしばしば失敗する。

### 4.1 ホスト名の許可リストとIPの許可リスト

文字列`127.0.0.1`をブロックするだけでは、次の場合に不十分である。

- チェックが通過した後にDNSが内部IPを返すことがある。これはDNS rebinding、つまりresolve-check-resolveのTOCTOUである。
- 10進数、16進数、IPv6マップ形式がループバックアドレスをエンコードし得る。
- 内部のホスト名エイリアスが、別の名前でブロック対象のターゲットを指すことがある。

安全なパターンは、DNSを解決し、得られたIPアドレスがポリシーの許可リストに含まれることを確認し、その検証済み(pinされた)IPにのみ、短いTTLで接続し、元のホスト名を再度信用するのではなくリダイレクトのたびに再検証することである。

### 4.2 リダイレクト

`http://allowed.example`が`http://169.254.169.254/`へ302リダイレクトすることがある。クライアントが再検証なしにリダイレクトに従えば、その制御は迂回される。

### 4.3 パーサーの食い違い

言語AのURLライブラリは、言語Bのパーサーと常に一致するとは限らない。『The Tangled Web』はまさにこの種のパーサーの不一致を強調している。システムの一方が「安全な」ホストと見なしていても、もう一方は別のホストに接続していることがある。

### 4.4 形式的なポリシーの構成

```text
1. スキームは https でなければならない
2. 名前解決したIPが公開用の許可リストに含まれていなければならない
3. 名前解決したIPが、ループバック、リンクローカル、RFC1918のプライベート、
   CGNAT、クラウドのメタデータアドレスであってはならない
```

巨大なブロックリストだけに頼るのではなく、宛先(既知のパートナーホスト)に対するポジティブな許可リストを優先する。

## 5. 危険なパターンと安全なパターン

### 5.1 危険なパターン

```python
# UNSAFE — attacker controls URL; server fetches anything reachable
import requests
url = request.args["url"]
resp = requests.get(url, timeout=3)
return resp.text  # may leak internal responses
```

### 5.2 より安全な構成: スキーム許可リスト、プライベートIPのブロック、リダイレクトなし、サイズ上限

```python
# HARDENED SKETCH — still review for DNS rebinding in production
from urllib.parse import urlparse
import ipaddress, socket, requests

ALLOWED_PORTS = {443}
BLOCK_NETS = [
    ipaddress.ip_network("0.0.0.0/8"),
    ipaddress.ip_network("10.0.0.0/8"),
    ipaddress.ip_network("127.0.0.0/8"),
    ipaddress.ip_network("169.254.0.0/16"),
    ipaddress.ip_network("172.16.0.0/12"),
    ipaddress.ip_network("192.168.0.0/16"),
    ipaddress.ip_network("::1/128"),
    ipaddress.ip_network("fc00::/7"),
    ipaddress.ip_network("fe80::/10"),
]

def ip_blocked(ip: str) -> bool:
    addr = ipaddress.ip_address(ip)
    return any(addr in net for net in BLOCK_NETS)

def safe_fetch(user_url: str) -> bytes:
    u = urlparse(user_url)
    if u.scheme != "https" or not u.hostname:
        raise ValueError("scheme")
    port = u.port or 443
    if port not in ALLOWED_PORTS:
        raise ValueError("port")
    infos = socket.getaddrinfo(u.hostname, port, type=socket.SOCK_STREAM)
    ips = {info[4][0] for info in infos}
    if not ips or any(ip_blocked(ip) for ip in ips):
        raise ValueError("ip")
    # Production: connect via pinned IP + SNI/Host carefully; re-check redirects
    r = requests.get(user_url, timeout=3, allow_redirects=False, stream=True)
    return r.content[: 200_000]
```

多くの製品にとってより安全な道は、生のURLをまったく受け取らないことである。代わりに、サーバーが固定URLへマッピングする内部の`resource_id`を受け取る。

## 6. クラウドメタデータのハードニング(概念)

インスタンスメタデータサービス(IMDS)は、クラウドのワークロードに一時的な認証情報を配布する。SSRFがIMDSに到達することは、現代のクラウドインシデント対応において最も影響の大きいパターンの一つである。

| 対策 | 目的 |
|:---|:---|
| IMDSv2(セッション指向) | 基本的なSSRFのGETでは容易に再現できないメソッド/ヘッダーのホップを要求する |
| Hop limit / ファイアウォール | コンテナが意図せずメタデータに到達することを防ぐ |
| 最小権限のロール | 盗まれた認証情報の被害範囲を限定する |
| 生のメタデータプロキシをしない | アプリはユーザー入力に由来するメタデータURLを決してfetchしない |

この文書はメタデータへの攻撃レシピを提供するものではなく、あくまでハードニングの側面のみを扱う。

## 7. 多層防御スタック

1. 間接参照を優先する。自由形式のURLではなくIDを渡す。
2. スキームの許可リスト、通常は`https`のみ。
3. 既知のパートナーに対する宛先の許可リスト。
4. DNS解決後にプライベート、リンクローカル、メタデータの範囲をブロックする。IPをpinする。
5. リダイレクトを無効化するか、すべてのホップで再検証する。
6. ネットワークegressポリシー。アプリのサブネットが機微なセグメントに到達できないようにする。
7. DLPまたは許可リストを強制する専用のアウトバウンドプロキシ。
8. 内部の生のレスポンスボディをクライアントに返さない。
9. タイムアウト、サイズ制限、Content-Typeの許可リスト。
10. 機能自体への認可。誰がfetchを起動できるかを制御する。

WAHHは「このアプリケーションがどこからアウトバウンド接続を行っているか」という攻撃面をマッピングすることを強調している。PDF生成、ffmpegのラッパー、webhookの配信など、自明でないものも含め、コードベース全体のすべてのHTTPクライアントを棚卸しする。

ホスト名の文字列一致だけをフィルタし、リダイレクトとDNSのTOCTOUウィンドウに対応しないSSRFの修正は脆いままである。ホスト名の文字列一致だけでは不十分であり、DNSの再解決、リダイレクト、スキームをまとめて制御する必要がある。

## 8. 許可された検出のシグナル

- `requests.get(user`、`HttpClient`、`curl_exec`、`file_get_contents("http`のようなパターンのコード検索。
- Egressの監視: アプリのpodが`169.254.169.254`やRFC1918の範囲へ予期せず接続していないかを監視する。
- ループバックアドレスを拒否し、プライベートIPへのリダイレクトを拒否し、非HTTPSスキームを拒否するユニットテスト。

```bash
# Lab only: verify YOUR egress firewall denies metadata IP from app netns
# (ops check — not an exploit)
curl -sS -o /dev/null -w "%{http_code}\n" --connect-timeout 2 https://example.com/
```

## 9. 開発者向けチェックリスト

| チェック項目 | 合格 |
|:---|:---|
| ユーザー指定のURLは本当に必要か | IDを優先する |
| スキーム | `https`のみ |
| リダイレクト | オフ、または再検証済み |
| IPポリシー | プライベート、リンクローカル、メタデータの範囲をブロック |
| DNS | TOCTOUを考慮。IPをpin |
| レスポンス | 生のまま反映しない。上限あり |
| Egress | ネットワークポリシーがdeny-by-default |
| クラウド | IMDSv2プラス最小限のロール |

```
 Client URL ─► Policy gate ─► Egress proxy ─► Allowlisted targets only
                 │ reject
                 └── private / metadata / bad scheme
```

## セキュリティノート: 脅威と対策

| 脅威パターン | メカニズム | 対策 |
|:---|:---|:---|
| 内部ポートへの接触 | サーバーがVPC内のサービスに到達する | Egress許可リスト |
| メタデータへのアクセス | リンクローカルのIMDSに到達可能 | IMDSv2。ブロックする。ユーザー指定URLを使わない |
| リダイレクトによる迂回 | 内部を指す302 | `allow_redirects=False`と再検証 |
| DNS rebinding | チェック後にIPが変わる | IPをpinする。短いTTL。再検証する |
| スキームの密輸 | 非HTTPハンドラが受け入れられる | スキームの許可リスト |
