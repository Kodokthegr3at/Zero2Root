## 1. 定義

CSRF(Cross-Site Request Forgery)は、すでに認証済みの被害者のブラウザが騙されて、状態を変更するリクエストをターゲットのオリジンへ送ってしまう攻撃クラスである。アプリケーションはそのリクエストを被害者の意図として受け入れてしまう。理由は、Cookieなどのambient(周辺的な)認証情報が自動的に一緒に送られるためである。

XSSと異なり、CSRFは一般にターゲットのオリジンへスクリプトを注入する必要がない。悪用されるのは、リクエストの宛先に一致するオリジンへブラウザが自動的にCookieを送るという、ブラウザ自体の挙動である。

CSRFは、ブラウザがCookieや場合によっては他のambientな認証情報を、リクエストが宛先URLに基づいて添付するという性質を悪用する。サーバーが信頼できる正規のUI操作によってリクエストが起動されたかどうかは考慮されない。

---

## 2. 成立条件(概念)

概念的には、次のすべてが成り立つときにCSRFは成立する。

1. 偽造されたHTTPリクエスト(例: `POST /transfer`)によって、意味のあるアクションを引き起こせる。
2. セッションまたは認証情報が自動的に送信される(セッションCookie、あるいはまれにレガシーなHTTP Basic)。
3. オリジン自身のページから読み取らなければならないリクエスト固有のシークレットが存在しない(対CSRFトークン、クロスサイトから偽造しにくいカスタムヘッダーなど)。
4. 被害者がブラウザにそれらの認証情報を含めさせる状況、つまりログイン状態にある。

$$
\mathsf{Auth}(req) = \mathsf{CookieJar}(origin)
\quad\text{without}\quad
\mathsf{Proof}(\text{user intent from same site})
$$

状態を変更する「安全な」メソッド(`GET`)はHTTP仕様に反しており、CSRFの攻撃面を広げる。リンク、`img`タグ、プリフェッチのいずれもそれを引き起こせるからである。WAHHの指摘は明確である。影響のあるアクションに決してGETを使ってはならない。冪等で安全なメソッドは何も変更してはならない。`GET`が状態を変更するなら、CSRFの攻撃面はクロスサイトでURLをリクエストできるあらゆる場所に広がる。

## 3. 根本原因: ambient authority

サーバーが目にするのは次のようなものである。

```http
POST /api/password HTTP/1.1
Host: bank.example
Cookie: session=...
```

サーバーはリクエストを送っているのが誰かを証明する(セッションによって)。しかし、正当なsame-originのUIが実際にそのアクションを起動したかどうかは証明していない。CSRFはこの隙間に存在する。認証は意図の認可と同じものではない。

『The Tangled Web』は、ブラウザの機能(クロスサイトのフォーム、リダイレクト、レガシーなプラグイン)がこの境界を歴史的にどう曖昧にしてきたかを論じている。現代的な対策はSameSite Cookie、CSRFトークン、Fetch Metadataである。

CSRFを修正するには、リクエストが自アプリケーション自身のページやフローから来たことを示す、偽造不可能でセッションに紐づく証明を要求するか、機微なアクションについてはクロスサイトリクエストでCookieが送られないようにする。

## 4. 対CSRFトークンモデル

### 4.1 Synchronizerトークン(古典的に推奨されるモデル)

1. サーバーはランダムなトークン$t \leftarrow \{0,1\}^{n}$を生成する(128ビット以上のエントロピーが推奨される)。
2. $t$をサーバー側のセッション、またはMACが付与されたサーバー側のアーティファクトに保存する。
3. $t$をフォームに埋め込むか、レスポンスを通じてsame-originのJSに公開する。
4. 状態を変更するリクエストでは、定数時間比較を使って$t_{\mathsf{req}} = t_{\mathsf{session}}$を検証する。

$$
\mathsf{Verify}:\;
t_{\mathsf{req}} \stackrel{?}{=} t_{\mathsf{sess}}
\;\wedge\;
\mathsf{SessionValid}
$$

### 4.2 Double-submit cookie(ステートレスな変種)

トークンはCookieとパラメータまたはヘッダーの両方に存在し、サーバーは両者が一致することを確認する。これはサブドメインやCookieインジェクションのリスクを明確に理解した上で組み合わせる必要がある。可能な限り、synchronizerパターンかフレームワーク組み込みのCSRF保護を優先する。

### 4.3 トークンが「ではないもの」

- 認可の代替ではない。IDORのチェックは依然として必要である。
- 同一オリジンでのXSSに対する保護ではない。そこで動くスクリプトはトークンをそのまま読み取れる。
- トークンはセッションごとに一意であるか、正しいローテーションを伴うフォームごとの一意性が必要である。

## 5. SameSite Cookie(RFC 6265bisの実践)

| 値 | クロスサイトでの挙動(簡略化) | 備考 |
|:---|:---|:---|
| `Strict` | クロスサイトリクエストではCookieが送られない | 強力。戻りのナビゲーションに影響することがある |
| `Lax` | トップレベルのGETナビゲーションでは送られる。ほとんどのクロスサイトPOSTでは保留される | 一般的なデフォルトのベースライン |
| `None` | クロスサイトでも送られる。`Secure`が必須 | 一部の埋め込みに必要。CSRFに対して最も注意が必要 |

`SameSite`はCookieベースのCSRFを減らすが、それだけがすべてではない。古いブラウザ、`SameSite=None`の運用、一部のクロスサイトフローには依然としてトークンや別の設計が必要になる。

多層防御とは、`SameSite=Lax`または`Strict`に加えて、状態を変更するエンドポイントに対CSRFトークンを組み合わせることを意味する。古いクライアントやクロスサイトのデプロイをサポートする場合は特にそうである。

## 6. アプリケーションの危険なパターンと安全なパターン

### 6.1 危険: リクエスト固有のシークレットのないセッションCookie

```http
POST /settings/email HTTP/1.1
Host: app.example
Cookie: session=abc
Content-Type: application/x-www-form-urlencoded

email=attacker@evil.example
```

十分なトークンやSameSiteの設定がなければ、クロスサイトのフォームが同じアクションを引き起こせる。

### 6.2 安全: フォーム内のsynchronizerトークン

```html
<form method="POST" action="/settings/email">
  <input type="hidden" name="csrf" value="{{ csrf_token }}">
  <input type="email" name="email">
  <button type="submit">Update</button>
</form>
```

```python
# SAFE sketch — framework comparison
if not hmac.compare_digest(session["csrf"], request.form["csrf"]):
    abort(403)
# then perform state change + authZ checks
```

### 6.3 安全: same-originのXHR/fetch向けカスタムヘッダー

SPAはしばしば`X-CSRF-Token`のようなヘッダーを送るか、次のいずれかのパターンに依拠する。

- `HttpOnly`のセッションCookeに加えて、metaタグから取得したトークンヘッダー、あるいは
- Cookieの代わりに`localStorage`やメモリに保持する`Authorization: Bearer`の値。このモデルでは古典的なCSRFは弱まるが、その分XSSがはるかに重大になるため、この脅威モデルは意識的に選ぶ必要がある。

## 7. JSON API、CORS、Fetch Metadata

素のクロスサイトHTMLフォームからの`Content-Type: application/json`リクエストは、`application/x-www-form-urlencoded`ほど簡単には成立しない。素のHTMLフォームは生のJSONを簡単には送れないからである。ただし「JSONだから安全」をルールにしてはならない。

- レガシーなプラグインや過去のブラウザのバグが、この前提を変えたことがある。
- form-urlencodedの入力も受け付けるエンドポイントは、JSON経由の話とは無関係に依然として脆弱である。
- 誤設定されたCORS、例えば`Access-Control-Allow-Origin: *`と`Allow-Credentials: true`の組み合わせ(実際に許可されてしまえば無効かつ危険な組み合わせ)は、認証情報を伴うクロスオリジンの問題を悪化させ得る。

Fetch Metadataヘッダー(`Sec-Fetch-Site`、`Sec-Fetch-Mode`、`Sec-Fetch-Dest`)を使うと、サーバーは機微なリソースに対するクロスサイトリクエストを拒否できる。このパターンはリソース分離ポリシーと呼ばれることが多い。

推奨されるAPIの姿勢は次の通りである。

1. 状態を変更するメソッドは、CSRFトークンかCookie以外の認証証明のいずれかを要求する。
2. 互換性が許す範囲で、Cookie認証による変更操作に対して想定外の`Sec-Fetch-Site`の値を拒否する。
3. CORSは厳密なオリジン許可リストを使い、任意の`Origin`を認証情報付きで反映してはならない。

## 8. 多層防御スタック

| 層 | 対策 |
|:---|:---|
| 1 | `GET`による状態変更を行わない |
| 2 | 変更操作に対CSRFトークンを付与する |
| 3 | セッションCookieに`SameSite=Lax`または`Strict`を設定する |
| 4 | `Secure` + `HttpOnly`のCookieフラグ |
| 5 | リスクの高いアクション(パスワード変更、出金など)には再認証やステップアップ認証を要求する |
| 6 | Fetch Metadataによる分離 |
| 7 | カスタムワークフローに対するorigin確認 |
| 8 | ユーザーへの通知や取引確認 |

Login CSRFとログアウトCSRFもWAHHの文献に登場する。セッション固定攻撃やログインの混同が自分の脅威モデルに関係する場合は、ログインのPOST自体にもトークンを検討する。

## 9. 開発者向けチェックリスト

| チェック項目 | 合格基準 |
|:---|:---|
| 変更操作 | POST/PUT/PATCH/DELETEのみ |
| トークン | Cookie認証による変更操作でサーバー側で検証されている |
| Cookie | `Secure; HttpOnly; SameSite`が意図的に設定されている |
| CORS | 明示的なorigin許可リスト。認証情報の使用は意識的な判断による |
| XSS | トークンが読み取り可能になるため、CSRFバイパスのリスクとして扱う |
| テスト | トークンが欠落または無効な場合に403が返ることを自動テストで確認している |
| 管理操作 | ステップアップ認証が必須 |

## セキュリティノート: 脅威と対策

| 脅威パターン | 理由 | 対策 |
|:---|:---|:---|
| 古典的なフォームCSRF | Cookieが自動送信される | トークン + SameSite |
| GETによる変更 | クロスサイトから簡単に引き起こせる | GETを読み取り専用にする |
| 「JSONだけなら安全」という誤解 | 他のContent-Type、または過去のブラウザのバグ | 明示的なCSRF設計 |
| オリジン上のXSS | トークン窃取、またはAPIの直接呼び出し | XSSそのものを修正する。HttpOnlyはCookie自体の保護には引き続き有効 |
| 誤設定されたCORS | 認証情報を伴うクロスオリジンの読み取りや呼び出し | 厳格なACAO許可リスト |
