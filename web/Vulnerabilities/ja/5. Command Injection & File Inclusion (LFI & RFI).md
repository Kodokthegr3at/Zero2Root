## 1. 共通の根本原因: コードとデータの混在

コマンドインジェクションとファイルインクルージョンはSQLインジェクションの兄弟であり、WAHHはこの一族全体を「インタプリタ言語への注入」と呼んでいる。攻撃者の影響を受けた文字列が、シェル、PHPの`include`、テンプレートエンジンなど、これから解釈されるものに組み込まれてしまう。

問題はこうだ。u をコマンド文字列にそのままつなげると、インタプリタが u の一部を新しいコマンドとして読んでしまうことがある。u を単なる値(リテラル)として渡せば、u はデータのままだ。

uがインタプリタの解釈のされ方を変えられるとき、データはコードになるか、意図されたものとは異なる範囲のパスになる。

主要な対策は常に構造的なものである。シェルを起動しないこと、任意のパスをincludeしないこと、文字列を組み立ててインタプリタに渡す代わりに、引数ベクトルや固定された許可リスト済みのリソースを受け取るAPIを使うことである。

## 2. OSコマンドインジェクション(CWE-78)

### 2.1 発生する場面

外部ツールを呼び出す機能ならどこにでも現れる。ImageMagick、`ping`、コンバータ、gitのラッパー、バックアップスクリプト、あるいは管理用の「diagnose hostname」ユーティリティなどである。

### 2.2 危険なパターン

シェルのメタ文字は、概念的にはコマンドの区切り、置換、パイプであり、意図した一つのコマンドを複数のコマンドに変えてしまう。この文書ではペイロードのカタログは示さない。要点はリスクのクラスを理解することである。

### 2.3 安全なアプローチ: argv配列、シェルを使わない

```python
# UNSAFE — shell=True + user input
os.system("ping -c 1 " + host)
subprocess.call("convert " + user_path + " out.png", shell=True)

# SAFE — no shell; fixed executable; validate host/path first
subprocess.run(
    ["/usr/bin/ping", "-c", "1", "--", host],
    check=False,
    capture_output=True,
    timeout=3,
)
# host must still match allowlist regex (e.g. DNS label rules)
```

```php
// UNSAFE
shell_exec("dig " . $_GET["d"]);

// SAFER — avoid shell; use library or escapeshellarg *only* if shell unavoidable
// Best: do not expose dig; use PHP DNS APIs / internal service
```

シェルが本当に避けられない場合は`escapeshellarg`やプラットフォームごとの同等機能を使うが、それでもargv配列より劣ることを理解しておく。

### 2.4 追加の対策

- 自由形式の文字列ではなく、既知のジョブのenumとして引数を許可リスト化する。
- 権限を落とす。seccompやAppArmorを適用する。コンテナには不要なバイナリを置かない。
- デバッグ用のユーティリティは本番イメージから取り除く。

## 3. Local File Inclusion(LFI)

### 3.1 定義

アプリケーションが入力に基づいてローカルファイルを`include`、`require`、または読み込む対象として選ぶ結果、意図した範囲外のファイルを読み込んでしまう、あるいは言語によってはコードとして実行してしまう。

概念的なアンチパターンは次の通りである。

```php
// UNSAFE sketch — user controls path segment
include($_GET["page"] . ".php");
```

### 3.2 なぜ危険か

| 結果 | メカニズム(クラス) |
|:---|:---|
| 情報漏洩 | 設定、鍵、ログの読み取り |
| コード実行 | 誤設定時に実行可能なPHPになってしまうアップロードファイルやログのinclude |
| 認証バイパス | 想定外の「ページ」のinclude |

「log poisoningからincludeへ」という連鎖は同じクラスの発展形であり、対策は変わらない。ユーザー指定のパスをincludeしないこと、そして後で実行されるファイルとしてユーザーのコンテンツを保存しないことである。

### 3.3 安全なパターン: 許可リストマップ

```php
// SAFE — explicit map, no filesystem path from user
$pages = [
  "home" => __DIR__ . "/pages/home.php",
  "about" => __DIR__ . "/pages/about.php",
];
$key = $_GET["page"] ?? "home";
if (!isset($pages[$key])) {
  http_response_code(404);
  exit;
}
include $pages[$key];
```

## 4. Remote File Inclusion(RFI)

RFIは、言語や設定がそれを許す場合(歴史的にはPHPの`allow_url_include`)に、リモートリソース(URL)をincludeまたは実行することである。これはURLの信頼問題とコード実行を組み合わせたものになる。

現代の多くのデフォルト設定ではリモートincludeが無効化されているが、思い込むのではなく確認すること。URLを受け付けるincludeはそもそも使わないのが望ましい。リモートのコンテンツが必要なら、SSRF対策を適用した上でデータとして取得し、コードとして`include`することは決してしない。

| 対策 | RFIとの関連 |
|:---|:---|
| 言語ランタイムでURL includeを無効化する | 重要 |
| ユーザー制御のincludeターゲットを持たない | 重要 |
| ネットワークegressの拒否 | 多層防御 |

## 5. パストラバーサルとの関係(CWE-22)

パストラバーサル、つまり`../`型のトリックのクラスは、LFIやファイルダウンロード機能にしばしば伴う。

確認すべきこと: `..` やシンボリックリンクを解決した後の最終的なパスが、まだベースフォルダの中にあるか。なければ拒否する。

安全なファイル読み取りのパターンは次の通りである。

```python
from pathlib import Path

BASE = Path("/var/app/static").resolve()

def read_user_file(name: str) -> bytes:
    # name: allowlist characters only, e.g. [A-Za-z0-9._-]+
    candidate = (BASE / name).resolve()
    if not candidate.is_relative_to(BASE):  # py3.9+: use try relative_to
        raise PermissionError("escape")
    return candidate.read_bytes()
```

リテラルな文字列`../`だけをフィルタすることに頼ってはならない。エンコーディングのトリック、ネストした表現、絶対パスはいずれも素朴なフィルタを回避できる。

## 6. 対比のまとめ

| パターン | 危険な発想 | 安全な発想 |
|:---|:---|:---|
| コマンド | `shell=True`と文字列連結 | `argv`リストと許可リスト |
| Include | `include($user)` | キーから固定パスへのマップ |
| ダウンロード | `open("/data/"+user)` | `resolve()`と`is_relative_to` |
| テンプレート | ユーザーがテンプレートパスを選ぶ | テンプレート名の許可リスト |
| RFI | URLのinclude | 無効化する。リモートのコードを決してincludeしない |

## 7. 多層防御スタック

### コマンドインジェクション

1. OSツールをシェル経由で呼び出すより、ネイティブライブラリを優先する。
2. `subprocess`や`execve`のargv配列を使う。ユーザーデータとともに`/bin/sh -c`を決して使わない。
3. 許可リスト(文字集合と長さ)で検証する。
4. 最小権限とサンドボックス。
5. 攻撃者が制御できるコマンド文字列ではなく、終了コードを構造化ログとして記録する。

### ファイルインクルージョンとトラバーサル

1. リソースIDを許可リスト化する。
2. パスを正規化し、ベースディレクトリのjailを強制する。
3. データストレージと実行可能なコードのルートディレクトリを分離する。
4. アップロードをWebルートの外に保存し、制御されたハンドラ経由で配信する。
5. 言語のリモートinclude機能を無効化する。必要に応じて`open_basedir`やchrootでハードニングする。
6. PHPでは、アップロードされたファイルを決して`include`しない。データを配信するだけなら`readfile`を使う。

『The Tangled Web』がここで関係するのは、パスとURLのパースがレイヤー間(プロキシ、アプリ、ファイルシステム)でしばしば食い違うからである。常にサーバー側の単一の信頼点で正規化する。

WAHHはこれらをOSおよび言語ランタイムへの注入として扱う。可変パスを受け取る`exec`、`system`、`popen`、`include`、`require`、`file_get_contents`の呼び出しをすべてレビューする。

## 8. 開発者向けチェックリスト

| 領域 | チェック |
|:---|:---|
| シェル | リクエストデータと共に`shell=True` / `system`を使わない |
| バイナリ | バイナリへのフルパス。固定されたフラグ |
| Include | マップまたは許可リストのみ |
| ファイル | `resolve()`とベースへの封じ込め |
| アップロード | 実行不可能な場所に保存 |
| 設定 | リモートincludeが無効化されている |
| テスト | 試みられたescapeパスがユニットテストで拒否される |
| SAST | コマンド実行と動的includeをカバーするルール |

```
 User input          Safe control plane
 ──────────          ──────────────────
  host/name    ──►   allowlist / map
  path piece   ──►   jail under BASE
  "command"    ──►   fixed argv, no shell
  remote URL   ──►   never include-as-code
```

## セキュリティノート: 脅威と対策

| 脅威クラス | 根本原因 | 対策 |
|:---|:---|:---|
| コマンドインジェクション | シェルの文法 | Argvと許可リスト |
| LFI | 動的なincludeまたはread | IDマップとjail |
| RFI | リモートコンテンツをコードとして扱う | 無効化する。URLを決してincludeしない |
| トラバーサル | 相対パスによるescape | 正規化による封じ込め |
| アップロード+includeの連鎖 | 実行可能なアップロードディレクトリ | 保存と実行を分離する |
