## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| SQL | アプリがデータベースに問い合わせるために使う言語 |
| SQLインジェクション | アプリをだまし、攻撃者の制御するSQLを実行させること |
| クエリ | データベースに送るコマンド |
| プリペアドステートメント | データをコードと分けて送るクエリ — 主な対策 |
| パラメータバインディング | プレースホルダに、DBがコードでなくデータとして扱う値を入れること |
| ブラインドSQLi | 直接の出力ではなく、挙動から結果を推測するインジェクション |
| WAF | Web Application Firewall。アプリの前段のフィルタ(多層防御) |

## 1. 脅威モデル、SQLiが重要な理由

SQLインジェクションは、信頼できないデータがSQL文の構造そのものに影響を与えるときに発生する。単なるリテラル値への影響ではない。WAHH(9章)は、データベースをアプリケーションの信頼の源として扱う。認証情報、個人情報、認可状態、監査ログがそこに集まる。攻撃者がSQL構文を制御できるとき、典型的な影響は次のようになる。

| 影響のクラス | 影響の例 |
|:---|:---|
| 機密性 | 認可範囲外の行やテーブルの読み取り |
| 完全性 | 業務意図の範囲外でのUPDATE/DELETE |
| 可用性 | 高コストなクエリ、ロック、truncateによるロジックレベルのDoS |
| 権限 | DBアカウントの権限が過剰な場合の危険なDB関数の悪用 |
| 横移動 | DBの機能と設定が許す場合に限りOSへピボットする。安全なデフォルトではない |

SQLiはCWE-89であり、OWASP A03:2021の*Injection*に分類される。

SQLエンジンに到達するすべての境界(HTTPパラメータ、ヘッダー、Cookie、JSONフィールド、ファイル名、メッセージキューのペイロード)を信頼できないものとして扱う。脆弱性の本質はデータベースを持つこと自体ではなく、コードとデータを一つの文字列に混ぜることにある。

## 2. 根本原因: クエリの構築

連結によってクエリを構築する場合を考える。

```text
Q = T₀ + u₁ + T₁ + u₂ + ... + Tₙ

例:
  "SELECT * FROM users WHERE name = '" + input + "'"
  input = ' OR '1'='1
  結果: SELECT * FROM users WHERE name = '' OR '1'='1'      (すべての行に一致してしまう)
```

ここでTᵢは固定のSQL断片(コード)であり、uⱼはユーザー入力(データ)である。安全性のためには次が必要になる。

```text
parse(Q) は parse(T₀ + lit(u₁) + T₁ + ...) と等しくなければならない
```

lit(·)は結果のASTを決して変えないという条件である。単純な文字列連結ではこれを満たせない。引用符、コメントの開始記号、演算子がリテラルを閉じて新しい句を開いてしまう可能性がある。

プリペアドステートメントとパラメータバインディングは、処理を二つの段階に分ける。

1. Prepare: パーサーはプレースホルダ(`?`、`$1`、名前付きパラメータ)を含むテンプレートを受け取る。
2. Execute: ドライバはバインドされた値をSQLテキストの外側で、型付きパラメータを使うバイナリプロトコル経由で送信する。

抽象的には次のように表せる。

```text
stmt = Prepare(T)       T = "SELECT * FROM users WHERE name = ?"
Execute(stmt, v)        v = [input]
```

vは、SQLとして再パースされるテキストとしてTに混ぜ込まれることがない。

エスケープは、対象の方言と文字コードに完全に対応していれば機能する場合もあるが、エンコーディングのトリックや不完全なエスケープ、誤ったAPIの使用によって破綻してきた歴史がある。自前のクォートエスケープよりもパラメータを優先する。

## 3. 注入クラス、概念的な分類(WAHH)

以下のクラスは効果がどう観測されるかを説明するものであり、攻撃レシピではない。

| クラス | 観測可能性 | 直感的な説明 | 対策上の注意 |
|:---|:---|:---|:---|
| In-band | 結果やエラーが同じHTTPレスポンスに現れる | 入力が見える出力を変える | パラメータと最小権限。DBエラーを隠す |
| Inferential(blind) | 挙動の違い(真偽、レイテンシ)しか見えない | アプリケーションがサイドチャネルで「答える」 | 根本対策は同じ。エラーとタイミングの挙動も正規化する |
| Out-of-band | DBの機能とネットワークのegressが許す場合のサイドチャネル(DBホストからのDNS/HTTPなど) | まれ。特定のDB機能とegressが必要 | DB層からのegressを遮断する。危険なDB機能を無効化する |
| Second-order | ペイロードが一度保存され、別のクエリで実行される | すべてのSQLシンクを独立して検証する | 管理用ジョブやレポートを含め、すべてのシンクをパラメータ化する |

WAHHの主張は、blindやout-of-bandは異なる種類のSQLではなく、アプリケーションがクエリ結果を直接表示しないときに使われる観測戦略だということである。主要な対策は変わらない。入力を構文にしないことである。クラスごとのペイロードカタログを追いかける必要はない。バッチジョブ、エクスポート、検索、生SQLにフォールバックするORMの経路を含め、クエリが構築されるすべての場所で構築モデルを修正する。

## 4. 二次インジェクションとマルチシンクの現実

典型的な危険パターンは次の通りである。

1. 入力はパラメータ化されたINSERTによって安全にカラムへ保存される。
2. その後、別のプロセスがその値を読み取り、レポートやcronジョブ、「高度な検索」機能のような動的SQLへ連結する。

「INSERT時にサニタイズ済みだから安全」では不十分である。個々のSQLシンクがそれぞれ独立して安全でなければならない。

`query()`や`execute()`を呼び出す、あるいは文字列テンプレートからSQLを組み立てるすべてのコードパスを脅威モデリングの対象にする。使用頻度の低い管理ツールも含まれる。INSERT時点では安全でも、後段のレポートで危険であれば、それは依然として二次SQLインジェクションである。入力が最初に通過するシンクだけでなく、すべてのSQLシンクを防御する。

## 5. 危険なコードと安全なコードのパターン

### 5.1 アンチパターン: 文字列連結(例示)

```php
// UNSAFE — user data becomes SQL syntax
$sql = "SELECT id, role FROM users WHERE email = '" . $_GET['email'] . "'";
$rows = $db->query($sql);
```

```python
# UNSAFE
sql = f"SELECT * FROM products WHERE category = '{category}' AND q = '{q}'"
cursor.execute(sql)
```

### 5.2 安全なパターン: バインドパラメータ

```php
// SAFE — structure fixed; values bound
$stmt = $pdo->prepare('SELECT id, role FROM users WHERE email = ?');
$stmt->execute([$email]);
```

```python
# SAFE (DB-API style)
cursor.execute(
    "SELECT * FROM products WHERE category = %s AND q = %s",
    (category, q),
)
```

```java
// SAFE
PreparedStatement ps = conn.prepareStatement(
    "SELECT id, role FROM users WHERE email = ?");
ps.setString(1, email);
```

### 5.3 動的な識別子(テーブル、カラム、ORDER BY)

パラメータバインディングは識別子の名前を束縛しない。`ORDER BY`やカラム名に対しては次を行う。

- `{"name","price","created_at"}`のような厳格な許可リストを用意し、固定のSQLリテラルにマッピングする。
- その集合の外にある入力は拒否する。

```text
if col not in {"name", "price", "created_at"}: reject
```

`"ORDER BY " + userInput`のような構築は決して行わない。

### 5.4 LIKEとワイルドカード

バインディングは構文レベルのインジェクションを防ぐが、`LIKE`の値の中では`%`と`_`が依然としてワイルドカードとして機能する。リテラル一致が必要な場合は、アプリケーション層でワイルドカード文字をエスケープする。

## 6. ORM、ストアドプロシージャ、NoSQL

| 技術 | 誤った安全感 | 実際に必要なこと |
|:---|:---|:---|
| ORM | 「SQLを書いていないから安全」 | 生のクエリや文字列補間を避ける。`whereRaw`や`order`など類似の条件APIをレビューする |
| ストアドプロシージャ | 「ロジックがDB側にある」 | 内部でSQLを連結しているプロシージャは依然としてインジェクション可能 |
| クエリビルダー | 流暢なAPI | 最終的なSQLがプレースホルダを使っており、文字列の貼り付けでないことを確認する |
| NoSQL(例: MongoのクエリオブジェクトOB) | 「SQLではないから安全」 | 信頼できないオブジェクトがJSONとしてフィルタにマージされる場合の演算子インジェクション(`$gt`、`$where`) |

NoSQLの場合、リクエストボディを`JSON.parse`してそのままフィルタクエリにマージしてはならない。許可したフィールドだけをパースし、フィルタオブジェクトはサーバー側で構築する。

WAHHの注入の章の考え方はSQL以外にも当てはまる。LDAP、OSシェル、XPath、テンプレートエンジンなど、どのインタプリタもコードとデータが一つの文字列に混ざると同じように壊れる。

## 7. 多層防御スタック

### 7.1 主要な対策(必須)

- パラメータ化クエリ、または動的なSQL連結を行わないストアドプロシージャ。
- 識別子や列挙的なフィルタに対する許可リスト。

### 7.2 二次的な対策

| 対策 | 目的 |
|:---|:---|
| 最小権限のDBアカウント | アプリ用ロールはDMLを制限。FILE、SUPER、`xp_cmdshell`系の権限は持たない |
| 認証情報の分離 | 可能な限りレポート用に読み取り専用レプリカの認証情報を使う |
| ネットワークのセグメンテーション | アプリとDB間の通信を閉域に保つ。DBに一般的なインターネットegressを与えない |
| エラー処理 | クライアントには汎用エラーのみ返す。詳細なSQLエラーは安全なログにのみ記録する |
| 入力検証 | 長さ、型、文字セットのチェックを多層防御として行う。パラメータの代替にはしない |
| WAF / RASP | 一時的なシグナルと仮想パッチであり、根本対策ではない |
| シークレット | フロントエンドコードにDB認証情報を置かない。定期的にローテーションし、vaultやKMSに保管する |

### 7.3 出力エンコーディングはSQLi対策にならない

HTMLエンコーディング(XSS対策)はSQLiを修正しない。対策はシンクの言語に合わせる必要がある。

優先順位は、まずすべてのシンクをパラメータ化し、次に最小権限を適用し、次に検証と許可リスト、最後に監視という順である。`OR`や`UNION`をフィルタするキーワードブラックリストに頼ってはならない。回避されやすく、正当な入力も壊してしまう。字句レベルのフィルタよりも構造的な安全性(バインドパラメータ)を優先する。

## 8. 許可された検出と検証のシグナル

自分のラボや許可されたペンテストでは、ペイロードのカタログではなくクラスレベルの兆候に注目する。

- 入力がリテラルから抜け出したときのアプリケーションの挙動差(汎用的な5xxか200か)を確認し、エラーを隠すのではなく根本原因を修正する。
- コードレビュー: 変数と並んで構築されるSQL文字列を探す。連結を検出するSAST用のルールを追加する。
- ユニットテストと結合テスト: ドライバがバインドパラメータを使っていることを確認する。SemgrepやCodeQLの`sql-injection`ルールをCIに組み込む。
- ロギング: クエリのテンプレートとパラメータのメタデータを記録する。パスワードフィールドは決して記録しない。

```bash
# Lab only: inspect that YOUR app uses TLS to DB and least-priv account
# (example connectivity check — not an attack tool)
psql "host=127.0.0.1 dbname=app user=app_rw sslmode=verify-full" -c 'SELECT current_user;'
```

## 9. 開発者向け対策チェックリスト

| チェック項目 | 合格基準 |
|:---|:---|
| すべてのSQLシンク | プリペアド、またはバインドパラメータ |
| ORDER BY / カラム | 許可リストのマッピングのみ |
| マルチテナントのフィルタ | セッションから取得したサーバー側の`tenant_id`。クライアント単独からは取得しない |
| エラー | スタックトレースやSQLテキストをクライアントに送らない |
| DBのロール | 最小限の権限。OS連携機能を持たない |
| マイグレーション / 管理スクリプト | 本番のリクエスト経路と同じ基準を適用する |
| 二次インジェクションの経路 | レポート、キュー、検索インデクサもパラメータ化する |
| テスト | 過去の連結バグごとに少なくとも1件の回帰テストを持つ |

```
 Trust boundary          Safe interior
 ┌─────────────┐         ┌──────────────────────────┐
 │ HTTP / MQ   │  values │  Prepare(T) + Bind(v)    │──► SQL engine
 │ untrusted   │────────►│  Allowlist(identifiers)  │
 └─────────────┘         └──────────────────────────┘
        ✗ never:  sql = "SELECT ... " + user
```

## セキュリティノート: 脅威と対策

| 脅威パターン | 成立する理由 | 対策 |
|:---|:---|:---|
| WHERE改変による認証バイパス | データがブール論理そのものになる | バインドパラメータ。認可はセッション経由でサーバー側にて強制する |
| UNION型の結果整形 | 出力が反映される際に攻撃者がカラムを揃える | パラメータ。反映されるSQLエラーやデータを最小化する |
| Blind推論 | アプリがブールやタイミングのサイドチャネルを漏らす | パラメータ。タイミングをほぼ均一にしたエラーページ。レート制限 |
| 特権的なDB機能 | 権限が過剰なDBアカウント | 危険な権限を剥奪する。egressを制御する |
| ORMの生SQL | 文字列を連結する抜け道 | 生APIを禁止またはレビューする。SASTを実行する |
