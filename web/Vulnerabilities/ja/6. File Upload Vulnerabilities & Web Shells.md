## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| ファイルアップロード | ユーザーがサーバーへファイルを送れる機能 |
| Webシェル | 攻撃者がコマンドを実行できるようにする、悪意あるアップロードファイル |
| Content-Type | アップロードが申告する種類(簡単に偽装できるので単独では信用しない) |
| マジックバイト | ファイル先頭にある本当のファイル種別の署名 |
| 拡張子の許可リスト | 既知の安全な拡張子だけを受け入れること |
| 実行 | 本当の危険: サーバーがアップロードファイルをコードとして実行すること |
| 再エンコード | 隠されたペイロードを除くために画像を作り直すこと |

## 1. 脅威モデル

ファイルアップロード機能は、クライアントをサーバーのファイルシステムやオブジェクトストアへの書き手に変える。WAHHは連鎖的な影響を強調している。アップロードされたファイルがWebランタイムによって実行されたり、脆弱なパーサーによって処理されたりすると、結果はRCE、(SVGやHTML経由の)stored XSS、URLを追うパーサー経由のSSRF、あるいはサービス拒否(zip爆弾、解凍の悪用)になり得る。

概念としてのWebシェルとは、アップロードされた後にHTTP経由で呼び出されるスクリプトであり、サーバーに攻撃者のコマンドを実行させるものである。この文書は、そのクラスのバグをどう防ぐかを説明するものであり、Webシェルの書き方やアップロード方法を説明するものではない。

CWE-434は*Unrestricted Upload of File with Dangerous Type*を扱う。危険というのは「`.php`」だけを意味するわけではない。テンプレート、サーバーサイドインクルード、オフィスコンバータ内の特定の「文書」形式、誤ったMIMEタイプで配信されるHTMLなど、環境が解釈するものすべてが含まれる。

端的に言えば、危険なアップロードとは、サーバーまたはブラウザが解釈または実行してしまう種類のファイルであって、十分な制御なしに置かれてしまったものである。

## 2. 根本原因

| 失敗 | 何が問題か |
|:---|:---|
| クライアントの`Content-Type`やファイル名を信頼する | どちらも攻撃者が制御できるメタデータである |
| Web実行可能なルート配下に保存する | URLがそのままコードランタイムにマッピングされる |
| ユーザーの拡張子をそのまま保持する | `.php`、`.aspx`、`.jsp`、二重拡張子、末尾のドット |
| ランダムなオブジェクトキーがない | 上書き、予測可能なパス、キャッシュポイズニング |
| 誤った`Content-Type`で配信する | ブラウザがHTML/JSとして実行してしまう(XSS) |
| 安全でないパーサーで処理する | ImageTragick系のバグ、XMLベースの「プレビュー」でのXXE |
| ファイル名に埋め込まれたシンボリックリンクやパス | 他のディレクトリへのトラバーサル |

## 3. コンテンツ検証、原則

### 3.1 多層チェック(単独では十分でない)

1. 拡張子の許可リスト、例えば`{png,jpg,webp,pdf}`をサーバー側でマッピングする。
2. マジックバイト、または`file(1)`風のスニッフィングを行い、宣言された種別と照合する。
3. 再エンコードまたはトランスコード。画像であればデコードしてから信頼できるライブラリで新しいファイルを書き出す。これによりほとんどのポリグロットの手口が破壊される。
4. サイズ制限。1ファイルごとと、ユーザーごとのクォータの両方。
5. ファイル名の破棄。ユーザーから送られた生のファイル名を保存キーとして再利用しない。

```text
次をすべて満たすときだけファイルを受け入れる:
  拡張子が許可リストにある
  かつ マジックバイトがその拡張子と一致する
  かつ サイズ ≤ 上限
```

### 3.2 ポリグロット(概念)

一つのファイルが、どのパーサーが読むかによって複数の形式として有効になり得る。例えば画像とスクリプトコンテンツを兼ねる場合である。再エンコードと、配信時の厳格な`Content-Type`により、このリスクを減らせる。

### 3.3 SVG / HTML

SVGは、特定の文脈で`image/svg+xml`としてインラインで配信された場合、スクリプトを含み得る。より安全な選択肢は、サーバー側でSVGをPNGへラスタライズするか、`Content-Disposition: attachment`と厳格なCSPを組み合わせて配信することである。

## 4. 安全な保存設計

```
 ┌──────── viewer / CDN ────────┐
 │  signed URL, short TTL       │
 └─────────────▲────────────────┘
               │
 ┌─────────────┴────────────────┐
 │ Object store bucket          │
 │  - random keys               │
 │  - no public execute         │
 │  - antivirus/async scan opt. │
 └─────────────▲────────────────┘
               │
         app writes only
```

原則:

- ドキュメントルートの外に保存するか、スクリプト実行がまったくできないバケットに保存する。
- オブジェクトキーはUUIDに、許可リストから選んだ固定拡張子を付けたものにする。
- データベースは`user_id → object_key → declared_type`をマッピングする。
- アクセスは、認可されたダウンロードハンドラか署名付きURL経由に限定する。
- Apache/Nginxでは、アップロードディレクトリの`location`ブロックで明示的にスクリプトエンジンを無効化する。他の層が誤設定されていた場合の多層防御として機能する。

## 5. 実行の防止

目標は、アップロードされたファイルをHTTPで開いても、サーバー側でコードが絶対に実行されないようにすることである。

対策:

- アップロードのパスをPHP、ASP、JSPのインタプリタへ決してマッピングしない。
- ダウンロード時のヘッダー: 正しい`Content-Type`と`X-Content-Type-Options: nosniff`。
- リスクのある種別には`Content-Disposition: attachment`を使う。
- アップロードフォルダのハンドラを運用/設定レイヤーで無効化する(自分のスタックに合わせて調整する)。

拡張子チェックが完璧であっても、別の場所にある後発のバグ(アップロードパスのLFI、テンプレートのinclude)がリスクを復活させることがある。アップロードチェック自体がどれほど優れていても、アップロードファイルは非実行かつコードとしてincludeできない状態に保つ。

## 6. 危険なパターンと安全なパターン

### 6.1 危険なパターン

```python
# UNSAFE — trusts filename & stores in web root
f = request.files["file"]
f.save("/var/www/html/uploads/" + f.filename)
# later: https://app/uploads/evil.php may execute if PHP enabled there
```

### 6.2 より安全な構成

```python
import uuid
from pathlib import Path

ALLOWED = {
    "image/png": ".png",
    "image/jpeg": ".jpg",
}
STORE = Path("/var/app/upload_data")  # not served as scripts

def save_upload(file_storage, sniffed_mime: str) -> str:
    if sniffed_mime not in ALLOWED:
        raise ValueError("type")
    if file_storage.content_length and file_storage.content_length > 5_000_000:
        raise ValueError("size")
    key = f"{uuid.uuid4().hex}{ALLOWED[sniffed_mime]}"
    dest = STORE / key
    # Prefer: decode/re-encode image here instead of raw save when applicable
    file_storage.save(dest)
    return key
```

```nginx
# Defense-in-depth example: deny script execution in a mistaken alias
location ^~ /media/ {
    internal;  # or alias to read-only files with types {}
    add_header X-Content-Type-Options nosniff always;
    default_type application/octet-stream;
}
```

## 7. メディア/ドキュメントプロセッサ

アップロードされたファイルは、サムネイル生成、ウイルススキャン、Officeファイルの PDF変換など、さらに処理されることが多い。

| リスクのクラス | 対策 |
|:---|:---|
| コンバータCLIでのコマンドインジェクション | Argv配列。許可リスト。サンドボックス |
| パーサーの脆弱性(画像、XML、フォント) | 更新されたライブラリ。ワーカーの分離。リソース制限 |
| XMLベース形式でのXXE | 外部エンティティを無効化する。安全なパーサーを使う |
| Zip爆弾 / 圧縮率 | 解凍後のサイズとエントリ数を制限する |
| リモートリンクされたリソース経由のSSRF | ワーカー内のネットワークアクセスを無効化する |

処理ワーカーは隔離環境で実行する。非rootコンテナ、egressなし、seccomp適用。

## 8. 多層防御スタック

1. アップロードAPIに対するAuthN/AuthZ。誰が何をアップロードできるかを制御する。
2. MIMEタイプ、マジックバイト、サイズの許可リスト。
3. ランダムなキー。ユーザーのファイル名を破棄する。
4. 可能であれば画像を再エンコードする。
5. 別のバケットまたはアカウントに、非実行の保存先を用意する。
6. 安全な配信ヘッダー、または署名付きURL。
7. 意味がある場合は非同期のマルウェアスキャン。
8. レート制限とクォータ。
9. アップロードエラーの急増や予期しない新しいオブジェクト種別の監視。
10. アップロードディレクトリを指し得るincludeやLFIの経路を持たない。

## 9. 開発者向けチェックリスト

| チェック項目 | 合格基準 |
|:---|:---|
| 保存場所 | スクリプトルートの外 |
| タイプポリシー | 許可リストとマジックバイトチェック |
| ファイル名 | サーバー生成 |
| 配信 | `nosniff`と正しいMIMEタイプ |
| SVG/HTML | ラスタライズ、または添付ファイルとして強制ダウンロード |
| ワーカー | サンドボックス化されたコンバータ |
| パス | ユーザー制御の保存先ディレクトリを持たない |
| テスト | 許可されない種別が拒否される。非実行の設定が検証されている |

```
 Client file
    │
    ▼
 Validate type/size ──► Re-encode? ──► Store random key
    │                                   │
    └ reject                            ▼
                              Serve via authz + safe headers
```

## セキュリティノート: 脅威と対策

| 脅威パターン | クラス | 対策 |
|:---|:---|:---|
| 実行可能なアップロード | Webランタイム経由のRCE | 非実行の保存とタイプの許可リスト |
| HTML/SVG経由のstored XSS | ブラウザでのスクリプト実行 | MIME制御、CSP、サニタイズまたはラスタライズ |
| 重要ファイルの上書き | 完全性 | ランダムなキー。ユーザー指定のパスを使わない |
| 悪意あるアーカイブ | DoS、またはパスへの書き込み | 制限。安全な展開 |
| コンバータの悪用 | RCE/SSRF | サンドボックス。Argv配列。egressなし |
