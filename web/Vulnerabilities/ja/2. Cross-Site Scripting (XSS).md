## 1. ブラウザの信頼モデル

ブラウザはドキュメントのオリジンが持つ権限でJavaScriptを実行する(同一オリジンポリシー)。攻撃者がアプリケーション自身のオリジンにスクリプトを注入すると、そのスクリプトはアプリケーションの一部として動作する。same-originのAPIを呼び出し、DOMを読み取り、多くの場合ログイン中のユーザーのセッションを代行して行動できる。これはスクリプトによるセッション乗っ取りであり、古典的なCSRFとは区別される。

XSSはこの境界を守れなかった結果である。信頼できないデータが実行可能なコードとして扱われてしまう。

Zalewskiの『The Tangled Web』は、XSSをブラウザ内部のconfused deputy問題として捉えている。被害者のブラウザが、サイト自身の権限を使って攻撃者制御のスクリプトを実行する「代理人」にされてしまう。XSSを直すというのは、信頼できない文字列をドキュメントやスクリプトへ安全に組み込むことであり、単に「悪い単語をフィルタする」ことではない。

## 2. XSSの分類、概念

| クラス | スクリプトが混入する場所 | 永続性 | 典型的なsink |
|:---|:---|:---|:---|
| Reflected | リクエストから即座にレスポンスへ | なし | 検索結果のエコー、エラーメッセージ |
| Stored | 保存された後に被害者へ配信される | あり | コメント、プロフィール、チケット |
| DOM-based | クライアント側のJSが信頼できないデータを危険なsinkへ書き込む | 場合による | `innerHTML`、`document.write`、URLからHTMLへ |

WAHHは、アプリケーションが危険なデータを永続化するかどうかでreflectedとstoredを区別している。DOM XSSは、サーバー側が正しく実装されていても、クライアント側のJavaScriptが`location`、`postMessage`、URLフラグメントを危険なsinkに結合すれば発生する。

三つすべてに共通する根本原因は一つである。JavaScriptまたはHTMLの注入sinkが、コンテキストに応じたエンコーディングや安全なAPIを経ずに、攻撃者の影響を受けたデータを取り込んでしまうことである。

## 3. 出力コンテキスト、エンコーディングはコンテキスト依存

信頼できない文字列$u$がドキュメントに挿入される場合を考える。正しいエンコーディングは文法的なコンテキストに依存する。

| コンテキスト | 生のままだと危険な理由 | 安全なアプローチ(原則) |
|:---|:---|:---|
| HTML本文のテキスト | マークアップやタグが解釈される | HTMLエンティティエンコード |
| HTML属性(引用符あり) | 引用符から抜け出す | 属性エンコード、かつ属性には常に引用符を付ける |
| JavaScriptの文字列リテラル | JS文字列から抜け出す | JS文字列エンコード、またはインラインスクリプトを避ける |
| URLのクエリ/パス | `javascript:`などの不正なスキーム | URLエンコードとスキームの許可リスト |
| CSS | 式やレガシーなエスケープ | 信頼できないCSSを避ける。厳格な許可リスト |
| `<script>`内のJSON | `</script>`による抜け出し | 安全なJSONシリアライズのパターン |

形式的には、コンテキスト$c$に対するエンコーディング$E_c$は次を保証しなければならない。

$$
\mathsf{parse}_c\big(T_0 \,\|\, E_c(u) \,\|\, T_1\big)
\;=\;
\mathsf{parse}_c\big(T_0 \,\|\, \mathsf{data}(u) \,\|\, T_1\big)
$$

これは$u$が常にデータであり続け、文法$c$の新しい非終端記号には決してならないことを意味する。

単一の「HTMLエスケープ」関数だけではすべてのコンテキストに対応できない。イベントハンドラ(`onclick=...`)への挿入とURLへの挿入は異なるコンテキストであり、それぞれ固有のエンコーディング規則を持つ。

最も安全なのは、信頼できないデータをscriptやstyleのコンテキストにまったく置かないことである。データは`textContent`として読み取る`data-*`属性経由で渡すか、その目的のために正しくエスケープされたJSONの塊を`JSON.parse`する。

## 4. 根本原因のパターン

1. リクエストやデータベースのフィールドを、自動エスケープなしにテンプレートへサーバー側で文字列連結する。
2. テンプレートエンジンのエスケープが無効化されている(`| safe`、`raw`、`{{{ }}}`)。
3. HTMLをパースするDOM sink、`innerHTML`、`outerHTML`、`insertAdjacentHTML`。
4. `$(userString)`のように文字列をHTMLとして解釈するjQuery系のAPI。
5. `postMessage`のデータの取り扱いミス、あるいはリッチなウィジェットの`outerHTML`。
6. ユーザーのコンテンツが添付ファイルや安全な種別ではなく`text/html`として配信されるContent-Typeの混同。

## 5. 危険なパターンと安全なパターン

### 5.1 HTML本文

```html
<!-- UNSAFE (template sketch) -->
<p>Hello {{ user.name }}</p>
<!-- dangerous if engine does not auto-escape, or name contains markup -->
```

```javascript
// UNSAFE
el.innerHTML = "Hello " + userName;

// SAFE — text node, not HTML parser
el.textContent = "Hello " + userName;
```

### 5.2 属性

```html
<!-- UNSAFE -->
<img src="{{ url }}">
<!-- prefer scheme allowlist https: only; never untrusted javascript: -->

<!-- SAFER pattern: fixed attribute structure + encoded value + validation -->
<a href="https://example.com/u?id={{ id | urlencode }}">profile</a>
```

### 5.3 インラインスクリプトの連結を避ける

```html
<!-- UNSAFE pattern -->
<script>var u = "{{ user_input }}";</script>
```

```html
<!-- SAFER: data island consumed as text, then JSON.parse -->
<div id="cfg" data-user=""></div>
<script>
  const raw = document.getElementById('cfg').dataset.user;
  // populate dataset from server with HTML-attribute encoding;
  // or serve application/json on a separate endpoint
</script>
```

### 5.4 フレームワークのデフォルト

現代的なフレームワーク(Reactの`{}`によるテキスト子要素、Angularのデフォルトエスケープ、Vueのテキスト補間)は、開発者がサニタイザなしで`dangerouslySetInnerHTML`、`[innerHTML]`、`v-html`を使わない限り、XSSリスクの大半を自動的に減らしてくれる。

## 6. CSP、Cookieフラグ、Trusted Types

### 6.1 Content-Security-Policy(多層防御)

CSPは実行を許可するスクリプトのオリジンを制限する。厳格なポリシーは次のようになる。

- `default-src 'self'`
- `script-src`にnonceまたはhashを使う(可能なら`'unsafe-inline'`と`'unsafe-eval'`を避ける)
- `object-src 'none'`、`base-uri 'none'`、アプリが実際に必要とする範囲での`frame-ancestors`

CSPはエンコーディングの代替ではない。エンコーディングが退行したときのためのセーフティネットである。

### 6.2 Cookieのハードニング(セッションへの影響を軽減)

| 属性 | 効果 |
|:---|:---|
| `HttpOnly` | そのCookieへの`document.cookie`アクセスを遮断する |
| `Secure` | TLS経由でのみ送信される |
| `SameSite=Lax/Strict` | クロスサイトでのCookie送信を減らす(CSRF関連) |
| `__Host-`プレフィックス | Cookieのpath/domainの制約を強制する |

`HttpOnly`はXSSによるCookie窃取を減らすが、XSSのペイロードは依然として被害者としてアプリケーションのAPIを呼び出せる。

### 6.3 Trusted Types(対応環境の場合)

Trusted Typesは、値がポリシーファクトリによって発行された信頼済みオブジェクトでない限り、危険な代入(`innerHTML`など)をブロックするブラウザのポリシーであり、開発者にすべてのsinkのレビューを強制する。

『The Tangled Web』は、HTMLとJSのパーサーが実際にはどれほど複雑かを強調している。生の文字列がHTMLに流れ込む場所が少ないほど、XSSの攻撃面は小さくなる。

HTMLのサニタイズは、リッチテキストが実際に製品要件である場合にのみ行い、タグと属性の許可リストで設定された、保守がしっかりしたサニタイザを使う。`<script>`タグを除去しようとする正規表現に頼ってはならない。

## 7. DOM XSS: sourceとsink(防御のためのマップ)

| 信頼できないsource(例) | 危険なsink(例) |
|:---|:---|
| `location`、`location.hash`、`location.search` | `innerHTML`、`outerHTML`、`document.write` |
| `document.referrer` | `eval`、`new Function`、`setTimeout(string)` |
| `postMessage`イベントの`data` | 検証されていないURLを使う`element.src` / `href` |
| HTMLへコピーされたWebストレージの値 | HTMLを解釈するjQuery系API |

上記のすべてのsourceを信頼できないものとして扱う。安全なsink(`textContent`、検証済みの値による`setAttribute`)を使い、すべての`postMessage`について`origin`とスキーマの両方を検証する。

## 8. 多層防御スタック

1. コンテキストを考慮した出力エンコーディング。フレームワークの自動エスケープをデフォルトで有効にする。
2. 危険なsinkを避ける。レビューなしの`v-html`や`dangerouslySetInnerHTML`を禁止する。
3. リッチコンテンツにのみ使うHTMLサニタイザの許可リスト。
4. CSPのnonceまたはhash。時間をかけて`unsafe-inline`を除去する。
5. Cookieフラグ、短いセッション寿命、機微な操作での再認証。
6. HTTPシリーズで扱ったセキュリティヘッダー(`X-Content-Type-Options`など関連ヘッダー)。
7. 生のHTML sinkに対するコードレビューとSASTルール。
8. 不正利用の報告、または本番環境でのCSPの`report-to`。個人情報の扱いには注意する。

## 9. 開発者向けチェックリスト

| 項目 | 合格? |
|:---|:---|
| テンプレートがデフォルトで自動エスケープされている | ☐ |
| インラインのJS/CSSに信頼できないデータがない | ☐ |
| DOMのコードが`textContent`や安全なURLビルダーを使っている | ☐ |
| リッチHTMLはサニタイザの許可リスト経由のみ | ☐ |
| 不要な`unsafe-inline`のないCSP | ☐ |
| セッションCookieが`HttpOnly; Secure; SameSite`を使っている | ☐ |
| ファイルダウンロードが安全な`Content-Type`と`Content-Disposition`を使っている | ☐ |
| `postMessage`のoriginとスキーマが検証されている | ☐ |

```
 Untrusted string u
        │
        ▼
  Choose context c ──► apply E_c(u) ──► insert into template
        │
        └── if need HTML subset ──► Sanitizer_allowlist(u) only
```

## セキュリティノート: 脅威と対策

| 脅威パターン | メカニズム | 対策 |
|:---|:---|:---|
| Reflected XSS | リクエストがHTMLにそのまま反映される | エンコード。CSP。生の入力を反映しない |
| Stored XSS | 永続化されたコンテンツが他のユーザーに配信される | 出力時にエンコード。リッチテキストをサニタイズする |
| DOM XSS | クライアント側のsinkが攻撃者のデータをパースする | 安全なDOM API。CSP |
| Mutation / mXSS | サニタイザとブラウザのパーサーの不一致 | 実績のあるサニタイザを使う。HTMLを単純化する |
| PDF/Flashのレガシーなスクリプト | プラグインの攻撃面 | プラグインを無効化する。モダンなブラウザを使う |
