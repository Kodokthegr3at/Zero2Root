## 1. 🎯 Authentication Goals

### 🇮🇩 Bahasa Indonesia
**Authentication** menetapkan identitas subjek; **session management** mempertahankan ikatan itu lintas request; **authorization** memutuskan izin. WAHH memisahkan bug “login lemah” dari “sesi mudah digampar/difiksasi/diculik.”

Tujuan keamanan klasik:

| Property | Meaning |
|:---|:---|
| Authenticity | Hanya pemilik kredensial yang membuka sesi |
| Integrity | Token/sesi tidak dapat diubah tanpa terdeteksi |
| Confidentiality | Secrets tidak bocor ke XSS/log/Referer |
| Binding | Sesi terikat ke konteks (user, device policy) |
| Revocation | Server dapat mematikan akses sebelum expiry |

### 🇬🇧 English
Passwords, WebAuthn, OIDC, and API keys are *credential classes*. Sessions and JWTs are *artifacts that prove a prior authentication* — their crypto and storage dominate modern failure modes.

### 日本語
パスワードやWebAuthnは資格情報、セッション/JWTは**認証済み状態の証明**です。保存方法と検証が安全性を決めます。

## 2. 🍪 Server-Side Session Model

$$
\begin{aligned}
&\mathsf{Login}(\mathsf{creds}) \Rightarrow \mathsf{sid} \leftarrow \{0,1\}^{n},\quad n\ge 128 \\
&\mathsf{Store}[\mathsf{sid}] = \{\mathsf{uid},\, \mathsf{meta},\, \mathsf{exp}\} \\
&\mathsf{Request}:\ \mathsf{Cookie}(\mathsf{sid}) \Rightarrow \mathsf{lookup}(\mathsf{sid})
\end{aligned}
$$

Keunggulan: **revocation** mudah (hapus `sid`); payload minimal di klien.

Risiko kelas (konsep, bukan exploit kit): prediksi `sid` (entropy rendah), fixation (tetapkan `sid` pra-login), theft (XSS/network), missing regeneration on privilege change.

**Mitigasi inti:** regenerate session ID on login; high entropy; server-side store; idle + absolute timeouts; bind critical steps to re-auth.

## 3. 🛡️ Cookie Hardening (*Tangled Web* / RFC 6265)

| Attribute | Role |
|:---|:---|
| `Secure` | HTTPS only |
| `HttpOnly` | Not readable from JS |
| `SameSite` | CSRF reduction |
| `Path` / `Domain` | Scope narrowly |

Jangan taruh sesi di `localStorage` jika dapat dihindari — XSS langsung mencuri. Jika SPA memakai Bearer di memory, pahami trade-off CSRF vs XSS.

## 4. 📐 JWT Structure — Mathematics of JWS Compact Serialization

JWT yang umum dipakai adalah **JWS** (RFC 7515) dalam bentuk compact:

$$
\texttt{JWT} \;=\; \mathsf{b64url}(H) \;\|\; \texttt{.} \;\|\; \mathsf{b64url}(P) \;\|\; \texttt{.} \;\|\; \mathsf{b64url}(S)
$$

di mana:

- $H$ = header JSON (algoritma, tipe, kadang `kid`)  
- $P$ = payload/claims JSON  
- $S$ = signature (atau MAC tag) atas signing input  

**Signing input:**

$$
\mathsf{SI} = \mathsf{b64url}(H) \,\|\, \texttt{.} \,\|\, \mathsf{b64url}(P)
$$

### 4.1 HMAC (alg `HS256`, etc.)

$$
S = \mathsf{HMAC}\text{-}\mathsf{SHA256}_{k}(\mathsf{SI})
$$

dengan kunci bersama $k$. Verifikasi: hitung ulang $S'$ dan bandingkan **constant-time** ke $S$.

### 4.2 Asymmetric (alg `RS256` / `ES256`, etc.)

$$
\mathsf{Verify}(\mathsf{SI},\, S,\, pk) = \mathsf{true/false}
$$

Tanda tangan dibuat dengan private key; verifikasi dengan **public key**. Berguna untuk microservices yang tidak berbagi secret HMAC.

### 4.3 Claims (payload)

Claims terdaftar umum (RFC 7519): `iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`. Aplikasi menambahkan claims privat — **jangan** taruh rahasia sensitif di JWT jika token dapat dibaca klien (header+payload hanya encoding, bukan enkripsi). Untuk kerahasiaan claims, gunakan **JWE** atau simpan data di server.

Base64url **bukan** kerahasiaan:

$$
\mathsf{b64url}^{-1}(P) = P_{\mathsf{json}}\quad\text{(siapa pun dapat membaca)}
$$

## 5. ✅ Correct Verification Checklist

Implementasi aman harus:

1. **Parse** tiga bagian; tolak format menyimpang.  
2. **Pilih kunci** dari trust store berdasarkan `kid` yang diizinkan — jangan unduh JWKS dari URL user.  
3. **Enforce algorithm allowlist** di server: mis. hanya `ES256` atau hanya `RS256`.  
4. **Verify signature** dengan API kripto yang diuji; gagal ⇒ reject.  
5. **Validate claims:**  
   - `exp` / `nbf` dengan clock skew kecil $\delta$  
   - `iss`, `aud` exact match  
   - `sub` mapped to authorization  
6. **Reject** token tanpa signature section / empty signature.  
7. **Constant-time** compare untuk HMAC.  
8. Log kegagalan tanpa mencetak token penuh.

```python
# SAFE sketch — algorithm allowlist + verify + claims
# (library APIs differ; never roll your own crypto)
import jwt  # PyJWT-style illustration

PUBLIC_KEY = open("jwks_rsa_pub.pem").read()
ALLOWED = ["RS256"]

def accept_bearer(token: str) -> dict:
    return jwt.decode(
        token,
        PUBLIC_KEY,
        algorithms=ALLOWED,          # critical
        audience="api.myapp.example",
        issuer="https://idp.myapp.example/",
        options={"require": ["exp", "iat", "sub"]},
    )
```

## 6. ⚠️ Algorithm Confusion — Concept Only

### 🇮🇩 Bahasa Indonesia
**Algorithm confusion** (juga terkait historis dengan `alg=none` dan salah verifikasi HMAC-vs-RSA): terjadi ketika *penerima* mempercayai header `alg` dari token, lalu memilih jalur verifikasi yang salah.

Contoh konsep:

- Token menyatakan `alg=HS256`, tetapi verifier memakai **public RSA key sebagai secret HMAC** — jika library mengizinkan, penyerang yang tahu public key dapat menempa MAC.  
- Token menyatakan `alg=none` dan signature kosong — verifier lama yang “menerima none” menerima payload apa pun.

$$
\text{Safe rule:}\quad
\mathsf{alg} \in \mathcal{A}_{\mathsf{server}}
\;\ll\;
\mathsf{alg}\text{ from untrusted header alone}
$$

Server **menetapkan** algoritma yang diterima; header hanya metadata yang harus cocok dengan kebijakan, bukan otoritas.

### 🇬🇧 English
This note intentionally omits exploit construction and cracking tooling. If you maintain a verifier, add regression tests: forged `alg` values must fail closed.

### 日本語
検証側は`alg`を攻撃者入力として扱い、**サーバ側許可リスト**でアルゴリズムを固定します。`none`や鍵種別の取り違えをテストで潰します。

## 7. 🧨 Common Design Flaws (Classes)

| Flaw class | Description | Mitigation |
|:---|:---|:---|
| Weak/guessable session IDs | Low entropy | CSPRNG ≥ 128-bit |
| Session fixation | Pre-login SID kept | Rotate on login |
| Long-lived JWT without revoke | Stolen token works until `exp` | Short `exp` + refresh rotation; deny-list `jti` if needed |
| Sensitive data in JWT | Readable claims | Minimal claims; server store |
| `kid` injection / header injection | Attacker points to evil key | Strict JWKS pin; allowlist kids |
| Missing `aud`/`iss` checks | Cross-service acceptance | Explicit audience |
| “Verify” only decodes | Base64 decode without crypto | Always verify signature |
| Refresh token abuse | Theft → long access | Rotate; bind; detect reuse |
| Password storage | Fast hashes | Argon2id/bcrypt/scrypt + pepper |

Password login: rate limit, lockout/backoff, MFA for privileged accounts, constant-time compare of password hashes via vetted KDF APIs.

## 8. ⚖️ Unsafe vs Safe Patterns

```python
# UNSAFE — trusts alg from token; or decode without verify
jwt.decode(token, key, options={"verify_signature": False})  # never in prod
jwt.decode(token, key, algorithms=["HS256", "RS256", "none"])  # too broad
```

```python
# SAFE — narrow algorithms; verify aud/iss/exp
jwt.decode(token, key, algorithms=["ES256"], audience=AUD, issuer=ISS)
```

```python
# SAFE session sketch
sid = secrets.token_urlsafe(32)
redis.setex(f"sess:{sid}", TTL, user_id)
# On login success: destroy old sid, issue new
```

## 9. 🛡️ Defense-in-Depth Stack

1. **Phishing-resistant MFA** for high value (WebAuthn).  
2. **HTTPS everywhere**; HSTS.  
3. Session cookies: `Secure; HttpOnly; SameSite`.  
4. JWT: short-lived access tokens; rotating refresh; allowlisted algs.  
5. Server-side revocation for breach response (`jti` / session store).  
6. Step-up auth for password change, payouts, API key minting.  
7. CSRF tokens if cookie-based session (see CSRF note).  
8. XSS defense — session theft class.  
9. Central auth (OIDC) with vetted libraries — don’t invent crypto protocols.  
10. Audit logs for auth failures / refresh reuse.

### Opaque vs JWT

| | Server session ID | JWT access token |
|:---|:---|:---|
| Revoke | Easy | Needs infra |
| Size | Tiny cookie | Larger |
| Crypto on verify | Lookup | Signature verify |
| Use case | Classic web apps | APIs / distributed readers |

Hybrid umum: opaque session untuk browser; JWT pendek untuk service-to-service dengan mTLS.

## 10. ✅ Developer Checklist

| Check | Pass |
|:---|:---|
| Session ID entropy | CSPRNG ≥ 128-bit |
| Rotate SID on login | Yes |
| Cookie flags | Secure HttpOnly SameSite set |
| JWT verify | Signature + `iss`/`aud`/`exp` |
| Alg policy | Server allowlist; no `none` |
| Keys | Private keys in KMS/HSM; rotate |
| Refresh | Rotation + reuse detection |
| Passwords | Modern KDF; no plaintext logs |
| Tests | alg confusion cases fail closed |

```
 AuthN success
     │
     ├─► create server session (opaque sid) ─► Set-Cookie hardened
     │
     └─► issue JWS access token
              SI = b64(H).b64(P)
              S  = Sign_k(SI) or MAC_k(SI)
              verify with allowlisted alg + claims
```

## 🔐 Security Notes — Threats & Defenses

| Threat class | Why | Defense |
|:---|:---|:---|
| Stolen session cookie | XSS / malware | HttpOnly; CSP; short TTL |
| Forged JWT | Broken verify / confused alg | Allowlist + proper verify |
| Long-lived bearer leakage | Logs, Referer, XSS | Short `exp`; avoid URL tokens |
| Fixation | SID set before auth | Regenerate on login |
| Credential stuffing | Reused passwords | MFA; rate limit; breach checks |
