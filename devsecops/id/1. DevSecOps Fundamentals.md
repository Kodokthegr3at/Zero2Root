## Istilah penting

| Istilah | Artinya |
|:---|:---|
| DevSecOps | Cara kerja yang menjadikan keamanan bagian rutin dari pengembangan dan rilis, bukan pemeriksaan di akhir |
| Shift left | Memindahkan pemeriksaan keamanan ke tahap awal, saat perbaikan masih murah |
| SDLC | Software Development Life Cycle: perencanaan, desain, coding, testing, rilis, operasi |
| Threat modeling | Memikirkan secara terstruktur apa yang bisa salah pada sebuah desain sebelum kodenya ditulis |
| SAST | Static Application Security Testing: memindai kode sumber tanpa menjalankannya |
| SCA | Software Composition Analysis: memeriksa library pihak ketiga terhadap daftar kerentanan |
| DAST | Dynamic Application Security Testing: menguji aplikasi yang sedang berjalan dari luar |
| IaC | Infrastructure as Code: server dan jaringan didefinisikan dalam file, misalnya Terraform |
| CI/CD | Continuous Integration / Continuous Delivery: build, test, dan rilis otomatis setiap ada perubahan |
| SBOM | Software Bill of Materials: daftar semua komponen di dalam sebuah software |

## 1. Dari DevOps ke DevSecOps

Dulu tim keamanan memeriksa aplikasi beberapa minggu sebelum rilis. Hasilnya daftar panjang temuan yang datang terlambat, dan rilis tertunda atau temuan diabaikan.

Sekarang banyak tim merilis beberapa kali sehari. Pemeriksaan manual di akhir tidak mungkin mengikuti kecepatan itu. DevSecOps menjawabnya dengan memasang pemeriksaan otomatis di setiap tahap, dan menjadikan developer pemilik keamanan kodenya sendiri.

```
 Rencana ──► Desain ──► Kode ──► Build ──► Test ──► Rilis ──► Operasi
             │          │        │         │        │         │
       threat model  secret   SAST     DAST    tanda     monitoring,
                     scan,    SCA,             tangan,   log (LC-072)
                     review   image,           SBOM
                              IaC scan
```

Biaya memperbaiki bug naik di setiap tahap. Celah SQL injection ([LC-047](../../web/Vulnerabilities/id/1.%20SQL%20Injection%20%28SQLi%29.md)) yang tertangkap saat review cukup diperbaiki satu baris. Celah yang sama yang ditemukan setelah data pelanggan bocor bisa berakhir dengan denda dan laporan ke regulator.

## 2. Secure SDLC dan threat modeling

Threat modeling dilakukan saat desain, sebelum kode ditulis. Empat pertanyaan dasarnya (Adam Shostack):

1. Apa yang sedang kita bangun?
2. Apa yang bisa salah?
3. Apa yang akan kita lakukan terhadapnya?
4. Apakah kita sudah melakukannya dengan cukup baik?

Untuk pertanyaan kedua, **STRIDE** membantu supaya tidak ada kategori yang terlewat:

| Huruf | Ancaman | Properti yang dilanggar | Contoh di fitur upload foto profil |
|:---|:---|:---|:---|
| S | Spoofing | Autentikasi | Mengunggah foto atas nama user lain |
| T | Tampering | Integritas | Mengganti foto orang lain lewat ID di URL |
| R | Repudiation | Non-repudiation | User menyangkal pernah mengunggah gambar terlarang, dan tidak ada log |
| I | Information disclosure | Kerahasiaan | Metadata GPS di foto ikut terpublikasi |
| D | Denial of service | Ketersediaan | File 5 GB memenuhi disk server |
| E | Elevation of privilege | Otorisasi | File `.php` yang diunggah lalu dijalankan server ([LC-052](../../web/Vulnerabilities/id/6.%20File%20Upload%20Vulnerabilities%20%26%20Web%20Shells.md)) |

Hasil threat modeling berupa daftar ancaman dan kontrolnya, misalnya "batasi ukuran 5 MB", "buang metadata EXIF", "simpan di bucket terpisah, jangan di folder web". Daftar ini menjadi tiket kerja biasa, sama seperti fitur lain.

Tool gratis: OWASP Threat Dragon atau Microsoft Threat Modeling Tool untuk menggambar diagram alur data. Papan tulis dan satu jam diskusi juga sudah cukup untuk memulai.

## 3. Secret scanning

Password, API key, dan token yang ikut ter-commit adalah salah satu kebocoran paling umum. Begitu sampai di repositori publik, bot bisa menemukannya dalam hitungan menit.

Dua lapis pertahanan:

| Lapis | Kapan | Tool |
|:---|:---|:---|
| Pre-commit hook | Di laptop developer, sebelum commit | `gitleaks protect --staged` |
| Pemindaian di CI | Setiap push dan pull request | `gitleaks detect` |
| Pemindaian di platform | Terus-menerus | GitHub secret scanning dan push protection |

```bash
gitleaks detect --source . -v           # pindai seluruh riwayat Git
gitleaks protect --staged -v            # pindai file yang akan di-commit
```

Kalau secret sudah ter-commit, menghapus commit tidak cukup. **Cabut dan ganti secret-nya**, lalu periksa log untuk melihat apakah sudah dipakai orang lain. Hal yang sama dibahas untuk access key cloud di [LC-077](../../cloud-security/id/1.%20Cloud%20Security%20Fundamentals.md).

## 4. SAST: membaca kode sumber

SAST memindai kode untuk pola berbahaya, misalnya input user yang langsung masuk ke query SQL.

```python
# Rentan: input digabung ke query
cursor.execute("SELECT * FROM users WHERE name = '" + name + "'")

# Aman: parameterized query
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
```

Semgrep adalah tool SAST open source yang aturannya ditulis mirip kode yang dicari:

```bash
pip install semgrep
semgrep scan --config auto .                    # aturan komunitas sesuai bahasa yang terdeteksi
semgrep scan --config p/owasp-top-ten --error . # gagal (exit 1) kalau ada temuan
```

Contoh aturan sendiri:

```yaml
rules:
  - id: sql-string-concat
    languages: [python]
    severity: ERROR
    message: Query SQL dibangun dengan penggabungan string. Pakai parameterized query.
    pattern: $CUR.execute("..." + $X)
```

| Kelebihan SAST | Keterbatasan SAST |
|:---|:---|
| Cepat, bisa jalan di setiap pull request | Banyak false positive kalau aturannya terlalu luas |
| Menunjuk file dan baris yang tepat | Tidak melihat konfigurasi server atau perilaku saat runtime |
| Tidak butuh aplikasi berjalan | Kesalahan logika bisnis jarang tertangkap |

## 5. SCA: dependency yang rentan

Aplikasi modern sebagian besar terdiri dari library pihak ketiga. Kerentanan di satu library populer, seperti Log4Shell di Log4j pada 2021, bisa memengaruhi ribuan aplikasi sekaligus.

| Ekosistem | Perintah bawaan |
|:---|:---|
| Python | `pip-audit` |
| Node.js | `npm audit` |
| Go | `govulncheck ./...` |
| Java | OWASP Dependency-Check |
| Semua (lintas bahasa) | `trivy fs .` |

```bash
trivy fs --scanners vuln --severity HIGH,CRITICAL .
```

Selain kerentanan, waspadai juga:

| Risiko | Contoh | Pertahanan |
|:---|:---|:---|
| Typosquatting | Paket `reqeusts` meniru `requests` | Periksa nama paket, pakai lockfile |
| Dependency confusion | Paket publik dengan nama sama seperti paket internal | Konfigurasi registry privat dengan benar, pakai scope atau namespace |
| Paket yang diambil alih | Maintainer lama kehilangan akunnya | Kunci versi di lockfile, perbarui dengan sengaja |

Dependabot atau Renovate bisa membuka pull request otomatis saat ada versi perbaikan.

## 6. Container dan infrastructure as code

### Image container

Image container ([LC-030](../../linux/id/23.%20Containerization.md)) membawa sistem operasi kecil berikut paket-paketnya, dan paket itu juga bisa rentan.

```bash
trivy image --severity HIGH,CRITICAL myapp:1.4.2
```

Praktik baik di `Dockerfile`:

```dockerfile
FROM python:3.12-slim              # base image kecil, versi jelas
RUN useradd -m appuser
COPY --chown=appuser . /app
USER appuser                       # jangan jalan sebagai root
CMD ["python", "/app/main.py"]
```

### Infrastructure as code

Kesalahan konfigurasi cloud dari LC-077 (bucket publik, port 22 ke `0.0.0.0/0`) bisa tertangkap sebelum di-deploy kalau infrastrukturnya ditulis sebagai kode.

```hcl
resource "aws_security_group_rule" "ssh" {
  type        = "ingress"
  from_port   = 22
  to_port     = 22
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]    # akan ditandai oleh scanner IaC
}
```

```bash
checkov -d ./terraform          # atau: trivy config ./terraform
```

## 7. DAST: menguji aplikasi yang berjalan

DAST mengirim request ke aplikasi yang sedang berjalan dan melihat responsnya, seperti yang dilakukan penyerang dari luar. DAST bisa menemukan hal yang tidak terlihat dari kode, misalnya header keamanan yang hilang ([LC-046](../../web/HTTP/id/3.%20HTTP%20Headers%20%26%20Security%20Headers.md)) atau konfigurasi server yang salah.

OWASP ZAP punya mode baseline yang hanya mengamati (pasif), cocok untuk pipeline:

```bash
docker run --rm -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t https://staging.contoh.internal
```

Aturan penting: jalankan DAST hanya ke **lingkungan milikmu sendiri**, idealnya staging. Jangan arahkan ke produksi tanpa koordinasi, dan jangan ke sistem orang lain.

| | SAST | DAST |
|:---|:---|:---|
| Butuh | Kode sumber | Aplikasi berjalan |
| Kapan | Setiap commit atau pull request | Setelah deploy ke staging |
| Menemukan | Pola berbahaya di kode | Masalah konfigurasi dan perilaku runtime |
| Menunjuk baris kode | Ya | Tidak |

## 8. Menyusun pipeline CI

Contoh workflow GitHub Actions yang menggabungkan pemeriksaan di atas. Setiap job gagal kalau ada temuan tingkat tinggi, jadi pull request tidak bisa di-merge sebelum diperbaiki.

```yaml
name: security
on: [pull_request]

permissions:
  contents: read            # token hanya bisa membaca, bukan menulis

jobs:
  secrets:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: docker run --rm -v "$PWD:/src" zricethezav/gitleaks:latest detect --source /src -v

  sast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker run --rm -v "$PWD:/src" semgrep/semgrep semgrep scan --config auto --error /src

  deps-and-iac:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker run --rm -v "$PWD:/src" aquasec/trivy:latest fs --scanners vuln,misconfig --severity HIGH,CRITICAL --exit-code 1 /src
```

Catatan: di contoh ini image tool memakai tag `latest` supaya ringkas. Di pipeline sungguhan, kunci ke versi tertentu supaya perubahan tool tidak tiba-tiba mengubah hasil, dan supaya image yang dipakai tidak bisa ditukar diam-diam.

Mulailah dari yang paling murah dan paling sedikit false positive: secret scanning dan SCA. SAST dan DAST menyusul setelah tim terbiasa.

## 9. Mengamankan pipeline itu sendiri

Pipeline CI punya akses ke kode, secret deploy, dan sering ke produksi. Pipeline yang dibobol berarti penyerang bisa menyisipkan kode ke rilis resmi. Itu yang terjadi pada beberapa serangan supply chain besar.

| Risiko | Kontrol |
|:---|:---|
| Token CI dengan izin berlebihan | Set `permissions:` seminimal mungkin per workflow |
| Action pihak ketiga diganti versinya | Kunci action ke commit SHA lengkap, bukan tag |
| Pull request dari fork mencuri secret | Jangan berikan secret ke workflow yang dipicu dari fork, hati-hati dengan `pull_request_target` |
| Secret tersimpan sebagai teks di workflow | Simpan di secret store CI, atau pakai OIDC ke cloud supaya tidak ada key permanen |
| Siapa saja bisa push ke `main` | Branch protection: wajib review dan wajib lulus pemeriksaan |

Mengunci action ke SHA:

```yaml
- uses: actions/checkout@<SHA commit lengkap 40 karakter>   # v4.x, catat versinya di komentar
```

**SBOM** mendata semua komponen dalam rilis. Saat muncul kerentanan baru seperti Log4Shell, tim yang punya SBOM bisa menjawab "apakah kita terdampak?" dalam hitungan menit.

```bash
syft myapp:1.4.2 -o cyclonedx-json > sbom.json
trivy sbom sbom.json                         # pindai SBOM untuk kerentanan
```

Langkah berikutnya yang bisa dipelajari: menandatangani image dengan Sigstore cosign dan kerangka SLSA untuk asal-usul build.

## 10. Triage: supaya developer tidak tenggelam dalam alert

Tool keamanan yang menghasilkan ratusan temuan per pull request akan cepat dimatikan. Beberapa aturan supaya tetap dipakai:

1. **Blokir hanya yang kritis.** Temuan HIGH dan CRITICAL menggagalkan build, sisanya dilaporkan saja.
2. **Hanya temuan baru.** Untuk repositori lama, gagalkan build hanya pada temuan yang diperkenalkan oleh pull request itu. Temuan lama dicatat sebagai utang dan dicicil.
3. **False positive ditandai dengan alasan.** Misalnya `# nosemgrep: sql-string-concat` disertai komentar kenapa aman, supaya bisa ditinjau.
4. **Ukur.** Waktu rata-rata memperbaiki temuan kritis, dan jumlah secret yang lolos ke repositori.
5. **Security champion.** Satu developer per tim yang paham dasar keamanan dan menjadi penghubung dengan tim security.

## 11. Latihan

### Task 1: konsep

1. Apa beda SAST dan DAST?
2. Apa kepanjangan STRIDE?
3. Secret ter-commit ke repositori publik. Kenapa menghapus commit itu tidak cukup?
4. Kenapa action pihak ketiga sebaiknya dikunci ke SHA, bukan tag?

<details><summary>Kunci jawaban</summary>

1. SAST membaca kode sumber tanpa menjalankannya. DAST menguji aplikasi yang sedang berjalan dari luar.
2. Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
3. Salinannya mungkin sudah diambil orang lain atau bot. Secret harus dicabut dan diganti.
4. Tag bisa dipindahkan ke commit lain oleh pemilik repositori action, atau oleh penyerang yang membajak akunnya. SHA commit tidak bisa diubah.

</details>

### Task 2: threat model kecil

Fitur baru: "lupa password". User memasukkan email, sistem mengirim link reset yang berlaku 1 jam.

Tulis minimal satu ancaman untuk setiap huruf STRIDE, lalu satu kontrol untuk masing-masing.

<details><summary>Contoh jawaban</summary>

| STRIDE | Ancaman | Kontrol |
|:---|:---|:---|
| S | Penyerang meminta reset untuk email korban dan menebak token | Token acak panjang (minimal 128 bit), sekali pakai |
| T | Token di link diubah untuk akun lain | Token terikat ke satu akun di server, bukan berisi ID user |
| R | User menyangkal pernah meminta reset | Log permintaan reset dengan waktu dan IP |
| I | Respons berbeda untuk email terdaftar dan tidak terdaftar | Pesan yang sama: "Kalau email terdaftar, link sudah dikirim" |
| D | Ribuan permintaan reset membanjiri email korban | Rate limit per email dan per IP |
| E | Link reset tetap berlaku setelah dipakai | Token hangus setelah dipakai atau setelah 1 jam, semua sesi lama diputus |

</details>

### Task 3: pipeline di repositori latihan

Buat repositori GitHub baru milikmu, lalu:

1. Tambahkan file Python dengan query SQL yang menggabungkan string dan satu file `config.py` berisi string mirip API key palsu (misalnya `AKIAIOSFODNN7EXAMPLE`, contoh resmi dari dokumentasi AWS).
2. Tambahkan workflow dari bagian 8.
3. Buka pull request dan lihat job mana yang gagal dan kenapa.
4. Perbaiki keduanya dan pastikan semua job lulus.

<details><summary>Hal yang perlu diperhatikan</summary>

- Gitleaks akan menandai key contoh itu. Pakai hanya key contoh resmi, jangan pernah key asli.
- Semgrep dengan `--config auto` biasanya menandai penggabungan string ke `execute()`. Kalau tidak, tambahkan aturan sendiri dari bagian 4.
- Setelah perbaikan, hapus key dari kode **dan** dari riwayat Git, atau buat repositori baru. Di repositori sungguhan, key yang pernah ter-commit tetap harus dianggap bocor.

</details>

## 12. Referensi cepat

```text
DI MANA PEMERIKSAAN DIPASANG
  Desain: threat model (STRIDE) · Kode: secret scan, review · Build: SAST, SCA, image, IaC
  Staging: DAST (baseline ZAP) · Rilis: SBOM, tanda tangan · Operasi: log & monitoring

TOOL
  gitleaks detect / protect --staged      secret
  semgrep scan --config auto --error      SAST
  trivy fs|image|config --exit-code 1     SCA, image, IaC
  checkov -d .                            IaC
  zap-baseline.py -t <staging>            DAST pasif
  syft <image> -o cyclonedx-json          SBOM

PIPELINE AMAN
  permissions minimal · action dikunci ke SHA · secret tidak ke fork
  OIDC ke cloud · branch protection

TRIAGE
  blokir HIGH/CRITICAL · hanya temuan baru · false positive dengan alasan
```
