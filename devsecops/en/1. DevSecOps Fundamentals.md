## Key terms

| Term | Meaning |
|:---|:---|
| DevSecOps | A way of working that makes security a routine part of development and release, not a check at the end |
| Shift left | Moving security checks to earlier stages, while fixes are still cheap |
| SDLC | Software Development Life Cycle: planning, design, coding, testing, release, operations |
| Threat modeling | Thinking in a structured way about what could go wrong with a design before the code is written |
| SAST | Static Application Security Testing: scanning source code without running it |
| SCA | Software Composition Analysis: checking third-party libraries against vulnerability lists |
| DAST | Dynamic Application Security Testing: testing a running application from the outside |
| IaC | Infrastructure as Code: servers and networks defined in files, such as Terraform |
| CI/CD | Continuous Integration / Continuous Delivery: automatic build, test, and release on every change |
| SBOM | Software Bill of Materials: a list of every component inside a piece of software |

## 1. From DevOps to DevSecOps

Security teams used to review an application a few weeks before release. The result was a long list of findings that arrived too late, so either the release slipped or the findings were ignored.

Many teams now release several times a day. A manual review at the end cannot keep up. DevSecOps answers this by putting automated checks at every stage, and by making developers the owners of their own code's security.

```
 Plan ──► Design ──► Code ──► Build ──► Test ──► Release ──► Operate
          │          │        │         │        │           │
    threat model  secret   SAST     DAST    signing,     monitoring,
                  scan,    SCA,             SBOM         logs (LC-072)
                  review   image,
                           IaC scan
```

The cost of fixing a bug rises at every stage. A SQL injection flaw ([LC-047](../../web/Vulnerabilities/en/1.%20SQL%20Injection%20%28SQLi%29.md)) caught in review is a one-line fix. The same flaw found after customer data has leaked can end in fines and a report to the regulator.

## 2. Secure SDLC and threat modeling

Threat modeling happens at design time, before the code is written. Its four basic questions (Adam Shostack):

1. What are we building?
2. What can go wrong?
3. What are we going to do about it?
4. Did we do a good enough job?

For the second question, **STRIDE** helps make sure no category is missed:

| Letter | Threat | Property violated | Example for a profile-photo upload feature |
|:---|:---|:---|:---|
| S | Spoofing | Authentication | Uploading a photo as another user |
| T | Tampering | Integrity | Replacing someone else's photo by changing an ID in the URL |
| R | Repudiation | Non-repudiation | A user denies uploading a forbidden image, and there is no log |
| I | Information disclosure | Confidentiality | GPS metadata in the photo gets published |
| D | Denial of service | Availability | A 5 GB file fills the server's disk |
| E | Elevation of privilege | Authorization | An uploaded `.php` file is executed by the server ([LC-052](../../web/Vulnerabilities/en/6.%20File%20Upload%20Vulnerabilities%20%26%20Web%20Shells.md)) |

The output of threat modeling is a list of threats and their controls, such as "limit size to 5 MB", "strip EXIF metadata", "store in a separate bucket, not the web folder". That list becomes ordinary work tickets, like any other feature.

Free tools: OWASP Threat Dragon or the Microsoft Threat Modeling Tool for drawing data-flow diagrams. A whiteboard and an hour of discussion are also enough to start.

## 3. Secret scanning

Passwords, API keys, and tokens that get committed are one of the most common leaks. Once they reach a public repository, bots can find them within minutes.

Layers of defense:

| Layer | When | Tool |
|:---|:---|:---|
| Pre-commit hook | On the developer's laptop, before the commit | `gitleaks protect --staged` |
| CI scan | On every push and pull request | `gitleaks detect` |
| Platform scan | Continuously | GitHub secret scanning and push protection |

```bash
gitleaks detect --source . -v           # scan the whole Git history
gitleaks protect --staged -v            # scan the files about to be committed
```

If a secret has already been committed, deleting the commit is not enough. **Revoke and replace the secret**, then check the logs to see whether someone has used it. The same point was made for cloud access keys in [LC-077](../../cloud-security/en/1.%20Cloud%20Security%20Fundamentals.md).

## 4. SAST: reading the source code

SAST scans code for dangerous patterns, such as user input flowing straight into a SQL query.

```python
# Vulnerable: input concatenated into the query
cursor.execute("SELECT * FROM users WHERE name = '" + name + "'")

# Safe: parameterized query
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
```

Semgrep is an open-source SAST tool whose rules look like the code they search for:

```bash
pip install semgrep
semgrep scan --config auto .                    # community rules for the detected languages
semgrep scan --config p/owasp-top-ten --error . # fails (exit 1) if there are findings
```

A custom rule:

```yaml
rules:
  - id: sql-string-concat
    languages: [python]
    severity: ERROR
    message: SQL query built with string concatenation. Use a parameterized query.
    pattern: $CUR.execute("..." + $X)
```

| SAST strengths | SAST limits |
|:---|:---|
| Fast enough to run on every pull request | Many false positives if the rules are too broad |
| Points at the exact file and line | Cannot see server configuration or runtime behavior |
| Needs no running application | Rarely catches business-logic mistakes |

## 5. SCA: vulnerable dependencies

Most of a modern application is third-party libraries. A flaw in one popular library, such as Log4Shell in Log4j in 2021, can affect thousands of applications at once.

| Ecosystem | Built-in command |
|:---|:---|
| Python | `pip-audit` |
| Node.js | `npm audit` |
| Go | `govulncheck ./...` |
| Java | OWASP Dependency-Check |
| Any (cross-language) | `trivy fs .` |

```bash
trivy fs --scanners vuln --severity HIGH,CRITICAL .
```

Beyond known vulnerabilities, also watch for:

| Risk | Example | Defense |
|:---|:---|:---|
| Typosquatting | A package called `reqeusts` imitating `requests` | Check package names, use a lockfile |
| Dependency confusion | A public package with the same name as an internal one | Configure the private registry correctly, use scopes or namespaces |
| Hijacked packages | An old maintainer loses their account | Pin versions in a lockfile, update deliberately |

Dependabot or Renovate can open pull requests automatically when a fixed version is released.

## 6. Containers and infrastructure as code

### Container images

A container image ([LC-030](../../linux/en/23.%20Containerization.md)) carries a small operating system and its packages, and those packages can be vulnerable too.

```bash
trivy image --severity HIGH,CRITICAL myapp:1.4.2
```

Good practice in a `Dockerfile`:

```dockerfile
FROM python:3.12-slim              # small base image, explicit version
RUN useradd -m appuser
COPY --chown=appuser . /app
USER appuser                       # do not run as root
CMD ["python", "/app/main.py"]
```

### Infrastructure as code

The cloud misconfigurations from LC-077 (public buckets, port 22 open to `0.0.0.0/0`) can be caught before deployment when the infrastructure is written as code.

```hcl
resource "aws_security_group_rule" "ssh" {
  type        = "ingress"
  from_port   = 22
  to_port     = 22
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]    # will be flagged by an IaC scanner
}
```

```bash
checkov -d ./terraform          # or: trivy config ./terraform
```

## 7. DAST: testing the running application

DAST sends requests to a running application and looks at the responses, the way an attacker would from outside. It can find things that are invisible in the code, such as missing security headers ([LC-046](../../web/HTTP/en/3.%20HTTP%20Headers%20%26%20Security%20Headers.md)) or a misconfigured server.

OWASP ZAP has a baseline mode that only observes (passive), which suits a pipeline:

```bash
docker run --rm -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t https://staging.example.internal
```

An important rule: run DAST only against **environments you own**, ideally staging. Do not point it at production without coordination, and never at someone else's systems.

| | SAST | DAST |
|:---|:---|:---|
| Needs | Source code | A running application |
| When | Every commit or pull request | After deploying to staging |
| Finds | Dangerous patterns in code | Configuration and runtime problems |
| Points at a line of code | Yes | No |

## 8. Building the CI pipeline

An example GitHub Actions workflow that combines the checks above. Each job fails on high-severity findings, so a pull request cannot be merged until they are fixed.

```yaml
name: security
on: [pull_request]

permissions:
  contents: read            # the token can only read, not write

jobs:
  secrets:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: docker run --rm -v "$PWD:/src" zricethezav/gitleaks:latest detect --source /src -v

  sast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker run --rm -v "$PWD:/src" semgrep/semgrep semgrep scan --config auto --error /src

  deps-and-iac:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker run --rm -v "$PWD:/src" aquasec/trivy:latest fs --scanners vuln,misconfig --severity HIGH,CRITICAL --exit-code 1 /src
```

Note: the tool images here use the `latest` tag to keep the example short. In a real pipeline, pin them to a specific version so a tool update cannot silently change the results, and so the image cannot be swapped without anyone noticing.

Start with the checks that are cheapest and have the fewest false positives: secret scanning and SCA. Add SAST and DAST once the team is used to them.

## 9. Securing the pipeline itself

A CI pipeline has access to the code, deploy secrets, and often production. A compromised pipeline lets an attacker slip code into an official release, which is what happened in several large supply-chain attacks.

| Risk | Control |
|:---|:---|
| A CI token with too many permissions | Set `permissions:` as narrowly as possible per workflow |
| A third-party action's version gets replaced | Pin actions to a full commit SHA, not a tag |
| Pull requests from forks steal secrets | Never give secrets to workflows triggered from forks; be careful with `pull_request_target` |
| Secrets stored as plain text in the workflow | Keep them in the CI secret store, or use OIDC to the cloud so there are no permanent keys |
| Anyone can push to `main` | Branch protection: required review and required passing checks |

Pinning an action to a SHA:

```yaml
- uses: actions/checkout@<full 40-character commit SHA>   # v4.x, note the version in a comment
```

An **SBOM** lists every component in a release. When a new flaw like Log4Shell appears, a team with SBOMs can answer "are we affected?" within minutes.

```bash
syft myapp:1.4.2 -o cyclonedx-json > sbom.json
trivy sbom sbom.json                         # scan the SBOM for vulnerabilities
```

Next steps worth learning: signing images with Sigstore cosign, and the SLSA framework for build provenance.

## 10. Triage: keeping developers from drowning in alerts

A security tool that produces hundreds of findings per pull request will soon be switched off. A few rules keep it in use:

1. **Block only what is critical.** HIGH and CRITICAL findings fail the build; the rest are just reported.
2. **New findings only.** On an older repository, fail the build only on findings introduced by that pull request. Existing findings are recorded as debt and paid down over time.
3. **Mark false positives with a reason.** For example `# nosemgrep: sql-string-concat` with a comment explaining why it is safe, so it can be reviewed.
4. **Measure.** Average time to fix critical findings, and the number of secrets that reach the repository.
5. **Security champions.** One developer per team who knows the security basics and acts as the link to the security team.

## 11. Practice

### Task 1: concepts

1. What is the difference between SAST and DAST?
2. What does STRIDE stand for?
3. A secret was committed to a public repository. Why is deleting that commit not enough?
4. Why should third-party actions be pinned to a SHA rather than a tag?

<details><summary>Answer key</summary>

1. SAST reads the source code without running it. DAST tests the running application from the outside.
2. Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
3. A copy may already have been taken by a person or a bot. The secret has to be revoked and replaced.
4. A tag can be moved to a different commit by the action's owner, or by an attacker who hijacks their account. A commit SHA cannot be changed.

</details>

### Task 2: a small threat model

New feature: "forgot password". The user enters an email, and the system sends a reset link valid for 1 hour.

Write at least one threat for each letter of STRIDE, then one control for each.

<details><summary>Example answer</summary>

| STRIDE | Threat | Control |
|:---|:---|:---|
| S | An attacker requests a reset for the victim's email and guesses the token | Long random token (at least 128 bits), single use |
| T | The token in the link is altered to target another account | The token is bound to one account on the server and does not contain the user ID |
| R | A user denies ever requesting a reset | Log reset requests with time and IP |
| I | Different responses for registered and unregistered emails | The same message: "If the email is registered, a link has been sent" |
| D | Thousands of reset requests flood the victim's inbox | Rate limits per email and per IP |
| E | The reset link still works after use | The token expires after use or after 1 hour, and all old sessions are ended |

</details>

### Task 3: a pipeline in a practice repository

Create a new GitHub repository of your own, then:

1. Add a Python file with a SQL query built by string concatenation, and a `config.py` containing a fake string that looks like an API key (for example `AKIAIOSFODNN7EXAMPLE`, the official example from the AWS documentation).
2. Add the workflow from section 8.
3. Open a pull request and see which jobs fail and why.
4. Fix both and confirm every job passes.

<details><summary>Things to note</summary>

- Gitleaks will flag that example key. Use only official example keys, never a real one.
- Semgrep with `--config auto` usually flags string concatenation passed to `execute()`. If it does not, add the custom rule from section 4.
- After the fix, remove the key from the code **and** from the Git history, or create a new repository. In a real repository, a key that was ever committed must still be treated as leaked.

</details>

## 12. Quick reference

```text
WHERE CHECKS GO
  Design: threat model (STRIDE) · Code: secret scan, review · Build: SAST, SCA, image, IaC
  Staging: DAST (ZAP baseline) · Release: SBOM, signing · Operate: logs & monitoring

TOOLS
  gitleaks detect / protect --staged      secrets
  semgrep scan --config auto --error      SAST
  trivy fs|image|config --exit-code 1     SCA, image, IaC
  checkov -d .                            IaC
  zap-baseline.py -t <staging>            passive DAST
  syft <image> -o cyclonedx-json          SBOM

A SAFE PIPELINE
  minimal permissions · actions pinned to SHA · no secrets for forks
  OIDC to the cloud · branch protection

TRIAGE
  block HIGH/CRITICAL · new findings only · false positives with a reason
```
