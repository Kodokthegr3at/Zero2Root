## 重要な用語

| 用語 | 意味 |
|:---|:---|
| DevSecOps | セキュリティを最後のチェックではなく、開発とリリースの日常的な一部にする働き方 |
| シフトレフト | 修正がまだ安いうちに、セキュリティのチェックを早い段階へ移すこと |
| SDLC | ソフトウェア開発ライフサイクル。計画、設計、コーディング、テスト、リリース、運用 |
| 脅威モデリング | コードを書く前に、設計のどこで何がうまくいかなくなりうるかを体系的に考えること |
| SAST | 静的アプリケーションセキュリティテスト。ソースコードを実行せずにスキャンする |
| SCA | ソフトウェア構成分析。サードパーティのライブラリを脆弱性リストと照合する |
| DAST | 動的アプリケーションセキュリティテスト。動いているアプリケーションを外から検査する |
| IaC | Infrastructure as Code。Terraformなどで、サーバーやネットワークをファイルで定義する |
| CI/CD | 継続的インテグレーション / 継続的デリバリー。変更のたびにビルド、テスト、リリースを自動で行う |
| SBOM | ソフトウェア部品表。ソフトウェアに含まれるすべての構成要素の一覧 |

## 1. DevOpsからDevSecOpsへ

以前は、セキュリティチームがリリースの数週間前にアプリケーションを検査していた。その結果、長い指摘リストが手遅れのタイミングで届き、リリースが遅れるか、指摘が無視されるかのどちらかになった。

今では1日に何度もリリースするチームが多い。最後の手作業の検査では、その速さに追いつけない。DevSecOpsは、すべての段階に自動チェックを置き、開発者を自分のコードのセキュリティの持ち主にすることで、これに応える。

| 段階 | セキュリティのチェック |
|:---|:---|
| 計画・設計 | 脅威モデリング |
| コード | シークレットスキャン、コードレビュー |
| ビルド | SAST、SCA、イメージスキャン、IaCスキャン |
| テスト | DAST |
| リリース | 署名、SBOM |
| 運用 | 監視、ログ (LC-072) |

バグを直すコストは段階が進むごとに上がる。レビューで見つかったSQLインジェクション ([LC-047](../../web/Vulnerabilities/ja/1.%20SQL%20Injection%20%28SQLi%29.md)) なら1行の修正で済む。同じ欠陥が顧客データの漏えい後に見つかれば、罰金や規制当局への報告にまで発展しかねない。

## 2. セキュアSDLCと脅威モデリング

脅威モデリングは、コードを書く前の設計の段階で行う。基本となる四つの問い (Adam Shostack):

1. 私たちは何を作っているのか。
2. 何がうまくいかなくなりうるか。
3. それに対して何をするのか。
4. 十分にうまくやれたか。

二つ目の問いでは、**STRIDE**を使うと分類の抜けを防げる:

| 文字 | 脅威 | 損なわれる性質 | プロフィール写真のアップロード機能での例 |
|:---|:---|:---|:---|
| S | なりすまし (Spoofing) | 認証 | 別のユーザーとして写真をアップロードする |
| T | 改ざん (Tampering) | 完全性 | URLのIDを変えて他人の写真を差し替える |
| R | 否認 (Repudiation) | 否認防止 | ユーザーが禁止画像のアップロードを否定し、ログもない |
| I | 情報漏えい (Information disclosure) | 機密性 | 写真のGPSメタデータが公開されてしまう |
| D | サービス拒否 (Denial of service) | 可用性 | 5 GBのファイルがサーバーのディスクを埋める |
| E | 権限昇格 (Elevation of privilege) | 認可 | アップロードされた`.php`ファイルがサーバーで実行される ([LC-052](../../web/Vulnerabilities/ja/6.%20File%20Upload%20Vulnerabilities%20%26%20Web%20Shells.md)) |

脅威モデリングの成果は、脅威とその対策の一覧だ。たとえば「サイズを5 MBまでに制限する」「EXIFメタデータを削除する」「Webフォルダではなく別のバケットに保存する」。この一覧は、ほかの機能と同じように普通の作業チケットになる。

無料のツール: データフロー図を描くならOWASP Threat DragonかMicrosoft Threat Modeling Tool。ホワイトボードと1時間の話し合いでも始めるには十分だ。

## 3. シークレットスキャン

コミットされてしまったパスワード、APIキー、トークンは、最もよくある漏えいの一つだ。公開リポジトリに届けば、ボットが数分で見つける。

防御の層:

| 層 | タイミング | ツール |
|:---|:---|:---|
| pre-commitフック | 開発者のPCで、コミットの前 | `gitleaks protect --staged` |
| CIでのスキャン | プッシュとプルリクエストのたび | `gitleaks detect` |
| プラットフォームのスキャン | 常時 | GitHubのシークレットスキャンとプッシュ保護 |

```bash
gitleaks detect --source . -v           # Gitの履歴全体をスキャンする
gitleaks protect --staged -v            # これからコミットするファイルをスキャンする
```

シークレットをすでにコミットしてしまったなら、コミットを消すだけでは足りない。**シークレットを無効にして新しいものに替え**、ログで誰かに使われていないか確認する。クラウドのアクセスキーについても[LC-077](../../cloud-security/ja/1.%20Cloud%20Security%20Fundamentals.md)で同じことを述べた。

## 4. SAST: ソースコードを読む

SASTは、ユーザーの入力がそのままSQLクエリに入るといった危険なパターンをコードから探す。

```python
# 脆弱: 入力をクエリに連結している
cursor.execute("SELECT * FROM users WHERE name = '" + name + "'")

# 安全: パラメータ化クエリ
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
```

Semgrepはオープンソースのツールで、ルールを探したいコードに似た形で書ける:

```bash
pip install semgrep
semgrep scan --config auto .                    # 検出された言語向けのコミュニティルール
semgrep scan --config p/owasp-top-ten --error . # 指摘があれば失敗 (exit 1)
```

独自ルールの例:

```yaml
rules:
  - id: sql-string-concat
    languages: [python]
    severity: ERROR
    message: SQLクエリが文字列連結で作られている。パラメータ化クエリを使うこと。
    pattern: $CUR.execute("..." + $X)
```

| SASTの長所 | SASTの限界 |
|:---|:---|
| プルリクエストごとに実行できるほど速い | ルールが広すぎると誤検知が多い |
| ファイルと行を正確に指せる | サーバーの設定や実行時の振る舞いは見えない |
| アプリケーションを動かす必要がない | ビジネスロジックの誤りはほとんど見つからない |

## 5. SCA: 脆弱な依存関係

現代のアプリケーションの大部分はサードパーティのライブラリでできている。2021年のLog4jのLog4Shellのように、人気のライブラリ一つの欠陥が何千ものアプリケーションに同時に影響しうる。

| エコシステム | 標準のコマンド |
|:---|:---|
| Python | `pip-audit` |
| Node.js | `npm audit` |
| Go | `govulncheck ./...` |
| Java | OWASP Dependency-Check |
| すべて (言語横断) | `trivy fs .` |

```bash
trivy fs --scanners vuln --severity HIGH,CRITICAL .
```

既知の脆弱性のほかに、次にも注意する:

| リスク | 例 | 防御 |
|:---|:---|:---|
| タイポスクワッティング | `requests`をまねた`reqeusts`というパッケージ | パッケージ名を確認し、ロックファイルを使う |
| 依存関係の混同 | 社内パッケージと同じ名前の公開パッケージ | プライベートレジストリを正しく設定し、スコープや名前空間を使う |
| 乗っ取られたパッケージ | 以前のメンテナーがアカウントを失う | ロックファイルでバージョンを固定し、意図して更新する |

DependabotやRenovateは、修正版が出たときに自動でプルリクエストを作れる。

## 6. コンテナとInfrastructure as Code

### コンテナイメージ

コンテナイメージ ([LC-030](../../linux/ja/23.%20Containerization.md)) には小さなOSとそのパッケージが入っていて、それらのパッケージも脆弱でありうる。

```bash
trivy image --severity HIGH,CRITICAL myapp:1.4.2
```

`Dockerfile`の良い書き方:

```dockerfile
FROM python:3.12-slim              # 小さなベースイメージ、明示的なバージョン
RUN useradd -m appuser
COPY --chown=appuser . /app
USER appuser                       # rootで動かさない
CMD ["python", "/app/main.py"]
```

### Infrastructure as Code

LC-077で見たクラウドの設定ミス (公開バケット、`0.0.0.0/0`に開いたポート22) は、インフラをコードで書いていればデプロイ前に見つけられる。

```hcl
resource "aws_security_group_rule" "ssh" {
  type        = "ingress"
  from_port   = 22
  to_port     = 22
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]    # IaCスキャナーが指摘する
}
```

```bash
checkov -d ./terraform          # または: trivy config ./terraform
```

## 7. DAST: 動いているアプリケーションを検査する

DASTは、攻撃者が外からするように、動いているアプリケーションにリクエストを送って応答を見る。セキュリティヘッダーの欠落 ([LC-046](../../web/HTTP/ja/3.%20HTTP%20Headers%20%26%20Security%20Headers.md)) やサーバーの設定ミスなど、コードからは見えないものを見つけられる。

OWASP ZAPには観察だけを行う (パッシブな) ベースラインモードがあり、パイプラインに向いている:

```bash
docker run --rm -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t https://staging.example.internal
```

大事なルール: DASTは**自分が所有する環境**、できればステージングに対してだけ実行する。調整なしに本番に向けてはいけないし、他人のシステムには決して向けない。

| | SAST | DAST |
|:---|:---|:---|
| 必要なもの | ソースコード | 動いているアプリケーション |
| タイミング | コミットやプルリクエストのたび | ステージングへのデプロイ後 |
| 見つけるもの | コード中の危険なパターン | 設定と実行時の問題 |
| コードの行を指せるか | はい | いいえ |

## 8. CIパイプラインを組む

上のチェックを組み合わせたGitHub Actionsのワークフロー例。重大度の高い指摘があると各ジョブが失敗するので、修正するまでプルリクエストをマージできない。

```yaml
name: security
on: [pull_request]

permissions:
  contents: read            # トークンは読み取りのみで、書き込みはできない

jobs:
  secrets:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: docker run --rm -v "$PWD:/src" zricethezav/gitleaks:latest detect --source /src -v

  sast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker run --rm -v "$PWD:/src" semgrep/semgrep semgrep scan --config auto --error /src

  deps-and-iac:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker run --rm -v "$PWD:/src" aquasec/trivy:latest fs --scanners vuln,misconfig --severity HIGH,CRITICAL --exit-code 1 /src
```

注意: この例では短くするためにツールのイメージに`latest`タグを使っている。実際のパイプラインでは特定のバージョンに固定すること。ツールの更新で結果が勝手に変わらないように、またイメージが気付かれずに差し替えられないようにするためだ。

最初は、コストが低く誤検知の少ないシークレットスキャンとSCAから始める。チームが慣れてからSASTとDASTを加える。

## 9. パイプライン自体を守る

CIパイプラインはコード、デプロイ用のシークレット、そして多くの場合本番環境にアクセスできる。パイプラインが侵害されると、攻撃者は公式リリースにコードを紛れ込ませられる。いくつかの大規模なサプライチェーン攻撃で実際に起きたことだ。

| リスク | 対策 |
|:---|:---|
| 権限が多すぎるCIトークン | ワークフローごとに`permissions:`をできるだけ絞る |
| サードパーティのアクションのバージョンが差し替えられる | アクションをタグではなく完全なコミットSHAに固定する |
| フォークからのプルリクエストがシークレットを盗む | フォークから起動されたワークフローにシークレットを渡さない。`pull_request_target`に注意する |
| ワークフローにシークレットが平文で書かれている | CIのシークレットストアに保存するか、OIDCでクラウドに接続して永続的なキーをなくす |
| 誰でも`main`にプッシュできる | ブランチ保護: レビュー必須、チェックの合格必須 |

アクションをSHAに固定する:

```yaml
- uses: actions/checkout@<40文字の完全なコミットSHA>   # v4.x、バージョンをコメントに残す
```

**SBOM**はリリースに含まれるすべての構成要素を一覧にする。Log4Shellのような新しい欠陥が出たとき、SBOMがあるチームは「自分たちは影響を受けるか」に数分で答えられる。

```bash
syft myapp:1.4.2 -o cyclonedx-json > sbom.json
trivy sbom sbom.json                         # SBOMを脆弱性スキャンする
```

次に学ぶとよいもの: Sigstoreのcosignによるイメージの署名と、ビルドの来歴を扱うSLSAフレームワーク。

## 10. トリアージ: 開発者をアラートで溺れさせない

プルリクエストごとに何百もの指摘を出すセキュリティツールは、すぐに止められてしまう。使われ続けるためのルール:

1. **重大なものだけをブロックする。** HIGHとCRITICALの指摘でビルドを失敗させ、それ以外は報告だけにする。
2. **新しい指摘だけ。** 古いリポジトリでは、そのプルリクエストで入った指摘だけでビルドを失敗させる。既存の指摘は負債として記録し、少しずつ返していく。
3. **誤検知には理由を付けて印を付ける。** たとえば`# nosemgrep: sql-string-concat`に、安全な理由を書いたコメントを添える。あとでレビューできるようにするためだ。
4. **測る。** 重大な指摘の平均修正時間と、リポジトリに届いたシークレットの数。
5. **セキュリティチャンピオン。** 各チームに一人、セキュリティの基本を理解し、セキュリティチームとの橋渡しをする開発者を置く。

## 11. 演習

### Task 1: 概念

1. SASTとDASTの違いは何か。
2. STRIDEは何の略か。
3. シークレットが公開リポジトリにコミットされた。そのコミットを消すだけでは足りない理由は何か。
4. サードパーティのアクションをタグではなくSHAに固定すべき理由は何か。

<details><summary>解答</summary>

1. SASTはソースコードを実行せずに読む。DASTは動いているアプリケーションを外から検査する。
2. Spoofing、Tampering、Repudiation、Information disclosure、Denial of service、Elevation of privilege。
3. 人やボットがすでにコピーを取っているかもしれないから。シークレットは無効にして新しいものに替える必要がある。
4. タグは、アクションの所有者や、そのアカウントを乗っ取った攻撃者によって別のコミットに付け替えられる。コミットSHAは変えられない。

</details>

### Task 2: 小さな脅威モデル

新機能: 「パスワードを忘れた場合」。ユーザーがメールアドレスを入力すると、1時間有効なリセット用リンクが送られる。

STRIDEの各文字について脅威を少なくとも一つ書き、それぞれに対策を一つ書け。

<details><summary>解答例</summary>

| STRIDE | 脅威 | 対策 |
|:---|:---|:---|
| S | 攻撃者が被害者のメールでリセットを要求し、トークンを推測する | 長いランダムなトークン (128ビット以上)、使い切り |
| T | リンクのトークンを変えて別のアカウントを狙う | トークンはサーバー側で一つのアカウントに結び付け、ユーザーIDを含めない |
| R | ユーザーがリセットを要求したことを否定する | リセット要求を時刻とIPとともに記録する |
| I | 登録済みと未登録のメールで応答が異なる | 同じメッセージにする: 「登録されていればリンクを送信しました」 |
| D | 大量のリセット要求で被害者の受信箱があふれる | メールアドレスごと、IPごとのレート制限 |
| E | 使用後もリセット用リンクが有効なまま | 使用後または1時間後にトークンを失効させ、古いセッションをすべて終了する |

</details>

### Task 3: 練習用リポジトリでのパイプライン

自分の新しいGitHubリポジトリを作り、次を行う:

1. 文字列連結でSQLクエリを作るPythonファイルと、APIキーに見える偽の文字列 (たとえばAWSのドキュメントにある公式の例`AKIAIOSFODNN7EXAMPLE`) を含む`config.py`を追加する。
2. 8節のワークフローを追加する。
3. プルリクエストを作り、どのジョブがなぜ失敗するかを見る。
4. 両方を修正し、すべてのジョブが合格することを確認する。

<details><summary>注意点</summary>

- Gitleaksはこの例のキーを指摘する。使うのは公式の例のキーだけにし、本物のキーは決して使わない。
- `--config auto`のSemgrepは、たいてい`execute()`に渡す文字列連結を指摘する。指摘されなければ4節の独自ルールを追加する。
- 修正後は、キーをコード**と**Gitの履歴の両方から消すか、新しいリポジトリを作る。実際のリポジトリでは、一度コミットされたキーは漏えいしたものとして扱う。

</details>

## 12. クイックリファレンス

```text
チェックを置く場所
  設計: 脅威モデル (STRIDE) · コード: シークレットスキャン、レビュー
  ビルド: SAST、SCA、イメージ、IaC · ステージング: DAST (ZAPベースライン)
  リリース: SBOM、署名 · 運用: ログと監視

ツール
  gitleaks detect / protect --staged      シークレット
  semgrep scan --config auto --error      SAST
  trivy fs|image|config --exit-code 1     SCA、イメージ、IaC
  checkov -d .                            IaC
  zap-baseline.py -t <staging>            パッシブなDAST
  syft <image> -o cyclonedx-json          SBOM

安全なパイプライン
  権限は最小限 · アクションはSHAに固定 · フォークにシークレットを渡さない
```
