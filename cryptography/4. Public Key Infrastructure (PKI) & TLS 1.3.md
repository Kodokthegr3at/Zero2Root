## 1. 🎯 Why PKI Exists

### 🇮🇩 Bahasa Indonesia
Kriptografi kunci publik menyelesaikan distribusi kunci **hanya jika** Anda yakin $pk$ benar-benar milik `example.com`. Tanpa pengikatan identitas:

$$
\text{MITM: } pk_{\text{attacker}} \text{ disubstitusi ke korban}
$$

**PKI** adalah seperangkat peran, kebijakan, dan format (X.509) agar **Certificate Authority (CA)** menandatangani pernyataan:

$$
\mathsf{Cert} = \mathsf{Sign}_{sk_{\mathsf{CA}}}\big(\mathsf{Subject},\; pk_{\mathsf{Subject}},\; \mathsf{validity},\; \mathsf{ext}\big)
$$

Browser/OS menyimpan **trust anchors** (root CA).

### 🇬🇧 English
PKI does not invent new math primitives; it **operationalizes** signatures + policy so clients can authenticate servers (and sometimes clients) at Internet scale (Wong Ch.7/9).

### 日本語
PKIは新しい数学というより、署名と方針で「この公開鍵は本当にその名前の所有者か」を大規模に検証する仕組みです。

## 2. 🏛️ Chain of Trust

```
[ Root CA ]  self-signed, often offline HSM
      │  signs
      ▼
[ Intermediate CA ]  day-to-day issuance
      │  signs
      ▼
[ End-entity / leaf ]  CN/SAN = example.com
```

### Validasi rantai (ide)
Client menerima leaf + intermediates. Verifikasi:

$$
\begin{aligned}
&\mathsf{Verify}(pk_{\text{root}},\; \mathsf{Cert}_{\text{inter}}) \\
&\mathsf{Verify}(pk_{\text{inter}},\; \mathsf{Cert}_{\text{leaf}}) \\
&\mathsf{nameMatch}(\mathsf{Cert}_{\text{leaf}},\; \texttt{example.com}) \\
&\mathsf{timeValid}(\mathsf{now}) \land \neg\mathsf{revoked}
\end{aligned}
$$

Path building juga memeriksa **Basic Constraints** (CA:TRUE), **Key Usage**, dan kebijakan EKUs (`serverAuth`).

## 3. 📄 X.509 Certificate Anatomy (v3)

| Field | Makna |
|:---|:---|
| `Subject` | Identitas pemilik (historis); modern mengandalkan **SAN** |
| `Subject Public Key Info` | Algoritma + $pk$ |
| `Issuer` | CA yang menandatangani |
| `Serial Number` | Unik per CA — penting untuk revocation |
| `Validity` | `notBefore` / `notAfter` |
| `Signature` | Tanda tangan CA atas TBSCertificate |
| Extensions | SAN, EKU, SKI/AKI, CRL DP, OCSP AIA, CT SCTs |

**SAN (Subject Alternative Name)** adalah sumber kebenaran nama modern (`DNS:example.com`, `DNS:*.example.com`).

## 4. 🔄 Certificate Lifecycle

### 4.1 CSR (Certificate Signing Request)
Pemohon menghasilkan $(pk,sk)$, lalu:

$$
\mathsf{CSR} = \mathsf{Sign}_{sk}(\mathsf{Subject},\; pk,\; \mathsf{attrs})
$$

CA memverifikasi kontrol domain (HTTP-01, DNS-01, dll. pada ACME) sebelum menerbitkan cert.

### 4.2 Revocation
- **CRL:** daftar serial dicabut, ditandatangani CA — bisa besar/lambat.
- **OCSP:** query status serial secara online.
- **OCSP stapling:** server menyertakan respons OCSP segar → privasi & latency lebih baik.
- **Short-lived certificates** (jam/hari): mengurangi ketergantungan revocation.

### 4.3 Certificate Transparency (CT)
Log append-only publik; browser mensyaratkan **SCT**. Memudahkan deteksi penerbitan gelap/salah.

## 5. ⚡ TLS 1.3 Handshake — Mechanics & Key Schedule

TLS 1.3 (RFC 8446) menghapus RSA key transport, CBC, RC4, SHA-1 cipher suites warisan, dan memangkas handshake penuh menjadi **1-RTT** (Wong Ch.9).

### 5.1 Full handshake (sketsa)

```
Client                                                 Server
  │ ClientHello                                      │
  │  + supported_versions=1.3                        │
  │  + cipher_suites (AEAD+hash)                     │
  │  + supported_groups (e.g. x25519)                │
  │  + key_share (client ephemeral pk)               │
  │─────────────────────────────────────────────────>│
  │                                                 │
  │              ServerHello + key_share            │
  │              {EncryptedExtensions}              │
  │              {Certificate}                      │
  │              {CertificateVerify}                │
  │              {Finished}                         │
  │<─────────────────────────────────────────────────│
  │ {Finished}                                      │
  │─────────────────────────────────────────────────>│
  │══════════ Application Data (AEAD) ══════════════│
```

`{...}` = terenkripsi dengan handshake traffic keys.

### 5.2 ECDHE shared secret
$$
\mathsf{SharedSecret} = \mathsf{ECDH}(sk_C^{\text{eph}},\, pk_S^{\text{eph}})
$$

### 5.3 HKDF key schedule (intuisi formal)
TLS 1.3 menurunkan banyak kunci dari secrets bertingkat. Inti pola:

$$
\begin{aligned}
\mathsf{EarlySecret} &\leftarrow \mathsf{HKDF\text{-}Extract}(0,\, \mathsf{PSK}\ \text{or}\ 0) \\
\mathsf{HandshakeSecret} &\leftarrow \mathsf{HKDF\text{-}Extract}(\mathsf{Derive}(\ldots),\, \mathsf{SharedSecret}) \\
\mathsf{MasterSecret} &\leftarrow \mathsf{HKDF\text{-}Extract}(\mathsf{Derive}(\ldots),\, 0) \\
\mathsf{TrafficKeys} &\leftarrow \mathsf{HKDF\text{-}Expand\text{-}Label}(\mathsf{Secret},\, \mathsf{label},\, \mathsf{TranscriptHash},\, L)
\end{aligned}
$$

**Transcript hash** mengikat semua handshake messages:

$$
\mathsf{TranscriptHash} = H(\mathsf{ClientHello}\,\|\,\ldots\,\|\,\mathsf{Finished})
$$

`CertificateVerify` = tanda tangan digital server atas transcript → membuktikan kepemilikan private key sertifikat **dan** mengikat ke ECDHE segar (authenticated key exchange).

### 5.4 Finished
$$
\mathsf{Finished} = \mathsf{HMAC}(\mathsf{FinishedKey},\, \mathsf{TranscriptHash})
$$

Memastikan kedua pihak melihat transcript identik (anti-downgrade/tamper).

## 6. 🔒 Record Layer — Encrypting Application Data

Setelah traffic keys siap, setiap record:

$$
\mathsf{ciphertext} \leftarrow \mathsf{AEAD}_{key}^{nonce}(\mathsf{plaintext}\,\|\,\mathsf{content\_type})
$$

Cipher suites modern contoh:
- `TLS_AES_128_GCM_SHA256`
- `TLS_AES_256_GCM_SHA384`
- `TLS_CHACHA20_POLY1305_SHA256`

Nonce TLS 1.3 dikonstruksi dari sequence number XOR IV statis — **jangan reuse** connection keys di luar state machine TLS.

## 7. 🛡️ Perfect Forward Secrecy (PFS) & 0-RTT

### PFS
Jika $sk$ jangka panjang server bocor di masa depan, sesi lalu tetap aman karena traffic keys bergantung pada **ephemeral** ECDHE:

$$
\text{leak } sk_{\text{long-term}} \not\Rightarrow \text{decrypt old } \mathsf{AEAD}\text{ records}
$$

TLS 1.3 **mewajibkan** (EC)DHE (kecuali PSK-only mode yang dirancang sadar risiko).

### 0-RTT (early data)
Dengan PSK resumed, client bisa mengirim data di flight pertama. Trade-off: **replay risk**. Aplikasi harus idempotent atau menolak 0-RTT untuk operasi sensitif.

## 8. ⚠️ Threats & Defenses (Konseptual)

| Threat | Idea | Defense |
|:---|:---|:---|
| Rogue/compromised CA | Cert palsu untuk domain Anda | CT monitoring, CAA DNS, pinning terbatas |
| MITM with stolen leaf key | Impersonation | Short-lived certs, HSM, rapid revoke |
| SSL stripping | Downgrade ke HTTP | HSTS, HTTPS-only |
| Weak verification | Skip hostname / trust-all | Default verifier OS/browser, no custom `InsecureSkipVerify` in prod |
| DNS hijack to attacker cert | Jika CA salah terbitkan | CAA + CT + DNSSEC (lapisan tambahan) |

**Certificate pinning:** mengikat app ke SPKI tertentu — efektif untuk mobile controlled apps, tetapi operasionalnya rapuh (rotasi kunci). Prefer CT + modern PKI hygiene untuk web publik.

## 9. 🛠️ OpenSSL Cheatsheet

```bash
# ── CSR (RSA) ────────────────────────────────────────────────
openssl req -new -newkey rsa:4096 -nodes \
  -keyout example.com.key -out example.com.csr \
  -subj "/C=ID/O=LearnCyber/CN=example.com"

# ── Self-signed lab cert (ECDSA P-256) ───────────────────────
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -days 365 -nodes -keyout server.key -out server.crt \
  -subj "/CN=localhost"

# ── Inspect remote chain ─────────────────────────────────────
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# ── Verify chain ─────────────────────────────────────────────
openssl verify -CAfile ca_chain.pem example.com.crt

# ── Show cert fields ─────────────────────────────────────────
openssl x509 -in server.crt -noout -text -fingerprint -sha256

# ── Test TLS 1.3 only ────────────────────────────────────────
openssl s_client -connect example.com:443 -tls1_3 -servername example.com </dev/null
```

## 🔐 Security Notes — Operator Checklist

1. Nonaktifkan TLS < 1.2 di server produksi; prefer TLS 1.3.
2. Cipher: AEAD only; aktifkan OCSP stapling.
3. HSTS + redirect HTTPS; pertimbangkan CAA records.
4. Private key: permission `0600`, idealnya HSM/KMS; jangan commit ke git.
5. Monitor CT logs untuk domain Anda.
