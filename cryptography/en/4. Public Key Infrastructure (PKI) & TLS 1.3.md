## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| PKI | Public Key Infrastructure: the whole system of authorities, certificates, and rules that tells you which public key belongs to whom |
| Certificate | A digital ID card: "this public key belongs to example.com", signed by a trusted authority |
| CA | Certificate Authority: an organization trusted to check identities and sign certificates |
| Root CA | The top-level CA. Its certificate comes pre-installed in your browser or OS |
| Intermediate CA | A CA that the root has authorized to sign certificates on its behalf |
| Leaf certificate | The certificate of the actual website or server |
| CSR | Certificate Signing Request: the "application form" you send to a CA |
| Revocation | Cancelling a certificate before it expires, for example after its key leaked |
| TLS | The protocol that puts the "S" in HTTPS: it encrypts and authenticates network connections |
| Handshake | The first few messages of a TLS connection, where both sides agree on keys and check identity |
| Forward secrecy (PFS) | A leaked server key later doesn't expose past recorded connections |

## 1. Why PKI Exists

Public-key crypto (LC-055) lets anyone encrypt to you using your public key. But there's a catch: **how do you know a public key really belongs to `example.com`?**

Without an answer, an attacker sitting between you and the server can simply hand you **their own** public key and pretend to be the server. You would encrypt everything to the attacker, who reads it and passes it on. This is a **man-in-the-middle (MITM)** attack, and you'd have no way to notice.

PKI solves this the way passports do. A trusted authority (the **CA**) checks who you are, then signs a statement:

```text
Certificate = CA's signature over {
    name:        example.com
    public key:  <the server's public key>
    valid from:  2026-01-01   until: 2026-04-01
    extensions:  allowed uses, where to check revocation, ...
}
```

Your browser and operating system come with a built-in list of CAs they trust (the **trust anchors**, or root CAs). If a certificate is signed by one of them, the browser accepts that the key really belongs to that name.

PKI doesn't use any new math. It's digital signatures (LC-055) plus a set of rules, operated at Internet scale (Wong, Ch.7/9).

## 2. The Chain of Trust

Root CAs are too important to use every day, so they're usually kept offline in a hardware security module (HSM). Instead, they authorize **intermediate CAs** to do the daily signing:

```
[ Root CA ]  self-signed, often offline HSM
      │  signs
      ▼
[ Intermediate CA ]  day-to-day issuance
      │  signs
      ▼
[ End-entity / leaf ]  CN/SAN = example.com
```

### How your browser checks a certificate

The server sends its leaf certificate plus the intermediate(s). The browser then checks:

```text
1. the root's public key verifies the intermediate's signature
2. the intermediate's public key verifies the leaf's signature
3. the name in the leaf certificate matches the site you typed (example.com)
4. today's date is inside the validity period, and the certificate isn't revoked
```

It also checks a few rules written inside the certificates: an intermediate must be marked as allowed to act as a CA (`CA:TRUE`), and the leaf must be allowed to be used for websites (`serverAuth`).

If any step fails, you get the familiar "Your connection is not private" warning.

## 3. What's Inside a Certificate (X.509 v3)

| Field | What it means |
|:---|:---|
| `Subject` | Who the certificate is for (older field; today the SAN is what matters) |
| `Subject Public Key Info` | The public key itself, and which algorithm it uses |
| `Issuer` | Which CA signed it |
| `Serial Number` | A unique number per CA, used when revoking |
| `Validity` | `notBefore` / `notAfter`: the start and end dates |
| `Signature` | The CA's signature over all the fields above |
| Extensions | SAN, allowed uses (EKU), key IDs, where to check revocation (CRL/OCSP), CT proofs |

The **SAN** (Subject Alternative Name) is where the real list of names lives, for example `DNS:example.com` and `DNS:*.example.com`. Browsers check the SAN, not the old `Subject` field.

## 4. A Certificate's Life

### 4.1 Requesting a certificate (CSR)

1. You generate your own key pair. The private key never leaves your server.
2. You create a **CSR** containing your name and public key, and sign it with your private key. This proves you really hold the matching private key.
3. The CA checks that you control the domain. With the ACME protocol (used by Let's Encrypt) that means placing a file on your website (HTTP-01) or adding a DNS record (DNS-01).
4. The CA signs and returns your certificate.

### 4.2 Revocation: cancelling a certificate early

If a private key leaks, the certificate must be cancelled before it expires. The options:

| Method | How it works | Downside |
|:---|:---|:---|
| CRL | The CA publishes a signed list of cancelled serial numbers | Lists get big and update slowly |
| OCSP | The browser asks the CA "is this serial still valid?" | Slower, and tells the CA which sites you visit |
| OCSP stapling | The server fetches a fresh OCSP answer itself and attaches it | Faster and more private |
| Short-lived certificates | Certificates valid only for days | Revocation matters much less |

In practice revocation is unreliable, which is why the industry is moving toward short-lived certificates.

### 4.3 Certificate Transparency (CT)

Every publicly trusted certificate must be recorded in public, append-only **CT logs**, and browsers demand proof of this (an SCT). This means a CA can't secretly issue a fake certificate for your domain: you can monitor the logs and spot it.

## 5. The TLS 1.3 Handshake, Step by Step

TLS 1.3 (RFC 8446) is a big cleanup of older TLS. It removed weak options (RSA key transport, CBC mode, RC4, SHA-1-based suites), and a full handshake now needs only **one round trip** (Wong, Ch.9).

```
Client                                                 Server
  │ ClientHello                                      │
  │  + supported_versions=1.3                        │
  │  + cipher_suites (AEAD+hash)                     │
  │  + supported_groups (e.g. x25519)                │
  │  + key_share (client ephemeral pk)               │
  │─────────────────────────────────────────────────>│
  │                                                 │
  │              ServerHello + key_share            │
  │              {EncryptedExtensions}              │
  │              {Certificate}                      │
  │              {CertificateVerify}                │
  │              {Finished}                         │
  │<─────────────────────────────────────────────────│
  │ {Finished}                                      │
  │─────────────────────────────────────────────────>│
  │══════════ Application Data (AEAD) ══════════════│
```

`{...}` means the message is already encrypted.

What happens, in plain words:

1. **ClientHello:** the client says which TLS versions and ciphers it supports, and immediately sends its half of a temporary key exchange (an ECDHE `key_share`, for example X25519).
2. **ServerHello:** the server picks the cipher and sends its own half of the key exchange. Now both sides can calculate the same shared secret (the ECDH idea from LC-055). **Everything after this point is encrypted.**
3. **Certificate:** the server sends its certificate chain (Section 2).
4. **CertificateVerify:** the server signs a hash of the whole conversation so far with its certificate's private key. This proves it really owns the certificate, *and* that it's taking part in this exact handshake right now.
5. **Finished (both sides):** each side sends an HMAC over the whole conversation. If an attacker changed or removed any earlier message (for example to force weaker settings), the values won't match and the connection is dropped.

### Where the keys come from

The shared ECDHE secret is not used directly. TLS 1.3 feeds it through HKDF (LC-056) in stages, producing separate keys for each purpose:

```text
(optional PSK)      → early secret
+ ECDHE secret      → handshake secret  → keys that protect the rest of the handshake
                    → master secret     → keys that protect the actual application data
```

A hash of every handshake message (the **transcript hash**) is mixed in along the way. So the final keys belong to this one specific conversation and nothing else.

## 6. Encrypting the Actual Data

Once the handshake is done, every piece of data (each **record**) is protected with AEAD (LC-054), which gives both secrecy and tamper detection:

```text
encrypted record = AEAD(traffic key, nonce, data + content type)
```

TLS 1.3 only allows a few cipher suites, all of them AEAD:
- `TLS_AES_128_GCM_SHA256`
- `TLS_AES_256_GCM_SHA384`
- `TLS_CHACHA20_POLY1305_SHA256`

The nonce for each record is built from a record counter, so it never repeats. That's why you must never take TLS keys and reuse them anywhere outside TLS.

## 7. Forward Secrecy and 0-RTT

### Forward secrecy (PFS)

Imagine someone records all your encrypted traffic today, and years later steals the server's private key. Can they decrypt the old recordings?

With TLS 1.3: **no.** The traffic keys come from a temporary (ephemeral) ECDHE key pair that was thrown away after the connection. The server's long-term key only *signs* the handshake; it never protects the traffic keys.

TLS 1.3 requires (EC)DHE for this reason. The only exception is a "PSK-only" mode, which deliberately gives up forward secrecy for specific use cases.

### 0-RTT (early data)

When a client reconnects to a server it visited recently, it can send data in its very first message, saving a round trip. The trade-off: an attacker can record that first message and **replay** it.

So 0-RTT is only safe for requests that do no harm when repeated, like loading a page (GET). Never allow 0-RTT for actions like payments or password changes.

## 8. Threats and Defenses

| Threat | What happens | Defense |
|:---|:---|:---|
| Rogue or hacked CA | Someone gets a valid fake certificate for your domain | Monitor CT logs, set CAA DNS records |
| Stolen server private key | The attacker can impersonate the server | Short-lived certificates, keys in an HSM, fast revocation |
| SSL stripping | The attacker downgrades the visitor to plain HTTP | HSTS, HTTPS-only |
| Broken certificate checks | App skips the hostname check or trusts everything | Use the OS/browser default verifier; never ship `InsecureSkipVerify` |
| DNS hijack leading to a mis-issued certificate | The attacker controls DNS and gets a certificate | CAA, CT monitoring, DNSSEC |

**Certificate pinning** means an app only accepts one specific key or certificate. It works well for mobile apps that you fully control, but it breaks easily when keys rotate. For public websites, CT monitoring plus good certificate hygiene is the better choice.

## 9. OpenSSL Cheatsheet

```bash
# ── Create a private key + CSR (RSA) ─────────────────────────
openssl req -new -newkey rsa:4096 -nodes \
  -keyout example.com.key -out example.com.csr \
  -subj "/C=ID/O=LearnCyber/CN=example.com"

# ── Self-signed certificate for a lab (ECDSA P-256) ──────────
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -days 365 -nodes -keyout server.key -out server.crt \
  -subj "/CN=localhost"

# ── See the certificate chain a server sends ─────────────────
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# ── Verify a certificate against a CA bundle ─────────────────
openssl verify -CAfile ca_chain.pem example.com.crt

# ── Read a certificate's fields ──────────────────────────────
openssl x509 -in server.crt -noout -text -fingerprint -sha256

# ── Test that a server supports TLS 1.3 ──────────────────────
openssl s_client -connect example.com:443 -tls1_3 -servername example.com </dev/null
```

## Security Notes: Operator Checklist

1. Turn off everything below TLS 1.2 on production servers, and prefer TLS 1.3.
2. Allow only AEAD cipher suites, and enable OCSP stapling.
3. Turn on HSTS and redirect HTTP to HTTPS. Consider CAA records.
4. Protect private keys: `0600` permissions, ideally in an HSM/KMS, and **never** commit them to git.
5. Watch the Certificate Transparency logs for certificates issued for your domains.
