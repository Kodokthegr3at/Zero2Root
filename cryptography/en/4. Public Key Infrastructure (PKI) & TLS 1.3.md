## 1. Why PKI Exists

Public-key cryptography solves key distribution only if you're confident that pk genuinely belongs to `example.com`. Without a binding to identity, an attacker can run a man-in-the-middle attack:

the attacker simply swaps the server's real public key for their own, and the victim has no way to notice.

PKI is a set of roles, policies, and formats (X.509) built around a Certificate Authority (CA) signing a statement:

```text
Cert = Sign(sk_CA, {Subject, pk_Subject, validity, extensions})
```

In words: the CA uses its private key to sign a statement that says "this public key belongs to this name, and is valid for this period."

Browsers and operating systems store trust anchors (root CAs) that underlie every verification.

PKI does not invent new math primitives. It operationalizes digital signatures plus policy so clients can authenticate servers, and sometimes clients, at Internet scale (Wong, Ch.7/9).

## 2. Chain of Trust

```
[ Root CA ]  self-signed, often offline HSM
      │  signs
      ▼
[ Intermediate CA ]  day-to-day issuance
      │  signs
      ▼
[ End-entity / leaf ]  CN/SAN = example.com
```

### Chain validation (the idea)

The client receives the leaf certificate along with its intermediates, then verifies:

```text
1. the root's public key verifies the intermediate certificate
2. the intermediate's public key verifies the leaf certificate
3. the name in the leaf matches example.com
4. the certificate is not expired and not revoked
```

Path building also checks Basic Constraints (CA:TRUE), Key Usage, and Extended Key Usage policies such as `serverAuth`.

## 3. X.509 Certificate Anatomy (v3)

| Field | Meaning |
|:---|:---|
| `Subject` | Owner identity (historical); modern practice relies on SAN |
| `Subject Public Key Info` | Key algorithm plus pk |
| `Issuer` | The CA that signed the certificate |
| `Serial Number` | Unique per CA; matters for revocation |
| `Validity` | `notBefore` / `notAfter` |
| `Signature` | The CA's signature over the TBSCertificate |
| Extensions | SAN, EKU, SKI/AKI, CRL DP, OCSP AIA, CT SCTs |

SAN (Subject Alternative Name) is the modern source of truth for names, for example `DNS:example.com` or `DNS:*.example.com`.

## 4. Certificate Lifecycle

### 4.1 CSR (Certificate Signing Request)

The applicant generates a key pair (pk,sk), then builds a request:

```text
CSR = Sign(sk, {Subject, pk, attributes})
```

Signing the request with sk proves that the applicant really holds the matching private key.

The CA verifies domain control (for example HTTP-01 or DNS-01 under the ACME protocol) before issuing the certificate.

### 4.2 Revocation

- CRL: a list of revoked serial numbers, signed by the CA. Can grow large and slow to update.
- OCSP: an online query for a single serial number's status.
- OCSP stapling: the server attaches a fresh OCSP response, improving both privacy and latency.
- Short-lived certificates (hours to days): reduce reliance on revocation altogether.

### 4.3 Certificate Transparency (CT)

A public, append-only log. Browsers require an SCT (Signed Certificate Timestamp). CT makes it far easier to detect mis-issued or fraudulent certificates.

## 5. TLS 1.3 Handshake: Mechanics and Key Schedule

TLS 1.3 (RFC 8446) removes RSA key transport, CBC mode, RC4, and legacy SHA-1-based cipher suites, and trims a full handshake down to 1-RTT (Wong, Ch.9).

### 5.1 Full handshake sketch

```
Client                                                 Server
  │ ClientHello                                      │
  │  + supported_versions=1.3                        │
  │  + cipher_suites (AEAD+hash)                     │
  │  + supported_groups (e.g. x25519)                │
  │  + key_share (client ephemeral pk)               │
  │─────────────────────────────────────────────────>│
  │                                                 │
  │              ServerHello + key_share            │
  │              {EncryptedExtensions}              │
  │              {Certificate}                      │
  │              {CertificateVerify}                │
  │              {Finished}                         │
  │<─────────────────────────────────────────────────│
  │ {Finished}                                      │
  │─────────────────────────────────────────────────>│
  │══════════ Application Data (AEAD) ══════════════│
```

`{...}` marks messages encrypted with the handshake traffic key.

### 5.2 ECDHE shared secret

```text
SharedSecret = ECDH(client's temporary private key, server's temporary public key)
```

### 5.3 HKDF key schedule (formal intuition)

TLS 1.3 derives many keys from a chain of secrets. The core pattern:

```text
PSK or 0         → EarlySecret
+ ECDHE secret   → HandshakeSecret  → handshake traffic keys
+ 0              → MasterSecret     → application traffic keys
```

Each step feeds the previous secret into HKDF together with new input. The transcript hash is mixed in along the way, so the keys are tied to this exact handshake.

The transcript hash binds every handshake message:

```text
TranscriptHash = Hash(ClientHello ‖ ServerHello ‖ ... ‖ Finished)
```

`CertificateVerify` is the server's digital signature over the transcript. It proves possession of the certificate's private key while also binding it to a fresh ECDHE exchange (authenticated key exchange).

### 5.4 Finished

```text
Finished = HMAC(FinishedKey, TranscriptHash)
```

Confirms both sides saw an identical transcript, defending against downgrade and tampering.

## 6. Record Layer: Encrypting Application Data

Once traffic keys are ready, every record is processed as:

```text
ciphertext = AEAD(key, nonce, plaintext ‖ content_type)
```

Example modern cipher suites:
- `TLS_AES_128_GCM_SHA256`
- `TLS_AES_256_GCM_SHA384`
- `TLS_CHACHA20_POLY1305_SHA256`

The TLS 1.3 nonce is built from a sequence number XORed with a static IV. Never reuse connection keys outside the TLS state machine.

## 7. Perfect Forward Secrecy (PFS) and 0-RTT

### PFS

If the server's long-term private key leaks in the future, past sessions stay safe because traffic keys depend on an ephemeral ECDHE exchange:

Leaking the long-term private key later does **not** let anyone decrypt old recorded sessions.

TLS 1.3 requires (EC)DHE, except in PSK-only mode, which is deliberately designed with this trade-off understood.

### 0-RTT (early data)

With a resumed PSK, the client can send data in the very first flight. The trade-off is replay risk. Applications must be idempotent, or must reject 0-RTT for sensitive operations.

## 8. Threats and Defenses (Conceptual)

| Threat | Idea | Defense |
|:---|:---|:---|
| Rogue or compromised CA | Fraudulent certificate for your domain | CT monitoring, CAA DNS records, limited pinning |
| MITM with a stolen leaf key | Impersonation | Short-lived certs, HSM, rapid revocation |
| SSL stripping | Downgrade to HTTP | HSTS, HTTPS-only |
| Weak verification | Skipping hostname checks or trusting everything | Default OS/browser verifier; no `InsecureSkipVerify` in production |
| DNS hijack toward an attacker's cert | If a CA mis-issues | CAA, CT, and DNSSEC as additional layers |

Certificate pinning binds an app to a specific SPKI. It works well for mobile apps the owner fully controls, but it's operationally fragile because of key rotation. For public web traffic, CT plus modern PKI hygiene is the better default.

## 9. OpenSSL Cheatsheet

```bash
# ── CSR (RSA) ────────────────────────────────────────────────
openssl req -new -newkey rsa:4096 -nodes \
  -keyout example.com.key -out example.com.csr \
  -subj "/C=ID/O=LearnCyber/CN=example.com"

# ── Self-signed lab cert (ECDSA P-256) ───────────────────────
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -days 365 -nodes -keyout server.key -out server.crt \
  -subj "/CN=localhost"

# ── Inspect remote chain ─────────────────────────────────────
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# ── Verify chain ─────────────────────────────────────────────
openssl verify -CAfile ca_chain.pem example.com.crt

# ── Show cert fields ─────────────────────────────────────────
openssl x509 -in server.crt -noout -text -fingerprint -sha256

# ── Test TLS 1.3 only ────────────────────────────────────────
openssl s_client -connect example.com:443 -tls1_3 -servername example.com </dev/null
```

## Security Notes: Operator Checklist

1. Disable TLS below 1.2 on production servers; prefer TLS 1.3.
2. Use AEAD cipher suites only; enable OCSP stapling.
3. Apply HSTS and redirect to HTTPS; consider CAA records.
4. Private keys need `0600` permissions, ideally live in an HSM/KMS, and should never be committed to git.
5. Monitor Certificate Transparency logs for your domains.
