## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| Plaintext | The original, readable message |
| Ciphertext | The scrambled message after encryption |
| Key | The secret value that locks and unlocks the message |
| Symmetric | The same key is used to encrypt and to decrypt |
| Block cipher | Encrypts data in fixed-size chunks (AES uses 16-byte blocks) |
| Stream cipher | Encrypts data bit by bit, by mixing it with a stream of random-looking bits |
| XOR | A simple bit operation: 0⊕0=0, 1⊕1=0, 0⊕1=1. Doing it twice with the same value gives you back the original |
| IV / nonce | A "number used once": a value that must be different for every message, so the same message never encrypts the same way twice |
| Mode of operation | The rules for encrypting a message that is longer than one block |
| MAC / tag | A short checksum made with a secret key. It proves the message wasn't changed |
| AEAD | Encryption that also includes a tag, so you get secrecy *and* tamper detection in one step (for example AES-GCM) |

## 1. What Cryptography Is Trying to Achieve

Cryptography protects data from people who are actively trying to read it or change it (David Wong, *Real-World Cryptography*, Ch.1). It usually aims for four things:

| Goal | Question it answers | Typical tool |
|:---|:---|:---|
| Confidentiality | Can anyone else read this? | Encryption |
| Integrity | Was this changed on the way? | MAC, AEAD tag |
| Authentication | Did this really come from who I think? | MAC, digital signature |
| Non-repudiation | Can the sender later deny sending it? | Digital signature |

Symmetric encryption on its own only gives you **confidentiality**. An attacker who can't read the message might still be able to change it. That's why modern systems use AEAD (AES-GCM or ChaCha20-Poly1305), which adds a tag to catch tampering.

## 2. How Symmetric Encryption Works

Think of a lockbox with one key, and both people have a copy of that key. One locks the box, the other unlocks it.

A symmetric scheme is made of three steps:

```text
KeyGen()   → k     create a secret key
Enc(k, m)  → c     encrypt message m into ciphertext c
Dec(k, c)  → m     decrypt c back into m
```

Two rules must always hold:

1. **It works both ways.** If you encrypt and then decrypt with the same key, you get the original message back.
2. **The ciphertext gives nothing away.** Someone who sees the ciphertext should learn nothing about the message, except roughly how long it is.

### Keep the key secret, not the algorithm

This idea is called **Kerckhoffs's principle**: the system must stay secure even if the attacker knows exactly which algorithm you use. AES is public, and everyone knows how it works. Your security comes only from keeping the key secret. A "secret algorithm" is not protection; sooner or later someone reverse-engineers it.

### Symmetric vs asymmetric at a glance

| | Symmetric | Asymmetric |
|:---|:---|:---|
| Keys | 1 shared secret | A public key + a private key |
| Speed | Very fast (CPUs have AES instructions) | Much slower |
| Typical sizes | AES-128 / AES-256 | RSA-2048+ / ECC-256+ |
| Main use | Encrypting the actual data: files, disks, network traffic | Agreeing on keys, signatures |
| What the attacker must do | Try every possible key | Solve a hard math problem (factoring, discrete log) |

The big weakness of symmetric crypto is getting the key to the other person safely. That's the problem asymmetric crypto solves (see LC-055).

## 3. Block Ciphers vs Stream Ciphers

### Block cipher

A block cipher takes one fixed-size chunk of plaintext plus the key, and outputs one chunk of ciphertext of the same size:

```text
C = E(k, P)        P = one plaintext block, C = one ciphertext block
```

AES always works on 128-bit (16-byte) blocks. A message longer than that has to be split into blocks, and a **mode of operation** (Section 5) decides how those blocks are linked together.

### Stream cipher

A stream cipher turns the key into a long stream of random-looking bits (the **keystream**), then XORs it with the message:

```text
ciphertext = message XOR keystream
message    = ciphertext XOR keystream     (XOR twice gives the original back)
```

The modern example is **ChaCha20**, usually paired with **Poly1305** for the tag.

Golden rule for stream ciphers: **never reuse the same keystream**. If two messages are XORed with the same keystream, an attacker can XOR the two ciphertexts together and the keystream cancels out, leaving the two messages mixed together. From there, guessing both messages is often easy.

## 4. Inside AES

AES (Advanced Encryption Standard, originally called Rijndael) won a public NIST competition and is now used almost everywhere (Wong, Ch.4).

| Variant | Key size | Rounds | Block size |
|:---|:---:|:---:|:---:|
| AES-128 | 128 bit | 10 | 128 bit |
| AES-192 | 192 bit | 12 | 128 bit |
| AES-256 | 256 bit | 14 | 128 bit |

AES treats the 16-byte block as a 4 × 4 grid of bytes, called the **state**. It then repeats the same four steps (a **round**) several times. Each round mixes the data a little more, until the output looks completely random.

```
┌──────────────────────────────────────────────────────────┐
│                    AES ENCRYPTION FLOW                   │
│  Plaintext (128-bit)                                     │
│       │                                                  │
│       ▼                                                  │
│  AddRoundKey (K0)                                        │
│       │                                                  │
│   ┌───┴───────────────────────────────┐                  │
│   │  Repeat Nr-1 times:               │                  │
│   │   SubBytes → ShiftRows →          │                  │
│   │   MixColumns → AddRoundKey (Kr)   │                  │
│   └───────────────────────────────────┘                  │
│       │                                                  │
│  Final: SubBytes → ShiftRows → AddRoundKey (K_Nr)        │
│       │                                                  │
│       ▼                                                  │
│  Ciphertext (128-bit)                                    │
└──────────────────────────────────────────────────────────┘
```

What each step does, in plain words:

| Step | What it does | Why it matters |
|:---|:---|:---|
| **SubBytes** | Replaces every byte with another byte from a fixed lookup table (the **S-box**) | This is the only non-linear step. Without it, AES could be solved like a system of simple equations |
| **ShiftRows** | Slides row 1 left by 1 position, row 2 by 2, row 3 by 3 | Spreads bytes across different columns |
| **MixColumns** | Mixes the 4 bytes in each column together | Changing one input byte now changes the whole column |
| **AddRoundKey** | XORs the state with a **round key** derived from your key | This is where the key actually enters the process |

After a few rounds, changing a single bit of the plaintext or the key changes about half of the output bits. This effect is called **diffusion**, or the avalanche effect.

The last round skips MixColumns. That's a design detail that makes decryption mirror encryption neatly.

> The S-box and MixColumns use arithmetic in a special number system called GF(2⁸), where "addition" is XOR. You don't need it to use AES. You only need it if you implement AES yourself, and you shouldn't: use a vetted library.

### How hard is it to break AES by brute force?

AES-128 has 2¹²⁸ possible keys, about 3.4 × 10³⁸ (a 39-digit number). On average an attacker finds the right key after trying half of them.

Even if a machine could test 10¹² keys per second (a trillion), that would still take around 5 × 10¹⁸ years, hundreds of millions of times the age of the universe.

So in practice nobody breaks AES by guessing the key. Real attacks go after **how AES is used**: weak key management, reused nonces, missing integrity checks, or side channels like timing.

## 5. Modes of Operation: From ECB to AEAD

AES only encrypts one 16-byte block. A mode of operation decides how to handle a longer message. Picking the wrong mode is one of the most common crypto mistakes.

### 5.1 ECB (Electronic Codebook): don't use it

Each block is encrypted on its own with the same key:

```text
C1 = E(k, P1)    C2 = E(k, P2)    C3 = E(k, P3)  ...
```

The problem: **identical plaintext blocks produce identical ciphertext blocks.** Patterns in the data stay visible. The famous example is the "ECB penguin": encrypt a picture of a penguin with ECB, and you can still clearly see the penguin in the encrypted image.

### 5.2 CBC (Cipher Block Chaining)

Before a block is encrypted, it's XORed with the previous ciphertext block. The first block uses a random **IV** instead:

```text
C1 = E(k, P1 XOR IV)
C2 = E(k, P2 XOR C1)
C3 = E(k, P3 XOR C2)  ...
```

Each block now depends on everything before it, so identical blocks no longer look identical.

Rules for CBC:
- The IV must be random and unpredictable, and new for every message.
- CBC hides the data, but it **doesn't detect tampering**. An attacker can flip bits in the ciphertext and cause predictable changes in the decrypted text. CBC must always be paired with a MAC (encrypt first, then add an HMAC over the ciphertext: "encrypt-then-MAC").

### 5.3 CTR (Counter Mode)

CTR turns AES into a stream cipher. Instead of encrypting the message, you encrypt a counter (nonce + 1, nonce + 2, ...) to produce a keystream, then XOR it with the message:

```text
keystream block i = E(k, nonce ‖ counter i)
Ci = Pi XOR keystream block i
```

Advantages: it can run in parallel, and no padding is needed. The big rule: **a nonce must never repeat with the same key**, or you are back to the reused-keystream problem from Section 3.

### 5.4 GCM (Galois/Counter Mode): the modern default

GCM = CTR mode for encryption + a built-in authentication tag. This is **AEAD**: one operation gives you both secrecy and tamper detection.

```text
encrypt:  (ciphertext, tag) = AES-GCM(key, nonce, plaintext, extra_data)
decrypt:  check the tag first → if it doesn't match, throw everything away
```

- The tag is usually 16 bytes.
- `extra_data` (AAD, "additional authenticated data") is data that stays readable but is still protected from tampering, such as a packet header.
- **If the tag check fails, reject the whole message.** Never "decrypt anyway."
- Like CTR, GCM falls apart if a nonce is ever reused with the same key. With GCM it's even worse: a repeated nonce can let an attacker forge tags.

### Summary

| Mode | Hides data | Detects tampering | Parallel | Verdict |
|:---|:---:|:---:|:---:|:---|
| ECB | Leaks patterns | No | Yes | Broken for almost everything |
| CBC | Yes | No | Decryption only | OK only with a MAC; IV must be random |
| CTR | Yes | No | Yes | Needs a MAC; nonce must be unique |
| GCM | Yes | Yes | Yes | Standard in TLS; never reuse a nonce |
| ChaCha20-Poly1305 | Yes | Yes | Yes | Great on devices without AES hardware |

Wong's advice still holds: **encryption without authentication is dangerous.** Use a ready-made AEAD (AES-GCM or ChaCha20-Poly1305) rather than gluing CBC and HMAC together yourself. If you must combine them, use encrypt-then-MAC with two separate keys, compare tags in constant time, and return the same error for every kind of failure.

## 6. Padding and the Padding Oracle Problem

CBC needs the message length to be an exact multiple of 16 bytes. If it isn't, extra bytes are added at the end. The standard way is **PKCS#7**: add N bytes, each with the value N.

```text
13-byte message → needs 3 more bytes  → add 03 03 03
10-byte message → needs 6 more bytes  → add 06 06 06 06 06 06
16-byte message → already full        → add a whole extra block of 10 10 ... 10 (16 bytes of 0x10)
```

The last rule means the receiver can always remove the padding without guessing.

### Padding oracle (the concept)

Suppose a server decrypts a CBC message and sends back **different errors** for "bad padding" and "bad data". That difference leaks information. By sending many slightly modified ciphertexts and watching which error comes back, an attacker can eventually recover the plaintext without ever knowing the key. This is known as a Vaudenay-style attack.

How to prevent it:
- Use AEAD (GCM / ChaCha20-Poly1305), where the tag is checked before anything else.
- If you are stuck with CBC, use encrypt-then-MAC and return **one identical error** for every failure.

> Educational note: this lesson explains why the attack works and how to stop it. It does not describe the step-by-step exploitation.

## 7. How Strong Is a Key, Really?

### The math is rarely the weak point

As Section 4 showed, guessing an AES-128 key is hopeless. On average an attacker has to try half of all keys:

```text
average time ≈ (number of possible keys ÷ 2) ÷ guesses per second
```

Each extra bit of key length doubles the work. AES-256 isn't "twice as strong" as AES-128, it's 2¹²⁸ times harder to brute-force.

### Practical rules (Wong / industry)

- **AES-128 is enough** for almost every modern application.
- **AES-256** adds extra margin. It's used for long-term secrets, some government standards, and protection against future quantum computers.
- **Don't invent your own scheme** ("double AES", custom modes, "AES-like" ciphers). Use well-studied modes from a well-tested library.
- **Protect the key itself:** keep it out of logs, source code, and backups. Store it in an HSM or a KMS where possible.

## 8. OpenSSL Cheatsheet (Your Own Files / Lab Only)

```bash
# ── Encrypt / decrypt a file with a password (AES-256-CBC + PBKDF2) ──
openssl enc -aes-256-cbc -salt -pbkdf2 -iter 100000 \
  -in confidential.txt -out secret.enc

openssl enc -d -aes-256-cbc -pbkdf2 -iter 100000 \
  -in secret.enc -out decrypted.txt

# ── Generate random key material ─────────────────────────────
openssl rand -hex 32    # 256-bit key
openssl rand -hex 12    # 96-bit nonce for GCM

# ── Compare speeds on your machine ───────────────────────────
openssl speed -evp aes-256-gcm
openssl speed -evp chacha20-poly1305
```

Note: `openssl enc` does **not** support AEAD modes like GCM, and it doesn't add a MAC to CBC output either. For authenticated encryption, use a library. For example, with Python's `cryptography` package:

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

key = AESGCM.generate_key(bit_length=256)
nonce = os.urandom(12)                       # new nonce for EVERY message
ct = AESGCM(key).encrypt(nonce, b"secret data", b"header")
pt = AESGCM(key).decrypt(nonce, ct, b"header")   # raises an error if anything was changed
```

## Security Notes: Threats and Defenses

| Threat | What goes wrong | Defense |
|:---|:---|:---|
| Pattern leakage | Using ECB | Never use ECB; use GCM or ChaCha20-Poly1305 |
| Bit-flipping | CBC without a MAC | AEAD, or encrypt-then-MAC |
| Nonce reuse | Same nonce twice with CTR/GCM | Random 96-bit nonces or a counter that never repeats |
| Padding oracle | Different errors for padding vs data | AEAD; one identical error message |
| Key exposure | Keys in logs, backups, swap, git | HSM/KMS, least privilege, secret scanning |
| Side channels | Timing/cache leaks in the S-box lookups | Constant-time libraries, hardware AES (AES-NI) |
