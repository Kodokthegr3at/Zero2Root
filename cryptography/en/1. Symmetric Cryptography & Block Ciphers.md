## 1. Cryptographic Goals: The Four Pillars

Modern cryptography hardens protocols so they stay secure in an adversarial environment (David Wong, *Real-World Cryptography*, Ch.1). Four classic goals:

1. Confidentiality: only authorized parties can read the plaintext.
2. Integrity: tampering is detectable, usually through a MAC or an AEAD tag.
3. Authentication: the sender's or source's identity can be verified.
4. Non-repudiation: a sender cannot easily deny a signed message, usually achieved with a digital signature rather than a symmetric cipher alone.

Symmetric ciphers primarily deliver confidentiality. Integrity and authenticity require a MAC or an AEAD construction such as AES-GCM or ChaCha20-Poly1305.

## 2. Formal Model: Symmetric Encryption

A symmetric encryption scheme is made of three algorithms:

```text
KeyGen()   → k     create a secret key
Enc(k, m)  → c     encrypt message m into ciphertext c
Dec(k, c)  → m     decrypt c back into m
```

Both sides use the same key k: one to lock the message, the other to unlock it.

**Correctness:**

```text
Dec(k, Enc(k, m)) = m
```

In plain words: encrypt a message, then decrypt it with the same key, and you always get the original message back.

**Semantic security (IND-CPA intuition):** an adversary who sees a ciphertext gains no meaningful advantage in distinguishing between two messages of its own choosing, aside from message length, which typically leaks.

A shared secret k is used for both encryption and decryption. Security depends on key secrecy, not algorithm secrecy (Kerckhoffs's principle): the system must remain secure even if everything except the key is public.

| Parameter | Symmetric | Asymmetric |
|:---|:---|:---|
| Keys | 1 shared secret | Public + private pair |
| Speed | Very fast (AES-NI) | Slower (modular / ECC math) |
| Typical sizes | AES-128 / AES-256 | RSA-2048+ / ECC-256+ |
| Main use | Bulk data, disk, TLS records | Key exchange, signatures |
| Hard problem | Exhaustive key search 2^(key length) | Factoring / DLOG / ECDLP |

## 3. Block Ciphers vs Stream Ciphers

A block cipher maps a fixed n-bit block to an n-bit block under key k:

```text
C = E(k, P)
```

The cipher takes one fixed-size block of plaintext P plus the key k, and outputs one ciphertext block C of the same size.

AES uses n = 128. Messages longer than one block need to be split and chained through a mode of operation.

A stream cipher produces a keystream s = s₁ s₂ ... and then:

```text
cᵢ = mᵢ XOR sᵢ
```

Each bit of the message is XORed with the next bit of the keystream.

A modern example is ChaCha20, often paired with Poly1305 as an AEAD.

Block ciphers alone are not enough for variable-length messages; modes (ECB/CBC/CTR/GCM) define how blocks chain together. CTR mode effectively turns a block cipher into a stream cipher by encrypting a counter.

## 4. AES Architecture: Substitution-Permutation Network

AES (Advanced Encryption Standard / Rijndael) was chosen through a NIST competition (Wong, Ch.4). Parameters:

| Variant | Key bits κ | Rounds Nᵣ | Block size |
|:---|:---:|:---:|:---:|
| AES-128 | 128 | 10 | 128 |
| AES-192 | 192 | 12 | 128 |
| AES-256 | 256 | 14 | 128 |

The AES state is viewed as a 4 × 4 byte matrix (column-major). Every round except the last is the composition:

```text
SubBytes → ShiftRows → MixColumns → AddRoundKey
```

The final round skips `MixColumns`.

### 4.1 AddRoundKey
```text
state = state XOR round_key
```
XORs the state with round key Kᵣ, produced by Key Expansion (the Rijndael key schedule).

### 4.2 SubBytes (the non-linear S-box)
Every byte b is replaced:

```text
new_byte = S_box[old_byte]
```

The S-box is inversion in the field GF(2⁸) followed by an affine transform. It is the only non-linear layer in AES and the main defense against linear and differential cryptanalysis.

AES's irreducible polynomial:

```text
m(x) = x⁸ + x⁴ + x³ + x + 1      (0x11B)
```

### 4.3 ShiftRows
Row r is shifted left by r positions (r=0,1,2,3), diffusing bytes across columns.

### 4.4 MixColumns
Each column is treated as a polynomial over GF(2⁸) and multiplied by a fixed matrix:

```text
[s0']   [02 03 01 01]   [s0]
[s1'] = [01 02 03 01] × [s1]
[s2']   [01 01 02 03]   [s2]
[s3']   [03 01 01 02]   [s3]
```

Each new byte is a mix of all four bytes in its column, so changing one input byte changes the whole column. The multiplication follows GF(2⁸) rules, not normal arithmetic.

Multiplying by `02` is a left shift plus a conditional XOR with `0x1B` (reduction by m(x)).

### 4.5 Brute-force strength
AES-128's key space:

AES-128 has 2¹²⁸ possible keys, about 3.4 × 10³⁸. That is a 39-digit number.

Even at 10¹⁸ trials per second (an extreme hypothetical), the expected time is around 2¹²⁷ operations, well beyond practical. Realistic threats come far more often from poor key management, nonce reuse, or side channels than from breaking AES's math.

AES is an SPN: alternating substitution (SubBytes) and permutation/diffusion (ShiftRows + MixColumns), keyed by AddRoundKey. Do not invent custom "AES-like" variants; use vetted libraries and modes.

```
┌──────────────────────────────────────────────────────────┐
│                    AES ENCRYPTION FLOW                   │
│  Plaintext (128-bit)                                     │
│       │                                                  │
│       ▼                                                  │
│  AddRoundKey (K0)                                        │
│       │                                                  │
│   ┌───┴───────────────────────────────┐                  │
│   │  Repeat Nr-1 times:               │                  │
│   │   SubBytes → ShiftRows →          │                  │
│   │   MixColumns → AddRoundKey (Kr)   │                  │
│   └───────────────────────────────────┘                  │
│       │                                                  │
│  Final: SubBytes → ShiftRows → AddRoundKey (K_Nr)        │
│       │                                                  │
│       ▼                                                  │
│  Ciphertext (128-bit)                                    │
└──────────────────────────────────────────────────────────┘
```

## 5. Modes of Operation: From ECB to AEAD

Suppose the message is split into blocks P₁,...,Pₜ (after padding, if needed).

### 5.1 ECB, Electronic Codebook (do not use)

```text
Cᵢ = E(k, Pᵢ)      each block is encrypted on its own
```

Identical blocks produce identical ciphertext, so patterns leak (the classic "ECB penguin" example). There is no IV or nonce.

### 5.2 CBC, Cipher Block Chaining

```text
C₀ = IV
Cᵢ = E(k, Pᵢ XOR Cᵢ₋₁)      encrypt
Pᵢ = D(k, Cᵢ) XOR Cᵢ₋₁      decrypt
```

Before a block is encrypted, it is XORed with the previous ciphertext block. That is why two identical plaintext blocks no longer produce identical output.

The IV must be unpredictable, ideally 128-bit random, and unique per message under the same key. CBC only provides confidentiality, not integrity, so the classic practice is AES-CBC + HMAC (encrypt-then-MAC), see Wong §4.4.

### 5.3 CTR, Counter Mode

```text
Sᵢ = E(k, nonce ‖ counterᵢ)
Cᵢ = Pᵢ XOR Sᵢ
```

The cipher encrypts a counter, not the message itself, to produce a keystream. The keystream is then XORed with the plaintext.

Parallelizable and needs no padding. The nonce/counter must never repeat under the same key; keystream reuse leaks the XOR of the two plaintexts.

### 5.4 GCM, Galois/Counter Mode (modern AEAD)

AES-GCM combines CTR for confidentiality with authentication over the Galois field GF(2¹²⁸).

```text
Yᵢ = E(k, nonce ‖ i)
Cᵢ = Pᵢ XOR Yᵢ                              encryption (same as CTR)
T  = GHASH(H, AAD, C) XOR E(k, nonce ‖ 0)   authentication tag
```

where H = E(k, 0¹²⁸) and GHASH is a polynomial calculation over the ciphertext that works like a fast keyed checksum.

AEAD (Authenticated Encryption with Associated Data):
- Output: $(C, T)$, ciphertext plus a tag (usually 128-bit).
- AAD (headers, addresses, metadata) is authenticated without being encrypted.
- If tag verification fails, reject the entire message. Never "decrypt anyway."

| Mode | Confidentiality | Integrity | Parallel | Security notes |
|:---|:---:|:---:|:---:|:---|
| ECB | Leaks patterns | No | Yes | Broken for almost all use cases |
| CBC | Yes | No | No (enc) / yes (dec) | Needs a MAC; IV must be unpredictable |
| CTR | Yes | No | Yes | Nonce uniqueness is critical |
| GCM | Yes | Yes | Yes | TLS standard; nonce reuse is catastrophic |
| ChaCha20-Poly1305 | Yes | Yes | Yes | Strong on CPUs without AES-NI |

Wong's point stands: encryption without authentication is dangerous. Prefer a single AEAD primitive (AES-GCM / ChaCha20-Poly1305) over assembling your own CBC+HMAC unless you are genuinely a protocol expert. If you do combine CBC and HMAC, use encrypt-then-MAC with independent keys, compare tags in constant time, and do not carelessly leak the distinction between a padding failure and a MAC failure.

## 6. PKCS#7 Padding and Oracle Risk

For modes that require a length that's a multiple of the block size (CBC), PKCS#7 appends p bytes each with value p:

```text
p = n - (len(m) mod n)
pad(m) = m followed by p bytes, each with value p
```

Example with 16-byte blocks: a 13-byte message needs p = 3, so the bytes `03 03 03` are appended.

If |m| is already a multiple of n, a full extra block of value n is added.

Padding oracle (concept): if decryption distinguishes "padding invalid" from "MAC/app error," an attacker can learn information about the plaintext by adaptively modifying the ciphertext (a Vaudenay-style attack). Mitigation: use AEAD, or encrypt-then-MAC with uniform error responses.

> Educational note: the exact exploitation steps for a padding oracle are deliberately not laid out as an attack procedure here. The focus is detection and mitigation in protocol design.

Uniform error handling combined with AEAD removes this classic class of padding-oracle leaks.

## 7. Kerckhoffs's Principle, Key Length, and Computational Cost

### Kerckhoffs's principle
Security should depend only on the secrecy of the key, not the secrecy of the algorithm.

### Brute-force estimate
If an attacker tests R keys per second, the expected time for AES-κ is:

```text
average time ≈ 2^(κ-1) / R seconds
```

On average the attacker finds the right key after trying half of all possible keys, which is where 2^(κ-1) comes from.

Example: κ=128, R=10¹² gives T_avg ~ 5 × 10¹⁸ years, far beyond the age of the universe.

### Practical rules (Wong / industry)
- AES-128 is sufficient for almost all modern applications.
- AES-256 gives extra margin, used for long-term policy or some government standards.
- Do not roll your own "double AES"; use analyzed modes and standards.

## 8. OpenSSL Cheatsheet (Lawful Use / Your Own Lab)

```bash
# ── AES-256-CBC + PBKDF2 (your local file) ───────────────────
openssl enc -aes-256-cbc -salt -pbkdf2 -iter 100000 \
  -in confidential.txt -out secret.enc

openssl enc -d -aes-256-cbc -pbkdf2 -iter 100000 \
  -in secret.enc -out decrypted.txt

# ── AES-256-GCM (explicit hex key & IV) ──────────────────────
# IV/nonce must be unique per message under the same key
openssl enc -aes-256-gcm -in secret.txt -out secret.gcm \
  -K <64_HEX_CHARS_KEY> -iv <24_HEX_CHARS_IV>

# ── Benchmark ────────────────────────────────────────────────
openssl speed -evp aes-256-gcm aes-256-cbc chacha20-poly1305

# ── Random key material ──────────────────────────────────────
openssl rand -hex 32    # 256-bit key
openssl rand -hex 12    # 96-bit GCM nonce (common)
```

## Security Notes: Threats and Defenses

| Threat | Mechanism | Defense |
|:---|:---|:---|
| Pattern leakage | ECB | Ban ECB; use CBC/CTR/GCM |
| Bit-flipping | CBC without a MAC | AEAD or encrypt-then-MAC |
| Nonce reuse | CTR/GCM | Unique nonce / monotonic counter |
| Key disclosure | Logging, backups, swap | HSM/KMS, least privilege, secure wipe |
| Side channel | Timing/cache on the S-box | Constant-time libraries, AES-NI |
