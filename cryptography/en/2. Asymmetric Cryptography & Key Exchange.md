## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| Public key (pk) | The key you can give to anyone. People use it to encrypt messages to you, or to check your signatures |
| Private key (sk) | The key only you have. You use it to decrypt, or to sign |
| Key pair | A public key and a private key that belong together |
| Modular arithmetic ("mod") | "Clock math": you only keep the remainder after dividing. 17 mod 12 = 5 |
| Prime number | A number only divisible by 1 and itself (2, 3, 5, 7, 11, ...) |
| One-way function | Easy to compute in one direction, practically impossible to reverse |
| Key exchange | A way for two people to agree on a shared secret key over a public network |
| Digital signature | Proof, made with a private key, that a message came from you and wasn't changed |
| Padding (RSA) | Random structure added to a message before RSA, so the raw math can't be abused |
| Ephemeral key | A temporary key used for one session and then thrown away |
| PFS (forward secrecy) | If your long-term key leaks later, old recorded sessions still can't be decrypted |

## 1. The Idea: A Public Key and a Private Key

Symmetric crypto has one big problem: both sides need the same secret key, and you can't safely send it over the internet before you have encryption.

Asymmetric crypto fixes this with **two different keys** that are mathematically linked:

- **Public key (pk):** you can publish it anywhere. It's like an open padlock: anyone can snap it shut on a box addressed to you.
- **Private key (sk):** you keep it absolutely secret. It's the only key that opens that padlock.

```text
KeyGen()         → (pk, sk)
c = Enc(pk, m)     anyone can encrypt with the public key
m = Dec(sk, c)     only the private key owner can decrypt
```

This works because of a **one-way function with a trapdoor**: a calculation that is easy to do and practically impossible to undo, unless you know one secret extra piece of information (the private key).

Public-key operations are much slower than AES. That's why real systems use them only to agree on or protect a key, and then encrypt the actual data with fast symmetric AEAD. This combination is called **hybrid encryption** (Section 7).

## 2. The Math You Need (Only a Little)

You don't have to be a mathematician. These four ideas are enough to follow RSA and Diffie-Hellman.

### 2.1 Modular arithmetic ("clock math")

`a mod n` means "the remainder when a is divided by n". A clock works this way with n = 12:

```text
17 mod 12 = 5          (17:00 is 5 o'clock)
25 mod 12 = 1
```

Two numbers are "equal mod n" (written `a ≡ b (mod n)`) when they leave the same remainder. For example 17 ≡ 5 (mod 12).

### 2.2 Euler's φ (phi) function

φ(n) counts how many numbers from 1 to n-1 share no common factor with n. For RSA you only need the shortcut for n = p × q, where p and q are prime:

```text
φ(n) = (p - 1) × (q - 1)

Example: p = 3, q = 11  →  n = 33,  φ(33) = 2 × 10 = 20
```

**Euler's theorem** says that raising a number to the power φ(n) always gives 1 (mod n), as long as that number shares no factor with n. That fact is what makes RSA decryption work.

### 2.3 Modular inverse

The inverse of e (mod φ(n)) is a number d such that e × d leaves remainder 1:

```text
e × d ≡ 1 (mod φ(n))

Example: φ(n) = 20, e = 3  →  d = 7,  because 3 × 7 = 21 = 20 + 1
```

Computers find d quickly with the Extended Euclidean Algorithm.

### 2.4 The discrete logarithm problem

Given g, p and A = gᵃ mod p, find a.

```text
easy direction:  a = 6  →  A = 5⁶ mod 23 = 8         (fast, even for huge numbers)
hard direction:  A = 8  →  a = ?                      (with huge numbers: practically impossible)
```

Going forward is fast. Going backward, with numbers that are hundreds of digits long, would take longer than the age of the universe. Diffie-Hellman is built on this gap.

## 3. RSA

RSA (Rivest-Shamir-Adleman) relies on one fact: **multiplying two large primes is easy, but splitting the result back into those two primes (factoring) is extremely hard.**

### 3.1 Making a key pair

1. Pick two large secret primes p and q.
2. Multiply them: n = p × q. This n is public.
3. Compute φ(n) = (p - 1)(q - 1).
4. Pick a public exponent e that shares no factor with φ(n). Almost everyone uses e = 65537.
5. Compute the private exponent d, the inverse of e (mod φ(n)).

```text
public key  = (n, e)
private key = (n, d)      often stored with p and q to speed up decryption
```

Anyone can see n, but without knowing p and q they can't compute φ(n), and so they can't compute d.

### 3.2 Encrypting and decrypting (textbook RSA)

```text
encrypt:  C = Mᵉ mod n
decrypt:  M = Cᵈ mod n

Example with n = 33, e = 3, d = 7:
  M = 4   →  C = 4³ mod 33 = 64 mod 33 = 31
  C = 31  →  M = 31⁷ mod 33 = 4   ✓
```

Why decryption gives back M: e and d were chosen so that e × d is "1 more than a multiple of φ(n)". By Euler's theorem, raising M to that power leaves M itself.

Real RSA uses numbers with 600+ digits, but the steps are exactly the same.

### 3.3 Never use textbook RSA directly

The version above is for learning only (Wong §6.3). In real life it is dangerous:

- **It's predictable:** the same message always gives the same ciphertext, so an attacker can test guesses.
- **It can be manipulated:** an attacker can change C in a way that changes M predictably (for example, doubling it) without knowing the key.

The fix is **padding**. **RSA-OAEP** mixes a fresh random value into the message before encrypting, so the same message encrypts differently every time and tampering is detected:

```text
C = RSA(pk, OAEP(M, random value))
```

Use the library's OAEP option (for example `RSA_PKCS1_OAEP_PADDING`). Never do the raw math yourself.

### 3.4 Practical notes

- Use **RSA-OAEP** for encryption and **RSA-PSS** for signatures. Avoid the old PKCS#1 v1.5 encryption in new designs: it has a long history of padding-oracle attacks.
- Decryption is usually sped up about 4× using a trick called CRT, which works modulo p and q separately. Libraries do this for you.
- TLS 1.3 no longer uses RSA to send keys at all. It uses (EC)DHE instead (Section 4), because that gives forward secrecy.

| Security level (approx.) | RSA key size | ECC key size (see §5) |
|:---|:---:|:---:|
| ~128-bit | 3072 bit or more | ~256 bit |
| ~192-bit | 7680 bit or more | ~384 bit |
| ~256-bit | 15360 bit or more | ~521 bit |

## 4. Diffie-Hellman Key Exchange

Diffie-Hellman (DH) lets two people agree on a shared secret over a public network, **without ever sending the secret itself** (Wong, Ch.5).

### The paint analogy

Alice and Bob publicly agree on a common color, say yellow. Each secretly picks a private color and mixes it into the yellow, then they swap their mixtures. Each adds their own private color again to what they received. Both end up with the same final color. An eavesdropper sees yellow and both mixtures, but can't "unmix" paint to find the private colors.

### The real version

Public settings: a large prime p and a number g (the "generator").

```text
Alice: picks secret a, sends A = gᵃ mod p
Bob:   picks secret b, sends B = gᵇ mod p
Alice computes Bᵃ mod p,  Bob computes Aᵇ mod p  →  both get gᵃᵇ mod p

Example with p = 23, g = 5:
  a = 6   →  A = 5⁶ mod 23 = 8
  b = 15  →  B = 5¹⁵ mod 23 = 19
  Alice: 19⁶ mod 23 = 2      Bob: 8¹⁵ mod 23 = 2   ✓ same key
```

```
Alice                                              Bob
  │ a random                                         │ b random
  │ A = g^a mod p                                    │ B = g^b mod p
  │─────────────── A ───────────────────────────────>│
  │<────────────── B ────────────────────────────────│
  │ K = B^a                                          │ K = A^b
  │═══════════════ K = g^{ab} ═══════════════════════│
```

An eavesdropper sees p, g, A and B. To get the shared key they would need a or b, which means solving the discrete logarithm problem from Section 2.4.

### Two important rules

1. **DH alone doesn't prove who you're talking to.** An attacker in the middle could run one DH exchange with Alice and another with Bob. That's why real protocols (like TLS) also sign the exchange with a certificate.
2. **Use a fresh key every session** (DHE / ECDHE, the "E" means ephemeral). Then even if a long-term key leaks later, past sessions stay safe. This is **forward secrecy (PFS)**.

Also: always check that the public values you receive are valid, and use standard groups (such as RFC 7919) or, better, elliptic curves.

## 5. Elliptic Curves (ECC)

Elliptic curve cryptography does the same jobs as RSA and DH, but with **much smaller keys** and faster operations. A 256-bit ECC key is about as strong as a 3072-bit RSA key. That's why ECC is the default in TLS, SSH, and mobile apps.

### What is an elliptic curve?

It's the set of points (x, y) that satisfy an equation like:

```text
y² = x³ + ax + b   (mod p)
```

Plotted over normal numbers, this looks like a smooth, symmetric curve.

### Adding points

You can "add" two points on the curve with a geometric rule: draw a straight line through them, find where it hits the curve a third time, and mirror that point across the x-axis. Adding a point to itself uses the tangent line instead.

Multiplying a point by a number k just means adding it to itself k times:

```text
k·G = G + G + ... + G      (k times)
```

Computers do this quickly using a "double and add" trick. But going backwards (given k·G and G, find k) is extremely hard. That's the **elliptic curve discrete log problem (ECDLP)**, and it's what keeps ECC secure.

### ECDH: Diffie-Hellman on a curve

```text
Alice: secret a  →  sends A = a·G
Bob:   secret b  →  sends B = b·G
Shared secret:  a·B = b·A = (a·b)·G
```

It's exactly the same idea as Section 4: only A and B travel over the network, and both sides still end up with the same point.

Common curves:
- **P-256** (also called prime256v1 or secp256r1): widely supported.
- **X25519** (RFC 7748): the modern favorite. Its API is designed to be hard to misuse.

Use high-level APIs (`X25519`, `Ed25519`) instead of doing point math yourself.

| Level | Symmetric | RSA | ECC |
|:---|:---:|:---:|:---:|
| Standard | 128 | 3072 | 256 (P-256 / X25519) |
| High | 192 | 7680 | 384 |
| Very high | 256 | 15360 | 521 / Ed448 |

## 6. Digital Signatures

A digital signature is the reverse of encryption: you use your **private** key to sign, and anyone uses your **public** key to check.

```text
σ = Sign(sk, message)
Verify(pk, message, σ) → true / false
```

A valid signature proves two things: the message came from the owner of the private key, and it wasn't changed afterwards. In practice you sign the **hash** of the message, not the message itself (see LC-056).

### The main signature schemes

| Scheme | Based on | Notes |
|:---|:---|:---|
| RSA-PSS | RSA | The recommended way to sign with RSA. Prefer it over old PKCS#1 v1.5 |
| ECDSA | Elliptic curves | Very common, but has a dangerous weak spot (below) |
| Ed25519 (EdDSA) | Elliptic curves | The modern default for SSH, Git, and many protocols |

### ECDSA's weak spot: the random number

Every ECDSA signature needs a fresh random number k, called the nonce. It must be **unique and secret** for every single signature. If the same k is used twice, or if k is even slightly predictable, an attacker can calculate the private key from just two signatures.

This really happened: Sony signed PlayStation 3 software with the same k every time, and the private signing key was recovered.

**Ed25519** avoids this problem completely. It computes the nonce from the private key and the message instead of from a random number generator, so a broken RNG can't leak the key. (For ECDSA, RFC 6979 does the same trick.)

## 7. Hybrid Encryption: How Real Systems Combine Both

Encrypting a big file directly with RSA would be slow and awkward. Real systems combine the strengths of both kinds of crypto:

1. Generate a random 256-bit **session key**.
2. Encrypt the actual data with that session key using fast symmetric AEAD (AES-GCM or ChaCha20-Poly1305).
3. Protect the session key with asymmetric crypto: either encrypt it with the recipient's RSA public key (RSA-OAEP), or derive it from an ECDH exchange.

```text
[ big data ] --AES-GCM with session key--> [ encrypted data ]
[ session key ] --recipient's public key--> [ encrypted session key ]
send both
```

This pattern is called **KEM/DEM** (Key Encapsulation + Data Encapsulation). It's also the basis of ECIES (Wong §6.4).

TLS, Signal, and almost every modern messaging app work this way: asymmetric crypto to agree on keys and prove identity, symmetric AEAD for the actual traffic.

## 8. Quantum Computers and Post-Quantum Crypto

A large enough quantum computer running **Shor's algorithm** could factor big numbers and solve discrete logs quickly. That would break RSA, DH, and ECC. Such a machine doesn't exist yet, but data recorded today could be decrypted in the future ("harvest now, decrypt later").

The industry response is **post-quantum cryptography (PQC)**, standardized by NIST:
- **ML-KEM** (Kyber): for agreeing on keys.
- **ML-DSA** (Dilithium) and **SLH-DSA**: for signatures.

Many TLS deployments already use **hybrid** key exchange, combining a classic method (X25519) with ML-KEM, so the connection stays safe even if one of them turns out to be broken.

Symmetric crypto is in much better shape. **Grover's algorithm** only roughly halves the effective key length, so AES-256 still keeps a comfortable margin, and SHA-256 stays fine.

## 9. OpenSSL Cheatsheet

```bash
# ── RSA 4096 key pair ────────────────────────────────────────
openssl genrsa -out private_rsa.pem 4096
openssl rsa -in private_rsa.pem -pubout -out public_rsa.pem

# ── Encrypt/decrypt a small file with OAEP (never raw RSA) ───
openssl pkeyutl -encrypt -pubin -inkey public_rsa.pem \
  -pkeyopt rsa_padding_mode:oaep -in key.bin -out key.enc
openssl pkeyutl -decrypt -inkey private_rsa.pem \
  -pkeyopt rsa_padding_mode:oaep -in key.enc -out key.bin

# ── ECC P-256 / Ed25519 keys ─────────────────────────────────
openssl ecparam -name prime256v1 -genkey -noout -out private_ec.pem
openssl genpkey -algorithm ED25519 -out private_ed25519.pem
openssl pkey -in private_ed25519.pem -pubout -out public_ed25519.pem

# ── Sign & verify a file (RSA + SHA-256) ─────────────────────
openssl dgst -sha256 -sign private_rsa.pem -out doc.sig document.pdf
openssl dgst -sha256 -verify public_rsa.pem -signature doc.sig document.pdf
```

RSA can only encrypt data smaller than its key, so `pkeyutl -encrypt` is meant for small things like a session key, not whole files. That's hybrid encryption from Section 7.

## Security Notes

| Risk | Cause | Defense |
|:---|:---|:---|
| Textbook RSA | No padding | Always use OAEP (encryption) or PSS (signatures) |
| ECDSA nonce reuse | Weak or broken random number generator | Ed25519, or deterministic ECDSA (RFC 6979) |
| Invalid public values | Not checking received points or group elements | Standard curves plus the library's validation |
| No forward secrecy | Static RSA key exchange | Ephemeral ECDHE only (as in TLS 1.3) |
| Private key theft | Key on disk, in backups, or in git | HSM, passphrase protection, short-lived keys |
| Future quantum attacks | Long-lived secrets protected only by RSA/ECC | Plan the move to hybrid / post-quantum algorithms |
