## Key Terms

You'll see these words throughout the lesson.

| Term | Plain meaning |
|:---|:---|
| Hash function | A function that turns any input into a short, fixed-size "fingerprint" |
| Digest / hash value | The fingerprint itself, for example a 256-bit SHA-256 output |
| Collision | Two different inputs that produce the same hash |
| Preimage | The original input that produced a given hash |
| Avalanche effect | A tiny change in the input completely changes the output |
| MAC | A hash-like tag that needs a secret key to create, so it proves both integrity and authenticity |
| HMAC | The standard, safe way to build a MAC from a hash function |
| Salt | A random value stored next to a password hash, so identical passwords get different hashes |
| KDF | Key derivation function: turns a password or raw secret into proper keys |
| Constant-time comparison | Comparing two values in a way that always takes the same time, so timing reveals nothing |

## 1. What a Hash Function Is

A hash function takes input of **any** length (a word, a file, a whole disk) and produces an output of a **fixed** length, like a fingerprint:

```text
SHA-256("hello") → 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
SHA-256("Hello") → 185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969
```

Changing one letter from lowercase to uppercase produced a completely different result. That's the **avalanche effect**.

A good cryptographic hash has these everyday properties (Wong, Ch.2):

- **Deterministic:** the same input always gives the same hash.
- **Avalanche:** changing a single bit flips about half of the output bits.
- **Fast:** quick to compute on a normal CPU. (That's good for files, but bad for passwords; see Section 8.)

Where hashes are used: checking that a download wasn't corrupted, digital signatures (you sign the hash, not the whole file), Git commit IDs, Merkle trees, and key derivation.

One important limit: **a plain hash doesn't prove who sent something.** Anyone can compute SHA-256 of a modified file. To prove authenticity you need a secret key, which means a MAC, HMAC, or AEAD (Section 6).

## 2. The Three Security Properties

A cryptographic hash must make three things practically impossible. Here n is the output size in bits (256 for SHA-256).

| Property | The attacker's task | Generic cost | Analogy |
|:---|:---|:---:|:---|
| **Preimage resistance** | Given a hash, find *any* input that produces it | about 2ⁿ tries | Given a fingerprint, find the person |
| **Second-preimage resistance** | Given one input, find a *different* input with the same hash | about 2ⁿ tries | Find someone with the same fingerprint as Alice |
| **Collision resistance** | Find *any* two inputs with the same hash | about 2^(n/2) tries | Find *any* two people with matching fingerprints |

Notice that collision resistance is the weakest: the attacker gets to choose both inputs freely, so it's much easier. Section 3 explains why it's 2^(n/2) instead of 2ⁿ.

For a 128-bit security level, modern designs therefore use hashes of at least 256 bits.

## 3. The Birthday Problem: Why Collisions Come Sooner Than You Think

How many people need to be in a room before there's a 50% chance that two of them share a birthday? Most people guess around 180 (half of 365). The real answer is **only 23**.

The reason: you're not looking for someone who matches *you*, you're looking for *any* matching pair. With 23 people there are already 253 possible pairs.

The same applies to hashes. If a hash has N possible outputs, you only need roughly the square root of N tries before a collision becomes likely:

```text
tries for a 50% chance of a collision ≈ 1.18 × √N

birthdays:  N = 365       →  1.18 × √365 ≈ 23 people
SHA-256:    N = 2²⁵⁶      →  about 2¹²⁸ tries
```

What this means in practice (Wong, "The birthday bound"):

- SHA-256 gives about 128 bits of collision resistance. That matches the 128-bit security target, which is why it's considered safe.
- **Cutting a hash short is dangerous.** A hash truncated to 64 bits can have collisions found with only about 2³² tries, which an ordinary computer can manage. If collisions matter (certificates, content addressing), keep at least 256 bits.

## 4. How Hash Functions Are Built

### 4.1 Merkle-Damgård (SHA-1, SHA-2)

Used by SHA-1 and SHA-256. The idea:

1. Pad the message so its length fits neatly into blocks (the original length is written into the padding).
2. Split it into blocks.
3. Start from a fixed starting value, and feed in one block at a time. Each step mixes the next block into a running state.
4. The final state is the hash.

```text
start value → mix(block 1) → mix(block 2) → mix(block 3) → ... → hash
```

The weakness: the hash output **is** the final internal state. Someone who knows the hash can keep "mixing in" more blocks without knowing the original message. This is the **length-extension attack** (Section 7).

### 4.2 Sponge (SHA-3 / Keccak)

SHA-3 works differently. It has a large internal state split into two parts:

- **Rate:** the part where input is "absorbed" and output is "squeezed out".
- **Capacity:** a hidden part that is never output directly. Security comes from this hidden part (roughly half its size, in bits).

Because part of the state is never revealed, SHA-3 is **not** vulnerable to length extension. The same design can also produce output of any length you like (SHAKE128/256, called XOFs).

```
 Merkle–Damgård                 Sponge (SHA-3)
 M1  M2  M3                     absorb → squeeze
  │   │   │                     ┌──────────────┐
  ▼   ▼   ▼                     │ rate r       │
 IV→f→f→f→ digest               │ capacity c   │──→ digest/XOF
                                └──────────────┘
```

## 5. Which Hash Functions Are Safe Today

| Function | Output size | Design | Status | Notes |
|:---|:---:|:---|:---|:---|
| MD5 | 128 | MD | **Broken** | Collisions can be found in seconds |
| SHA-1 | 160 | MD | **Broken** | Real collision published in 2017 (SHAttered) |
| SHA-256 | 256 | MD | Safe | Watch out for length extension if misused |
| SHA-512 | 512 | MD | Safe | Often faster on 64-bit CPUs |
| SHA3-256 | 256 | Sponge | Safe | A structurally different backup option |
| SHAKE256 | any | Sponge (XOF) | Safe | Output length of your choice |
| BLAKE3 | 256 | Tree | Safe, very fast | Uses multiple cores and SIMD |

Practical rule: use SHA-256 or BLAKE3 for file integrity, and SHA-256, SHA-3 or BLAKE3 for new protocols. **Never use MD5 or SHA-1 for anything security-related.**

## 6. MAC and HMAC: Hashing with a Secret Key

A plain hash proves a file wasn't *accidentally* corrupted. It doesn't stop an attacker, because the attacker can change the file and recompute the hash.

A **MAC** (Message Authentication Code) mixes in a secret key. Only someone who has the key can produce a valid tag:

```text
tag = MAC(key, message)
Verify(key, message, tag) → true / false
```

If the message changes even slightly, the tag no longer matches. And without the key, an attacker can't make a new valid tag.

### HMAC (RFC 2104)

HMAC is the standard way to turn a hash like SHA-256 into a MAC. It hashes **twice**, with the key mixed in each time:

```text
HMAC(K, m) = Hash( outer_key ‖ Hash( inner_key ‖ m ) )

inner_key = key XOR 0x36 0x36 ...   (ipad)
outer_key = key XOR 0x5c 0x5c ...   (opad)
```

The outer hash "seals" the result, which is what stops length-extension attacks. HMAC-SHA256 is safe even though SHA-256 alone is vulnerable to length extension.

### Poly1305

A very fast MAC, used together with ChaCha20 in the AEAD scheme ChaCha20-Poly1305.

### Two rules

- **Never build a MAC as `Hash(key ‖ message)` or `Hash(message ‖ key)`.** Use HMAC, KMAC, Poly1305, or an AEAD tag.
- **Compare tags in constant time.** A normal comparison stops at the first wrong byte, so measuring how long it takes can leak how many bytes were right. Use `hmac.compare_digest` (Python) or `CRYPTO_memcmp` (C).

## 7. Length-Extension Attacks (Concept)

With Merkle-Damgård hashes (SHA-1, SHA-256), the hash output is the internal state at the end. If an attacker knows `Hash(secret ‖ message)` and the length of the input, they can continue the calculation and produce a valid hash for `secret ‖ message ‖ padding ‖ extra_data`, **without knowing the secret.**

So this common homemade design is **not** safe:

```text
auth_tag = SHA256(secret ‖ message)        ✗  vulnerable to length extension
auth_tag = HMAC-SHA256(secret, message)    ✓  safe
```

Fixes: use HMAC, use a hash without this weakness (SHA-3, BLAKE3), or use an AEAD.

> Educational note: this section explains why the naive design fails and how to choose the correct construction. It doesn't describe exploiting a third-party system.

## 8. Storing Passwords Safely

SHA-256 is designed to be fast, and that's exactly the problem for passwords. A single GPU can test **billions** of SHA-256 guesses per second, so a stolen database of SHA-256 password hashes falls quickly.

Passwords need a **deliberately slow** function that also uses lots of memory, so that GPUs and custom chips lose their advantage:

```text
stored_hash = KDF(password, salt, cost settings)
```

| KDF | Properties | Notes |
|:---|:---|:---|
| **Argon2id** | Slow and memory-hard | Winner of the Password Hashing Competition; the modern default (Wong) |
| scrypt | Memory-hard | Good, but the settings need careful tuning |
| bcrypt | Slow (CPU-hard) | Still common; only uses the first 72 bytes of a password |
| PBKDF2 | Repeats HMAC many times | Not memory-hard; needs a very high iteration count |

### Salt and pepper

- **Salt:** a random value (16+ bytes), different for every user, stored next to the hash. Two users with the same password get different hashes, and precomputed "rainbow tables" become useless.
- **Pepper (optional):** an extra secret kept on the server, not in the database. If only the database leaks, the hashes are still protected.

What to store: the KDF output, the salt, and the settings used. At login, compute the hash again with the same salt and settings and compare it in constant time. For new systems, **use Argon2id**.

## 9. HKDF: Turning One Secret into Many Keys

After a key exchange (for example ECDH), you get one shared secret. It isn't perfectly random, and you usually need several separate keys from it (one for each direction, one for IVs, and so on). HKDF handles this in two steps:

```text
1. Extract:  PRK = HMAC(salt, raw_secret)            → "cleans" the secret into uniform randomness
2. Expand:   key = HKDF-Expand(PRK, label, length)   → produces as many keys as you need
```

The `label` (called `info`) makes each derived key different, for example `"client key"` and `"server key"`.

HKDF is used in TLS 1.3, Signal, and the Noise protocol framework.

## 10. Cheatsheet

```bash
# ── Check file integrity ─────────────────────────────────────
sha256sum file.iso
sha256sum -c SHA256SUMS          # check against a published list
b2sum file.tar                   # BLAKE2b (part of coreutils)

# ── OpenSSL digest / HMAC ────────────────────────────────────
openssl dgst -sha256 file.bin
echo -n 'payload' | openssl dgst -sha256 -hmac 'secret-key'

# ── Argon2 password hashing (Python, argon2-cffi) ────────────
python3 -c "
from argon2 import PasswordHasher
ph = PasswordHasher()          # Argon2id with safe defaults
h = ph.hash('correct horse battery staple')
print(h)
print(ph.verify(h, 'correct horse battery staple'))
"
```

## Security Notes

| Bad practice | Risk | Use instead |
|:---|:---|:---|
| MD5 or SHA-1 for security | Collisions are practical | SHA-256 or stronger |
| `Hash(secret ‖ msg)` as a MAC | Length extension | HMAC or AEAD |
| Fast hash (SHA-256) for passwords | GPU cracking | Argon2id |
| Truncating hashes to 64 bits | Collisions in about 2³² tries | At least 128 bits (preimage) / 256 bits (collision) |
| Normal `==` to compare tags | Timing leak | `hmac.compare_digest` / `CRYPTO_memcmp` |
