## 1. Formal Definition

A cryptographic hash function is an efficient mapping:

$$
H: \{0,1\}^{*} \rightarrow \{0,1\}^{n}
$$

that compresses an arbitrary-length input into a fixed $n$-bit digest (for example $n=256$ for SHA-256).

Desired operational properties (Wong, Ch.2):
- Deterministic: $H(m)$ is always the same for the same $m$.
- Avalanche: changing 1 input bit flips roughly 50% of the output bits.
- Efficient: fast to evaluate on general-purpose CPUs, the opposite of what a password KDF wants.

A hash produces a fixed-size fingerprint for integrity checks, commitments, Merkle trees, digital signatures (hash-then-sign), and KDFs. A bare hash is not authentication without a secret key; for that, use a MAC, HMAC, or AEAD.

## 2. Classical Security Properties

Let $\mathcal{A}$ be an adversary with a practical computational bound.

### 2.1 Preimage resistance (one-way)
Given $h$, it should be hard to find $m$ with $H(m)=h$:

$$
\Pr\big[H(\mathcal{A}(h))=h\big] \approx \mathsf{negl}
$$

Generic complexity is around $2^{n}$ attempts.

### 2.2 Second-preimage resistance
Given $m_1$, it should be hard to find $m_2\neq m_1$ with $H(m_1)=H(m_2)$. Generic complexity is also around $2^{n}$.

### 2.3 Collision resistance
It should be hard to find any pair $m_1\neq m_2$ with $H(m_1)=H(m_2)$.
Because of the birthday bound, generic complexity is around $2^{n/2}$.

### 2.4 Relationship between the properties
Collision resistance implies second-preimage resistance (asymptotically, in most formalizations). The reverse does not always hold. Modern designs target collision security around $2^{n/2}$ with $n\ge 256$ for a 128-bit security level.

## 3. The Birthday Bound: Probability Formula

The birthday problem: how many people are needed for the chance that two share a birthday to reach 50% or more? The answer is about 23, not $\sqrt{365}$ as a naive guess without the combinatorics would suggest.

For $k$ uniform samples from a space of size $N=2^{n}$:

$$
\Pr[\text{collision}] \approx 1 - \exp\!\left(-\frac{k(k-1)}{2N}\right)
$$

For a probability around 1/2:

$$
k \approx \sqrt{2\ln 2}\cdot\sqrt{N} \approx 1.177\sqrt{N} = \Theta\!\big(2^{n/2}\big)
$$

Implications (Wong, "The birthday bound"):
- SHA-256 ($n=256$) gives a generic collision bound around $2^{128}$, matching a 128-bit security target.
- Truncation is dangerous: to keep collision resistance around 128 bits, the digest must be at least 256 bits; for preimage resistance alone, 128 bits is enough.

Always size a digest to match the property the application needs. Collision-sensitive applications (certificates, git-style content addressing under adversarial input) need the full birthday margin.

## 4. Constructions: Merkle-Damgard vs Sponge

### 4.1 Merkle-Damgard (SHA-1, SHA-2)
1. Pad the message (the message length is encoded at the end of the padding).
2. Split into blocks $M_1,\ldots,M_L$ as wide as the compression function.
3. Iterate:

$$
\begin{aligned}
IV &= H_0 \\
H_i &= f(H_{i-1}, M_i),\quad i=1,\ldots,L \\
H(M) &= H_L
\end{aligned}
$$

where $f$ is the compression function (for SHA-256, built from SHA-family rounds).

Consequence: vulnerable to length-extension (see §7) if used naively as a MAC via `H(K‖M)`.

### 4.2 Sponge (SHA-3 / Keccak)
A $b$-bit state consists of a rate $r$ plus capacity $c$ ($b=r+c$). Input is absorbed into the rate, permuted through $\pi$, then output is squeezed:

$$
\text{security is tied to }c/2\text{ against generic attacks}
$$

SHA-3 is immune to MD-style length-extension. This construction also provides XOFs (SHAKE128/256) with flexible-length output.

```
 Merkle–Damgård                 Sponge (SHA-3)
 M1  M2  M3                     absorb → squeeze
  │   │   │                     ┌──────────────┐
  ▼   ▼   ▼                     │ rate r       │
 IV→f→f→f→ digest               │ capacity c   │──→ digest/XOF
                                └──────────────┘
```

## 5. Hash Algorithm List and Status

| Function | Digest | Construction | Status | Notes |
|:---|:---:|:---|:---|:---|
| MD5 | 128 | MD | Broken | Practical collisions |
| SHA-1 | 160 | MD | Broken | SHAttered (2017) |
| SHA-256 | 256 | MD | Secure | Vulnerable to length-extension if misused |
| SHA-512 | 512 | MD | Secure | Performs well on 64-bit CPUs |
| SHA-3-256 | 256 | Sponge | Secure | Structural alternative |
| SHAKE256 | variable | XOF | Secure | Flexible output |
| BLAKE3 | 256 | Tree | Secure, fast | Parallel / SIMD |

Practical rule: use SHA-256/BLAKE3 for file integrity; use SHA-256 or SHA-3/BLAKE3 for new protocols. Do not use MD5/SHA-1 for anything security-relevant.

## 6. Message Authentication Codes (MAC) and HMAC

A MAC uses a secret key to provide authentication and integrity together:

$$
t = \mathsf{MAC}_K(m),\qquad \mathsf{Verify}_K(m,t)\in\{0,1\}
$$

### HMAC (RFC 2104)
$$
\mathsf{HMAC}(K,m)=H\Big((K' \oplus \mathsf{opad}) \,\|\, H\big((K' \oplus \mathsf{ipad}) \,\|\, m\big)\Big)
$$

- $K'$ is the key, padded or truncated to the hash's block size.
- $\mathsf{ipad}=0x36\ldots$, $\mathsf{opad}=0x5c\ldots$

HMAC stays secure with SHA-256 even though the underlying MD construction is vulnerable to length-extension when used naively.

### Poly1305
A fast MAC based on a polynomial evaluated modulo $2^{130}-5$, paired with ChaCha20 as an AEAD (ChaCha20-Poly1305).

Never build your own MAC as `H(K‖m)` or `H(m‖K)`. Use HMAC, KMAC, Poly1305, or an AEAD tag. Compare tags in constant time.

## 7. Length-Extension Attacks (Concept)

For a Merkle-Damgard hash, if an adversary knows $H(M)$ and the length $|M|$, it can compute $H(M \,\|\, \mathsf{pad} \,\|\, M')$ without knowing $M$, by continuing the internal state forward.

Implication: `auth = SHA256(secret ‖ message)` is not a safe MAC. Mitigation: HMAC, SHA-3/BLAKE3, or AEAD.

> Educational note: this note focuses on why the naive design fails and how to pick the correct construction, not on exploitation steps against a third-party system.

## 8. Password Hashing and Memory-Hard KDFs

SHA-256 is deliberately fast, which means a GPU or ASIC can test billions of candidates per second. Passwords must use a slow or memory-hard KDF instead.

Given a cost parameter $t$ (iterations/time), memory $m$, and parallelism $p$:

$$
\mathsf{Hash}_{pwd} = \mathsf{KDF}(\mathsf{password},\;\mathsf{salt};\; t,m,p)
$$

| KDF | Properties | Notes |
|:---|:---|:---|
| Argon2id | Memory-hard, balanced against side channels | PHC winner; modern default choice (Wong) |
| scrypt | Memory-hard | Good; parameters need careful tuning |
| bcrypt | CPU-hard (Blowfish-based) | Still common; has a password-length limit |
| PBKDF2 | HMAC iteration | Not memory-hard; needs very high iteration counts |

A per-user salt (16+ random bytes) prevents rainbow tables. A pepper (a server-side secret) is an optional addition.

Store only the KDF output, the salt, and the parameters. On login, recompute and compare in constant time. Argon2id is recommended for new systems.

---

## 9. HKDF: Extract-then-Expand

From a raw shared secret (for example, the output of ECDH) that is not perfectly uniform:

$$
\begin{aligned}
PRK &\leftarrow \mathsf{HKDF\text{-}Extract}(salt,\, IKM) = \mathsf{HMAC}(salt,\, IKM) \\
OKM &\leftarrow \mathsf{HKDF\text{-}Expand}(PRK,\, info,\, L)
\end{aligned}
$$

- Extract: makes the entropy uniform.
- Expand: produces $L$ bytes of application keys (traffic keys, IV keys, and so on).

Used widely in TLS 1.3, Signal, and Noise.

## 10. Cheatsheet

```bash
# ── Integrity ────────────────────────────────────────────────
sha256sum file.iso
sha256sum -c SHA256SUMS
b2sum file.tar                 # BLAKE2b (util-linux)

# ── OpenSSL digest / HMAC ────────────────────────────────────
openssl dgst -sha256 file.bin
echo -n 'payload' | openssl dgst -sha256 -hmac 'secret-key'

# ── Argon2 example (Python) ──────────────────────────────────
python3 -c "
from argon2 import PasswordHasher
ph = PasswordHasher()          # Argon2id defaults
h = ph.hash('correct horse battery staple')
print(h)
print(ph.verify(h, 'correct horse battery staple'))
"
```

## Security Notes

| Anti-pattern | Risk | Replace with |
|:---|:---|:---|
| MD5/SHA-1 for security | Collision | SHA-256 or higher |
| `H(secret‖msg)` as a MAC | Length extension | HMAC / AEAD |
| Fast hash for passwords | GPU cracking | Argon2id |
| Truncating to 64 bits | Fast birthday break | At least 128-bit (preimage) / 256-bit (collision) |
| Non-constant-time tag comparison | Timing leak | `hmac.compare_digest` / `CRYPTO_memcmp` |
