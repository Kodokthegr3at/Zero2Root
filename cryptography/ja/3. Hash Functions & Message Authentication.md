## 1. 形式的定義

暗号学的ハッシュ関数は、次のような効率的な写像である。

```text
H(任意の長さの入力) → 固定長 n ビットの出力

SHA-256("hello") → 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

任意長の入力を固定長 n ビットのダイジェストに圧縮する(例えばSHA-256では n=256)。

望ましい動作特性は次のとおり(Wong, 第2章)。
- 決定性:同じ m に対して H(m) は常に同じ値になる。
- 雪崩効果(アバランチ):入力の1ビットを変えると、出力のおよそ50%のビットが変わる。
- 効率性:汎用CPU上で高速に計算できる。これはパスワード用KDFに求められる性質とは正反対である。

ハッシュは、完全性の検証、コミットメント、Merkle木、デジタル署名(hash-then-sign)、KDFに使う固定長のフィンガープリントを作る。ただし、秘密鍵を伴わない素のハッシュは認証にはならない。認証にはMAC、HMAC、またはAEADを使う必要がある。

## 2. 古典的なセキュリティ特性

計算量に現実的な上限を持つ攻撃者 A を考える。

### 2.1 事前像耐性(one-way性)
h が与えられたとき、H(m)=h となる m を見つけることが難しい。

つまり、強力な攻撃者であっても、そのような m を見つけられる見込みはほぼゼロだ。

汎用的な攻撃の計算量はおよそ 2ⁿ 回の試行である。

### 2.2 第二事前像耐性
m₁ が与えられたとき、H(m₁)=H(m₂) となる m₂ ≠ m₁ を見つけることが難しい。こちらも汎用計算量はおよそ 2ⁿ である。

### 2.3 衝突耐性
H(m₁)=H(m₂) となる任意のペア m₁ ≠ m₂ を見つけることが難しい。
誕生日バウンドにより、汎用計算量はおよそ 2^(n/2) である。

### 2.4 各特性の関係
衝突耐性は(多くの形式化において漸近的に)第二事前像耐性を含意する。逆は必ずしも成り立たない。現代的な設計では、128ビットのセキュリティレベルを目標として n ≥ 256 とし、衝突耐性をおよそ 2^(n/2) に設定する。

## 3. 誕生日バウンド:確率の式

誕生日問題:2人の誕生日が一致する確率が50%以上になるには何人必要か。答えはおよそ23人であり、組み合わせを考慮しない素朴な直感が示す √365 とは異なる。

サイズ N=2ⁿ の空間から一様に k 個をサンプリングする場合、

2つが一致する確率は、k が増えるにつれて想像以上に速く大きくなる。

確率がおよそ1/2になる条件は、

```text
k ≈ 1.18 × √N   つまり約 2^(n/2) 回の試行
```

つまり256ビットのハッシュでは、*何らかの*衝突を見つけるのに必要なのは 2²⁵⁶ 回ではなく約 2¹²⁸ 回だ。

ここから導かれる帰結(Wong「The birthday bound」):
- SHA-256(n=256)は、汎用的な衝突攻撃に対しておよそ 2¹²⁸ の強度を持ち、128ビットのセキュリティ目標に一致する。
- 切り詰め(truncation)は危険である。128ビット相当の衝突耐性を維持するにはダイジェストは最低256ビット必要であり、事前像耐性だけでよければ128ビットで十分である。

ダイジェスト長は、アプリケーションが必要とする性質に応じて選ぶべきである。衝突に敏感な用途(証明書、敵対的な入力下でのgit風のコンテンツアドレッシングなど)では、誕生日バウンドの余裕を十分に確保する必要がある。

## 4. 構成法:Merkle-Damgard対スポンジ

### 4.1 Merkle-Damgard(SHA-1、SHA-2)
1. メッセージをパディングする(メッセージ長をパディングの末尾に符号化する)。
2. 圧縮関数の幅に合わせてブロック M₁,...,M_L に分割する。
3. 反復する。

```text
H₀ = IV
Hᵢ = f(Hᵢ₋₁, Mᵢ)      各ブロック i = 1 ... L について
H(M) = H_L
```

各ブロックを内部状態に順番に混ぜていき、最後の状態がハッシュ値になる。

ここで f は圧縮関数である(SHA-256の場合、SHAファミリーのラウンド構造に基づく)。

この構成の帰結として、`H(K‖M)` のような形で単純にMACとして使うと伸長攻撃(§7参照)に対して脆弱になる。

### 4.2 スポンジ構成(SHA-3 / Keccak)
b ビットの状態は、レート r とキャパシティ c からなる(b=r+c)。入力はレート部分に吸収(absorb)され、置換 π が適用されたのち、出力が絞り出される(squeeze)。

汎用的な攻撃に対する安全性は、およそ c/2 ビットになる。

SHA-3はMD構成のような伸長攻撃に対して耐性を持つ。この構成はまた、出力長を柔軟に選べるXOF(SHAKE128/256)も提供する。

```
 Merkle–Damgård                 Sponge (SHA-3)
 M1  M2  M3                     absorb → squeeze
  │   │   │                     ┌──────────────┐
  ▼   ▼   ▼                     │ rate r       │
 IV→f→f→f→ digest               │ capacity c   │──→ digest/XOF
                                └──────────────┘
```

## 5. ハッシュアルゴリズムの一覧と現状

| 関数 | ダイジェスト長 | 構成法 | 状態 | 備考 |
|:---|:---:|:---|:---|:---|
| MD5 | 128 | MD | 破られている | 実用的な衝突が発見済み |
| SHA-1 | 160 | MD | 破られている | SHAttered(2017年) |
| SHA-256 | 256 | MD | 安全 | 誤用すると伸長攻撃に弱い |
| SHA-512 | 512 | MD | 安全 | 64ビットCPUで高速 |
| SHA-3-256 | 256 | スポンジ | 安全 | 構造的な代替案 |
| SHAKE256 | 可変長 | XOF | 安全 | 出力長を柔軟に選べる |
| BLAKE3 | 256 | ツリー | 安全、高速 | 並列化/SIMDに向く |

実務上の目安:ファイルの完全性確認にはSHA-256かBLAKE3を、新規プロトコルにはSHA-256かSHA-3/BLAKE3を使う。セキュリティ用途でMD5やSHA-1を使ってはならない。

## 6. メッセージ認証コード(MAC)とHMAC

MACは秘密鍵を使って認証と完全性を同時に提供する。

```text
t = MAC(K, m)
Verify(K, m, t) → true / false
```

### HMAC(RFC 2104)
```text
HMAC(K, m) = H( (K' XOR opad) ‖ H( (K' XOR ipad) ‖ m ) )
```

言い換えると、鍵(ipadと混ぜたもの)とメッセージをハッシュし、その結果を鍵(opadと混ぜたもの)ともう一度ハッシュする。この2段構えが伸長攻撃を防ぐ。

- K' は、ハッシュのブロックサイズに合わせてパディングまたは切り詰めた鍵である。
- ipad=0x36...、opad=0x5c...

MD構成が単純な使い方では伸長攻撃に弱いのに対し、HMACはSHA-256を使っても安全である。

### Poly1305
法 2¹³⁰-5 の多項式評価に基づく高速なMACで、ChaCha20と組み合わせてAEAD(ChaCha20-Poly1305)として使われる。

`H(K‖m)` や `H(m‖K)` のような自作MACを作ってはならない。HMAC、KMAC、Poly1305、またはAEADのタグを使う。タグの比較は必ず定数時間で行う。

## 7. 伸長攻撃(概念)

Merkle-Damgard型のハッシュでは、攻撃者が H(M) と長さ |M| を知っていれば、内部状態を引き継ぐことで、M 自体を知らなくても H(M ‖ pad ‖ M') を計算できる。

このことから、`auth = SHA256(secret ‖ message)` は安全なMACではない。対策はHMAC、SHA-3/BLAKE3、またはAEADの使用である。

> 教育上の注記:このノートの焦点は、素朴な設計がなぜ破綻するのか、そして正しい構成をどう選ぶべきかを理解することであり、第三者システムへの攻撃手順の解説ではない。

## 8. パスワードハッシュとメモリハードなKDF

SHA-256は意図的に高速に設計されているため、GPUやASICを使えば毎秒数十億の候補を試行できてしまう。パスワードには、低速またはメモリハードなKDFを使わなければならない。

コストパラメータ t(反復回数/時間)、メモリ m、並列度 p を用いて、

```text
stored_hash = KDF(password, salt, t, m, p)
```

| KDF | 特性 | 備考 |
|:---|:---|:---|
| Argon2id | メモリハード、サイドチャネルへの耐性もバランス良く確保 | PHC(Password Hashing Competition)の優勝方式。現代の標準的な選択(Wong) |
| scrypt | メモリハード | 良好だが、パラメータ選定には注意が必要 |
| bcrypt | CPUハード(Blowfishベース) | 依然として広く使われるが、パスワード長に上限がある |
| PBKDF2 | HMACの反復 | メモリハードではなく、非常に多くの反復回数が必要 |

ユーザーごとに一意なソルト(16バイト以上のランダム値)はレインボーテーブル攻撃を防ぐ。ペッパー(サーバー側の秘密)は任意の追加対策である。

保存するのはKDFの出力、ソルト、パラメータのみとする。ログイン時には同じ計算をやり直し、定数時間で比較する。新規システムにはArgon2idが推奨される。

## 9. HKDF:Extract-then-Expand

ECDHの出力のような、完全には一様でない生の共有秘密から鍵を導出する場合、

```text
PRK = HKDF-Extract(salt, IKM) = HMAC(salt, IKM)
OKM = HKDF-Expand(PRK, info, L)
```

- Extract:エントロピーを一様化する。
- Expand:アプリケーション用の鍵(トラフィック鍵、IV鍵など)を L バイト生成する。

TLS 1.3、Signal、Noiseなどで広く使われている。

## 10. チートシート

```bash
# ── Integrity ────────────────────────────────────────────────
sha256sum file.iso
sha256sum -c SHA256SUMS
b2sum file.tar                 # BLAKE2b (util-linux)

# ── OpenSSL digest / HMAC ────────────────────────────────────
openssl dgst -sha256 file.bin
echo -n 'payload' | openssl dgst -sha256 -hmac 'secret-key'

# ── Argon2 example (Python) ──────────────────────────────────
python3 -c "
from argon2 import PasswordHasher
ph = PasswordHasher()          # Argon2id defaults
h = ph.hash('correct horse battery staple')
print(h)
print(ph.verify(h, 'correct horse battery staple'))
"
```

| セキュリティ用途でのMD5/SHA-1 | 衝突 | SHA-256以上 |
