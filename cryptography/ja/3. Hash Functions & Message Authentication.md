## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| ハッシュ関数 | どんな入力も、決まった長さの短い「指紋」に変える関数 |
| ダイジェスト / ハッシュ値 | 指紋そのもの。たとえばSHA-256の256ビットの出力 |
| 衝突(collision) | 異なる2つの入力が同じハッシュになること |
| 原像(preimage) | あるハッシュを生み出した元の入力 |
| アバランシェ効果 | 入力の小さな変化で出力がまったく変わること |
| MAC | 作るのに秘密鍵が必要な、ハッシュのようなタグ。完全性と真正性の両方を証明する |
| HMAC | ハッシュ関数からMACを作る、標準的で安全な方法 |
| ソルト | パスワードのハッシュの隣に保存する乱数。同じパスワードでも違うハッシュになる |
| KDF | 鍵導出関数。パスワードや生の秘密をきちんとした鍵に変える |
| 定数時間比較 | 常に同じ時間で2つの値を比べる方法。時間から何も漏れないようにする |

## 1. ハッシュ関数とは

ハッシュ関数は、**どんな**長さの入力(1つの単語、ファイル、ディスク丸ごと)でも受け取り、**決まった**長さの出力を、指紋のように作り出す。

```text
SHA-256("hello") → 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
SHA-256("Hello") → 185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969
```

小文字1文字を大文字に変えただけで、結果がまったく別物になった。これが**アバランシェ効果**だ。

良い暗号学的ハッシュには、次のような日常的な性質がある(Wong 第2章)。

- **決定的:** 同じ入力からは必ず同じハッシュが出る。
- **アバランシェ:** 1ビット変えるだけで、出力のおよそ半分のビットが反転する。
- **高速:** 普通のCPUですばやく計算できる(ファイルには好都合だが、パスワードには不都合。第8節を参照)。

ハッシュが使われる場面: ダウンロードしたファイルが壊れていないかの確認、デジタル署名(ファイル全体ではなくハッシュに署名する)、GitのコミットID、Merkle木、鍵の導出。

重要な限界が1つある。**ただのハッシュでは、誰が送ったかは証明できない。** 書き換えたファイルのSHA-256は誰でも計算できるからだ。真正性を証明するには秘密鍵が必要で、それがMAC、HMAC、AEADである(第6節)。

## 2. 3つの安全性の性質

暗号学的ハッシュは、次の3つを事実上不可能にしなければならない。ここで n は出力のビット数(SHA-256なら256)である。

| 性質 | 攻撃者の課題 | 汎用的なコスト | たとえ |
|:---|:---|:---:|:---|
| **原像困難性** | あるハッシュを生む入力を*何か1つ*見つける | 約2ⁿ回 | 指紋から本人を探す |
| **第二原像困難性** | ある入力と同じハッシュになる*別の*入力を見つける | 約2ⁿ回 | Aliceと同じ指紋の人を探す |
| **衝突困難性** | 同じハッシュになる2つの入力を*何でもよいので*見つける | 約2^(n/2)回 | 指紋が一致する2人を*誰でもいいから*探す |

衝突困難性がいちばん弱いことに注意してほしい。攻撃者が2つの入力を自由に選べるので、ずっと簡単になる。2ⁿではなく2^(n/2)になる理由は第3節で説明する。

そのため、128ビットの安全性を目指す現代の設計では、256ビット以上のハッシュを使う。

## 3. 誕生日問題: 衝突は思ったより早く起きる

部屋に何人いれば、誕生日が同じ2人がいる確率が50%になるだろうか。多くの人は180人くらい(365の半分)と答える。正解は**たった23人**だ。

理由は、*自分*と同じ誕生日の人を探しているのではなく、*どれでもいいから*一致するペアを探しているからだ。23人いれば、ペアの組み合わせはすでに253通りある。

ハッシュでも同じことが起きる。ハッシュの出力が N 通りあるなら、衝突が起きそうになるまでに必要な試行は、だいたい N の平方根回で済む。

```text
衝突の確率が50%になる試行回数 ≈ 1.18 × √N

誕生日:   N = 365       →  1.18 × √365 ≈ 23人
SHA-256:  N = 2²⁵⁶      →  約2¹²⁸回
```

実際には次のことを意味する(Wong「The birthday bound」)。

- SHA-256の衝突困難性はおよそ128ビット。これは128ビットの安全性目標に合っており、だから安全とみなされている。
- **ハッシュを短く切り詰めるのは危険だ。** 64ビットに切り詰めたハッシュは、約2³²回の試行で衝突が見つかる。普通のコンピュータでもできてしまう。衝突が問題になる用途(証明書、コンテンツアドレッシング)では、256ビット以上を保つこと。

## 4. ハッシュ関数の作り方

### 4.1 Merkle-Damgård(SHA-1、SHA-2)

SHA-1とSHA-256が使っている方式。考え方は次のとおり。

1. メッセージにパディングを足して、ブロックにきれいに分けられる長さにする(元の長さはパディングの中に書き込む)。
2. ブロックに分割する。
3. 決まった初期値から始め、ブロックを1つずつ入れていく。各ステップで、次のブロックを内部状態に混ぜ込む。
4. 最後の状態がハッシュになる。

```text
初期値 → 混ぜる(ブロック1) → 混ぜる(ブロック2) → 混ぜる(ブロック3) → … → ハッシュ
```

弱点: ハッシュの出力が最後の内部状態**そのもの**であること。ハッシュを知っている人は、元のメッセージを知らなくても、さらにブロックを「混ぜ込み」続けられる。これが**伸長攻撃**だ(第7節)。

### 4.2 スポンジ構造(SHA-3 / Keccak)

SHA-3はしくみが違う。大きな内部状態を2つに分けて使う。

- **レート:** 入力を「吸収(absorb)」し、出力を「絞り出す(squeeze)」部分。
- **キャパシティ:** 直接は出力されない隠れた部分。安全性はこの部分から生まれる(ビット数のおよそ半分)。

状態の一部が決して外に出ないので、SHA-3は伸長攻撃に**弱くない**。同じ設計で、好きな長さの出力を作ることもできる(SHAKE128/256。XOFと呼ばれる)。

```
 Merkle–Damgård                 Sponge (SHA-3)
 M1  M2  M3                     absorb → squeeze
  │   │   │                     ┌──────────────┐
  ▼   ▼   ▼                     │ rate r       │
 IV→f→f→f→ digest               │ capacity c   │──→ digest/XOF
                                └──────────────┘
```

## 5. 今安全なハッシュ関数はどれか

| 関数 | 出力長 | 構造 | 状況 | 備考 |
|:---|:---:|:---|:---|:---|
| MD5 | 128 | MD | **破られている** | 衝突を数秒で見つけられる |
| SHA-1 | 160 | MD | **破られている** | 2017年に実際の衝突が公開された(SHAttered) |
| SHA-256 | 256 | MD | 安全 | 使い方を誤ると伸長攻撃に注意 |
| SHA-512 | 512 | MD | 安全 | 64ビットCPUでは速いことが多い |
| SHA3-256 | 256 | スポンジ | 安全 | 構造の異なる代替手段 |
| SHAKE256 | 任意 | スポンジ(XOF) | 安全 | 出力長を選べる |
| BLAKE3 | 256 | ツリー | 安全、非常に高速 | 複数コアとSIMDを活用する |

実践的なルール: ファイルの完全性にはSHA-256かBLAKE3、新しいプロトコルにはSHA-256、SHA-3、BLAKE3を使う。**セキュリティに関わる用途でMD5やSHA-1は絶対に使わない。**

## 6. MACとHMAC: 秘密鍵を使ったハッシュ

ただのハッシュで証明できるのは、ファイルが*偶然*壊れていないことだけだ。攻撃者は止められない。ファイルを書き換えてハッシュを計算し直せばよいからだ。

**MAC**(メッセージ認証コード)は秘密鍵を混ぜ込む。正しいタグを作れるのは鍵を持っている人だけだ。

```text
タグ = MAC(鍵, メッセージ)
Verify(鍵, メッセージ, タグ) → true / false
```

メッセージが少しでも変わればタグは一致しなくなる。そして鍵がなければ、攻撃者は新しい正しいタグを作れない。

### HMAC(RFC 2104)

HMACは、SHA-256のようなハッシュをMACに変える標準的な方法だ。鍵を毎回混ぜながら、**2回**ハッシュする。

```text
HMAC(K, m) = Hash( 外側の鍵 ‖ Hash( 内側の鍵 ‖ m ) )

内側の鍵 = 鍵 XOR 0x36 0x36 …   (ipad)
外側の鍵 = 鍵 XOR 0x5c 0x5c …   (opad)
```

外側のハッシュが結果を「封印」するので、伸長攻撃を防げる。SHA-256単体は伸長攻撃に弱いが、HMAC-SHA256は安全だ。

### Poly1305

非常に高速なMACで、AEAD方式ChaCha20-Poly1305の中でChaCha20と一緒に使われる。

### 2つのルール

- **MACを `Hash(鍵 ‖ メッセージ)` や `Hash(メッセージ ‖ 鍵)` で作ってはならない。** HMAC、KMAC、Poly1305、またはAEADのタグを使う。
- **タグは定数時間で比較する。** 普通の比較は最初に違うバイトで止まるので、かかった時間を測ると何バイト目まで合っていたかが漏れてしまう。`hmac.compare_digest`(Python)や `CRYPTO_memcmp`(C)を使うこと。

## 7. 伸長攻撃(考え方)

Merkle-Damgård型のハッシュ(SHA-1、SHA-256)では、ハッシュの出力が処理の最後の内部状態になっている。攻撃者が `Hash(秘密 ‖ メッセージ)` と入力の長さを知っていれば、計算を続けて `秘密 ‖ メッセージ ‖ パディング ‖ 追加データ` に対する正しいハッシュを、**秘密を知らないまま**作れてしまう。

つまり、よく見かける次のような自作の設計は**安全ではない**。

```text
auth_tag = SHA256(秘密 ‖ メッセージ)         ✗  伸長攻撃に弱い
auth_tag = HMAC-SHA256(秘密, メッセージ)     ✓  安全
```

対策: HMACを使う、この弱点のないハッシュ(SHA-3、BLAKE3)を使う、またはAEADを使う。

> 教育上の注記: この節では、素朴な設計がなぜ失敗するのか、正しい構成をどう選ぶのかを説明している。第三者のシステムを悪用する方法は扱わない。

## 8. パスワードを安全に保存する

SHA-256は速くなるように設計されているが、パスワードにとってはそれこそが問題になる。GPU1枚で、SHA-256の推測を1秒間に**数十億回**も試せる。SHA-256でハッシュしたパスワードのデータベースが盗まれれば、すぐに破られてしまう。

パスワードには、**わざと遅く**、しかもメモリを大量に使う関数が必要だ。そうすればGPUや専用チップの優位がなくなる。

```text
保存するハッシュ = KDF(パスワード, ソルト, コストの設定)
```

| KDF | 特性 | 備考 |
|:---|:---|:---|
| **Argon2id** | 遅く、メモリハード | Password Hashing Competitionの優勝方式。現代の標準的な選択(Wong) |
| scrypt | メモリハード | 良いが、設定の調整に注意が必要 |
| bcrypt | 遅い(CPUハード) | 今もよく使われる。パスワードの先頭72バイトしか使わない |
| PBKDF2 | HMACを何度も繰り返す | メモリハードではない。非常に多い反復回数が必要 |

### ソルトとペッパー

- **ソルト:** ユーザーごとに異なる乱数(16バイト以上)で、ハッシュの隣に保存する。同じパスワードの2人でも違うハッシュになり、事前に計算された「レインボーテーブル」は役に立たなくなる。
- **ペッパー(任意):** データベースではなくサーバー側に置く追加の秘密。データベースだけが漏れても、ハッシュは守られる。

保存するもの: KDFの出力、ソルト、使った設定。ログイン時は、同じソルトと設定でハッシュを計算し直し、定数時間で比較する。新しいシステムでは**Argon2idを使うこと**。

## 9. HKDF: 1つの秘密から多くの鍵を作る

鍵交換(たとえばECDH)のあとには、1つの共有された秘密が得られる。これは完全にランダムではなく、しかも通常はそこから別々の鍵がいくつも必要になる(送信方向ごとの鍵、IV用の鍵など)。HKDFはこれを2段階で処理する。

```text
1. Extract:  PRK = HMAC(ソルト, 生の秘密)            → 秘密を一様なランダムさに「整える」
2. Expand:   鍵 = HKDF-Expand(PRK, ラベル, 長さ)    → 必要な数だけ鍵を作る
```

`ラベル`(`info` と呼ぶ)によって、導出される鍵がそれぞれ違うものになる。たとえば `"client key"` と `"server key"` だ。

HKDFはTLS 1.3、Signal、Noiseプロトコルフレームワークで使われている。

## 10. チートシート

```bash
# ── ファイルの完全性を確認する ───────────────────────────────
sha256sum file.iso
sha256sum -c SHA256SUMS          # 公開されている一覧と照合する
b2sum file.tar                   # BLAKE2b(coreutilsに含まれる)

# ── OpenSSLでダイジェスト / HMAC ─────────────────────────────
openssl dgst -sha256 file.bin
echo -n 'payload' | openssl dgst -sha256 -hmac 'secret-key'

# ── Argon2でパスワードをハッシュする(Python、argon2-cffi) ───
python3 -c "
from argon2 import PasswordHasher
ph = PasswordHasher()          # 安全なデフォルト設定のArgon2id
h = ph.hash('correct horse battery staple')
print(h)
print(ph.verify(h, 'correct horse battery staple'))
"
```
