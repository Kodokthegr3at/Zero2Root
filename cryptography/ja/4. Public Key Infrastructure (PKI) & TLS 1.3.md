## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| PKI | 公開鍵基盤。どの公開鍵が誰のものかを教えてくれる、認証局・証明書・ルールの仕組み全体 |
| 証明書 | デジタルの身分証。「この公開鍵は example.com のもの」と、信頼された機関が署名したもの |
| CA | 認証局。身元を確認して証明書に署名することを信頼されている組織 |
| ルートCA | 最上位のCA。その証明書はブラウザやOSにあらかじめ入っている |
| 中間CA | ルートから、代わりに証明書へ署名する権限を与えられたCA |
| リーフ証明書 | 実際のWebサイトやサーバーの証明書 |
| CSR | 証明書署名要求。CAに送る「申請書」 |
| 失効(revocation) | 期限が来る前に証明書を無効にすること。たとえば鍵が漏れたとき |
| TLS | HTTPSの「S」にあたるプロトコル。ネットワーク接続を暗号化し、相手を認証する |
| ハンドシェイク | TLS接続の最初のいくつかのメッセージ。両者が鍵に合意し、身元を確認する |
| 前方秘匿性(PFS) | 後からサーバーの鍵が漏れても、記録済みの過去の接続は明かされない性質 |

## 1. なぜPKIが必要なのか

公開鍵暗号(LC-055)を使えば、誰でもあなたの公開鍵であなた宛てに暗号化できる。しかし問題がある。**その公開鍵が本当に `example.com` のものだと、どうやって分かるのか?**

答えがなければ、あなたとサーバーの間にいる攻撃者は、**自分の**公開鍵を渡してサーバーになりすませばよい。あなたはすべてを攻撃者宛てに暗号化し、攻撃者はそれを読んでから先へ渡す。これが**中間者(MITM)攻撃**で、あなたには気づく手段がない。

PKIはパスポートと同じやり方でこれを解決する。信頼された機関(**CA**)があなたの身元を確認し、次のような主張に署名する。

```text
証明書 = CAによる次の内容への署名 {
    名前:        example.com
    公開鍵:      <サーバーの公開鍵>
    有効期間:    2026-01-01 から 2026-04-01 まで
    拡張:        許可された用途、失効の確認先、…
}
```

ブラウザやOSには、信頼するCAの一覧(**トラストアンカー**、つまりルートCA)が最初から入っている。証明書がそのどれかに署名されていれば、ブラウザはその鍵が本当にその名前のものだと受け入れる。

PKIは新しい数学を使わない。デジタル署名(LC-055)に一連のルールを加え、インターネット規模で運用しているだけだ(Wong 第7章/第9章)。

## 2. 信頼の連鎖

ルートCAは重要すぎて日常的には使えないので、普通はハードウェアセキュリティモジュール(HSM)の中にオフラインで保管される。代わりに**中間CA**に権限を与え、日々の署名を任せる。

```
[ Root CA ]  self-signed, often offline HSM
      │  signs
      ▼
[ Intermediate CA ]  day-to-day issuance
      │  signs
      ▼
[ End-entity / leaf ]  CN/SAN = example.com
```

### ブラウザによる証明書の確認

サーバーはリーフ証明書と中間証明書を送ってくる。ブラウザは次を確認する。

```text
1. ルートの公開鍵で、中間証明書の署名を検証する
2. 中間証明書の公開鍵で、リーフ証明書の署名を検証する
3. リーフ証明書の名前が、入力したサイト(example.com)と一致する
4. 今日の日付が有効期間内で、証明書が失効していない
```

証明書に書かれたいくつかのルールも確認する。中間証明書にはCAとして働いてよいという印(`CA:TRUE`)が必要で、リーフ証明書はWebサイト用に使ってよいもの(`serverAuth`)でなければならない。

どれか1つでも失敗すると、おなじみの「この接続ではプライバシーが保護されません」という警告が出る。

## 3. 証明書の中身(X.509 v3)

| フィールド | 意味 |
|:---|:---|
| `Subject` | 証明書の対象(古いフィールド。今重要なのはSAN) |
| `Subject Public Key Info` | 公開鍵そのものと、使うアルゴリズム |
| `Issuer` | どのCAが署名したか |
| `Serial Number` | CAごとに一意の番号。失効のときに使う |
| `Validity` | `notBefore` / `notAfter`: 開始日と終了日 |
| `Signature` | 上のすべてのフィールドに対するCAの署名 |
| 拡張 | SAN、許可された用途(EKU)、鍵ID、失効の確認先(CRL/OCSP)、CTの証明 |

**SAN**(Subject Alternative Name)に、実際の名前の一覧が入っている。たとえば `DNS:example.com` や `DNS:*.example.com` だ。ブラウザが確認するのはSANで、古い `Subject` フィールドではない。

## 4. 証明書の一生

### 4.1 証明書を申請する(CSR)

1. 自分で鍵ペアを作る。秘密鍵がサーバーの外に出ることはない。
2. 名前と公開鍵を入れた**CSR**を作り、秘密鍵で署名する。これで、対応する秘密鍵を本当に持っていることを証明する。
3. CAは、あなたがそのドメインを管理していることを確認する。ACMEプロトコル(Let's Encryptが使う)では、Webサイトにファイルを置く(HTTP-01)か、DNSレコードを追加する(DNS-01)。
4. CAが署名し、証明書を返す。

### 4.2 失効: 証明書を早めに無効にする

秘密鍵が漏れたら、期限前に証明書を無効にしなければならない。方法は次のとおり。

| 方法 | しくみ | 欠点 |
|:---|:---|:---|
| CRL | CAが無効にしたシリアル番号の一覧を、署名付きで公開する | 一覧が大きくなり、更新も遅い |
| OCSP | ブラウザがCAに「このシリアル番号はまだ有効か」と問い合わせる | 遅く、どのサイトを見ているかがCAに知られる |
| OCSPステープリング | サーバー自身が最新のOCSP応答を取ってきて添付する | 速く、プライバシーも守られる |
| 短命な証明書 | 数日しか有効でない証明書 | 失効の重要性がずっと小さくなる |

実際には失効はあまり当てにならない。そのため業界は短命な証明書へと移りつつある。

### 4.3 Certificate Transparency(CT)

公に信頼されるすべての証明書は、誰でも見られて追記しかできない**CTログ**に記録しなければならず、ブラウザはその証拠(SCT)を求める。つまりCAが、あなたのドメインの偽の証明書をこっそり発行することはできない。ログを監視すれば見つけられるからだ。

## 5. TLS 1.3のハンドシェイクを順番に見る

TLS 1.3(RFC 8446)は、古いTLSを大掃除したものだ。弱い選択肢(RSA鍵輸送、CBCモード、RC4、SHA-1ベースのcipher suite)が取り除かれ、完全なハンドシェイクに必要な往復は**1回**だけになった(Wong 第9章)。

```
Client                                                 Server
  │ ClientHello                                      │
  │  + supported_versions=1.3                        │
  │  + cipher_suites (AEAD+hash)                     │
  │  + supported_groups (e.g. x25519)                │
  │  + key_share (client ephemeral pk)               │
  │─────────────────────────────────────────────────>│
  │                                                 │
  │              ServerHello + key_share            │
  │              {EncryptedExtensions}              │
  │              {Certificate}                      │
  │              {CertificateVerify}                │
  │              {Finished}                         │
  │<─────────────────────────────────────────────────│
  │ {Finished}                                      │
  │─────────────────────────────────────────────────>│
  │══════════ Application Data (AEAD) ══════════════│
```

`{...}` は、そのメッセージがすでに暗号化されていることを表す。

何が起きているかを分かりやすく説明すると、次のようになる。

1. **ClientHello:** クライアントは対応しているTLSのバージョンと暗号を伝え、一時的な鍵交換の自分の分(ECDHEの `key_share`、たとえばX25519)をすぐに送る。
2. **ServerHello:** サーバーは暗号を選び、鍵交換の自分の分を送る。これで両者は同じ共有秘密を計算できる(LC-055のECDHの考え方)。**ここから先はすべて暗号化される。**
3. **Certificate:** サーバーが証明書チェーンを送る(第2節)。
4. **CertificateVerify:** サーバーは、ここまでの会話全体のハッシュに、証明書の秘密鍵で署名する。これで、本当にその証明書の持ち主であること、*そして*まさに今このハンドシェイクに参加していることを証明する。
5. **Finished(両者):** それぞれが会話全体に対するHMACを送る。攻撃者がそれまでのメッセージを書き換えたり消したりしていれば(たとえば弱い設定を強制するために)、値が一致せず接続は切られる。

### 鍵はどこから来るのか

ECDHEの共有秘密はそのまま使われない。TLS 1.3はそれをHKDF(LC-056)に段階的に通し、用途ごとに別々の鍵を作る。

```text
(任意のPSK)          → early secret
+ ECDHEの秘密        → handshake secret  → 残りのハンドシェイクを守る鍵
                     → master secret     → 実際のアプリケーションデータを守る鍵
```

途中で、すべてのハンドシェイクメッセージのハッシュ(**トランスクリプトハッシュ**)も混ぜ込まれる。だから最終的な鍵は、この1つの会話だけのものになり、ほかのどこにも使えない。

## 6. 実際のデータを暗号化する

ハンドシェイクが終わると、データの1つ1つ(各**レコード**)がAEAD(LC-054)で守られる。秘密性と改ざん検知の両方が得られる。

```text
暗号化されたレコード = AEAD(トラフィック鍵, ノンス, データ + コンテンツタイプ)
```

TLS 1.3で許されるcipher suiteはわずかで、すべてAEADだ。
- `TLS_AES_128_GCM_SHA256`
- `TLS_AES_256_GCM_SHA384`
- `TLS_CHACHA20_POLY1305_SHA256`

各レコードのノンスはレコードのカウンタから作られるので、決して繰り返さない。だからTLSの鍵を取り出して、TLS以外の場所で使い回してはならない。

## 7. 前方秘匿性と0-RTT

### 前方秘匿性(PFS)

誰かが今日、あなたの暗号化された通信をすべて記録し、何年も後にサーバーの秘密鍵を盗んだとしよう。古い記録を復号できるだろうか?

TLS 1.3なら**できない**。トラフィック鍵は、接続のあとで捨てられた一時的な(ephemeral)ECDHEの鍵ペアから作られている。サーバーの長期鍵はハンドシェイクに*署名する*だけで、トラフィック鍵を守ることは一度もない。

この理由から、TLS 1.3は(EC)DHEを必須にしている。唯一の例外は「PSKのみ」モードで、特定の用途のために、あえて前方秘匿性を手放している。

### 0-RTT(early data)

最近アクセスしたサーバーに再接続するとき、クライアントは最初のメッセージでもうデータを送れるので、往復を1回節約できる。その代わり、攻撃者はその最初のメッセージを記録して**再送(リプレイ)**できてしまう。

だから0-RTTが安全なのは、繰り返されても害のないリクエスト(ページの読み込みのようなGET)だけだ。支払いやパスワード変更のような操作には、決して0-RTTを許してはならない。

## 8. 脅威と防御

| 脅威 | 何が起きるか | 防御 |
|:---|:---|:---|
| 不正な、または侵害されたCA | 誰かがあなたのドメインの有効な偽証明書を手に入れる | CTログの監視、CAAのDNSレコード |
| サーバーの秘密鍵の盗難 | 攻撃者がサーバーになりすませる | 短命な証明書、HSMでの鍵管理、迅速な失効 |
| SSLストリッピング | 攻撃者が訪問者をただのHTTPに格下げする | HSTS、HTTPSのみ |
| 壊れた証明書チェック | アプリがホスト名の確認を飛ばしたり、何でも信頼したりする | OS/ブラウザ標準の検証機能を使う。`InsecureSkipVerify` を本番に出さない |
| DNS乗っ取りによる誤発行 | 攻撃者がDNSを握り、証明書を手に入れる | CAA、CTの監視、DNSSEC |

**証明書ピンニング**とは、アプリが特定の鍵や証明書だけを受け入れることだ。完全に自分で管理しているモバイルアプリではうまく機能するが、鍵をローテーションすると簡単に壊れる。公開のWebサイトでは、CTの監視と証明書の適切な管理のほうが良い選択である。

## 9. OpenSSLチートシート

```bash
# ── 秘密鍵とCSRを作る(RSA) ─────────────────────────────────
openssl req -new -newkey rsa:4096 -nodes \
  -keyout example.com.key -out example.com.csr \
  -subj "/C=ID/O=LearnCyber/CN=example.com"

# ── ラボ用の自己署名証明書(ECDSA P-256) ─────────────────────
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -days 365 -nodes -keyout server.key -out server.crt \
  -subj "/CN=localhost"

# ── サーバーが送る証明書チェーンを見る ───────────────────────
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# ── CAバンドルに対して証明書を検証する ───────────────────────
openssl verify -CAfile ca_chain.pem example.com.crt

# ── 証明書のフィールドを読む ─────────────────────────────────
openssl x509 -in server.crt -noout -text -fingerprint -sha256

# ── サーバーがTLS 1.3に対応しているか試す ────────────────────
openssl s_client -connect example.com:443 -tls1_3 -servername example.com </dev/null
```

## セキュリティノート: 運用者向けチェックリスト

1. 本番サーバーではTLS 1.2未満をすべて無効にし、TLS 1.3を優先する。
2. AEADのcipher suiteだけを許可し、OCSPステープリングを有効にする。
3. HSTSを有効にし、HTTPをHTTPSへリダイレクトする。CAAレコードも検討する。
4. 秘密鍵を守る: パーミッションは `0600`、できればHSM/KMSに置き、**絶対に**gitにコミットしない。
5. 自分のドメイン宛てに発行された証明書がないか、Certificate Transparencyのログを監視する。
