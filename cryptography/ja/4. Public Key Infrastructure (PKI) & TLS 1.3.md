## 1. PKIが必要な理由

公開鍵暗号は、pk が本当に `example.com` のものであると確信できて初めて、鍵配送の問題を解決する。身元への束縛がなければ、攻撃者は次のような中間者攻撃(MITM)を行える。

攻撃者はサーバーの本物の公開鍵を自分の鍵にすり替えるだけでよく、被害者はそれに気づけない。

PKIとは、認証局(CA)が次のような主張に署名するための、役割・方針・フォーマット(X.509)の集合である。

```text
Cert = Sign(sk_CA, {Subject, pk_Subject, validity, extensions})
```

つまりCAは自分の秘密鍵を使って、「この公開鍵はこの名前のもので、この期間有効である」という主張に署名する。

ブラウザやOSは、この検証全体の起点となるトラストアンカー(ルートCA)を保持している。

PKIは新しい数学的プリミティブを発明するものではない。デジタル署名と運用方針を組み合わせることで、クライアントがインターネット規模でサーバー(場合によってはクライアントも)を認証できるようにする仕組みである(Wong, 第7/9章)。

## 2. 信頼の連鎖

```
[ Root CA ]  self-signed, often offline HSM
      │  signs
      ▼
[ Intermediate CA ]  day-to-day issuance
      │  signs
      ▼
[ End-entity / leaf ]  CN/SAN = example.com
```

### チェーン検証の考え方

クライアントはリーフ証明書と中間証明書を受け取り、次を検証する。

```text
1. ルートの公開鍵で中間証明書を検証する
2. 中間証明書の公開鍵でリーフ証明書を検証する
3. リーフの名前が example.com と一致する
4. 証明書が期限切れでなく、失効もしていない
```

パス構築の際には、Basic Constraints(CA:TRUE)、Key Usage、`serverAuth` などのExtended Key Usageの方針も確認する。

## 3. X.509証明書(v3)の構造

| フィールド | 意味 |
|:---|:---|
| `Subject` | 所有者の識別情報(歴史的な項目)。現代の実務ではSANに依拠する |
| `Subject Public Key Info` | 鍵アルゴリズムと pk |
| `Issuer` | 署名したCA |
| `Serial Number` | CAごとに一意。失効管理で重要 |
| `Validity` | `notBefore` / `notAfter` |
| `Signature` | TBSCertificateに対するCAの署名 |
| 拡張領域 | SAN、EKU、SKI/AKI、CRL配布点、OCSP AIA、CTのSCT |

SAN(Subject Alternative Name)は、現代において名前の正しさを判定するための基準となる項目であり、`DNS:example.com` や `DNS:*.example.com` のように記述される。

## 4. 証明書のライフサイクル

### 4.1 CSR(証明書署名要求)

申請者は鍵ペア (pk,sk) を生成し、次のような要求を作る。

```text
CSR = Sign(sk, {Subject, pk, attributes})
```

要求に sk で署名することで、申請者が対応する秘密鍵を本当に持っていることを証明する。

CAは、証明書を発行する前にドメイン制御を検証する(ACMEプロトコルにおけるHTTP-01やDNS-01など)。

### 4.2 失効(Revocation)

- CRL:失効した証明書のシリアル番号一覧で、CAが署名する。サイズが大きくなりやすく、更新も遅れがちである。
- OCSP:特定のシリアル番号の状態をオンラインで問い合わせる仕組み。
- OCSPステープリング:サーバー自身が最新のOCSPレスポンスを添付する方式で、プライバシーとレイテンシの両面で優れている。
- 短命証明書(数時間から数日):失効の仕組みへの依存そのものを減らす。

### 4.3 Certificate Transparency(CT)

追記専用の公開ログ。ブラウザはSCT(Signed Certificate Timestamp)を要求する。CTにより、誤発行や不正な証明書の検出が容易になる。

## 5. TLS 1.3のハンドシェイク:仕組みと鍵スケジュール

TLS 1.3(RFC 8446)は、RSA鍵転送、CBCモード、RC4、SHA-1ベースの旧式cipher suiteを廃止し、フルハンドシェイクを1-RTTまで短縮した(Wong, 第9章)。

### 5.1 フルハンドシェイクの概略

```
Client                                                 Server
  │ ClientHello                                      │
  │  + supported_versions=1.3                        │
  │  + cipher_suites (AEAD+hash)                     │
  │  + supported_groups (e.g. x25519)                │
  │  + key_share (client ephemeral pk)               │
  │─────────────────────────────────────────────────>│
  │                                                 │
  │              ServerHello + key_share            │
  │              {EncryptedExtensions}              │
  │              {Certificate}                      │
  │              {CertificateVerify}                │
  │              {Finished}                         │
  │<─────────────────────────────────────────────────│
  │ {Finished}                                      │
  │─────────────────────────────────────────────────>│
  │══════════ Application Data (AEAD) ══════════════│
```

`{...}` はハンドシェイクトラフィック鍵で暗号化されたメッセージを表す。

### 5.2 ECDHEによる共有秘密

```text
SharedSecret = ECDH(クライアントの一時的な秘密鍵, サーバーの一時的な公開鍵)
```

### 5.3 HKDFによる鍵スケジュール(形式的な直感)

TLS 1.3は、段階的なシークレットの連鎖から多数の鍵を導出する。核となるパターンは次のとおり。

```text
PSK または 0     → EarlySecret
+ ECDHEの秘密    → HandshakeSecret  → ハンドシェイク用トラフィック鍵
+ 0              → MasterSecret     → アプリケーション用トラフィック鍵
```

各段階で、前のシークレットを新しい入力と一緒にHKDFに入れる。途中でトランスクリプトハッシュも混ぜるので、鍵はこのハンドシェイクだけに結びつく。

トランスクリプトハッシュは、すべてのハンドシェイクメッセージを束縛する。

```text
TranscriptHash = Hash(ClientHello ‖ ServerHello ‖ ... ‖ Finished)
```

`CertificateVerify` は、トランスクリプトに対するサーバーのデジタル署名である。証明書の秘密鍵を所有していることを証明すると同時に、それをその場限りのECDHE鍵交換に結びつける(認証付き鍵交換)。

### 5.4 Finished

```text
Finished = HMAC(FinishedKey, TranscriptHash)
```

両者が同一のトランスクリプトを見ていることを確認し、ダウングレード攻撃や改ざんへの対策となる。

## 6. レコード層:アプリケーションデータの暗号化

トラフィック鍵が確立すると、各レコードは次のように処理される。

```text
ciphertext = AEAD(key, nonce, plaintext ‖ content_type)
```

現代的なcipher suiteの例:
- `TLS_AES_128_GCM_SHA256`
- `TLS_AES_256_GCM_SHA384`
- `TLS_CHACHA20_POLY1305_SHA256`

TLS 1.3のノンスは、シーケンス番号と静的IVのXORから構成される。TLSのステートマシンの外側でコネクション鍵を再利用してはならない。

## 7. 完全前方秘匿性(PFS)と0-RTT

### PFS

サーバーの長期秘密鍵が将来漏洩したとしても、トラフィック鍵がその場限りのECDHE交換に依存しているため、過去のセッションは安全なままである。

後から長期秘密鍵が漏れても、記録済みの過去のセッションを誰かが復号できるようには**ならない**。

TLS 1.3は(EC)DHEを必須としている。ただし、リスクを承知のうえで設計されたPSKのみのモードは例外である。

### 0-RTT(early data)

PSKを再利用する場合、クライアントは最初のフライトでデータを送信できる。その代償はリプレイのリスクである。アプリケーションは冪等であるか、機密性の高い操作については0-RTTを拒否しなければならない。

## 8. 脅威と対策(概念)

| 脅威 | 攻撃の考え方 | 対策 |
|:---|:---|:---|
| 不正または侵害されたCA | 自ドメインに対する偽造証明書 | CTモニタリング、CAA DNSレコード、限定的なピンニング |
| リーフ鍵の窃取によるMITM | なりすまし | 短命証明書、HSM、迅速な失効 |
| SSLストリッピング | HTTPへのダウングレード | HSTS、HTTPS専用化 |
| 検証の不備 | ホスト名チェックの省略、全信頼設定 | OS/ブラウザ標準の検証器を使う。本番環境で`InsecureSkipVerify`を使わない |
| 攻撃者証明書へのDNSハイジャック | CAの誤発行が起きた場合 | CAA、CT、DNSSECをさらなる防御層として追加 |

証明書ピンニングは、アプリを特定のSPKIに束縛する手法である。自社が完全に管理するモバイルアプリには有効だが、鍵のローテーションがあるため運用上は壊れやすい。公開Webにおいては、CTと現代的なPKIの衛生管理を優先するほうがよい。

## 9. OpenSSLチートシート

```bash
# ── CSR (RSA) ────────────────────────────────────────────────
openssl req -new -newkey rsa:4096 -nodes \
  -keyout example.com.key -out example.com.csr \
  -subj "/C=ID/O=LearnCyber/CN=example.com"

# ── Self-signed lab cert (ECDSA P-256) ───────────────────────
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -days 365 -nodes -keyout server.key -out server.crt \
  -subj "/CN=localhost"

# ── Inspect remote chain ─────────────────────────────────────
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# ── Verify chain ─────────────────────────────────────────────
openssl verify -CAfile ca_chain.pem example.com.crt

# ── Show cert fields ─────────────────────────────────────────
openssl x509 -in server.crt -noout -text -fingerprint -sha256

# ── Test TLS 1.3 only ────────────────────────────────────────
openssl s_client -connect example.com:443 -tls1_3 -servername example.com </dev/null
```

## セキュリティノート:運用者向けチェックリスト

1. 本番サーバーではTLS 1.2未満を無効化し、TLS 1.3を優先する。
2. AEAD系のcipher suiteのみを使い、OCSPステープリングを有効にする。
3. HSTSを適用してHTTPSへリダイレクトする。CAAレコードの導入も検討する。
4. 秘密鍵のパーミッションは`0600`とし、理想的にはHSM/KMSに保管する。gitにコミットしてはならない。
5. 自社ドメインについて、Certificate Transparencyのログを監視する。
