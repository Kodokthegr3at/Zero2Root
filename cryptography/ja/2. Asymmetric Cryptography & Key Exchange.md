## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| 公開鍵(pk) | 誰に渡してもよい鍵。あなた宛てのメッセージを暗号化したり、あなたの署名を確かめたりするのに使われる |
| 秘密鍵(sk) | あなただけが持つ鍵。復号や署名に使う |
| 鍵ペア | 対になった公開鍵と秘密鍵 |
| 剰余演算(mod) | 「時計の計算」。割った余りだけを残す。17 mod 12 = 5 |
| 素数 | 1と自分自身でしか割り切れない数(2, 3, 5, 7, 11, …) |
| 一方向関数 | 一方向の計算は簡単だが、逆にたどるのは事実上不可能な関数 |
| 鍵交換 | 公開のネットワーク越しに、2人が共通の秘密鍵に合意する方法 |
| デジタル署名 | 秘密鍵で作る「このメッセージは自分が送り、書き換えられていない」という証明 |
| パディング(RSA) | RSAの前にメッセージへ加えるランダムな構造。素の数学を悪用されないようにする |
| 一時鍵(ephemeral) | 1回のセッションだけ使って捨てる鍵 |
| PFS(前方秘匿性) | 長期鍵が後から漏れても、記録済みの過去のセッションは復号できない性質 |

## 1. 考え方: 公開鍵と秘密鍵

共通鍵暗号には大きな問題が1つある。両者が同じ秘密鍵を持つ必要があるのに、暗号化がまだない状態ではインターネット越しに鍵を安全に送れないのだ。

公開鍵暗号は、数学的につながった**2つの別々の鍵**でこれを解決する。

- **公開鍵(pk):** どこに公開してもよい。開いた南京錠のようなもので、誰でもあなた宛ての箱にカチッと閉められる。
- **秘密鍵(sk):** 絶対に秘密にしておく。その南京錠を開けられるのはこの鍵だけだ。

```text
KeyGen()         → (pk, sk)
c = Enc(pk, m)     公開鍵を使えば誰でも暗号化できる
m = Dec(sk, c)     復号できるのは秘密鍵の持ち主だけ
```

これが成り立つのは、**落とし戸(トラップドア)付きの一方向関数**があるからだ。計算するのは簡単だが、逆にたどるのは事実上不可能。ただし秘密の追加情報(秘密鍵)を知っていれば戻せる。

公開鍵の処理はAESよりずっと遅い。だから実際のシステムでは、公開鍵暗号は鍵の合意や保護だけに使い、実際のデータは高速な共通鍵AEADで暗号化する。この組み合わせを**ハイブリッド暗号**という(第7節)。

## 2. 必要な数学(ほんの少しだけ)

数学者になる必要はない。RSAとディフィー・ヘルマンを理解するには、次の4つの考え方で十分だ。

### 2.1 剰余演算(「時計の計算」)

`a mod n` は「a を n で割った余り」という意味。時計は n = 12 でこの計算をしている。

```text
17 mod 12 = 5          (17時は5時)
25 mod 12 = 1
```

余りが同じ2つの数は「n を法として等しい」といい、`a ≡ b (mod n)` と書く。たとえば 17 ≡ 5 (mod 12)。

### 2.2 オイラーのφ(ファイ)関数

φ(n) は、1から n-1 までの数のうち、n と共通の約数を持たないものの個数を数える。RSAに必要なのは、p と q が素数で n = p × q のときの近道だけだ。

```text
φ(n) = (p - 1) × (q - 1)

例: p = 3, q = 11  →  n = 33,  φ(33) = 2 × 10 = 20
```

**オイラーの定理**によると、n と共通の約数を持たない数を φ(n) 乗すると、必ず 1 (mod n) になる。この事実がRSAの復号を成り立たせている。

### 2.3 モジュラー逆元

e の(φ(n) を法とした)逆元とは、e × d の余りが1になるような数 d のことだ。

```text
e × d ≡ 1 (mod φ(n))

例: φ(n) = 20, e = 3  →  d = 7(3 × 7 = 21 = 20 + 1 だから)
```

コンピュータは拡張ユークリッドの互除法で d をすばやく求める。

### 2.4 離散対数問題

g、p、A = gᵃ mod p が分かっているとき、a を求める問題。

```text
簡単な向き:  a = 6  →  A = 5⁶ mod 23 = 8         (巨大な数でも速い)
難しい向き:  A = 8  →  a = ?                      (巨大な数では事実上不可能)
```

前向きの計算は速い。逆向きの計算は、数百桁の数では宇宙の年齢より長くかかる。ディフィー・ヘルマンはこの差の上に作られている。

## 3. RSA

RSA(Rivest-Shamir-Adleman)は、ある1つの事実に頼っている。**大きな素数2つを掛けるのは簡単だが、その結果を元の2つの素数に分解する(素因数分解)のは非常に難しい。**

### 3.1 鍵ペアを作る

1. 秘密の大きな素数 p と q を選ぶ。
2. 掛け合わせる: n = p × q。この n は公開する。
3. φ(n) = (p - 1)(q - 1) を計算する。
4. φ(n) と共通の約数を持たない公開指数 e を選ぶ。ほぼ全員が e = 65537 を使う。
5. 秘密指数 d、つまり e の(φ(n) を法とした)逆元を計算する。

```text
公開鍵 = (n, e)
秘密鍵 = (n, d)      復号を速くするため p と q も一緒に保存することが多い
```

n は誰でも見られるが、p と q を知らなければ φ(n) を計算できず、したがって d も計算できない。

### 3.2 暗号化と復号(教科書的RSA)

```text
暗号化:  C = Mᵉ mod n
復号:    M = Cᵈ mod n

例: n = 33, e = 3, d = 7 のとき
  M = 4   →  C = 4³ mod 33 = 64 mod 33 = 31
  C = 31  →  M = 31⁷ mod 33 = 4   ✓
```

復号で M に戻る理由: e × d が「φ(n) の倍数 + 1」になるように e と d を選んでいるからだ。オイラーの定理により、M をその数で累乗すると M だけが残る。

本物のRSAは600桁以上の数を使うが、手順はまったく同じである。

### 3.3 教科書的RSAをそのまま使ってはならない

上のやり方は学習用でしかない(Wong §6.3)。実際に使うと危険だ。

- **予測できてしまう:** 同じメッセージは常に同じ暗号文になるので、攻撃者は推測を試せる。
- **操作できてしまう:** 鍵を知らなくても、C を変えて M を予測どおりに変える(たとえば2倍にする)ことができる。

対策は**パディング**だ。**RSA-OAEP**は暗号化の前に新しい乱数をメッセージに混ぜるので、同じメッセージでも毎回違う暗号文になり、改ざんも検知できる。

```text
C = RSA(pk, OAEP(M, 乱数))
```

ライブラリのOAEPオプション(たとえば `RSA_PKCS1_OAEP_PADDING`)を使うこと。素の計算を自分でやってはいけない。

### 3.4 実践上の注意

- 暗号化には**RSA-OAEP**、署名には**RSA-PSS**を使う。古いPKCS#1 v1.5暗号化は、パディングオラクル攻撃の長い歴史があるので、新しい設計では避ける。
- 復号は通常、CRTという工夫で約4倍速くなる。p と q をそれぞれ法として別々に計算する方法で、ライブラリが自動でやってくれる。
- TLS 1.3はもはやRSAで鍵を送らない。前方秘匿性が得られる(EC)DHE(第4節)を使う。

| 安全性の目安 | RSAの鍵長 | ECCの鍵長(§5参照) |
|:---|:---:|:---:|
| 約128ビット | 3072ビット以上 | 約256ビット |
| 約192ビット | 7680ビット以上 | 約384ビット |
| 約256ビット | 15360ビット以上 | 約521ビット |

## 4. ディフィー・ヘルマン鍵交換

ディフィー・ヘルマン(DH)を使うと、2人は公開のネットワーク越しに、**秘密そのものを一度も送らずに**共通の秘密に合意できる(Wong 第5章)。

### 絵の具のたとえ

AliceとBobは、共通の色(たとえば黄色)を公開で決める。それぞれがこっそり自分だけの色を選んで黄色に混ぜ、その混ぜた色を交換する。受け取った色に、もう一度自分だけの色を混ぜる。すると2人とも同じ最終的な色になる。盗聴者には黄色と2つの混ぜた色が見えるが、絵の具を「分離」して秘密の色を取り出すことはできない。

### 本物の手順

公開の設定: 大きな素数 p と数 g(「生成元」)。

```text
Alice: 秘密の a を選び、A = gᵃ mod p を送る
Bob:   秘密の b を選び、B = gᵇ mod p を送る
Alice は Bᵃ mod p、Bob は Aᵇ mod p を計算  →  どちらも gᵃᵇ mod p になる

例: p = 23, g = 5 のとき
  a = 6   →  A = 5⁶ mod 23 = 8
  b = 15  →  B = 5¹⁵ mod 23 = 19
  Alice: 19⁶ mod 23 = 2      Bob: 8¹⁵ mod 23 = 2   ✓ 同じ鍵
```

```
Alice                                              Bob
  │ a random                                         │ b random
  │ A = g^a mod p                                    │ B = g^b mod p
  │─────────────── A ───────────────────────────────>│
  │<────────────── B ────────────────────────────────│
  │ K = B^a                                          │ K = A^b
  │═══════════════ K = g^{ab} ═══════════════════════│
```

盗聴者に見えるのは p、g、A、B だ。共通の鍵を得るには a か b が必要で、それには第2.4節の離散対数問題を解かなければならない。

### 2つの重要なルール

1. **DHだけでは、相手が誰なのかは証明できない。** 間にいる攻撃者が、Aliceとの間で1回、Bobとの間で1回、別々にDHを行うことができる。だから実際のプロトコル(TLSなど)では、交換内容に証明書で署名もする。
2. **セッションごとに新しい鍵を使う**(DHE / ECDHE。「E」はephemeral、一時的という意味)。そうすれば、後で長期鍵が漏れても過去のセッションは安全なままだ。これが**前方秘匿性(PFS)**である。

さらに、受け取った公開値が正しいか必ず確認し、標準のグループ(RFC 7919など)、できれば楕円曲線を使うこと。

## 5. 楕円曲線暗号(ECC)

楕円曲線暗号は、RSAやDHと同じ役割を、**ずっと小さな鍵**とより速い処理でこなす。256ビットのECC鍵は、3072ビットのRSA鍵とほぼ同じ強さだ。だからECCはTLS、SSH、モバイルアプリの標準になっている。

### 楕円曲線とは

次のような式を満たす点 (x, y) の集まりである。

```text
y² = x³ + ax + b   (mod p)
```

普通の数で描くと、x軸を境に上下対称な、なめらかな曲線になる。

### 点の足し算

曲線上の2点は、図形的なルールで「足す」ことができる。2点を通る直線を引き、その直線が曲線と交わる3つ目の点を見つけ、x軸に対して折り返す。同じ点どうしを足すときは接線を使う。

点を数 k 倍するとは、その点を k 回足し合わせることだ。

```text
k·G = G + G + ... + G      (k 回)
```

コンピュータは「2倍して足す(double and add)」という工夫でこれを速く計算する。しかし逆向き(k·G と G から k を求める)は非常に難しい。これが**楕円曲線離散対数問題(ECDLP)**で、ECCの安全性はこれに支えられている。

### ECDH: 楕円曲線上のディフィー・ヘルマン

```text
Alice: 秘密の a  →  A = a·G を送る
Bob:   秘密の b  →  B = b·G を送る
共通の秘密:  a·B = b·A = (a·b)·G
```

第4節とまったく同じ考え方だ。ネットワークを流れるのは A と B だけで、それでも両者は同じ点にたどり着く。

よく使われる曲線:
- **P-256**(prime256v1、secp256r1とも呼ばれる): 幅広く対応している。
- **X25519**(RFC 7748): 現代の定番。APIが誤用しにくいように設計されている。

点の計算を自分でやらず、高水準のAPI(`X25519`、`Ed25519`)を使うこと。

| レベル | 共通鍵 | RSA | ECC |
|:---|:---:|:---:|:---:|
| 標準 | 128 | 3072 | 256(P-256 / X25519) |
| 高 | 192 | 7680 | 384 |
| 非常に高い | 256 | 15360 | 521 / Ed448 |

## 6. デジタル署名

デジタル署名は暗号化の逆だ。**秘密**鍵で署名し、誰でもあなたの**公開**鍵で確かめられる。

```text
σ = Sign(sk, メッセージ)
Verify(pk, メッセージ, σ) → true / false
```

正しい署名は2つのことを証明する。メッセージが秘密鍵の持ち主から来たこと、そしてその後に書き換えられていないことだ。実際には、メッセージそのものではなくメッセージの**ハッシュ**に署名する(LC-056を参照)。

### 主な署名方式

| 方式 | 基盤 | 備考 |
|:---|:---|:---|
| RSA-PSS | RSA | RSAで署名するときの推奨方式。古いPKCS#1 v1.5より優れている |
| ECDSA | 楕円曲線 | 非常に普及しているが、危険な弱点がある(下記) |
| Ed25519(EdDSA) | 楕円曲線 | SSH、Gitなど多くのプロトコルで使われる現代の標準 |

### ECDSAの弱点: 乱数

ECDSAの署名には、毎回新しい乱数 k(ノンス)が必要だ。これは署名ごとに**一意で秘密**でなければならない。同じ k を2回使ったり、k が少しでも予測できたりすると、攻撃者はたった2つの署名から秘密鍵を計算できてしまう。

これは実際に起きた。ソニーはPlayStation 3のソフトウェアに毎回同じ k で署名しており、署名用の秘密鍵が割り出された。

**Ed25519**はこの問題を完全に避けている。ノンスを乱数生成器ではなく秘密鍵とメッセージから計算するので、乱数生成器が壊れていても鍵は漏れない(ECDSAでも、RFC 6979が同じ工夫をしている)。

## 7. ハイブリッド暗号: 実際のシステムは両方を組み合わせる

大きなファイルを直接RSAで暗号化するのは遅く、扱いにくい。実際のシステムは両方の暗号の長所を組み合わせる。

1. ランダムな256ビットの**セッション鍵**を作る。
2. 実際のデータを、そのセッション鍵と高速な共通鍵AEAD(AES-GCMかChaCha20-Poly1305)で暗号化する。
3. セッション鍵を公開鍵暗号で守る。受信者のRSA公開鍵で暗号化する(RSA-OAEP)か、ECDHの交換から導出する。

```text
[ 大きなデータ ] --セッション鍵でAES-GCM--> [ 暗号化されたデータ ]
[ セッション鍵 ] --受信者の公開鍵--> [ 暗号化されたセッション鍵 ]
両方を送る
```

このパターンを**KEM/DEM**(鍵カプセル化 + データカプセル化)という。ECIESの土台でもある(Wong §6.4)。

TLS、Signal、そしてほぼすべての現代的なメッセージアプリはこの形で動いている。公開鍵暗号で鍵の合意と身元の証明を行い、実際の通信は共通鍵AEADで守る。

## 8. 量子コンピュータと耐量子暗号

十分に大きな量子コンピュータで**ショアのアルゴリズム**を動かせば、大きな数の素因数分解や離散対数がすぐに解けてしまう。そうなればRSA、DH、ECCは破られる。そのような機械はまだ存在しないが、今日記録されたデータが将来復号されるおそれがある(「今収集して、後で復号する」)。

業界の答えは、NISTが標準化した**耐量子暗号(PQC)**だ。
- **ML-KEM**(Kyber): 鍵の合意用。
- **ML-DSA**(Dilithium)と**SLH-DSA**: 署名用。

多くのTLSの導入例では、すでに古典的な方式(X25519)とML-KEMを組み合わせた**ハイブリッド**鍵交換が使われている。片方が破られても接続は安全なままだ。

共通鍵暗号はずっと安心できる状況にある。**グローバーのアルゴリズム**は実効的な鍵長をおよそ半分にするだけなので、AES-256には十分な余裕が残り、SHA-256も問題ない。

## 9. OpenSSLチートシート

```bash
# ── RSA 4096の鍵ペア ─────────────────────────────────────────
openssl genrsa -out private_rsa.pem 4096
openssl rsa -in private_rsa.pem -pubout -out public_rsa.pem

# ── 小さなファイルをOAEPで暗号化/復号(素のRSAは使わない) ─────
openssl pkeyutl -encrypt -pubin -inkey public_rsa.pem \
  -pkeyopt rsa_padding_mode:oaep -in key.bin -out key.enc
openssl pkeyutl -decrypt -inkey private_rsa.pem \
  -pkeyopt rsa_padding_mode:oaep -in key.enc -out key.bin

# ── ECC P-256 / Ed25519の鍵 ──────────────────────────────────
openssl ecparam -name prime256v1 -genkey -noout -out private_ec.pem
openssl genpkey -algorithm ED25519 -out private_ed25519.pem
openssl pkey -in private_ed25519.pem -pubout -out public_ed25519.pem

# ── ファイルへの署名と検証(RSA + SHA-256) ───────────────────
openssl dgst -sha256 -sign private_rsa.pem -out doc.sig document.pdf
openssl dgst -sha256 -verify public_rsa.pem -signature doc.sig document.pdf
```

RSAで暗号化できるのは鍵長より小さいデータだけなので、`pkeyutl -encrypt` はファイル全体ではなく、セッション鍵のような小さなものに使う。これが第7節のハイブリッド暗号である。

## セキュリティノート

| リスク | 原因 | 防御 |
|:---|:---|:---|
| 教科書的RSA | パディングなし | 必ずOAEP(暗号化)かPSS(署名)を使う |
| ECDSAのノンス再利用 | 弱い、または壊れた乱数生成器 | Ed25519、または決定的ECDSA(RFC 6979) |
| 不正な公開値 | 受け取った点やグループの要素を確認しない | 標準の曲線 + ライブラリの検証機能 |
| 前方秘匿性がない | 静的なRSA鍵交換 | 一時的なECDHEだけを使う(TLS 1.3と同じ) |
| 秘密鍵の盗難 | ディスク、バックアップ、gitに鍵がある | HSM、パスフレーズによる保護、短命な鍵 |
| 将来の量子攻撃 | 長期間守る秘密をRSA/ECCだけで保護している | ハイブリッド / 耐量子アルゴリズムへの移行を計画する |
