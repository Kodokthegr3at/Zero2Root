## 1. Mengapa PKI Ada

Kriptografi kunci publik menyelesaikan masalah distribusi kunci hanya jika kita yakin bahwa $pk$ benar-benar milik `example.com`. Tanpa pengikatan identitas, seorang penyerang bisa melakukan man-in-the-middle:

$$
\text{MITM: } pk_{\text{attacker}} \text{ disubstitusi ke korban}
$$

PKI adalah seperangkat peran, kebijakan, dan format (X.509) yang membuat Certificate Authority (CA) menandatangani pernyataan berikut:

$$
\mathsf{Cert} = \mathsf{Sign}_{sk_{\mathsf{CA}}}\big(\mathsf{Subject},\; pk_{\mathsf{Subject}},\; \mathsf{validity},\; \mathsf{ext}\big)
$$

Browser dan sistem operasi menyimpan trust anchor (root CA) yang menjadi dasar semua verifikasi ini.

PKI tidak menciptakan primitif matematika baru. PKI mengoperasionalkan tanda tangan digital ditambah kebijakan, sehingga klien bisa mengautentikasi server (dan kadang klien) dalam skala Internet (Wong, Ch.7/9).

## 2. Rantai Kepercayaan

```
[ Root CA ]  self-signed, often offline HSM
      │  signs
      ▼
[ Intermediate CA ]  day-to-day issuance
      │  signs
      ▼
[ End-entity / leaf ]  CN/SAN = example.com
```

### Validasi rantai (ide dasar)

Klien menerima sertifikat leaf beserta intermediate-nya, lalu memverifikasi:

$$
\begin{aligned}
&\mathsf{Verify}(pk_{\text{root}},\; \mathsf{Cert}_{\text{inter}}) \\
&\mathsf{Verify}(pk_{\text{inter}},\; \mathsf{Cert}_{\text{leaf}}) \\
&\mathsf{nameMatch}(\mathsf{Cert}_{\text{leaf}},\; \texttt{example.com}) \\
&\mathsf{timeValid}(\mathsf{now}) \land \neg\mathsf{revoked}
\end{aligned}
$$

Path building juga memeriksa Basic Constraints (CA:TRUE), Key Usage, dan kebijakan Extended Key Usage seperti `serverAuth`.

## 3. Anatomi Sertifikat X.509 (v3)

| Field | Makna |
|:---|:---|
| `Subject` | Identitas pemilik (historis); praktik modern mengandalkan SAN |
| `Subject Public Key Info` | Algoritma kunci beserta $pk$ |
| `Issuer` | CA yang menandatangani |
| `Serial Number` | Unik per CA, penting untuk revocation |
| `Validity` | `notBefore` / `notAfter` |
| `Signature` | Tanda tangan CA atas TBSCertificate |
| Extensions | SAN, EKU, SKI/AKI, CRL DP, OCSP AIA, CT SCTs |

SAN (Subject Alternative Name) adalah sumber kebenaran nama yang dipakai secara modern, misalnya `DNS:example.com` atau `DNS:*.example.com`.

## 4. Siklus Hidup Sertifikat

### 4.1 CSR (Certificate Signing Request)

Pemohon menghasilkan pasangan kunci $(pk,sk)$, lalu membuat permintaan:

$$
\mathsf{CSR} = \mathsf{Sign}_{sk}(\mathsf{Subject},\; pk,\; \mathsf{attrs})
$$

CA memverifikasi kontrol domain (misalnya HTTP-01 atau DNS-01 pada protokol ACME) sebelum menerbitkan sertifikat.

### 4.2 Revocation (pencabutan)

- CRL: daftar nomor seri yang dicabut, ditandatangani CA. Bisa berukuran besar dan lambat diperbarui.
- OCSP: query status sebuah nomor seri secara online.
- OCSP stapling: server menyertakan respons OCSP yang masih segar, memberi privasi dan latensi yang lebih baik.
- Sertifikat berumur pendek (dalam hitungan jam atau hari): mengurangi ketergantungan pada mekanisme revocation.

### 4.3 Certificate Transparency (CT)

Log publik yang bersifat append-only. Browser mensyaratkan SCT (Signed Certificate Timestamp). Mekanisme ini memudahkan deteksi penerbitan sertifikat yang salah atau tidak sah.

## 5. Handshake TLS 1.3: Mekanisme dan Key Schedule

TLS 1.3 (RFC 8446) menghapus RSA key transport, mode CBC, RC4, dan cipher suite berbasis SHA-1 yang sudah usang, sekaligus memangkas handshake penuh menjadi 1-RTT (Wong, Ch.9).

### 5.1 Sketsa handshake penuh

```
Client                                                 Server
  │ ClientHello                                      │
  │  + supported_versions=1.3                        │
  │  + cipher_suites (AEAD+hash)                     │
  │  + supported_groups (e.g. x25519)                │
  │  + key_share (client ephemeral pk)               │
  │─────────────────────────────────────────────────>│
  │                                                 │
  │              ServerHello + key_share            │
  │              {EncryptedExtensions}              │
  │              {Certificate}                      │
  │              {CertificateVerify}                │
  │              {Finished}                         │
  │<─────────────────────────────────────────────────│
  │ {Finished}                                      │
  │─────────────────────────────────────────────────>│
  │══════════ Application Data (AEAD) ══════════════│
```

Tanda `{...}` menunjukkan pesan yang dienkripsi dengan handshake traffic key.

### 5.2 Shared secret ECDHE

$$
\mathsf{SharedSecret} = \mathsf{ECDH}(sk_C^{\text{eph}},\, pk_S^{\text{eph}})
$$

### 5.3 Key schedule HKDF (intuisi formal)

TLS 1.3 menurunkan banyak kunci dari secret bertingkat. Pola intinya:

$$
\begin{aligned}
\mathsf{EarlySecret} &\leftarrow \mathsf{HKDF\text{-}Extract}(0,\, \mathsf{PSK}\ \text{atau}\ 0) \\
\mathsf{HandshakeSecret} &\leftarrow \mathsf{HKDF\text{-}Extract}(\mathsf{Derive}(\ldots),\, \mathsf{SharedSecret}) \\
\mathsf{MasterSecret} &\leftarrow \mathsf{HKDF\text{-}Extract}(\mathsf{Derive}(\ldots),\, 0) \\
\mathsf{TrafficKeys} &\leftarrow \mathsf{HKDF\text{-}Expand\text{-}Label}(\mathsf{Secret},\, \mathsf{label},\, \mathsf{TranscriptHash},\, L)
\end{aligned}
$$

Transcript hash mengikat seluruh pesan handshake:

$$
\mathsf{TranscriptHash} = H(\mathsf{ClientHello}\,\|\,\ldots\,\|\,\mathsf{Finished})
$$

`CertificateVerify` adalah tanda tangan digital server atas transcript. Ini membuktikan kepemilikan private key sertifikat sekaligus mengikatnya ke ECDHE yang segar (authenticated key exchange).

### 5.4 Finished

$$
\mathsf{Finished} = \mathsf{HMAC}(\mathsf{FinishedKey},\, \mathsf{TranscriptHash})
$$

Memastikan kedua pihak melihat transcript yang identik, sebagai pertahanan terhadap downgrade dan tampering.

## 6. Record Layer: Mengenkripsi Data Aplikasi

Setelah traffic key siap, setiap record diproses sebagai berikut:

$$
\mathsf{ciphertext} \leftarrow \mathsf{AEAD}_{key}^{nonce}(\mathsf{plaintext}\,\|\,\mathsf{content\_type})
$$

Contoh cipher suite modern:
- `TLS_AES_128_GCM_SHA256`
- `TLS_AES_256_GCM_SHA384`
- `TLS_CHACHA20_POLY1305_SHA256`

Nonce TLS 1.3 dibentuk dari sequence number yang di-XOR dengan IV statis. Jangan pernah memakai ulang kunci koneksi di luar state machine TLS.

---

## 7. Perfect Forward Secrecy (PFS) dan 0-RTT

### PFS

Jika private key jangka panjang server bocor di masa depan, sesi lampau tetap aman karena traffic key bergantung pada ECDHE yang bersifat ephemeral:

$$
\text{leak } sk_{\text{long-term}} \not\Rightarrow \text{decrypt old } \mathsf{AEAD}\text{ records}
$$

TLS 1.3 mewajibkan (EC)DHE, kecuali pada mode PSK-only yang memang dirancang dengan risiko yang disadari.

### 0-RTT (early data)

Dengan PSK yang di-resume, klien bisa mengirim data pada flight pertama. Trade-off-nya adalah risiko replay. Aplikasi harus idempotent, atau menolak 0-RTT untuk operasi yang sensitif.

## 8. Ancaman dan Pertahanan (Konseptual)

| Ancaman | Ide serangan | Pertahanan |
|:---|:---|:---|
| CA nakal atau diretas | Sertifikat palsu untuk domain Anda | Monitoring CT, CAA DNS, pinning terbatas |
| MITM dengan private key leaf yang dicuri | Impersonation | Sertifikat berumur pendek, HSM, revocation cepat |
| SSL stripping | Downgrade ke HTTP | HSTS, HTTPS-only |
| Verifikasi lemah | Melewati pengecekan hostname atau trust-all | Verifier default OS/browser, jangan pakai `InsecureSkipVerify` di produksi |
| DNS hijack menuju sertifikat penyerang | Jika CA salah menerbitkan | CAA, CT, dan DNSSEC sebagai lapisan tambahan |

Certificate pinning mengikat aplikasi ke SPKI tertentu. Ini efektif untuk aplikasi mobile yang dikendalikan penuh oleh pemiliknya, tetapi secara operasional rapuh karena rotasi kunci. Untuk web publik, lebih baik mengandalkan CT dan kebersihan PKI modern.

## 9. Cheatsheet OpenSSL

```bash
# ── CSR (RSA) ────────────────────────────────────────────────
openssl req -new -newkey rsa:4096 -nodes \
  -keyout example.com.key -out example.com.csr \
  -subj "/C=ID/O=LearnCyber/CN=example.com"

# ── Self-signed lab cert (ECDSA P-256) ───────────────────────
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -days 365 -nodes -keyout server.key -out server.crt \
  -subj "/CN=localhost"

# ── Inspect remote chain ─────────────────────────────────────
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# ── Verify chain ─────────────────────────────────────────────
openssl verify -CAfile ca_chain.pem example.com.crt

# ── Show cert fields ─────────────────────────────────────────
openssl x509 -in server.crt -noout -text -fingerprint -sha256

# ── Test TLS 1.3 only ────────────────────────────────────────
openssl s_client -connect example.com:443 -tls1_3 -servername example.com </dev/null
```

## Catatan Keamanan: Checklist Operator

1. Nonaktifkan TLS di bawah versi 1.2 pada server produksi; utamakan TLS 1.3.
2. Gunakan cipher AEAD saja; aktifkan OCSP stapling.
3. Terapkan HSTS dan redirect ke HTTPS; pertimbangkan CAA record.
4. Private key harus berizin `0600`, idealnya disimpan di HSM/KMS, dan jangan pernah dikomit ke git.
5. Pantau log Certificate Transparency untuk domain Anda.
