## Istilah penting

Istilah-istilah ini akan sering muncul di materi.

| Istilah | Artinya |
|:---|:---|
| PKI | Public Key Infrastructure: seluruh sistem otoritas, sertifikat, dan aturan yang memberi tahu public key mana milik siapa |
| Sertifikat | KTP digital: "public key ini milik example.com", ditandatangani otoritas yang dipercaya |
| CA | Certificate Authority: organisasi yang dipercaya untuk memeriksa identitas dan menandatangani sertifikat |
| Root CA | CA tingkat paling atas. Sertifikatnya sudah terpasang di browser atau OS-mu |
| Intermediate CA | CA yang diberi wewenang oleh root untuk menandatangani sertifikat atas namanya |
| Sertifikat leaf | Sertifikat milik website atau server yang sebenarnya |
| CSR | Certificate Signing Request: "formulir pengajuan" yang kamu kirim ke CA |
| Revocation (pencabutan) | Membatalkan sertifikat sebelum masa berlakunya habis, misalnya setelah kuncinya bocor |
| TLS | Protokol yang menjadi huruf "S" di HTTPS: mengenkripsi dan mengautentikasi koneksi jaringan |
| Handshake | Beberapa pesan pertama di koneksi TLS, tempat kedua pihak menyepakati kunci dan mengecek identitas |
| Forward secrecy (PFS) | Kalau kunci server bocor di kemudian hari, koneksi lama yang sudah direkam tetap tidak terbuka |

## 1. Kenapa PKI Dibutuhkan

Kripto public key (LC-055) memungkinkan siapa pun mengenkripsi pesan untukmu dengan public key-mu. Tapi ada masalahnya: **bagaimana kamu tahu sebuah public key benar-benar milik `example.com`?**

Tanpa jawaban itu, penyerang yang berada di antara kamu dan server bisa saja memberikan public key **miliknya sendiri** dan berpura-pura menjadi server. Kamu akan mengenkripsi semuanya untuk penyerang, yang lalu membacanya dan meneruskannya. Inilah serangan **man-in-the-middle (MITM)**, dan kamu tidak punya cara untuk menyadarinya.

PKI menyelesaikan masalah ini seperti cara kerja paspor. Otoritas yang dipercaya (**CA**) memeriksa siapa kamu, lalu menandatangani pernyataan:

```text
Sertifikat = tanda tangan CA atas {
    nama:          example.com
    public key:    <public key milik server>
    berlaku mulai: 2026-01-01   sampai: 2026-04-01
    ekstensi:      penggunaan yang diizinkan, tempat mengecek pencabutan, ...
}
```

Browser dan sistem operasimu sudah membawa daftar CA yang mereka percaya (**trust anchor**, atau root CA). Kalau sebuah sertifikat ditandatangani salah satu CA itu, browser menerima bahwa kunci tersebut memang milik nama itu.

PKI tidak memakai matematika baru. PKI adalah tanda tangan digital (LC-055) ditambah seperangkat aturan, yang dijalankan dalam skala Internet (Wong, Ch.7/9).

## 2. Rantai Kepercayaan

Root CA terlalu penting untuk dipakai sehari-hari, jadi biasanya disimpan offline di hardware security module (HSM). Sebagai gantinya, root CA memberi wewenang ke **intermediate CA** untuk melakukan penandatanganan harian:

```
[ Root CA ]  self-signed, often offline HSM
      │  signs
      ▼
[ Intermediate CA ]  day-to-day issuance
      │  signs
      ▼
[ End-entity / leaf ]  CN/SAN = example.com
```

### Cara browser mengecek sertifikat

Server mengirim sertifikat leaf beserta intermediate-nya. Browser lalu mengecek:

```text
1. public key root memverifikasi tanda tangan di sertifikat intermediate
2. public key intermediate memverifikasi tanda tangan di sertifikat leaf
3. nama di sertifikat leaf cocok dengan situs yang kamu ketik (example.com)
4. tanggal hari ini masih dalam masa berlaku, dan sertifikatnya tidak dicabut
```

Browser juga mengecek beberapa aturan yang tertulis di dalam sertifikat: intermediate harus ditandai boleh bertindak sebagai CA (`CA:TRUE`), dan leaf harus diizinkan dipakai untuk website (`serverAuth`).

Kalau ada satu langkah yang gagal, muncullah peringatan yang sudah sering kamu lihat: "Your connection is not private".

## 3. Isi Sebuah Sertifikat (X.509 v3)

| Field | Artinya |
|:---|:---|
| `Subject` | Untuk siapa sertifikat ini (field lama; sekarang yang penting adalah SAN) |
| `Subject Public Key Info` | Public key-nya sendiri, dan algoritma yang dipakai |
| `Issuer` | CA mana yang menandatanganinya |
| `Serial Number` | Nomor unik per CA, dipakai saat pencabutan |
| `Validity` | `notBefore` / `notAfter`: tanggal mulai dan berakhir |
| `Signature` | Tanda tangan CA atas semua field di atas |
| Ekstensi | SAN, penggunaan yang diizinkan (EKU), ID kunci, tempat mengecek pencabutan (CRL/OCSP), bukti CT |

**SAN** (Subject Alternative Name) adalah tempat daftar nama yang sebenarnya, misalnya `DNS:example.com` dan `DNS:*.example.com`. Browser mengecek SAN, bukan field `Subject` yang lama.

## 4. Siklus Hidup Sertifikat

### 4.1 Mengajukan sertifikat (CSR)

1. Kamu membuat pasangan kunci sendiri. Private key tidak pernah keluar dari servermu.
2. Kamu membuat **CSR** yang berisi namamu dan public key-mu, lalu menandatanganinya dengan private key. Ini membuktikan kamu benar-benar memegang private key pasangannya.
3. CA mengecek bahwa kamu menguasai domain tersebut. Dengan protokol ACME (dipakai Let's Encrypt), caranya dengan menaruh file di website-mu (HTTP-01) atau menambahkan record DNS (DNS-01).
4. CA menandatangani dan mengirimkan sertifikatmu.

### 4.2 Pencabutan: membatalkan sertifikat lebih awal

Kalau private key bocor, sertifikatnya harus dibatalkan sebelum masa berlakunya habis. Pilihannya:

| Metode | Cara kerja | Kekurangan |
|:---|:---|:---|
| CRL | CA memublikasikan daftar nomor seri yang dibatalkan, dan daftar itu ditandatangani | Daftarnya membesar dan lambat diperbarui |
| OCSP | Browser bertanya ke CA "apakah nomor seri ini masih valid?" | Lebih lambat, dan CA jadi tahu situs mana yang kamu kunjungi |
| OCSP stapling | Server sendiri yang mengambil jawaban OCSP terbaru lalu melampirkannya | Lebih cepat dan lebih privat |
| Sertifikat berumur pendek | Sertifikat hanya berlaku beberapa hari | Pencabutan jadi jauh kurang penting |

Dalam praktik, pencabutan tidak bisa diandalkan, karena itu industri bergerak ke sertifikat berumur pendek.

### 4.3 Certificate Transparency (CT)

Setiap sertifikat yang dipercaya publik wajib dicatat di **log CT** yang publik dan hanya bisa ditambah (append-only), dan browser meminta bukti pencatatannya (SCT). Artinya, CA tidak bisa diam-diam menerbitkan sertifikat palsu untuk domainmu: kamu bisa memantau log-nya dan menemukannya.

## 5. Handshake TLS 1.3 Langkah demi Langkah

TLS 1.3 (RFC 8446) adalah pembersihan besar dari TLS versi lama. Opsi-opsi lemah dihapus (RSA key transport, mode CBC, RC4, cipher suite berbasis SHA-1), dan handshake penuh sekarang hanya butuh **satu kali bolak-balik (round trip)** (Wong, Ch.9).

```
Client                                                 Server
  │ ClientHello                                      │
  │  + supported_versions=1.3                        │
  │  + cipher_suites (AEAD+hash)                     │
  │  + supported_groups (e.g. x25519)                │
  │  + key_share (client ephemeral pk)               │
  │─────────────────────────────────────────────────>│
  │                                                 │
  │              ServerHello + key_share            │
  │              {EncryptedExtensions}              │
  │              {Certificate}                      │
  │              {CertificateVerify}                │
  │              {Finished}                         │
  │<─────────────────────────────────────────────────│
  │ {Finished}                                      │
  │─────────────────────────────────────────────────>│
  │══════════ Application Data (AEAD) ══════════════│
```

`{...}` artinya pesan itu sudah terenkripsi.

Yang terjadi, dalam bahasa sederhana:

1. **ClientHello:** klien menyebutkan versi TLS dan cipher yang didukungnya, dan langsung mengirim bagiannya dari pertukaran kunci sementara (`key_share` ECDHE, misalnya X25519).
2. **ServerHello:** server memilih cipher dan mengirim bagiannya dari pertukaran kunci. Sekarang kedua pihak bisa menghitung rahasia bersama yang sama (ide ECDH dari LC-055). **Semua pesan setelah titik ini terenkripsi.**
3. **Certificate:** server mengirim rantai sertifikatnya (Bagian 2).
4. **CertificateVerify:** server menandatangani hash dari seluruh percakapan sejauh ini dengan private key sertifikatnya. Ini membuktikan server benar-benar pemilik sertifikat itu, *dan* sedang ikut dalam handshake yang ini, saat ini.
5. **Finished (kedua pihak):** masing-masing mengirim HMAC atas seluruh percakapan. Kalau penyerang mengubah atau menghapus pesan sebelumnya (misalnya untuk memaksa pengaturan yang lebih lemah), nilainya tidak akan cocok dan koneksi diputus.

### Dari mana kuncinya berasal

Rahasia bersama ECDHE tidak dipakai langsung. TLS 1.3 memasukkannya ke HKDF (LC-056) secara bertahap, dan menghasilkan kunci terpisah untuk setiap keperluan:

```text
(PSK opsional)      → early secret
+ secret ECDHE      → handshake secret  → kunci untuk melindungi sisa handshake
                    → master secret     → kunci untuk melindungi data aplikasi
```

Hash dari setiap pesan handshake (**transcript hash**) ikut dicampurkan di sepanjang proses. Jadi kunci akhirnya hanya berlaku untuk percakapan yang satu ini, bukan yang lain.

## 6. Mengenkripsi Data Sebenarnya

Setelah handshake selesai, setiap potong data (setiap **record**) dilindungi dengan AEAD (LC-054), yang memberi kerahasiaan sekaligus deteksi perubahan:

```text
record terenkripsi = AEAD(traffic key, nonce, data + tipe konten)
```

TLS 1.3 hanya mengizinkan beberapa cipher suite, dan semuanya AEAD:
- `TLS_AES_128_GCM_SHA256`
- `TLS_AES_256_GCM_SHA384`
- `TLS_CHACHA20_POLY1305_SHA256`

Nonce untuk setiap record dibangun dari counter record, jadi tidak pernah berulang. Karena itu kunci TLS tidak boleh diambil lalu dipakai ulang di luar TLS.

## 7. Forward Secrecy dan 0-RTT

### Forward secrecy (PFS)

Bayangkan seseorang merekam semua traffic terenkripsimu hari ini, lalu bertahun-tahun kemudian mencuri private key server. Bisakah dia mendekripsi rekaman lama?

Dengan TLS 1.3: **tidak bisa.** Traffic key berasal dari pasangan kunci ECDHE sementara (ephemeral) yang sudah dibuang setelah koneksi selesai. Kunci jangka panjang server hanya *menandatangani* handshake; kunci itu tidak pernah melindungi traffic key.

Karena alasan ini TLS 1.3 mewajibkan (EC)DHE. Satu-satunya pengecualian adalah mode "PSK-only", yang memang sengaja melepas forward secrecy untuk kasus penggunaan tertentu.

### 0-RTT (early data)

Saat klien tersambung lagi ke server yang baru saja dikunjunginya, klien bisa langsung mengirim data di pesan pertamanya, sehingga menghemat satu round trip. Konsekuensinya: penyerang bisa merekam pesan pertama itu lalu **mengirim ulang (replay)**.

Jadi 0-RTT hanya aman untuk request yang tidak berbahaya kalau diulang, seperti memuat halaman (GET). Jangan pernah mengizinkan 0-RTT untuk aksi seperti pembayaran atau ganti password.

## 8. Ancaman dan Pertahanan

| Ancaman | Apa yang terjadi | Pertahanan |
|:---|:---|:---|
| CA nakal atau diretas | Seseorang mendapat sertifikat palsu yang valid untuk domainmu | Pantau log CT, pasang record DNS CAA |
| Private key server dicuri | Penyerang bisa menyamar sebagai server | Sertifikat berumur pendek, kunci di HSM, pencabutan cepat |
| SSL stripping | Penyerang menurunkan koneksi pengunjung ke HTTP biasa | HSTS, HTTPS-only |
| Pengecekan sertifikat rusak | Aplikasi melewati cek hostname atau mempercayai semuanya | Pakai verifier bawaan OS/browser; jangan pernah merilis `InsecureSkipVerify` |
| DNS dibajak sehingga sertifikat salah terbit | Penyerang menguasai DNS lalu mendapat sertifikat | CAA, pemantauan CT, DNSSEC |

**Certificate pinning** artinya aplikasi hanya menerima satu kunci atau sertifikat tertentu. Cara ini bagus untuk aplikasi mobile yang sepenuhnya kamu kendalikan, tapi mudah rusak saat kunci dirotasi. Untuk website publik, pemantauan CT plus kebersihan sertifikat yang baik adalah pilihan yang lebih tepat.

## 9. Cheatsheet OpenSSL

```bash
# ── Buat private key + CSR (RSA) ─────────────────────────────
openssl req -new -newkey rsa:4096 -nodes \
  -keyout example.com.key -out example.com.csr \
  -subj "/C=ID/O=LearnCyber/CN=example.com"

# ── Sertifikat self-signed untuk lab (ECDSA P-256) ───────────
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -days 365 -nodes -keyout server.key -out server.crt \
  -subj "/CN=localhost"

# ── Lihat rantai sertifikat yang dikirim server ──────────────
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# ── Verifikasi sertifikat terhadap bundle CA ─────────────────
openssl verify -CAfile ca_chain.pem example.com.crt

# ── Baca isi field sertifikat ────────────────────────────────
openssl x509 -in server.crt -noout -text -fingerprint -sha256

# ── Tes apakah server mendukung TLS 1.3 ──────────────────────
openssl s_client -connect example.com:443 -tls1_3 -servername example.com </dev/null
```

## Catatan Keamanan: Checklist Operator

1. Matikan semua versi di bawah TLS 1.2 di server produksi, dan utamakan TLS 1.3.
2. Izinkan hanya cipher suite AEAD, dan aktifkan OCSP stapling.
3. Aktifkan HSTS dan redirect HTTP ke HTTPS. Pertimbangkan record CAA.
4. Lindungi private key: permission `0600`, idealnya di HSM/KMS, dan **jangan pernah** di-commit ke git.
5. Pantau log Certificate Transparency untuk sertifikat yang terbit atas nama domainmu.
