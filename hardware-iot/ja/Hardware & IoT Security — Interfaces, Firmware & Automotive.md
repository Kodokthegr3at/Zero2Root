## 1. 組み込み / IoT脅威モデル

IoTデバイスは、シリコン、ファームウェア、無線/ネットワーク、クラウドが組み合わさったものです。脅威は物理的な経路(デバッグポート)、ローカルな経路(Wi-Fi/BLE)、リモートな経路(クラウドAPI)から来ます。

価値の高い資産に簡単に手が届き、しかも守りが弱いとき、リスクは最大になります。この3つのどれか1つを下げれば、リスクも下がります。

守るべき典型的な資産には、デバイス鍵、クラウドの認証情報、センサーデータ、そして(自動車、医療、産業分野における)安全機能が含まれます。

高い保証レベルが求められる設計(セットトップボックス、車両のECU、産業用コントローラーなど)では、攻撃者がデバイスを物理的に所有している前提で考えるべきです。デバッグインタフェースや未署名のファームウェア更新経路が残っていれば、ネットワーク側の対策だけでは不十分になります。

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  Sensors /  │──▶│  MCU / SoC  │──▶│  Radio/NIC  │──▶ Cloud / Mobile
│  Actuators  │◀──│  + firmware │◀──│  BLE/Wi-Fi  │◀──
└─────────────┘   └──────┬──────┘   └─────────────┘
                         │
                  Debug / flash pads
```

## 2. デバッグインタフェース、所有者による識別

デバイスの所有者やベンダー側のセキュリティエンジニアは、他人のデバイスを攻撃するためではなく、自分たちのデバイスを守るために(無効化、ヒューズの切断、認証の追加など)デバッグポートを特定する必要がよくあります。

### 2.1 UART(Universal Asynchronous Receiver/Transmitter)
| 信号 | 機能 |
|:---|:---|
| TX | データ送信 |
| RX | データ受信 |
| GND | 共通グラウンド |
| Vcc | いきなり接続しない。先に電圧を確認する |

物理的な特徴: 隣接した2〜4個のテストパッド、`TX/RX` というシルク印刷のヘッダーが付いていることもあります。よく使われるボーレート(概念として): 115200、57600、9600。

防御策: 本番環境ではコンソールを無効化し、ログインに認証を要求するか、シェル自体を取り除きます。ログに残す情報も機微なものは制限します。

### 2.2 JTAG / SWD

JTAG(IEEE 1149.1)は境界スキャンとデバッグに使われます。典型的なピンは `TCK`、`TMS`、`TDI`、`TDO`、`TRST`(オプション)です。
SWD(ARM)は2本の線、`SWDIO` と `SWCLK` を使います。

デバッグポートが本当に危険になるのは、パッドに手が届き、認証がなく、デバッグ用ヒューズがまだ開いている、という3つがそろったときです。

防御策(ベンダー側):
- 本番環境ではヒューズやライフサイクルステートを使ってデバッグを無効化する。
- RMA対応のためにデバッグアクセスを残す必要がある場合は、パスワードやセキュアなデバッグ認証を使う。
- エポキシ樹脂やアンダーフィルは主たる対策にはならず、攻撃を遅らせる効果しかない。

```
PCB edge                 SoC
  ○ TCK  ──────────────▶|
  ○ TMS  ──────────────▶|  Debug TAP
  ○ TDI  ──────────────▶|
  ○ TDO  ◀──────────────|
  ○ GND  ───────────────┘
```

注記: サードパーティ製品の保護を回避するためのデバッグ悪用手順は、ここには含めません。目的はあくまで、この攻撃対象領域を特定し、塞ぐことです。

## 3. 基板バス、SPI、I2C、外部フラッシュ

| バス | 典型的な配線 | 用途 | 概念上のリスク |
|:---|:---|:---|:---|
| SPI | SCLK、MOSI、MISO、CS | NORフラッシュのファームウェア | CSやフラッシュが露出しているとダンプされうる |
| I2C | SDA、SCL | EEPROM、センサー | 設定データや弱い鍵 |
| eMMC / SD | パラレル / SD | OSのストレージ | ファイルシステムの抽出 |

### ファームウェアの格納レイアウト(概念図)
```
┌──────────────┬──────────────┬──────────────┬────────────┐
│ Bootloader   │ Kernel / RTOS│ Rootfs / app │ Config/NV  │
│ (+sig?)      │              │              │            │
└──────────────┴──────────────┴──────────────┴────────────┘
```

防御策: 機微な不揮発性領域は暗号化し、シークレットはハードウェアのroot of trustに紐付け、平文の認証情報をフラッシュに置かないようにします。

## 4. ファームウェア、抽出と解析の概念

*Practical IoT Hacking* と *Hardware Hacking Handbook* は、セキュリティ解析のためにファームウェアをどう取得するかを扱っています。この教材ではその中でも概念と防御目的の部分に絞ります。

### 正当なファームウェアの入手元
| 入手元 | 有効な場面 |
|:---|:---|
| ベンダーの更新パッケージ | サプライチェーンや更新の整合性の解析 |
| 社内のビルド成果物 | ベンダーのSDL |
| 自分が所有するデバイス + 認可されたラボ | 購入した機器での研究 |
| オープンソースのリリース | コミュニティによる監査 |

### 解析の目的(防御)
1. ハードコードされた認証情報やバックドアサービスを見つける。
2. 更新が署名されているかどうかを確認する。
3. リッスンしているネットワークサービスを洗い出す。
4. TLSの設定と証明書ストアを確認する。
5. コンポーネントのバージョンを特定し、既知のCVEと照合する。

ファームウェア更新が安全といえるのは、署名されていて、署名の連鎖が検証され、脆弱な古いバージョンに戻せない(アンチロールバック)場合だけです。

静的解析の概念: イメージの展開(ラボ環境でbinwalk系のツールを使う)、ファイルシステムの抽出、文字列のトリアージ、設定のレビュー。
動的解析: 自分が所有するイメージに対してエミュレータやテストハーネスを使う。他人が運用しているフリート全体を狙うものではありません。

## 5. セキュアブート、メジャードブート、ファームウェア署名

### セキュアブートのチェーン
```
ROM root key
    │ verify
    ▼
Bootloader
    │ verify
    ▼
Kernel / OS image
    │ verify
    ▼
dm-verity / app containers (optional)
```

| 仕組み | 機能 |
|:---|:---|
| セキュアブート | 有効な署名のないイメージを拒否する |
| メジャードブート | 証明のためにハッシュをPCR/TPMに記録する |
| アンチロールバック | 既知の脆弱性がある古いバージョンを拒否する |
| ハードウェアroot of trust | 鍵をヒューズ、OTP、SoC上のHSMに保存する |

### 署名モデル
```text
σ = Sign(ベンダーの秘密鍵, Hash(image))

次の両方を満たすときだけイメージを受け入れる:
  Verify(pk, image, σ) = OK   かつ   バージョン ≥ 許可された最小バージョン
```

典型的な失敗パターン: デバッグブートが有効なまま残されている、ベンダーの秘密鍵が流出する、あるいは検証処理がヒューズによる保護なしでパッチ可能なソフトウェアとして実装されている、などです。

## 6. IoTのネットワークとクラウドの面

| レイヤー | 例 | ハードニング |
|:---|:---|:---|
| ローカル無線 | BLE、Zigbee、Wi-Fi AP | 強固なペアリングPIN、WPS無効化、鍵のローテーション |
| LANサービス | 旧式のTelnet/HTTP | 撤去し、HTTPS/SSHのみを使い、定期的にパッチを当てる |
| クラウドAPI | デバイスとMQTT/HTTPブローカー間 | 相互TLS、最小権限のスコープ付きトークン |
| モバイル companion | 監視アプリ | 安全なストレージ、成熟した証明書ピンニング |
| 更新チャネル | OTA | 署名付きOTA + アンチロールバック |

最小権限のデバイスID: すべてのデバイスは固有のIDを持つべきで、フリート全体で共有する単一のグローバル鍵は使うべきではありません。

そうすれば、鍵が固有でローテーションされている限り、1台が破られてもフリート全体を明け渡すことにはなりません。

## 7. CANバスのアーキテクチャ(自動車)

*The Car Hacker's Handbook* が指摘しているように、現代の車両は実質的にECUのネットワークです。CAN(Controller Area Network)は最も広く使われている差動シリアルバスです。

### アーキテクチャ上の特性
| 特性 | 意味 |
|:---|:---|
| マルチマスター | 複数のECUが送信できる |
| IDによる優先度 | IDが小さいほど優先度が高い |
| ブロードキャスト | 同じバス上のすべてのノードにフレームが見える |
| 標準の認証機構がない(クラシックな仕様) | フレームは「ログイン」しない。信頼はバスへのアクセス自体になる |

```
ECU_A ----+------ ECU_B ------+------ ECU_C
          |                   |
         CAN_H / CAN_L differential pair
```

### フレーム(概念)
```text
CANフレーム = ID(何のメッセージか) | DLC(データ長) | データ(0〜8バイト) | CRC(エラーチェック)
```

ISO-TPやUDSは診断用のトランスポートとしてCANを使います。ここは厳しく管理すべき領域です。

### 車両内の典型的なドメイン
| ドメイン | 機能例 | 重要度 |
|:---|:---|:---|
| パワートレイン | エンジン / トランスミッション | セーフティクリティカル |
| シャシー | ABS / ステアリングアシスト | セーフティクリティカル |
| ボディ | 窓 / ドアロック | 利便性 + セキュリティ |
| インフォテインメント | メディア / アプリ | 攻撃の侵入口として重要度が高い |
| OBD-II | 診断ポート | 物理的な侵入口 |
| テレマティクス | セルラーモデム | リモートの侵入口 |

## 8. 自動車セキュリティの防御策

ここでのセキュリティエンジニア向けの焦点は、攻撃スクリプトではなくセグメンテーションと制御です。

| 防御策 | 説明 |
|:---|:---|
| ゲートウェイECU | CAN/Ethernetのドメイン間をフィルタリング/ポリシー制御する |
| バスのセグメンテーション | インフォテインメントをセーフティ系ドメインから隔離する |
| セキュアな診断 | 機微なUDSセッションの前に認証を行う |
| ECUごとの署名付きファームウェア | 各ECUにセキュアブートを適用する |
| 車両向けIDS/IPS | フレームのIDや頻度の異常を検出する(ベンダー提供) |
| OBDアクセスポリシー | アフターマーケットのドングルを制限し、利用者に周知する |
| テレマティクスのハードニング | モデムへのパッチ適用、クラウドへの相互認証 |
| サプライチェーン | サプライヤー製ECUのコードレビュー |

```
Infotainment ──X──▶ Safety CAN
       │              ▲
       ▼              │ policy
   Gateway ECU ───────┘
       │
       ▼
   Telematics (auth'd)
```

ゲートウェイのフィルタリングが強く、ドメインがしっかり分離されているほど、攻撃者が車のある部分(たとえばインフォテインメント)から別の部分(たとえばブレーキ)へ移るのは難しくなります。

厳格なルール: この教材はCANインジェクションのスクリプト、リプレイ攻撃のレシピ、イモビライザーの回避手順を提供しません。アーキテクチャを理解することは、防御的な設計と認可されたアセスメントのために役立ちます。

## 9. デバイス所有者/ベンダー向けラボ実践

自分が所有するデバイス、あるいは認可されたラボでの安全な実践手順です。

1. 基板を撮影し、シルク印刷とテストパッドを記録する。
2. アダプタを接続する前に電圧を測定する(3.3Vか5Vか)。
3. デバッグポートの一覧を作成し、量産前に塞ぐ計画を立てる。
4. 公式の更新チャネルからファームウェアを取得し、署名を検証する。
5. 隔離されたラボ用Wi-Fiでネットワークサービスをスキャンする。
6. 発見事項は、無調整で公開する攻撃チェーンとしてではなく、SAST/ハードニングのバックログとして記録する。

| やってはいけないこと | やるべきこと |
|:---|:---|
| 他人の車両のECUをプローブする | トレーニング用ECUや合法なラボで練習する |
| セーフティの回避手順を公開する | ベンダーと調整した上で開示する |
| ピンの電圧を無視する | まずマルチメーターで確認する |
| フリート全体で共有するクラウド鍵を使う | デバイスごとの認証情報を使う |

## 10. 識別と防御のチートシート

```text
HARDWARE SURFACE CHECK (owner/vendor)
[ ] UART pads present? → disable console / auth in prod
[ ] JTAG/SWD exposed? → fuse/disable/secure debug
[ ] External flash readable? → encrypt secrets; signed images
[ ] OTA signed + anti-rollback?
[ ] Unique device identity (no fleet-wide key)?
[ ] Cloud API: mTLS / scoped tokens?
[ ] Automotive: gateway between IVI and safety domains?
[ ] Diagnostics: authenticated UDS sessions?
```

| インタフェース | 識別のヒント | 主な防御策 |
|:---|:---|:---|
| UART | 3〜4個のパッド、TX/RXのラベル | シェルを無効化、ログに秘密情報を残さない |
| JTAG | 5個以上のパッド、または10/20ピンのフットプリント | ライフサイクルでの無効化 / 認証 |
| SWD | MCU近くの2本線 | JTAGと同様 |
| SPIフラッシュ | SoC近くの8ピンNOR | セキュアブート + NVの暗号化 |
| OBD-II | キャビン内のコネクタ | アクセスポリシー + 認証された診断 |
| CAN | ECUへのツイストペア | ゲートウェイとセグメンテーション |

## セキュリティノート、脅威と防御

| 脅威 | 仕組み | 防御策 |
|:---|:---|:---|
| デバッグの悪用 | 開いたUART/JTAG | デバッグの無効化/ヒューズ/認証 |
| ファームウェアのクローンやインプラント | 未署名の更新 | セキュアブート + アンチロールバック |
| フリート鍵の流出 | 共有された対称鍵 | デバイスごとの鍵 + ローテーション |
| クラウドアカウントの乗っ取り | 弱いペアリング | 強固なプロビジョニング、所有者アカウントのMFA |
| インフォテインメントからセーフティ系への越境 | フラットなネットワーク | ゲートウェイでのフィルタリング / ドメイン分離 |
| 悪意あるOBDドングル | バスへのアクセス | 利用者教育、診断機能の制限 |
| サプライチェーンのバックドア | サードパーティ製ECUのコード | 監査、SBOM、署名 |

ここで扱わないもの: CAN攻撃スクリプト、イモビライザーの無効化、エアバッグ/安全機能の悪用、ECU向けのRCEプレイブック。
