## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| ARP | 1つのローカルネットワークの中で、あるIPに対応するMACアドレスを探すプロトコル |
| MACアドレス | ネットワークカードのハードウェアID。ローカルネットワーク内の配送に使う |
| ARPキャッシュ | 機器が保持する「このIP = このMAC」の短期的な表 |
| ブロードキャスト | ローカルセグメントの全員に送るメッセージ |
| ゲートウェイ | 機器がほかのネットワークへ届くために使うルーター |
| スプーフィング / ポイズニング | 機器に偽のIP-MAC対応を覚え込ませること |
| MITM | 中間者。2者の間に静かに割り込み、通信を中継する |
| DAI | Dynamic ARP Inspection。嘘のARPメッセージを捨てるスイッチの機能 |
| セグメンテーション | ネットワークを小さなゾーンに分け、攻撃者が届く範囲を狭めること |

## 1. ARPはなぜ存在するのか

1つのローカルネットワークの中では、機器はIPアドレスではなく**MACアドレス**(各ネットワークカードのハードウェアID)を使ってデータを届ける。しかしプログラムやルーティングは**IPアドレス**で動く。両者をつなぐ何かが必要だ。それが**ARP**(Address Resolution Protocol)である。

```text
ARPは1つの問いに答える:  「IP 10.0.0.9 はどのMACアドレスか?」
```

これは**ローカルセグメント**(同じブロードキャストドメイン)の中でしか働かない。遠くのサーバーをARPで探すことはない。その代わり、自分のマシンは**ゲートウェイ**をARPで探し、フレームをゲートウェイのMACに渡して、あとはルーターに任せる。

```
  Host A                    スイッチ                    Host B
  10.0.0.5                                              10.0.0.9
         ──── 「10.0.0.9 は誰? 10.0.0.5 に教えて」(ブロードキャスト) ────►
         ◄─── 「10.0.0.9 は bb:bb:bb:bb:bb:bb にある」(リプライ) ──────────
  以降は bb:bb:… 宛てにフレームを送る ───────────────────────────────────►
```

最大の弱点はARPの設計そのものに組み込まれている。**リプライが本当のことを言っているか確かめる方法がない。** 先に、いちばん説得力を持って答えた者が勝つ。このたった1つの事実が、この教材のすべての攻撃の根であり、第6節の防御が存在する理由だ。(IPv6はARPの代わりにNDPという似たプロトコルを使う。)

## 2. リクエストとリプライのしくみ

ARPの主なメッセージは2つだけだ。

| 操作 | 意味 |
|:---|:---|
| リクエスト | 「このIPは誰? 教えて。」(全員へのブロードキャストで送る) |
| リプライ | 「そのIPはこのMACにある。」(尋ねた相手に返す) |

```text
A → 全員:  「IP_B は誰? A に教えて」
B → A:     「IP_B は MAC_B にある」
```

このやりとりのあと、AはBへ直接フレームを送れる。多くのシステムは、耳にしたARPトラフィックからも対応を静かに学習する。便利だが、まさにそれが、**頼んでもいない**予期しないリプライが危険信号である理由だ。

## 3. ARPキャッシュ

毎回尋ねずに済むよう、各機器は短期的な表を保持する。

```text
IPアドレス  →  (MACアドレス, 状態, インターフェース, 期限)
```

```bash
ip neigh show      # LinuxでARP/NDPキャッシュを見る
```

エントリは期限が切れて更新される。理解すべき大事な点はこれだ。**キャッシュは、そのセグメントで発言を許された者と同じだけしか信頼できない。** 機器が追加の確認なしにリプライを受け入れるなら、偽のリプライが正しいエントリを静かに上書きしうる。

実践的なヒント: ネットワークカードを交換したり番号を振り直したりした後、古くなったキャッシュのエントリが、期限切れになるまで「幽霊」のような接続の問題を起こすことがある。キャッシュのフラッシュは自分が管理するマシンだけで行うこと。

## 4. 関連するしくみ

| しくみ | 何か | セキュリティ上の注意 |
|:---|:---|:---|
| Proxy ARP | ローカルにない機器の代わりにルーターがARPに答える | ローカルの信頼を広げる。意図しないなら監査する |
| Gratuitous ARP | 頼まれていない「ここにいます」という通知 | フェイルオーバーには正当だが、フィルタしなければスプーフの手段にもなる |
| ARP probe(RFC 5227) | IPを使う前にアドレスの衝突を確認する | アドレス重複の検出に役立つ |

```
  通常:        「B は誰?」          →  「B は MAC_B にある」
  Gratuitous:  「A は MAC_A にある」 →  (通知。全員のキャッシュを更新する)
```

## 5. ローカルでの中間者攻撃という問題

ARPのリプライは検証されないので、同じセグメントにいる悪意ある機器は、**ゲートウェイのIPが攻撃者のMACにある**と被害者に信じ込ませられる。被害者はその後、「インターネットへ」のトラフィックを本物のルーターではなく攻撃者へ送る。

攻撃者がそのトラフィックを静かに先へ転送すれば、被害者は何も気づかない。一方で攻撃者は真ん中に座り、暗号化されていないものは何でも読んだり書き換えたりできる。これが**ローカルネットワーク層での中間者攻撃**だ。

```
  前:   被害者 ───────────────► ゲートウェイ ──► インターネット

  後:   被害者 ──► 攻撃者 ──► ゲートウェイ ──► インターネット
                 (通りすがりにトラフィックを読む/書き換える)
```

> この教材は、攻撃が**なぜ**可能なのかと、その止め方を説明する。ポイズニングの手順やスプーフのツールは意図的に載せていない。

防御上の意味: 「ゲートウェイのMAC宛てのフレームが本当にゲートウェイに届く」と思い込まないこと。上位層を暗号化すること(TLSをどこでも)は攻撃者が読める範囲を狭めるが、ローカル層での信頼は取り戻さない。特に可用性や、エンドツーエンドで暗号化されていないものには効かない。下記の対策はやはり必要だ。

## 6. 防御

| 対策 | しくみ | どこに合うか |
|:---|:---|:---|
| DHCPスヌーピング | スイッチが本物のDHCPリースから正当な (MAC, IP, ポート) を記録する | DAIの土台 |
| Dynamic ARP Inspection(DAI) | スイッチが各ARPメッセージをその記録と照合し、嘘のものを捨てる | 企業のアクセスネットワーク |
| 静的ARPエントリ | 重要なホストやルーターに手動で設定する固定の対応 | ゲートウェイ、小さなサーバー |
| ポートセキュリティ | スイッチのポートが受け入れるMACアドレスの数を制限する | アクセスの端 |
| セグメンテーション / プライベートVLAN | 機器どうしがローカル層で自由に到達できないようにする | どこでも。最も強いアーキテクチャ上の対策 |

ここでいちばん強力な考え方は**セグメンテーション**だ。ローカルセグメントが小さいほど、そもそも攻撃者がARPの小細工で届ける機器が少なくなる。静的エントリは大きなネットワークには向かないので、実践的な組み合わせはアクセススイッチでのDHCPスヌーピング + DAIに、監視を重ねることだ。

```
  [ ユーザーVLAN ] ──DAI + DHCPスヌーピング──► [ ゲートウェイ ] ──フィルタ──► [ サーバーVLAN ]
```

## 7. 検出と監視

自分が運用するネットワークで調べる価値のあるシグナル:

| シグナル | 考えられる意味 |
|:---|:---|
| 多くのホストで一斉にゲートウェイのMACが突然変わる | スプーフの試み、または不安定な対応 |
| 2つの異なるMACが同じIPを主張する | アドレスの衝突、またはスプーフ |
| ARPリクエストの嵐 | ループ、設定ミス、または激しいスキャン |
| スイッチでDAIの「drop」カウンタが増える | 記録された対応に反するARPメッセージ |

```bash
# 自分が所有するホストでの正当な観察
ip neigh show
sudo tcpdump -ni eth0 arp     # 自分のNICでARPトラフィックを見る
```

見えたものを、スイッチ自身のDAIログやDHCPリースの一覧と突き合わせる。

## 8. セキュリティノート

| 問題 | リスク | 防御 |
|:---|:---|:---|
| ARPは認証できない | 偽のIP-MAC対応 | DHCPスヌーピング + DAI |
| 1つの大きく平らなセグメント | ローカルのMITMと偵察が容易 | VLAN / セグメンテーション |
| フィルタされないgratuitous ARP | キャッシュの大量上書き | レート制限 / 検査 |
| 古い静的エントリ | NIC交換後の障害 | 更新のための手順書 |
| IPv6を無視 | ARPだけ考えていると生じる穴 | RA Guard、ND検査 |
| 平文のプロトコル | MITMが成功すると読める | どこでもTLS、加えてHSTS |

原則: ローカルネットワークは、スイッチのポリシーが実際に強制する範囲までしか信頼しない。エンドツーエンドの暗号化はリンク層の対策を補うもので、置き換えるものではない。

## 9. チートシート

```bash
# ── 近傍テーブルを調べる(自分のホスト) ──────────────────────
ip neigh show
ip -4 neigh show dev eth0
ip -6 neigh show               # IPv6(NDP)版

# ── 自分のホストでエントリを管理(本番では慎重に) ───────────
sudo ip neigh add 10.0.0.1 lladdr aa:bb:cc:dd:ee:ff dev eth0 nud permanent
sudo ip neigh del 10.0.0.1 dev eth0
sudo ip neigh flush dev eth0

# ── 通常の名前解決を起こす ───────────────────────────────────
ping -c 1 10.0.0.9
ip neigh get 10.0.0.9 dev eth0

# ── 自分のNICでARPを受動的に観察する ─────────────────────────
sudo tcpdump -ni eth0 arp -vv

# ── LinuxブリッジでのMAC学習 ─────────────────────────────
bridge fdb show
```

| コマンド | 用途 |
|:---|:---|
| `ip neigh` | ARP/NDPキャッシュを見る・編集する |
| `tcpdump arp` | 自分のNICでARPトラフィックを監査する |
| `bridge fdb` | LinuxブリッジのMAC学習を見る |
