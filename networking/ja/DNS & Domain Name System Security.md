## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| DNS | インターネットの「電話帳」。`example.com` のような名前をIPアドレスに変える |
| リゾルバ | あなたの代わりに名前解決を行うサービス(普通はISPのものか公開のもの) |
| 権威サーバー | あるドメインの本当の答えを保持するサーバー |
| レコード(RR) | DNSの1件の項目。名前とその値(アドレス、メールサーバーなど) |
| ゾーン | 1つのドメインのレコードの集まり。1つの単位として管理される |
| TTL | ある答えを、再び問い合わせるまでにキャッシュしてよい時間 |
| キャッシュ | 最近の答えの保存コピー。同じ問い合わせが次回は即座に返る |
| DNSSEC | DNSの答えへのデジタル署名。偽の答えを見分けられるようにする |
| DoT / DoH | 暗号化された接続で送るDNS(TLS経由、またはHTTPS経由) |

## 1. DNSとは、そして名前の木

コンピュータはIPアドレスで話すが、人間は名前で覚える。**DNS**(Domain Name System)は、一方をもう一方に翻訳するサービスだ。`example.com` と入力すると、DNSが `93.184.216.34` を返す。インターネットの電話帳である。

名前は逆さまの木として整理され、ルートから始めて**右から左へ**読む。

```
                    .  (ルート)
                   / \
                 com  org  ...
                /  \
           example  google
              /
           www            →  完全な名前: www.example.com.
```

| レベル | 例 | 誰が運営するか |
|:---|:---|:---|
| ルート | `.` | ルートサーバー |
| TLD(トップレベルドメイン) | `com`, `id`, `jp` | レジストリ |
| ドメイン / ゾーン | `example.com` | ある組織 |
| ホスト | `www`, `mail` | ドメイン内の1台のマシン |

木全体を知っているサーバーは1つもない。各レベルは次のレベルを下へ**委任**する(「`.com` のサーバーに聞け、そこが `example.com` のサーバーを教えてくれる」)。この委任があるから、DNSはインターネット全体に対応できる。

## 2. 名前解決は実際どう起きるか

3人の登場人物がいる。

| 登場人物 | 役割 |
|:---|:---|
| スタブリゾルバ | OSの中の小さなクライアント。リゾルバに尋ねるだけ |
| フルリゾルバ(recursive) | 面倒な作業をこなし、答えを覚える(キャッシュ) |
| 権威サーバー | あるドメインの本当のレコードを保持する |

リゾルバがまだ答えをキャッシュしていなければ、木を上からたどる。

```text
1. ルートサーバーに聞く       → 「分からないが、.com のサーバーに聞け」
2. .com のサーバーに聞く      → 「example.com のサーバーに聞け」
3. example.com のサーバーに聞く → 「www.example.com は 93.184.216.34」  ✓
```

```
あなた ──► フルリゾルバ ──► ルート
                │            │  「.com に聞け」
                ├──► .com ───┘
                │     │  「example.com に聞け」
                └──► example.com ──► 答え
                │
        答えをTTLの間キャッシュするので、次回は即座
```

各レコードには、どれだけキャッシュしてよいかを示す**TTL**がある。キャッシュがあるからDNSは速い。なければ、クリックのたびに木全体をもう一度たどることになる。

衛生に関する注意: **フルリゾルバ**(クライアントのために木をたどる)と**権威サーバー**(あるドメインの答えを返す)は別の仕事だ。公開の権威サーバーがオープンなrecursionも兼ねるべきではない。悪用と増幅の磁石になるからだ。

## 3. よく出てくるレコードの種類

| 種類 | 保持するもの | 例 |
|:---|:---|:---|
| A | IPv4アドレス | `93.184.216.34` |
| AAAA | IPv6アドレス | `2606:2800:...` |
| CNAME | 別名(「この名前は本当はあの名前」) | `www → origin.cdn.net.` |
| MX | そのドメインのメールの行き先 | `10 mail.example.com.` |
| NS | そのゾーンの権威サーバーはどれか | `ns1.example.com.` |
| TXT | 自由なテキスト(SPFやドメイン確認に使う) | `"v=spf1 ..."` |
| PTR | 逆引き: IPから名前へ戻す | 逆引きで使う |
| DNSKEY / RRSIG / DS | DNSSECの鍵と署名(第4節) | 鍵 / 署名データ |

DNSは通常UDPポート53(小さく速い)で流れる。大きな答えはTCPポート53に切り替わる。

## 4. DNSSEC: 答えが本物だと証明する

素のDNSには弱点がある。答えが届いたとき、それが本当に正しい場所から来て、途中ですり替えられていないことを確かめる仕組みが組み込まれていない。**DNSSEC**は、**デジタル署名**を加えてこれを解決する(署名の考え方はLC-055から)。

各ゾーンは自分のレコードに署名する。検証するリゾルバは署名を確認でき、答えが本物で改ざんされていないと確信できる。

```text
確認:  Verify(ゾーンの公開鍵, レコード, 署名) → 本物 / 偽物
```

信頼はルートから下へ連鎖する。PKIの証明書チェーン(LC-057)に似ている。ルートが `.com` を保証し、`.com` が `example.com` を保証し、という具合だ。リゾルバはルートを信頼するだけで、チェーン全体を信頼できる。

```
ルート(信頼の出発点)
  │ 保証する
  ▼
.com
  │ 保証する
  ▼
example.com  ──署名する──►  自分のレコード
```

重要: DNSSECは答えが**本物**だと証明するが、答えを**隠さない**。質問も答えも平文のまま流れる。プライバシーにはDoTかDoHが必要だ(次の節)。

## 5. DNSのプライバシー: DoT と DoH

従来のDNSは平文で送られるので、経路上の誰もがあなたが引いたすべての名前を見られ、改ざんもしうる。2つの仕組みがこれを暗号化する。

| 仕組み | やり方 | ポート |
|:---|:---|:---|
| 従来のDNS | 平文 | UDP/TCP 53 |
| DoT(DNS over TLS) | DNSをTLS接続で包む | TCP 853 |
| DoH(DNS over HTTPS) | DNSをHTTPSで運び、Web通信に紛れ込ませる | TCP 443 |

利点は、名前解決への受動的な盗聴と経路上の改ざんを止めることだ。ただしトレードオフがある。どのリゾルバを使っても(大手のDoH事業者も含めて)、そのリゾルバはあなたのクエリを見られる。だからプライバシーポリシーを信頼できるものを選ぶこと。多くの組織は、セキュリティのログ記録を機能させ続けるため、あえて内部リゾルバを強制し、勝手なDoHをブロックする。最良の組み合わせは、暗号化された経路(DoT/DoH)**と**、DNSSECを検証するリゾルバだ。

## 6. ゾーン転送: 設定ミスのリスク

**ゾーン転送**(AXFR)は正当な機能だ。バックアップのDNSサーバーが、メインのサーバーからレコードの一覧全体をコピーできるようにする。問題は、それが誰にでも開かれたままになっているときだ。

見知らぬ人がゾーン転送を要求できると、内部ホスト名の一覧**全体**を一度にダウンロードできてしまう。サーバー、命名規則、何もかもだ。これは偵察の宝の山で、本物の攻撃なしに手渡されてしまう。

自分のゾーンを守る方法:

- ゾーン転送は、既知のバックアップサーバーにだけ、IPで許可する。
- 転送を**TSIG**(両サーバーが確認する共有の秘密)で保護する。
- 秘密のホスト名を安全のよりどころにしない。セグメンテーションと最小権限を適用し続ける。

> この教材は設定ミスを見つけて直すためのもので、実行するためではない。権威サーバーのログで、予期しない転送の試みを監視すること。

## 7. キャッシュポイズニングと、その防ぎ方

**考え方:** リゾルバは受け入れた答えを何でもキャッシュする。攻撃者が本物の答えより先に**偽の**答えを滑り込ませ、それを有効に見せかけられれば、リゾルバは間違ったアドレスをキャッシュし、TTLの間ずっと全員に渡してしまう。アドレスバーには本物の名前が出たまま、被害者は攻撃者のサーバーへ送られる。

偽物が受け入れられるには、リゾルバの質問といくつかの乱数に一致しなければならない。かつてはその乱数が小さすぎて安全ではなかった。現代の防御はどれも、偽の答えをはるかに作りにくくするか、検出しやすくすることで働く。

| 防御 | 役割 |
|:---|:---|
| 送信元ポートの無作為化 + クエリIDの無作為化 | 攻撃者が推測すべき量を大きく増やす |
| DNSクッキー | 経路外からの安上がりなスプーフを拒む共有トークン |
| DNSSEC検証 | 偽の答えは署名確認に失敗して捨てられる |
| 暗号化された経路(DoT/DoH) | 経路上の攻撃者が読んだり注入したりできなくする |

気づくべき危険信号: 正当な更新なしに突然変わるアドレス、名前解決の失敗の急増、あるリゾルバの答えが別の信頼できるリゾルバと食い違うこと。本当の守りは多層防御だ。推測を難しくする無作為性と、**加えて**偽造を検出できるようにするDNSSEC。

## 8. セキュリティノート

| 問題 | リスク | 防御 / 検出 |
|:---|:---|:---|
| 平文のDNS | 盗聴と経路上の改ざん | DoT/DoH、信頼できるリゾルバ |
| 検証しないリゾルバ | 偽の答えが気づかれず通る | DNSSEC検証を有効にする |
| オープンなフルリゾルバ | 悪用と増幅 | クライアントを制限し、recursiveと権威を分ける |
| オープンなゾーン転送 | ゾーン全体が吸い出される | IPで制限 + TSIG、ログでアラート |
| DHCP経由の不正なリゾルバ | 名前解決がリダイレクトされる | DHCPスヌーピング、RA Guard、DoHポリシー |

ラボの衛生: 自分が所有するリゾルバとゾーンだけをテストすること。答えがおかしいときは、`dig +dnssec` の結果を2つ目の信頼できる公開リゾルバと比べる。

## 9. チートシート

```bash
# ── 基本の名前解決 ───────────────────────────────────────────
dig example.com A +short       # IPv4アドレスだけ
dig example.com AAAA           # IPv6
dig MX example.com             # メールサーバー
dig NS example.com             # 権威ネームサーバー

# ── ルートからの道筋全体を見る ───────────────────────────────
dig +trace example.com

# ── DNSSECの確認 ─────────────────────────────────────────────
dig example.com A +dnssec      # 署名(RRSIG)を表示
delv example.com A             # 設定済みなら検証付きの名前解決

# ── 逆引き ───────────────────────────────────────────────────
dig -x 93.184.216.34

# ── 自分のシステムのリゾルバ ─────────────────────────────────
resolvectl status
resolvectl query example.com
```

| コマンド | 用途 |
|:---|:---|
| `dig +short` | 簡潔な答え |
| `dig +dnssec` | DNSSECの署名を表示 |
| `dig +trace` | ルートから下への名前解決を観察 |
| `resolvectl` | システム自身のリゾルバを調べる |
