## Istilah penting

| Istilah | Artinya |
|:---|:---|
| Cluster | Kumpulan mesin yang dikelola Kubernetes untuk menjalankan container |
| Control plane | Komponen pusat: API server, etcd, scheduler, controller manager |
| Node | Mesin yang menjalankan pod, dengan kubelet dan container runtime |
| Pod | Unit terkecil di Kubernetes, berisi satu atau beberapa container |
| Namespace | Pembagian logis di dalam cluster, misalnya per tim atau per aplikasi |
| RBAC | Role-Based Access Control: siapa boleh melakukan apa terhadap resource apa di cluster |
| Service account | Identitas untuk pod saat berbicara dengan API server |
| securityContext | Pengaturan keamanan pod atau container, misalnya user dan capability |
| NetworkPolicy | Aturan firewall antar pod |
| Admission controller | Pemeriksa yang menerima atau menolak objek sebelum disimpan ke cluster |

## 1. Kenapa Kubernetes perlu dipelajari khusus

Container ([LC-030](../../linux/id/23.%20Containerization.md)) sudah punya risiko sendiri. Kubernetes menambah lapisan baru: API server yang bisa membuat dan menghapus apa saja di cluster, identitas untuk setiap pod, dan jaringan yang secara default membiarkan semua pod saling berbicara.

Akibat kesalahan konfigurasi di Kubernetes sering lebih besar daripada di satu server:

| Kesalahan | Akibat |
|:---|:---|
| API server atau dashboard terbuka ke internet tanpa autentikasi | Siapa pun bisa menjalankan container di cluster, sering dipakai untuk mining kripto |
| Pod berjalan `privileged` | Container bisa mengambil alih node tempatnya berjalan |
| Service account default punya hak luas | Satu aplikasi yang dibobol bisa mengendalikan seluruh cluster |
| Tidak ada network policy | Penyerang di satu pod bisa menjangkau database di namespace lain |
| Secret disimpan tanpa enkripsi dan bisa dibaca banyak pihak | Kredensial database dan API ikut bocor |

## 2. Arsitektur singkat dan model 4C

```
 kubectl / CI ──► API server ──► etcd (semua state cluster, termasuk Secret)
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
        Node 1     Node 2     Node 3
        kubelet    kubelet    kubelet
        [pod][pod] [pod]      [pod][pod]
```

Semua perubahan lewat **API server**. Karena itu, siapa yang boleh berbicara dengan API server dan apa yang boleh ia lakukan adalah pertanyaan keamanan yang paling penting.

Dokumentasi Kubernetes memakai model **4C**. Setiap lapisan hanya seaman lapisan di luarnya:

| Lapisan | Contoh kontrol |
|:---|:---|
| Cloud | IAM, jaringan VPC, akses ke node (LC-077, LC-081) |
| Cluster | RBAC, admission control, enkripsi etcd, audit log |
| Container | Image yang dipindai, user non-root, capability minimal |
| Code | Aplikasi yang aman, dependency yang dipindai (LC-078) |

## 3. Akses ke API server dan RBAC

Setiap permintaan ke API server melewati tiga tahap: **autentikasi** (siapa kamu), **otorisasi** (bolehkah kamu, biasanya lewat RBAC), dan **admission** (apakah objek ini sesuai aturan).

RBAC punya empat jenis objek:

| Objek | Berlaku di | Isi |
|:---|:---|:---|
| Role | Satu namespace | Daftar izin |
| ClusterRole | Seluruh cluster | Daftar izin |
| RoleBinding | Satu namespace | Menghubungkan Role atau ClusterRole ke user, grup, atau service account |
| ClusterRoleBinding | Seluruh cluster | Menghubungkan ClusterRole ke subjek di seluruh cluster |

Contoh Role yang sempit:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: baca-pod
  namespace: toko
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
```

Izin yang harus diperlakukan setara admin cluster:

| Izin | Kenapa berbahaya |
|:---|:---|
| `*` pada `*` | Semua aksi, semua resource |
| `create` pada `pods` (atau Deployment, Job, dan sejenisnya) | Bisa membuat pod yang memasang service account lain atau berjalan privileged |
| `get` / `list` pada `secrets` | Membaca semua kredensial di namespace itu, termasuk token service account |
| `create` pada `pods/exec` | Menjalankan perintah di dalam container mana pun |
| `escalate`, `bind` pada roles | Bisa memberi dirinya izin yang lebih tinggi |
| `impersonate` pada users, groups, serviceaccounts | Bertindak sebagai identitas lain |
| `get` pada `nodes/proxy` | Berbicara langsung dengan kubelet, melewati sebagian kontrol |
| Binding ke ClusterRole `cluster-admin` | Admin penuh |

Memeriksa izin sebuah identitas:

```bash
kubectl auth can-i --list -n toko --as=system:serviceaccount:toko:default
kubectl auth can-i create pods -n toko --as=system:serviceaccount:toko:web
kubectl get clusterrolebindings -o wide | grep cluster-admin
```

## 4. Service account dan token

Setiap pod berjalan dengan sebuah service account. Kalau tidak disebutkan, pod memakai service account `default` di namespace-nya, dan secara default token-nya dipasang ke dalam pod di `/var/run/secrets/kubernetes.io/serviceaccount/`.

Kalau aplikasi di pod dibobol, penyerang memegang token itu dan bisa memanggil API server dengan izin service account tersebut.

| Praktik | Cara |
|:---|:---|
| Jangan pasang token kalau tidak dibutuhkan | `automountServiceAccountToken: false` di pod atau service account |
| Satu service account per aplikasi | Jangan pakai `default`, jangan berbagi antar aplikasi |
| Izin seminimal mungkin | Kebanyakan aplikasi web sama sekali tidak perlu berbicara dengan API server |
| Token berumur pendek | Kubernetes modern memakai projected token yang kedaluwarsa. Hindari Secret token lama yang tidak pernah kedaluwarsa |

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
  namespace: toko
automountServiceAccountToken: false
```

## 5. Keamanan pod

`securityContext` menentukan seberapa besar kekuasaan sebuah container terhadap node tempatnya berjalan.

Pod yang aman:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: toko
spec:
  serviceAccountName: web
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: web
      image: registry.contoh.internal/toko/web:1.4.2
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      resources:
        limits: { cpu: "500m", memory: "256Mi" }
```

Pengaturan yang berbahaya:

| Pengaturan | Akibat |
|:---|:---|
| `privileged: true` | Container punya hampir semua akses yang dimiliki node |
| `hostPath` ke `/`, `/etc`, atau socket container runtime | Container bisa membaca atau mengubah file node, termasuk menjalankan container baru di luar kendali Kubernetes |
| `hostNetwork`, `hostPID`, `hostIPC` | Container berbagi jaringan atau proses dengan node |
| Capability `SYS_ADMIN`, `NET_ADMIN` | Kekuasaan setara root untuk banyak operasi |
| Berjalan sebagai root tanpa batasan | Celah di aplikasi langsung menjadi root di container |
| Tanpa `resources.limits` | Satu pod bisa menghabiskan CPU dan memori node |

## 6. Pod Security Standards

Kubernetes menyediakan tiga tingkat standar keamanan pod, ditegakkan oleh **Pod Security Admission** bawaan:

| Tingkat | Isi |
|:---|:---|
| Privileged | Tanpa batasan. Hanya untuk komponen sistem yang memang butuh |
| Baseline | Melarang hal yang jelas berbahaya: privileged, hostPath, hostNetwork, capability berbahaya |
| Restricted | Baseline ditambah wajib non-root, `allowPrivilegeEscalation: false`, drop ALL capability, seccomp |

Diaktifkan dengan label pada namespace:

```bash
kubectl label namespace toko \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/warn=restricted
```

Strategi penerapan yang aman: pasang mode `warn` dan `audit` dulu, perbaiki workload yang melanggar, baru aktifkan `enforce`.

## 7. Network policy

Secara default, **semua pod bisa berbicara dengan semua pod** di cluster, lintas namespace. NetworkPolicy membatasinya, asalkan plugin jaringan (CNI) yang dipakai mendukungnya, misalnya Calico atau Cilium.

Mulai dari menolak semua, lalu buka yang dibutuhkan:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: tolak-semua
  namespace: toko
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-ke-db
  namespace: toko
spec:
  podSelector:
    matchLabels: { app: db }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: web }
      ports:
        - protocol: TCP
          port: 5432
```

Jangan lupa membuka egress untuk DNS (port 53 ke CoreDNS), karena tanpa itu aplikasi tidak bisa mencari nama host. Batasi juga egress ke internet, supaya pod yang dibobol tidak bebas mengirim data keluar atau mengunduh tool.

## 8. Secret

Objek Secret di Kubernetes hanya di-**encode base64**, bukan dienkripsi. Siapa pun yang bisa membaca Secret lewat API, atau membaca etcd secara langsung, mendapatkan isinya.

```bash
kubectl get secret db-cred -n toko -o jsonpath='{.data.password}' | base64 -d
```

| Kontrol | Penjelasan |
|:---|:---|
| Enkripsi etcd at rest | Konfigurasi `EncryptionConfiguration` dengan provider KMS. Di layanan cloud terkelola, aktifkan enkripsi Secret dengan kunci KMS |
| Batasi RBAC ke Secret | Hampir tidak ada manusia atau aplikasi yang perlu `list` semua Secret |
| Secret manager eksternal | AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, atau Vault, disambungkan lewat External Secrets Operator atau Secrets Store CSI Driver |
| Jangan taruh Secret di Git | Manifest berisi Secret yang ter-commit sama saja dengan bocor. Pakai Sealed Secrets atau SOPS kalau harus disimpan di Git |

## 9. Supply chain image dan admission control

Image yang berjalan di cluster harus berasal dari sumber yang dipercaya dan sudah dipindai. Pemindaian dengan Trivy sudah dibahas di [LC-078](../../devsecops/id/1.%20DevSecOps%20Fundamentals.md). Di cluster, aturan ini ditegakkan oleh admission controller.

| Aturan | Contoh |
|:---|:---|
| Hanya registry tertentu | Tolak image yang bukan dari `registry.contoh.internal` |
| Tanpa tag `latest` | Wajib tag versi atau digest |
| Image harus ditandatangani | Verifikasi tanda tangan cosign |
| Wajib `resources.limits` dan label pemilik | Supaya bisa ditelusuri dan tidak menghabiskan node |

Tool yang umum: **Kyverno** (aturan ditulis dalam YAML Kubernetes) dan **OPA Gatekeeper** (aturan ditulis dalam Rego). Contoh aturan Kyverno:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: hanya-registry-internal
spec:
  validationFailureAction: Enforce
  rules:
    - name: cek-registry
      match:
        any:
          - resources:
              kinds: ["Pod"]
      validate:
        message: "Image harus berasal dari registry.contoh.internal"
        pattern:
          spec:
            containers:
              - image: "registry.contoh.internal/*"
```

## 10. Kubernetes di cloud: EKS, AKS, GKE

Layanan Kubernetes terkelola mengurus control plane, tapi tanggung jawab bersama ([LC-077](1.%20Cloud%20Security%20Fundamentals.md)) tetap berlaku: konfigurasi workload, RBAC, dan jaringan tetap tanggung jawabmu.

| Topik | Yang perlu dilakukan |
|:---|:---|
| Endpoint API server | Jadikan privat, atau batasi ke rentang IP tertentu |
| Identitas pod ke cloud | IRSA atau EKS Pod Identity di AWS, Workload Identity di AKS dan GKE. Jangan simpan access key di Secret ([LC-081](2.%20Cloud%20IAM%20in%20Depth.md)) |
| Metadata service node | Pod jangan sampai bisa memakai role milik node. Di EKS, wajibkan IMDSv2 dengan hop limit 1 supaya pod biasa tidak bisa mengambil token metadata |
| Akses admin | Peta IAM ke RBAC Kubernetes (EKS access entries, Azure RBAC untuk AKS, GKE IAM) dengan prinsip least privilege |
| Update | Ikuti versi Kubernetes yang masih didukung, update node secara rutin |

## 11. Audit log dan deteksi runtime

### Audit log Kubernetes

API server bisa mencatat setiap permintaan. Di layanan terkelola, aktifkan pengiriman audit log ke layanan log cloud (misalnya EKS control plane logging ke CloudWatch).

Kejadian yang perlu dibuatkan alert:

| Kejadian | Kenapa |
|:---|:---|
| `create` pada `pods/exec` | Seseorang menjalankan perintah di dalam container produksi |
| Pod baru dengan `privileged`, `hostPath`, atau `hostPID` | Pola umum untuk mengambil alih node |
| ClusterRoleBinding baru ke `cluster-admin` | Hak admin penuh diberikan |
| `list` atau `get` Secret oleh service account yang biasanya tidak pernah membacanya | Kredensial sedang dikumpulkan |
| Permintaan dari `system:anonymous` yang berhasil | Akses tanpa autentikasi terbuka |

### Deteksi runtime

Audit log hanya melihat API server. Apa yang terjadi di dalam container dilihat oleh tool runtime seperti **Falco** (open source, berbasis eBPF):

```text
Contoh aturan bawaan Falco:
  Terminal shell in container          → shell interaktif dibuka di container
  Write below etc                      → file di /etc diubah saat runtime
  Contact K8S API Server From Container → container memanggil API server tanpa diduga
```

Semua alert ini dikirim ke SIEM yang sama dengan log lain ([LC-072](../../blue-team/id/1.%20SOC%20%26%20Log%20Analysis.md)).

### Task 2: perbaiki manifest pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: laporan
  namespace: keuangan
spec:
  hostNetwork: true
  containers:
    - name: laporan
      image: laporan:latest
      securityContext:
        privileged: true
      volumeMounts:
        - name: host
          mountPath: /host
  volumes:
    - name: host
      hostPath:
        path: /
```

Sebutkan semua masalahnya, lalu tulis versi yang aman. Aplikasi ini hanya membaca database dan membuat file PDF.

<details><summary>Kunci jawaban</summary>

Masalah: `hostNetwork`, `privileged`, seluruh filesystem node dipasang lewat `hostPath: /`, tag `latest`, image tanpa registry yang jelas, tanpa `runAsNonRoot`, tanpa drop capability, tanpa batas resource, dan token service account default ikut terpasang.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: laporan
  namespace: keuangan
spec:
  serviceAccountName: laporan
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: laporan
      image: registry.contoh.internal/keuangan/laporan:2.1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: ["ALL"] }
      resources:
        limits: { cpu: "500m", memory: "512Mi" }
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}
```

Volume `emptyDir` di `/tmp` disediakan karena filesystem root dibuat read-only, sementara pembuatan PDF butuh tempat menulis sementara.

</details>

### Task 3: tinjau RBAC

```yaml
kind: Role
metadata: { name: deployer, namespace: toko }
rules:
  - apiGroups: ["", "apps"]
    resources: ["pods", "deployments", "secrets"]
    verbs: ["*"]
```

Role ini dipasang ke service account pipeline CI yang men-deploy aplikasi toko. Apa risikonya, dan bagaimana mempersempitnya?

<details><summary>Kunci jawaban</summary>

Risiko: pipeline bisa membaca dan mengubah semua Secret di namespace `toko`, menghapus apa saja, dan membuat pod sembarang, termasuk pod yang memasang service account lain atau Secret apa pun. Kalau pipeline dibobol, seluruh namespace ikut dikuasai.

Versi yang lebih sempit: hanya mengubah Deployment, tanpa akses Secret, tanpa membuat pod secara langsung.

```yaml
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "patch", "update"]
```

Ditambah aturan admission (Pod Security `restricted` dan Kyverno) supaya Deployment yang di-patch pun tidak bisa menjalankan pod berbahaya.

</details>
