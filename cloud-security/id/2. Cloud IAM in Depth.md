## Istilah penting

| Istilah | Artinya |
|:---|:---|
| Principal | Pihak yang meminta akses: user, role, layanan, atau akun lain |
| Identity-based policy | Policy yang ditempelkan ke user, grup, atau role |
| Resource-based policy | Policy yang ditempelkan ke resource, misalnya bucket policy di S3 |
| Trust policy | Resource-based policy pada role yang menentukan siapa yang boleh memakai (assume) role itu |
| Condition | Syarat tambahan di policy, misalnya wajib MFA atau hanya dari organisasi tertentu |
| SCP / RCP | Service Control Policy / Resource Control Policy: batas maksimum izin untuk principal / resource di seluruh akun AWS Organizations |
| Permission boundary | Batas maksimum izin yang bisa dimiliki satu user atau role |
| Explicit deny | Pernyataan `"Effect": "Deny"` yang selalu menang |
| Confused deputy | Layanan tepercaya yang tertipu menjalankan aksi untuk pihak yang tidak berhak |
| OIDC federation | Login tanpa key permanen memakai token dari penyedia identitas, misalnya GitHub Actions |

## 1. Kenapa IAM perlu dipelajari lebih dalam

Di [LC-077](1.%20Cloud%20Security%20Fundamentals.md) kamu belajar bahwa di cloud, identitas adalah perimeter. Pelajaran ini membahas detailnya, karena kesalahan IAM jarang terlihat jelas. Policy yang tampak aman bisa memberi akses admin lewat jalan memutar, dan trust policy yang sedikit longgar bisa membuka akun ke pihak luar.

Tiga hal yang akan kamu pelajari:

1. Membaca policy dan memprediksi hasilnya dengan tepat.
2. Mengenali izin yang berbahaya walaupun namanya terdengar tidak berbahaya.
3. Mengurangi izin secara bertahap berdasarkan data pemakaian.

Contoh di pelajaran ini memakai AWS, dengan bagian khusus untuk Azure dan Google Cloud.

## 2. Anatomi sebuah policy

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BacaLaporanDenganMFA",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::laporan-keuangan",
        "arn:aws:s3:::laporan-keuangan/*"
      ],
      "Condition": {
        "Bool": { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}
```

| Elemen | Arti |
|:---|:---|
| `Effect` | `Allow` atau `Deny` |
| `Action` | Operasi API, formatnya `layanan:NamaAksi`. Wildcard `*` berarti semua |
| `Resource` | ARN resource yang dituju. `s3:ListBucket` berlaku ke bucket, `s3:GetObject` ke object (`/*`) |
| `Condition` | Syarat tambahan. Di contoh ini, hanya berlaku kalau sesi memakai MFA |
| `Principal` | Hanya ada di resource-based policy dan trust policy: siapa yang diberi izin |

Condition key yang sering dipakai untuk keamanan:

| Key | Fungsi |
|:---|:---|
| `aws:MultiFactorAuthPresent` | Wajib MFA |
| `aws:SourceIp` | Hanya dari rentang IP tertentu |
| `aws:PrincipalOrgID` | Hanya principal dari organisasi AWS milikmu |
| `aws:SourceAccount`, `aws:SourceArn` | Mencegah confused deputy saat layanan AWS bertindak atas namamu |
| `sts:ExternalId` | Mencegah confused deputy saat pihak ketiga memakai role-mu |
| `aws:RequestedRegion` | Membatasi region yang boleh dipakai |

## 3. Bagaimana AWS memutuskan "boleh" atau "tidak"

Setiap permintaan API dievaluasi dengan urutan logika berikut (disederhanakan untuk permintaan di dalam satu akun):

```
 1. Ada Deny eksplisit di policy mana pun?            ──► ya ──► DITOLAK
 2. SCP / RCP organisasi mengizinkan aksi ini?        ──► tidak ──► DITOLAK
 3. Resource-based policy mengizinkan principal ini?  ──► ya ──► DIIZINKAN *
 4. Identity-based policy mengizinkan?                ──► tidak ──► DITOLAK (implicit deny)
 5. Permission boundary (kalau ada) mengizinkan?      ──► tidak ──► DITOLAK
 6. Session policy (kalau ada) mengizinkan?           ──► tidak ──► DITOLAK
                                                      ──► ya ──► DIIZINKAN

 * Ada pengecualian, misalnya untuk role session dan permission boundary.
   Lihat bagan resmi "Policy evaluation logic" di AWS IAM User Guide.
```

Tiga aturan yang perlu diingat:

1. **Default-nya ditolak.** Tanpa `Allow`, jawabannya tidak.
2. **Deny eksplisit selalu menang**, di level mana pun.
3. **Pagar pembatas (SCP, permission boundary, session policy) tidak memberi izin.** Mereka hanya membatasi. Izin tetap harus diberikan oleh identity-based atau resource-based policy.

Jangan menebak. Pakai simulator:

```bash
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::111122223333:role/analis \
  --action-names s3:GetObject s3:DeleteObject \
  --resource-arns arn:aws:s3:::laporan-keuangan/q3.pdf \
  --query 'EvaluationResults[].{Aksi:EvalActionName,Hasil:EvalDecision}'
```

## 4. Pagar pembatas: SCP dan permission boundary

### Service Control Policy

SCP berlaku untuk **semua** principal di akun anggota AWS Organizations, termasuk root akun anggota. Ini cara organisasi menetapkan aturan yang tidak bisa dilanggar oleh admin di akun mana pun.

Contoh SCP yang sering dipakai:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "JanganMatikanAuditLog",
      "Effect": "Deny",
      "Action": ["cloudtrail:StopLogging", "cloudtrail:DeleteTrail", "cloudtrail:UpdateTrail"],
      "Resource": "*"
    },
    {
      "Sid": "HanyaRegionYangDipakai",
      "Effect": "Deny",
      "NotAction": ["iam:*", "organizations:*", "sts:*", "support:*"],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["ap-southeast-3", "ap-northeast-1"] }
      }
    }
  ]
}
```

Contoh kedua disederhanakan. Contoh resmi dari AWS mengecualikan lebih banyak layanan global, seperti CloudFront dan Route 53, supaya tidak ikut terblokir.

SCP pertama membuat penyerang yang sudah menjadi admin akun tetap tidak bisa mematikan CloudTrail (ingat Task 2 di LC-077). SCP kedua menutup region yang tidak dipakai, yang sering dipilih penyerang untuk menjalankan server mining karena tidak ada yang mengawasinya.

Catatan: SCP tidak berlaku untuk management account organisasi. Karena itu, jangan jalankan workload di management account.

### Permission boundary

Permission boundary membatasi izin maksimum satu user atau role. Kegunaan utamanya adalah **delegasi yang aman**: tim developer boleh membuat role sendiri untuk aplikasinya, asalkan setiap role baru wajib memakai boundary tertentu. Dengan begitu developer tidak bisa membuat role yang lebih kuat dari boundary itu.

```json
{
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:AttachRolePolicy"],
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": {
    "StringEquals": { "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/BoundaryAplikasi" }
  }
}
```

## 5. Akses lintas akun dan confused deputy

Organisasi yang matang memakai banyak akun AWS: produksi, staging, log, keamanan. Akses antar akun dilakukan dengan **assume role**.

Supaya akun A bisa memakai role di akun B, **dua sisi harus setuju**:

| Sisi | Policy | Isi |
|:---|:---|:---|
| Akun B (pemilik role) | Trust policy pada role | Mengizinkan principal dari akun A memanggil `sts:AssumeRole` |
| Akun A (pemanggil) | Identity-based policy | Mengizinkan user atau role di akun A memanggil `sts:AssumeRole` ke role di akun B |

Trust policy yang terlalu longgar adalah kesalahan yang berbahaya:

```json
{ "Effect": "Allow", "Principal": { "AWS": "*" }, "Action": "sts:AssumeRole" }
```

Trust policy di atas mengizinkan **akun AWS mana pun di dunia** memakai role tersebut. Perbaiki dengan menyebut akun atau role yang spesifik, atau dengan menambahkan condition `aws:PrincipalOrgID`.

### Confused deputy

Misalkan kamu memakai layanan SaaS pemantau biaya, dan layanan itu meminta akses ke akunmu lewat sebuah role. Layanan itu melayani ribuan pelanggan memakai akun AWS yang sama. Kalau penyerang yang juga pelanggan memasukkan ARN role milikmu ke pengaturannya, layanan itu bisa tertipu dan mengakses akunmu atas permintaan penyerang.

Pertahanannya adalah **External ID**, nilai unik per pelanggan yang dibuat oleh vendor:

```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::999988887777:root" },
  "Action": "sts:AssumeRole",
  "Condition": { "StringEquals": { "sts:ExternalId": "pelanggan-7f3a91" } }
}
```

Untuk layanan AWS sendiri yang bertindak atas namamu (misalnya SNS menulis ke bucket), pakai condition `aws:SourceAccount` atau `aws:SourceArn`.

IAM Access Analyzer bisa mendaftar semua resource yang bisa diakses dari luar akun atau organisasi:

```bash
aws accessanalyzer create-analyzer --analyzer-name org-analyzer --type ORGANIZATION
aws accessanalyzer list-findings --analyzer-arn <arn-analyzer> \
  --query 'findings[?status==`ACTIVE`].{Resource:resource,Principal:principal}'
```

## 6. Izin yang diam-diam setara admin

Beberapa izin terdengar sempit, tapi siapa pun yang memilikinya bisa memberi dirinya sendiri hak yang lebih besar. Saat meninjau policy, perlakukan izin-izin ini sama seriusnya dengan `AdministratorAccess`:

| Izin | Kenapa berbahaya |
|:---|:---|
| `iam:CreatePolicyVersion`, `iam:SetDefaultPolicyVersion` | Bisa mengganti isi policy yang sudah menempel pada dirinya |
| `iam:AttachUserPolicy`, `iam:AttachRolePolicy`, `iam:PutUserPolicy`, `iam:PutRolePolicy` | Bisa menempelkan policy apa pun, termasuk admin |
| `iam:CreateAccessKey`, `iam:CreateLoginProfile`, `iam:UpdateLoginProfile` untuk user lain | Bisa membuat kredensial untuk user yang lebih kuat |
| `iam:UpdateAssumeRolePolicy` | Bisa mengubah siapa yang boleh memakai role yang kuat |
| `iam:PassRole` dikombinasikan dengan membuat EC2, Lambda, atau layanan lain | Bisa menjalankan kode dengan role yang lebih kuat dari dirinya |

`iam:PassRole` perlu perhatian khusus. Developer sering diberi `iam:PassRole` dengan `"Resource": "*"` supaya bisa men-deploy aplikasi. Akibatnya, ia bisa memasang role admin ke fungsi Lambda yang ia buat sendiri. Batasi `Resource` ke role aplikasi tertentu saja:

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } }
}
```

Tool open source seperti PMapper atau Cloudsplaining bisa menganalisis akunmu sendiri dan mencari jalur seperti ini secara otomatis. Jalankan dengan kredensial read-only.

## 7. Identitas untuk mesin: role, OIDC, dan workload identity

Access key permanen untuk aplikasi dan pipeline adalah sumber kebocoran yang paling umum. Hampir selalu ada alternatif tanpa key:

| Di mana kode berjalan | Cara tanpa key permanen |
|:---|:---|
| EC2 | Instance profile (role untuk EC2) |
| Lambda, ECS | Execution role / task role |
| EKS (Kubernetes) | IAM Roles for Service Accounts atau EKS Pod Identity |
| GitHub Actions, GitLab CI | OIDC federation ke role |
| Pusat data sendiri | IAM Roles Anywhere dengan sertifikat X.509 |

Contoh trust policy untuk GitHub Actions. Perhatikan condition `sub` yang membatasi ke satu repositori dan satu branch:

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:kodokthegr3at/zero2root-app:ref:refs/heads/main"
    }
  }
}
```

Kesalahan yang sering terjadi adalah memakai wildcard terlalu luas, misalnya `repo:kodokthegr3at/*` atau tanpa condition `sub` sama sekali. Akibatnya, repositori lain, termasuk fork, bisa memakai role deploy produksi. Ini melengkapi bagian keamanan pipeline di [LC-078](../../devsecops/id/1.%20DevSecOps%20Fundamentals.md).

## 8. Azure dan Google Cloud

### Azure

Azure punya **dua sistem peran yang terpisah**:

| Sistem | Mengatur | Contoh peran |
|:---|:---|:---|
| Microsoft Entra ID roles | Direktori: user, grup, aplikasi | Global Administrator, Privileged Role Administrator |
| Azure RBAC | Resource: VM, storage, jaringan | Owner, Contributor, Reader, User Access Administrator |

Azure RBAC berlaku berjenjang: **management group → subscription → resource group → resource**. Peran yang diberikan di level atas turun ke semua yang ada di bawahnya.

| Praktik | Penjelasan |
|:---|:---|
| Hindari Owner di level subscription untuk pekerjaan harian | Owner dan User Access Administrator bisa memberi akses ke orang lain |
| Pakai Privileged Identity Management (PIM) | Peran admin aktif hanya saat diminta, dengan persetujuan dan batas waktu |
| Managed identity untuk aplikasi | Pengganti secret atau sertifikat di kode |
| Global Administrator seminimal mungkin | Microsoft menyarankan kurang dari lima orang |

```bash
az role assignment list --all --query "[?roleDefinitionName=='Owner'].{who:principalName,scope:scope}" -o table
```

### Google Cloud

| Jenis peran | Contoh | Saran |
|:---|:---|:---|
| Basic | Owner, Editor, Viewer | Hindari di produksi, terlalu luas |
| Predefined | `roles/storage.objectViewer` | Pilihan utama |
| Custom | Buatan sendiri | Untuk kebutuhan yang sangat spesifik |

Hal penting di GCP:

1. **Service account key** (file JSON) sama berisikonya dengan access key AWS. Pakai Workload Identity Federation, lalu blokir pembuatan key dengan organization policy `iam.disableServiceAccountKeyCreation`.
2. Izin `iam.serviceAccounts.actAs` dan `iam.serviceAccountTokenCreator` mirip `iam:PassRole` di AWS. Siapa pun yang punya izin ini bisa bertindak sebagai service account yang lebih kuat.
3. IAM Recommender memberi saran pengurangan izin berdasarkan pemakaian 90 hari terakhir.

```bash
gcloud projects get-iam-policy ID_PROYEK \
  --flatten="bindings[].members" --filter="bindings.role:roles/owner OR bindings.role:roles/editor" \
  --format="table(bindings.role, bindings.members)"
```

## 9. Menuju least privilege

Hampir tidak ada yang bisa menulis policy minimal dengan benar pada percobaan pertama. Pendekatan yang realistis bersifat bertahap:

```
 1. Mulai dari policy terkelola yang cukup (misalnya ReadOnly + izin tulis spesifik)
 2. Jalankan beberapa minggu, kumpulkan data pemakaian
 3. Hasilkan policy dari aktivitas nyata, buang yang tidak pernah dipakai
 4. Validasi, uji di staging, terapkan
 5. Ulangi secara berkala
```

Tool yang membantu:

| Tool | Fungsi |
|:---|:---|
| IAM Access Analyzer policy generation | Membuat draf policy dari CloudTrail berdasarkan aksi yang benar-benar dipakai |
| IAM Access Analyzer unused access | Mencari role, key, dan izin yang tidak dipakai |
| Last accessed information | Kapan terakhir sebuah layanan dipakai oleh principal tertentu |
| `validate-policy` | Memeriksa kesalahan dan peringatan keamanan di policy sebelum dipasang |

```bash
aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY \
  --policy-document file://policy.json \
  --query 'findings[].{Jenis:findingType,Pesan:issueCode}'

JOB=$(aws iam generate-service-last-accessed-details \
  --arn arn:aws:iam::111122223333:role/app-laporan --query JobId --output text)
aws iam get-service-last-accessed-details --job-id "$JOB" \
  --query 'ServicesLastAccessed[?TotalAuthenticatedEntities==`0`].ServiceNamespace'
```

Perintah terakhir menampilkan layanan yang diizinkan untuk role itu tetapi tidak pernah dipakai. Layanan-layanan itu adalah kandidat untuk dihapus dari policy.

## 10. Mendeteksi perubahan IAM yang berisiko

Perubahan IAM jarang terjadi di akun yang sehat, jadi setiap perubahan pantas diperhatikan. Event CloudTrail yang perlu dibuatkan alert:

| Event | Kenapa |
|:---|:---|
| `CreatePolicyVersion` dengan `SetAsDefault=true` | Isi policy diganti, bisa menjadi eskalasi |
| `AttachUserPolicy`, `AttachRolePolicy` dengan `AdministratorAccess` | Hak admin baru diberikan |
| `PutUserPolicy`, `PutRolePolicy` | Inline policy baru, sering luput dari review |
| `UpdateAssumeRolePolicy` | Siapa yang boleh memakai role berubah |
| `CreateAccessKey` untuk user lain | Kredensial baru untuk identitas yang bukan dirinya |
| `CreateUser` lalu `CreateLoginProfile` di luar jam kerja | Akun backdoor |
| `AssumeRole` dari akun yang tidak dikenal | Akses lintas akun yang tidak diharapkan |
| `DeleteRolePermissionsBoundary`, `DetachRolePolicy` pada boundary | Pagar pembatas dilepas |

Event-event ini dikirim ke SIEM ([LC-072](../../blue-team/id/1.%20SOC%20%26%20Log%20Analysis.md)) dan dijadikan aturan deteksi. GuardDuty juga punya temuan bawaan untuk pola IAM yang mencurigakan.

## 11. Latihan

### Task 1: prediksi hasil evaluasi

Role `analis` punya dua policy:

```json
{ "Effect": "Allow", "Action": "s3:*", "Resource": "*" }
```

```json
{ "Effect": "Deny", "Action": "s3:DeleteObject", "Resource": "arn:aws:s3:::laporan-keuangan/*" }
```

Akunnya juga terkena SCP yang hanya mengizinkan region `ap-southeast-3`.

1. Bisakah `analis` membaca file di `laporan-keuangan`?
2. Bisakah `analis` menghapus file di `laporan-keuangan`?
3. Bisakah `analis` membuat bucket baru di region `us-east-1`?

<details><summary>Kunci jawaban</summary>

1. Bisa. Ada `Allow s3:*` dan tidak ada Deny untuk `GetObject` (asumsikan bucket ada di region yang diizinkan).
2. Tidak bisa. Deny eksplisit selalu menang.
3. Tidak bisa. SCP membatasi region, dan pagar pembatas tidak bisa dilewati oleh `Allow` di identity-based policy.

</details>

### Task 2: tinjau trust policy

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" }
  }
}
```

Role ini memiliki `AdministratorAccess` dan dipakai untuk deploy produksi. Apa masalahnya, dan bagaimana memperbaikinya?

<details><summary>Kunci jawaban</summary>

Tidak ada condition `sub`, jadi workflow dari repositori GitHub mana pun yang memakai provider OIDC ini bisa memakai role tersebut. Ini termasuk repositori milik orang lain, karena token GitHub Actions dikeluarkan oleh penerbit yang sama untuk semua repositori.

Perbaikan:

1. Tambahkan `"token.actions.githubusercontent.com:sub": "repo:organisasi/repo:ref:refs/heads/main"` atau, lebih baik lagi, batasi ke environment `production`.
2. Ganti `AdministratorAccess` dengan izin yang hanya dibutuhkan untuk deploy aplikasi itu.

</details>

### Task 3: cari izin yang setara admin

Policy untuk tim developer:

```json
{
  "Statement": [
    { "Effect": "Allow", "Action": ["lambda:*", "logs:*"], "Resource": "*" },
    { "Effect": "Allow", "Action": "iam:PassRole", "Resource": "*" },
    { "Effect": "Allow", "Action": ["iam:Get*", "iam:List*"], "Resource": "*" }
  ]
}
```

1. Kombinasi izin mana yang berbahaya?
2. Tulis ulang statement yang berbahaya supaya lebih aman.

<details><summary>Kunci jawaban</summary>

1. `lambda:*` (termasuk membuat fungsi) digabung dengan `iam:PassRole` ke resource `*`. Developer bisa membuat fungsi Lambda dan memasangkan role apa pun ke fungsi itu, termasuk role admin, lalu menjalankan kode dengan hak admin.
2. Batasi `PassRole` ke role aplikasi dan hanya untuk layanan Lambda:

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } }
}
```

Lalu pastikan role `app-*` dibuat dengan permission boundary, supaya tidak ada yang bisa membuat role `app-*` dengan izin admin.

</details>

## 12. Referensi cepat

```text
EVALUASI POLICY (AWS)
  default ditolak · Deny eksplisit selalu menang
  SCP, permission boundary, session policy = pagar, tidak memberi izin
  aws iam simulate-principal-policy ...

LINTAS AKUN
  trust policy di akun tujuan + identity policy di akun asal
  jangan "Principal": "*" · pakai aws:PrincipalOrgID
  vendor pihak ketiga → sts:ExternalId · layanan AWS → aws:SourceArn/SourceAccount

IZIN SETARA ADMIN
  iam:CreatePolicyVersion · iam:Attach*/Put*Policy · iam:UpdateAssumeRolePolicy
  iam:CreateAccessKey (user lain) · iam:PassRole + membuat compute

MESIN TANPA KEY
  instance profile · task/execution role · IRSA/Pod Identity · OIDC (cek "sub") · Roles Anywhere

AZURE
  Entra ID roles ≠ Azure RBAC · MG > subscription > RG > resource · PIM · managed identity

GCP
  hindari Owner/Editor · tanpa service account key (WIF) · actAs ≈ PassRole · IAM Recommender

LEAST PRIVILEGE
  pakai → ukur → hasilkan policy dari CloudTrail → validasi → ulangi
```
