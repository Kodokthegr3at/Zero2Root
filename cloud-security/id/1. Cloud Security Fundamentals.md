## 1. Cloud itu komputer orang lain

Saat memakai cloud, kamu menyewa server, penyimpanan, dan layanan dari penyedia seperti AWS, Microsoft Azure, atau Google Cloud. Semuanya diatur lewat API: membuat server, membuka port, atau membagikan file cukup dengan satu perintah.

Kemudahan ini sekaligus risikonya. Satu perintah yang salah bisa membuka database ke seluruh internet dalam hitungan detik. Laporan insiden cloud dari tahun ke tahun menunjukkan pola yang sama: penyebab utamanya jarang berupa celah di cloud itu sendiri. Penyebab utamanya adalah **miskonfigurasi** dan **kredensial yang bocor**.

| Penyedia | Nama layanan yang sering muncul |
|:---|:---|
| AWS | IAM, S3, EC2, VPC, CloudTrail, GuardDuty |
| Azure | Entra ID, Blob Storage, Virtual Machines, VNet, Activity Log, Defender for Cloud |
| Google Cloud | IAM, Cloud Storage, Compute Engine, VPC, Cloud Audit Logs, Security Command Center |

Contoh di pelajaran ini memakai AWS karena paling banyak dipakai, tapi konsepnya sama di ketiga penyedia.

## 2. Model tanggung jawab bersama

Penyedia cloud mengamankan **cloud-nya**. Kamu mengamankan **apa yang kamu taruh di dalamnya**.

```
                     IaaS (EC2)      PaaS (RDS)      SaaS (Microsoft 365)
Data & akses user    Kamu            Kamu            Kamu
Aplikasi             Kamu            Kamu            Penyedia
OS & patch           Kamu            Penyedia        Penyedia
Jaringan virtual     Kamu            Bersama         Penyedia
Hardware & gedung    Penyedia        Penyedia        Penyedia
```

Ada dua hal yang **selalu** jadi tanggung jawabmu di model mana pun:

1. **Data**: siapa yang boleh membacanya dan apakah dienkripsi.
2. **Identitas dan akses**: akun siapa saja yang ada, izinnya apa, dan apakah memakai MFA.

Kesalahpahaman yang sering terjadi: "Kami pakai AWS, jadi pasti aman." AWS menjaga data center-nya, tapi kalau bucket-mu kamu set publik, AWS akan dengan patuh menyajikannya ke siapa pun.

## 3. IAM: identitas adalah perimeter baru

Di jaringan kantor, firewall menjadi batas. Di cloud, siapa pun yang memegang kredensial yang benar bisa memanggil API dari mana saja. Jadi batasnya adalah **identitas**.

### Akun root

Akun root (di AWS, email yang dipakai saat mendaftar) punya hak penuh dan tidak bisa dibatasi.

| Aturan | Alasan |
|:---|:---|
| Aktifkan MFA di akun root | Password saja tidak cukup untuk akun yang bisa menghapus semuanya |
| Jangan buat access key untuk root | Key root yang bocor = seluruh akun hilang |
| Jangan pakai root untuk pekerjaan harian | Buat user atau role admin terpisah |

### Least privilege

Berikan izin sekecil mungkin yang masih cukup untuk pekerjaannya. Bandingkan dua policy ini:

```json
{ "Effect": "Allow", "Action": "*", "Resource": "*" }
```

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::laporan-keuangan/*"
}
```

Policy pertama memberi izin melakukan apa saja terhadap apa saja. Policy kedua hanya boleh membaca file di satu bucket. Kalau kredensial dengan policy kedua bocor, kerugiannya terbatas pada satu bucket itu.

### Role lebih baik daripada access key

| | Access key | Role |
|:---|:---|:---|
| Masa berlaku | Permanen sampai dihapus | Sementara, biasanya 1 jam |
| Disimpan di mana | Sering di file, kode, atau variabel environment | Diberikan otomatis ke server atau layanan |
| Kalau bocor | Bisa dipakai bertahun-tahun | Kedaluwarsa sendiri |

Aplikasi yang berjalan di EC2, Lambda, atau Kubernetes sebaiknya memakai role. Access key permanen hanya untuk kasus yang benar-benar tidak bisa memakai role.

Pemeriksaan cepat dengan AWS CLI (hanya membaca, tidak mengubah apa pun):

```bash
aws iam get-account-summary --query 'SummaryMap.AccountMFAEnabled'   # 1 = root sudah pakai MFA
aws iam generate-credential-report && aws iam get-credential-report \
  --query Content --output text | base64 -d | cut -d, -f1,8,9,10     # user, MFA aktif, key aktif, terakhir dirotasi
```

## 4. Penyimpanan: bucket yang tidak sengaja publik

Bucket penyimpanan yang dibuka ke publik adalah salah satu penyebab kebocoran data paling sering. Biasanya ada yang membuka akses "sebentar saja" untuk berbagi file, lalu lupa menutupnya.

Pertahanan di AWS:

| Kontrol | Fungsi |
|:---|:---|
| S3 Block Public Access (tingkat akun) | Menolak setiap pengaturan yang membuat bucket publik, di semua bucket |
| Enkripsi default (SSE-S3 atau SSE-KMS) | Data tersimpan dalam keadaan terenkripsi |
| Versioning + Object Lock | Melindungi dari penghapusan dan ransomware |
| Pre-signed URL | Berbagi satu file dengan link yang kedaluwarsa, tanpa membuka bucket |

```bash
aws s3control get-public-access-block --account-id 111122223333   # semua nilai harus true
aws s3api get-bucket-policy-status --bucket nama-bucket            # IsPublic harus false
```

Padanannya: di Azure, matikan "Allow Blob public access" di storage account. Di GCP, aktifkan "Public access prevention" di bucket.

## 5. Jaringan: security group dan metadata service

### Security group

Security group adalah firewall di depan server cloud. Aturan paling berbahaya adalah membuka port administrasi ke seluruh internet:

```text
Inbound  TCP 22    0.0.0.0/0   ← SSH terbuka ke semua orang
Inbound  TCP 3389  0.0.0.0/0   ← RDP terbuka ke semua orang
Inbound  TCP 3306  0.0.0.0/0   ← database terbuka ke semua orang
```

`0.0.0.0/0` artinya semua alamat IPv4 (lihat notasi CIDR di [LC-040](../../networking/id/IP%20Addressing%20%26%20Subnetting.md)). Server dengan SSH terbuka akan menerima ribuan percobaan login dalam beberapa jam. Untuk administrasi, pakai layanan seperti AWS Systems Manager Session Manager atau bastion yang dibatasi IP kantor.

```bash
# Cari security group yang membuka sesuatu ke 0.0.0.0/0
aws ec2 describe-security-groups \
  --filters Name=ip-permission.cidr,Values=0.0.0.0/0 \
  --query 'SecurityGroups[].{ID:GroupId,Name:GroupName}'
```

### Metadata service

Setiap server cloud bisa bertanya tentang dirinya sendiri ke alamat khusus `169.254.169.254`. Salah satu yang bisa diambil dari sana adalah kredensial sementara milik role server itu.

Masalahnya muncul kalau aplikasi di server itu punya celah SSRF ([LC-050](../../web/Vulnerabilities/id/4.%20Server-Side%20Request%20Forgery%20%28SSRF%29.md)). Penyerang bisa menyuruh aplikasi meminta alamat itu dan mendapatkan kredensial role-nya. Kasus kebocoran data bank besar di tahun 2019 berawal dari pola ini.

Pertahanannya adalah **IMDSv2**, yang mewajibkan token sesi dari request PUT terlebih dahulu. Request GET biasa hasil SSRF tidak bisa mendapatkan token itu.

```bash
aws ec2 modify-instance-metadata-options --instance-id i-0abc123 \
  --http-tokens required --http-endpoint enabled
```

## 6. Secret dan access key

Access key yang tidak sengaja ikut ter-commit ke repositori Git publik bisa ditemukan bot dalam hitungan menit, lalu dipakai, misalnya, untuk menyewa server mining kripto atas tagihanmu.

| Jangan | Lakukan |
|:---|:---|
| Menulis access key di kode | Pakai role, atau secret manager (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager) |
| Menyimpan `.env` di repositori | Masukkan `.env` ke `.gitignore` ([LC-002](../../basics/id/Git%20%E2%80%94%20Version%20Control%20System.md)) |
| Membiarkan key lama tetap aktif | Rotasi key secara rutin, hapus yang tidak dipakai |

Kalau key sudah terlanjur ter-commit, **menghapus commit tidak cukup**, karena salinannya mungkin sudah diambil. Langkah yang benar: nonaktifkan key itu di konsol, buat key baru, lalu periksa CloudTrail untuk melihat apa yang sudah dilakukan dengan key lama.

Mencegah kebocoran sebelum terjadi:

```bash
gitleaks detect --source . -v          # pindai repositori untuk secret
gitleaks protect --staged              # pakai sebagai pre-commit hook
```

## 7. Logging: siapa melakukan apa, kapan

Setiap aksi di cloud adalah panggilan API, dan panggilan API bisa dicatat. Ini keuntungan besar dibanding server fisik.

| Penyedia | Audit log | Deteksi ancaman bawaan |
|:---|:---|:---|
| AWS | CloudTrail | GuardDuty |
| Azure | Activity Log, Entra ID sign-in logs | Microsoft Defender for Cloud |
| GCP | Cloud Audit Logs | Security Command Center |

Contoh satu event CloudTrail (diringkas):

```json
{
  "eventTime": "2026-10-18T02:14:09Z",
  "eventName": "PutBucketPolicy",
  "userIdentity": { "type": "IAMUser", "userName": "deploy-bot" },
  "sourceIPAddress": "198.51.100.23",
  "requestParameters": { "bucketName": "backup-pelanggan" }
}
```

Pastikan:

1. CloudTrail aktif di **semua region**, bukan hanya region yang kamu pakai. Penyerang suka memakai region yang tidak diawasi.
2. Log disimpan di bucket terpisah yang tidak bisa dihapus oleh admin biasa.
3. Ada alert untuk event berisiko seperti `ConsoleLogin` tanpa MFA, `StopLogging`, `DeleteTrail`, `PutBucketPolicy`, `CreateAccessKey`, dan `AuthorizeSecurityGroupIngress` ke `0.0.0.0/0`.

```bash
aws cloudtrail describe-trails --query 'trailList[].{Name:Name,MultiRegion:IsMultiRegionTrail}'
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=ConsoleLogin --max-results 5
```

Log cloud ini bisa dikirim ke SIEM yang sama dengan log lain ([LC-072](../../blue-team/id/1.%20SOC%20%26%20Log%20Analysis.md)).

## 8. Mengaudit akun cloud

Mengecek ratusan pengaturan secara manual tidak realistis. Ada standar dan tool gratis untuk itu.

| Tool atau standar | Fungsi |
|:---|:---|
| CIS Foundations Benchmark (AWS, Azure, GCP) | Daftar pengaturan aman yang diakui industri, lengkap dengan cara mengeceknya |
| Prowler | Tool open source yang menjalankan ratusan pemeriksaan, termasuk CIS, di AWS, Azure, dan GCP |
| ScoutSuite | Tool open source yang membuat laporan HTML dari konfigurasi akun cloud |
| AWS Security Hub / Defender for Cloud / Security Command Center | Versi bawaan penyedia |

```bash
pip install prowler
prowler aws --compliance cis_3.0_aws     # butuh kredensial read-only (policy SecurityAudit)
# Hasil: daftar PASS / FAIL per pemeriksaan, plus laporan HTML dan CSV
```

Jalankan audit memakai akun dengan izin **read-only** (policy `SecurityAudit` di AWS). Audit tidak perlu, dan tidak boleh, punya izin untuk mengubah apa pun.

Urutan perbaikan yang masuk akal:

1. Akun root: MFA dan tanpa access key.
2. Audit log aktif di semua region.
3. Tidak ada bucket atau database publik.
4. Tidak ada port administrasi terbuka ke `0.0.0.0/0`.
5. Access key lama dirotasi atau diganti role.
6. IMDSv2 diwajibkan di semua server.

## 9. Latihan

### Task 1: konsep

1. Di model IaaS, siapa yang bertanggung jawab memasang patch OS: penyedia atau pelanggan?
2. Dua hal apa yang selalu menjadi tanggung jawab pelanggan di semua model?
3. Kenapa role lebih aman daripada access key permanen?
4. Apa yang dicegah oleh IMDSv2?

<details><summary>Kunci jawaban</summary>

1. Pelanggan.
2. Data, serta identitas dan akses.
3. Kredensial role bersifat sementara dan kedaluwarsa sendiri, sedangkan access key berlaku sampai dihapus dan sering tersimpan di file atau kode.
4. Pencurian kredensial role dari metadata service lewat SSRF, karena request harus diawali PUT untuk mendapatkan token sesi.

</details>

### Task 2: baca event CloudTrail

```text
02:10:41  ConsoleLogin            user=intern-03  MFAUsed=No   src=203.0.113.50  result=Success
02:12:05  CreateAccessKey         user=intern-03  target=intern-03
02:13:30  ListBuckets             user=intern-03  (pakai access key baru)
02:14:09  PutBucketPolicy         user=intern-03  bucket=backup-pelanggan  Principal="*"
02:20:55  StopLogging             user=intern-03  trail=main-trail
```

1. Sebutkan tiga hal yang mencurigakan.
2. Apa arti `Principal="*"` di policy bucket?
3. Kenapa event terakhir sangat mengkhawatirkan?
4. Apa tiga langkah pertama yang kamu lakukan sebagai responder?

<details><summary>Kunci jawaban</summary>

1. Login tanpa MFA pada jam 2 pagi, akun magang langsung membuat access key baru, bucket backup dibuat publik, dan logging dimatikan.
2. Siapa pun, termasuk orang yang tidak punya akun AWS, diberi akses ke bucket itu.
3. Penyerang berusaha menghapus jejak. Semua yang terjadi setelah 02:20:55 tidak lagi tercatat di trail itu.
4. Nonaktifkan access key dan sesi `intern-03`, aktifkan kembali logging, lalu kembalikan policy bucket dan periksa log akses S3 untuk melihat apakah data sudah diunduh. Setelah itu baru analisis bagaimana password `intern-03` bisa bocor.

</details>

### Task 3: audit akunmu sendiri

Di akun AWS Free Tier milikmu sendiri:

1. Aktifkan MFA di akun root.
2. Buat user atau role terpisah dengan policy `SecurityAudit`.
3. Jalankan Prowler dengan pemeriksaan CIS, lalu catat lima temuan FAIL dengan tingkat keparahan tertinggi.
4. Perbaiki satu temuan, jalankan ulang, dan pastikan statusnya berubah menjadi PASS.

<details><summary>Contoh perintah</summary>

```bash
aws iam create-role --role-name auditor --assume-role-policy-document file://trust.json
aws iam attach-role-policy --role-name auditor --policy-arn arn:aws:iam::aws:policy/SecurityAudit
prowler aws --compliance cis_3.0_aws --severity critical high
```

</details>
