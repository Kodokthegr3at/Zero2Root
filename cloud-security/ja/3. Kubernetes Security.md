## 1. Kubernetesを個別に学ぶ理由

コンテナ ([LC-030](../../linux/ja/23.%20Containerization.md)) にはそれ自体のリスクがある。Kubernetesはさらに層を加える。クラスター内のあらゆるものを作成・削除できるAPIサーバー、Podごとのアイデンティティ、そして既定ではすべてのPodが互いに通信できるネットワークだ。

Kubernetesの設定ミスは、1台のサーバーよりも被害が大きくなりやすい:

| 誤り | 結果 |
|:---|:---|
| APIサーバーやダッシュボードを認証なしでインターネットに公開 | 誰でもクラスターでコンテナを動かせる。暗号資産マイニングによく使われる |
| `privileged`で動くPod | コンテナが自分の動いているノードを乗っ取れる |
| 既定のサービスアカウントに広い権限 | 一つのアプリケーションが侵害されるとクラスター全体を操作される |
| ネットワークポリシーがない | 一つのPodに入った攻撃者が、別の名前空間のデータベースに届く |
| Secretが暗号化されず、多くの人が読める | データベースやAPIの認証情報も漏れる |

## 2. 簡単なアーキテクチャと4Cモデル

```
 kubectl / CI ──► API server ──► etcd (Secretを含むクラスターの全状態)
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
        Node 1     Node 2     Node 3
        kubelet    kubelet    kubelet
        [pod][pod] [pod]      [pod][pod]
```

すべての変更は**APIサーバー**を通る。だから、誰がAPIサーバーと通信でき、何をしてよいのかが、最も重要なセキュリティの問いになる。

Kubernetesのドキュメントは**4C**モデルを使う。各層の安全性は、その外側の層の安全性を超えられない:

| 層 | 対策の例 |
|:---|:---|
| Cloud | IAM、VPCのネットワーク、ノードへのアクセス (LC-077、LC-081) |
| Cluster | RBAC、アドミッション制御、etcdの暗号化、監査ログ |
| Container | スキャン済みのイメージ、非rootユーザー、最小限のケーパビリティ |
| Code | 安全なアプリケーション、スキャン済みの依存関係 (LC-078) |

## 3. APIサーバーへのアクセスとRBAC

APIサーバーへのリクエストは三つの段階を通る。**認証** (あなたは誰か)、**認可** (許されているか。通常はRBAC)、**アドミッション** (このオブジェクトはルールに従っているか)。

RBACには4種類のオブジェクトがある:

| オブジェクト | 範囲 | 内容 |
|:---|:---|:---|
| Role | 一つの名前空間 | 権限の一覧 |
| ClusterRole | クラスター全体 | 権限の一覧 |
| RoleBinding | 一つの名前空間 | RoleやClusterRoleをユーザー、グループ、サービスアカウントに結び付ける |
| ClusterRoleBinding | クラスター全体 | ClusterRoleをクラスター全体の主体に結び付ける |

範囲の狭いRole:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-pods
  namespace: shop
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
```

クラスター管理者と同等に扱うべき権限:

| 権限 | 危険な理由 |
|:---|:---|
| `*`に対する`*` | すべてのリソースへのすべての操作 |
| `pods` (やDeployment、Jobなど) の`create` | 別のサービスアカウントを付けたPodや、privilegedなPodを作れる |
| `secrets`の`get` / `list` | その名前空間のサービスアカウントのトークンを含む、すべての認証情報を読める |
| `pods/exec`の`create` | どのコンテナの中でもコマンドを実行できる |
| ロールに対する`escalate`、`bind` | 自分により高い権限を与えられる |
| users、groups、serviceaccountsに対する`impersonate` | 別のIDとして振る舞える |
| `nodes/proxy`の`get` | kubeletと直接通信し、一部の制御を回避できる |
| ClusterRole `cluster-admin`へのバインディング | 完全な管理者 |

IDの権限を確認する:

```bash
kubectl auth can-i --list -n shop --as=system:serviceaccount:shop:default
kubectl auth can-i create pods -n shop --as=system:serviceaccount:shop:web
kubectl get clusterrolebindings -o wide | grep cluster-admin
```

## 4. サービスアカウントとトークン

すべてのPodはいずれかのサービスアカウントで動く。指定しなければ、その名前空間の`default`サービスアカウントが使われ、既定ではそのトークンがPod内の`/var/run/secrets/kubernetes.io/serviceaccount/`にマウントされる。

Pod内のアプリケーションが侵害されると、攻撃者はそのトークンを手に入れ、そのサービスアカウントの権限でAPIサーバーを呼び出せる。

| 実践 | 方法 |
|:---|:---|
| 必要でなければトークンをマウントしない | Podかサービスアカウントで`automountServiceAccountToken: false` |
| アプリケーションごとに一つのサービスアカウント | `default`を使わず、アプリケーション間で共有しない |
| 最小限の権限 | ほとんどのWebアプリケーションはAPIサーバーと通信する必要がない |
| 短命なトークン | 最近のKubernetesは期限切れになるprojectedトークンを使う。期限のない古いSecret形式のトークンは避ける |

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
  namespace: shop
automountServiceAccountToken: false
```

## 5. Podのセキュリティ

`securityContext`は、コンテナが動いているノードに対してどれだけの力を持つかを決める。

安全なPod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: shop
spec:
  serviceAccountName: web
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: web
      image: registry.example.internal/shop/web:1.4.2
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      resources:
        limits: { cpu: "500m", memory: "256Mi" }
```

危険な設定:

| 設定 | 結果 |
|:---|:---|
| `privileged: true` | コンテナがノードの持つほぼすべてのアクセス権を得る |
| `/`、`/etc`、コンテナランタイムのソケットへの`hostPath` | コンテナがノードのファイルを読み書きでき、Kubernetesの管理外で新しいコンテナを起動することもできる |
| `hostNetwork`、`hostPID`、`hostIPC` | コンテナがノードのネットワークやプロセスを共有する |
| ケーパビリティ`SYS_ADMIN`、`NET_ADMIN` | 多くの操作でroot相当の力 |
| 制限なしにrootで動く | アプリケーションの欠陥がそのままコンテナ内のrootになる |
| `resources.limits`がない | 一つのPodがノードのCPUとメモリを使い果たせる |

## 6. Pod Security Standards

Kubernetesには、Podのセキュリティ基準が3段階用意されていて、組み込みの**Pod Security Admission**で強制される:

| レベル | 内容 |
|:---|:---|
| Privileged | 制限なし。本当に必要なシステムコンポーネントだけに使う |
| Baseline | privileged、hostPath、hostNetwork、危険なケーパビリティなど、明らかに危険なものを禁止する |
| Restricted | Baselineに加えて、非root、`allowPrivilegeEscalation: false`、ALLケーパビリティの削除、seccompを必須にする |

名前空間のラベルで有効にする:

```bash
kubectl label namespace shop \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/warn=restricted
```

安全な導入の手順: まず`warn`と`audit`のモードを入れ、ルールに違反するワークロードを直してから`enforce`を有効にする。

## 7. ネットワークポリシー

既定では、**すべてのPodが**名前空間をまたいで**すべてのPodと通信できる**。NetworkPolicyでこれを制限できる。ただし、CalicoやCiliumのように、使っているネットワークプラグイン (CNI) が対応している必要がある。

まずすべてを拒否し、必要なものだけを開ける:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: shop
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-to-db
  namespace: shop
spec:
  podSelector:
    matchLabels: { app: db }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: web }
      ports:
        - protocol: TCP
          port: 5432
```

DNS (CoreDNSへのポート53) の送信を許可するのを忘れないこと。これがないとアプリケーションはホスト名を解決できない。インターネットへの送信も制限し、侵害されたPodが自由にデータを送り出したりツールをダウンロードしたりできないようにする。

## 8. Secret

KubernetesのSecretは**base64でエンコードされているだけ**で、暗号化されてはいない。APIでSecretを読める人や、etcdを直接読める人は、その中身を手に入れる。

```bash
kubectl get secret db-cred -n shop -o jsonpath='{.data.password}' | base64 -d
```

| 対策 | 説明 |
|:---|:---|
| etcdの保存時暗号化 | KMSプロバイダーを使って`EncryptionConfiguration`を設定する。クラウドのマネージドサービスでは、KMSキーによるSecretの暗号化を有効にする |
| SecretへのRBACを絞る | すべてのSecretを`list`する必要がある人やアプリケーションはほとんどいない |
| 外部のシークレットマネージャー | AWS Secrets Manager、Azure Key Vault、GCP Secret Manager、Vaultを、External Secrets OperatorやSecrets Store CSI Driverでつなぐ |
| SecretをGitに置かない | Secretを含むマニフェストをコミットすれば漏えいと同じ。どうしてもGitに置くならSealed SecretsかSOPSを使う |

## 9. イメージのサプライチェーンとアドミッション制御

クラスターで動くイメージは、信頼できる出所のもので、スキャン済みでなければならない。Trivyによるスキャンは[LC-078](../../devsecops/ja/1.%20DevSecOps%20Fundamentals.md)で扱った。クラスターでは、こうしたルールをアドミッションコントローラーで強制する。

| ルール | 例 |
|:---|:---|
| 承認済みのレジストリだけ | `registry.example.internal`以外のイメージを拒否する |
| `latest`タグを使わない | バージョンのタグかダイジェストを必須にする |
| イメージは署名済みであること | cosignの署名を検証する |
| `resources.limits`と所有者のラベルを必須に | ワークロードを追跡でき、ノードを使い果たさないようにする |

よく使われるツール: **Kyverno** (ルールをKubernetesのYAMLで書く) と**OPA Gatekeeper** (ルールをRegoで書く)。Kyvernoのルールの例:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: internal-registry-only
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-registry
      match:
        any:
          - resources:
              kinds: ["Pod"]
      validate:
        message: "Images must come from registry.example.internal"
        pattern:
          spec:
            containers:
              - image: "registry.example.internal/*"
```

## 10. クラウドのKubernetes: EKS、AKS、GKE

マネージドのKubernetesサービスはコントロールプレーンを運用してくれるが、責任共有 ([LC-077](1.%20Cloud%20Security%20Fundamentals.md)) は変わらない。ワークロードの設定、RBAC、ネットワークは引き続き利用者の仕事だ。

| 項目 | すべきこと |
|:---|:---|
| APIサーバーのエンドポイント | プライベートにするか、特定のIP範囲に制限する |
| Podのクラウド上のID | AWSではIRSAかEKS Pod Identity、AKSとGKEではWorkload Identity。アクセスキーをSecretに保存しない ([LC-081](2.%20Cloud%20IAM%20in%20Depth.md)) |
| ノードのメタデータサービス | Podがノードのロールを使えないようにする。EKSではIMDSv2を必須にしてホップ制限を1にし、普通のPodがメタデータのトークンを取得できないようにする |
| 管理者のアクセス | IAMとKubernetesのRBACの対応付け (EKSのアクセスエントリ、AKS向けのAzure RBAC、GKEのIAM) を最小権限で行う |
| 更新 | サポートされているKubernetesのバージョンを使い、ノードを定期的に更新する |

## 11. 監査ログとランタイム検知

### Kubernetesの監査ログ

APIサーバーはすべてのリクエストを記録できる。マネージドサービスでは、監査ログをクラウドのログサービスに送る設定を有効にする (EKSならコントロールプレーンのログをCloudWatchへ)。

アラートを設定すべき事象:

| 事象 | 理由 |
|:---|:---|
| `pods/exec`の`create` | 誰かが本番のコンテナ内でコマンドを実行している |
| `privileged`、`hostPath`、`hostPID`を持つ新しいPod | ノードを乗っ取るときのよくあるパターン |
| `cluster-admin`への新しいClusterRoleBinding | 完全な管理者権限が与えられた |
| 普段Secretを読まないサービスアカウントによるSecretの`list`や`get` | 認証情報が集められている |
| `system:anonymous`からの成功したリクエスト | 認証なしのアクセスが開いている |

### ランタイム検知

監査ログが見ているのはAPIサーバーだけだ。コンテナの中で起きていることは、**Falco** (オープンソース、eBPFベース) のようなランタイムのツールで見る:

```text
Falcoの組み込みルールの例:
  Terminal shell in container           → コンテナで対話的なシェルが開かれた
  Write below etc                       → 実行中に/etc以下のファイルが変更された
  Contact K8S API Server From Container → コンテナが想定外にAPIサーバーを呼び出した
```

これらのアラートはすべて、ほかのログと同じSIEM ([LC-072](../../blue-team/ja/1.%20SOC%20%26%20Log%20Analysis.md)) に送る。

## 13. 演習

### Task 1: 概念

1. KubernetesのSecretは既定で暗号化されているか。
2. Secretを読む権限がなくても`create pods`が危険なのはなぜか。
3. Pod Security Standardsの三つのレベルは何か。
4. KubernetesのPod間の既定のネットワークの振る舞いはどうなっているか。

<details><summary>解答</summary>

1. されていない。中身はbase64でエンコードされているだけで、保存時の暗号化を有効にする必要がある。
2. Podを作る人は、より強いサービスアカウントをそのPodに付けたり、Secretをボリュームとしてマウントしたり、privilegedなPodを作ってノードを乗っ取ったりできるから。
3. Privileged、Baseline、Restricted。
4. NetworkPolicyで制限するまで、すべてのPodが名前空間をまたいですべてのPodと通信できる。

</details>

### Task 2: Podのマニフェストを直す

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: reports
  namespace: finance
spec:
  hostNetwork: true
  containers:
    - name: reports
      image: reports:latest
      securityContext:
        privileged: true
      volumeMounts:
        - name: host
          mountPath: /host
  volumes:
    - name: host
      hostPath:
        path: /
```

問題点をすべて挙げ、安全な版を書け。このアプリケーションはデータベースを読み、PDFファイルを作るだけだ。

<details><summary>解答</summary>

問題点: `hostNetwork`、`privileged`、`hostPath: /`によるノードのファイルシステム全体のマウント、`latest`タグ、レジストリが不明なイメージ、`runAsNonRoot`なし、ケーパビリティの削除なし、リソース制限なし、既定のサービスアカウントのトークンがマウントされている。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: reports
  namespace: finance
spec:
  serviceAccountName: reports
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: reports
      image: registry.example.internal/finance/reports:2.1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: ["ALL"] }
      resources:
        limits: { cpu: "500m", memory: "512Mi" }
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}
```

ルートファイルシステムを読み取り専用にしたが、PDFの作成には一時的に書き込む場所が必要なので、`/tmp`に`emptyDir`ボリュームを用意している。

</details>

### Task 3: RBACをレビューする

```yaml
kind: Role
metadata: { name: deployer, namespace: shop }
rules:
  - apiGroups: ["", "apps"]
    resources: ["pods", "deployments", "secrets"]
    verbs: ["*"]
```

このRoleは、ショップのアプリケーションをデプロイするCIパイプラインのサービスアカウントに結び付けられている。リスクは何で、どう絞り込むか。

<details><summary>解答</summary>

リスク: パイプラインは`shop`名前空間のすべてのSecretを読み書きでき、何でも削除でき、別のサービスアカウントや任意のSecretをマウントするPodを含む、どんなPodでも作れる。パイプラインが侵害されれば、名前空間全体が乗っ取られる。

より狭い版: Deploymentの変更だけを許し、Secretへのアクセスと直接のPod作成はなくす。

```yaml
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "patch", "update"]
```

さらにアドミッションのルール (Pod Securityの`restricted`とKyverno) を加え、変更されたDeploymentでも危険なPodを動かせないようにする。

</details>

## 14. クイックリファレンス

```text
アクセス
  認証 → 認可 (RBAC) → アドミッション
  kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa>
  管理者と同等: * · create pods · get/list secrets · pods/exec · escalate/bind · impersonate · nodes/proxy

サービスアカウント
  アプリケーションごとに一つ · automountServiceAccountToken: false · 最小限の権限

安全なPod
  runAsNonRoot · allowPrivilegeEscalation: false · readOnlyRootFilesystem
  capabilities drop ALL · seccomp RuntimeDefault · resources.limits
  避ける: privileged · hostPath · hostNetwork/PID/IPC

POD SECURITY ADMISSION
  名前空間のラベル: pod-security.kubernetes.io/enforce=restricted (先にwarn/audit)

ネットワーク
  既定: すべてのPodが互いに届く → deny-allのNetworkPolicy + 必要なものだけ開ける (DNSを忘れずに)

SECRET
  base64 ≠ 暗号化 · etcdを暗号化 (KMS) · 厳しいRBAC · 外部のシークレットマネージャー

クラウド
  プライベートなAPIエンドポイント · IRSA/Pod Identity/Workload Identity · IMDSv2のホップ制限1

検知と監査
  監査ログ: pods/exec、privilegedなPod、cluster-adminのバインディング、不審なSecretの読み取り
  ランタイムはFalco · kube-bench · kubescape · trivy k8s
```
