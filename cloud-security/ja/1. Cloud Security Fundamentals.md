## 重要な用語

| 用語 | 意味 |
|:---|:---|
| IaaS、PaaS、SaaS | クラウドのサービスモデル。サーバー、プラットフォーム、完成したアプリケーションのいずれかを借りる |
| 責任共有 | セキュリティの責任をクラウド事業者と利用者でどう分けるか |
| IAM | Identity and Access Management。誰がどのリソースに何をしてよいか |
| ポリシー | 権限を記したJSON文書。例: 「バケットXを読んでよい」 |
| ロール | サービスやユーザーが一時的に引き受けるID。固定のパスワードを持たない |
| アクセスキー | コードやCLIからクラウドのAPIを呼ぶためのIDとシークレットの組 |
| バケット | オブジェクトストレージの入れ物。Amazon S3やAzureのBlobコンテナーなど |
| セキュリティグループ | クラウドのサーバーの前に置く仮想ファイアウォール |
| VPC | Virtual Private Cloud。クラウド内の自分専用のプライベートネットワーク |
| 監査ログ | すべてのAPI呼び出しの記録。AWSはCloudTrail、AzureはActivity Log、GCPはCloud Audit Logs |

## 1. クラウドは他人のコンピューター

クラウドでは、AWS、Microsoft Azure、Google Cloudなどの事業者からサーバー、ストレージ、サービスを借りる。すべてAPIで操作するので、サーバーの作成も、ポートの開放も、ファイルの共有も、コマンド一つで済む。

その手軽さがそのままリスクになる。たった一つの間違ったコマンドで、データベースが数秒のうちにインターネット全体へ公開されてしまう。クラウドのインシデント報告は毎年同じ傾向を示している。根本原因がクラウドそのものの欠陥であることはまれで、ほとんどは**設定ミス**と**認証情報の漏えい**だ。

| 事業者 | よく出てくるサービス |
|:---|:---|
| AWS | IAM、S3、EC2、VPC、CloudTrail、GuardDuty |
| Azure | Entra ID、Blob Storage、Virtual Machines、VNet、Activity Log、Defender for Cloud |
| Google Cloud | IAM、Cloud Storage、Compute Engine、VPC、Cloud Audit Logs、Security Command Center |

このレッスンでは最も広く使われているAWSを例にするが、考え方は3社とも同じだ。

## 2. 責任共有モデル

事業者は**クラウドそのもの**を守る。利用者は**クラウドに置いたもの**を守る。

| | IaaS (EC2) | PaaS (RDS) | SaaS (Microsoft 365) |
|:---|:---|:---|:---|
| データとユーザーのアクセス | 利用者 | 利用者 | 利用者 |
| アプリケーション | 利用者 | 利用者 | 事業者 |
| OSとパッチ | 利用者 | 事業者 | 事業者 |
| 仮想ネットワーク | 利用者 | 共有 | 事業者 |
| ハードウェアと建物 | 事業者 | 事業者 | 事業者 |

どのモデルでも、**必ず**利用者の責任になるものが二つある:

1. **データ**: 誰が読めるのか、暗号化されているのか。
2. **IDとアクセス**: どんなアカウントがあり、何が許可され、MFAを使っているか。

よくある誤解: 「AWSを使っているから安全なはずだ」。AWSはデータセンターを守るが、利用者がバケットを公開に設定すれば、AWSは言われたとおり誰にでもそれを配信する。

## 3. IAM: IDが新しい境界になる

社内ネットワークではファイアウォールが境界になる。クラウドでは、正しい認証情報を持っていれば、どこからでもAPIを呼べる。つまり境界は**ID**だ。

### ルートアカウント

ルートアカウント (AWSでは登録に使ったメールアドレス) は完全な権限を持ち、制限できない。

| ルール | 理由 |
|:---|:---|
| ルートでMFAを有効にする | すべてを削除できるアカウントにパスワードだけでは足りない |
| ルートのアクセスキーを作らない | ルートのキーが漏れれば、アカウント全体を失う |
| 日常業務でルートを使わない | 別の管理者ユーザーやロールを作る |

### 最小権限

仕事に必要な最小限の権限だけを与える。次の二つのポリシーを比べてみる:

```json
{ "Effect": "Allow", "Action": "*", "Resource": "*" }
```

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::finance-reports/*"
}
```

一つ目は、あらゆるものに対して何でもできるポリシーだ。二つ目は、一つのバケットのファイルを読むことしかできない。二つ目のポリシーを持つ認証情報が漏れても、被害はそのバケットだけで済む。

### アクセスキーよりロール

| | アクセスキー | ロール |
|:---|:---|:---|
| 有効期間 | 削除するまで永続 | 一時的。通常は1時間 |
| 保存場所 | ファイル、コード、環境変数に置かれがち | サーバーやサービスに自動で渡される |
| 漏れた場合 | 何年も使われうる | 自動で失効する |

EC2、Lambda、Kubernetesで動くアプリケーションはロールを使うべきだ。永続的なアクセスキーは、どうしてもロールを使えない場合だけにする。

AWS CLIでの簡単な確認 (読み取りのみで、何も変更しない):

```bash
aws iam get-account-summary --query 'SummaryMap.AccountMFAEnabled'   # 1 = ルートがMFAを使用中
aws iam generate-credential-report && aws iam get-credential-report \
  --query Content --output text | base64 -d | cut -d, -f1,8,9,10     # ユーザー、MFA有効、キー有効、最終ローテーション
```

## 4. ストレージ: うっかり公開されたバケット

公開されたストレージバケットは、データ漏えいの最も多い原因の一つだ。たいていは誰かがファイルを共有するために「少しの間だけ」公開し、そのまま閉じ忘れる。

AWSでの対策:

| 制御 | 目的 |
|:---|:---|
| S3ブロックパブリックアクセス (アカウント単位) | バケットを公開にする設定を、すべてのバケットで拒否する |
| デフォルト暗号化 (SSE-S3またはSSE-KMS) | データを暗号化して保存する |
| バージョニング + Object Lock | 削除やランサムウェアから守る |
| 署名付きURL | バケットを公開せず、期限付きのリンクで1ファイルだけ共有する |

```bash
aws s3control get-public-access-block --account-id 111122223333   # すべての値がtrueであるべき
aws s3api get-bucket-policy-status --bucket bucket-name            # IsPublicはfalseであるべき
```

対応する設定: Azureではストレージアカウントの「Blobのパブリックアクセスを許可する」をオフにする。GCPではバケットで「公開アクセス防止」を有効にする。

## 5. ネットワーク: セキュリティグループとメタデータサービス

### セキュリティグループ

セキュリティグループは、クラウドのサーバーの前にあるファイアウォールだ。最も危険なのは、管理用のポートをインターネット全体に開くルールだ:

```text
Inbound  TCP 22    0.0.0.0/0   ← SSHが全員に開いている
Inbound  TCP 3389  0.0.0.0/0   ← RDPが全員に開いている
Inbound  TCP 3306  0.0.0.0/0   ← データベースが全員に開いている
```

`0.0.0.0/0`はすべてのIPv4アドレスを意味する ([LC-040](../../networking/ja/IP%20Addressing%20%26%20Subnetting.md)のCIDR表記を参照)。SSHを開いたサーバーには、数時間で何千回ものログイン試行が届く。管理にはAWS Systems Manager Session Managerのようなサービスか、社内のIPに限定した踏み台サーバーを使う。

```bash
# 0.0.0.0/0に何かを開いているセキュリティグループを探す
aws ec2 describe-security-groups \
  --filters Name=ip-permission.cidr,Values=0.0.0.0/0 \
  --query 'SecurityGroups[].{ID:GroupId,Name:GroupName}'
```

### メタデータサービス

クラウドのサーバーは、特別なアドレス`169.254.169.254`で自分自身の情報を問い合わせられる。そこから取得できるものの一つに、そのサーバーのロールの一時的な認証情報がある。

問題になるのは、そのサーバー上のアプリケーションにSSRFの欠陥 ([LC-050](../../web/Vulnerabilities/ja/4.%20Server-Side%20Request%20Forgery%20%28SSRF%29.md)) がある場合だ。攻撃者はアプリケーションにそのアドレスへリクエストさせ、ロールの認証情報を手に入れられる。2019年の大手銀行のデータ漏えいは、このパターンから始まった。

対策は**IMDSv2**だ。IMDSv2では、まずPUTリクエストでセッショントークンを取得する必要がある。SSRFで作られる普通のGETリクエストでは、このトークンを得られない。

```bash
aws ec2 modify-instance-metadata-options --instance-id i-0abc123 \
  --http-tokens required --http-endpoint enabled
```

## 6. シークレットとアクセスキー

公開のGitリポジトリにうっかりコミットされたアクセスキーは、数分のうちにボットに見つかる。そして、たとえば暗号資産マイニング用のサーバーを利用者の請求で借りるのに使われる。

| してはいけない | すべきこと |
|:---|:---|
| アクセスキーをコードに書く | ロールか、シークレットマネージャー (AWS Secrets Manager、Azure Key Vault、GCP Secret Manager) を使う |
| `.env`をリポジトリに入れる | `.env`を`.gitignore`に追加する ([LC-002](../../basics/ja/Git%20%E2%80%94%20Version%20Control%20System.md)) |
| 古いキーを有効なまま放置する | キーを定期的にローテーションし、使っていないものは削除する |

キーをすでにコミットしてしまった場合、**コミットを消すだけでは足りない**。誰かがすでにコピーを取っているかもしれないからだ。正しい手順は、コンソールでそのキーを無効にし、新しいキーを作り、CloudTrailで古いキーが何に使われたかを確認することだ。

漏えいを未然に防ぐ:

```bash
gitleaks detect --source . -v          # リポジトリのシークレットをスキャンする
gitleaks protect --staged              # pre-commitフックとして使う
```

## 7. ログ: 誰が、いつ、何をしたか

クラウドでの操作はすべてAPI呼び出しであり、API呼び出しは記録できる。これは物理サーバーと比べた大きな利点だ。

| 事業者 | 監査ログ | 組み込みの脅威検知 |
|:---|:---|:---|
| AWS | CloudTrail | GuardDuty |
| Azure | Activity Log、Entra IDのサインインログ | Microsoft Defender for Cloud |
| GCP | Cloud Audit Logs | Security Command Center |

CloudTrailのイベントの例 (一部省略):

```json
{
  "eventTime": "2026-10-18T02:14:09Z",
  "eventName": "PutBucketPolicy",
  "userIdentity": { "type": "IAMUser", "userName": "deploy-bot" },
  "sourceIPAddress": "198.51.100.23",
  "requestParameters": { "bucketName": "customer-backup" }
}
```

次の点を確認する:

1. CloudTrailが、使っているリージョンだけでなく**すべてのリージョン**で有効になっている。攻撃者は誰も見ていないリージョンを好む。
2. ログは、普通の管理者が削除できない別のバケットに保存されている。
3. 危険なイベントにアラートがある。たとえばMFAなしの`ConsoleLogin`、`StopLogging`、`DeleteTrail`、`PutBucketPolicy`、`CreateAccessKey`、`0.0.0.0/0`への`AuthorizeSecurityGroupIngress`。

```bash
aws cloudtrail describe-trails --query 'trailList[].{Name:Name,MultiRegion:IsMultiRegionTrail}'
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=ConsoleLogin --max-results 5
```

クラウドのログは、ほかのログと同じSIEM ([LC-072](../../blue-team/ja/1.%20SOC%20%26%20Log%20Analysis.md)) に送れる。

## 8. クラウドアカウントを監査する

何百もの設定を手作業で確認するのは現実的ではない。そのための基準と無料のツールがある。

| ツールまたは基準 | 目的 |
|:---|:---|
| CIS Foundations Benchmark (AWS、Azure、GCP) | 業界で認められた安全な設定の一覧。それぞれの確認方法つき |
| Prowler | AWS、Azure、GCPで、CISを含む数百の確認を実行するオープンソースのツール |
| ScoutSuite | クラウドアカウントの設定からHTMLレポートを作るオープンソースのツール |
| AWS Security Hub / Defender for Cloud / Security Command Center | 事業者の組み込み版 |

```bash
pip install prowler
prowler aws --compliance cis_3.0_aws     # 読み取り専用の認証情報が必要 (SecurityAuditポリシー)
# 出力: 確認ごとのPASS / FAILと、HTMLおよびCSVのレポート
```

監査は**読み取り専用**のアカウント (AWSでは`SecurityAudit`ポリシー) で行う。監査に変更の権限は必要なく、持たせるべきでもない。

修正の順序の目安:

1. ルートアカウント: MFAあり、アクセスキーなし。
2. すべてのリージョンで監査ログが有効。
3. 公開されたバケットやデータベースがない。
4. 管理用ポートが`0.0.0.0/0`に開いていない。
5. 古いアクセスキーをローテーションするか、ロールに置き換える。
6. すべてのサーバーでIMDSv2を必須にする。

## 9. 演習

### Task 1: 概念

1. IaaSモデルで、OSのパッチ適用の責任は事業者と利用者のどちらにあるか。
2. どのモデルでも必ず利用者の責任になる二つのものは何か。
3. ロールが永続的なアクセスキーより安全な理由は何か。
4. IMDSv2は何を防ぐか。

<details><summary>解答</summary>

1. 利用者。
2. データと、IDおよびアクセス。
3. ロールの認証情報は一時的で自動的に失効するが、アクセスキーは削除するまで有効で、ファイルやコードに保存されがちだから。
4. SSRFを使ったメタデータサービスからのロール認証情報の窃取。リクエストはまずPUTでセッショントークンを得る必要があるため。

</details>

### Task 2: CloudTrailのイベントを読む

```text
02:10:41  ConsoleLogin            user=intern-03  MFAUsed=No   src=203.0.113.50  result=Success
02:12:05  CreateAccessKey         user=intern-03  target=intern-03
02:13:30  ListBuckets             user=intern-03  (新しいアクセスキーを使用)
02:14:09  PutBucketPolicy         user=intern-03  bucket=customer-backup  Principal="*"
02:20:55  StopLogging             user=intern-03  trail=main-trail
```

1. 不審な点を三つ挙げよ。
2. バケットポリシーの`Principal="*"`は何を意味するか。
3. 最後のイベントが特に心配な理由は何か。
4. 対応者として最初に行う三つの手順は何か。

<details><summary>解答</summary>

1. 午前2時のMFAなしのログイン、インターンのアカウントがすぐに新しいアクセスキーを作成したこと、バックアップ用バケットが公開されたこと、ログが停止されたこと。
2. AWSアカウントを持たない人も含め、誰にでもそのバケットへのアクセスが許可される。
3. 攻撃者が痕跡を消そうとしている。02:20:55以降の操作は、そのトレイルにはもう記録されない。
4. `intern-03`のアクセスキーとセッションを無効にし、ログを再び有効にする。次にバケットポリシーを元に戻し、S3のアクセスログでデータがダウンロードされたかを確認する。そのあとで、`intern-03`のパスワードがどう漏れたかを分析する。

</details>

### Task 3: 自分のアカウントを監査する

自分が所有するAWS無料利用枠のアカウントで:

1. ルートアカウントでMFAを有効にする。
2. `SecurityAudit`ポリシーを付けた別のユーザーかロールを作る。
3. CISの確認でProwlerを実行し、重大度の高いFAILを五つ記録する。
4. 一つを修正して再実行し、その状態がPASSに変わることを確認する。

<details><summary>コマンドの例</summary>

```bash
aws iam create-role --role-name auditor --assume-role-policy-document file://trust.json
aws iam attach-role-policy --role-name auditor --policy-arn arn:aws:iam::aws:policy/SecurityAudit
prowler aws --compliance cis_3.0_aws --severity critical high
```

</details>

### 無料のラボ

| 提供元 | 内容 | 費用 |
|:---|:---|:---|
| AWS無料利用枠 | 練習用のAWSアカウント。多くのサービスが一定の範囲まで無料 | 無料 (予算アラートを設定する) |
| flaws.cloudとflaws2.cloud | AWSの設定ミスの演習。flaws2には防御側専用のコースがある | 無料 |
| Prowler | オープンソースのクラウドセキュリティ監査 | 無料 |
| CIS Benchmarks | AWS、Azure、GCPの安全な設定ガイド | 無料 (PDFをダウンロード) |
| AWS Skill Builder: Security Fundamentals | AWSによる入門コース | 無料 |

始める前に練習用アカウントに**予算アラート**を設定しておくこと。消し忘れたリソースで請求額に驚かずに済む。

## 10. クイックリファレンス

```text
責任共有
  事業者: ハードウェア、建物、基盤サービス
  利用者 (常に): データ + IDとアクセス

IAM
  ルート: MFAあり、アクセスキーなし、日常では使わない
  最小権限 · アクセスキーよりロール · 全ユーザーにMFA

ストレージ
  ブロックパブリックアクセス (AWS) · パブリックBlobを無効化 (Azure) · 公開アクセス防止 (GCP)

ネットワーク
  22/3389/DBを0.0.0.0/0に開かない · IMDSv2を必須に

ログ
  全リージョンでCloudTrail · 別の場所に保存 · アラート: StopLogging、DeleteTrail、
  MFAなしのConsoleLogin、CreateAccessKey、PutBucketPolicy

監査
  prowler aws --compliance cis_3.0_aws  (読み取り専用アカウント: SecurityAudit)
```
