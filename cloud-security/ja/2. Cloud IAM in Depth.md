## 重要な用語

| 用語 | 意味 |
|:---|:---|
| プリンシパル | アクセスを求める主体。ユーザー、ロール、サービス、別のアカウント |
| アイデンティティベースのポリシー | ユーザー、グループ、ロールに付けるポリシー |
| リソースベースのポリシー | S3のバケットポリシーのように、リソースに付けるポリシー |
| 信頼ポリシー | ロールに付けるリソースベースのポリシーで、誰がそのロールを引き受けられるかを決める |
| 条件 (Condition) | MFAの必須化や特定の組織への所属など、ポリシーの追加の条件 |
| SCP / RCP | サービスコントロールポリシー / リソースコントロールポリシー。AWS Organizations全体で、プリンシパル / リソースが持てる権限の上限 |
| アクセス許可の境界 | 一つのユーザーやロールが持てる権限の上限 |
| 明示的な拒否 | `"Effect": "Deny"`の文。常に優先される |
| 混乱した代理 (confused deputy) | 信頼されたサービスがだまされ、権限のない者のために操作を行ってしまう問題 |
| OIDCフェデレーション | GitHub ActionsなどのIDプロバイダーのトークンを使い、永続的なキーなしでサインインすること |

## 1. IAMを詳しく学ぶ理由

[LC-077](1.%20Cloud%20Security%20Fundamentals.md)では、クラウドではIDが境界になることを学んだ。このレッスンでは詳細を扱う。IAMの誤りは見えにくいからだ。安全に見えるポリシーが回り道で管理者権限を与えてしまうこともあるし、少し緩い信頼ポリシーがアカウントを外部に開いてしまうこともある。

このレッスンで学ぶ三つのこと:

1. ポリシーを読み、その結果を正確に予測する。
2. 名前が無害に聞こえても、危険な権限を見抜く。
3. 利用データをもとに、権限を段階的に減らす。

例はAWSを使い、AzureとGoogle Cloudには専用の節を設ける。

## 2. ポリシーの構造

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadReportsWithMFA",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::finance-reports",
        "arn:aws:s3:::finance-reports/*"
      ],
      "Condition": {
        "Bool": { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}
```

| 要素 | 意味 |
|:---|:---|
| `Effect` | `Allow`か`Deny` |
| `Action` | API操作。`サービス:アクション名`の形式。ワイルドカード`*`はすべてを意味する |
| `Resource` | 対象のARN。`s3:ListBucket`はバケットに、`s3:GetObject`はオブジェクト (`/*`) に適用される |
| `Condition` | 追加の条件。この例ではMFAを使ったセッションの場合だけ適用される |
| `Principal` | リソースベースのポリシーと信頼ポリシーにだけある。誰に許可するか |

セキュリティでよく使う条件キー:

| キー | 目的 |
|:---|:---|
| `aws:MultiFactorAuthPresent` | MFAを必須にする |
| `aws:SourceIp` | 特定のIP範囲からだけ許可する |
| `aws:PrincipalOrgID` | 自分のAWS組織のプリンシパルだけに許可する |
| `aws:SourceAccount`、`aws:SourceArn` | AWSのサービスが自分の代わりに動くときの、混乱した代理問題を防ぐ |
| `sts:ExternalId` | 第三者が自分のロールを使うときの、混乱した代理問題を防ぐ |
| `aws:RequestedRegion` | 使ってよいリージョンを制限する |

## 3. AWSが「許可」か「拒否」かを決める方法

APIリクエストは、おおむね次の順で評価される (一つのアカウント内のリクエストの場合を簡略化):

| 順番 | 確認すること | 結果 |
|:---|:---|:---|
| 1 | いずれかのポリシーに明示的な拒否があるか | あれば**拒否** |
| 2 | 組織のSCP / RCPが許可しているか | していなければ**拒否** |
| 3 | リソースベースのポリシーがこのプリンシパルを許可しているか | していれば**許可** (例外あり) |
| 4 | アイデンティティベースのポリシーが許可しているか | していなければ**拒否** (暗黙の拒否) |
| 5 | アクセス許可の境界 (あれば) が許可しているか | していなければ**拒否** |
| 6 | セッションポリシー (あれば) が許可しているか | していなければ**拒否**、していれば**許可** |

ロールセッションやアクセス許可の境界などには例外がある。AWS IAMユーザーガイドの公式の図「Policy evaluation logic」を参照すること。

覚えておくべき三つのルール:

1. **既定は拒否。** `Allow`がなければ答えはノー。
2. **明示的な拒否は**、どの階層にあっても**常に優先される**。
3. **ガードレール (SCP、アクセス許可の境界、セッションポリシー) は権限を与えない。** 制限するだけだ。権限はアイデンティティベースかリソースベースのポリシーで与える必要がある。

推測せず、シミュレーターを使う:

```bash
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::111122223333:role/analyst \
  --action-names s3:GetObject s3:DeleteObject \
  --resource-arns arn:aws:s3:::finance-reports/q3.pdf \
  --query 'EvaluationResults[].{Action:EvalActionName,Result:EvalDecision}'
```

## 4. ガードレール: SCPとアクセス許可の境界

### サービスコントロールポリシー

SCPは、AWS Organizationsのメンバーアカウント内の**すべての**プリンシパルに適用される。そのアカウントのルートユーザーも例外ではない。どのアカウントの管理者も破れないルールを、組織として決めるための手段だ。

よく使われるSCP:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DoNotDisableAuditLogs",
      "Effect": "Deny",
      "Action": ["cloudtrail:StopLogging", "cloudtrail:DeleteTrail", "cloudtrail:UpdateTrail"],
      "Resource": "*"
    },
    {
      "Sid": "OnlyRegionsWeUse",
      "Effect": "Deny",
      "NotAction": ["iam:*", "organizations:*", "sts:*", "support:*"],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["ap-southeast-3", "ap-northeast-1"] }
      }
    }
  ]
}
```

二つ目の例は簡略化している。AWSの公式の例では、CloudFrontやRoute 53などのグローバルサービスがブロックされないよう、より多くのサービスを除外している。

一つ目のSCPがあれば、アカウントの管理者になった攻撃者でもCloudTrailを止められない (LC-077のTask 2を思い出そう)。二つ目は使っていないリージョンを閉じる。誰も見ていないリージョンは、攻撃者が暗号資産マイニング用のサーバーを動かすのに好んで使う。

注意: SCPは組織の管理アカウントには適用されない。管理アカウントでワークロードを動かさないこと。

### アクセス許可の境界

アクセス許可の境界は、一つのユーザーやロールが持てる権限の上限を決める。主な使い道は**安全な権限委任**だ。開発チームが自分たちのアプリケーション用のロールを作ってよいことにし、その代わりに新しいロールには必ず特定の境界を付けさせる。こうすれば、開発者はその境界より強いロールを作れない。

```json
{
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:AttachRolePolicy"],
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": {
    "StringEquals": { "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/AppBoundary" }
  }
}
```

## 5. アカウント間アクセスと混乱した代理問題

成熟した組織は、本番、ステージング、ログ、セキュリティなど、多くのAWSアカウントを使う。アカウント間のアクセスは**ロールの引き受け (AssumeRole)** で行う。

アカウントAがアカウントBのロールを使うには、**双方の合意**が必要だ:

| 側 | ポリシー | 内容 |
|:---|:---|:---|
| アカウントB (ロールの持ち主) | ロールの信頼ポリシー | アカウントAのプリンシパルに`sts:AssumeRole`を許可する |
| アカウントA (呼び出し側) | アイデンティティベースのポリシー | アカウントAのユーザーやロールに、アカウントBのロールへの`sts:AssumeRole`を許可する |

緩すぎる信頼ポリシーは危険な誤りだ:

```json
{ "Effect": "Allow", "Principal": { "AWS": "*" }, "Action": "sts:AssumeRole" }
```

この信頼ポリシーは、**世界中のどのAWSアカウントにも**そのロールの利用を許してしまう。特定のアカウントやロールを指定するか、`aws:PrincipalOrgID`の条件を加えて直す。

### 混乱した代理問題

たとえば、コストを監視するSaaSを使っていて、そのサービスがロール経由で自分のアカウントへのアクセスを求めているとする。そのサービスは同じAWSアカウントから何千もの顧客にサービスを提供している。同じく顧客である攻撃者が自分の設定に他人のロールのARNを入力すると、サービスがだまされ、攻撃者の求めに応じて他人のアカウントにアクセスしてしまう。

対策は**外部ID (External ID)** だ。ベンダーが顧客ごとに作る一意の値を使う:

```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::999988887777:root" },
  "Action": "sts:AssumeRole",
  "Condition": { "StringEquals": { "sts:ExternalId": "customer-7f3a91" } }
}
```

AWS自身のサービスが自分の代わりに動く場合 (SNSがバケットに書き込むなど) は、`aws:SourceAccount`か`aws:SourceArn`の条件を使う。

IAM Access Analyzerを使うと、アカウントや組織の外からアクセスできるリソースをすべて一覧にできる:

```bash
aws accessanalyzer create-analyzer --analyzer-name org-analyzer --type ORGANIZATION
aws accessanalyzer list-findings --analyzer-arn <analyzer-arn> \
  --query 'findings[?status==`ACTIVE`].{Resource:resource,Principal:principal}'
```

## 6. 実は管理者と同等の権限

名前は狭そうに見えても、持っている人が自分に大きな権限を与えられてしまう権限がある。ポリシーをレビューするときは、これらを`AdministratorAccess`と同じくらい重く扱う:

| 権限 | 危険な理由 |
|:---|:---|
| `iam:CreatePolicyVersion`、`iam:SetDefaultPolicyVersion` | 自分に付いているポリシーの中身を差し替えられる |
| `iam:AttachUserPolicy`、`iam:AttachRolePolicy`、`iam:PutUserPolicy`、`iam:PutRolePolicy` | 管理者を含むどんなポリシーでも付けられる |
| ほかのユーザーに対する`iam:CreateAccessKey`、`iam:CreateLoginProfile`、`iam:UpdateLoginProfile` | より強いユーザーの認証情報を作れる |
| `iam:UpdateAssumeRolePolicy` | 強いロールを誰が使えるかを変えられる |
| `iam:PassRole`とEC2、Lambdaなどの作成の組み合わせ | 自分より強いロールでコードを実行できる |

`iam:PassRole`には特に注意が必要だ。開発者はアプリケーションをデプロイできるように、`"Resource": "*"`の`iam:PassRole`を与えられがちだ。その結果、自分で作ったLambda関数に管理者のロールを付けられてしまう。`Resource`を特定のアプリケーション用ロールに絞る:

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } }
}
```

PMapperやCloudsplainingのようなオープンソースのツールで、自分のアカウントを分析し、こうした経路を自動で探せる。読み取り専用の認証情報で実行すること。

## 7. マシンのID: ロール、OIDC、ワークロードID

アプリケーションやパイプライン用の永続的なアクセスキーは、最もよくある漏えいの原因だ。ほとんどの場合、キーを使わない代わりの方法がある:

| コードが動く場所 | キーを使わない方法 |
|:---|:---|
| EC2 | インスタンスプロファイル (EC2用のロール) |
| Lambda、ECS | 実行ロール / タスクロール |
| EKS (Kubernetes) | IAM Roles for Service AccountsまたはEKS Pod Identity |
| GitHub Actions、GitLab CI | ロールへのOIDCフェデレーション |
| 自社のデータセンター | X.509証明書を使うIAM Roles Anywhere |

GitHub Actions用の信頼ポリシー。`sub`の条件で、一つのリポジトリと一つのブランチに限定している点に注目:

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:kodokthegr3at/zero2root-app:ref:refs/heads/main"
    }
  }
}
```

よくある誤りは、`repo:kodokthegr3at/*`のような広すぎるワイルドカードや、`sub`の条件がまったくないことだ。そうすると、フォークを含むほかのリポジトリが本番デプロイ用のロールを使えてしまう。これは[LC-078](../../devsecops/ja/1.%20DevSecOps%20Fundamentals.md)のパイプラインの保護を補う内容だ。

## 8. AzureとGoogle Cloud

### Azure

Azureには**二つの別々のロールのしくみ**がある:

| しくみ | 管理対象 | ロールの例 |
|:---|:---|:---|
| Microsoft Entra IDのロール | ディレクトリ: ユーザー、グループ、アプリケーション | 全体管理者 (Global Administrator)、特権ロール管理者 |
| Azure RBAC | リソース: VM、ストレージ、ネットワーク | 所有者 (Owner)、共同作成者 (Contributor)、閲覧者 (Reader)、ユーザーアクセス管理者 |

Azure RBACは階層になっている: **管理グループ → サブスクリプション → リソースグループ → リソース**。上の階層で与えたロールは、その下のすべてに引き継がれる。

| 実践 | 説明 |
|:---|:---|
| 日常業務でサブスクリプション単位の所有者を使わない | 所有者とユーザーアクセス管理者は、他人にアクセスを与えられる |
| Privileged Identity Management (PIM) を使う | 管理者ロールは要求したときだけ、承認と時間制限付きで有効になる |
| アプリケーションにはマネージドID | コード内のシークレットや証明書の代わりになる |
| 全体管理者は最小限に | Microsoftは5人未満を推奨している |

```bash
az role assignment list --all --query "[?roleDefinitionName=='Owner'].{who:principalName,scope:scope}" -o table
```

### Google Cloud

| ロールの種類 | 例 | 助言 |
|:---|:---|:---|
| 基本ロール | オーナー、編集者、閲覧者 | 本番では避ける。広すぎる |
| 事前定義ロール | `roles/storage.objectViewer` | 主な選択肢 |
| カスタムロール | 自分で作る | ごく特定の用途向け |

GCPでの要点:

1. **サービスアカウントキー** (JSONファイル) は、AWSのアクセスキーと同じくらい危険だ。Workload Identity Federationを使い、組織のポリシー`iam.disableServiceAccountKeyCreation`でキーの作成をブロックする。
2. `iam.serviceAccounts.actAs`と`iam.serviceAccountTokenCreator`の権限は、AWSの`iam:PassRole`に似ている。これらを持つ人は、より強いサービスアカウントとして振る舞える。
3. IAM Recommenderは、過去90日の利用をもとに権限の削減を提案する。

```bash
gcloud projects get-iam-policy PROJECT_ID \
  --flatten="bindings[].members" --filter="bindings.role:roles/owner OR bindings.role:roles/editor" \
  --format="table(bindings.role, bindings.members)"
```

## 9. 最小権限に近づける

最小限のポリシーを最初から正しく書ける人はほとんどいない。現実的なやり方は段階的に進めることだ:

1. 十分な権限を持つ管理ポリシーから始める (たとえばReadOnlyに特定の書き込み権限を加える)。
2. 数週間動かし、利用データを集める。
3. 実際の操作からポリシーを生成し、一度も使われていないものを外す。
4. 検証し、ステージングで試してから適用する。
5. 定期的に繰り返す。

役に立つツール:

| ツール | 目的 |
|:---|:---|
| IAM Access Analyzerのポリシー生成 | 実際に使われた操作をもとに、CloudTrailからポリシーの下書きを作る |
| IAM Access Analyzerの未使用アクセス | 使われていないロール、キー、権限を見つける |
| 最終アクセス情報 | プリンシパルが各サービスを最後に使った時期 |
| `validate-policy` | 付ける前に、ポリシーの誤りとセキュリティ上の警告を確認する |

```bash
aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY \
  --policy-document file://policy.json \
  --query 'findings[].{Type:findingType,Issue:issueCode}'

JOB=$(aws iam generate-service-last-accessed-details \
  --arn arn:aws:iam::111122223333:role/app-reports --query JobId --output text)
aws iam get-service-last-accessed-details --job-id "$JOB" \
  --query 'ServicesLastAccessed[?TotalAuthenticatedEntities==`0`].ServiceNamespace'
```

最後のコマンドは、そのロールに許可されているが一度も使われていないサービスを一覧にする。それらはポリシーから外す候補になる。

## 10. 危険なIAMの変更を検知する

健全なアカウントではIAMの変更はまれなので、変更は一つひとつ注意する価値がある。アラートを設定すべきCloudTrailのイベント:

| イベント | 理由 |
|:---|:---|
| `SetAsDefault=true`の`CreatePolicyVersion` | ポリシーの中身が差し替えられた。権限昇格の可能性 |
| `AdministratorAccess`を付ける`AttachUserPolicy`、`AttachRolePolicy` | 新たに管理者権限が与えられた |
| `PutUserPolicy`、`PutRolePolicy` | 新しいインラインポリシー。レビューから漏れやすい |
| `UpdateAssumeRolePolicy` | ロールを使える人が変わった |
| ほかのユーザーに対する`CreateAccessKey` | 呼び出し元以外のIDに新しい認証情報 |
| 勤務時間外の`CreateUser`に続く`CreateLoginProfile` | バックドア用のアカウント |
| 未知のアカウントからの`AssumeRole` | 想定外のアカウント間アクセス |
| 境界に対する`DeleteRolePermissionsBoundary`、`DetachRolePolicy` | ガードレールが外されている |

これらのイベントをSIEM ([LC-072](../../blue-team/ja/1.%20SOC%20%26%20Log%20Analysis.md)) に送り、検知ルールにする。GuardDutyにも、不審なIAMのパターンに対する組み込みの検出結果がある。

## 11. 演習

### Task 1: 評価結果を予測する

ロール`analyst`には二つのポリシーがある:

```json
{ "Effect": "Allow", "Action": "s3:*", "Resource": "*" }
```

```json
{ "Effect": "Deny", "Action": "s3:DeleteObject", "Resource": "arn:aws:s3:::finance-reports/*" }
```

このアカウントには、`ap-southeast-3`リージョンだけを許可するSCPも適用されている。

1. `analyst`は`finance-reports`のファイルを読めるか。
2. `analyst`は`finance-reports`のファイルを削除できるか。
3. `analyst`は`us-east-1`に新しいバケットを作れるか。

<details><summary>解答</summary>

1. 読める。`Allow s3:*`があり、`GetObject`への拒否はない (バケットが許可されたリージョンにあると仮定)。
2. 削除できない。明示的な拒否は常に優先される。
3. 作れない。SCPがリージョンを制限しており、ガードレールはアイデンティティベースのポリシーの`Allow`では越えられない。

</details>

### Task 2: 信頼ポリシーをレビューする

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" }
  }
}
```

このロールは`AdministratorAccess`を持ち、本番のデプロイに使われている。何が問題で、どう直すか。

<details><summary>解答</summary>

`sub`の条件がないため、このOIDCプロバイダーを使うGitHubのどのリポジトリのワークフローでも、このロールを使えてしまう。GitHub Actionsのトークンは、すべてのリポジトリに対して同じ発行者から出されるので、他人のリポジトリも含まれる。

修正:

1. `"token.actions.githubusercontent.com:sub": "repo:org/repo:ref:refs/heads/main"`を加える。さらに良いのは`production`環境に限定すること。
2. `AdministratorAccess`を、そのアプリケーションのデプロイに必要な権限だけに置き換える。

</details>

### Task 3: 管理者と同等の権限を見つける

開発チーム向けのポリシー:

```json
{
  "Statement": [
    { "Effect": "Allow", "Action": ["lambda:*", "logs:*"], "Resource": "*" },
    { "Effect": "Allow", "Action": "iam:PassRole", "Resource": "*" },
    { "Effect": "Allow", "Action": ["iam:Get*", "iam:List*"], "Resource": "*" }
  ]
}
```

1. 危険な権限の組み合わせはどれか。
2. 危険な文を、より安全に書き直せ。

<details><summary>解答</summary>

1. (関数の作成を含む) `lambda:*`と、`*`に対する`iam:PassRole`の組み合わせ。開発者はLambda関数を作り、管理者ロールを含む任意のロールをそれに付けて、管理者権限でコードを実行できる。
2. `PassRole`をアプリケーション用ロールとLambdaサービスだけに制限する:

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } }
}
```

さらに`app-*`のロールはアクセス許可の境界付きで作らせ、管理者権限を持つ`app-*`ロールを誰も作れないようにする。

</details>
