## Key terms

| Term | Meaning |
|:---|:---|
| Principal | The party requesting access: a user, role, service, or another account |
| Identity-based policy | A policy attached to a user, group, or role |
| Resource-based policy | A policy attached to a resource, such as an S3 bucket policy |
| Trust policy | The resource-based policy on a role that defines who may assume it |
| Condition | An extra requirement in a policy, such as MFA or membership in a specific organization |
| SCP / RCP | Service Control Policy / Resource Control Policy: the maximum permissions for principals / resources across accounts in AWS Organizations |
| Permission boundary | The maximum permissions a single user or role can have |
| Explicit deny | A `"Effect": "Deny"` statement, which always wins |
| Confused deputy | A trusted service tricked into acting on behalf of a party that has no right to it |
| OIDC federation | Signing in without permanent keys, using tokens from an identity provider such as GitHub Actions |

## 1. Why IAM deserves a closer look

In [LC-077](1.%20Cloud%20Security%20Fundamentals.md) you learned that in the cloud, identity is the perimeter. This lesson covers the details, because IAM mistakes are rarely obvious. A policy that looks safe can grant admin access by a roundabout route, and a slightly loose trust policy can open an account to outsiders.

Three things you will learn:

1. Reading a policy and predicting its outcome exactly.
2. Recognizing dangerous permissions even when their names sound harmless.
3. Reducing permissions step by step based on usage data.

The examples use AWS, with a dedicated section for Azure and Google Cloud.

## 2. Anatomy of a policy

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadReportsWithMFA",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::finance-reports",
        "arn:aws:s3:::finance-reports/*"
      ],
      "Condition": {
        "Bool": { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}
```

| Element | Meaning |
|:---|:---|
| `Effect` | `Allow` or `Deny` |
| `Action` | API operations, in the form `service:ActionName`. The wildcard `*` means all |
| `Resource` | The ARN of the target. `s3:ListBucket` applies to the bucket, `s3:GetObject` to objects (`/*`) |
| `Condition` | Extra requirements. Here, it only applies if the session used MFA |
| `Principal` | Only in resource-based and trust policies: who is granted access |

Condition keys often used for security:

| Key | Purpose |
|:---|:---|
| `aws:MultiFactorAuthPresent` | Require MFA |
| `aws:SourceIp` | Only from specific IP ranges |
| `aws:PrincipalOrgID` | Only principals from your own AWS organization |
| `aws:SourceAccount`, `aws:SourceArn` | Prevent the confused deputy when an AWS service acts on your behalf |
| `sts:ExternalId` | Prevent the confused deputy when a third party uses your role |
| `aws:RequestedRegion` | Restrict which regions may be used |

## 3. How AWS decides "allow" or "deny"

Every API request is evaluated in roughly this order (simplified for requests within a single account):

```
 1. An explicit Deny in any policy?                   ──► yes ──► DENIED
 2. Do the organization's SCPs / RCPs allow it?       ──► no  ──► DENIED
 3. Does a resource-based policy allow this principal? ──► yes ──► ALLOWED *
 4. Does an identity-based policy allow it?           ──► no  ──► DENIED (implicit deny)
 5. Does the permission boundary (if any) allow it?   ──► no  ──► DENIED
 6. Does the session policy (if any) allow it?        ──► no  ──► DENIED
                                                      ──► yes ──► ALLOWED

 * There are exceptions, for example for role sessions and permission boundaries.
   See the official "Policy evaluation logic" chart in the AWS IAM User Guide.
```

Three rules to remember:

1. **The default is deny.** Without an `Allow`, the answer is no.
2. **An explicit deny always wins**, at any level.
3. **Guardrails (SCPs, permission boundaries, session policies) never grant permissions.** They only limit. Access still has to be granted by an identity-based or resource-based policy.

Do not guess. Use the simulator:

```bash
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::111122223333:role/analyst \
  --action-names s3:GetObject s3:DeleteObject \
  --resource-arns arn:aws:s3:::finance-reports/q3.pdf \
  --query 'EvaluationResults[].{Action:EvalActionName,Result:EvalDecision}'
```

## 4. Guardrails: SCPs and permission boundaries

### Service Control Policies

An SCP applies to **every** principal in a member account of AWS Organizations, including that account's root user. It is how an organization sets rules that no admin in any account can break.

A commonly used SCP:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DoNotDisableAuditLogs",
      "Effect": "Deny",
      "Action": ["cloudtrail:StopLogging", "cloudtrail:DeleteTrail", "cloudtrail:UpdateTrail"],
      "Resource": "*"
    },
    {
      "Sid": "OnlyRegionsWeUse",
      "Effect": "Deny",
      "NotAction": ["iam:*", "organizations:*", "sts:*", "support:*"],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["ap-southeast-3", "ap-northeast-1"] }
      }
    }
  ]
}
```

The second example is simplified. AWS's official example excludes more global services, such as CloudFront and Route 53, so they are not blocked as well.

The first SCP means an attacker who has become admin of an account still cannot turn off CloudTrail (remember Task 2 in LC-077). The second closes unused regions, which attackers like to use for crypto-mining servers because nobody watches them.

Note: SCPs do not apply to the organization's management account, so do not run workloads in the management account.

### Permission boundaries

A permission boundary limits the maximum permissions of one user or role. Its main use is **safe delegation**: a developer team may create its own roles for its applications, as long as every new role must carry a specific boundary. The developers then cannot create a role more powerful than that boundary.

```json
{
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:AttachRolePolicy"],
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": {
    "StringEquals": { "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/AppBoundary" }
  }
}
```

## 5. Cross-account access and the confused deputy

Mature organizations use many AWS accounts: production, staging, logging, security. Access between accounts happens through **assuming a role**.

For account A to use a role in account B, **both sides must agree**:

| Side | Policy | Contents |
|:---|:---|:---|
| Account B (role owner) | The role's trust policy | Allows principals from account A to call `sts:AssumeRole` |
| Account A (caller) | Identity-based policy | Allows a user or role in account A to call `sts:AssumeRole` on the role in account B |

An overly loose trust policy is a dangerous mistake:

```json
{ "Effect": "Allow", "Principal": { "AWS": "*" }, "Action": "sts:AssumeRole" }
```

This trust policy lets **any AWS account in the world** use the role. Fix it by naming specific accounts or roles, or by adding an `aws:PrincipalOrgID` condition.

### The confused deputy

Say you use a SaaS cost-monitoring service that asks for access to your account through a role. The service serves thousands of customers from the same AWS account. If an attacker who is also a customer enters your role's ARN in their own settings, the service can be tricked into accessing your account at the attacker's request.

The defense is an **External ID**, a unique per-customer value generated by the vendor:

```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::999988887777:root" },
  "Action": "sts:AssumeRole",
  "Condition": { "StringEquals": { "sts:ExternalId": "customer-7f3a91" } }
}
```

For AWS's own services acting on your behalf (for example SNS writing to a bucket), use the `aws:SourceAccount` or `aws:SourceArn` condition.

IAM Access Analyzer can list every resource reachable from outside your account or organization:

```bash
aws accessanalyzer create-analyzer --analyzer-name org-analyzer --type ORGANIZATION
aws accessanalyzer list-findings --analyzer-arn <analyzer-arn> \
  --query 'findings[?status==`ACTIVE`].{Resource:resource,Principal:principal}'
```

## 6. Permissions that quietly equal admin

Some permissions sound narrow, but whoever holds them can grant themselves more. When reviewing policies, treat these as seriously as `AdministratorAccess`:

| Permission | Why it is dangerous |
|:---|:---|
| `iam:CreatePolicyVersion`, `iam:SetDefaultPolicyVersion` | Can replace the contents of a policy already attached to them |
| `iam:AttachUserPolicy`, `iam:AttachRolePolicy`, `iam:PutUserPolicy`, `iam:PutRolePolicy` | Can attach any policy, including admin |
| `iam:CreateAccessKey`, `iam:CreateLoginProfile`, `iam:UpdateLoginProfile` on other users | Can create credentials for a more powerful user |
| `iam:UpdateAssumeRolePolicy` | Can change who may use a powerful role |
| `iam:PassRole` combined with creating EC2, Lambda, or other services | Can run code with a role more powerful than their own |

`iam:PassRole` needs special attention. Developers are often given `iam:PassRole` on `"Resource": "*"` so they can deploy applications. As a result, they can attach an admin role to a Lambda function they create themselves. Restrict `Resource` to specific application roles:

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } }
}
```

Open-source tools such as PMapper and Cloudsplaining can analyze your own account and find paths like these automatically. Run them with read-only credentials.

## 7. Identities for machines: roles, OIDC, and workload identity

Permanent access keys for applications and pipelines are the most common source of leaks. There is almost always a keyless alternative:

| Where the code runs | Keyless option |
|:---|:---|
| EC2 | Instance profile (a role for EC2) |
| Lambda, ECS | Execution role / task role |
| EKS (Kubernetes) | IAM Roles for Service Accounts or EKS Pod Identity |
| GitHub Actions, GitLab CI | OIDC federation to a role |
| Your own data center | IAM Roles Anywhere with X.509 certificates |

A trust policy for GitHub Actions. Note the `sub` condition that limits it to one repository and one branch:

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:kodokthegr3at/zero2root-app:ref:refs/heads/main"
    }
  }
}
```

A common mistake is a wildcard that is too broad, such as `repo:kodokthegr3at/*`, or no `sub` condition at all. Other repositories, including forks, can then use the production deploy role. This completes the pipeline security section of [LC-078](../../devsecops/en/1.%20DevSecOps%20Fundamentals.md).

## 8. Azure and Google Cloud

### Azure

Azure has **two separate role systems**:

| System | Governs | Example roles |
|:---|:---|:---|
| Microsoft Entra ID roles | The directory: users, groups, applications | Global Administrator, Privileged Role Administrator |
| Azure RBAC | Resources: VMs, storage, networks | Owner, Contributor, Reader, User Access Administrator |

Azure RBAC is hierarchical: **management group → subscription → resource group → resource**. A role granted at a higher level flows down to everything below it.

| Practice | Explanation |
|:---|:---|
| Avoid Owner at subscription level for daily work | Owner and User Access Administrator can grant access to others |
| Use Privileged Identity Management (PIM) | Admin roles are active only when requested, with approval and a time limit |
| Managed identities for applications | Replace secrets or certificates in code |
| Keep Global Administrators to a minimum | Microsoft recommends fewer than five |

```bash
az role assignment list --all --query "[?roleDefinitionName=='Owner'].{who:principalName,scope:scope}" -o table
```

### Google Cloud

| Role type | Example | Advice |
|:---|:---|:---|
| Basic | Owner, Editor, Viewer | Avoid in production; too broad |
| Predefined | `roles/storage.objectViewer` | The main choice |
| Custom | Your own | For very specific needs |

Key points in GCP:

1. **Service account keys** (JSON files) are as risky as AWS access keys. Use Workload Identity Federation, then block key creation with the organization policy `iam.disableServiceAccountKeyCreation`.
2. The permissions `iam.serviceAccounts.actAs` and `iam.serviceAccountTokenCreator` resemble AWS's `iam:PassRole`. Whoever holds them can act as a more powerful service account.
3. IAM Recommender suggests permission reductions based on the last 90 days of usage.

```bash
gcloud projects get-iam-policy PROJECT_ID \
  --flatten="bindings[].members" --filter="bindings.role:roles/owner OR bindings.role:roles/editor" \
  --format="table(bindings.role, bindings.members)"
```

## 9. Working toward least privilege

Almost nobody writes a correct minimal policy on the first try. A realistic approach is gradual:

```
 1. Start from a sufficient managed policy (for example ReadOnly + specific write permissions)
 2. Run for a few weeks and collect usage data
 3. Generate a policy from real activity, drop what is never used
 4. Validate, test in staging, apply
 5. Repeat periodically
```

Helpful tools:

| Tool | Purpose |
|:---|:---|
| IAM Access Analyzer policy generation | Drafts a policy from CloudTrail based on actions actually used |
| IAM Access Analyzer unused access | Finds unused roles, keys, and permissions |
| Last accessed information | When a principal last used a given service |
| `validate-policy` | Checks a policy for errors and security warnings before it is attached |

```bash
aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY \
  --policy-document file://policy.json \
  --query 'findings[].{Type:findingType,Issue:issueCode}'

JOB=$(aws iam generate-service-last-accessed-details \
  --arn arn:aws:iam::111122223333:role/app-reports --query JobId --output text)
aws iam get-service-last-accessed-details --job-id "$JOB" \
  --query 'ServicesLastAccessed[?TotalAuthenticatedEntities==`0`].ServiceNamespace'
```

The last command lists services the role is allowed to use but has never used. Those are candidates for removal from the policy.

## 10. Detecting risky IAM changes

IAM changes are rare in a healthy account, so every change deserves attention. CloudTrail events worth an alert:

| Event | Why |
|:---|:---|
| `CreatePolicyVersion` with `SetAsDefault=true` | A policy's contents were replaced, possibly an escalation |
| `AttachUserPolicy`, `AttachRolePolicy` with `AdministratorAccess` | New admin rights granted |
| `PutUserPolicy`, `PutRolePolicy` | New inline policies, which often escape review |
| `UpdateAssumeRolePolicy` | Who may use a role has changed |
| `CreateAccessKey` for another user | New credentials for an identity other than the caller |
| `CreateUser` followed by `CreateLoginProfile` outside working hours | A backdoor account |
| `AssumeRole` from an unknown account | Unexpected cross-account access |
| `DeleteRolePermissionsBoundary`, `DetachRolePolicy` on a boundary | A guardrail being removed |

Send these events to the SIEM ([LC-072](../../blue-team/en/1.%20SOC%20%26%20Log%20Analysis.md)) and turn them into detection rules. GuardDuty also has built-in findings for suspicious IAM patterns.

## 11. Practice

### Task 1: predict the evaluation result

The role `analyst` has two policies:

```json
{ "Effect": "Allow", "Action": "s3:*", "Resource": "*" }
```

```json
{ "Effect": "Deny", "Action": "s3:DeleteObject", "Resource": "arn:aws:s3:::finance-reports/*" }
```

Its account is also subject to an SCP that only allows the `ap-southeast-3` region.

1. Can `analyst` read files in `finance-reports`?
2. Can `analyst` delete files in `finance-reports`?
3. Can `analyst` create a new bucket in `us-east-1`?

<details><summary>Answer key</summary>

1. Yes. There is an `Allow s3:*` and no Deny for `GetObject` (assuming the bucket is in an allowed region).
2. No. An explicit deny always wins.
3. No. The SCP restricts regions, and a guardrail cannot be overridden by an `Allow` in an identity-based policy.

</details>

### Task 2: review a trust policy

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" }
  }
}
```

This role has `AdministratorAccess` and is used for production deploys. What is wrong, and how do you fix it?

<details><summary>Answer key</summary>

There is no `sub` condition, so workflows from any GitHub repository using this OIDC provider can use the role. That includes other people's repositories, because GitHub Actions tokens come from the same issuer for every repository.

Fix:

1. Add `"token.actions.githubusercontent.com:sub": "repo:org/repo:ref:refs/heads/main"`, or better, restrict it to the `production` environment.
2. Replace `AdministratorAccess` with only the permissions needed to deploy that application.

</details>

### Task 3: find the admin-equivalent permissions

A policy for the developer team:

```json
{
  "Statement": [
    { "Effect": "Allow", "Action": ["lambda:*", "logs:*"], "Resource": "*" },
    { "Effect": "Allow", "Action": "iam:PassRole", "Resource": "*" },
    { "Effect": "Allow", "Action": ["iam:Get*", "iam:List*"], "Resource": "*" }
  ]
}
```

1. Which combination of permissions is dangerous?
2. Rewrite the dangerous statement to make it safer.

<details><summary>Answer key</summary>

1. `lambda:*` (including creating functions) combined with `iam:PassRole` on `*`. A developer can create a Lambda function, attach any role to it, including an admin role, and run code with admin rights.
2. Restrict `PassRole` to application roles and to the Lambda service only:

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } }
}
```

Then make sure `app-*` roles are created with a permission boundary, so nobody can create an `app-*` role with admin permissions.

</details>

## 12. Quick reference

```text
POLICY EVALUATION (AWS)
  default deny · an explicit Deny always wins
  SCPs, permission boundaries, session policies = guardrails, never grant
  aws iam simulate-principal-policy ...

CROSS-ACCOUNT
  trust policy in the target account + identity policy in the source account
  no "Principal": "*" · use aws:PrincipalOrgID
  third-party vendors → sts:ExternalId · AWS services → aws:SourceArn/SourceAccount

ADMIN-EQUIVALENT PERMISSIONS
  iam:CreatePolicyVersion · iam:Attach*/Put*Policy · iam:UpdateAssumeRolePolicy
  iam:CreateAccessKey (other users) · iam:PassRole + creating compute

KEYLESS MACHINES
  instance profile · task/execution role · IRSA/Pod Identity · OIDC (check "sub") · Roles Anywhere

AZURE
  Entra ID roles ≠ Azure RBAC · MG > subscription > RG > resource · PIM · managed identity

GCP
  avoid Owner/Editor · no service account keys (WIF) · actAs ≈ PassRole · IAM Recommender

LEAST PRIVILEGE
  use → measure → generate a policy from CloudTrail → validate → repeat
```
