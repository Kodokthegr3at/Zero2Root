## Key terms

| Term | Meaning |
|:---|:---|
| IaaS, PaaS, SaaS | Cloud service models: you rent servers, a platform, or a finished application |
| Shared responsibility | How security duties are split between the cloud provider and the customer |
| IAM | Identity and Access Management: who may do what to which resource |
| Policy | A JSON document that grants permissions, such as "may read bucket X" |
| Role | A temporary identity that a service or user can assume, with no fixed password |
| Access key | An ID and secret pair used to call the cloud API from code or the CLI |
| Bucket | An object storage container, such as Amazon S3 or an Azure Blob container |
| Security group | A virtual firewall in front of a cloud server |
| VPC | Virtual Private Cloud: your own private network inside the cloud |
| Audit log | A record of every API call: CloudTrail in AWS, Activity Log in Azure, Cloud Audit Logs in GCP |

## 1. The cloud is someone else's computer

With the cloud, you rent servers, storage, and services from a provider such as AWS, Microsoft Azure, or Google Cloud. Everything is controlled through an API: creating a server, opening a port, or sharing a file takes a single command.

That convenience is also the risk. One wrong command can expose a database to the whole internet within seconds. Year after year, cloud incident reports show the same pattern: the root cause is rarely a flaw in the cloud itself. It is **misconfiguration** and **leaked credentials**.

| Provider | Services you will see often |
|:---|:---|
| AWS | IAM, S3, EC2, VPC, CloudTrail, GuardDuty |
| Azure | Entra ID, Blob Storage, Virtual Machines, VNet, Activity Log, Defender for Cloud |
| Google Cloud | IAM, Cloud Storage, Compute Engine, VPC, Cloud Audit Logs, Security Command Center |

The examples in this lesson use AWS because it is the most widely used, but the concepts are the same on all three providers.

## 2. The shared responsibility model

The provider secures **the cloud**. You secure **what you put in it**.

```
                     IaaS (EC2)      PaaS (RDS)      SaaS (Microsoft 365)
Data & user access   You             You             You
Application          You             You             Provider
OS & patching        You             Provider        Provider
Virtual network      You             Shared          Provider
Hardware & building  Provider        Provider        Provider
```

Two things are **always** your responsibility, whatever the model:

1. **Data**: who can read it, and whether it is encrypted.
2. **Identity and access**: which accounts exist, what they are allowed to do, and whether they use MFA.

A common misunderstanding: "We use AWS, so it must be secure." AWS guards its data centers, but if you set your bucket to public, AWS will dutifully serve it to anyone.

## 3. IAM: identity is the new perimeter

In an office network, the firewall is the boundary. In the cloud, anyone holding valid credentials can call the API from anywhere. The boundary is **identity**.

### The root account

The root account (in AWS, the email used to sign up) has full rights and cannot be restricted.

| Rule | Reason |
|:---|:---|
| Turn on MFA for root | A password alone is not enough for an account that can delete everything |
| Never create access keys for root | A leaked root key means the whole account is gone |
| Do not use root for daily work | Create a separate admin user or role |

### Least privilege

Grant the smallest set of permissions that still gets the job done. Compare these two policies:

```json
{ "Effect": "Allow", "Action": "*", "Resource": "*" }
```

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::finance-reports/*"
}
```

The first policy allows anything on everything. The second can only read files in one bucket. If credentials with the second policy leak, the damage is limited to that one bucket.

### Roles beat access keys

| | Access key | Role |
|:---|:---|:---|
| Lifetime | Permanent until deleted | Temporary, usually 1 hour |
| Where it is stored | Often in files, code, or environment variables | Handed to the server or service automatically |
| If it leaks | Usable for years | Expires on its own |

Applications running on EC2, Lambda, or Kubernetes should use roles. Keep permanent access keys only for cases that truly cannot use a role.

Quick checks with the AWS CLI (read-only, changes nothing):

```bash
aws iam get-account-summary --query 'SummaryMap.AccountMFAEnabled'   # 1 = root uses MFA
aws iam generate-credential-report && aws iam get-credential-report \
  --query Content --output text | base64 -d | cut -d, -f1,8,9,10     # user, MFA active, key active, last rotated
```

## 4. Storage: buckets made public by accident

Storage buckets opened to the public are one of the most frequent causes of data leaks. Usually someone opens access "just for a moment" to share a file, then forgets to close it.

Defenses in AWS:

| Control | Purpose |
|:---|:---|
| S3 Block Public Access (account level) | Rejects any setting that would make a bucket public, across every bucket |
| Default encryption (SSE-S3 or SSE-KMS) | Data is stored encrypted |
| Versioning + Object Lock | Protects against deletion and ransomware |
| Pre-signed URLs | Share one file through an expiring link without opening the bucket |

```bash
aws s3control get-public-access-block --account-id 111122223333   # every value should be true
aws s3api get-bucket-policy-status --bucket bucket-name            # IsPublic should be false
```

Equivalents: in Azure, turn off "Allow Blob public access" on the storage account. In GCP, enable "Public access prevention" on the bucket.

## 5. Network: security groups and the metadata service

### Security groups

A security group is the firewall in front of a cloud server. The most dangerous rule is opening an admin port to the whole internet:

```text
Inbound  TCP 22    0.0.0.0/0   ← SSH open to everyone
Inbound  TCP 3389  0.0.0.0/0   ← RDP open to everyone
Inbound  TCP 3306  0.0.0.0/0   ← database open to everyone
```

`0.0.0.0/0` means every IPv4 address (see CIDR notation in [LC-040](../../networking/en/IP%20Addressing%20%26%20Subnetting.md)). A server with SSH open will receive thousands of login attempts within hours. For administration, use a service such as AWS Systems Manager Session Manager, or a bastion host restricted to office IPs.

```bash
# Find security groups that open anything to 0.0.0.0/0
aws ec2 describe-security-groups \
  --filters Name=ip-permission.cidr,Values=0.0.0.0/0 \
  --query 'SecurityGroups[].{ID:GroupId,Name:GroupName}'
```

### The metadata service

Every cloud server can ask about itself at the special address `169.254.169.254`. Among the things it can fetch there are the temporary credentials of the server's role.

The problem appears when an application on that server has an SSRF flaw ([LC-050](../../web/Vulnerabilities/en/4.%20Server-Side%20Request%20Forgery%20%28SSRF%29.md)). An attacker can make the application request that address and obtain the role's credentials. A major bank's data breach in 2019 started from this pattern.

The defense is **IMDSv2**, which requires a session token obtained through a PUT request first. A plain GET request produced by SSRF cannot get that token.

```bash
aws ec2 modify-instance-metadata-options --instance-id i-0abc123 \
  --http-tokens required --http-endpoint enabled
```

## 6. Secrets and access keys

An access key accidentally committed to a public Git repository can be found by bots within minutes, then used, for example, to rent crypto-mining servers on your bill.

| Don't | Do |
|:---|:---|
| Write access keys into code | Use roles, or a secret manager (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager) |
| Keep `.env` in the repository | Add `.env` to `.gitignore` ([LC-002](../../basics/en/Git%20%E2%80%94%20Version%20Control%20System.md)) |
| Leave old keys active | Rotate keys regularly and delete unused ones |

If a key has already been committed, **deleting the commit is not enough**, because a copy may already have been taken. The right steps: deactivate the key in the console, create a new one, then check CloudTrail to see what was done with the old key.

Stopping leaks before they happen:

```bash
gitleaks detect --source . -v          # scan the repository for secrets
gitleaks protect --staged              # use as a pre-commit hook
```

## 7. Logging: who did what, and when

Every action in the cloud is an API call, and API calls can be recorded. That is a big advantage over physical servers.

| Provider | Audit log | Built-in threat detection |
|:---|:---|:---|
| AWS | CloudTrail | GuardDuty |
| Azure | Activity Log, Entra ID sign-in logs | Microsoft Defender for Cloud |
| GCP | Cloud Audit Logs | Security Command Center |

An example CloudTrail event (trimmed):

```json
{
  "eventTime": "2026-10-18T02:14:09Z",
  "eventName": "PutBucketPolicy",
  "userIdentity": { "type": "IAMUser", "userName": "deploy-bot" },
  "sourceIPAddress": "198.51.100.23",
  "requestParameters": { "bucketName": "customer-backup" }
}
```

Make sure that:

1. CloudTrail is on in **every region**, not just the ones you use. Attackers like regions nobody watches.
2. Logs are kept in a separate bucket that ordinary admins cannot delete.
3. There are alerts for risky events such as `ConsoleLogin` without MFA, `StopLogging`, `DeleteTrail`, `PutBucketPolicy`, `CreateAccessKey`, and `AuthorizeSecurityGroupIngress` to `0.0.0.0/0`.

```bash
aws cloudtrail describe-trails --query 'trailList[].{Name:Name,MultiRegion:IsMultiRegionTrail}'
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=ConsoleLogin --max-results 5
```

These cloud logs can be sent to the same SIEM as your other logs ([LC-072](../../blue-team/en/1.%20SOC%20%26%20Log%20Analysis.md)).

## 8. Auditing a cloud account

Checking hundreds of settings by hand is not realistic. There are standards and free tools for it.

| Tool or standard | Purpose |
|:---|:---|
| CIS Foundations Benchmark (AWS, Azure, GCP) | An industry-recognized list of secure settings, with instructions for checking each one |
| Prowler | Open-source tool that runs hundreds of checks, including CIS, on AWS, Azure, and GCP |
| ScoutSuite | Open-source tool that builds an HTML report from a cloud account's configuration |
| AWS Security Hub / Defender for Cloud / Security Command Center | The providers' built-in versions |

```bash
pip install prowler
prowler aws --compliance cis_3.0_aws     # needs read-only credentials (SecurityAudit policy)
# Output: PASS / FAIL per check, plus HTML and CSV reports
```

Run audits with a **read-only** account (the `SecurityAudit` policy in AWS). An audit does not need, and should not have, permission to change anything.

A sensible order for fixing things:

1. Root account: MFA and no access keys.
2. Audit logging on in every region.
3. No public buckets or databases.
4. No admin ports open to `0.0.0.0/0`.
5. Old access keys rotated or replaced with roles.
6. IMDSv2 required on every server.

## 9. Practice

### Task 1: concepts

1. In the IaaS model, who is responsible for patching the OS: the provider or the customer?
2. Which two things are always the customer's responsibility in every model?
3. Why is a role safer than a permanent access key?
4. What does IMDSv2 prevent?

<details><summary>Answer key</summary>

1. The customer.
2. Data, and identity and access.
3. Role credentials are temporary and expire on their own, while an access key is valid until deleted and is often stored in files or code.
4. Theft of role credentials from the metadata service through SSRF, because a request must start with a PUT to obtain a session token.

</details>

### Task 2: read CloudTrail events

```text
02:10:41  ConsoleLogin            user=intern-03  MFAUsed=No   src=203.0.113.50  result=Success
02:12:05  CreateAccessKey         user=intern-03  target=intern-03
02:13:30  ListBuckets             user=intern-03  (using the new access key)
02:14:09  PutBucketPolicy         user=intern-03  bucket=customer-backup  Principal="*"
02:20:55  StopLogging             user=intern-03  trail=main-trail
```

1. Name three suspicious things.
2. What does `Principal="*"` in a bucket policy mean?
3. Why is the last event especially worrying?
4. What are your first three steps as a responder?

<details><summary>Answer key</summary>

1. A login without MFA at 2 a.m., an intern account immediately creating a new access key, a backup bucket made public, and logging turned off.
2. Anyone, including people with no AWS account at all, is granted access to the bucket.
3. The attacker is trying to erase their tracks. Nothing after 02:20:55 is recorded in that trail any more.
4. Disable the access key and sessions of `intern-03`, turn logging back on, then restore the bucket policy and check the S3 access logs to see whether data was downloaded. Only after that, analyze how the `intern-03` password leaked.

</details>

### Task 3: audit your own account

In an AWS Free Tier account you own:

1. Turn on MFA for the root account.
2. Create a separate user or role with the `SecurityAudit` policy.
3. Run Prowler with the CIS checks and note the five FAIL findings with the highest severity.
4. Fix one finding, run it again, and confirm that its status changes to PASS.

<details><summary>Example commands</summary>

```bash
aws iam create-role --role-name auditor --assume-role-policy-document file://trust.json
aws iam attach-role-policy --role-name auditor --policy-arn arn:aws:iam::aws:policy/SecurityAudit
prowler aws --compliance cis_3.0_aws --severity critical high
```

</details>

## 10. Quick reference

```text
SHARED RESPONSIBILITY
  Provider: hardware, buildings, core services
  You (always): data + identity & access

IAM
  Root: MFA, no access keys, not for daily use
  Least privilege · roles > access keys · MFA for every user

STORAGE
  Block Public Access (AWS) · disable public blob (Azure) · public access prevention (GCP)

NETWORK
  No 22/3389/DB to 0.0.0.0/0 · require IMDSv2

LOGS
  CloudTrail in every region · stored separately · alerts: StopLogging, DeleteTrail,
  ConsoleLogin without MFA, CreateAccessKey, PutBucketPolicy

  prowler aws --compliance cis_3.0_aws  (read-only account: SecurityAudit)
```
