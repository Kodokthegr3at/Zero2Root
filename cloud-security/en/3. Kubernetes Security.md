## Key terms

| Term | Meaning |
|:---|:---|
| Cluster | A set of machines that Kubernetes manages to run containers |
| Control plane | The central components: API server, etcd, scheduler, controller manager |
| Node | A machine that runs pods, with a kubelet and a container runtime |
| Pod | The smallest unit in Kubernetes, holding one or more containers |
| Namespace | A logical division inside the cluster, for example per team or per application |
| RBAC | Role-Based Access Control: who may do what to which resource in the cluster |
| Service account | The identity a pod uses when talking to the API server |
| securityContext | Security settings for a pod or container, such as its user and capabilities |
| NetworkPolicy | Firewall rules between pods |
| Admission controller | A check that accepts or rejects objects before they are stored in the cluster |

## 1. Why Kubernetes needs its own lesson

Containers ([LC-030](../../linux/en/23.%20Containerization.md)) already have their own risks. Kubernetes adds new layers: an API server that can create and delete anything in the cluster, an identity for every pod, and a network that by default lets every pod talk to every other pod.

A misconfiguration in Kubernetes often does more damage than on a single server:

| Mistake | Consequence |
|:---|:---|
| API server or dashboard exposed to the internet without authentication | Anyone can run containers in the cluster, often for crypto mining |
| Pods running `privileged` | A container can take over the node it runs on |
| The default service account has broad rights | One compromised application can control the whole cluster |
| No network policies | An attacker in one pod can reach a database in another namespace |
| Secrets stored unencrypted and readable by many | Database and API credentials leak too |

## 2. A short architecture and the 4C model

```
 kubectl / CI ──► API server ──► etcd (all cluster state, including Secrets)
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
        Node 1     Node 2     Node 3
        kubelet    kubelet    kubelet
        [pod][pod] [pod]      [pod][pod]
```

Every change goes through the **API server**. Who may talk to it, and what they may do, is therefore the most important security question.

The Kubernetes documentation uses the **4C** model. Each layer is only as secure as the layer around it:

| Layer | Example controls |
|:---|:---|
| Cloud | IAM, VPC networking, node access (LC-077, LC-081) |
| Cluster | RBAC, admission control, etcd encryption, audit logs |
| Container | Scanned images, non-root users, minimal capabilities |
| Code | Secure applications, scanned dependencies (LC-078) |

## 3. API server access and RBAC

Every request to the API server goes through three stages: **authentication** (who are you), **authorization** (are you allowed, usually through RBAC), and **admission** (does this object follow the rules).

RBAC has four kinds of objects:

| Object | Scope | Contents |
|:---|:---|:---|
| Role | One namespace | A list of permissions |
| ClusterRole | The whole cluster | A list of permissions |
| RoleBinding | One namespace | Links a Role or ClusterRole to a user, group, or service account |
| ClusterRoleBinding | The whole cluster | Links a ClusterRole to subjects across the cluster |

A narrow Role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-pods
  namespace: shop
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
```

Permissions that should be treated as cluster admin:

| Permission | Why it is dangerous |
|:---|:---|
| `*` on `*` | Every action on every resource |
| `create` on `pods` (or Deployments, Jobs, and similar) | Can create a pod that mounts another service account or runs privileged |
| `get` / `list` on `secrets` | Reads every credential in that namespace, including service account tokens |
| `create` on `pods/exec` | Runs commands inside any container |
| `escalate`, `bind` on roles | Can grant themselves higher permissions |
| `impersonate` on users, groups, serviceaccounts | Acts as another identity |
| `get` on `nodes/proxy` | Talks directly to the kubelet, bypassing some controls |
| A binding to the `cluster-admin` ClusterRole | Full admin |

Checking an identity's permissions:

```bash
kubectl auth can-i --list -n shop --as=system:serviceaccount:shop:default
kubectl auth can-i create pods -n shop --as=system:serviceaccount:shop:web
kubectl get clusterrolebindings -o wide | grep cluster-admin
```

## 4. Service accounts and tokens

Every pod runs as a service account. If none is specified, the pod uses the `default` service account in its namespace, and by default its token is mounted into the pod at `/var/run/secrets/kubernetes.io/serviceaccount/`.

If the application in the pod is compromised, the attacker holds that token and can call the API server with that service account's permissions.

| Practice | How |
|:---|:---|
| Do not mount the token unless needed | `automountServiceAccountToken: false` on the pod or service account |
| One service account per application | Do not use `default`, do not share between applications |
| Minimal permissions | Most web applications never need to talk to the API server |
| Short-lived tokens | Modern Kubernetes uses projected tokens that expire. Avoid old Secret-based tokens that never expire |

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
  namespace: shop
automountServiceAccountToken: false
```

## 5. Pod security

`securityContext` decides how much power a container has over the node it runs on.

A secure pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: shop
spec:
  serviceAccountName: web
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: web
      image: registry.example.internal/shop/web:1.4.2
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      resources:
        limits: { cpu: "500m", memory: "256Mi" }
```

Dangerous settings:

| Setting | Consequence |
|:---|:---|
| `privileged: true` | The container gets almost all the access the node has |
| `hostPath` to `/`, `/etc`, or the container runtime socket | The container can read or change node files, including starting new containers outside Kubernetes' control |
| `hostNetwork`, `hostPID`, `hostIPC` | The container shares the node's network or processes |
| Capabilities `SYS_ADMIN`, `NET_ADMIN` | Root-equivalent power for many operations |
| Running as root without restrictions | A flaw in the application immediately means root in the container |
| No `resources.limits` | One pod can exhaust the node's CPU and memory |

## 6. Pod Security Standards

Kubernetes provides three levels of pod security standards, enforced by the built-in **Pod Security Admission**:

| Level | Contents |
|:---|:---|
| Privileged | No restrictions. Only for system components that truly need it |
| Baseline | Blocks the obviously dangerous: privileged, hostPath, hostNetwork, dangerous capabilities |
| Restricted | Baseline plus required non-root, `allowPrivilegeEscalation: false`, drop ALL capabilities, seccomp |

Enabled with labels on a namespace:

```bash
kubectl label namespace shop \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/warn=restricted
```

A safe rollout: turn on `warn` and `audit` first, fix the workloads that violate the rules, then enable `enforce`.

## 7. Network policies

By default, **every pod can talk to every pod** in the cluster, across namespaces. NetworkPolicy restricts this, provided the network plugin (CNI) supports it, for example Calico or Cilium.

Start by denying everything, then open what is needed:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: shop
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-to-db
  namespace: shop
spec:
  podSelector:
    matchLabels: { app: db }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: web }
      ports:
        - protocol: TCP
          port: 5432
```

Remember to allow egress for DNS (port 53 to CoreDNS); without it, applications cannot resolve host names. Also restrict egress to the internet, so a compromised pod cannot freely send data out or download tools.

## 8. Secrets

A Kubernetes Secret is only **base64-encoded**, not encrypted. Anyone who can read Secrets through the API, or read etcd directly, gets the contents.

```bash
kubectl get secret db-cred -n shop -o jsonpath='{.data.password}' | base64 -d
```

| Control | Explanation |
|:---|:---|
| Encrypt etcd at rest | Configure `EncryptionConfiguration` with a KMS provider. On managed cloud services, enable Secret encryption with a KMS key |
| Restrict RBAC on Secrets | Almost no person or application needs to `list` every Secret |
| An external secret manager | AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, or Vault, connected through the External Secrets Operator or the Secrets Store CSI Driver |
| No Secrets in Git | A committed manifest containing a Secret counts as leaked. Use Sealed Secrets or SOPS if it must live in Git |

## 9. Image supply chain and admission control

Images running in the cluster must come from trusted sources and be scanned. Scanning with Trivy was covered in [LC-078](../../devsecops/en/1.%20DevSecOps%20Fundamentals.md). In the cluster, these rules are enforced by an admission controller.

| Rule | Example |
|:---|:---|
| Approved registries only | Reject images not from `registry.example.internal` |
| No `latest` tag | Require a version tag or digest |
| Images must be signed | Verify cosign signatures |
| Require `resources.limits` and an owner label | So workloads can be traced and cannot exhaust nodes |

Common tools: **Kyverno** (rules written as Kubernetes YAML) and **OPA Gatekeeper** (rules written in Rego). A Kyverno rule:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: internal-registry-only
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-registry
      match:
        any:
          - resources:
              kinds: ["Pod"]
      validate:
        message: "Images must come from registry.example.internal"
        pattern:
          spec:
            containers:
              - image: "registry.example.internal/*"
```

## 10. Kubernetes in the cloud: EKS, AKS, GKE

Managed Kubernetes services run the control plane for you, but shared responsibility ([LC-077](1.%20Cloud%20Security%20Fundamentals.md)) still applies: workload configuration, RBAC, and networking remain your job.

| Topic | What to do |
|:---|:---|
| API server endpoint | Make it private, or restrict it to specific IP ranges |
| Pod identity in the cloud | IRSA or EKS Pod Identity on AWS, Workload Identity on AKS and GKE. Do not store access keys in Secrets ([LC-081](2.%20Cloud%20IAM%20in%20Depth.md)) |
| Node metadata service | Pods must not be able to use the node's role. On EKS, require IMDSv2 with a hop limit of 1 so ordinary pods cannot obtain a metadata token |
| Admin access | Map IAM to Kubernetes RBAC (EKS access entries, Azure RBAC for AKS, GKE IAM) with least privilege |
| Updates | Stay on supported Kubernetes versions and update nodes regularly |

## 11. Audit logs and runtime detection

### Kubernetes audit logs

The API server can record every request. On managed services, enable sending audit logs to the cloud logging service (for example, EKS control plane logging to CloudWatch).

Events worth an alert:

| Event | Why |
|:---|:---|
| `create` on `pods/exec` | Someone is running commands inside a production container |
| A new pod with `privileged`, `hostPath`, or `hostPID` | A common pattern for taking over a node |
| A new ClusterRoleBinding to `cluster-admin` | Full admin rights granted |
| `list` or `get` on Secrets by a service account that normally never reads them | Credentials are being collected |
| Successful requests from `system:anonymous` | Unauthenticated access is open |

### Runtime detection

Audit logs only see the API server. What happens inside containers is seen by runtime tools such as **Falco** (open source, eBPF-based):

```text
Examples of Falco's built-in rules:
  Terminal shell in container           → an interactive shell opened in a container
  Write below etc                       → a file under /etc changed at runtime
  Contact K8S API Server From Container → a container unexpectedly calling the API server
```

All these alerts go to the same SIEM as your other logs ([LC-072](../../blue-team/en/1.%20SOC%20%26%20Log%20Analysis.md)).

## 13. Practice

### Task 1: concepts

1. Are Kubernetes Secrets encrypted by default?
2. Why is `create pods` dangerous even without permission to read Secrets?
3. What are the three Pod Security Standards levels?
4. What is the default network behavior between pods in Kubernetes?

<details><summary>Answer key</summary>

1. No. The contents are only base64-encoded. Encryption at rest must be enabled.
2. Whoever creates a pod can attach a more powerful service account to it, mount Secrets as volumes, or create a privileged pod to take over the node.
3. Privileged, Baseline, Restricted.
4. Every pod can talk to every pod, across namespaces, until a NetworkPolicy restricts it.

</details>

### Task 2: fix a pod manifest

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: reports
  namespace: finance
spec:
  hostNetwork: true
  containers:
    - name: reports
      image: reports:latest
      securityContext:
        privileged: true
      volumeMounts:
        - name: host
          mountPath: /host
  volumes:
    - name: host
      hostPath:
        path: /
```

List every problem, then write a secure version. The application only reads a database and generates PDF files.

<details><summary>Answer key</summary>

Problems: `hostNetwork`, `privileged`, the node's entire filesystem mounted through `hostPath: /`, the `latest` tag, an image with no clear registry, no `runAsNonRoot`, no dropped capabilities, no resource limits, and the default service account token mounted.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: reports
  namespace: finance
spec:
  serviceAccountName: reports
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: reports
      image: registry.example.internal/finance/reports:2.1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: ["ALL"] }
      resources:
        limits: { cpu: "500m", memory: "512Mi" }
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}
```

The `emptyDir` volume at `/tmp` is there because the root filesystem is read-only, while generating PDFs needs somewhere to write temporarily.

</details>

### Task 3: review RBAC

```yaml
kind: Role
metadata: { name: deployer, namespace: shop }
rules:
  - apiGroups: ["", "apps"]
    resources: ["pods", "deployments", "secrets"]
    verbs: ["*"]
```

This Role is bound to the CI pipeline's service account that deploys the shop application. What is the risk, and how do you narrow it?

<details><summary>Answer key</summary>

Risk: the pipeline can read and change every Secret in the `shop` namespace, delete anything, and create arbitrary pods, including pods that mount other service accounts or any Secret. If the pipeline is compromised, the whole namespace goes with it.

A narrower version: change Deployments only, with no Secret access and no direct pod creation.

```yaml
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "patch", "update"]
```

Add admission rules (Pod Security `restricted` and Kyverno) so that even a patched Deployment cannot run dangerous pods.

</details>

## 14. Quick reference

```text
ACCESS
  authentication → authorization (RBAC) → admission
  kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa>
  admin-equivalent: * · create pods · get/list secrets · pods/exec · escalate/bind · impersonate · nodes/proxy

SERVICE ACCOUNTS
  one per application · automountServiceAccountToken: false · minimal permissions

A SECURE POD
  runAsNonRoot · allowPrivilegeEscalation: false · readOnlyRootFilesystem
  capabilities drop ALL · seccomp RuntimeDefault · resources.limits
  avoid: privileged · hostPath · hostNetwork/PID/IPC

POD SECURITY ADMISSION
  namespace label: pod-security.kubernetes.io/enforce=restricted (warn/audit first)

NETWORK
  default: every pod reaches every pod → deny-all NetworkPolicy + open what is needed (remember DNS)

SECRETS
  base64 ≠ encryption · encrypt etcd (KMS) · strict RBAC · external secret manager

CLOUD
  private API endpoint · IRSA/Pod Identity/Workload Identity · IMDSv2 hop limit 1

DETECTION & AUDIT
  audit logs: pods/exec, privileged pods, cluster-admin bindings, unusual Secret reads
  Falco for runtime · kube-bench · kubescape · trivy k8s
```
