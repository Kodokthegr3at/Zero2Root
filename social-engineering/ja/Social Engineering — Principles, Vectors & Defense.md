## 重要な用語

この教材でよく出てくる言葉です。

| 用語 | 意味 |
|:---|:---|
| ソーシャルエンジニアリング（SE） | コンピュータをハッキングする代わりに、人をだましてアクセス権や情報を渡させたり、行動を取らせたりすること |
| プリテキスト | 攻撃者が使う作り話（「IT部門の者です」「新しい取引先です」） |
| ラポール | 相手の警戒心を下げるために攻撃者が作る親しい関係 |
| OSINT | 公開情報（LinkedIn、会社のWebサイト、SNSなど、誰でも見られる情報）の収集 |
| アウトオブバンド検証 | 依頼を、すでに信頼している*別の*経路で確認すること。例: 送金を求めるメールが来たら、メールに書かれた番号ではなく、社内名簿の番号に電話して確認する |
| コールバック | 一度電話を切り、相手の公式番号にかけ直すこと |
| デュアルコントロール | 重要な操作には2人の承認が必要。1人がだまされただけでは実行できない |
| BEC | ビジネスメール詐欺。メールで社員をだまし、間違った口座に送金させる詐欺 |
| SOC | セキュリティオペレーションセンター。セキュリティの報告を受けて対応するチーム |
| RoE | Rules of Engagement（交戦規定）。セキュリティテストで何をしてよいか・いけないかを定めた署名済みの文書 |

## 1. 攻撃対象としての人的レイヤー

攻撃者が社員を説得して「ドアを開けさせる」ことができれば、ファイアウォールもウイルス対策も役に立たない。Mitnick（*The Art of Deception*）は、攻撃者が利用する人間の3つの習性を挙げている。人は助けたがり、対立を避けたがり、権威がありそうな相手を信じてしまう。

ソーシャルエンジニアリングが成功しやすいのは、次の条件がそろったときだ。

- 相手を**信頼している**
- 依頼が**急ぎ**に感じられる
- 価値のあるものに**アクセスできる**
- 依頼を**簡単に確認する方法がない**

このうち1つでも、特に最後の1つをなくせば、攻撃はずっと難しくなる。

つまり、ソーシャルエンジニアリングが狙うのはソフトウェアのバグではなく、人の考え方と社内手続きの隙間だ。だから防御の中心も人とプロセスになる。明確な手順、「確認してからにします」と言いやすい文化、そして依頼を確実に確認できる方法だ。

```
┌──────────────┐     trust / fear / greed      ┌──────────────┐
│  Attacker    │ ─────────────────────────────▶│   Target     │
│  narrative   │◀──── info / access / action ──│   human      │
└──────────────┘                               └──────────────┘
        │                                              │
        └────────── defense: verify out-of-band ───────┘
```

## 2. Cialdiniの影響力の原理（防御の視点）

心理学者Robert Cialdiniは、人が「はい」と言いやすくなる要因をいくつか示した。HadnagyはそれをもとにSEのフレームワークを作っている。ここで学ぶのは、操作を**見抜く**ためであり、使うためではない。

| 原理 | 意味 | 攻撃者の使い方 | 防御 |
|:---|:---|:---|:---|
| 返報性 | 助けてくれた人には借りがあると感じる | 「先週手伝ったので、あのファイルを送ってもらえますか」 | 恩があっても通常の手続きは省略しない |
| コミットメントと一貫性 | 前に言ったことを守りたくなる | 「さっき手伝えると言いましたよね…」 | 何かおかしいと感じたら、いつでも考えを変えてよい |
| 社会的証明 | 他の人と同じ行動をとる | 「スタッフ全員がもうこのリンクから更新しています」 | 「みんな」ではなく公式の情報源で確認する |
| 権威 | 上司や制服に従う | 「IT部長が今すぐリセットしてほしいそうです」 | 公式番号にかけ直す。2人目の承認を求める |
| 好意 | 好きな相手を助けたくなる | 親しげな雑談のあとに、急に機微な依頼 | 親しいことと権限があることは別 |
| 希少性・緊急性 | 何かを失いそうになると焦る | 「15分後にアカウントが閉鎖されます」 | ルール: 急な時間的圧力のもとでは重要な操作をしない |
| ユニティ | 「仲間」を信じる | 同じコミュニティや取引先の人間を装う | どれだけ身近に見えても身元を確認する |

### すべてに共通するパターン

どの原理も、**急いで**、**確認せずに**行動させようとする。だから防御の考え方はいつも同じだ。重要な操作の前に、短い確認ステップ（コールバック、チケット、2人目の承認）を入れる。そのステップは、みんなが実際に守れるほど手軽で、しかも急かされても飛ばせないほど確実でなければならない。

## 3. ソーシャルエンジニアリングの物語サイクル

多くのソーシャルエンジニアリングは似た流れをたどる（*Practical Social Engineering* とHadnagyに基づく）。これは攻撃を見抜くための全体像であり、攻撃の手引きではない。

```
下調べ → 作り話を用意 → 接触 → 信頼を築く → 依頼 → 立ち去る →（報告）
```

| ステップ | 攻撃者がすること | 防御 |
|:---|:---|:---|
| 下調べ（OSINT） | 会社や個人の公開情報を集める | 公開する情報を減らす。社員にプライバシーについて教える |
| 作り話（プリテキスト） | 連絡するもっともらしい理由を作る | 最後にアクセスを求めてくる話は疑う |
| 接触 | メール、電話、対面、チャット | 公式の経路を使う。社外メールには警告バナーを付ける |
| 信頼を築く（ラポール） | 相手を安心させる | 雑談の直後に急な依頼が来たら注意する |
| 依頼 | 行動や情報を求める | 依頼が「ちょっとしたこと」に見えても確認を飛ばさない |
| 立ち去る | 怪しまれずに会話を終える | ログを残し、あとで振り返る |
| 報告 | （許可されたテストの場合のみ）結果をまとめる | 書面のRoEがある場合のみ |

重要: このリポジトリでは、フィッシングキットの作り方、Evilginxなどのツールの設定、BadUSBデバイスの作成、詐欺スクリプトの書き方は扱わない。焦点は心理学、検知、訓練にある。

## 4. 代表的な経路（概念）

「経路」とは、攻撃が被害者に届くルートのこと。

| 経路 | 内容 | よく求められるもの |
|:---|:---|:---|
| フィッシング / スピアフィッシング | クリックや返信を求める偽メッセージ。スピアフィッシングは特定の1人を狙う | パスワード、マルウェアリンクのクリック、支払いの変更 |
| ビッシング | 詐欺電話（音声によるフィッシング） | パスワードリセット、MFAコード、顧客データ |
| スミッシング | 詐欺SMSやチャット | 偽の「荷物配達」や「銀行」リンクのクリック |
| プリテキスティング（ヘルプデスク） | 社員や取引先を装ってヘルプデスクに電話する | アカウントのロック解除、VPNへの追加 |
| 物理的ななりすまし | 関係者のふりをして直接現れる | 社員の後について施錠されたドアを通る（テールゲーティング） |
| ビジネスメール詐欺（BEC） | 偽の請求書や偽の「社長」メール | 支払先口座の変更 |
| クイド・プロ・クオ | 「ITの問題を直しますので、これをインストールしてください」 | リモートアクセスツールのインストール |

### 被害はどこまで大きくなるか

被害が大きくなるのは、次のようなときだ。

- 渡した**アクセス権が大きい**（管理者アカウントは一般アカウントより危険）
- 関わるデータが**機微である**（顧客データは昼食のメニューよりずっと重要）
- 会社が**気づくのが遅い**（1時間のアクセスは1か月のアクセスより被害がはるかに小さい）

## 5. 検知シグナル: レッドフラグ

### メッセージの内容から

- 極端に急がせ、脅しを伴う（「今すぐやらないとクビになる」）。
- 通常の手続きを飛ばすよう、または秘密にするよう求める（「誰にも言わないで」）。
- 本物とほとんど同じメールアドレス。例: `paypal.com` ではなく `paypa1.com`、あるいは不自然なサブドメイン。
- MFAコード、パスワード、暗号資産のシードフレーズを求める。本物のIT担当者は絶対に求めない。
- 取引先が、別の経路での確認なしに口座を変更しようとする。

### 依頼のされ方から

- 業務時間外の連絡で、すぐに返事をするよう迫る。
- 見慣れないリモート操作ツールのインストールを求める。
- チケットの作成やコールバックを拒む。

### すぐ使える対応表

| 気づいたこと | 危険度 | すぐにすること |
|:---|:---:|:---|
| パスワード / MFAコードを求められた | 高 | 会話をやめてSOCに報告する |
| 支払情報の変更を求められた | 高 | 経理部門から2人目の承認を得る |
| 「ログインページ」へのリンク | 中〜高 | 報告する。クリックせず、本物のサイトを自分で開く |
| 発注書のない「新しい」取引先 | 中 | 調達部門に確認する |
| 入館ドアで誰かが後ろからついてきた | 中 | 丁寧に名前を尋ね、警備員にエスコートを頼む |

## 6. 効果的な啓発訓練

悪い訓練とは、年1回見てすぐ忘れるビデオのこと。良い訓練は、定期的に行い、効果を測り、誰にも恥をかかせない。

### プログラムの作り方

1. **現状を把握する。** アンケートと、許可を得たフィッシング模擬演習（書面のRoEとHRの承認つき）で、今の状態を確認する。
2. **理由を教える。** 影響力の原理とコールバックの習慣を説明する。「リンクをクリックするな」だけでは足りない。
3. **タイミングを選ぶ。** 詐欺が増える時期（確定申告、給与支払い、取引先の契約更新）に短いヒントを送る。
4. **役割に合わせる。** 経理はBEC、ヘルプデスクは偽の電話、経営層はホエーリング（経営幹部を狙うフィッシング）について学ぶ。
5. **効果を測る。** 良い兆候: 報告する人が増える、2回目のクリックが減る、報告が早くなる。
6. **恥をかかせない。** すぐに報告した人は、たとえ先にクリックしていても褒める。

### 訓練は割に合っているか

訓練の費用に対して、不審なメッセージを報告する人が増え、成功する攻撃が減っていれば、その訓練には価値がある。だからクリック率よりも報告率のほうが良い指標になることが多い。1件の素早い報告が会社全体を守ることもある。

### 15分のセッション例

| 分 | 内容 |
|:---:|:---|
| 0-3 | あなたの業界で実際にあった話（匿名化済み） |
| 3-8 | 3つのレッドフラグと、それぞれの確認方法 |
| 8-12 | 練習: 詐欺電話のシナリオに対応する |
| 12-15 | 報告の仕方と、報告したあとに何が起きるか |

## 7. 組織的コントロール

1人がだまされても大事故にならないように、会社が用意しておくルールと仕組み。

| コントロール | 仕組み | 防ぐもの |
|:---|:---|:---|
| アウトオブバンド検証 | HRの名簿にある番号にかけ直す | 詐欺電話、BEC |
| デュアルコントロール | 送金や権限変更には2人の承認が必要 | 1人がだまされて起きる不正 |
| 最小権限 + JIT | 必要なアクセス権だけを、必要な時間だけ与える（ジャストインタイム） | ヘルプデスクがだまされて過剰な権限を与えること |
| メール認証 | SPF、DKIM、DMARCを有効にし、自社ドメインを偽ったメールをメールサーバーが見抜けるようにする | 自社ドメインを名乗る偽メール |
| 外部メールバナー | 社外からのメールに「外部」ラベルを付ける | 偽の「社内」メール |
| ヘルプデスクでの本人確認 | リセットの前に社員ID + コールバック | ヘルプデスク経由のアカウント乗っ取り |
| 物理アクセスポリシー | バッジと来訪者のエスコート | テールゲーティング |
| フィッシングに強いMFA | パスキーやFIDO2セキュリティキー（偽サイトでは使えない） | パスワードの盗難 |
| データ分類 | 機微なデータにラベルを付け、電話では絶対に伝えない | 情報の話しすぎ |

重要な依頼の正しい流れ:

```
Request sensitive action
        │
        ▼
  Ticket required? ──no──▶ deny / redirect
        │ yes
        ▼
  Identity proof (policy)
        │
        ▼
  Out-of-band confirm (if high risk)
        │
        ▼
  Dual approval (if financial / admin)
        │
        ▼
  Execute + audit log
```

## 8. 倫理、法律、許可されたテスト

| 活動 | 事前に必要なもの |
|:---|:---|
| SEテスト / フィッシング模擬演習 | 書面のRoEと、法務・HR・経営層の承認 |
| 社員についての調査（OSINT） | 公開情報だけを使い、現地のプライバシー法に従う |
| 物理的ななりすましテスト | 建物の管理者の許可と、テストを安全に中止する方法 |
| だましの手口を教える | すぐ使えるキットは配らず、検知に焦点を当てる |

法律は国によって異なる（詐欺、コンピュータへのアクセス、通話の録音など）。許可のないテストは、法律や雇用契約に違反するおそれがある。

## 9. ソーシャルエンジニアリングのインシデント対応

誰かがだまされてしまったあとにすること:

1. **封じ込める:** 攻撃者との会話をやめる。パスワードを伝えてしまったなら、アカウントをロックするか保護する。
2. **証拠を残す:** メール（ヘッダーも含む）、電話番号、録音（合法な場合）、チャットログを保存する。
3. **リセットする:** パスワードを変え、すべてのセッションからログアウトさせ、必要ならMFAデバイスを交換する。攻撃者がメール転送ルールを追加していないか確認する。
4. **知らせる:** SOC / インシデント対応チームに報告する。支払いが絡むなら経理、顧客データが絡むなら法務にも伝える。
5. **調べる:** 新しいメールボックスルール、受信箱に新しくアクセスできるようになった人、普段と違うVPNログインを探す。
6. **学ぶ:** 訓練とコントロールを見直す。報告した人を決して責めない。その人は会社を助けたのだ。

**報告が早いほど、被害は小さくなる。** これが身につけるべき最も大切な習慣だ。

## 10. 防御チートシート

```text
行動する前に確認
[ ] 誰かに急かされていないか？
[ ] 公式の経路で相手の身元を確認したか？
[ ] 通常の手続きを飛ばすよう言われていないか？
[ ] 秘密（パスワード / MFAコード / シードフレーズ）を求められていないか？
[ ] 口座の変更や管理者権限に関わる話ではないか？

ひとつでも「はい」なら → 止まる → チケット作成 / かけ直す → 報告
```

| 役割 | 守るべきひとつの習慣 |
|:---|:---|
| すべての社員 | 間違いかもしれなくても、不審なことは報告する |
| ヘルプデスク | ポリシーで決めた本人確認なしにリセットしない |
| 経理 | 支払いの変更は必ず別の経路で確認する |
| エグゼクティブアシスタント | 予定調整や送金の前にホエーリングのチェックリストを使う |
| セキュリティチーム | クリックした人数だけでなく、報告した人数を数える |

## セキュリティノート: 脅威と防御

| 脅威 | 起こり方 | 防御 |
|:---|:---|:---|
| パスワードの盗難 | 偽のログインページ / 詐欺電話 | FIDO2。MFAコードは決して共有しない。報告する |
| BEC詐欺 | 偽の請求書 / 偽の「社長」メール | デュアルコントロール。取引先にかけ直す |
| ヘルプデスクへのプリテキスティング | 電話でヘルプデスクをだましてリセットさせる | 厳格な本人確認 |
| テールゲーティング | 入館ドアで人の後ろについて入る | 「どなたですか？」と聞くのが当たり前の文化。ターンスタイル |
| 情報の話しすぎ | 攻撃者が信頼を築いてから多くを聞き出す | データ分類。必要なことだけを伝える |
| 恥の文化 | 恥ずかしさからインシデントが隠される | 素早い報告を評価する |

扱わない内容: フィッシングキットの構築、認証情報を盗むプロキシ、BadUSBペイロード、すぐに使える詐欺スクリプト。
