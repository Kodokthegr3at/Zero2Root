## 1. 攻撃対象としての人的レイヤー

技術的なセキュリティは、攻撃者が人を説得してアクセス権を与えさせたり、秘密を渡させたり、何らかの行動を取らせたりできれば回避される。Mitnick（*The Art of Deception*）は、人は基本的に助けたがり、対立を避けたがり、正当に見える権威を信頼しがちだと指摘している。

$$
\mathsf{Risk}_{SE} = f(\mathsf{Trust},\; \mathsf{Urgency},\; \mathsf{Access},\; \mathsf{VerificationGap})
$$

信頼と緊急性が高いほど、そして検証が弱いほど、ソーシャルエンジニアリングが成功する可能性は高くなる。

ソーシャルエンジニアリング（SE）が突くのは、主にメモリ破壊ではなく、認知バイアスと組織プロセスの隙間だ。防御は、単なるファイアウォールルールの追加ではなく、プロセス、文化、検証チャネルによって行う。

```
┌──────────────┐     trust / fear / greed      ┌──────────────┐
│  Attacker    │ ─────────────────────────────▶│   Target     │
│  narrative   │◀──── info / access / action ──│   human      │
└──────────────┘                               └──────────────┘
        │                                              │
        └────────── defense: verify out-of-band ───────┘
```

## 2. Cialdiniの影響力の原理（防御の視点）

Hadnagyは影響力の心理学の上にSEのフレームワークを構築している。これらの原理は、欺瞞キャンペーンを準備するためではなく、操作を検知するために理解しておく。

| 原理 | 直感 | 操作の例 | 防御 |
|:---|:---|:---|:---|
| 返報性 | 恩義の感覚 | 「先に手伝ったので、ファイルを送り返してほしい」 | ポリシー: 贈り物が手続きのバイパスを正当化することは決してない |
| コミットメントと一貫性 | 以前の発言との一貫性を保とうとする | 「さっき手伝えると言いましたよね…」 | 新しい事実が出てきたら判断を変えることを常に許容する |
| 社会的証明 | 他人に従う | 「スタッフ全員がすでにこのリンクから更新済みです」 | 公式のソース経由で検証する |
| 権威 | 上司や制服に従う | 「IT部長が今すぐリセットしてほしいと言っています」 | 公式番号へのコールバック、デュアルコントロール |
| 好意 | 好きな相手を助けたくなる | 過剰なラポール形成の後に機微な依頼 | 親しみやすさと認可を切り離す |
| 希少性・緊急性 | 失うことへの恐れ | 「アカウントは15分で閉鎖されます」 | SLA: 作られた時間的圧力の下では機微な操作を行わない |
| ユニティ | 「私たちは同じ仲間だ」 | コミュニティやベンダーへの偽の帰属 | 検証済みのバッジと身元確認 |

### 簡単な定式化

$$
\mathsf{Compliance} \uparrow \;\text{when}\; \sum_i w_i \cdot \mathsf{Principle}_i > \mathsf{VerificationFriction}
$$

防御は、生産性を殺さない範囲でVerificationFriction（コールバック、チケット、デュアル承認）を引き上げることで機能する。

## 3. ソーシャルエンジニアリングの物語サイクル

*Practical Social Engineering* / Hadnagyより（一般的なサイクルであり、攻撃のプレイブックではない）:

```
OSINT (public) → Pretext design → Contact → Rapport → Ask → Exit → Report
```

| フェーズ | 何が起きるか | 防御コントロール |
|:---|:---|:---|
| OSINT | 組織や個人に関する公開情報の収集 | 公開する情報の最小化、プライバシー研修 |
| Pretext | もっともらしく聞こえるストーリーの構築 | アクセスを求めるストーリーには疑問を持つ |
| Contact | メール、電話、対面、チャット | 公式チャネルと警告バナー |
| Rapport | 心理的な距離を縮める | 雑談の直後に来る唐突な依頼に注意する |
| Ask | 行動や情報の要求 | 依頼が「些細」に見えても検証を絶対に省略しない |
| Exit | 警戒されずに会話を終える | ログ記録と事後レビュー |
| Report | （許可されたレッドチームの場合）文書化 | 書面のRoEがある場合のみ |

強調しておきたい点: このリポジトリは、フィッシングキットの構築、Evilginxのセットアップ、BadUSBペイロードの作成、欺瞞スクリプトの記述を教えるものではない。焦点は心理学、検知、訓練にある。

## 4. 代表的な経路（概念）

| 経路 | 簡単な説明 | 通常求められるもの |
|:---|:---|:---|
| フィッシング / スピアフィッシング | 行動喚起を含む欺瞞メッセージ | 認証情報、マルウェアクリック、送金先変更 |
| ビッシング | 電話 / VoIP | パスワードリセット、MFAコード、顧客データ |
| スミッシング | SMS / モバイルチャット | 「荷物」や「銀行」のリンク |
| プリテキスティング（ヘルプデスク） | 従業員やベンダーになりすます | アカウントのロック解除、VPNグループへの追加 |
| なりすまし | 物理的接近、バッジのぞき見 | テールゲーティング、「ベンダーの来客」 |
| ビジネスメール詐欺（BEC） | 送金や請求書の不正操作 | 支払口座の変更 |
| クイド・プロ・クオ | 「ITを手伝うので、これをインストールしてください…」 | リモートアクセスツール |

$$
\mathsf{Impact} = \mathsf{PrivilegeGranted} \times \mathsf{DataSensitivity} \times \mathsf{SpeedOfDetection}^{-1}
$$

## 5. 検知シグナル: レッドフラグ

### 言葉・内容

- 極端な緊急性と処罰の脅し。
- 手続きを飛ばすよう求める（「誰にも言わないで」）。
- メールドメインの不一致（同形文字、不自然なサブドメイン）。
- MFAコード、パスワード、シードフレーズの要求（正当なITはこれらを決して求めない）。
- デュアルチャネル検証なしのベンダー口座変更。

### プロセス

- 通常の業務時間外の連絡と即応の圧力。
- 標準外のリモートツールの使用要求。
- チケットやコールバックの拒否。

### クイックトリアージ表

| シグナル | 深刻度 | 直ちに取るべき行動 |
|:---|:---:|:---|
| パスワード / MFAを求める | 高 | 停止し、SOCに報告 |
| 送金指示を変更する | 高 | 経理部門のデュアル承認 |
| 「ログインポータル」のリンク | 中〜高 | 報告し、クリックせず、公式ポータルで検証 |
| PO（発注書）のない「新規」ベンダー | 中 | 調達部門で検証 |
| ドアでのテールゲーティング | 中 | 丁寧に確認し、警備員にエスコートを依頼 |

## 6. 効果的な啓発訓練

悪い訓練とは、年1回のビデオですぐに忘れられるものだ。良い訓練とは、繰り返され、測定可能で、誰も恥をかかせないものだ。

### プログラム設計

1. ベースライン: アンケートに加え、許可された模擬演習（RoEとHRの合意のもとでの社内フィッシングシミュレーション）を行う。
2. 原理を教える: Cialdiniの原理とコールバック手順を教える。「リンクをクリックするな」だけでは不十分。
3. ジャストインタイム: 確定申告シーズン、給与計算、ベンダー更新時期にヒントを提供する。
4. ロールベース: 経理（BEC）、ヘルプデスク（プリテキスティング）、経営層（ホエーリング）。
5. 測定する: 報告率の上昇、繰り返しクリック率の低下、報告までの時間の短縮。
6. 恥をかかせない文化: 迅速な報告が評価される行動になるようにする。

$$
\mathsf{TrainingROI} \propto \frac{\mathsf{ReportRate} \times \mathsf{PreventedLoss}}{\mathsf{ProgramCost}}
$$

### 15分のマイクロカリキュラム例

| 分 | 内容 |
|:---:|:---|
| 0-3 | あなたの業界での実話（匿名化済み） |
| 3-8 | 3つのレッドフラグとその検証方法 |
| 8-12 | シナリオ演習（ビッシングスクリプトへの防御） |
| 12-15 | 報告方法と報告後に何が起きるか |

## 7. 組織的コントロール

| コントロール | 実装 | 対抗する脅威 |
|:---|:---|:---|
| アウトオブバンド検証 | HRディレクトリに載っている番号へのコールバック | ビッシング / BEC |
| デュアルコントロール | 送金や権限付与には2人が必要 | 単独犯による不正 |
| 最小権限 + JIT | 期限付きアクセス | ヘルプデスクへのプリテキスティング |
| メール認証 | SPF、DKIM、DMARCの強制 | ドメインのなりすまし |
| 外部メールバナー | 「外部」の警告表示 | 偽の社内メール |
| ヘルプデスクでの身元確認 | 従業員ID + コールバック | ソーシャルによるアカウント乗っ取り |
| 物理アクセスポリシー | バッジ + 訪問者のエスコート | テールゲーティング |
| 可能な限りフィッシング耐性のあるMFA | パスキー/FIDO2 | 認証情報の窃取 |
| データ分類 | 電話で機微なデータを口にしない | 過剰な情報共有 |

```
Request sensitive action
        │
        ▼
  Ticket required? ──no──▶ deny / redirect
        │ yes
        ▼
  Identity proof (policy)
        │
        ▼
  Out-of-band confirm (if high risk)
        │
        ▼
  Dual approval (if financial / admin)
        │
        ▼
  Execute + audit log
```

## 8. 倫理、法律、許可されたテスト

| 活動 | 要件 |
|:---|:---|
| レッドチームSE / フィッシングシミュレーション | 書面のRoE、法務、HR、経営層スポンサー |
| 従業員へのOSINT | 公開情報源に限定し、現地のプライバシー法を尊重する |
| 物理的ななりすまし | 施設の許可と安全確保のための中止基準 |
| 欺瞞技術を詳細に教える | 「すぐ使えるキット」の配布を避け、検知に焦点を当てる |

法律は法域によって異なる（詐欺、コンピュータへの不正アクセス、通話録音など）。許可のない模擬演習は、法律や雇用契約に違反する可能性がある。

## 9. ソーシャルエンジニアリングのインシデント対応

1. 封じ込め: 欺瞞的な会話を続けない。認証情報が漏洩していればアカウントを保護する。
2. 保全: メールヘッダー、電話番号、（合法な範囲で）録音、チャットログを保存する。
3. リセット: 必要に応じてパスワード、セッション、MFAデバイスをリセットし、転送ルールを確認する。
4. 通知: SOC / IR、BECの場合は経理部門、顧客データが絡む場合は法務部門に連絡する。
5. ハント: メールボックスルール、新しい代理受信者、通常と異なるVPN利用を確認する。
6. 教訓: 訓練とコントロールを更新する。報告してくれた被害者を責めない。

$$
t_{\text{detect}} \downarrow \Rightarrow \mathsf{ExpectedLoss} \downarrow
$$

## 10. 防御チートシート

```text
CHECK BEFORE YOU ACT
[ ] Is there manufactured urgency?
[ ] Is identity verified through an official channel?
[ ] Is a normal procedure being skipped?
[ ] Is a secret being requested (password/MFA/seed)?
[ ] Is there an account or admin-access change?

IF YES TO ANY → STOP → TICKET / CALLBACK → REPORT
```

| 役割 | ひとつの黄金習慣 |
|:---|:---|
| すべての従業員 | 間違っているかもしれないと恐れず、不審な点を報告する |
| ヘルプデスク | ポリシーで定めた証明なしにリセットしない |
| 経理 | 支払変更には常にデュアルチャネル |
| エグゼクティブアシスタント | スケジュールや送金の前にホエーリングチェックリストを確認する |
| セキュリティ | クリック率だけでなく報告率を測定する |

## セキュリティノート: 脅威と防御

| 脅威 | メカニズム | 防御 |
|:---|:---|:---|
| 認証情報の窃取 | 偽ログイン / ビッシング | FIDO2、MFAコードを決して共有しない、報告する |
| BEC詐欺 | 請求書詐欺 / CEO詐欺 | デュアルコントロール、ベンダーへのコールバック |
| ヘルプデスクへのプリテキスティング | ソーシャルによるリセット | 強固な身元確認 |
| テールゲーティング | 物理的な追従入館 | 見知らぬ人に声をかける文化、ターンスタイル |
| 過剰な情報共有 | ラポールの悪用 | データ分類、need-to-know原則 |
| 恥の文化 | インシデントが隠蔽される | 迅速な報告を評価する |

扱わない内容: フィッシングキットの構築、プロキシによる認証情報の収集、BadUSBペイロード、すぐに使える欺瞞スクリプト。
