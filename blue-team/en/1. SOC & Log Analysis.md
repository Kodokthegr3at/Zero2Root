## Key terms

| Term | Meaning |
|:---|:---|
| Blue team | The defenders: they monitor, detect, and respond to attacks |
| SOC | Security Operations Center, the team that watches a company's security around the clock |
| Log | An automatic record of what happened on a system (who logged in, when, from where) |
| SIEM | Software that collects and searches logs from many machines at once (Splunk, Wazuh, Elastic) |
| Alert | An automatic warning when something suspicious happens |
| Triage | Sorting alerts into serious and harmless |
| False positive | An alert that turns out not to be an attack |
| IOC | Indicator of Compromise: traces of an attack such as a malicious IP, a malware hash, or an odd domain |
| Incident response | The steps for handling an attack that has already happened |

## 1. Red team vs blue team

Picture a house. The red team is the person the owner hires to try to break in so the weak spots come to light. The blue team is the guard, the CCTV, and the alarm.

| | Red team | Blue team |
|:---|:---|:---|
| Job | Find weaknesses (with permission) | Detect and stop attacks |
| Main question | "Where can I get in?" | "Did someone get in? When? How?" |
| Typical tools | Nmap, Burp Suite | SIEM, EDR, Wireshark, logs |
| Job openings | Fewer | Many more |

A lot of people start their security career as a Level 1 SOC Analyst, so this lesson also helps with job hunting.

## 2. What a SOC is

A SOC watches a company's security continuously, usually in 24-hour shifts. The flow looks roughly like this:

```
           ┌─────────────────────────────────────┐
 Server ──►│                                     │
 Laptop ──►│   SIEM  (collect + search + alert)  │──► Alert ──► L1 analyst (triage)
Firewall ─►│                                     │                   │
           └─────────────────────────────────────┘                   ▼
                                                        serious? ──► L2/L3 analyst (investigate)
                                                                              │
                                                                              ▼
                                                                     Incident Response
```

| Role | Daily work |
|:---|:---|
| L1 analyst | Looks at incoming alerts and decides whether they are real or false positives |
| L2 analyst | Digs deeper: what happened and how far it spread |
| L3 analyst / Threat Hunter | Looks for attacks that never triggered an alert |
| Detection Engineer | Writes new detection rules |

## 3. Logs, the computer's diary

Every time someone logs in, runs a program, or opens a website, the system writes a line about it. That line is a log entry. Without logs, the blue team has nothing to investigate.

A single log line usually answers when, where, what, who, and from where:

```
Oct 16 09:12:44 server1 sshd[2211]: Failed password for root from 203.0.113.50 port 51122 ssh2
└─── when ───┘ └ where ┘ └ what ┘   └──── what happened ───────┘ └ who┘   └─── from where ──┘
```

The logs you will open most often:

| Source | Location / name | Contents |
|:---|:---|:---|
| Linux logins (Debian/Ubuntu) | `/var/log/auth.log` | SSH logins, sudo, wrong passwords |
| Linux logins (Fedora/RHEL) | `/var/log/secure` or `journalctl` | Same as above |
| Web server | `/var/log/nginx/access.log`, `/var/log/apache2/access.log` | Every request to the site |
| Windows | Event Viewer, Security section | Event ID 4624 (successful logon), 4625 (failed logon), 4688 (new process) |
| Firewall | Depends on the product | Allowed or blocked connections |

Windows Event IDs 4624, 4625, and 4688 come up in SOC interviews a lot, so it is worth memorizing them.

## 4. Reading Linux logs by hand

Before you touch a SIEM, get used to reading logs with basic commands. You already learned `grep`, `awk`, and `sort` in [LC-019](../../linux/en/12.%20Filter%20Contents%20%E2%80%94%20Output%20Filtering%20%26%20Text%20Processing.md).

### 4.1 Who failed to log in?

```bash
# Debian/Ubuntu
sudo grep "Failed password" /var/log/auth.log | tail

# Fedora/RHEL (systemd journal)
sudo journalctl -u sshd | grep "Failed password" | tail
```

### 4.2 Which IP failed most often?

If one IP fails hundreds of times, it is almost certainly brute force.

```bash
sudo grep "Failed password" /var/log/auth.log \
  | grep -oE 'from [0-9.]+' \
  | sort | uniq -c | sort -rn | head
```

Example output:

```
    412 from 203.0.113.50     ← 412 failures, almost certainly brute force
      3 from 192.168.1.10     ← probably you mistyping
```

### 4.3 Did that IP eventually get in?

Hundreds of failed attempts are noisy, but the thing to act on right away is a successful login from the same IP.

```bash
sudo grep "Accepted" /var/log/auth.log | grep 203.0.113.50
```

If this prints anything, the attacker is in. Escalate to the analyst above you.

### 4.4 Who used sudo?

```bash
sudo grep "sudo:" /var/log/auth.log | grep COMMAND
```

### 4.5 Reading a web access log

```bash
# Top 10 IPs by request count
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head

# Requests that returned 404 (often scanners looking for files)
awk '$9 == 404 {print $1, $7}' /var/log/nginx/access.log | head
```

Signs of a scanner or attacker in an access log:

| What you see | What it probably means |
|:---|:---|
| Hundreds of 404s in a minute from one IP | Directory brute force (gobuster and friends) |
| Requests for `/wp-admin`, `/.env`, `/.git/` when you do not run WordPress | Bots hunting for common holes |
| User-Agent `sqlmap`, `Nikto`, `Nmap` | A scanner that does not bother to hide |
| Odd characters in the URL (`'`, `<script>`, `../`) | Injection attempts (see [LC-047](../../web/Vulnerabilities/en/1.%20SQL%20Injection%20%28SQLi%29.md), [LC-048](../../web/Vulnerabilities/en/2.%20Cross-Site%20Scripting%20%28XSS%29.md), [LC-051](../../web/Vulnerabilities/en/5.%20Command%20Injection%20%26%20File%20Inclusion%20%28LFI%20%26%20RFI%29.md)) |

## 5. SIEM: all logs in one place

A company can have hundreds of servers, and running `grep` on each of them is not realistic. A SIEM pulls logs from every machine into one place. There you can search all machines at once, write rules that raise alerts automatically, and build dashboards such as failed logins per hour.

| SIEM | Notes |
|:---|:---|
| Wazuh | Free and open source, the best fit for a home lab |
| Elastic (ELK) | Free basic tier, widely used |
| Splunk | Most common in enterprises, has a Free edition (500 MB/day) |
| Microsoft Sentinel | Cloud SIEM on Azure |

The same search in two SIEMs:

```text
Splunk:  index=linux "Failed password" | stats count by src_ip | sort -count
Elastic: event.outcome:failure AND event.category:authentication
```

The logic is the same as the `grep | sort | uniq -c` pipeline in section 4. Once the manual version makes sense, a SIEM is just new syntax.

## 6. Alerts, triage, and false positives

An L1 analyst can get hundreds of alerts a day and has to decide quickly which ones need follow-up. That sorting is called triage. For each alert, ask:

1. What triggered it? Read the rule.
2. Which user and machine are involved? A production server matters more than an intern's laptop.
3. Is this normal? An admin logging in at 3 a.m. from abroad is odd. A login from the office at 9 a.m. is not.
4. Did the attack succeed? A failed login and a successful one carry very different weight.
5. What happened before and after? After the login, was there `sudo`, a file download, or a strange outbound connection?

| Triage result | Meaning | Action |
|:---|:---|:---|
| True positive | A real attack | Escalate to L2 or the IR team |
| False positive | Not an attack, e.g. an employee forgot their password | Close, record why, suggest a rule fix |
| Benign true positive | The activity happened but was legitimate, e.g. an authorized pentest | Close and record |

## 7. Incident response in 4 steps (NIST SP 800-61)

If triage shows a real attack, follow this cycle:

```
 1. Preparation ──► 2. Detection & Analysis ──► 3. Containment, Eradication, Recovery ──► 4. Post-incident
      ▲                                                                                       │
      └──────────────────────── lessons feed into the next round of preparation ◄─────────────┘
```

Example for a successful SSH brute force:

| Step | What you do |
|:---|:---|
| 1. Preparation | Logging enabled, SIEM in place, an emergency contact list exists |
| 2. Detection & analysis | Alert fires: successful login from 203.0.113.50 after 412 failures |
| 3. Containment | Block the IP at the firewall ([LC-034](../../linux/en/27.%20Firewall%20Setup.md)), lock the compromised account, isolate the server |
| 3. Eradication | Hunt for backdoors: new users, odd cron jobs ([LC-025](../../linux/en/18.%20Task%20Scheduling.md)), unknown SSH keys in `~/.ssh/authorized_keys` |
| 3. Recovery | Change passwords, disable SSH password login (keys only), restore from backup if needed |
| 4. Post-incident | Find out why root could log in over SSH, fix the config, write a new alert rule |

```text
Oct 16 02:10:02 web1 sshd[902]: Failed password for root from 198.51.100.7 port 40002 ssh2
Oct 16 02:10:03 web1 sshd[903]: Failed password for admin from 198.51.100.7 port 40003 ssh2
Oct 16 02:10:04 web1 sshd[904]: Failed password for admin from 198.51.100.7 port 40004 ssh2
```

1. Which IP is brute forcing?
2. How many times did it fail?
3. Which account was compromised, and at what time?
4. What did the attacker run after getting in, and why is it dangerous?
5. Is the `sari` activity at 09:00 suspicious?

```bash

grep "COMMAND" practice.log
```
