## Key terms

| Term | Meaning |
|:---|:---|
| NSM | Network Security Monitoring: collecting and analyzing traffic to detect attacks |
| PCAP | A file holding a full recording of network packets |
| Flow | A connection summary: who talked to whom, which port, how many bytes, how long |
| IDS | Intrusion Detection System: alerts when traffic matches an attack pattern |
| IPS | Intrusion Prevention System: like an IDS, but can block on the spot |
| Signature | A rule describing a specific attack pattern |
| Beaconing | Malware contacting its C2 server at regular intervals, e.g. every 60 seconds |
| C2 | Command and Control, the server an attacker uses to steer infected machines |
| JA3/JA4 | TLS client fingerprints, useful for spotting malware even when traffic is encrypted |

## 1. Why monitor the network

Host logs ([LC-072](1.%20SOC%20%26%20Log%20Analysis.md)) can be wiped once an attacker becomes root. Network traffic is harder to fake because it has already gone past before the attacker gets a chance to clean up. Printers, IP cameras, and IoT devices ([LC-070](../../hardware-iot/en/Hardware%20%26%20IoT%20Security%20%E2%80%94%20Interfaces%2C%20Firmware%20%26%20Automotive.md)) often keep no logs at all, but their traffic still crosses the network.

An NSM sensor usually sits at the network's ingress/egress point and receives a copy of the traffic from a mirror port (SPAN) or a network TAP.

```
 Internet ── Firewall ── Switch ──┬── Server
                            │     └── Laptop
                       mirror port
                            │
                       ┌────▼────┐
                       │ Sensor  │  Zeek + Suricata + PCAP recording
                       └────┬────┘
                            ▼
                          SIEM
```

## 2. Three kinds of network data

| Kind | Contents | Size | Example tools | When to use it |
|:---|:---|:---|:---|:---|
| Full packet capture | Every byte | Huge | tcpdump, Wireshark | Complete evidence, deep analysis |
| Transaction logs | Per-protocol summaries (DNS queries, HTTP requests, TLS certificates) | Medium | Zeek | Daily investigation, threat hunting |
| Flow | Who talked to whom, how many bytes | Small | NetFlow, IPFIX | Big-picture patterns, can be kept for months |
| Alerts | Only what matched a signature | Tiny | Suricata, Snort | Automated detection |

A common practice: keep flow for months, Zeek logs for a few weeks, and full PCAP for only a few days because of its size.

## 3. Wireshark for packet analysis

Capturing packets was covered in [LC-032](../../linux/en/25.%20Linux%20Networking%20%E2%80%94%20Diagnostics%20%26%20Packet%20Analysis.md). Here the focus is reading a PCAP to find signs of attack.

### 3.1 Display filters you will use often

| Goal | Filter |
|:---|:---|
| Traffic to/from one IP | `ip.addr == 10.0.0.5` |
| HTTP requests only | `http.request` |
| HTTP logins via POST | `http.request.method == "POST"` |
| DNS queries only | `dns.flags.response == 0` |
| SYN without ACK (port scan hint) | `tcp.flags.syn == 1 && tcp.flags.ack == 0` |
| Server name in TLS (SNI) | `tls.handshake.extensions_server_name` |
| Packets containing a word | `frame contains "password"` |

### 3.2 The most useful menus

1. **Statistics > Conversations**: sort by bytes. A very large outbound connection may mean exfiltration.
2. **Statistics > Protocol Hierarchy**: unusual protocols (IRC, Tor) stand out immediately.
3. **Follow > TCP Stream**: read the whole conversation like a chat.
4. **File > Export Objects > HTTP**: pull out files downloaded over HTTP, such as malware. Open them only in an analysis VM ([LC-063](../../malware-analysis/en/1.%20Static%20Malware%20Analysis%20Fundamentals.md)).

### 3.3 tshark for repetitive work

```bash
# Top 10 queried domains
tshark -r capture.pcap -Y "dns.flags.response==0" -T fields -e dns.qry.name \
  | sort | uniq -c | sort -rn | head

# Every HTTP User-Agent
tshark -r capture.pcap -Y http.request -T fields -e http.user_agent | sort -u
```

## 4. Zeek: turning traffic into logs

Zeek does not raise alerts. It reads traffic and writes tidy logs per protocol, and those logs are what analysts search later.

```bash
# Process a PCAP; .log files land in the current directory
zeek -C -r capture.pcap
ls
# conn.log  dns.log  http.log  ssl.log  files.log  weird.log ...
```

| Log file | Contents |
|:---|:---|
| `conn.log` | Every connection: IPs, ports, duration, bytes |
| `dns.log` | DNS queries and answers |
| `http.log` | Method, host, URI, User-Agent, status |
| `ssl.log` | TLS version, SNI, certificate details |
| `files.log` | Files seen on the wire, with hashes |
| `weird.log` | Things that break protocol standards |

`zeek-cut` pulls out specific columns:

```bash
# Longest connections
cat conn.log | zeek-cut id.orig_h id.resp_h id.resp_p duration | sort -k4 -rn | head

# HTTP hosts visited
cat http.log | zeek-cut host uri | sort | uniq -c | sort -rn | head
```

## 5. Suricata: signature-based IDS

Suricata matches traffic against thousands of rules. The most common free ruleset is Emerging Threats Open.

### 5.1 Anatomy of a rule

```text
alert http any any -> any any (msg:"Possible SQLi in URI"; \
    http.uri; content:"UNION"; nocase; content:"SELECT"; nocase; \
    sid:1000001; rev:1;)
```

| Part | Meaning |
|:---|:---|
| `alert` | Action: raise an alert (`drop` in IPS mode) |
| `http any any -> any any` | Protocol, source, destination |
| `msg` | Text shown in the alert |
| `http.uri; content:"UNION"` | Look for `UNION` in the URI |
| `nocase` | Case-insensitive |
| `sid` | Unique rule ID; local rules use numbers above 1000000 |

### 5.2 Running it on a PCAP

```bash
sudo suricata -r capture.pcap -S local.rules -l ./out
cat out/fast.log
# Alerts are also written as JSON in out/eve.json
jq 'select(.event_type=="alert") | .alert.signature' out/eve.json | sort | uniq -c
```

### 5.3 Limits

Signatures only catch what is already known. HTTPS payloads are encrypted, so Suricata can only see metadata such as SNI, certificates, and JA3. That gap is where Zeek logs and threat hunting ([LC-074](3.%20Threat%20Hunting%20%26%20Detection%20Engineering%20%28Sigma%2C%20YARA%2C%20ATT%26CK%29.md)) come in.

## 6. Attack patterns visible on the wire

| Pattern | What it looks like | How to check |
|:---|:---|:---|
| Port scan | One IP sends SYNs to many ports, mostly answered by RST | `conn.log`: many `REJ` or `S0` states from one source |
| Brute force | Hundreds of short connections to port 22/3389/445 | Group `conn.log` by source and destination port |
| Beaconing | Connections to the same IP at near-identical intervals | Compute time gaps between connections; a constant gap like 60 s is suspicious |
| DNS tunneling | Very long random subdomains, lots of TXT records | `dns.log`: `query` longer than 50 characters |
| Exfiltration | Large uploads to a rarely used IP | `conn.log`: `orig_bytes` far larger than `resp_bytes` |
| ARP spoofing | One MAC claims many IPs | Wireshark: `arp.duplicate-address-detected` ([LC-042](../../networking/en/ARP%20%26%20Local%20Network%20Attacks.md)) |

Finding DNS tunneling candidates in Zeek:

```bash
cat dns.log | zeek-cut query | awk 'length($1) > 50' | head
```

## 7. Practice

### Task 1: concepts

1. Which kind of network data is smallest but can be kept the longest?
2. Does Zeek produce alerts or logs?
3. Why does Suricata struggle to detect attacks inside HTTPS?
4. A connection to one IP every 60 seconds for 8 hours is which pattern?

<details><summary>Answer key</summary>

1. Flow (NetFlow/IPFIX)
2. Logs. Zeek is not alert-focused.
3. The payload is encrypted, so only metadata (SNI, certificate, JA3) can be matched.
4. Beaconing, probably malware calling its C2.

</details>

### Task 2: conn.log analysis

A slice of `conn.log` (columns: time, source IP, destination IP, port, orig_bytes, resp_bytes):

```text
10:00:00 10.0.0.23 185.199.10.5 443 320 1200
10:01:00 10.0.0.23 185.199.10.5 443 318 1200
10:02:00 10.0.0.23 185.199.10.5 443 321 1200
10:02:30 10.0.0.40 10.0.0.1 53 60 120
10:03:00 10.0.0.23 185.199.10.5 443 319 1200
10:05:12 10.0.0.31 203.0.113.80 443 734003200 4100
10:06:00 10.0.0.12 10.0.0.50 22 0 0
10:06:00 10.0.0.12 10.0.0.50 23 0 0
10:06:00 10.0.0.12 10.0.0.50 80 0 0
10:06:01 10.0.0.12 10.0.0.50 445 0 0
```

1. Which host shows beaconing?
2. Which host is probably exfiltrating, and roughly how much data?
3. Which host is port scanning?

<details><summary>Answer key</summary>

1. `10.0.0.23` to `185.199.10.5`, every 60 seconds with nearly identical sizes.
2. `10.0.0.31` sent about 700 MB to `203.0.113.80` and received only 4 KB.
3. `10.0.0.12` tried ports 22, 23, 80, 445 on `10.0.0.50` within one second with no data.

</details>

### Task 3: write a Suricata rule

Write a rule that alerts when the HTTP User-Agent contains `sqlmap`. Test it on a PCAP you record yourself while running sqlmap against a local DVWA.

<details><summary>Sample answer</summary>

```text
alert http any any -> any any (msg:"sqlmap scanner detected"; \
    http.user_agent; content:"sqlmap"; nocase; sid:1000002; rev:1;)
```

</details>

## 8. Quick reference

```text
WIRESHARK
  ip.addr==X · http.request · dns.flags.response==0 · tls.handshake.extensions_server_name
  Statistics > Conversations · Follow TCP Stream · Export Objects > HTTP

ZEEK
  zeek -C -r file.pcap
  cat conn.log | zeek-cut id.orig_h id.resp_h id.resp_p orig_bytes resp_bytes

SURICATA
  suricata -r file.pcap -S my.rules -l out/   →  out/fast.log, out/eve.json
  alert <proto> src port -> dst port (msg:"..."; content:"..."; sid:1000001; rev:1;)

PATTERNS
  scan: many ports, no data · beacon: constant gap · exfil: orig_bytes >> resp_bytes
  DNS tunnel: very long queries
```
