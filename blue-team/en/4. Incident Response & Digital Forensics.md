## Key terms

| Term | Meaning |
|:---|:---|
| DFIR | Digital Forensics and Incident Response |
| Artifact | A trace left on a system by activity, e.g. a Prefetch file or a registry entry |
| Acquisition | Making a forensically sound copy of evidence (disk or memory) |
| Image | A bit-for-bit copy of a disk or RAM saved to a file |
| Chain of custody | A record of who held the evidence, when, and why |
| Write blocker | A device that prevents writes to the evidence disk while it is copied |
| Timeline | A sequence of events assembled from many artifacts |
| Persistence | How an attacker keeps access across reboots |
| Triage collection | Quickly gathering only the key artifacts instead of a full disk image |

## 1. IR and forensics: how they fit together

Incident response aims to stop the attack and restore service as fast as possible. Forensics aims to answer, with evidence, what happened, how, and since when. They run side by side: IR needs forensic answers to know what to clean up, and forensics needs IR to avoid destroying evidence during containment.

| Question | Answered with |
|:---|:---|
| How did the attacker get in? | Web logs, email, execution artifacts |
| When did they first get in? | The timeline |
| Which machines did they touch? | Authentication logs, lateral movement artifacts |
| What data did they take? | Network logs, file access artifacts |
| Are they still inside? | Persistence checks, memory |

## 2. Order of volatility

Collect the evidence that disappears fastest first (RFC 3227).

| Order | Evidence | Lost when |
|:---|:---|:---|
| 1 | CPU registers, cache | Nanoseconds |
| 2 | RAM: processes, network connections, encryption keys | The machine powers off |
| 3 | Network state, ARP table | Minutes |
| 4 | Temp files, swap | Reboot or cleanup |
| 5 | Disk | Overwritten |
| 6 | Remote logs, backups | Log rotation |

A common mistake is pulling the power cable right away. Memory is gone, and fileless malware ([LC-074](3.%20Threat%20Hunting%20%26%20Detection%20Engineering%20%28Sigma%2C%20YARA%2C%20ATT%26CK%29.md)) lives only in RAM. When possible, image memory first, then isolate the network.

## 3. Chain of custody and evidence integrity

If a case might end up in court or with HR, you must be able to show the evidence never changed.

```bash
# Hash evidence right after acquisition
sha256sum disk.img > disk.img.sha256

# Verify at any later point
sha256sum -c disk.img.sha256
```

A chain of custody form contains at least:

| Field | Example |
|:---|:---|
| Evidence ID | EV-2026-014-01 |
| Description | Dell Latitude laptop, S/N XXXX, 512 GB NVMe disk |
| Collected by / time | Analyst A, 2026-10-16 14:05 UTC+7 |
| SHA-256 hash | `9f86d0...` |
| Handed to / time / reason | Analyst B, 2026-10-16 16:30, analysis |

The rule: always analyze a copy, never the original evidence.

## 4. Acquisition: disk and memory

### 4.1 Memory

| OS | Free tools | Example |
|:---|:---|:---|
| Windows | WinPmem, DumpIt, Magnet RAM Capture | `winpmem.exe mem.raw` |
| Linux | LiME (kernel module), AVML | `sudo avml mem.lime` |
| VM | Hypervisor snapshot | The `.vmem` file in VMware |

### 4.2 Disk

```bash
# Full disk image (connect the evidence disk through a write blocker)
sudo dc3dd if=/dev/sdb of=disk.img hash=sha256 log=acquisition.log

# Alternative: ewfacquire produces compressed E01 files with stored metadata
sudo ewfacquire /dev/sdb
```

### 4.3 Triage collection

Imaging a 1 TB disk can take hours. Across many machines, collect only the key artifacts:

| Tool | Purpose |
|:---|:---|
| KAPE | Collects Windows artifacts (registry, event logs, Prefetch) in minutes |
| Velociraptor | Collection and hunting across hundreds of endpoints at once |
| UAC (Unix-like Artifacts Collector) | The Linux and macOS equivalent |

## 5. Memory forensics with Volatility 3

```bash
pip install volatility3
vol -f mem.raw windows.info          # identify the OS
vol -f mem.raw windows.pslist        # process list
vol -f mem.raw windows.pstree        # processes with parents
vol -f mem.raw windows.cmdline       # each process's command line
vol -f mem.raw windows.netscan       # network connections
vol -f mem.raw windows.malfind       # suspicious executable memory (injection hint)
vol -f mem.raw windows.dlllist --pid 1234
```

What to look for:

| Sign | Example |
|:---|:---|
| Names that imitate system processes | `svch0st.exe`, `lsas.exe` |
| Wrong location | `svchost.exe` running from `C:\Users\...\AppData` |
| Wrong parent | A `svchost.exe` whose parent is not `services.exe` |
| Outbound connections from unlikely processes | `notepad.exe` talking to port 443 |
| `malfind` hits | A `PAGE_EXECUTE_READWRITE` region containing an `MZ` header |

Memorize the normal Windows process tree: `System` → `smss.exe` → `wininit.exe` → `services.exe` → `svchost.exe`, and `wininit.exe` → `lsass.exe`. There must be exactly one `lsass.exe`.

## 6. The Windows artifacts you will use most

| Artifact | Location | Answers |
|:---|:---|:---|
| Event Logs | `C:\Windows\System32\winevt\Logs\*.evtx` | Logons (4624/4625), processes (4688), new services (7045), cleared logs (1102) |
| Prefetch | `C:\Windows\Prefetch\*.pf` | Which programs ran, when, and how many times |
| Amcache | `C:\Windows\AppCompat\Programs\Amcache.hve` | Programs executed, with SHA-1 hashes |
| ShimCache | `SYSTEM` registry hive | Programs that existed on disk |
| Registry Run keys | `HKLM\...\Run`, `HKCU\...\Run` | Persistence |
| Scheduled Tasks | `C:\Windows\System32\Tasks\` | Persistence |
| LNK & Jump Lists | `%AppData%\Microsoft\Windows\Recent\` | Which files the user opened |
| ShellBags | `NTUSER.DAT`, `UsrClass.dat` | Which folders were browsed |
| $MFT, $UsnJrnl | NTFS root | Files created, modified, deleted ([LC-006](../../basics/OperatingSystem/en/Windows%20File%20System.md)) |
| Browser history | Chrome/Edge/Firefox profiles | Sites visited and files downloaded |

Extra Event IDs for IR:

| ID | Meaning |
|:---|:---|
| 4720 | User account created |
| 4732 | User added to a local group (e.g. Administrators) |
| 4698 | Scheduled task created |
| 7045 | New service installed |
| 1102 | Security log cleared, almost always a red flag |
| 4648 | Logon with explicit credentials (runas, lateral movement) |

Free parsers from Eric Zimmerman (EZ Tools): `PECmd` for Prefetch, `AmcacheParser`, `RECmd` for the registry, `MFTECmd`, `EvtxECmd`, and Timeline Explorer to read the output. For event logs, Hayabusa and Chainsaw scan `.evtx` files directly with Sigma rules ([LC-074](3.%20Threat%20Hunting%20%26%20Detection%20Engineering%20%28Sigma%2C%20YARA%2C%20ATT%26CK%29.md)).

```powershell
PECmd.exe -d C:\case\Prefetch --csv C:\case\out
hayabusa.exe csv-timeline -d C:\case\evtx -o timeline.csv
```

## 7. Linux artifacts

| Artifact | Location | Answers |
|:---|:---|:---|
| Auth logs | `/var/log/auth.log`, `/var/log/secure`, `journalctl` | Logins, sudo ([LC-072](1.%20SOC%20%26%20Log%20Analysis.md)) |
| Shell history | `~/.bash_history`, `~/.zsh_history` | Commands typed |
| Last logins | `last`, `lastb`, `/var/log/wtmp` | Who logged in, from where |
| Cron | `/etc/crontab`, `/var/spool/cron/`, `/etc/cron.*` | Persistence ([LC-025](../../linux/en/18.%20Task%20Scheduling.md)) |
| systemd | `/etc/systemd/system/`, `~/.config/systemd/user/` | Service persistence |
| SSH keys | `~/.ssh/authorized_keys` | Key-based backdoors |
| New users | `/etc/passwd`, `/etc/shadow` | Extra accounts, UID 0 other than root |
| New files | `find / -newermt "2026-10-15" -type f` | What changed since the incident date |
| Processes | `/proc/<pid>/exe`, `/proc/<pid>/cmdline` | Binaries deleted from disk but still running |

A useful trick: attackers often delete their binary after launching it. If the process is still alive, you can recover the original file:

```bash
ls -l /proc/*/exe 2>/dev/null | grep deleted
sudo cp /proc/4242/exe /case/recovered_4242.bin
```

## 8. Building a timeline

A timeline merges many sources into one sequence of events.

```bash
# Plaso: parse a disk image into a single timeline
log2timeline.py --storage-file case.plaso disk.img
psort.py -o l2tcsv -w timeline.csv case.plaso "date > '2026-10-15'"
```

A timeline after the analyst has trimmed it:

| Time (UTC) | Source | Event |
|:---|:---|:---|
| 10-15 08:02 | Email gateway | Email "Invoice_Oct.xlsm" delivered to rina@ |
| 10-15 08:05 | Prefetch | `EXCEL.EXE` executed |
| 10-15 08:05 | Sysmon 1 | Excel launched `powershell -enc ...` |
| 10-15 08:06 | Zeek conn | Connection to 203.0.113.99:443 |
| 10-15 08:06 | Registry | Run key `Updater` created |
| 10-15 13:40 | 4624 type 3 | Account rina logged on to FILESRV01 |
| 10-15 13:52 | Zeek conn | 2.1 GB upload from FILESRV01 to 203.0.113.99 |

From this you can see the entry point (phishing), persistence, lateral movement, and exfiltration, each with a timestamp.

## 9. Writing an incident report

| Section | Content |
|:---|:---|
| Executive summary | One paragraph for management: what happened, impact, current status |
| Scope | Systems examined, time range |
| Timeline | A table like the one in section 8 |
| Technical findings | Per finding: evidence, artifact, ATT&CK technique |
| IOCs | IPs, domains, hashes, file names, Run keys |
| Root cause | Why the attack succeeded |
| Recommendations | Short term (already done) and long term |

Write facts with their sources. Separate "proven" ("Prefetch shows `mimikatz.exe` ran at 13:45") from "suspected" ("domain credentials were likely stolen as well").

### Task 1: concepts

1. Which comes first: a disk image or a memory image? Why?
2. The Windows Event ID for a newly installed service?
3. Which Windows artifact shows that a program ran, along with a run count?
4. Why analyze a copy instead of the original evidence?

<details><summary>Answer key</summary>

1. Memory, because it is the most volatile and disappears the moment the machine powers off.
2. 7045
3. Prefetch
4. So the original stays unchanged, its hash still matches, and the chain of custody remains valid.

</details>

### Task 2: read Volatility output

```text
PID   PPID  ImageFileName   Path
4     0     System
388   4     smss.exe        \SystemRoot\System32\smss.exe
512   388   wininit.exe     C:\Windows\System32\wininit.exe
620   512   services.exe    C:\Windows\System32\services.exe
636   512   lsass.exe       C:\Windows\System32\lsass.exe
812   620   svchost.exe     C:\Windows\System32\svchost.exe
2210  3104  svchost.exe     C:\Users\rina\AppData\Roaming\svchost.exe
3104  2988  powershell.exe  C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
2988  2400  EXCEL.EXE       C:\Program Files\Microsoft Office\root\Office16\EXCEL.EXE
```

1. Which process is fake? Give two reasons.
2. Lay out the process chain from the start to the fake process.
3. Which Volatility plugins would you run next on that process?

<details><summary>Answer key</summary>

1. PID 2210 `svchost.exe`. It lives in `AppData\Roaming` instead of `System32`, and its parent is `powershell.exe` instead of `services.exe`.
2. `EXCEL.EXE` (2988) → `powershell.exe` (3104) → fake `svchost.exe` (2210).
3. `windows.netscan` for its connections, `windows.cmdline --pid 2210`, `windows.malfind --pid 2210`, then dump the process for analysis ([LC-063](../../malware-analysis/en/1.%20Static%20Malware%20Analysis%20Fundamentals.md)).

</details>
