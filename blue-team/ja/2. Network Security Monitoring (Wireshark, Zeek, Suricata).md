## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| NSM | Network Security Monitoring。攻撃を検知するためにトラフィックを収集・分析すること |
| PCAP | ネットワークパケットを丸ごと記録したファイル |
| フロー | 接続の要約。誰が誰と、どのポートで、何バイト、どれくらいの時間通信したか |
| IDS | Intrusion Detection System。攻撃パターンに一致するトラフィックでアラートを出す |
| IPS | Intrusion Prevention System。IDSと同様だが、その場でブロックできる |
| シグネチャ | 特定の攻撃パターンを記述したルール |
| ビーコン | マルウェアが一定間隔(例: 60秒ごと)でC2サーバに接続すること |
| C2 | Command and Control。攻撃者が感染マシンを操るためのサーバ |
| JA3/JA4 | TLSクライアントの指紋。暗号化された通信でもマルウェアの識別に役立つ |

## 1. なぜネットワークを監視するのか

ホストのログ([LC-072](1.%20SOC%20%26%20Log%20Analysis.md))は、攻撃者がrootになれば消されてしまう。ネットワークトラフィックは、攻撃者が痕跡を消す前にすでに流れ去っているので偽装が難しい。また、プリンタ、IPカメラ、IoT機器([LC-070](../../hardware-iot/ja/Hardware%20%26%20IoT%20Security%20%E2%80%94%20Interfaces%2C%20Firmware%20%26%20Automotive.md))はログを持たないことが多いが、その通信はネットワーク上に現れる。

NSMセンサーは通常ネットワークの出入口に置かれ、ミラーポート(SPAN)やネットワークTAPからトラフィックのコピーを受け取る。

```
 Internet ── Firewall ── Switch ──┬── Server
                            │     └── Laptop
                       ミラーポート
                            │
                       ┌────▼────┐
                       │ Sensor  │  Zeek + Suricata + PCAP記録
                       └────┬────┘
                            ▼
                          SIEM
```

## 2. 3種類のネットワークデータ

| 種類 | 内容 | サイズ | ツール例 | 使いどころ |
|:---|:---|:---|:---|:---|
| フルパケットキャプチャ | すべてのバイト | 非常に大きい | tcpdump、Wireshark | 完全な証拠、詳細分析 |
| トランザクションログ | プロトコルごとの要約(DNSクエリ、HTTPリクエスト、TLS証明書) | 中 | Zeek | 日々の調査、スレットハンティング |
| フロー | 誰が誰と、何バイト | 小さい | NetFlow、IPFIX | 全体傾向の把握。数か月保存できる |
| アラート | シグネチャに一致したものだけ | ごく小さい | Suricata、Snort | 自動検知 |

よくある運用は、フローを数か月、Zeekログを数週間、フルPCAPはサイズの都合で数日だけ保存するというものである。

## 3. Wiresharkによるパケット分析

パケットの取得はLC-032で扱った。ここでは攻撃の兆候を探すためにPCAPを読むことに集中する。

### 3.1 よく使う表示フィルタ

| 目的 | フィルタ |
|:---|:---|
| 1つのIPとの通信 | `ip.addr == 10.0.0.5` |
| HTTPリクエストのみ | `http.request` |
| POSTによるHTTPログイン | `http.request.method == "POST"` |
| DNSクエリのみ | `dns.flags.response == 0` |
| ACKなしのSYN(ポートスキャンの兆候) | `tcp.flags.syn == 1 && tcp.flags.ack == 0` |
| TLSのサーバ名(SNI) | `tls.handshake.extensions_server_name` |
| 特定の語を含むパケット | `frame contains "password"` |

### 3.2 特に役立つメニュー

1. **Statistics > Conversations**: バイト数で並べ替える。極端に大きい外向き接続は情報持ち出しの可能性がある。
2. **Statistics > Protocol Hierarchy**: 珍しいプロトコル(IRC、Torなど)がすぐ目に付く。
3. **Follow > TCP Stream**: 会話全体をチャットのように読める。
4. **File > Export Objects > HTTP**: HTTPでダウンロードされたファイル(マルウェアなど)を取り出す。開くのは分析用VMの中だけにする([LC-063](../../malware-analysis/ja/1.%20Static%20Malware%20Analysis%20Fundamentals.md))。

### 3.3 繰り返し作業にはtshark

```bash
# 問い合わせ回数の多いドメイン上位10
tshark -r capture.pcap -Y "dns.flags.response==0" -T fields -e dns.qry.name \
  | sort | uniq -c | sort -rn | head

# すべてのHTTP User-Agent
tshark -r capture.pcap -Y http.request -T fields -e http.user_agent | sort -u
```

## 4. Zeek: トラフィックをログに変える

Zeekはアラートを出さない。トラフィックを読み、プロトコルごとに整ったログを書く。アナリストが後で検索するのはこのログである。

```bash
# PCAPを処理すると、カレントディレクトリに.logファイルができる
zeek -C -r capture.pcap
ls
# conn.log  dns.log  http.log  ssl.log  files.log  weird.log ...
```

| ログファイル | 内容 |
|:---|:---|
| `conn.log` | すべての接続: IP、ポート、時間、バイト数 |
| `dns.log` | DNSクエリと応答 |
| `http.log` | メソッド、ホスト、URI、User-Agent、ステータス |
| `ssl.log` | TLSバージョン、SNI、証明書情報 |
| `files.log` | 通過したファイルとそのハッシュ |
| `weird.log` | プロトコル標準から外れた事象 |

`zeek-cut` で特定の列を取り出す。

```bash
# 最も長い接続
cat conn.log | zeek-cut id.orig_h id.resp_h id.resp_p duration | sort -k4 -rn | head

# 訪問されたHTTPホスト
cat http.log | zeek-cut host uri | sort | uniq -c | sort -rn | head
```

## 5. Suricata: シグネチャ型IDS

Suricataはトラフィックを何千ものルールと照合する。最も一般的な無料ルールセットはEmerging Threats Openである。

### 5.1 ルールの構造

```text
alert http any any -> any any (msg:"URI内のSQLiの可能性"; \
    http.uri; content:"UNION"; nocase; content:"SELECT"; nocase; \
    sid:1000001; rev:1;)
```

| 部分 | 意味 |
|:---|:---|
| `alert` | アクション: アラートを出す(IPSモードなら `drop`) |
| `http any any -> any any` | プロトコル、送信元、宛先 |
| `msg` | アラートに表示されるテキスト |
| `http.uri; content:"UNION"` | URIの中に `UNION` を探す |
| `nocase` | 大文字小文字を区別しない |
| `sid` | ルールの一意なID。自作ルールは1000000より大きい番号を使う |

### 5.2 PCAPに対して実行する

```bash
sudo suricata -r capture.pcap -S local.rules -l ./out
cat out/fast.log
# アラートはJSON形式でout/eve.jsonにも書かれる
jq 'select(.event_type=="alert") | .alert.signature' out/eve.json | sort | uniq -c
```

### 5.3 限界

シグネチャは既知のものしか捕まえられない。HTTPSの中身は暗号化されているので、SuricataにはSNI、証明書、JA3といったメタデータしか見えない。その隙間を埋めるのがZeekのログとスレットハンティング([LC-074](3.%20Threat%20Hunting%20%26%20Detection%20Engineering%20%28Sigma%2C%20YARA%2C%20ATT%26CK%29.md))である。

## 6. ネットワーク上に見える攻撃パターン

| パターン | 見え方 | 確認方法 |
|:---|:---|:---|
| ポートスキャン | 1つのIPが多数のポートにSYNを送り、ほとんどRSTが返る | `conn.log`: 1つの送信元から `REJ` や `S0` 状態が多数 |
| ブルートフォース | ポート22/3389/445への短い接続が何百回も | `conn.log` を送信元と宛先ポートで集計 |
| ビーコン | 同じIPへほぼ同じ間隔で接続 | 接続間の時間差を計算する。60秒のような一定間隔は怪しい |
| DNSトンネリング | 非常に長くランダムなサブドメイン、TXTレコードの多用 | `dns.log`: `query` が50文字を超える |
| 情報持ち出し | めったに使わないIPへの大きなアップロード | `conn.log`: `orig_bytes` が `resp_bytes` よりはるかに大きい |
| ARPスプーフィング | 1つのMACが多数のIPを名乗る | Wireshark: `arp.duplicate-address-detected`([LC-042](../../networking/ja/ARP%20%26%20Local%20Network%20Attacks.md)) |

ZeekでDNSトンネリングの候補を探す例:

```bash
cat dns.log | zeek-cut query | awk 'length($1) > 50' | head
```

## 7. 演習

### Task 1: 概念

1. サイズが最も小さく、最も長く保存できるネットワークデータは?
2. Zeekが出すのはアラートかログか?
3. SuricataがHTTPS内の攻撃を検知しにくいのはなぜか?
4. 1つのIPへ60秒ごとの接続が8時間続く。これはどのパターンか?

<details><summary>解答</summary>

1. フロー(NetFlow/IPFIX)
2. ログ。Zeekはアラート中心のツールではない。
3. 中身が暗号化されており、照合できるのはメタデータ(SNI、証明書、JA3)だけだから。
4. ビーコン。C2に接続するマルウェアの可能性が高い。

</details>

### Task 2: conn.logの分析

`conn.log` の一部(列: 時刻、送信元IP、宛先IP、ポート、orig_bytes、resp_bytes):

```text
10:00:00 10.0.0.23 185.199.10.5 443 320 1200
10:01:00 10.0.0.23 185.199.10.5 443 318 1200
10:02:00 10.0.0.23 185.199.10.5 443 321 1200
10:02:30 10.0.0.40 10.0.0.1 53 60 120
10:03:00 10.0.0.23 185.199.10.5 443 319 1200
10:05:12 10.0.0.31 203.0.113.80 443 734003200 4100
10:06:00 10.0.0.12 10.0.0.50 22 0 0
10:06:00 10.0.0.12 10.0.0.50 23 0 0
10:06:00 10.0.0.12 10.0.0.50 80 0 0
10:06:01 10.0.0.12 10.0.0.50 445 0 0
```

1. ビーコンを示しているホストは?
2. 情報を持ち出していそうなホストと、そのおおよそのデータ量は?
3. ポートスキャンをしているホストは?

<details><summary>解答</summary>

1. `10.0.0.23` から `185.199.10.5` へ。60秒ごとで、サイズもほぼ同じ。
2. `10.0.0.31` が `203.0.113.80` へ約700 MBを送り、受け取ったのは4 KBだけ。
3. `10.0.0.12` が `10.0.0.50` のポート22、23、80、445を1秒以内にデータなしで試している。

</details>

### Task 3: Suricataルールを書く

HTTPのUser-Agentに `sqlmap` が含まれるときにアラートを出すルールを書け。ローカルのDVWAに対してsqlmapを実行しながら自分で記録したPCAPで試すこと。

<details><summary>解答例</summary>

```text
alert http any any -> any any (msg:"sqlmapスキャナを検知"; \
    http.user_agent; content:"sqlmap"; nocase; sid:1000002; rev:1;)
```

</details>

```text
WIRESHARK
  ip.addr==X · http.request · dns.flags.response==0 · tls.handshake.extensions_server_name
  Statistics > Conversations · Follow TCP Stream · Export Objects > HTTP

ZEEK
  zeek -C -r file.pcap

SURICATA
  suricata -r file.pcap -S my.rules -l out/   →  out/fast.log, out/eve.json
  alert <proto> src port -> dst port (msg:"..."; content:"..."; sid:1000001; rev:1;)

パターン
  スキャン: 多数のポート、データなし · ビーコン: 一定間隔 · 持ち出し: orig_bytes >> resp_bytes
  DNSトンネル: 非常に長いクエリ
```

## 対応するレッドチームのレッスン

以下の攻撃は、それぞれ別のレッスンで攻撃者側の視点から扱っている。両方を並べて読むと、攻撃の手順から、どんな痕跡が残るかが見えてくる。

| レッスン | 攻撃者がすること | ここで探すもの |
|:---|:---|:---|
| [LC-059 Port Scanning & Network Enumeration (Nmap)](../../ethical-hacking/ja/2.%20Port%20Scanning%20%26%20Network%20Enumeration%20%28Nmap%29.md) | Nmapによるポートスキャン | 1つの送信元から多数のポートへの接続、半開きの接続（Zeekの`conn.log`で`S0`） |
| [LC-042 ARP & Local Network Attacks](../../networking/ja/ARP%20%26%20Local%20Network%20Attacks.md) | 中間者になるためのARPスプーフィング | 1つのMACが複数のIPに応答、gratuitous ARPの大量送信 |
| [LC-041 DNS & Domain Name System Security](../../networking/ja/DNS%20%26%20Domain%20Name%20System%20Security.md) | トンネリングを含むDNSの悪用 | `dns.log`の長くランダムなサブドメインと異常に多いクエリ数 |
| [LC-060 Metasploit Framework & Exploitation](../../ethical-hacking/ja/3.%20Metasploit%20Framework%20%26%20Exploitation.md) | エクスプロイトとMeterpreterセッション | 既知のペイロードに対するSuricataのアラート、4444番ポートへのコールバック |
| [LC-050 Server-Side Request Forgery (SSRF)](../../web/Vulnerabilities/ja/4.%20Server-Side%20Request%20Forgery%20%28SSRF%29.md) | 内部サービスへのSSRF | Webサーバーが突然`169.254.169.254`や内部アドレスと通信する |
