## 重要な用語

この教材でよく出てくる言葉である。

| 用語 | 意味 |
|:---|:---|
| ブルーチーム | 守る側のチーム。監視し、検知し、攻撃に対応する |
| SOC | Security Operations Center。企業のセキュリティを24時間監視するチーム |
| ログ | システムで起きたこと(誰が、いつ、どこからログインしたか)の自動記録 |
| SIEM | 多数のマシンのログを集めて一度に検索するソフトウェア(Splunk、Wazuh、Elasticなど) |
| アラート | 怪しい出来事が起きたときの自動警告 |
| トリアージ | アラートを深刻なものとそうでないものに振り分けること |
| 誤検知(false positive) | 調べてみると攻撃ではなかったアラート |
| IOC | Indicator of Compromise。悪性IP、マルウェアのハッシュ、怪しいドメインなど攻撃の痕跡 |
| インシデント対応 | すでに起きた攻撃を処理する手順 |

## 1. レッドチームとブルーチーム

一軒の家を想像してほしい。レッドチームは、弱点を見つけるために家の持ち主が雇った侵入役である。ブルーチームは警備員であり、防犯カメラであり、警報装置である。

| | レッドチーム | ブルーチーム |
|:---|:---|:---|
| 仕事 | 弱点を探す(許可を得て) | 攻撃を検知して止める |
| 主な問い | 「どこから入れるか」 | 「誰か入ったか。いつ、どこから」 |
| 代表的なツール | Nmap、Burp Suite | SIEM、EDR、Wireshark、ログ |
| 求人数 | 少なめ | はるかに多い |

セキュリティのキャリアをSOCアナリスト(L1)から始める人は多い。この教材は就職活動にも役立つ。

## 2. SOCとは何か

SOCは企業のセキュリティを途切れなく監視するチームで、たいてい24時間のシフト制で動く。流れはおおよそ次のとおりである。

```
           ┌─────────────────────────────────────┐
 Server ──►│                                     │
 Laptop ──►│   SIEM  (収集 + 検索 + アラート)     │──► Alert ──► L1アナリスト (トリアージ)
Firewall ─►│                                     │                   │
           └─────────────────────────────────────┘                   ▼
                                                        深刻? ──► L2/L3アナリスト (調査)
                                                                              │
                                                                              ▼
                                                                     インシデント対応
```

| 役割 | 日々の仕事 |
|:---|:---|
| L1アナリスト | 届いたアラートを見て、本物か誤検知かを判断する |
| L2アナリスト | さらに深く調べる。何が起き、影響はどこまで広がったか |
| L3アナリスト / スレットハンター | アラートを一度も鳴らさなかった攻撃を探す |
| 検知エンジニア | 新しい検知ルールを書く |

## 3. ログ、コンピュータの日記

誰かがログインしたり、プログラムを実行したり、Webサイトを開いたりするたびに、システムは1行の記録を書く。これがログである。ログがなければ、ブルーチームには調べる材料がない。

ログ1行で、いつ、どこで、何が、誰が、どこから、がだいたい分かる。

```
Oct 16 09:12:44 server1 sshd[2211]: Failed password for root from 203.0.113.50 port 51122 ssh2
└─── いつ ───┘ └ どこで┘ └ 何が ┘   └──── 何が起きたか ────────┘ └ 誰 ┘   └─── どこから ────┘
```

よく開くログ:

| ソース | 場所 / 名前 | 内容 |
|:---|:---|:---|
| Linuxログイン(Debian/Ubuntu) | `/var/log/auth.log` | SSHログイン、sudo、パスワード誤り |
| Linuxログイン(Fedora/RHEL) | `/var/log/secure` または `journalctl` | 同上 |
| Webサーバ | `/var/log/nginx/access.log`、`/var/log/apache2/access.log` | サイトへのすべてのリクエスト |
| Windows | イベントビューアーのセキュリティ | イベントID 4624(ログオン成功)、4625(ログオン失敗)、4688(新規プロセス) |
| ファイアウォール | 製品による | 許可またはブロックされた接続 |

WindowsのイベントID 4624、4625、4688はSOCの面接でよく聞かれるので、覚えておくとよい。

## 4. Linuxのログを手で読む

SIEMを使う前に、基本的なコマンドでログを読むことに慣れておこう。`grep`、`awk`、`sort`はLC-019で学んだ。

### 4.1 誰がログインに失敗したか

```bash
# Debian/Ubuntu
sudo grep "Failed password" /var/log/auth.log | tail

# Fedora/RHEL (systemd journal)
sudo journalctl -u sshd | grep "Failed password" | tail
```

### 4.2 どのIPが一番多く失敗したか

1つのIPが何百回も失敗しているなら、ほぼ確実にブルートフォースである。

```bash
sudo grep "Failed password" /var/log/auth.log \
  | grep -oE 'from [0-9.]+' \
  | sort | uniq -c | sort -rn | head
```

出力例:

```
    412 from 203.0.113.50     ← 412回失敗。ほぼ確実にブルートフォース
      3 from 192.168.1.10     ← たぶん自分の打ち間違い
```

### 4.3 そのIPは最終的に侵入できたか

何百回もの失敗は騒がしいが、すぐに対処すべきなのは同じIPからのログイン成功である。

```bash
sudo grep "Accepted" /var/log/auth.log | grep 203.0.113.50
```

何か出力されたら、攻撃者はすでに中にいる。上位のアナリストにエスカレーションする。

### 4.4 誰がsudoを使ったか

```bash
sudo grep "sudo:" /var/log/auth.log | grep COMMAND
```

### 4.5 Webのアクセスログを読む

```bash
# リクエスト数上位10のIP
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head

# 404を返したリクエスト(ファイルを探すスキャナであることが多い)
awk '$9 == 404 {print $1, $7}' /var/log/nginx/access.log | head
```

アクセスログに現れるスキャナや攻撃者の特徴:

| 見えるもの | おそらくの意味 |
|:---|:---|
| 1つのIPから1分間に何百もの404 | ディレクトリのブルートフォース(gobusterなど) |
| WordPressを使っていないのに `/wp-admin`、`/.env`、`/.git/` へのリクエスト | よくある穴を探すボット |
| User-Agentが `sqlmap`、`Nikto`、`Nmap` | 身元を隠さないスキャナ |
| URL中の妙な文字(`'`、`<script>`、`../`) | インジェクションの試み([LC-047](../../web/Vulnerabilities/ja/1.%20SQL%20Injection%20%28SQLi%29.md)、[LC-048](../../web/Vulnerabilities/ja/2.%20Cross-Site%20Scripting%20%28XSS%29.md)、LC-051参照) |

## 5. SIEM: すべてのログを一か所に

企業には何百台ものサーバがあることもあり、1台ずつ `grep` するのは現実的ではない。SIEMは全マシンのログを一か所に集める。そこで全マシンを一度に検索し、自動でアラートを出すルールを書き、1時間あたりのログイン失敗数のようなダッシュボードを作れる。

| SIEM | メモ |
|:---|:---|
| Wazuh | 無料のオープンソース。自宅ラボに最適 |
| Elastic (ELK) | 基本機能は無料で、広く使われている |
| Splunk | 企業で最も一般的。Free版あり(1日500 MB) |
| Microsoft Sentinel | Azure上のクラウドSIEM |

2つのSIEMで同じ検索をする例:

```text
Splunk:  index=linux "Failed password" | stats count by src_ip | sort -count
Elastic: event.outcome:failure AND event.category:authentication
```

考え方は4章の `grep | sort | uniq -c` パイプラインと同じである。手作業版が理解できていれば、SIEMでは構文を覚えるだけでよい。

## 6. アラート、トリアージ、誤検知

L1アナリストは1日に何百ものアラートを受け取ることがあり、どれを追うべきかを素早く決めなければならない。この振り分けをトリアージと呼ぶ。アラートごとに次を確認する。

1. 何がこのアラートを発生させたか。ルールを読む。
2. どのユーザーとマシンが関係しているか。本番サーバはインターンのノートPCより重要である。
3. これは普通のことか。管理者が午前3時に海外からログインするのは妙だが、午前9時にオフィスからなら普通である。
4. 攻撃は成功したか。ログイン失敗と成功では重みがまったく違う。
5. 前後に何があったか。ログイン後に `sudo`、ファイルのダウンロード、怪しい外向き通信はなかったか。

| トリアージ結果 | 意味 | 対応 |
|:---|:---|:---|
| True positive | 本物の攻撃 | L2またはIRチームへエスカレーション |
| False positive | 攻撃ではない。例: 社員がパスワードを忘れた | クローズし、理由を記録し、ルール改善を提案 |
| Benign true positive | 活動は実際にあったが正当なもの。例: 許可済みのペネトレーションテスト | クローズして記録 |

## 7. インシデント対応の4ステップ (NIST SP 800-61)

トリアージで本物の攻撃だと分かったら、次のサイクルに従う。

```
 1. 準備 ──► 2. 検知と分析 ──► 3. 封じ込め・根絶・復旧 ──► 4. 事後対応
    ▲                                                          │
    └──────────── 教訓を次の準備に活かす ◄──────────────────────┘
```

SSHブルートフォースが成功した場合の例:

| ステップ | やること |
|:---|:---|
| 1. 準備 | ログが有効、SIEMが導入済み、緊急連絡先リストがある |
| 2. 検知と分析 | アラート発生: 412回の失敗の後、203.0.113.50からログイン成功 |
| 3. 封じ込め | ファイアウォールでIPをブロック([LC-034](../../linux/ja/27.%20Firewall%20Setup.md))、侵害されたアカウントをロック、サーバを隔離 |
| 3. 根絶 | バックドアを探す: 新しいユーザー、妙なcronジョブ([LC-025](../../linux/ja/18.%20Task%20Scheduling.md))、`~/.ssh/authorized_keys` の見知らぬ鍵 |
| 3. 復旧 | パスワード変更、SSHのパスワードログインを無効化(鍵のみ)、必要ならバックアップから復元 |
| 4. 事後対応 | なぜrootがSSHでログインできたのかを調べ、設定を直し、新しいアラートルールを書く |

## 8. 演習

### Task 1: 概念

1. ログオン失敗のWindowsイベントIDは?
2. UbuntuでSSHログイン試行が記録されるログファイルは?
3. 「ブルートフォース」アラートの原因が、パスワードを忘れた社員だった。これは何か?
4. 攻撃者のIPをブロックするのはNISTの何番目のステップか?

<details><summary>解答</summary>

1. 4625
2. `/var/log/auth.log`
3. 誤検知(false positive)
4. ステップ3(封じ込め)

</details>

### Task 2: ログ分析

次のログを `practice.log` として保存し、`grep`、`awk`、`sort`、`uniq` で問いに答えよ。

```text
Oct 16 02:10:01 web1 sshd[901]: Failed password for root from 198.51.100.7 port 40001 ssh2
Oct 16 02:10:02 web1 sshd[902]: Failed password for root from 198.51.100.7 port 40002 ssh2
Oct 16 02:10:03 web1 sshd[903]: Failed password for admin from 198.51.100.7 port 40003 ssh2
Oct 16 02:10:04 web1 sshd[904]: Failed password for admin from 198.51.100.7 port 40004 ssh2
Oct 16 02:10:05 web1 sshd[905]: Failed password for budi from 198.51.100.7 port 40005 ssh2
Oct 16 02:10:09 web1 sshd[906]: Accepted password for budi from 198.51.100.7 port 40006 ssh2
Oct 16 02:11:30 web1 sudo:     budi : TTY=pts/0 ; PWD=/home/budi ; USER=root ; COMMAND=/usr/bin/cat /etc/shadow
Oct 16 09:00:12 web1 sshd[990]: Failed password for sari from 192.168.1.20 port 50100 ssh2
Oct 16 09:00:20 web1 sshd[991]: Accepted password for sari from 192.168.1.20 port 50101 ssh2
```

1. ブルートフォースをしているIPは?
2. そのIPは何回失敗したか?
3. 侵害されたアカウントはどれで、何時か?
4. 侵入後に攻撃者は何を実行し、なぜそれが危険か?
5. 09:00の `sari` の活動は怪しいか?

<details><summary>コマンドのヒント</summary>

```bash
grep "Failed" practice.log | grep -oE 'from [0-9.]+' | sort | uniq -c
grep "Accepted" practice.log
grep "COMMAND" practice.log
```

</details>

<details><summary>解答</summary>

1. `198.51.100.7`
2. 5回
3. `budi`、02:10:09
4. `cat /etc/shadow`。このファイルには全ユーザーのパスワードハッシュが入っているので、攻撃者は他のアカウントのクラックを狙っている可能性が高い。深刻なインシデントであり、エスカレーションが必要である。
5. あまり怪しくない。sariは一度打ち間違えた後に成功しており、社内のローカルIPから、勤務時間中である。おそらく正常である。

</details>

### Task 3: 自分のSOCラボを作る

1. DockerでWazuhをインストールする。公式ドキュメントの「Wazuh Docker deployment」に従う。
2. 別のLinux VMにWazuhエージェントを入れる。
3. 別のマシンから、自分のVMに間違ったパスワードで10回SSHしてみる。
4. Wazuhのダッシュボードで「sshd: authentication failed」アラートを探す。これが最初の検知である。

## 対応するレッドチームのレッスン

以下の攻撃は、それぞれ別のレッスンで攻撃者側の視点から扱っている。両方を並べて読むと、攻撃の手順から、どんな痕跡が残るかが見えてくる。

| レッスン | 攻撃者がすること | ここで探すもの |
|:---|:---|:---|
| [LC-058 Penetration Testing Methodology & Reconnaissance](../../ethical-hacking/ja/1.%20Penetration%20Testing%20Methodology%20%26%20Reconnaissance.md) | 偵察とディレクトリの総当たり | 1つのIPから数百のパスへのリクエスト、`access.log`での404の急増 |
| [LC-047 SQL Injection (SQLi)](../../web/Vulnerabilities/ja/1.%20SQL%20Injection%20%28SQLi%29.md) | URLパラメータからのSQLインジェクション | リクエストURL内の`'`、`UNION SELECT`、`OR 1=1` |
| [LC-048 Cross-Site Scripting (XSS)](../../web/Vulnerabilities/ja/2.%20Cross-Site%20Scripting%20%28XSS%29.md) | ページへのスクリプト注入 | パラメータ内の`<script>`、`onerror=`、`javascript:` |
| [LC-051 Command Injection & File Inclusion (LFI & RFI)](../../web/Vulnerabilities/ja/5.%20Command%20Injection%20%26%20File%20Inclusion%20%28LFI%20%26%20RFI%29.md) | コマンドインジェクションとファイルインクルージョン | パラメータ内の`;`、`|`、`../`、`/etc/passwd` |
| [LC-053 Authentication, Session & JWT Attacks](../../web/Vulnerabilities/ja/7.%20Authentication%2C%20Session%20%26%20JWT%20Attacks.md) | パスワード推測とクレデンシャルスタッフィング | 大量の`Failed password`や4625の後、同じIPから1回の成功 |
| [LC-061 Privilege Escalation & Post-Exploitation](../../ethical-hacking/ja/4.%20Privilege%20Escalation%20%26%20Post-Exploitation.md) | 侵入後の権限昇格 | `auth.log`の不審な`sudo`行、新しいアカウント、変更されたcronジョブ |
