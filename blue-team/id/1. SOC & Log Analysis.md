## Istilah penting

| Istilah | Artinya |
|:---|:---|
| Blue team | Tim yang bertahan: memantau, mendeteksi, dan merespons serangan |
| SOC | Security Operations Center, tim yang memantau keamanan perusahaan sepanjang hari |
| Log | Catatan otomatis tentang apa yang terjadi di sistem (siapa login, kapan, dari mana) |
| SIEM | Software yang mengumpulkan dan mencari log dari banyak mesin sekaligus (contoh: Splunk, Wazuh, Elastic) |
| Alert | Peringatan otomatis saat ada kejadian mencurigakan |
| Triage | Memilah alert, mana yang serius dan mana yang bukan apa-apa |
| False positive | Alert yang ternyata bukan serangan |
| IOC | Indicator of Compromise, jejak serangan seperti IP jahat, hash file malware, atau domain aneh |
| Incident response | Langkah-langkah menangani serangan yang sudah terjadi |

## 1. Red team vs blue team

Bayangkan sebuah rumah. Red team itu orang yang disewa pemilik rumah untuk mencoba membobolnya, supaya celahnya ketahuan. Blue team itu satpam, CCTV, dan alarmnya.

| | Red team | Blue team |
|:---|:---|:---|
| Tugas | Mencari celah (dengan izin) | Mendeteksi dan menghentikan serangan |
| Pertanyaan utama | "Bisa masuk lewat mana?" | "Ada yang masuk? Kapan? Lewat mana?" |
| Alat khas | Nmap, Burp Suite | SIEM, EDR, Wireshark, log |
| Lowongan kerja | Lebih sedikit | Jauh lebih banyak |

Banyak orang memulai karier keamanan sebagai SOC Analyst Level 1, jadi materi ini juga berguna saat cari kerja.

## 2. Apa itu SOC

SOC adalah tim yang memantau keamanan perusahaan terus-menerus, biasanya bergiliran 24 jam. Alurnya kira-kira begini:

```
           ┌─────────────────────────────────────┐
 Server ──►│                                     │
 Laptop ──►│   SIEM  (kumpulkan + cari + alert)  │──► Alert ──► Analis L1 (triage)
Firewall ─►│                                     │                   │
           └─────────────────────────────────────┘                   ▼
                                                        serius? ──► Analis L2/L3 (investigasi)
                                                                              │
                                                                              ▼
                                                                     Incident Response
```

| Peran | Kerjanya sehari-hari |
|:---|:---|
| Analis L1 | Melihat alert yang masuk, lalu memutuskan asli atau false positive |
| Analis L2 | Menyelidiki lebih dalam: apa yang terjadi dan seberapa luas dampaknya |
| Analis L3 / Threat Hunter | Mencari serangan yang tidak memicu alert sama sekali |
| Detection Engineer | Menulis aturan deteksi baru |

## 3. Log, catatan harian komputer

Setiap kali seseorang login, menjalankan program, atau membuka website, sistem menulis satu baris catatan. Catatan itu disebut log. Tanpa log, blue team tidak punya bahan untuk diselidiki.

Satu baris log biasanya sudah menjawab kapan, di mana, apa, siapa, dan dari mana:

```
Oct 16 09:12:44 server1 sshd[2211]: Failed password for root from 203.0.113.50 port 51122 ssh2
└── kapan ───┘ └ di mana┘ └ apa ─┘   └──── apa yang terjadi ────┘ └ siapa ┘   └─── dari mana ───┘
```

Log yang paling sering kamu buka:

| Sumber | Lokasi / nama | Isinya |
|:---|:---|:---|
| Login Linux (Debian/Ubuntu) | `/var/log/auth.log` | Login SSH, sudo, password salah |
| Login Linux (Fedora/RHEL) | `/var/log/secure` atau `journalctl` | Sama seperti di atas |
| Web server | `/var/log/nginx/access.log`, `/var/log/apache2/access.log` | Setiap request ke website |
| Windows | Event Viewer, bagian Security | Event ID 4624 (login sukses), 4625 (login gagal), 4688 (proses baru) |
| Firewall | Tergantung produk | Koneksi yang diizinkan atau diblokir |

Event ID Windows 4624, 4625, dan 4688 sering ditanyakan di interview SOC, jadi sebaiknya dihafal.

## 4. Membaca log Linux secara manual

Sebelum pakai SIEM, biasakan membaca log dengan perintah dasar. `grep`, `awk`, dan `sort` sudah kamu pelajari di [LC-019](../../linux/id/12.%20Filter%20Contents%20%E2%80%94%20Output%20Filtering%20%26%20Text%20Processing.md).

### 4.1 Siapa yang gagal login?

```bash
# Debian/Ubuntu
sudo grep "Failed password" /var/log/auth.log | tail

# Fedora/RHEL (systemd journal)
sudo journalctl -u sshd | grep "Failed password" | tail
```

### 4.2 IP mana yang paling sering gagal login?

Kalau satu IP gagal ratusan kali, kemungkinan besar itu brute force.

```bash
sudo grep "Failed password" /var/log/auth.log \
  | grep -oE 'from [0-9.]+' \
  | sort | uniq -c | sort -rn | head
```

Contoh hasil:

```
    412 from 203.0.113.50     ← 412 kali gagal, hampir pasti brute force
      3 from 192.168.1.10     ← mungkin kamu sendiri salah ketik
```

### 4.3 Apakah IP itu akhirnya berhasil masuk?

Ratusan percobaan gagal memang mengganggu, tapi yang perlu segera ditangani adalah login yang berhasil dari IP yang sama.

```bash
sudo grep "Accepted" /var/log/auth.log | grep 203.0.113.50
```

Kalau perintah ini mengeluarkan hasil, penyerang sudah masuk. Laporkan ke analis di atasmu.

### 4.4 Siapa yang memakai sudo?

```bash
sudo grep "sudo:" /var/log/auth.log | grep COMMAND
```

### 4.5 Membaca access log web

```bash
# 10 IP dengan request terbanyak
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head

# Request yang menghasilkan 404 (sering berasal dari scanner yang mencari file)
awk '$9 == 404 {print $1, $7}' /var/log/nginx/access.log | head
```

Ciri-ciri scanner atau penyerang di access log:

| Yang terlihat | Kemungkinan artinya |
|:---|:---|
| Ratusan 404 dalam satu menit dari satu IP | Directory brute force (misalnya gobuster) |
| Request ke `/wp-admin`, `/.env`, `/.git/` padahal kamu tidak pakai WordPress | Bot otomatis mencari celah umum |
| User-Agent `sqlmap`, `Nikto`, `Nmap` | Scanner yang tidak menyamarkan diri |
| Karakter aneh di URL (`'`, `<script>`, `../`) | Percobaan injeksi (lihat [LC-047](../../web/Vulnerabilities/id/1.%20SQL%20Injection%20%28SQLi%29.md), [LC-048](../../web/Vulnerabilities/id/2.%20Cross-Site%20Scripting%20%28XSS%29.md), [LC-051](../../web/Vulnerabilities/id/5.%20Command%20Injection%20%26%20File%20Inclusion%20%28LFI%20%26%20RFI%29.md)) |

## 5. SIEM: mengumpulkan semua log di satu tempat

Perusahaan bisa punya ratusan server, dan menjalankan `grep` di tiap server satu per satu jelas tidak mungkin. SIEM menarik log dari semua mesin ke satu tempat. Di sana kamu bisa mencari di semua mesin sekaligus, membuat aturan yang otomatis memunculkan alert, dan membuat dashboard seperti grafik login gagal per jam.

| SIEM | Catatan |
|:---|:---|
| Wazuh | Gratis dan open source, paling cocok untuk lab di rumah |
| Elastic (ELK) | Versi dasarnya gratis, banyak dipakai |
| Splunk | Paling umum di perusahaan, ada versi Free (500 MB/hari) |
| Microsoft Sentinel | SIEM cloud di Azure |

Contoh pencarian yang sama di dua SIEM:

```text
Splunk:  index=linux "Failed password" | stats count by src_ip | sort -count
Elastic: event.outcome:failure AND event.category:authentication
```

Logikanya sama dengan pipeline `grep | sort | uniq -c` di bagian 4. Kalau versi manualnya sudah paham, di SIEM kamu tinggal belajar sintaksnya.

## 6. Alert, triage, dan false positive

Analis L1 bisa menerima ratusan alert sehari, jadi harus cepat memutuskan mana yang perlu ditindaklanjuti. Proses memilah ini disebut triage. Untuk setiap alert, tanyakan:

1. Apa yang memicu alert ini? Baca aturannya.
2. User dan mesin mana yang terlibat? Server produksi lebih kritis daripada laptop anak magang.
3. Apakah ini normal? Admin login jam 3 pagi dari luar negeri itu aneh, sedangkan login dari kantor jam 9 pagi biasa saja.
4. Apakah serangannya berhasil? Login gagal dan login sukses sangat berbeda bobotnya.
5. Apa yang terjadi sebelum dan sesudahnya? Setelah login, apakah ada `sudo`, download file, atau koneksi keluar yang aneh?

| Hasil triage | Artinya | Tindakan |
|:---|:---|:---|
| True positive | Memang serangan | Eskalasi ke L2 atau tim IR |
| False positive | Bukan serangan, misalnya karyawan lupa password | Tutup, catat alasannya, usulkan perbaikan aturan |
| Benign true positive | Aktivitasnya memang terjadi tapi sah, misalnya pentest yang sudah diizinkan | Tutup dan catat |

## 7. Incident response dalam 4 langkah (NIST SP 800-61)

Kalau hasil triage menunjukkan serangan sungguhan, ikuti siklus ini:

```
 1. Persiapan ──► 2. Deteksi & Analisis ──► 3. Penahanan, Pembersihan, Pemulihan ──► 4. Evaluasi
      ▲                                                                                  │
      └──────────────────────── pelajaran dipakai untuk persiapan berikutnya ◄───────────┘
```

Contohnya untuk kasus brute force SSH yang berhasil masuk:

| Langkah | Yang dilakukan |
|:---|:---|
| 1. Persiapan | Log aktif, SIEM terpasang, ada daftar kontak darurat |
| 2. Deteksi & analisis | Muncul alert: login sukses dari 203.0.113.50 setelah 412 kali gagal |
| 3. Penahanan | Blokir IP di firewall ([LC-034](../../linux/id/27.%20Firewall%20Setup.md)), kunci akun yang dibobol, isolasi server |
| 3. Pembersihan | Cari backdoor: user baru, cron job aneh ([LC-025](../../linux/id/18.%20Task%20Scheduling.md)), SSH key asing di `~/.ssh/authorized_keys` |
| 3. Pemulihan | Ganti password, matikan login SSH pakai password (pakai key saja), pulihkan dari backup kalau perlu |
| 4. Evaluasi | Cari tahu kenapa root boleh login lewat SSH, perbaiki konfigurasinya, lalu buat aturan alert baru |

### Task 2: analisis log

Simpan potongan log di bawah sebagai `latihan.log`, lalu jawab soalnya pakai `grep`, `awk`, `sort`, dan `uniq`.

```text
Oct 16 02:10:01 web1 sshd[901]: Failed password for root from 198.51.100.7 port 40001 ssh2
Oct 16 02:10:02 web1 sshd[902]: Failed password for root from 198.51.100.7 port 40002 ssh2
Oct 16 02:10:03 web1 sshd[903]: Failed password for admin from 198.51.100.7 port 40003 ssh2
Oct 16 02:10:04 web1 sshd[904]: Failed password for admin from 198.51.100.7 port 40004 ssh2
Oct 16 02:10:05 web1 sshd[905]: Failed password for budi from 198.51.100.7 port 40005 ssh2
Oct 16 02:10:09 web1 sshd[906]: Accepted password for budi from 198.51.100.7 port 40006 ssh2
Oct 16 02:11:30 web1 sudo:     budi : TTY=pts/0 ; PWD=/home/budi ; USER=root ; COMMAND=/usr/bin/cat /etc/shadow
Oct 16 09:00:12 web1 sshd[990]: Failed password for sari from 192.168.1.20 port 50100 ssh2
Oct 16 09:00:20 web1 sshd[991]: Accepted password for sari from 192.168.1.20 port 50101 ssh2
```

1. IP mana yang melakukan brute force?
2. Berapa kali IP itu gagal login?
3. Akun apa yang berhasil dibobol, dan jam berapa?
4. Perintah apa yang dijalankan penyerang setelah masuk, dan kenapa itu berbahaya?
5. Apakah kejadian `sari` jam 09:00 mencurigakan?

<details><summary>Petunjuk perintah</summary>

```bash
grep "Failed" latihan.log | grep -oE 'from [0-9.]+' | sort | uniq -c
grep "Accepted" latihan.log
grep "COMMAND" latihan.log
```

</details>

<details><summary>Kunci jawaban</summary>

1. `198.51.100.7`
2. 5 kali
3. `budi`, jam 02:10:09
4. `cat /etc/shadow`. File itu berisi hash password semua user, jadi penyerang kemungkinan ingin meng-crack password akun lain. Ini insiden serius dan harus dieskalasi.
5. Tidak terlalu. Sari salah ketik sekali lalu berhasil, dari IP lokal kantor, di jam kerja. Kemungkinan besar normal.

</details>

### Task 3: bangun lab SOC sendiri

1. Install Wazuh pakai Docker. Ikuti panduan "Wazuh Docker deployment" di dokumentasi resminya.
2. Pasang Wazuh agent di VM Linux lain.
3. Dari mesin lain, coba login SSH ke VM milikmu sendiri dengan password salah sebanyak 10 kali.
4. Buka dashboard Wazuh dan cari alert "sshd: authentication failed". Itu deteksi pertamamu.
